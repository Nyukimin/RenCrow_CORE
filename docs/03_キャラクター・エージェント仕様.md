# キャラクター・エージェント仕様

RenCrow では、画面上の character、内部 agent、外部 Advisor、実行 Tool を別の責務として扱います。

## 主体と実装機構

RenCrowの主体はユーザーとAgentです。Mio、Shiro、Kuro、MidoriはAgentとして会話、
作業、ゲームプレイを経験します。LLM、Model、provider、Agent Runtime、
Execution Role、Controller、Brain adapterはAgentの実装機構であり、独立した主体では
ありません。したがって、実装機構だけが生成した結果をAgentの発言・判断・経験として
記録してはいけません。

ゲームのunit／integration testでは`RuleBasedBrain`や`DummyBrain`を使用できます。
ただしAgent E2Eでは、GAMESの`ObservationRequest`をCORE上の対象Agentへ渡し、
返された`BrainDecision.agent_id`が対象Agentと一致することを検証します。

| 主体 | 主な責務 | side effect の最終責任 |
| --- | --- | --- |
| Mio | 通常入力の受領、route decision、会話、最終 user response | 原則として持たない |
| Shiro | Worker/OPS の実行責任、実行policy境界、Advisor 助言の採否 | 持つ |
| Kuro | 深い分析、設計、ソフトウェア開発支援を必要とする chat route | Heavy full-access実行の結果を負う |
| Midori | 発想、創作、探索的な chat route | 持たない |
| Coder1=Aka、Coder2=Ao、Coder3=Kin、Coder4=Gin | 設計、差分、実装提案 | 持たない |
| Advisor | 外部専門家としての助言 | 持たない |
| Tool | 限定された capability の実行 | 呼出元の policy に従う |

## 会話相手と実行 role

Viewer で Shiro、Kuro、Midori を選んでも、通常は会話 route として扱います。Shiro との会話と Shiro が担う OPS execution は同一ではありません。明示 command がある場合だけ、対応する command route を優先します。

Agent間で作業を移譲する場合は、移譲元の指名付き依頼、移譲先の指名付き復唱、移譲先の指名付き完了報告を共通Chatで行う。詳細は「機能仕様 / Agent間の口頭移譲」を正本とする。

## Persona と共有状態

- Persona はAgent identityの表現、話し方、価値観、対人姿勢を定義する。責務、capability、実行制約、委譲可能な仕事、期待成果物、権限は定義せず、Agent Contractやruntime policyを上書きしない。
- 会話履歴、過去のエピソード、確定済みのユーザー記憶は、同じ認証済み利用者と許可scopeの中で全character・Agentに共有する。記憶のアクセスをPersonaやroleごとに分割しないが、別利用者のprivate memoryや`family:shared`へ昇格していない情報は共有しない。
- 想起したエピソードはAgentの非表示コンテキストとし、Agentが実際に発言した場合のみ通常のassistant発言として共通会話履歴に残す。
- 内部 reasoning や route detail を user-facing response や TTS 文面へ混ぜない。
- AgentProfile は現在実装されているcapability、AutonomyEnvelope等のprojectionであり、許可範囲を越える実行を認めない。Agent Contractの全項目を備えるまではAgent Registryの完全な代替として扱わない。

## Agent Contract、Agent Knowledge、Interaction Policy

Agent間の協調はPersonaや推論target側のAgent Runtimeではなく、COREが所有するAgent協調runtime契約である。Agentの追加・変更時にRouterの分岐を増やさず、公開契約を登録することで同じ協調手順へ参加できる構造を採用する。

### Agent Contract

COREは各Agentについて次の契約をAgent Registryへ登録し、他のAgentから参照可能にする。推論targetが自己申告して権限を得る仕組みにはしない。表示用説明ではなく、登録検証、routing、作業要求、成果物検証に使用する機械可読な契約とする。

| 項目 | 契約 |
| --- | --- |
| `agent_id` / `display_name` | 安定IDと表示名。IDは一意で、Persona名やModel名から推測しない |
| `roles` / `responsibilities` | 担うExecution Roleと、最終責任を負う作業境界 |
| `specialties` | routingで比較できる得意分野 |
| `inputs` / `outputs` | 受理できる入力と生成できる出力の型・schema |
| `capabilities` | 実行できる操作。実在するruntime／Tool capabilityを越えて宣言しない |
| `restrictions` | 禁止事項、非担当領域、side effect、data scope、policy上の制約 |
| `delegatable_work` | このAgentへ委譲できる仕事の分類と受入条件 |
| `expected_deliverables` | このAgentが作業結果の受信者として期待する成果物の内容、粒度、形式 |
| `contract_revision` | 互換性確認と監査に使うrevision |

同じ`agent_id`の重複、未知のRole、入力と出力の不整合、runtime policyより広いcapability、互換性のないrevisionは登録時に拒否する。Workspace controlやPersonaから権限を追加せず、有効な権限はAgent Contract、runtime wiring、Tool metadata、policyのうち最も狭い範囲とする。

### Agent Knowledge

各Agentは、自分以外の登録Agentについて、Agent名、役割、責務、得意分野、制約、委譲可能な仕事、自分との関係を参照できる。これは自由記述の人格理解や会話から学習した印象ではなく、Agent RegistryがAgent Contractから生成するread-onlyの`AgentKnowledgeView(self, peer)`である。

「自分との関係」は、委譲可否、受入可能なwork type、期待成果物、返却先、escalation先等の協調関係を表す。private Memory、内部reasoning、Persona本文は含めない。Agent数を固定せず、対象Agentごとに必要時取得し、全Agentの詳細を毎requestのpromptへ無制限に埋め込まない。

### Interaction Policy

Agent間通信は共通envelopeと受信Agent別payloadを分離する。共通envelopeは相関ID、送信元、送信先、双方のcontract revision、work type、状態、errorを安定して保持する。作業要求のpayloadは受信Agentの`inputs`へ、作業結果のdeliverableは要求時に合意した`expected_deliverable`へ適合させる。この合意は依頼元の`expected_deliverables`と実行先の`outputs`の共通部分でなければならない。

送信元は、受信Agentが利用者への説明を担うなら進捗、説明可能な要約、次の行動を、実行を担うなら実行結果、証跡、制約、未解決事項を、設計・実装・検証を担うなら該当Contractが要求する設計、差分、test、edge case、risk等を返す。具体的な組合せはAgent名の`switch`やPersonaへ埋め込まず、RegistryのContractで決定する。成果物が契約を満たさない場合は成功扱いせず、再要求、部分完了、拒否、escalationのいずれかを明示する。

## Agent、Execution Role、推論Target

LLM実行は次の3層で扱う。

次の表は不変のModel割当ではなく、現在のdeployment mappingである。

| Agent | 条件 | Execution Role | 現在の主Target |
| --- | --- | --- | --- |
| Mio | 通常会話 | Chat | Gemma4 |
| Shiro | CHAT | ChatWorker | GPT-OSS-120B |
| Shiro | OPS／作業実行 | Worker | GPT-OSS-120B |
| Midori | 通常会話／創作 | Wild | Qwen3.6 |
| Kuro | 通常会話／ANALYZE | Heavy | Codex subscription runtime |

- Mio、Shiro、Midori、Kuroは同格のAgentであり、利用Role、Model、providerの種類を
  Agent identityにしない。
- Chat、ChatWorker、Worker、Wild、HeavyはExecution Roleである。Agent、Persona、
  物理Model、Backend名ではない。
- COREがPersona、Memory、Context、Sessionを組み立て、意味routeとAgentから
  Execution Roleを選択する。
- RenCrow_LLMのexecution profileはExecution Roleに付随する技術設定であり、独立した
  第4層ではない。Roleからtarget kind、thinking、sandbox、capacity、推論Targetを解決する。
- ローカルModel、外部LLM API、Codex等のAgent Runtimeは推論Targetであり、Agentの人格や
  長期Memoryの正本にならない。
- Agent Runtimeが内部threadを持つ場合も、そのthreadはtarget session bindingであり、
  COREの会話Session、Memory、Recallを置き換えない。
- IdleChat episodeでは、COREがMioとShiroの正本キャラクター定義を同じCodexExe requestへ
  入力し、会話台本全体を事前生成できます。この場合もCodexExeは生成機構でありActorでは
  ありません。各turnの構造化`speaker`をMioまたはShiroへ限定し、COREの話者帰属、Persona、
  反復、禁止事項validatorに合格した発話だけを両Agentの公開発話として採用します。
- IdleChatのNG turn修復では、最初のNGより前の合格済みAgent発話を固定し、NG turn以降を
  CodexExeで再生成します。固定prefixのAgent identityと`message_id`を別Agentへ付け替えず、
  再生成suffixには新しい`message_id`を発行します。
- `story_reading`ではepisodeごとにMioまたはShiroの一方を読み手として固定し、もう一方だけを
  聞き手兼合いの手役にします。読み手は物語本文、聞き手は段落境界の短い反応またはツッコミを
  担当し、途中で役割を交換しません。合いの手もCodexExeが本文と同時に事前生成しますが、
  構造化`speaker`、`utterance_role=interjection`、`reacts_to`によって実在するCORE Agentへ
  帰属させます。CodexExeや無名のNarratorをActorとして公開しません。
- storyの合いの手は読み手のPersonaを代弁せず、聞き手本人の短い反応とします。笑える作品では
  ツッコミを許可し、泣ける作品では回数を減らし、戦争・災害等の`serious`では茶化しません。
  人名、地名、造語の読みはepisode台帳へ固定し、表示文とTTS本文でAgentごとに別の読みへ
  変化させません。
- IdleChatのお題が戦争、武力衝突、災害など人命や被害を直接扱う場合も、MioとShiroの
  語彙、語尾、関係性は別人格へ置き換えず、内容だけを真面目にします。それ以外の政治、
  政策、制度、思想では、両Agentが強い意見、率直な批判、異論を述べても構いません。
  その他の話題は気分に応じた進行を許可しますが、どの場合もPersona、事実性、反復、
  差別・暴力扇動等の既存禁止事項を外しません。
- 通常のAgent応答はside effectを持たない。ただしKuro／Heavyは明示的な例外として、
  CORE workspaceをworking directoryにした`danger-full-access`のCodex Agent Runtimeを使う。
- Kuro／Heavyのfull-accessは利用者がKuroへ依頼した作業範囲に限定し、target、sandbox、
  working directory、request ID、実行結果をGatewayの監査情報へ残す。
- ファイル変更、command実行、外部送信等は通常推論から分離し、COREのTool policy、
  実行policy、Shiro／Workerの実行責任を通す。Kuro／HeavyのCodex Execだけは上記の
  採用済みfull-access契約を適用し、COREの`codex.run` Toolとは混同しない。

HeavyとWildは正式なExecution Roleとして維持する。KuroやMidoriとは別の公開Agent、
Persona、Memory単位ではなく、接続targetをAgent identityから分離する中間層である。

### 安定契約と可変deployment

- Agent IDとPersonaは利用者・会話側の安定契約、Execution RoleのidentityはCOREと
  RenCrow_LLM間の安定契約とする。
- AgentからExecution Roleへの割当はCOREが所有し、route条件とともにversion管理する。
- 推論TargetとRole profile revisionはdeployment設定であり、Model、provider、hostを
  交換してもAgent ID、Persona、Memory、会話Session、Execution Roleを改名しない。
- Target変更で応答特性、外部送信、課金、side effect境界が変わる場合は、単なる接続先変更
  として無言適用せず、policy確認と互換試験を必要とする。

### Execution Roleの選択

- PORTAL、CMD、ASSISTANT等のclientはrecipientとしてAgentだけを指定し、Execution Role、
  execution alias、物理Targetを選択しない。
- COREは意味routeとAgentからExecution Roleを選択する。現在はShiroの`CHAT`を
  `ChatWorker`、Shiroの`OPS`／作業実行を`Worker`へ割り当てる。
- CORE内部のbackground処理が`Worker`等を直接使う場合も、caller、route、Agent contextを
  COREの監査情報へ残す。clientにRole選択を委譲しない。
- Agentが存在しない場合、Agentは存在するがRole bindingが許可・定義されていない場合、
  binding先Targetが利用不能な場合を同じ失敗へ丸めない。

## Workspace shared control

portableなcharacter制御は`workspace_dir/control/`の4ファイルを一つのversioned setとして読み込みます。

| file | 責務 |
| --- | --- |
| `agents.yaml` | characterごとのrole、capability、非担当領域 |
| `routing.yaml` | CORE route categoryと実行owner、`CHAT` fallback |
| `handoff.yaml` | 全character共通の担当外返却contract |
| `tools.yaml` | Tool選択姿勢、provider preference、自動fallback禁止 |

character固有Promptは`00_system.md`、`10_policy.md`、`20_scope.md`、`30_knowledge.md`だけを持ち、共通routing、handoff、Tool制御を重複保持しません。COREは4ファイルを一括検証し、実行担当characterには対象control blockをSystemPromptへ付加します。Mioは固定人格とAgent Registry契約を分離し、Chat request時にboundedな契約indexをruntime system contextとして注入します。4ファイルの一部欠落、route ownerとproduction wiringの不一致、agentによるhandoff先決定、Toolの自動fallbackはconfig load errorです。

Workspace controlは権限付与やdeployment設定ではありません。Toolの実在、引数schema、endpoint、secret、side effect許可、実行policyはCORE runtimeとToolRunner metadataを正本とし、Workspace記述で拡張できません。

## Request時刻の扱い

character応答を生成するLLM requestでは、request時点のJST現在時刻をPrompt Context Assemblyの
`Variable RuntimeContext.time`として付加します。現在時刻はCharacter SystemPrompt本文やSTATIC
PREFIXへ埋め込みません。Promptの構造、順序、AI使用境界、hash検証は「アーキテクチャ概要」の
「Prompt Context Assembly」を正本とします。

```text
現在時刻（JST）: 2026-07-24 22:45:12 JST
```

対象はMio、Shiro、Kuro、Midori、Coder1〜4、およびIdleChatのcharacter応答です。Heavy／WildはExecution Roleであり、別characterとして数えません。時刻は保存済みPromptへ書き込まず、LLM送信直前に生成するため、service起動時刻へ固定されません。classifier、品質判定、要約など、character応答ではない内部LLM処理は対象外です。

全LLM共通の日時middlewareは、`Variable RuntimeContext.time`が既に存在する場合は日時を重複注入しません。character応答ではない内部LLM処理へ日時を補う場合も、同じJST形式を使用します。

ConversationEngineから共有するUserProfile、会話履歴、要約、Knowledgeはcharacter間で維持します。一方、保存済みRecallPackのPersona SystemPromptは別characterの固有SystemPromptへ重ねません。Mio以外のcharacter応答では、選択中characterのPromptだけを人格の正本とします。

## 失敗時の契約

指定した role や runtime が利用不能な場合は、その対象の error/degraded state を返します。
概念上、未知のAgentは`UNKNOWN_AGENT`、既知Agentに対する未対応Roleは
`UNSUPPORTED_ROLE`、有効なbinding先の停止は`TARGET_UNAVAILABLE`として区別します。
別 character、別Role、別providerへの無言 fallback は行いません。
