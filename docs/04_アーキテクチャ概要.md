画像生成経路は`CORE -> RenCrow_Image -> ForgeNeo / Z-Image`とする。
RenCrow_Imageは描画用インターフェースの正本であり、backend endpoint、workflow、
model、LoRA、生成parameterを所有する。CORE ConfigはRenCrow_Imageへの接続を持つ。

例外として、Mio、Shiro、Midori、Kuroが文章生成工程の一部としてCodexExe経由の
ImageGenを利用することは許可する。この例外は通常の画像生成routeへ適用せず、
COREから画像生成backendへ直接接続する根拠にしない。

別の狭い例外として、IdleChat Topic Stock ProducerはShiro帰属の1ワード／2ワード
候補生成とJudge、Forecastのキーワード抽出、候補生成、JudgeをCodexExeで実行できます。
IdleChat Episode ProducerはCORE正本の
Mio／Shiroキャラクター定義を同じCodexExe requestへ入力して完成会話台本を生成できます。これらのCodexExe profileは
`read-only`、`ephemeral`、side effect禁止とし、Kuro／Heavyの`danger-full-access`、通常Chat、
COREの汎用`codex.run` Toolへ適用しません。CodexExeはActorではなく、COREが構造化speakerと
validatorを通してMio／Shiroへ帰属させた合格発話だけを公開します。

画像・動画認識経路は
`Client -> CORE -> RenCrow_Vision -> Wild backend -> RenCrow_Vision -> CORE`
とする。COREはraw mediaの受付、保存、Vision requestの相関、結果の利用者応答または
Agent contextへの接続を所有する。RenCrow_Visionはmedia検証、動画frame sampling、
Wild呼び出し、結果正規化を所有する。

RenCrow_Visionは認識backendとの通信contractを所有する。COREの通常Agent requestと
Vision内部requestは混同しない。CORE ConfigはRenCrow_Visionのbase URLだけを持ち、
認識backendのendpoint、model、media変換parameterを持たない。

RenCrow_Visionはrecipient、Agent、会話routeを選択せず、Wildの解析結果をCOREへ返す。
COREが後段Agentへ解析結果を渡す場合は、raw mediaではなく正規化済みtextと必要最小限の
metadataだけを渡す。

STT経路は`Viewer -> CORE /stt -> RenCrow_STT Go Gateway -> external STT target`とする。
ViewerはCORE同一originのWebSocketへ音声を送り、COREはRenCrow_STTの
`POST /v1/audio/transcriptions`だけを呼び出す。CORE ConfigはRenCrow_STTの
Gateway base URL、timeout、CORE側の入力queue／debugだけを持つ。認識engine、model、
language、target URL、stream方式はRenCrow_STTと外部targetが所有し、COREへ複製しない。
COREはGatewayのHTTP URLから`/ws/transcribe`等の外部WebSocket endpointを推定・接続しない。
ViewerのWebSocket frameはCOREが受付・WAV正規化し、同じRenCrow_STT HTTP provider契約へ渡す。
production wiring testは`buildSTTRuntime`から`/stt`を開き、実際に
`POST /v1/audio/transcriptions`が呼ばれてfinal eventが返ることを強制する。

TTS経路は`CORE -> RenCrow_TTS Go Gateway -> RenCrow_Irodori_TTS`とする。
COREはGatewayの公開APIだけを参照し、Irodori固有のmodel、reference音声、SEED、
推論parameterを設定または所有しない。COREの設定はGateway base URL、timeout、
既定voice、再生方法、Gateway所有tokenへのfile referenceに限定する。非loopbackの合成requestは
COREがowner Bearer tokenを付与し、Gatewayが同期検証する。token本体はConfig、log、Evidenceへ
複製せず、Irodoriのtarget credentialとも共用しない。合成成功responseは
`gateway_service: "tts-gateway"`を必須とし、Gatewayが返す
`/audio/{target}/{token}`相対pathから音声を取得する。

LLM経路は`CMD/PORTAL -> CORE Agent -> Execution Role -> RenCrow LLM Gateway -> RenCrow LLM Runtime -> Backend -> Model`とする。COREはCHAT/OPS/CODE等の意味route、Agent、Execution Role、外部providerへ入力を送信してよいかを決める。RenCrow LLM GatewayはRoleに付随するexecution profileからRuntimeを解決し、RenCrow LLM RuntimeがBackendとModelを解決する。execution profileはRoleのtarget kind、thinking、sandbox、capacity、Runtime設定であり、独立した第4層ではない。

作業委譲経路（Status: source一部実装・runtime acceptance未成立）は`CORE Shiro -> nativeharnessclient -> rencrow-harness serve --stdio -> RenCrow LLM Gateway -> RenCrow LLM Runtime -> Backend -> Model`とする。Harness source moduleはCOREの`go.mod`で固定され、COREにはclient／orchestrator source、accepted OPS input store/read owner境界、server設定でnative profileを選んだ通常Agent OPSのreceipt→canonical Task／first Run→Shiro route sourceがあります。runtime試験97件は全件`not_run`であり、Harnessとの実通信、再起動後のruntime運用受入、End-to-end receiptは未確認です。COREは親Task／Run／委譲Actionと成果の採用を所有し、RenCrow_Harnessが委譲された子Task、Run、Session、Tool、checkpointを所有する。人が`rencrow-harness`を直接使う経路はCOREを経由しない。この経路を選択していない作業は、Kuro／Heavy、`codex.run`、CodexExe、既存のShiro作業経路を含めて現行どおりとする。詳細は[RenCrow_Harness委譲境界](#rencrow_harness委譲境界)を正本とする。

現在のdeployment mappingは`Mio -> Chat -> Gemma4`、`Shiro CHAT -> ChatWorker -> GPT-OSS-120B`、
`Shiro OPS -> Worker -> GPT-OSS-120B`、`Midori -> Wild -> Qwen3.8-27B（Magnitude、M5 Max）`、
`Kuro -> Heavy -> Codex subscription Agent Runtime`とする。

Agent IDとExecution Role identityは安定contractとして維持し、Runtime、Backend、Modelは
Role profile revisionで交換できるdeployment設定とする。これらの変更はAgent、Persona、
Memory、会話Sessionの移動ではない。clientはAgentだけを選択し、COREがrouteからRoleを
選び、RenCrow LLM GatewayがRoleからRuntimeを、RuntimeがBackendとModelを解決する。

KuroはMio、Shiro、Midoriと同格のAgentであり、Codexや`codex exec`そのものではない。
HeavyはKuroとCodexの間に置く正式なExecution Roleであり、Agent、Persona、物理Modelではない。
Heavyの現行Role profileはCodex Agent Runtimeを`danger-full-access`で実行し、CORE workspaceを
working directoryとする。GatewayはKuro／Heavy bindingのRole profileと実targetの双方に
`danger-full-access`を必須とし、異なる設定を起動時に拒否する。COREの`codex.run` Toolは
独立した限定Tool contractであり、そのsandbox制限を通常Kuro経路へ流用しない。

COREのprovider policyは`Chat`をNO-Think、`ChatWorker`をreasoning lowへ固定し、
`Worker`には強制しない。この制御はAgent実装より内側のprovider境界に置き、IdleChatや
判断用のChatWorker呼び出しも同じprovider境界を通る。Gateway障害は同じrouteの
終端errorとして観測する。

## 標準Go配布境界

この節を、RenCrowの標準runtime、OS portability、外部system、外部compute、optional sidecar、
CUDA用WSLの最上位製品規約とします。RenCrow_CORE、EcoSystem、すべての現行／planned module、
installer、Config、運用script、testはこの規約に従います。module固有文書は内部実装を補足できますが、
この境界を再定義または弱体化しません。

RenCrowは、可能な限りGoだけで動かします。標準配布はnative Go binary、設定、必要な静的assetで
構成し、Ubuntu、Windows、macOSで同じmodule contractを提供します。browser JavaScriptは
利用者のbrowserで実行するため、Node.js runtime依存とは扱いません。標準profileの起動条件へ
Python、Node.js、Docker、WSL、外部database、message queue、vector storeを追加しません。
永続化が必要な標準機能は、Go process内またはGoから直接扱えるOS共通の組み込みstoreを優先します。

ここでいう外部systemは、RenCrowのGo process外で別に導入、起動、監視するbackend、engine、
database、queue、search service、browser automation、data collector、Model／GPU runtime等です。
外部systemを採用できるのは、Goだけでは目的を合理的に達成できない理由があり、次の条件をすべて
満たす場合に限ります。

- 所有moduleの公開contractの外側へ隔離し、CORE、PORTAL、CMD、他moduleから物理実装へ直結しない。
- Ubuntu、Windows、macOSのすべてで、同じprotocol、Config schema、health／readiness、結果、
  error code、`disabled`／`unavailable`の意味を提供する。
- 物理backend、起動方法、supervisor、pathはOSごとに異なってよいが、その差をmodule adapterと
  installerの内側で吸収する。
- 未配置、未設定、未readyのときは対象capabilityだけを明示的に`disabled`または`unavailable`とし、
  COREと無関係なGo capabilityを停止させない。fake成功、暗黙fallback、別routeへの迂回を行わない。
- 三OSで同等に提供できないsystemは標準依存にせず、対象OSと制約を明示したoptional external
  compute／development toolとして隔離する。

この規約の例外は、CORE正本とmachine-readable deployment policyに対象module、理由、対象OS、
影響するcapability、失敗時挙動、終了または再評価条件が定義され、起動時検証を通る場合だけ有効です。
runtime requestやAgent判断から例外を新設せず、未定義の構成は同期的に`blocked`とします。

| 分類 | 標準installer | OS要件 | 未配置時の扱い |
| --- | --- | --- | --- |
| 標準Go runtime | 同梱 | Ubuntu／Windows／macOS native | required componentの起動失敗 |
| optional Go module／sidecar | 利用者選択時だけ同梱 | 三OSで同じ公開contract | `disabled`または`unavailable` |
| 外部compute | 同梱しない | 三OSで同じmodule-facing contract。物理実装差は許容 | 対象capabilityだけ`unavailable` |
| optional非Go tool | 同梱しない | 対応OSと用途を明記。標準runtimeから要求しない | 標準runtimeへ影響させない |
| Windows CUDA用WSL | 同梱しない | Windowsだけの外部compute特例 | GPU capabilityだけ`unavailable` |

| Component | 標準artifact | 状態 | 同梱しないもの |
| --- | --- | --- | --- |
| RenCrow_CORE | `rencrow` | Go実装済み・必須 | 各capabilityのbackend、optional Tool runtime |

RenCrow_VisionとRenCrow_ImageのGo Gatewayを標準起動経路とします。両repositoryに残る
Python実装はdevelopment、contract比較、移行用であり、標準installerの必須runtimeでは
ありません。動画処理のFFmpeg／FFprobeは必要なVision hostだけへ置く外部実行物として扱い、
Python依存とは区別します。

Browser ActorはNode.js／Playwright、WebwrightはPythonを使うoptional capabilityです。
標準installerはこれらを導入・起動せず、設定で明示的に有効化した
hostだけがdependencyを用意します。未配置、未設定、health不成立を成功へfallbackせず、
`disabled`または`unavailable`として観測します。

### X Bookmark optional intake境界

X Bookmark収集は標準Go配布に含めない、RenCrow_Tools所有のNode.js／Playwright optional
CLIです。runtimeとデータの境界は次で固定します。

```text
利用者が許可した専用browser profile
  -> RenCrow_Tools rencrow-x-bookmarks
    -> raw_capture.jsonl / rencrow_core.jsonl / report.json
      -> RenCrow_CORE knowledge import
        -> pending staging
          -> 明示review
            -> Knowledge
```

COREはbrowser session、Playwright、XのDOM selectorを所有せず、ToolsはCOREのproduction DB、
Knowledge promotion、Recallを所有しません。RenCrow_CMDはこのCLIを`rencrowctl`へ複製せず、
CORE Public APIが提供する一般操作だけを担当します。CLI未配置または認証期限切れを標準runtimeの
失敗にせず、optional capabilityの`disabled`または明示的な収集errorとして扱います。

データ意味と同一ユーザー連続返信の統合規則は
[「X Bookmark収集・Knowledge取込」](02_機能仕様.md#x-bookmark収集knowledge取込)
を正本とします。

### CUDA用WSLの限定境界

Windows上のWSLは、明示的に選択したCUDA／GPU backendを動かす外部computeにだけ使用できます。
これはCUDA deviceとLinux向けGPU stackを利用するための限定境界であり、WSLをRenCrowの一般runtime
またはWindows互換層として採用する根拠にはなりません。

- COREと各RenCrow moduleのGateway／control processはWindows nativeのGo binaryとして動かす。
- CUDA用WSL内のbackendへは、LLM／STT／TTS／Vision／Image等の所有moduleが通常の公開contractで
  接続する。CORE、PORTAL、CMDはWSL process、CUDA backend、物理endpointを直接操作しない。
- WSLをdatabase、message queue、vector store、news収集、storage、browser sidecar、一般Tool、
  supervisor、installerの代替として使わない。
- WSL、CUDA、backendがないWindows環境でも、対象GPU capability以外のnative Go runtimeを起動できる
  状態を保つ。対象capabilityは`unavailable`として理由を観測可能にする。
- WSL内で成功したtestは外部computeのWindows接続確認であり、Windows native runtimeの合格証拠には
  数えない。native Go processとWSL external computeを別々に検証する。
- Ubuntu／macOSでは別の物理GPU backendを選択できるが、module-facing contractと失敗時の意味は
  Windowsと同じにする。

### 共通HTTP health contract

HTTP serverを提供するGo moduleは、Ubuntu、Windows、macOSで次のendpointと意味を
共通にします。既存の`/health`、`/live`、`/ready`は互換aliasとして残せますが、
新しいmodule間監視は以下を使います。

- `GET /health/live`: Go processがrequestを受付できれば200。外部backendの状態は混ぜない。
- `GET /health/ready`: moduleの対象capabilityが使用可能なら200。外部systemが未配置、
  未設定、未readyなら503と`status=unavailable`を返す。
- JSONに`ok`、`status`、`service`、`runtime=go`を含め、失敗時は安定したmodule固有
  error codeと理由を返す。OS固有のprocess起動方法やpathを公開contractに含めない。
- readiness不成立は対象capabilityの失敗であり、livenessや無関係なGo capabilityを失敗にしない。

### 予約PORTと同一Taskの置換起動契約

この節を、RenCrowが管理するnetwork listenerのPORT予約、所有権、置換起動の
cross-module正本とします。各moduleは自分が所有するConfigで実値とTaskを定義し、
COREは物理Backend PORTの実値を複製管理しません。

用語と同一性を次で固定します。

- `ManagedTask`は所有module、安定した`task_id`、host identity、roleまたはprofileで
  識別する。Config revisionやprocess IDが変わっても、同じ`task_id`なら同一Taskの
  新旧instanceである。
- `ReservedPort`は`host identity + transport + bind scope/address + port`で識別する。
  PORT番号の一致だけで同一Taskと判定しない。
- `TaskInstance`は`task_id`に加え、instance ID、PIDとprocess start identity、実行file、
  Config revisionを起動記録へ持つ。listenerの所有判定はPIDだけに依存しない。

`start`、`restart`、`replace`は同じ置換起動として、次の順序を必須とします。

1. 所有moduleのConfigから`task_id`と`ReservedPort`を決定的に解決し、その予約用の
   lifecycle lockを取得する。
2. listener、所有記録、supervisor状態を照合する。PORTが空いていれば新instanceの
   起動へ進む。
3. 前の同一Task instanceが使用中なら、先にsupervisorの自動再起動を抑止し、
   所有moduleの停止経路でgraceful stopする。有限時間内に停止しない場合は、所有を
   引き続き確認できるそのTask instanceに限り、moduleの宣言済みpolicyで強制停止できる。
4. 旧processの終了と`ReservedPort`からlistenerが消失したことを別々に確認する。
   解放未確認のまま新instanceを起動しない。
5. 新instanceを同じ`ReservedPort`で起動する。別PORTの探索や再割り当ては行わない。
6. 新しいinstance identity、予約どおりのlistener、liveness、readinessを順に検証し、
   全て成立した後だけreadyを報告する。
7. `task_id`、新旧instance ID、予約、停止理由、各時刻、結果とerror codeを監査記録へ残す。

予約PORTが別Taskまたは所有不明processに使用されている場合、そのprocessを停止せず
`PORT_OWNERSHIP_CONFLICT`でfail closedします。同一Taskの停止を確認できない場合は
`PORT_RELEASE_TIMEOUT`、新instanceの起動またはreadinessが失敗した場合は
`TASK_START_FAILED`とします。いずれも`port=0`、空きPORT scan、`port+1`、random PORT、
別profileへの退避で成功に見せません。

同一Taskを並列化する場合は、別の`task_id`と`ReservedPort`を起動前にConfigへ明示します。
実行時にreplica用PORTを発明しません。置換処理はRenCrow runtimeの決定的な通常運用であり、
人の判断待ちにしません。所有不明なら自動許可も停止もせず、即時に競合として返します。
この自律運用契約はRenCrow runtimeに対するものであり、開発Toolが従う外部操作の権限契約を
変更しません。

unit testのprocess内で閉じ、deploymentやRenCrow E2E成功を主張しないsocket fixtureは
OSのephemeral portを使用できます。RenCrowの実service、sidecar、Backend、E2E harnessのいずれかを
起動するtestは対象profileに予約を明示し、productionと同じ競合処理を検証します。

映画カタログのdomain、SQLite正本、検索、評価、Public API、policy、監査、artifact検証、
transactional importはCOREが所有します。外部サイト巡回、robots.txt、rate limit、HTML解析、
immutable JSONL artifact生成はRenCrow_Toolsのoptional Go sidecarが所有します。COREは
`movie_catalog.crawler_url`でsidecarへ接続し、Python crawlerを直接起動しません。
sidecar未配置時は`503`と`MOVIE_CATALOG_CRAWLER_UNAVAILABLE`を返し、旧Python実装へ
暗黙fallbackしません。

映画・人物ViewerのD0/D1は、映画catalogの直接関係treeをViewerへ投影するCOREの派生表示です。
これは会話Memory、UserMemory、Memory L1、Knowledge Relationのhopではありません。D0 rootは
現段階では映画または人物に限定し、明示assessmentのpositive値、成功した明示映画名／人物名／URL
取得対象、または明示assessmentが存在しない場合だけ許可する既存watch／favorite fallbackから決定
します。D1はD0からのvalidated direct relationで到達する映画、人物、音楽作品、主題歌、劇伴、
サウンドトラック、小説、漫画、舞台、ゲーム等のカードを含み、D1から先へ自動展開しません。
映画側credit／直接関係とprovenanceは`movie_catalog`が所有し、音楽・小説・漫画・舞台・ゲーム等の
汎用work card正本は既存storage canonどおり`hobby_graph`が所有します。Viewer projectionは両者を
validated direct relationで接続しますが、movie_catalogへ汎用work cardを複製しません。文字列だけで
validated itemへ確定できない場合はprovenance付き`partial`または`unresolved` cardを返し、推測で
補完しません。root、relation、depthは読み取り時に計算し、depthや派生カードをMemory L1または
映画catalogへ重複保存しません。L1のvalidated domain graph assertionからcatalogへ投影する経路と、
Viewer評価からD0/D1を作る経路は別方向の責務です。

#### Movie Catalog graph schema v2／import実装仕様

映画catalogの取得artifactは、既存のmovie／person JSONLを`rencrow.movie_catalog.v2`へ段階的に
拡張します。v2はJSONLの各行に`kind`（`manifest | node | edge`）を持ち、`manifest`を1件、`node`と`edge`を
そのmanifestへ束ねます。manifestはartifact全体の境界とD0候補を宣言し、nodeは映画・人物・
音楽作品・原作等のカード候補、edgeは映画側が検証した直接関係だけを表します。v2の最小shapeは
次のとおりです。fieldを省略して意味を推測せず、未知の`schema_version`と壊れた参照は拒否します。

```json
{"schema_version":"rencrow.movie_catalog.v2","kind":"manifest","manifest_id":"manifest-1","root_node_id":"movie:101","root_kind":"movie","root_id":"101","root_label":"作品名","root_url":"https://eiga.com/movie/101/","source_url":"https://eiga.com/movie/101/","validation_state":"confirmed","provenance_urls":["https://eiga.com/movie/101/"]}
{"schema_version":"rencrow.movie_catalog.v2","kind":"node","node_id":"movie:101","node_kind":"movie","target_id":"101","label":"作品名","url":"https://eiga.com/movie/101/","depth":0,"validation_state":"validated","provenance_urls":["https://eiga.com/movie/101/"]}
{"schema_version":"rencrow.movie_catalog.v2","kind":"node","node_id":"person:7","node_kind":"person","target_id":"7","label":"人物名","url":"https://eiga.com/person/7/","depth":1,"validation_state":"validated","provenance_urls":["https://eiga.com/movie/101/"]}
{"schema_version":"rencrow.movie_catalog.v2","kind":"edge","edge_id":"movie:101-person:7-director","from_node_id":"movie:101","to_node_id":"person:7","from_kind":"movie","to_kind":"person","relation_type":"director","source":"eiga","provenance_urls":["https://eiga.com/movie/101/"]}
```

`manifest.root_kind`と`root_node_id`のroot kindは現段階では`movie | person`だけです。nodeの
`node_kind`は`movie | person | music | source_work`を許容します。nodeの`validation_state`は
`validated | partial | unresolved`、edgeは`validated`だけをD1採用対象とします。文字列だけで
`hobby_graph`の正本itemへ確定できないnodeはartifact内で一意なnode_idを持たせても、Viewerの
`target_id`は空のまま`partial`／`unresolved`で返します。`provenance_urls`、relation_type、labelを
根拠なしに補完しません。edgeの両端、manifestの整合性、root参照、manifest_idは一つのartifact内で
整合しなければなりません。artifactのnode `depth`はsidecarの取得境界を検証するための入力metadata
であり、ViewerのCard `depth`ではありません。COREはこれをCard depthとして保存・再利用しません。

root importは次の一つのtransaction境界で実行します。

1. sidecar responseのjob、artifact URL、SHA-256、byte数を検証し、JSONL全体をstagingで読みます。
2. manifestが一つであること、schema、node／edge IDの一意性、edgeの両端、provenance、record境界、root
   kindを検証します。1件でも不正ならDB transactionを開始せず、または開始済みならrollbackします。
3. 検証済みnode／edgeと取得成功のroot eligibilityを同じCORE transactionへimportします。sidecarは
   CORE SQLiteへ接続せず、depthやD0/D1 cardを保存しません。
4. commit成功後だけ取得対象を明示import済みrootとして扱い、ViewerがD0/D1を派生します。失敗時は
   root、node、edge、fetch receiptの一部だけを残さず、旧catalog状態を維持します。

カード投影はrootごとにdirect edgeを一度だけ評価します。root node自身を`depth=0`、rootからの
validated edgeの到達先を`depth=1`とし、depth=1 nodeから次のedgeを辿りません。このD1-only invariant
はSQL／resolverの取得条件とtestで固定し、artifactの取得metadataをCard depthへ流用しません。同じ`kind + target_id`
は一件へまとめ、複数rootから届く場合は最小depthを返します。target_idのないcardは正規化label、
relation、provenanceの組み合わせでのみdedupeします。

#### Person related catalog collection境界

評価済み人物から映画、ドラマ、受賞歴、音楽、アニメ、小説、漫画を収集する経路は、映画.com crawlerの
暗黙拡張ではなく、カテゴリ別のread-only provider adapterを持つ独立workflowとします。COREは対象人物、
request scope、source policy、identity resolution、artifact検証、transactional import、receiptを所有し、
外部HTTP取得とsource固有responseの正規化はRenCrow_Toolsのoptional Go providerが所有します。標準profileへ
Python、Node.js、browser automationを追加せず、provider未配置時はカテゴリ単位で`unavailable`を返します。

収集は`resolve person identity -> collect category artifacts -> validate Japanese presentation -> import`の順です。
identity artifactは映画.com person ID、Wikidata QID、MusicBrainz MBID等のうち確認できたIDと、
照合に使ったevidenceを持ちます。名前だけの一致はconfirmed identityにしません。カテゴリartifactは
`run_id`、`person_ref`、`category`、`source`、`source_record_id`、`source_url`、`retrieved_at`、原名、sourceが
明示した日本語名、日本語名の根拠URL、説明原文、日本語説明、relation、validation stateを持つimmutable
JSONLとし、hash・byte数を検証してからimportします。

採用するprovider roleは次です。映画.comは既存の日本語映画・人物情報、Wikidataの公開CC0経路はidentityと
横断的な候補発見、ジャパンサーチはAPI提供が許可された利活用メタデータ、国立国会図書館サーチは
API提供対象一覧で申請不要と明示されたCC BY／CC0／PDM書誌だけを小説／漫画の確認に使います。文化庁事業に由来する
メディア芸術データベースの公開SPARQLはアニメ／漫画／メディア芸術祭受賞、MusicBrainzの認証不要・
非商用GETはartist／recording／release／work、賞主催者の公開公式ページは受賞の最終確認を担当します。
利用契約、利用申請、API key、access tokenまたは課金を必要とするsource、非公式の第三者APIはprovider
allowlistへ登録せず、artifact importでも拒否します。ジャパンサーチはrecordのメタデータ二次利用条件が
PDM／CC0／CC BY／CC BY-SAのどれかと確認できた場合だけ取り込み、元コンテンツの利用可否と混同しません。
Wikidataの候補だけを受賞の公式確認の代替にせず、providerごとのauthorityとrights URLをartifactへ記録します。

#### Collection plannerの取得順序と停止契約

収集の速さと成功率を両立するため、COREは人物・カテゴリごとに一つの`collection plan`を作り、providerを
闇雲に並列実行しません。plannerは次の順で同じ入力から同じ計画を生成します。

1. `known | like`の明示評価、要求カテゴリ、既存のpositive／negative receipt、refresh期限を確認する。十分に新しい
   local resultが十分ならTier 0で終了する。negative receiptは対応sourceのHTTPだけを省略し、次のapplicable sourceを評価する。
2. identityを一度だけ解決する。映画.com人物ID、生年月日、既存作品、保存済み外部IDを照合し、confirmed external IDを
   全カテゴリで再利用する。名前だけの一致は確定に使わず、`ambiguous | unresolved`なら外部カテゴリ取得を開始しない。
3. 要求カテゴリをprovider batchへまとめる。同一providerが複数カテゴリを検索できる場合は一つのbounded queryとし、
   固定LIMIT、pagination上限、host単位のrate limitを適用する。
4. Tier 0のindexed `movie_catalog`／`hobby_graph`とreceiptを読み、未充足のcoverageだけをTier 1、Tier 2へ渡す。
   Tier 1はカテゴリ専門sourceのconfirmed external IDによる直接照会とする。必要なIDがない場合だけ
   Wikidataを1回照会し、identity照合用IDと候補発見に使う。
5. 現行revisionはカテゴリごとに実装・検証した固定sourceだけを試す。ドラマ=`jpsearch`、受賞歴=`wikidata_award`、
   音楽=`musicbrainz`、アニメ／漫画=`mediaarts_db`、小説=`ndl_national_bibliography`である。受賞はconfirmed Wikidata QID、
   小説はconfirmed NDL authority URIを必須とし、identity不足を名前検索や別sourceへ暗黙fallbackしない。

次sourceは前sourceが`unavailable`、`ambiguous`、stale、または要求された明示coverage gapを残した場合だけ発行します。
十分なvalidated resultが得られたカテゴリは後続sourceを呼ばず、全件sourceへfan-outしません。429／5xx／一時的network
failureだけを有限回再試行し、`Retry-After`とbackoffを使います。semantic empty、identity ambiguity、rights rejection、
schema errorは再試行しません。カテゴリは`complete | partial | unavailable | ambiguous | rejected`のいずれかで停止し、
未実行のsourceを成功扱いにしません。

plannerとproviderは、少なくとも次のreceiptを同じ`run_id`へ保存します。

```json
{
  "plan_revision": "person-related-plan.v1/1",
  "attempts": [{
    "source": "wikidata", "priority": 10, "reason": "tier1_cross_category",
    "status": "ready", "started_at": "RFC3339", "completed_at": "RFC3339",
    "item_count": 2, "error_code": ""
  }],
  "stop_reason": "enough_validated_results | all_sources_terminal | identity_ambiguous | unavailable",
  "next_source": "jpsearch"
}
```

各attemptは発行順にsource、priority、理由、状態、時刻、件数、error codeを持ち、各itemはsource hit、record ID、provenance、
rights、authority、`name_state`を持ちます。source・category別の直近90日のterminal attemptが30件以上の場合だけ、
`validated hit率 × 平均完全性 ÷ (1 + p95 latency秒)`で同じauthorityのsourceを次回planへ昇格できます。個人評価による順序変更、identityや受賞のauthorityを下げる昇格は許可せず、
同率時は固定source名順で決定し、使用した統計snapshotとplan revisionを記録します。

作品名等の固有名詞には翻訳工程を適用しません。presentation validatorは、日本語表示名がsource recordまたは
根拠URLに存在する場合だけ`source_ja | official_ja`を許可し、それ以外は原名を`original`として採用します。
`translated_ja`を固有名詞の状態として受理せず、生成された邦題、sourceにない日本語名、原名を失ったrecordを
artifact validationで拒否します。説明文の翻訳と固有名詞の採否は別工程・別fieldです。

#### WorkSummaryの保存境界とquery projection

作品説明は関係artifactの付加情報であり、`WorkSummary`という公開意味契約で扱います。artifact／DBのfield対応は
`summary_original -> description_original`、`summary_language -> description_language`、
`summary_ja -> description_ja`、`summary_translation_state -> description_translation_state`に固定します。
sourceが返した説明原文はsource factとして非破壊保存し、`summary_ja`はsourceが提供した日本語説明、またはその原文説明だけを
忠実に翻訳したものに限ります。タイトル、credit、review、周辺本文、別作品、LLM知識から要約を作りません。
固有名詞は検証済み`display_name` tokenを使い、翻訳工程で邦題を生成しません。

public semantic stateは`summary_state=source_summary | translated_summary | unavailable`です。内部の
`source_status=ready | unavailable`、`translation_status=not_required | ready | failed | not_attempted`を分離して保持し、
翻訳失敗時も外国語原文を失わない一方、通常の日本語queryへ外国語原文をサマリとして投影しません。`lookup`の作品行には
`summary_ja`と`summary_state`を返し、debug／内部scopeだけが原文、原語、翻訳状態を参照できます。

収集器は初回の専門source responseに含まれる説明を関係と同時に取り込みます。COREは欠落作品へ正確なsource record ID、canonical URI、
ISBN、MBID、MADB／ジャパンサーチ／NDL IDでsummaryだけを後段追加できる更新契約を持ち、最大20作品／request、最大2 source／作品に
制限します。summary enrichment workerは実装済みで、fixed-ID endpoint、lease、hash／size／manifest検証を通ったpatchだけを
適用します。production配布とsource別E2Eが成立していない説明は`unavailable`のままです。後段更新はidentity・名前・relationを
上書きできません。関係の`relation_status`とサマリの`summary_state`は独立し、category responseの
`summary_coverage={ready,unavailable,total}`で欠落を明示します。

作品カテゴリのsummary候補は、映画=`movie_catalog`概要、ドラマ=`jpsearch`、アニメ／漫画=`mediaarts_db`、
小説=`ndl_national_bibliography`、音楽=`musicbrainz`のfixed recordです。受賞recordとMusicBrainz relation metadataは
作品サマリの代用にせず、対応する公開説明sourceがない場合は`unavailable`です。
各summaryはsource、source record ID、canonical／evidence URL、取得時刻、content hash、language、rightsを持ち、
source／category TTLとnegative summary receiptを使って同じ欠落照会を抑止します。未提供でもvalidated work/relationのimportを失敗させません。

`movie_catalog`と`hobby_graph`を跨ぐtransactionは作りません。先にimmutable artifactとidentity receiptを確定し、
各DBへ冪等importした結果をrun receiptで追跡します。一方だけ失敗した場合は成功側を虚偽のrollback済みにせず、
カテゴリ別`ready | partial | unavailable | ambiguous | rejected`を保持して再開します。通常queryは固定person IDと
category／relationのnamed indexだけを使用し、外部検索、全件scan、別カテゴリ探索をquery-time fallbackにしません。

#### Person related catalog 次期実装順序と完了契約

人物関連catalogの次期revisionは、依存関係を逆転させず、次の4段階を直列に導入します。後段の機能を先に
`available`へせず、各段階のmigration、production wiring、Runtime Capability Snapshot、receipt、実E2Eがそろった時点で
その段階だけを実装済みにします。

1. `summary補完worker`
2. `公開利用可能な受賞・小説source`
3. `identity mapping`
4. `knowledge_memoryの索引化`

##### 1. summary補完worker

COREのbackground workerが、作品import時に作る`hobby_summary_jobs`だけをnamed indexでclaimします。lookup結果や
`hobby_related_items`を定期的に全件走査して欠落を探しません。jobは`category + item_id`を一意keyとし、
`pending | leased | ready | unavailable | dead`、`source_cursor`、`next_attempt_at`、`lease_until`、`attempt_count`、
`last_reason`、`updated_at`を保持します。claimは`state + next_attempt_at`のindexを使い、一度に最大20作品、1作品最大2 source、
1 worker batch最大40 patchに固定します。lease切れは再開できますが、同じ`category + item_id + source + content_sha256`の適用は
冪等です。

COREはjob作成、claim、source順、TTL、translation handoff、`ApplySummaryPatch`、receiptを所有します。RenCrow_Tools providerは
固定されたsource record ID／canonical URI／ISBN／MBID／MADB ID／NDL IDだけを入力に外部HTTPを行い、検索語だけの再探索や
任意URLを受けません。provider responseは`source_status`、原文、原語、sourceが明示した日本語説明、provenance、rights、取得時刻、
content hashを返します。sourceに日本語説明がなければ、COREは通常の`CORE -> RenCrow LLM Gateway -> RenCrow LLM Runtime`
経路へ説明本文だけの忠実翻訳を依頼できます。固有名詞tokenは入力の検証済み`display_name`から固定し、モデル出力で邦題、人物名、
relation、identityを変更しません。翻訳失敗は原文を保持した`unavailable`で確定し、別作品の本文やWeb検索で埋めません。

positive／negative summary receiptはsource別TTLを持ちます。HTTP 429、5xx、一時network failureだけを有限retryし、
`Retry-After`を優先します。空結果、rights不適合、schema不正、identity不一致はretryしません。完了証拠は、queue claimの
no-scan `EXPLAIN QUERY PLAN`、lease競合、再起動再開、重複apply、20作品／2 source上限、タイトル非翻訳、negative TTL、
provider停止時fail-closedのtestに加え、productionで欠落作品が`unavailable -> source_summary | translated_summary`へ変わり、
同じ人物lookupとViewerに日本語サマリが表示されるE2Eです。

provider transportは`POST /v1/person-related-catalog/summaries`へ固定します。requestは`request_id`と最大20件の
`targets[]`だけを持ち、各targetは`category`、`item_id`、`source`、`source_record_id`、`canonical_url`と、存在する場合だけ
`isbn | mbid | mediaarts_id | jpsearch_id | ndl_id`を持ちます。`name`、任意query、任意path、任意headerは受けません。
responseは既存collectionと同じ同一origin artifact URL、SHA-256、byte数、status、reason、retrieved_atを返し、artifactの
各rowは`SummaryPatch`と同じfieldだけを持ちます。COREはhash／size／schema／target一致を検証してから一transactionでapplyします。
summary TTLの初期値はready=30日、semantic unavailable=7日、rights rejection=30日とし、source policy revisionでのみ変更します。
公開lookupは期限切れrowをreadyとして投影せず`unavailable`にし、同時にdue jobを既に持つことをschema testで保証します。

##### 2. 公開利用可能な受賞・小説source

契約、利用申請、API key、access token、課金を必要としない固定endpointだけをsource registryへ載せます。受賞の第1 sourceは
WikidataのCC0 structured dataとし、confirmed QIDに対する受賞statement、qualifier、reference、sourceが持つ日本語labelだけを
取り込みます。referenceを持たないstatementは`candidate`、Wikimedia外の根拠URLを持つstatementは`validated_secondary`、
賞主催者の公開公式ページで同じ人物・賞・回／年を確認できたものだけを`confirmed`とします。公式ページが機械取得を許可しない、
または利用条件を確認できない場合もWikidata事実を捨てず`validated_secondary`で返し、公式確認済みとは表示しません。

小説の第1 sourceはNDLサーチのうち、API提供対象一覧で利用申請不要かつPDM／CC0／CC BY互換と明示されたメタデータに固定します。
初期実装は国立国会図書館作成の全国書誌`iss-ndl-opac-national`を対象とし、横断`any`や利用条件不明providerを使いません。
著者標目／典拠IDをconfirmed identityへ結び、資料種別、ISBN、版、出版者、刊行年とsourceにある日本語書名だけを取得します。
CC BY attribution、provider ID、record ID、rights URL、取得時刻を保存・表示し、本文・紹介文・書影の権利をメタデータの利用条件から
推測しません。継続取得は明示User-Agent、host rate limit、直列pagination、最大20件、429 `Retry-After`、positive／negative TTLに従います。

source adapterはfixtureだけでなく、rights policy evaluatorを純粋関数としてtestし、allowlist外provider、rights欠落、申請必要、
日本語名のないrecordをそれぞれ`rejected | unavailable`へ確定します。production完了には、受賞と小説が
`rights_unverified`で一律停止せず、公開条件を満たすrecordだけがartifact、DB、indexed lookup、Mio、Viewerまで届くE2Eと、
provenance／attribution表示の確認が必要です。

##### 3. identity mapping

現在の`external_ids_json`をquery-timeにdecodeして照合する設計から、正規化された
`hobby_person_external_ids(authority, external_id, person_ref_id, state, evidence_url, observed_at, updated_at)`へ移行します。
`authority + external_id`を一意key、`person_ref_id + authority + state`をnamed indexとします。候補根拠は
`hobby_person_identity_evidence`へ分離し、name、birth date、known work、official／authority URLの一致・不一致とsource時刻を保持します。
個人情報の推測値やLLMの記憶はidentity evidenceにしません。

resolverは既存movie catalog person IDをanchorに、保存済みconfirmed ID、公式／authority ID、Wikidata QID、MusicBrainz MBID、
NDL典拠IDを一run一回だけ照合します。名前一致だけは`candidate`、名前に加えて独立したbirth dateまたは既存作品一致がある場合は
`confirmed`、衝突は`ambiguous`、不足は`unresolved`です。`ambiguous | unresolved`を自動mergeせずカテゴリ取得を止め、候補と理由を
receiptへ残します。人の返答待ちstatusは作らず、新しい根拠を持つ次requestで再評価します。

identity transportは`POST /v1/person-related-catalog/identities/resolve`へ固定します。requestは`run_id`、
`movie_catalog_person_id`、検証済み人物名、公開人物URL、既存confirmed external ID、照合用の生年月日／既存作品IDだけを持ちます。
responseは`confirmed | ambiguous | unresolved`、authority別candidate ID、matched／conflicted evidence field、evidence URL、
retrieved_at、expires_at、reasonを返し、artifactを生成しません。COREはresponseを再判定して正規化表へ保存し、providerの
`confirmed`を無条件採用しません。positive identity TTLは90日、ambiguous／unresolvedは7日です。同じrun_idの全categoryは
この一つの結果を共有し、provider batchへconfirmed IDを渡します。plan revisionは`person-related-plan.v2/1`とし、
runtimeがcategoryごとに別run_idを生成したり、plannerの複数category batchを一categoryへ縮退させたりしません。

migrationは既存JSONをbatchで読み、validation済みIDだけを冪等backfillします。二重write期間を経て、readerを正規化表へ切り替え、
件数・unique conflict・orphanが0であることを確認してからJSONをcompatibility projectionへ降格します。完了証拠はauthority別exact lookupの
no-scan plan、同姓同名、別人ID衝突、複数categoryでの一回解決、再起動、旧row migration、CLAMP等group identityの
`ambiguous | unavailable`維持、confirmed人物の受賞／小説取得E2Eです。

##### 4. knowledge_memoryの索引化

`knowledge_memory`の`payload TEXT`を直接LIKE検索または全件decodeする経路は作りません。COREは保存時に公開検索可能fieldだけを抽出し、
`knowledge_memory_search_documents`と`knowledge_memory_search_terms`へ同一transactionでdual-writeします。日本語検索はGoの固定normalizerで
Unicode正規化と2-gram token化を行い、term表を`scope + user_id + token + record_type + record_id`のcovering indexでexact検索します。
queryは最大16 token、候補最大50、最終結果最大20、固定record type、固定scopeを必須とし、SQL、table、column、path、order、任意filterを
入力にしません。

通常Agentへ公開できるのはreview済み`creative_knowledge | news_knowledge`のsummary projectionだけです。
`personal_archive | daily_intake_rule | temporal_memory_marker | dream_consolidation_run`はraw DB Toolから除外し、authenticated user scopeと
所有serviceの明示operationがある場合だけ参照できます。検索indexにraw payload、prompt、dream本文、credential、内部review noteを複製しません。
候補取得後もrecordの現行visibilityとowner scopeを再検証し、不一致は返しません。

backfillはcursor付き最大200 row／transactionで中断再開可能にし、migration中はcapability catalogを`blocked / indexing`、schema・index・
coverage・integrity確認後だけ`available`へ変えます。semantic Toolを追加する場合は`knowledge.search`の閉じたoperationとし、
Runtime Capability Snapshot、Worker policy、audit receiptへ接続します。完了証拠は全record typeのdual-write、削除／更新、scope隔離、
sensitive field非漏洩、旧DB backfill再開、named indexを使う`EXPLAIN QUERY PLAN`と対象表`SCAN`なし、missing indexでfail-closed、
Chat／Workerのbounded search E2Eです。

現行defaultのJSONL deploymentからは、legacy source JSONLを削除・上書きしないone-shot migration inputとして読み、SQLite domain rowと
search projectionをbackfillします。JSONLとSQLiteを永続的な二重正本にせず、Common Raw migration後のrecord count、ID、content hashの
manifestが一致してからConfigを`knowledge_memory.storage=sqlite`へ切り替えます。source root／manifest不在、count／hash不一致、asset／schema
欠落は空成功にせず、切替前、live DB未配置、またはindex coverage未完了では`data_capability.describe`の`knowledge_memory`を`blocked`のままにします。

##### 未完了部分を閉じるproduction契約

2026-08-12の再検証で未接続だったauthority lifecycleは、次の契約で実装します。production完了は実module間E2Eの
成功後に確定し、手作業のDB更新や起動時全件scanで補いません。COREは
`hobby_person_identity_jobs`を所有し、人物assessmentが`known | like`へ遷移した時、受賞／小説収集がconfirmed identity不足で
停止した時、または保存済みidentityのTTLが切れた時だけjobを冪等に作ります。初回migrationはcursor付き最大200人物／transaction、
通常claimは`state + next_attempt_at + movie_catalog_person_id`のnamed indexから最大20件とし、各tickで人物表を走査しません。

jobは`pending | leased | confirmed | ambiguous | unresolved | dead`、`lease_until`、`attempt_count`、`next_attempt_at`、
`last_reason`を保持します。CORE workerは固定transportへ1人物1runで問い合わせ、返却候補を既存のidentity state machineで
再判定してからevidenceとexternal IDを同一transactionで保存します。名前一致だけをconfirmedにせず、exact authority cross-reference、
または名前と独立した生年月日／既存作品一致を必須にします。positive TTLは90日、`ambiguous | unresolved`は7日、retryは429、
5xx、一時network errorだけを最大3 attemptとします。schema、rights、identity conflictはterminalです。同じ人物の全categoryは
一つの解決結果を共有し、LLM知識、一般Web検索、任意URL、別providerへfallbackしません。

production migrationは既存validated artifactのIDだけを冪等backfillし、宮崎駿を含む特定人物のIDをmigrationやConfigへ
hard-codeしません。完了条件は、評価済み人物からjob作成、固定authority解決、evidence保存、受賞／小説収集、indexed lookup、
Mio、Viewerまでのproduction E2Eです。少なくともconfirmed人物、同姓同名、authority conflict、restart後lease再開、TTL再評価、
20件claim上限、対象表`SCAN`なしを検証し、`ambiguous | unresolved`では外部作品収集を行わないことを確認します。

Knowledge MemoryをAgent Toolへ公開する前に、CORE domainへ型付き`ToolExecutionScope`を追加します。必須fieldは

ToolLoop wrapperは同じtyped scopeを欠落なく搬送し、user委譲を受けたAgentも元のauthenticated userを拡張できません。

`knowledge.search`のargsはquery、固定record type enum、最大20件のlimitだけです。public scopeはreview済みpublic projectionだけ、
user scopeは`authenticated_user_id`とownerが一致するrowだけを候補取得後にも再検証します。scope欠落、衝突、未知の認証sourceは
`TOOL_EXECUTION_SCOPE_MISSING | TOOL_EXECUTION_SCOPE_INVALID`で`blocked`とし、public扱い、別DB、raw payload、Web検索へfallback
しません。Tool／Snapshotを`available`へするgateはschema、named index、coverage、typed-scope production wiringの全成立です。
受入testはargsからのscope偽装拒否、user A／B分離、Agent委譲時のscope保持、wrapper通過、Chat／Worker E2E、receiptへの
request／actor相関と本文非記録を含みます。

##### Direct local ingressのorigin invariant

- **Failure**: reverse proxy／Tailscale Serveが外部requestをbackendへloopbackとして転送すると、
  loopback限定のowner writeまたはlocal Agent OPSが外部から到達可能になる。
- **Problem**: `RemoteAddr`だけを検査する判定が複数adapterへ分散し、backendから見えるloopbackを
  direct localと誤認していた。
- **Cause**: proxyが付与するorigin headerとHost authorityを、認証・method判定より前に共通検査していなかった。
- **Lesson**: loopbackは到達経路の一要素にすぎず、HTTP requestのorigin証拠を単一のsecurity ownerで
  fail-closedに検証しなければならない。
- **Invariant**: requestが非nilで、RemoteAddrがhost:port形式のIPv4／IPv6 loopback、Host authorityが`localhost`または
  loopback IP（portは省略または1〜65535の有効値）、かつ`Forwarded`、`Via`、`X-Forwarded-*`、
  `X-Real-IP`、`Tailscale-*` headerを一つも持たない場合だけdirect localとする。その他はremote／proxiedとして扱う。
- **Enforcement**: `internal/infrastructure/security.IsDirectLoopbackRequest`をorigin判定の唯一の正本とし、
  ViewerのMemory、ChatGPT、Atlas、DCI owner write ingressとCMDのlocal Agent OPS／pprof／assistant local通知が
  同じ判定を使用する。remote／proxied requestは各ownerの認証・method判定より前に404とし、proxy用headerを
  信頼済みoriginへ変換するfallbackを持たない。
- **Tests**: security packageのDirectLoopback table testでIPv4／IPv6、localhost、authority port、remote／host不一致、
  不正port、各proxy header（大文字小文字差を含む）を検証する。Viewer DCIとCMD local-onlyのintegration testでは
  loopback＋proxy headerを404、direct localを成功とし、既存owner／Agent OPS focused testとrace testで再確認する。

ToolLoopのFailure Knowledgeとして、Toolが失敗した後にLLMが同じTool名と同じcanonical JSON引数を
再提示しても、同一外部操作を再実行してはいけません。Problemは同一失敗が最大iterationまで反復して
空応答または上位HTTP失敗になり得たこと、Causeはloopが失敗callのsignatureを保持しなかったことです。
Invariantはretryを各owner Toolのtyped policyへ限定し、ToolLoopは同一失敗callの2回目を実行前に
`blocked`で終端することです。`internal/application/toolloop`のbehavior testで、provider呼出2回、
Tool実行1回、非空のblocked結果を強制します。

認証済みingressが存在しないdeploymentではpublic scopeだけを別契約で使用でき、user-private capabilityは
`scope_unavailable`のままです。実機E2Eのために未認証headerをuser identityとして信頼したり、hard-codeした
test userをpublic routeへ埋め込んだりしません。設定済みprincipalは検証済みtokenとの組だけで有効です。

G4は受賞recordに作品サマリがないことをworker失敗とみなしません。完了E2Eは、対象カテゴリの
source contractが説明を提供できる実作品を選びます。G5は実在人物のconfirmed NDL authorityが得られない場合に、
名前検索、別authority、別providerへ縮退せず`unavailable | ambiguous`を完了証拠として保存します。

##### workspace rootとmodule名の決定論的解決

module registryはfilesystem環境ではなく入力文字列から決定論的に解決します。解決順は、正規化した具体module root path、
canonical module ID／name、path spanを除いた独立alias tokenです。workspace親rootだけがpathとして現れ、具体module rootを
含まない入力はmoduleとして発見せず`ambiguous`を返します。親root文字列中の`workspace`をWorkspace snapshot aliasへ
部分一致させません。一方、pathでない独立語`workspace`は既存aliasとして扱えます。複数の具体moduleが現れた場合も
一つを推測せず`ambiguous`です。Linux、Windows、macOS separator、Unicode／case正規化、親root単体、具体module root、
独立alias、複数moduleのtable testを必須とし、filesystemの存在有無で結果を変えません。

transport endpointは互換のため`POST /v1/movie-catalog/crawls`を維持します。既存URL requestの
`seed_url`、既存responseのjob／artifact／hash／size field、v1 movie／person JSONL importは変更
しません。`query`は`seed_url`と排他的な追加fieldで、どちらか一方をsidecarへ渡します。sidecarとCORE
のv2 artifact schemaは`rencrow.movie_catalog.v2`へ揃えます。既存sidecarが
queryを理解しない場合もURLへ勝手に変換せず、明示errorを返してfallbackしません。`candidates`は
response/errorへの追加fieldで、旧clientは無視でき、CORE adapterはupstreamの`D0_RESOLUTION_AMBIGUOUS`
（HTTP 409）と候補を保持して利用者の明示選択を待たずに確定しません。Python crawler、映画.comの`/search`、
robots／rate limit迂回はv1／v2のどちらでも許可しません。

受入testは次の順序で実施します。

1. v1 URL payload／responseと既存movie／person artifactの互換test、v2 manifest／node／edgeのschema、
   unknown version、duplicate／dangling reference、provenance不足のreject test。
2. Crawler adapterのURL／query one-of、query payload、409 ambiguityとcandidates保持、unavailable／
   no-fallback test。
3. hash／size検証とroot transactionのcommit／malformed artifact rollback、再importの冪等性test。
4. D0 positive root／negative-only除外／明示assessment優先／fallback、複数root最小depth、D1 direct
   relation、D2非展開、partial／unresolved、movie_catalog／hobby_graph ownership境界のunit test。
5. Public APIのcards item kind、候補選択、error code／HTTP status、個人評価をCategoryRecallへ注入
   しないことのcontract test。
6. 最後にViewerの既存checkbox再読込、D0/D1表示・取得、query候補の明示選択、robots遵守を含むE2Eを
   実施し、handler／UIの実装結果とschema／adapter結果を同じ証跡へ束ねます。

どのcapabilityでも、Gatewayが利用不能なときにCORE、PORTAL、CMDから物理backendへ
直結しません。正規module経路の復旧を優先し、別topologyはCORE正本とdeployment policyに事前定義され、
機械検証を通るfallbackだけに限定します。未定義時は人へ判断を求めず`blocked`にします。

## CORE / RenCrow_LLM Chat境界

この節を、COREとRenCrow_LLMの入出力および責務分担の現行正本とします。
RenCrow_LLM側のdocs、実装、test、運用設定はこの契約に従い、別の意味を再定義しません。

COREからRenCrow_LLMへの要求は、ユーザーがChatへ入力するのと同等の論理messageです。
RenCrow_LLMからCOREへの応答は、ユーザーがChatで受け取るのと同等の論理assistant出力です。
ここでいう同等とは、物理Modelやproviderが変わってもCOREが同じChat contractで扱えることを
意味し、HTTP等のtransport metadataを禁止する意味ではありません。

責務を次で固定します。

- COREはAgent、Persona、Memory、Execution Role、利用policy、会話またはdomain上の
  入出力contractを所有する。
- COREはModel、provider、Backend、decoder、chat template、tokenization、stop条件、
  KV／prompt cache、生成時の外装や癖を認識せず、それらを理由に分岐しない。
- RenCrow LLM GatewayはRole profileからRuntimeを解決し、RenCrow LLM Runtimeは
  Backend／Model adapterとresponse-normalization境界でrequestとresponseの
  モデル／provider／decoder固有差を吸収する。
- COREはLLMをAgent（Execution Roleの実行alias）で指定する。Codex等の開発client向けに
  RenCrow_LLMは物理Modelを指定するmodel routeを持つが、CORE→Gatewayの契約は変えない
  （正本: `RenCrow_LLM/docs/13_モデル直指定経路仕様.md`）。
- COREがdomain上の構造化出力を必要とする場合は、論理requestに
  `ResponseFormatJSONObject`を指定する。RenCrow_LLM向けclient adapterはこれを
  OpenAI-compatible `response_format: {"type":"json_object"}`へ変換する。
- `response_format.type=json_object`かつnon-streamの呼び出しに限り、ModelがJSONへ付けた
  単一のMarkdownコードフェンスはRenCrow LLM Runtimeが除去し、COREへ単一JSON objectを返す。
  この分岐にModel名、Backend名、decoder名を使用しない。
- 通常Chatで利用者が要求したコードブロックやMarkdownは会話内容であるため、
  RenCrow LLM Runtimeは一律に除去しない。正規化は呼び出しcontractと
  Backend／Model adapterに基づいて行う。
- Runtimeが除去できる外装は、assistant content全体を囲む単一のコードフェンスで、
  info stringが空または`json`のものに限定する。内側はtrailing contentのない単一JSON object
  でなければならない。Runtimeは外装を正規化しても意味payloadを書き換えず、欠落fieldや
  domain判断を捏造しない。contractを満たす出力へ正規化できない場合は
  `NORMALIZATION_ERROR`として返し、Gatewayはこれを`TARGET_UNAVAILABLE`へ置換せずCOREへ返す。
- 現行contractでは`json_object`のRuntime正規化はnon-streamだけを対象とし、
  `stream=true`との併用を`INVALID_REQUEST`として拒否する。
- COREは正規化済み出力に対して、JSON構造、未知field、trailing content、Agent intent、
  `available_actions`等のdomain contractを厳密に検証する。

Model固有不具合をCOREのparser、handler、Agent、Game bridgeへ追加して吸収することを
禁止します。COREでModel名、provider名、decoder名または固有出力形式を条件にする必要が
生じた場合は、まずRenCrow LLM Runtimeのadapter／normalization責務違反として修正します。

## RenCrow_Harness委譲境界

Status: 採用済み設計・部分実装（RenCrow_Harness設計v0.2.2、2026-10-07）。COREは認証済みuser専用のaccepted OPS input保存・exact read境界、native profileがserver設定で選択された通常Agent OPSのreceipt受付・canonical Task／first Run claim・Shiro routeを実装しています。Task criteria pin freeze、Action proof persistence、RunGet／EventsRead／EvidenceReadによる採用source、同一Taskのauthenticated native Resume claimとknown-ID reconciliationおよびfocused testsがあります。固定Harness moduleに対するactual verifier CLI＋Gateway doubleのpositive integrationも通っています。Harnessとの実Gateway／実model利用者route、runtime試験97件、再起動後の運用受入は未完了または未確認です。本節はCOREと兄弟moduleが従う境界契約であり、sourceとfocused testだけでruntime運用受入済みとは扱いません。この経路が稼働するまで、Shiroの作業経路（CodexWorkPath、SubagentManager／toolloop、plain Generate）、Kuro／Heavy、COREの`codex.run` Tool、IdleChatのCodexExeは現行どおり動作します。工程と状態は[RenCrow_Harnessロードマップ](08_実装状況・ロードマップ.md#rencrow_harnessロードマップ)を正本とします。

現在の内部境界は、Common Raw manifest／record／ingested state、accepted OPS identity receipt、
空のcanonical first-thread bindingをconversation_l1の一transactionで作成します。受付は共有L1 poolから
connectionを予約し、receipt lookupより前に`BEGIN IMMEDIATE`を実行して独立store handle間のwriterを直列化します。
global pool設定やSQLite DSNは変更せず、途中失敗時はrequest contextから独立したbounded rollbackを行い、
rollbackを確認できないconnectionはpoolへ返さず破棄します。receiptはRaw本文を
複製せず、exact readerがowner／request、receipt identity、Raw metadata／hash／length、ingested stateを
照合してから本文を返します。readerが許可するのはcompleted manifestと初期ingested event一件だけで、
後続のforget等のlifecycle stateは未対応としてfail closedします。receiptのRaw referencesはacceptance transactionと
readerがapplication側で検証します。共用L1 SQLite connectionでは`PRAGMA foreign_keys`を有効化していません。
local／remote owner portは、runtimeがLocalAgentOpsの有効principalに応じてlocal L1または選択済みstoragehost L1 clientを
`AcceptedOPSInputStore`として公開します。remote clientはuser-parentのtyped execution scopeとrequest／owner／actor identityを
送信前に照合し、hostはconfigured principalとの一致後にだけその設定値からuser scopeを構成します。Raw本文は明示DTOの
`raw_message`を通して一度だけ送信し、receiptとread resultのidentityおよびRaw hashを照合します。remote Shiro readは未対応で、
再送時はstored receiptの元IDsを保持して検証します。通常の同一owner／request／canonical input再送はownerのstored receiptへ収束します。
ただしstoragehostのmutating journalはowner receiptと原子的ではありません。owner commit後、journal DONE前にhostが停止した場合、
同じstoragehost `op_id`は再実行せず`outcome_unknown`で停止します。owner DB reopen後のexact readでcommit済みRawが確認できても、
それはstoragehost操作のrecovery receiptではありません。Remote Shiro readは未対応で、LocalAgentOpsが無効またはprincipalが空のときも
通常のL1操作は維持します。これはHTTP受付、署名、Harness RPC、実行の経路ではありません。

Action ownerには、native delegationの永続化・reconciliation foundationがあります。canonical `native_harness.delegate` ActionはTask／Runごとに一つだけで、TaskID、RunID、Kind、Name、CurrentAttemptIDを固定し、typed `Attempt.NativeDelegation`にclosed `OpenStart`／`Resume` mode、optional accepted OPS input reference、Open／StartまたはResume mutation slot、Resume source Action／Attempt、exact RPC params bytesとSHA-256、delivery state、immutable result、bounded last observation、最終RunResultを保持します。Openをaccepted resultとして記録するまでStartを準備できず、Resume modeはOpen／Startを持てません。外部RPCを試みる前に`delivery_unknown`をAction JSONL/WALへcommitします。unknown deliveryはActionをopen、Attemptをrunningのまま保ち、generic retry／completionを拒否します。Human relayのStartを初めて凍結する場合、typed request capabilityからConversation ownerのreceiptと原文を再読・照合し、同じStart builder内で署名してからexact bytesを固定します。凍結後の同一invocation内retryは保存済みbytesをそのまま使います。Resumeも現在のTask Run fence内に限り同じidempotency key／bytesで有限retryし、unknownでrequestが終了した後は再送しません。確定したowner rejectionだけはrejected slotとfailed Action／Attemptを一transactionで保存し、Harness RunResultを捏造しません。transport error、interrupt、timeoutはrejectionではなくunknownのままです。受理済みStart／ResumeからRunResultとterminal Action／Attemptへの遷移も一transactionでcommitし、reopen時にbytes hash、slot order、status transition、native identityとTask／Run uniquenessを検証します。

source adapterはcanonical Task ownerのGetでRunとoptional accepted OPS claimを確認し、Task generation fence内でのみOpen／Start／Resume／明示的InterruptRunとAction outcome保存を行います。native-capable Taskは作成時にHarness ownerの`verification-digest`出力をimmutable `ExpectedCriteriaRevision`として固定します。後からの変更やlegacy Taskのbackfillは拒否し、Actionの最初のAttemptは同じpinを保存してOpen／Start前に一致を検査します。Resumeは同じTaskのauthenticated owner claimが結んだ最新expected Runと保存済みsource IDsを再確認し、Task pinを使って新しいAttemptのproofを採用します。各mutating requestはSDK encoderのexact bytesとidempotency keyをActionへ先に固定し、`AwaitRun`は空のinterrupt prefixでread-only pollingします。

`completed`かつ`verification=passed`に加えて、RunResult criteria revisionとTask pinの一致、nonempty unique verifier evidence、unresolved Actionの不存在を確認します。StartResultのchild Task／Run／Thread IDsでterminal `RunGet`を照合してcanonical RunResult bytesを一致させ、EventsReadを連続sequenceと同じchild identityで読みます。`action.prepared(kind=verification,name=process.exec)`→`action.dispatch_started`→exit 0かつcapture completeの`action.completed`→最後の`run.terminal`という順序と、EvidenceRead `raw/v1` zero rangeのID／range／sealed metadata／lowercase SHA-256／byte countを確認します。zero-rangeの`partial=true`は許容し、full capture bytesのintegrityまでは主張しません。

採用時はraw RunResult bytesとterminal Action／Attemptを一transactionで保存し、そのRunResult hash、criteria pin、terminal event／sequence、verifier Action／Attempt/completion IDs、Evidence ID／raw hash／byte countをcompact immutable proofとして同時に保存します。same-Thread Resumeのproof readerは対象Runのterminal sequenceまでThread-global連続event prefixを検証し、前のRunの履歴を許可しつつ、verifier／terminal evidenceは対象Runだけに限定します。known receipt／Run／Session IDsのread-only reconciliationはidentityとterminal proofが一致した場合だけ新Runを採用し、read failure、running、unknown、ID mismatch、proof欠落はsuccessful statusにせずunknown／blockedにします。replayとrestart recoveryもTask pin、source claim、proofのRunResult hash／criteria／evidence consistencyを要求します。Human OriginProof source wiringとfocused testsはありますが、production live E2Eとrestart後のunknown delivery reconciliationは別gateです。

### process・protocol境界

- COREは固定のbinary pathとconfig path（絶対path）で子process`rencrow-harness serve --stdio --config <絶対path>`を起動する。shell文字列で組み立てず、listener PORTを持たない。起動設定は[RenCrow_Harness委譲設定](05_設定リファレンス.md#rencrow_harness委譲設定)を参照する。
- protocolはUTF-8のJSON-RPC 2.0を1行1objectのNDJSONで送る。1frame最大16MiB、深さ64とし、重複key、trailing値、不正UTF-8は拒否し、batchは未対応とする。stdoutはprotocol専用、stderrは機密を含まない診断だけとし、最初に`initialize`でprotocol version `rencrow-harness/v1`を照合する。
- Codex App Server、ACP、MCPとの互換は主張しない。method／DTOの詳細はRenCrow_Harness source moduleの内部契約であり、COREはprotocolのclientである。CORE Public APIとして再公開しない（[RenCrow_Harness native RPCとの境界](06_Public_API仕様.md#rencrow_harness-native-rpcとの境界)）。
- CORE側が持つのは、新設adapter`internal/adapter/nativeharnessclient`とcomposition wiringだけとする。既存の`ToolHarness`、`super_agent_harness`とは別名で、それらを置き換えない。HarnessはCOREの`internal/*`をimportしない。COREはHarnessのstore driverやruntimeを取り込まず、`pkg/client`のprotocol clientだけを使う。Harness moduleをimportするのは子package`nativeharnessclient/delegation`（とtest用helper、composition file）だけとし、config、domain、orchestratorは型の境界（domainのport、orchestratorのadmission interface）だけを持つ。architecture testがこれを固定する。
- connectionの主体はhostのtrusted profileで固定し、payloadの自己申告を認証に使わない。CORE用profileの値は[RenCrow_Harness委譲設定](05_設定リファレンス.md#rencrow_harness委譲設定)を正本とする。principal文法は`^[a-z][a-z0-9_-]{0,31}:[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`とする。

### 委譲の意味

- COREは親Task／Runの中に委譲Action／Attemptを一つ記録し、そのAttemptのidempotency keyで`turn/start`を呼ぶ。HarnessはTurn、子Task、Runを一transactionで作り、`ParentTaskID`へ`upstream.task_id`を記録する。親子は別の仕事であり、同義のaliasではない。
- `upstream={owner:"RenCrow_CORE", task_id, trace_id, session_id, thread_id, turn_id, action_id, attempt_id}`は参照であり、authorityを与えない。COREはHarness内部のTool ActionをCORE Actionとして再実行・再発行しない。
- RunResult.statusは`completed`／`incomplete`／`rejected`／`blocked`／`cancelled`／`failed`／`restart_required`の7値とする。`completed`は有効な最終応答の確定だけを示し、Task達成ではない。別fieldの`verification.status`は`passed`／`failed`／`not_run`／`unknown`とする。COREは自身の受入条件とEvidenceで親Taskを採用する。既存のstring／error返却へ変換する場合も、`completed`以外をnil errorの成功にしない。
- COREの取消は`turn/interrupt`へ伝える。receiptは停止信号の記録であり、外部Tool停止完了とは別の事実とする。
- 再開は同じTaskに新RunIDと新TraceIDを発行する。`ResumeInput.limits`は必須で、COREは自身の残予算以内の完全なlimitsを渡す。旧Runの消費とunknownは消えない。client終了や再接続時は同じidempotency keyでreceiptを取得し、二重のstart／resumeをしない。
- 追加入力のdispositionは`next_step`／`interrupt_current`／`next_turn`とし、COREは意味判断してこの値を付けられる。
- COREが渡すContextは四区分の型付き`ContextBlock`であり、[RenCrow_Harnessへ渡すContextBlock](#rencrow_harnessへ渡すcontextblock)を正本とする。本人が入力した原文を中継する場合だけ`OriginProof`を付け、COREが生成した委譲依頼はAutomationとする。検証式は[RenCrow_Harness委譲の安全境界](07_安全・自動実行・データ方針.md#rencrow_harness委譲の安全境界)を正本とする。

### 委譲対象の選択

- Shiroの対象routeは、execution profile `shiro_native_coding_v1`（LLM Modelのprofileとは別の、CORE実行backendの選択）とする。COREのadmissionまたはorchestratorが認証済み設定から選び、本文keywordやModel出力からは選ばない。
- 選択済みのRunは、成功か失敗かを問わず、既存のShiro作業経路へfallbackしない。対象は当該profileへ明示的にadmitした新規のcoding／workspace作業だけで、それ以外の作業は現行どおりとする。
- 分岐位置とadmission失敗時の扱いは[Shiroのnative coding実行profile](03_キャラクター・エージェント仕様.md#shiroのnative-coding実行profile)、設定の論理項目は[RenCrow_Harness委譲設定](05_設定リファレンス.md#rencrow_harness委譲設定)を正本とする。

### LLM接続・保存・観測・Identity

- LLM接続: Harnessは推論にRenCrow_LLM Gatewayの正規Public APIだけを使い、物理Backendへ直結せず、COREの内部Providerも経由しない。HarnessはGatewayの正式Callerに追加される（RenCrow_LLM側の正本更新は別作業）。COREが自身で行うLLM呼出しの契約は[CORE / RenCrow_LLM Chat境界](#core--rencrow_llm-chat境界)から変わらない。CORE委譲ではShiroの既存Gateway binding（execution alias、`agent_id`／`execution_role`必須）を`binding_ref`で渡し、standalone CLIはmodel routeを使う。どちらも解決済みprofile revisionを固定し、別Model、route、effortへ暗黙にfallbackしない。初回の実bindingはRenCrow_Qwen38_FlashのQwen／MLX構成とし、strict正規化と最終入力のtoken計数APIはRenCrow_LLM／profile側の必須作業とする。
- 保存: Harnessは論理store `harness.execution`を所有する。COREはこのstoreへwriteせず、APIで参照するだけで、CORE DBと同一transactionだとは仮定しない。外部COREのSession／Thread／Turn／Taskは参照だけで、foreign keyをCORE DBへ跨がせない。使用不能なときはfail closedとし、CORE DBの再利用や別の場所へのfallbackをしない。物理配置は[全module共通の物理契約](05_設定リファレンス.md#全module共通の物理契約)を正本とする。新しい保存責任として、RenCrow_Harness module自身のStorage Proposal／Durable Store Manifestで独立storeとして登録する（未登録）。
- 観測: HarnessはEventを自身のstoreへappend-onlyで保存し、EventIDを自分で発行する。COREはHarnessのEventを自分のCanonical Event Storeへ写してCORE事実にしない。相関の規則は[RenCrow_Harness委譲の相関](10_ログ仕様.md#rencrow_harness委譲の相関)を正本とする。
- Identity: Harnessは新しいID体系を持たず、Canonical ID名とprefixをそのまま使うissuerとして追加される。COREへID発行を問い合わせない。所有の異なるIDは`(owner, id)`で区別する。詳細は[RenCrow_Harnessのissuer境界](architecture/identity/IDENTITY_CANONICAL.md#51-rencrow_harnessのissuer境界)を正本とする。

## Prompt Context Assembly

この節を、COREがLLMへ渡すPrompt Context Assemblyの現行正本とします。実装、Viewer、

### 基本原則

LLM入力は、固定情報、記憶、実行時情報、ユーザー入力を明確に分離します。

通常のプログラム処理で一意に決定できる処理へ生成AIを使用しません。AIは要約、意味圧縮、
通常の規則だけでは確定できない曖昧な意味判断に限定します。

### STATIC PREFIX

生成、要約、並べ替えを行いません。

#### Character SystemPrompt

Workspaceの現在のcharacter bundleを唯一の現在人格正本とし、次の4ブロックを定義順に
決定論的に一度だけ連結します。

```text

30_knowledge.md
```

各ブロックの役割は、`00_system`がAgent Identity・人格・存在定義、`10_policy`が判断原則・
対人姿勢・協調方針、`20_scope`が担当範囲・禁止境界、`30_knowledge`がAgent固有の静的知識です。

各ブロックの出現数は必ず1回でなければならず、順序変更、AI要約、AI再構成、AI補完、
RecallPack等からの再注入を禁止します。Prompt Builderは少なくとも各ブロックの出現数と、
必要に応じて各ブロックおよび完成したSTATIC PREFIXのhashを検証します。重複または欠落した
LLM Requestは正常なPromptとして扱いません。

#### Stable RuntimeContext

人格とは分離された、複数Request間で比較的安定したruntime契約です。Agent Registry、
CORE Interaction Policy、Tool Registry、runtime wiringから機械的に構築します。

```text

Interaction Contract
Tool / Capability Boundary
```

Agent本人やLLMの自己申告から構築せず、生成AIを使用しません。Agent Contractにはagent_id、
roles、responsibilities、specialties、inputs、outputs、capabilities、restrictions、
delegatable_work、expected_deliverables、contract_revision等を含めます。Interaction
Contractには委譲先、入出力、deliverable schema、escalation、completion／failure contractを、
Tool Boundaryには利用可能なTool、引数schema、runtime wiring、policy上の境界を含めます。

### Agent Runtime Capability Catalog

有効Tool一覧は、実行に使うproduction Worker `RunnerV2`のmetadataと、設定済みSQLite
Tool Registryのplatform適合行をCORE内で統合して構築します。runtime toolとの名前衝突は
実行順と同じくruntime側を優先します。RenCrow_Toolsの実行fileをdirectory scanで自動登録せず、
`browser.run`やWebwright providerなどCOREが明示的にadapter接続したものだけを利用できます。
一覧取得は実行権限を追加せず、実行は同じWorker Runnerとpolicyを通ります。

COREは同じproduction wiringから`Runtime Capability Snapshot`を決定論的に構築します。実行を所有する
Shiro／WorkerとCoderにはTool、Skill、MCPの利用可能／利用不可と理由を含むfull snapshotを渡します。
会話とroute判断を所有し、Toolを直接実行しないMioには同じsnapshot revisionから分類別の利用可能／利用不可
件数とCORE owner境界だけを投影し、個別Tool／Data Capability全件をpromptへ複製しません。Mioは必要能力を
Orchestratorへ返し、正確な利用可否とpermissionは実行時のCORE policyが判定します。Kuro、Midori、Mioが
直接実行できない能力は、定義済みhandoffでShiro／Workerへ渡します。

DBをAgent能力として公開するときは、物理SQLite fileやtableをToolにせず、CORE所有の
semantic data capabilityへ投影します。`data_capability.describe`は設定済みDBを
`available`、`unavailable`、`restricted`、`blocked`として列挙・説明し、物理pathやrowを
返しません。実データへのアクセスは`movie_catalog.lookup`、`glossary.lookup`のような

名前付きindexによる完全一致を契約にします。任意SQL、table／column／path指定、全件一覧、
部分一致scan、別DBやWebへのfallbackは許可しません。

Conversation L1／Archive、Persona、Advisor、各種audit／workflow store等のprivate／internal DBは
catalog上で所有者と制限理由だけを示し、raw Agent Toolを提供しません。認証済みconversation
scopeや各feature owner serviceの既存projectionだけが参照境界です。未配置DBは`unavailable`、
索引やscope enforcementが不足する能力は`blocked`とし、fileの存在だけでavailableにしません。

Data Capability Catalogの`physical_key`は、設定と互換性を保つためのlogical key
（`storage.databases.<name>`）であり、AgentやViewerへ物理file pathを公開するfieldではありません。
`owner_route_only=true`のentryは、COREがlocal DBを正本として読まず、owner moduleの認証済みread／write
routeだけを実行境界とします。現在このflagが付く`investment`の正本ownerは`RenCrow_TRADE`です。
したがって、CORE側の同名pathが未設定または存在しなくても、登録済みowner routeのread／writeが揃えば
runtime statusは`available`になります。routeが未登録または不完全なら、local fileの存在に関係なく
`unavailable`または`blocked`で閉じます。flagのないCORE-owned storeは、従来どおりCOREの設定済み
storageとそのowner routeの契約で判定します。

Redisはactive-threadの再構築可能なprojectionであり、L1 SQLite正本ではありません。COREは起動時に
既存Redis接続を検証し、稼働中はDebug Viewerのruntime config取得時に同じ接続へ1秒以内のPINGを行います。
結果は`disabled | available | unavailable`として独立表示し、Redis障害だけでCORE全体の
`/health/ready`を失敗させません。接続URL、credential、backend error本文はprojectionへ出しません。

実装済みのsemantic Tool契約は次のとおりです。`data_capability.describe`は
`list_catalog | list_available | describe`だけを受け、20個の`storage.databases` keyを
metadataとして返します。`movie_catalog.lookup`は`kind=movie | person`、名前、最大20件の上限と、
映画の`overview | cast | staff`または人物の`profile | filmography`を受けます。
`glossary.lookup`は`define_term`または`list_category`だけを受け、最大20件を返します。
`music_catalog.lookup`は`kind=artist | song`、完全一致名、任意の歌手名、最大20件だけを受け、
歌手・楽曲metadataと歌唱関係を返します。`lyrics_catalog.lookup`は完全一致の楽曲名、任意の歌手名・言語、
`information=rights | syntax | full_text`だけを受けます。`rights`は本文を返さず、`syntax`は
`non_reconstructable=1`の特徴量だけを返し、`full_text`は`licensed | public_domain | user_owned`、
license reference、`storage_mode=full_text`がDB上ですべて成立する行だけを返します。
entity解決は正規化keyの完全一致と名前付きindexを使い、0件、複数候補、schema／index不足を
明示してfail-closedにします。起動時のschema migration／lookup key backfillはquery-timeの
Agent照会とは別工程であり、照会時にcatalog-wide fallback scanを行いません。

Mioは発話から対象種別、名前、知りたい情報を保守的に抽出し、対応ToolがRuntime Capability
Snapshotに存在するときだけ1回呼びます。たとえば映画概要、cast、staff、人物profile、出演作、
DB一覧、利用可能data、用語DBの利用可否、引用符付き用語／categoryを認識します。固有対象を
確定できない一般質問はこの経路へ奪わず、matched intentでToolが利用不可または失敗した場合も
Web検索や別DBへfallbackしません。映画intentはdata／glossary intentより先に判定します。

Skillは設定済みrootの検証済み`SKILL.md`を起動時にメモリへ読み込み、Workerだけが`skill.read`で
完全一致名から本文を取得します。呼出時の任意path読込やSkill本文による権限拡大は行いません。
MCPは起動時に接続と`tools/list`が成功したserver/toolだけをWorker Runnerへ名前空間付きで登録し、
同じ接続で実行します。未接続、無効、起動失敗、一覧失敗をavailableとして扱わず、別経路へ
fallbackしません。

### Tool / Skill / MCP capability onboarding

新しいcapabilityは、実在するsource/list、production runtime wiring、Worker metadataまたは
catalog、`Runtime Capability Snapshot`、対象AgentのStable RuntimeContext、policy付き実行または
handoffまでが一つの接続契約です。Snapshotに反映されないcapabilityを追加した状態を完成と
みなしません。`workspace/control/tools.yaml`、Prompt、docs、configへ静的な重複一覧を作らず、
runtimeの観測結果だけを現在の可用性として扱います。

| 種別 | onboarding route | 実行境界 |
| --- | --- | --- |
| Tool | Worker `RunnerV2.ListTools` metadata → Snapshot → Stable RuntimeContext | Worker Runnerとpolicy |
| Skill | 設定済みrootの検証済み`SKILL.md` → startup `SkillCatalog`／`skill.read` → Snapshot | Workerのquery Tool。本文は権限を付与しない |
| MCP | 起動・`tools/list`観測 → namespaced Worker adapter／同一client → Snapshot | 観測済みToolだけをWorker policy内で呼ぶ |

各追加ではsource/list、snapshot変換、prompt注入、実行またはhandoff、利用不能時のfail-closedを
契約テストで確認します。認識用Snapshotは権限付与や自動fallbackを行いません。

### Capability revisionとapply／restart境界

Tool、Skill、MCPの現在の可用性は、同じ観測時点のsource/listから作る一つの
`Runtime Capability Snapshot`で表します。Snapshotは少なくとも
`snapshot_revision`、canonical JSONの`snapshot_hash`、生成時刻、各capabilityの`kind`、
canonical name、source revision、source hash、availability、unavailable reasonを持ちます。
`snapshot_hash`は表示順とfield順を正規化した内容から計算し、AgentやLLMの自己申告では変更
できません。snapshot revisionは観測された投影が変わったときだけ進みます。

現在のruntime挙動は次の通りです。

- Agentが追加したToolは、COREの認証済みdynamic registryへ登録され、Workerの許可済み
  execution pathで実行・一覧取得できます。ただし起動済みAgentのStable RuntimeContextへ
  snapshotを即時再注入しません。実行可能なdynamic Toolと、Agentが安定して認識するSnapshotを
  同一視しません。
- Skillは設定済みrootの`SKILL.md`をstartup時に検証したcatalogが正本です。稼働中に追加・変更
  されたSkillは、そのまま`skill.read`やStable RuntimeContextへ反映しません。
- MCPはstartup時の接続と同一clientによる`tools/list`観測が正本です。稼働中の追加、serverの
  再接続、一覧変更は、再観測とSnapshot再生成が完了するまでavailableと扱いません。
- 上記のいずれも、未観測source、任意directory scan、Skill本文、MCP serverの自己申告だけで
  capabilityをavailableにしません。provider、Tool、Skill、MCPを別経路へ暗黙fallbackしません。

Agent作成のcapabilityも通常のonboardingと同じ検証を通ります。Agentは登録requestを作れますが、
登録だけでpermission、route owner、外部送信、supervisor操作を得ません。ToolはCOREのdynamic
registryとWorker policy、Skillは設定済みcatalog、MCPは接続済みclientと`tools/list`観測が
成立しなければ、登録結果を`unavailable`または`blocked`として返します。

反映は`capability apply`という明示的なoperationで行います。apply requestは、期待する各能力の
`kind`とcanonical name、source revision／hash、request_id、idempotency key、request時点の
`current_snapshot_revision`／`current_snapshot_hash`を持ちます。COREはrequestのscope、
capability、source、policy、runtime availabilityを同期検証し、検証後に期待する最終Snapshotの
revision／hashをreceiptへ固定します。requestに任意unit、path、binary、command、PORT、providerを
指定するfieldはありません。

既存Snapshotに期待する全capabilityがcanonical name、kind、source revision、source hashまで
一致していれば、再起動せず`completed`で閉じます。dynamic Toolが実行可能でもStable Snapshotへ
未反映なら、この条件を満たさずapply対象です。新しい観測またはcatalog変更が必要な場合だけ、
COREは現在の応答を返した後に再起動を予約します。

applyの責務は次の境界で固定します。

| 責務 | 所有者 |
| --- | --- |
| capability metadata、schema、enabled、permission、policy、snapshot revision／hash、Public API、receipt | RenCrow_CORE |
| `rencrowctl capability apply|status`の利用者／Agent CLI facade | RenCrow_CMD |
| 応答後に継続するnative Go supervisor worker／subcommandとOS adapter | RenCrow_CORE distribution |
| 再利用可能な通常Tool／helper | RenCrow_Tools（apply／restartの必須依存ではない） |

RenCrow_CMDはCOREのAPIを呼ぶだけで、snapshot計算、policy判定、receipt管理、`systemctl`、
Windows service、macOS launchdの直接操作を実装しません。CORE distributionのsupervisorは
CORE listenerとは別の短命workerとしてrequest_idを保持し、現在の応答が完了してから既知の
`rencrow-core` ManagedTaskへ置換起動を依頼します。再起動中に終了するCORE process自身が、再起動後の
成功を主張してはいけません。再接続後のstatus照会が、永続receiptと新しいinstanceの観測を
`request_id`で再結合します。

Linuxはsystemd user、Windowsはnative service／supervisor、macOSはlaunchd adapterを使います。
三OSとも論理的には同じ`rencrow-core` target、ReservedPort、停止・起動・liveness・readiness・
Snapshot検証を行います。WSL、別PORT、別unit、別binary、別provider、別Toolへの退避は行いません。
固定PORTと所有権、旧instance停止、listener解放、readinessの順序とerror codeは本書の
[予約PORTと同一Taskの置換起動契約](#予約portと同一taskの置換起動契約)に従います。

applyの機械状態は、同期判定と後段phaseを分けて表します。

```text
decision=execute
  -> phase=validated
  -> phase=completed                         (Snapshot一致、再起動不要)
  -> phase=restart_scheduled                 (receipt永続化後、応答返却済み)
  -> phase=stopping
  -> phase=starting
  -> phase=verifying
  -> phase=completed | failed

decision=rejected | blocked                  (人待ちphaseを持たず即時終端)
```

`verifying`では、新instance identity、同じReservedPortのlistener、`/health/live`、
`/health/ready`、期待したcapabilityのcanonical name／kind／source revision／source hash、
receiptに固定した最終Snapshot revision／hashをすべて照合します。一つでも不一致なら成功に
丸めず`failed`とします。失敗後に別PORT、古いSnapshot、未観測能力、別経路の成功値を返しません。
詳細なrequest／responseとclient profileは[Public API仕様のCapability Apply](06_Public_API仕様.md#capability-applyとstatus)、
receipt配置は[設定リファレンスのCapability receipt](05_設定リファレンス.md#capability-applyとreceipt)、
policy判定は[安全・自動実行・データ方針](07_安全・自動実行・データ方針.md#capability-applyの同期policy)、
観測eventは[ログ仕様のCapability apply](10_ログ仕様.md#capability-applyの観測)を正本とします。

### Capability apply受入境界

実装完了には、文書の存在だけでなく、次の機械検証とcanonical runtime確認を含めます。

- 同じsource/list、同じpolicy、同じConfigから同じSnapshot revision／canonical hashが生成され、
  unavailable reasonがavailableへ変換されないこと。
- Agent-created Toolのdynamic registry反映と、Stable Snapshotがstartup固定であることを別々に確認し、
  Skillのstartup catalog、MCPの接続／`tools/list`／同一client lifecycleを検証すること。
- apply requestの必須field、kind／canonical name、source revision／hash、current Snapshotの
  stale検出、認証scope、idempotency conflict、policy rejected、source／dependency blockedを検証すること。
- 期待capabilityが既にSnapshotへ一致している場合に再起動しないこと、未反映の場合にreceiptを先に
  atomic保存し、現在のresponse後へsupervisorを引き継ぐことを検証すること。
- receiptの再読込だけで再起動途中から復帰でき、停止したCORE processがcompletedを自己発行せず、
  新instanceのidentity、同じReservedPort、`/health/live`、`/health/ready`、Snapshot membership／
  hashを別processから検証すること。
- 所有不明process、別TaskのPORT、listener解放timeout、起動失敗、readiness timeout、Snapshot mismatch、
  unknown requestを、別PORT・別unit・別provider・fallbackなしで安定errorへ閉じること。
- Linux systemd user、Windows native service／supervisor、macOS launchd adapterで同じrequest、receipt、
  phase、error、status recoveryを確認し、WSLを経路へ含めないこと。
- `rencrowctl capability apply|status`、Public API、CORE log、receiptが同じ`request_id`／`trace_id`で
  相関し、CLI stdout／stderrと秘密情報の非混入を確認すること。

### DYNAMIC AREA

現在の会話、記憶、実行状況によって変化する情報です。

#### RecallPack

RecallPackは今回の推論に必要な過去情報を選択した想起結果であり、過去履歴そのものでも
SystemPromptでもありません。L0はShortContextとRollingSummary、L1はRaw Conversation検索結果、
Search Cache、当日Knowledge、L2はthread／期間要約、L3はLongFacts・長期エピソード・確定済み
Memoryです。UserProfileの確定情報はDBから取得し、Knowledgeはlexical、metadata、vector、
rule、relation等で検索します。検索と通常のscore計算に生成AIを使用しません。曖昧性が極めて
高い候補間のrerankだけを例外として許可します。

##### CategoryRecallSourceと決定論的なsource選択

永続DBはすべてRenCrowの広義のMemoryであり、Agent／workflowが会話、作業、診断、監査その他の認証済みrequest purpose／role／authenticated scopeで必要な情報を想起するsourceである。これはRenCrowの永続化に対する必須不変条件であり、Viewer表示、保管、owner service内部処理、Tool登録、catalog掲載だけでは完了とみなさない。各DBの所有moduleは、物理DB、path、table／column、任意SQLをAgent／LLMへ渡さず、readには用途別のread-only `CategoryRecallSource`、owner-service adapter、または同等のnamed Toolを、writeにはowner moduleの検証済みcommand／workflowを必ず提供する。read projectionはprovenance、scope、freshness、validation、role、budgetを、writeはschema、migration、validation、audit、idempotencyを検証する。安全な読み書き経路がないDBは、実装済みや利用可能と扱わず、Data Capability Catalogで`blocked`または`unavailable`として理由を公開する。`restricted`／`owner_service_only`は経路の存在や完了を示す状態ではない。

Agent／workflowのDB読み書きは、次のowner経路だけを通る。

```text
Agent／workflow request（purpose／role／authenticated scope）
  -> CORE route／policy
  -> owner module
       read  -> purpose-specific Recall Adapter／named Tool -> bounded Recall projection
       write -> validated command／workflow -> owner write receipt
  -> Agent／workflow
```

全カテゴリの意味データを会話から想起する入口は、COREが所有する`CategoryRecallSource` portと
決定論的な`CategoryRecallRegistry`に統一します。個別のcatalog DB、module-owned DB、生成AI routeを
Prompt Builderから直接呼び出しません。portのqueryは次の5項目だけを受け、現在の発話、確定済みの
active domain、認証済み利用者scope、request時点、hard limitを明示します。

| query field | 意味 |
| --- | --- |
| `message` | 現在の利用者発話。source選択と決定論的なlexical／metadata検索の入力 |
| `active_domain` | Routerが確定した現在domain。空または未確定でもstatic marker／entity hintで選択でき、値がある場合は追加signalとしてsource選択を絞る |
| `user_scope` | 認証済み利用者と許可されたscope。別利用者、未許可private／family scopeへ拡張しない |
| `time` | freshness判定に使うCOREのrequest時点。source側の時計で置換しない |
| `limit` | 全カテゴリ合計およびsourceごとのhard上限。sourceやLLMが拡大しない |

`CategoryRecallSource`は、検索結果とsource failureを同じmachine-readable resultへ返します。recordの
wire fieldは`category`、`source_id`、`record_id`、`title`、`summary`、`provenance_urls`、
`retrieved_at`、`validated_at`、`fresh_until`、`state`、`sensitivity`、`scope`、`roles`、`score`を
必須とします。failureは少なくとも`category`、`source_id`、安定した`code`、`state`、`retryable`、
`observed_at`を持ち、自由文だけで失敗を表しません。recordの`state`はvalidationと鮮度を表し、
`stale`、`invalid`、provenance欠落、scope不一致、またはsource unavailableの結果はRecallへ注入
しません。failureと除外理由はRecall traceへ残します。

`CategoryRecallRegistry`は、静的なcategory marker、現在のactive domain、起動時に構築したentity hint
indexだけをsource選択に使います。毎ターン全DBをqueryすること、sourceのrecord本文をRegistryへ複製する
こと、Registryが生成AIへrouteすることを禁止します。Registryが選んだsourceだけが上記queryを実行し、
通常の検索、候補抽出、score、freshness判定はDB／Registry／Clock／Ruleで決定します。

source登録の正本は次です。

- 全カテゴリ共通sourceは、validation済みで利用者scopeとprovenanceを持つL1 Knowledgeです。newsを含む
  外部取得物は、未検証stagingではなく、このL1 promotionを通過したrecordだけを登録します。
- `movie_catalog`と`hobby_graph`は、COREのconfigured DB pathを使うread-only専用sourceとして登録します。
  Movie／Hobbyの個人interaction、rating、note、preference、ViewerのD0 root状態はowner scope schemaが
  まだないため、CategoryRecallへ注入せず、公開catalog recordだけを返します。ViewerのD0/D1カードは
  CategoryRecallのsourceやMemory L1のprojectionではありません。movie_catalogの映画側credit／provenance
  とhobby_graphの汎用work itemを結ぶViewer projectionも、CategoryRecallへ個人評価を渡しません。
- investmentなどmodule-owned DBをCOREが直接読むことは禁止します。validated L1へpromotionされたprojection
  または所有moduleのgateway adapterだけをCategoryRecallSourceとして登録します。COREのDB pathを増やして
  sibling moduleの正本を取り込む設計にしません。

`storage.databases`の20 catalog keyと、そこから投影した`data_capability`／Agent Stable Runtime Contextは同じ起動時snapshotを参照します。module-owned storeのrouteが未登録、未設定、または`ready`でない場合は、そのoperationを`unavailable`または`blocked`として返し、別DB、旧route、Web、fake endpointへfallbackしません。`investment`の6 logical domainとAgent operationの一覧は[機能仕様の固定契約](02_機能仕様.md#data-capability-catalogとinvestmentの固定契約)に従います。

CategoryRecallの結果はRecallPackへ`CategorySnippets`として追加します。これはaccepted recordのprompt用
projectionであり、会話履歴やcategory DBへ再保存する履歴ではありません。`HasContext`、prompt message
serialization／ordering、recall budgetとbudget drop、role／sensitivity／scope filter、RecallTraceの
採用・除外・source failureを同じCategorySnippets経路へ通します。promptへ入れないrecordも、理由を
`stale`、`invalid`、`missing_provenance`、`source_unavailable`、`scope_denied`、`role_denied`、
`budget_dropped`等の安定codeでtraceします。通常応答の履歴には、想起recordやCategorySnippetsを保存せず、
COREが実際に生成・発話したassistant eventだけを保存します。

role filterの公開roleはChat personas向けの`chat`、`worker`、`heavy`、`creative`です。`coder`、`wild`、
`ops`は通常Chatと同じ共有を受けず、実行目的、source policy、sensitivity、認証scopeに基づく明示的な
policy bindingがある場合だけ許可します。freshness期限を持つnews／investmentは、`fresh_until`を過ぎた
record、検証失敗、provenance欠落、source unavailableを事実として注入せず、除外とsource状態をtraceします。

runtimeは`storage.databases`で解決したconfigured DB pathだけを使います。source pathがmissing、未設定、
またはread-only adapterが利用不能でも、利用可能な別sourceの結果だけを返す部分失敗とし、欠落部分を
生成、別DB直読、別route、legacy fallbackで埋めません。全sourceが使えない場合はmachine-readableな
`source_unavailable`を返します。CategoryRecallの実装は次の順序で進め、既存のPrompt Contextと
source registry contractを壊さないことを受入条件にします。

1. **Contract／Red**: query、record、failure、Registryの型と安定codeを先に定義し、marker、active domain、
   entity hintに無関係なsourceを選ばないこと、全DB query／生成AI routeを行わないこと、履歴へ保存しないことの失敗テストを固定する。
2. **Source／Green**: L1 validated Knowledge、read-only movie catalog／hobby graph、L1 promotionまたは
   module gateway adapterを実装し、configured path、validation、provenance、freshness、scopeを検証する。
   writeはowner moduleのschema／migration／validation済みcommand／workflowだけを通し、auditとidempotencyを確認する。
3. **RecallPack／Trace**: `CategorySnippets`を`HasContext`、prompt、budget、role filter、trace全層へ
   接続し、stale／invalid／missing provenance／unavailable、role／scope拒否とbudget dropを記録する。
4. **Runtime／Integration**: startup Registryとentity hint indexを構築し、missing sourceの部分失敗、
   no-history、investmentのCORE DB直読禁止をruntime wiringで確認する。
5. **Production Agent E2E**: 認証済みproduction Agent／workflowのrequest purpose／role／scopeから関連category
   だけが選ばれ、readは用途別Recall Adapter／named Toolを通ってprovenance、scope、freshness、validation、role、
   budgetを満たしたprojectionだけを返し、writeはowner moduleの検証済みcommand／workflowを通ることを確認する。
   read／write双方の`Agent-owned production E2E`を必須とし、testだけのscope注入、Viewerのpublic scope、owner service内部処理、
   Tool登録、catalog掲載だけを成功証拠にしない。source failure、履歴非保存、traceの採用／除外理由も同じtraceで
   再検証できなければ完了としません。

RollingSummary、MidSummaryの新規生成、Memory Candidate抽出、曖昧な関連性判定にはAIを
使用してよいものとします。ただしAIが推測したUserProfileやMemory Candidateを、確認なしに
confirmed／pinned情報として扱いません。

#### 記憶処理の一方向runtime境界

記憶の決定的処理は、次の入口からCOREのowner routeへ一方向に流します。command、validator、receiptの
詳細は[機能仕様のCLI-first／LLM-residual契約](02_機能仕様.md#記憶処理のcli-firstllm-residual契約)を正本とし、
この節ではruntimeの責務だけを固定します。

```text
通常Chat: SaveMessage -> L1 Raw event -> ProfilePromotion -> candidate -> CORE validation／dedupe -> receipt
外部export: RenCrow_Tools native Go local inspect／convert／verify -> deterministic bundle -> RenCrow_CMD one request -> CORE Common Raw -> projection -> RecallPack
operator: terminal -> RenCrow_CMD -> authenticated CORE owner API -> policy -> transaction／outbox -> receipt
```

| runtime boundary | 所有者 | この境界で決めること |
| --- | --- | --- |
| terminal／external adapter | RenCrow_CMD／RenCrow_Tools | CMDはcommand構文・HTTP mapping・認証tokenのtransport・response表示のみ。Toolsはlocal native Go inspect／convert／verify・bundle出力のみ。どちらもDB、owner、request ID、policy、scope、memory state、receiptを決定しない |
| authenticated owner route | RenCrow_CORE | user／actor／scope、request／idempotency identity、policy、ID／hash／順序、状態遷移、dry-run／apply、dedupe、retention、transaction／receipt、失敗状態 |
| semantic residual | RenCrow_LLMを経由したCOREのProfileExtractor／ThreadSummarizer | 候補の意味抽出、summary／keywords。副作用、確定状態、scope、rankingは持たない |
| prompt／Recall | RenCrow_CORE | `confirmed | pinned`かつnon-sensitiveのbounded UserMemory projection、ranking、budget、trace、injection |

ProfilePromotionのsource／focused実装はCOREがbounded projectionを読み、LLMの前後でdeterministic validation／dedupeを
行います。Raw、candidate、assistant-only evidence、private本文を直接Promptへ渡さず、通常ChatはProfileExtractorの完了を待ちません。EndTurnのconversation
responseとmemory persistenceは別typed outcomeとし、trace、state、archive followerの部分commitをcompletedへ丸めず、
transactionまたはdurable outboxのreceipt終端を待ちます。UserMemory owner routeとRecall／trace、archive、lifecycle、
Parquet owner workflowは実装・配備済みです。ChatGPT Common Rawはproduction backfill、全ProfilePromotion job終端、
machine finalize、Mio実会話のRecall traceまで2026-08-24 JSTに確認済みです。他source adapter、全Agent、全DBのE2Eは
個別の配備gateとして扱い、この結果だけで完了にしません。

ProfilePromotionの実行順は`ListProfilePromotionProjection -> ProfileExtractor -> deterministic validation／dedupe ->
CompleteProfilePromotionBatch`です。projectionはowner-scopedなactive L1 rowの`candidate | confirmed | pinned`だけを
state優先度、`updated_at`、`rowid`で安定選択し、そのprefixから最大32件／statement 512 rune／合計8192 runeにboundedします。
ViewerのUserMemory全件確認は、汎用L1 event本文をrequestごとに全走査せず、同じSQLite内の
`l1_user_memory_viewer_projection`を使います。この表はL1 eventのinsert／update／delete triggerから同期される
再生成可能な検索索引で、memory stateやEvidenceの正本ではありません。Viewerは索引でIDをbounded選択した後、
bounded DTO索引です。Viewerは索引行をUserMemory schema／state／Evidenceで再検証して返します。
statement／Evidenceの部分一致は、DTO projectionのtriggerと同期するFTS5 trigram索引を使います。
検索語は3–256文字のphraseとしてescapeし、再起動直後のcold cacheでも全候補本文や2GBの汎用L1 event tableを走査しません。
valid rowの合計が超過してもfailureにせずprefixで打ち切ります。
選択rowのcorruptionはskipせず、read failureと同様にLLM呼出前の有限failureへ終端します。extractorへのLLM responseは
64KiB以下のexact JSON object `{preferences: map[string]string, facts: []string}`だけを許し、未知key、前後文字、markdown、
非string preference、空要素、長さ超過、CR／LF／NULを拒否します。raw候補最大16件をdedupe前に検証し、COREがtype、scope、
sensitivity、confidence、candidate state、batch evidenceを所有します。同じbounded projectionをextractor contextとexisting dedupeに
使い、未boundedな全projectionをdedupe専用に追加取得しません。候補は`candidate`から自動昇格せず、invalid時は
completeせずfailed receiptで終端します。

strict validationに失敗した場合だけ、COREは固定訂正指示を同じ論理要求へ1回だけ追加してrepair生成を行い、返答を再度strict validationします。1回の`Extract`（複数groupを順に処理する場合を含む）でrepairできるのは最大1回です。provider呼出の失敗は`unavailable`として直ちに返し、内部repair／retryを行いません。初回またはrepair後の不正応答は`invalid`です。MemoryPromotion Serviceがjobの`last_error`へ書く値は`profile_extractor_unavailable`または`profile_extractor_invalid`などの固定codeだけで、provider error、raw response、promptは永続化しません。`context.Canceled`は`failed`へ進めず、leaseをdeferして再試行対象へ戻します。

LLMを残す理由は、同じbounded入力から利用者本人の安定した事実・嗜好と、質問・引用・第三者資料・仮説を意味的に区別する曖昧性が残るためです。取得、sanitize、上限処理、schema／policy検証、dedupe、状態遷移、保存、receiptはCLI／COREの決定的Boundaryで実行します。ProfilePromotionの論理request budgetは、evidence block最大3000 rune、既知profile context最大800 rune（完全な行のみ）、material digest最大800 rune、初回prompt最大6648 rune、repair指示込み最大7160 rune、初回`GenerateRequest.MaxTokens=1024`、groupごとの候補最大4件、全group merge後最大16件です。strict validation違反時の1回限りrepairは固定categoryのみを使い、raw応答を再入力せず、候補2件、各文字列100文字、`MaxTokens=512`へ縮小します。これは物理Modelの`n_ctx`ではなく、COREとRenCrow_LLM間の三OS共通契約です。

ThreadSummarizerはthreadごとに正規RenCrow_LLM routeを一回だけ呼びます。LLM responseは64KiB以下のexact JSON
`{"summary": string, "keywords": []string}`に限定し、summaryは正規化後1〜1024 rune、keywordsは正規化後
1〜64 runeを3〜5個かつcase-fold keyで一意とします。COREがthread／session、source turn count、順序index、speaker、
本文をversioned canonical encodingへ束縛したSHA-256 evidenceとrolesを導出し、LLMにattributionを生成させません。
summaryと`schema_version`、`generation_mode=llm | deterministic_fallback`、provider、固定failure code、evidence hash、
source turn count、roles、生成時刻のreceiptは同じarchive SQLite transactionでcommitします。raw provider errorとinvalid
outputは保存せず、fallbackは必ず`deterministic_fallback`として区別します。receiptのない既存summaryはread projectionで
`legacy_unverified`とし、LLM成功へ昇格しません。

EndTurnのcanonical入口は独立した`turn_id`、`trace_id`、`root_task_id`、User／actual Agentの`message_id`を必須にするtyped `ConversationTurnRequest`です。CORE ingressはこれらをUUIDv7で一度だけ生成し、相互または別種IDから派生させず、durable active-thread stateを基に両発話を同じthreadへ配置します。L1 SQLiteの一transactionで
2 Raw messages、event log、User側ProfilePromotion job、実際に使用したRecallPackのtrace一式、turn receipt、required
follower outboxをcommitします。turn ID＋canonical payload SHA-256が同じ再送はstored result、同じIDでhashが異なる再送は
`conflict`です。時刻、`turn_index`、process-local sequenceはidentityに使いません。

Redisはactive-thread projection、archive SQLite／VectorDB／Redis cleanupはthread-close followerであり、SQLite正本の
transaction参加者ではありません。outboxは`turn_id + target`でidempotentにclaimし、commit直後とstartupにpending／stale
runningを再生します。thread-close followerはL1のIDからsourceを再構成し、ThreadSummarizer receiptを経てarchive／vector／
cleanupの順に収束します。`ConversationTurnResult`は`completed | partial | failed`、turn／trace／message／receipt ID、各follower
status、固定error codeだけを返し、private本文やraw backend errorを含めません。SQLite commit後のfollower失敗は`partial`、
SQLite transaction失敗は`failed`であり、いずれもconversation response自体の成否と混同しません。

#### Recall／Trace owner read boundary

owner readはlegacy Viewer routeを直接公開せず、COREの一方向routeへ接続します。focused実装とtestは完了していますが、
配備binary、migration済みproduction DB、configured ownerを使うAgent／CMDのcanonical E2Eは別gateとして未確認です。

```text
RenCrow_CMD
  -> GET /v1/memory/user/recall?query=<1..512 rune>&limit=<1..50,default12>
  -> CORE authenticated user + ToolExecutionScope/DataScopeUser
  -> deterministic UserMemory ranking (max scan 100)
  -> owner-scoped trace Start(started) -> items/injection -> Finish(completed|partial)
  -> bounded projection + typed receipt
```

Trace list／showは`GET /v1/memory/user/traces`とescaped exact-ID routeで、owner_id一致のsummaryだけを返します。
`recall_trace.owner_id`は新規traceで必須、owner不明legacy rowはowner APIから非公開です。通常AgentのBeginTurn traceも
owner_idとUserMemoryの選択／除外理由を持ちます。active、非superseded、非decayed、`confirmed | pinned`、normal sensitivity、
scope適合だけを採用し、candidate、sensitive、inactive、superseded、decayed、budget drop、source failureをtraceへ残します。
LLMはranking／state／scopeを決めず、short context／full transcript／sensitive summaryはowner projectionから除去します。
途中のstore／source／index failureをcompletedへ丸めず、`partial`またはtyped `blocked`で終端します。

#### Parquet owner export／verify boundary

ParquetはCORE owner APIの明示的なsource実装です。CMDの`memory export parquet`は
`POST /viewer/memory/export/parquet`を空bodyまたは`{}`で1回呼び、`memory export verify --request-id`は
escaped targetを一つだけ持つ`GET /viewer/memory/export/{request-id}`を1回呼びます。POSTは`cmd-control`、GETは
`cmd-diagnostics`で、loopback／owner Bearer scopeを既存Memory boundaryから受けます。COREがowner／actorとcurrent request IDを生成し、
callerのpath、user、current request ID、DB情報を受け付けません。

configured absolute `storage.memory.cold_export_dir`内で、Archive SQLiteの一つのread snapshotから5つのdeterministic relative
Parquet fileを作り、rows／bytes／SHA-256 manifest、private staging、atomic finalization、receipt、cleanup／quarantineを確定します。
source DBは変更せず、verifyはexact targetのartifact manifest／file hash／countを再検証し、同一export requestの再送もartifactを検証して
replayします。CMDはDBを開かず、receipt／hashを計算せず、typed relative metadataだけを表示します。旧24時間／env fallbackのautomatic
Parquet jobは現行runtimeで起動・定義しません。

Conversation Memory等に保存された過去時点のPersona snapshotは履歴・監査用途として保持
してよいものの、現在ターンのLLM入力へ再注入してはなりません。現在の人格は常にWorkspaceの
現行Character SystemPromptです。

保存済みAgent発話が反復退化していてもConversation Memoryの監査証跡は削除・改変しません。
RecallPackのprompt投影境界は、連続同一runeまたは隣接反復motifを機械判定し、該当する
Agent発話だけを会話例、発言帰属要約、`expression history`から除外します。ユーザー発話は
引用や意図的反復を含む正本入力なのでこの判定の対象外です。除外は`RecallTraceItem`へ
`filtered_status`と理由を残し、保存正本とLLM入力を混同しません。

#### Variable RuntimeContext

Requestごとに変化する現在状態です。`mode`、Router確定済みの`route`、rule判定の`tone`、
System Clockの`time`、job／task／execution／error／completion等の`state`、機械取得した
`expression history`を含みます。Prompt Builder自身がrouteやruntime stateを再判断せず、
現在時刻を固定SystemPromptへ埋め込みません。

#### User Message

現在のユーザー発話を常に最後へ配置します。ユーザー入力をSystemPromptへ埋め込まず、添付
ファイル等は定義済みMessage Contractに従って付加します。

### RenCrow_Harnessへ渡すContextBlock

Status: 採用済み設計。COREのCategoryRecall exact-source producerとnative context source resolverはfocused実装済み（2026-10-09）。実ActorによるHarness Start／retryのE2E、実LLM利用、production deploymentは未確認です。COREのSTATIC PREFIX hashが安定していることだけでは、これらの運用受入を意味しません。

[RenCrow_Harness委譲境界](#rencrow_harness委譲境界)でHarnessへ作業を委譲するとき、COREは標準入力順序の前四区分を型付き`ContextBlock`で渡します。現在のUser Messageは区分としてではなく、`StartInput.input`で渡します。

| `kind` | 標準入力順序の区分 |
| --- | --- |
| `character_system_prompt` | Character SystemPrompt |
| `stable_runtime_context` | Stable RuntimeContext |
| `recall_pack` | RecallPack |
| `variable_runtime_context` | Variable RuntimeContext |

- 公開fieldは`kind`／`text`／`revision`／`source`の4個だけとし、digestやoriginを足さない。`source`は`null`または出所参照`{owner, source_id, raw_hash, projection_version, range{start, end}, origin, sequence}`である。`source`の`origin`は出所参照の値であり、本文が認証済みであることの証明にはならない。
- `context_blocks`に`user_message`を入れた要求は`INVALID_REQUEST`とする。現在のUser原文は`StartInput.input`が正本であり、HarnessがUser区分を一回だけ構成する。
- `context_blocks`は最大256件とする（`StartInput`の配列上限）。COREはblockを作る前に件数を検査し、超過した要求は送らずに拒否する。
- `revision`は内容addressであり、版の順序や本人認証を意味しない。次の式を正本とし、他文書は式を複製せずこの小節を参照する。

```text
revision = "ctx-v1:" + hex(SHA256(
  b"rencrow-context-block/v1\0" + LP(kind) + LP(text) + SOURCE(source)
))
LP(s) = uint64_big_endian(len(UTF8(s))) + UTF8(s)
SOURCE(null) = 0x00
SOURCE(ref)  = 0x01 + LP(owner) + LP(source_id) + LP(raw_hash)
             + LP(projection_version) + LP(decimal(range.start))
             + LP(decimal(range.end)) + LP(origin) + LP(decimal(sequence))
```

- `source`なしは`0x00`のNULLタグで表し、空文字列と区別する。`text`の空白、改行、Unicodeはそのまま入力し、trimや正規化をしない。
- request_id、受付時刻、進捗をCharacter／Stableへ混ぜない。同一の`kind`／`text`／`source`なら同じrevisionになる。Variableは必要時に本文が変わり、revisionも変わる。出所やscopeが変わる場合は`source`または対応するprofile revisionを変更する。
- Harnessは同じ規則でrevisionを照合し、`text_digest = SHA256(UTF8(text))`を受信側で独立に計算する。`SourceRef.raw_hash`は原本全体のhashであり、引用範囲のtext_digestと同一とは限らない。logical revisionの一致をKV cache hitと同一視しない。
- native Worker BeginTurnのCategoryRecallだけがprivateなtyped provenance intentを付けます。このintentは認証・権限を付与しません。intentを受けたL1 Knowledge sourceは、既存の非空`SummaryDraft`を既存どおりtrimしたbytesが、owner検証済みCommon Raw全体に存在するときだけ、そのSummaryと正確に一致するRecall blockへSourceRefを付けます。`raw_hash`はtrim前の原本全体、`range`は最初に一致した半開UTF-8 byte範囲、revisionは`knowledge-recall-quote/v1`です。要約を変更・生成せず、Raw本文をpromptへ渡しません。title／URL等のenvelope、Raw fallback、原本と一致しない要約は`source=null`です。認証、receipt、hash、lifecycle、policyの不一致は候補を除外して固定failure traceへ記録し、sourceなしの成功へdowngradeしません。その他のCategoryRecallは既存のFTS／projection選択とsource-null動作を維持します。
- このSourceRefはCORE内部のtyped Prompt metadataであり、通常LLM provider JSONへ含めません。private Rawの検証は、typed `ToolExecutionScope`で認証userと`DataScopeUser`を検証したCORE owner readに限定し、AgentはさらにAgent actor／`agent_orchestrator`／`DataScopeInternal`を必要とします。query文字列、role、metadataからidentityを導出しません。
- COREは既存`assemblePromptContext`のtyped messagesから区分をそのまま取得し、`source`を付与してrevisionを生成し、immutable snapshotを委譲Actionの根拠として保存する。`renderSystemMessages`でflattenした文字列から分類を復元しない。
- Shiroの既存経路にRecallがなかったことをgoldenとして固定せず、委譲に必要なRecall投影を正規経路で供給する。
- Model messagesへのrole写像（Character=system、Stable=developer、Recall／Variable=user data envelope等）はHarnessが所有し、COREはこれを定義・再実装しない。
- standalone CLIでは、Characterは明示profileの実行役説明、Recallは空または利用者指定とし、CORE人格を自動取得しない。
- 検証として、COREとHarnessが同じ入力から同じrevisionを独立に再現すること、flatten済み文字列から区分を復元する実装が存在しないことを実装時のtestで確認する。

## Agent協調runtime境界

Agent間協調はCORE domainのruntime契約であり、推論target側のAgent Runtime、RenCrow LLM Runtime、Persona、個別Modelの機能ではありません。論理構成を次で固定します。

```text
Sender Agent
  -> CORE Agent Router
     -> Agent Registry / AgentKnowledgeView
     -> policy / Role binding / runtime availability
  -> AgentWorkRequest
  -> Recipient CORE Agent
     -> Execution Role / runtime target
  -> AgentWorkResult
  -> deliverable validation / observation
  -> Sender Agent
```

### Agent RegistryとRouter

Agent Registryは「キャラクター・エージェント仕様」のAgent Contractを一意な`agent_id`で保持し、Agent一覧、個別Contract、`AgentKnowledgeView(self, peer)`、capabilityによる候補検索をCORE内部へ提供する。現在のAgentProfile catalog、Workspace control、Role binding、runtime healthは入力projectionとして統合してよいが、いずれか単独を完全なRegistryとみなさない。Registryは権限を新規付与せず、runtime policyとproduction wiringを越える宣言を拒否する。

Routerは次の順に解決する。

1. 明示command、利用者が指定したAgent、既に確定した返却先を優先する。
2. Registryで`delegatable_work`、`inputs`、`capabilities`、`restrictions`を満たす候補だけを抽出する。
3. policy、Role binding、runtime availability、data scopeを検証する。
4. 得意分野、依頼元の`expected_deliverables`、候補の`outputs`の適合度から候補を選び、選択根拠と双方のcontract revisionをtraceへ残す。

候補なし、契約不整合、権限不足、Role未定義、runtime unavailableを同じfailureへ丸めず、別のerror codeとする。明示指定Agentを黙ってfallbackしない。新しい専門Agentの追加はContractとproduction wiringの登録で行い、Router本体にAgent名の分岐を追加しない。PORTAL等の公開recipient allowlistは外部公開契約であり、Registryへの登録だけで自動公開しない。

### Agent IPC

Agent間の論理IPCはtransportに依存しない次のenvelopeを使用する。process内call、queue、HTTP等へtransportが変わってもdomain fieldの意味を変えない。

| envelope | 必須内容 |
| --- | --- |
| `AgentWorkRequest` | `request_id`、`trace_id`、`task_id`、`session_id`、`from_agent_id`、`to_agent_id`、`from_contract_revision`、`to_contract_revision`、`work_type`、入力または参照、制約、`expected_deliverable` |
| `AgentWorkResult` | `request_id`、`trace_id`、`task_id`、`from_agent_id`、`to_agent_id`、`from_contract_revision`、`to_contract_revision`、`status`、`deliverable_type`、成果物または参照、証跡、制約、未解決事項、次の行動、error |

共通envelopeをAgentごとに別schemaへ分裂させない。Request payloadは実行先の`inputs`へ適合させ、Result deliverableは依頼元の`expected_deliverables`と実行先の`outputs`から要求時に合意したschemaへ適合させる。大きなartifact、log、Memory、mediaは複製せず、許可scope付き参照とprovenanceを渡す。受信側は未知revision、宛先不一致、許可されないwork type、schema不適合を拒否し、silent successにしない。

共通Chat上の可視化は`agent.delegate`、`agent.acknowledge`、`agent.report`の既存lifecycleを維持する。IPC envelopeはこの会話eventを置換せず、同じ`request_id`、`trace_id`、`task_id`、`session_id`で相関する。

### 周辺領域との責務分離

| 領域 | この契約による責務 |
| --- | --- |
| Agent Registry | Contractの登録・検証・照会、Knowledge view生成、revision管理 |
| Router | Registry検索、policy／availability検証、候補選択、選択根拠のtrace |
| Runtime | Request実行、Result生成、timeout／cancel／failureの確定。人格や長期Memoryの正本にはならない |
| Persona | 表現、話し方、価値観、対人姿勢だけを提供し、責務・権限・成果物を決めない |
| Observation | sender／recipient、revision、期待／実際のdeliverable、status、相関IDを記録する。内部reasoningは記録しない |
| Memory | 協調結果をsession／実行証跡として保持できるが、自動でUserMemoryや確定Knowledgeへ昇格しない |
| IPC | transport非依存envelope、schema validation、相関、timeout、cancel、重複排除を担う |
| Worker | Contract内の作業を実行し、証跡、制約、未解決事項をResultとして返す |
| Chat | Agent間の依頼・復唱・報告と、利用者向けに説明可能な要約を共通会話へ表示する |

Agent数に論理上の上限を置かない。Movie、Music、News、History等の専門Agentも同じContract、Knowledge view、Router、IPCへ参加する。deploymentはcapacityや同時実行数を制限してよいが、Agent identity数の仕様上限にはしない。Agent一覧の全件prompt注入を避け、Registry検索、必要なKnowledge viewだけの取得、artifact参照によりAgent数増加へ対応する。

## Game境界

Agent所有ゲームのlifecycleは次で固定する。

```text
CORE Agent
  -> RenCrow_GAMES launch
  -> GAMES ObservationRequest
  -> CORE Agent decision (/viewer/games/decision)
  -> GAMES validation / deterministic Executor
  -> ObserverFrame / result
  -> CORE observer proxy / candidate memory
  -> user
```

起動意思、Persona、Recall、LLM routing、候補記憶、ユーザー向けsame-origin proxyは
COREが所有する。world state、rules、available action、validation、実行、Replay、
Observer UIとgame loopはRenCrow_GAMESが所有する。AgentがGame Toolを呼び、
RenCrow_GAMESがゲームを実行し、その進行をObserver UIで利用者へ表示する。

CORE AgentはGAMESが提示した観測と利用可能actionから次の行動を決めます。
RenCrow_GAMESはAgentの決定を検証してworldへ適用し、CORE／RenCrow_LLMがworld stateを
直接変更することを認めません。`RuleBasedBrain`／`DummyBrain`を使う経路はtestまたは
local simulationであり、Agent所有E2Eとして扱いません。CORE停止時はAgent turnを
ローカルbrainへfallbackせず、明示したunavailable/degradedとして観測します。

## Trade境界

金融研究、学習、Portfolio risk、TradeGateのdomain正本は`RenCrow_TRADE`が所有します。
COREはAgent workflowと認証済みPublic projectionを所有し、Broker、口座、TRADE Ledger、
Market Data providerへ直接接続しません。

```text
PORTAL / CMD / Agent
        -> RenCrow_CORE
        -> RenCrow_TRADE private API
        -> TRADE domain / policy / ledger
        -> Broker adapter（現在は未実装・禁止）
```

Disabled Foundationでは、COREはTRADEのBearer認証済み`GET /v1/status`、純粋Policy評価、
非更新Risk Preview、simulation-only commit、無発注Shadow観測記録、および認証済みAgentのMemory Owner APIを利用します。
COREは`GET /viewer/trade/status`へ必要な状態を投影し、TRADEのprivate token、base URL、
内部error本文をclientへ返しません。TRADE未設定、token読込失敗、到達不能、contract不一致を
それぞれ`disabled`または`unavailable`として返し、成功値や仮Portfolioを生成しません。
TRADE側で100万円Simulatorを明示設定した場合だけ、同statusに含まれる検証済みsnapshotを投影します。

TRADE Memory OwnerのAgent向けcanonical routeは次です。`data.recall`／`data.write` registryの実行主体は
CORE-managedなShiro／`worker`に限定し、modelがidentity、role、user delegation、request ID、purpose、policyを
選択しません。TRADE private owner APIは他のtyped CORE workflow用にKuro／`heavy` scopeも検証できますが、
Kuro／Heavyは`data.*` runnerを直接持たず、DB操作が必要な場合は定義済みhandoffでShiro／Workerへ渡します。

```text
Shiro(worker) Agent
  -> CORE data.recall / data.write
  -> trusted ToolExecutionScopeからtyped child scope／purpose／決定的subrequest ID
  -> RenCrow_TRADE private API（loopback default :8767）
  -> TRADE Owner DB（investmentのsource／learning／market／replay／portfolio／ledger）
```

readはexact queryまたは`query=current`にbounded `limit=1`を付け、OwnerEvidenceを検証します。investmentの
`portfolio_snapshot`は独立したcurrent readに加え、`ensure_portfolio_initialized` receiptの完全一致する
小文字`sha256:<64 hex>` `audit_ref`をhandoff queryとして受け付け、Owner responseのsnapshot hashと
`OwnerEvidence.ProvenanceRef`の両方を同じ値へ束縛します。writeはstrict request、OwnerReceipt、audit／idempotencyを検証します。typed child scopeの決定的なsubrequest IDは
同一turnのreceipt conflictを避けます。`ledger`の`record_shadow_observation`は`study_id`と`decision_id`だけを受け、
COREがOwner replay／market record、fixed Outcome Label Contract hash、Global Policyから観測を再構成します。
modelがmarket、action、policyを直接供給すること、COREがTRADE DBへ直接接続することは禁止です。
`dependencies.memory_owner`が`ready`でない、listener／readinessがない、またはroute snapshotが不一致なら、
Agent operationは`unavailable`／`blocked`で閉じます。

COREのTRADE timeoutは`1..60000` msで、既定は`3000` msです。45秒のcatalog-bound Memory Source収集を含む
場合は`60000` msを推奨します。default listenerは`127.0.0.1:8767`（`:8766`はSTT）であり、status probeだけでは
Memory Owner routeやAgent-owned production E2Eの完了を意味しません。

このbridgeは金融取引・注文経路に対してread-onlyであり、Broker、Paper、LIVE、注文、本人認可操作、
knowledge promotionを有効にしません。Memory Ownerの検証済みnon-order write（source／learning／market／
replay／portfolio／ledger）は別のbounded routeとして扱います。TRADEが停止しても
CORE内investment機能、fake endpoint、backend直結、Broker直結へfallbackしません。

購入前Risk Previewは、COREがplanのcanonical JSON SHA-256をrequest scopeへ束縛し、active
Global Policy、deployment、TRADE module policyで`portfolio_risk_preview`を事前評価した場合だけ、
`POST /v1/portfolio/risk-preview`へ送ります。TRADEは設定済み100万円Simulatorの検証済みsnapshotと
planを純粋計算へ渡し、`pass | block`を返します。どちらの結果もPortfolioを変更せず、注文権限を
作りません。Global Policy未許可、stale policy revision、証跡保存失敗、TRADE不通はfail closedです。

Simulatorへの反映は注文経路と分離した`POST /viewer/trade/simulation-commit`だけを使います。COREは
明示操作、active Global Policy、PreviewのPortfolio event count/hashとinput snapshot SHA-256を束縛し、
TRADEは最終write境界でも同じPolicyとcurrent snapshotを再評価してから、100万円Simulatorへ
`simulated_fill`をatomic appendします。これはBroker、Paper、LIVE、本人認可record、Proposal、Intent、Orderを
作らず、staleなPreviewを再利用しません。

現在市場の未知期間を評価するShadow観測は`POST /viewer/trade/shadow/observations`を使います。
COREは明示`allow_record=true`、認証済みuserまたは実在CORE Agentの`actor_id`、判断context hash、
Outcome開示前に固定した採点契約hashをGlobal Policyへ束縛し、TRADEの追記専用hash-chain台帳へ渡します。
このrouteはPortfolioを更新せず、Broker／Paper／LIVEを呼ばず、knowledgeを昇格しません。

Outcomeは`POST /viewer/trade/shadow/outcomes`で同じ観測の後続eventとして記録します。元の観測hashを
変更せず、Outcome Label Contract hash、Outcome data hash、結果label、evidenceをGlobal Policyへ束縛します。
Outcomeの確認は独立readなら`GET /viewer/trade/shadow/outcomes/report?study_id=<id>`、write→read handoffなら
receipt由来のexact `event_id=shadow-event/sha256:<64 lowercase hex>`で行います。event lookup時は返却された
study IDとOwnerEvidence provenanceをevent IDへexact bindingします。TRADE側で台帳全体を再検証して集計し、COREは読み取り専用projectionとして返します。`review_required`は独立review前を示し、
knowledge promotion、Portfolio更新、Broker／Paper／LIVE実行を許可しません。
このrouteもPortfolio、Broker、Paper、LIVE、knowledge promotionへ到達しません。

Outcome reportの人手／独立確認は`POST /viewer/trade/shadow/outcomes/reviews`で行います。report
canonical hashと最新event hashを同時に束縛し、TRADE側の分離review ledgerへ追記します。これは
stale report、改ざん、二重reviewを検出するための監査記録であり、review結果だけでknowledge
promotion、Portfolio更新、Broker／Paper／LIVE実行を許可しません。

review ledgerの現在状態は`GET /viewer/trade/shadow/outcomes/reviews/report?study_id=<id>`で読み取ります。
`independently_reviewed`は独立review eventが検証済みという意味だけであり、学習昇格や外部実行を
自動で許可しません。

## LLM deployment境界

正式名称と順序を次で固定します。

```text
CORE
  -> RenCrow LLM Gateway
  -> RenCrow LLM Runtime
  -> Backend
  -> Model
```

- `RenCrow LLM Gateway`: CORE向けChat API、Execution RoleからRuntimeへのrouting、
  session binding、queue／capacity、Runtime status集約を所有する。
- `RenCrow LLM Runtime`: 推論サーバ側の層。Backend／Model inventory、lifecycle、
  readiness、capacity、adapter、decoder差、response normalizationを所有する。
- `Backend`: llama.cpp、MLX、Ollama、provider runtime等の推論tool／engine。
- `Model`: Gemma4、GPT-OSS-120B、Qwen3.6等の物理推論model。

`central Gateway`と`Host Node`は正式なレイヤー名として使用しません。既存バイナリ名
`rencrow-llm`はRenCrow LLM Gateway、`rencrow-llm-node`はRenCrow LLM Runtimeの
実装artifactとして扱います。`node`という語はbinary、config、API等の既存実装識別子に
限定し、仕様上の責務名にはしません。

```text
CORE host
  rencrow
    -> RenCrow LLM Gateway (rencrow-llm)
         |-> Mac RenCrow LLM Runtime (rencrow-llm-node)
         |     `-> Backend -> GPT-OSS-120B / Qwen3.6
         `-> RTX5060 RenCrow LLM Runtime (rencrow-llm-node)
               `-> llama.cpp Backend -> Gemma4
```

COREはRenCrow LLM Runtimeのprocess、GPU、Model path、Backend portを管理しない。
Runtimeの配置、Backend監視、Model readiness、loopback bind、Gatewayとの認証は
RenCrow_LLMのdeployment契約であり、COREはGatewayが集約したRuntime／Backend／Model状態
だけを受け取る。

正規経路が利用不能な場合は、config、credential、process、network、Runtime、
Backend readiness、capacity、logを確認し、このdeployment経路自体を復旧します。
E2E成功だけを目的にRuntimeを迂回するBackend直結、local代替、fake endpoint、別Model、
module省略経路へ切り替えません。例外topologyはCORE正本とdeployment policyに事前定義され、
起動時検証を通る場合だけ使用できます。復旧不能時は失敗境界を報告し、代替結果を正規runtimeや
Agent-owned E2E成功として扱いません。reject理由を使った再考は正規経路の修復案へ向けます。

## LLM Ops Capability層（llmfit統合）

本章はStatus: Proposedの構成であり、現時点では未実装です。機能契約は
[機能仕様のLLM Ops / Hardware Capability](02_機能仕様.md#llm-ops--hardware-capabilityllmfit統合)を
正本とします。

### 構成

各LLM実行ノード上のllmfitが観測したHardware Capability／Model Fitを、RenCrow COREのLLMFit Adapterが
取得し、Hardware Capability Serviceが正規化して、既存のObservability Layer経由でViewer／Opsへ
届けます。複数ノードの結果は同一のOps画面へ集約します。

```text
LLM Node A (llama.cpp / MLX / Ollama 等) + llmfit --+
LLM Node B (llama.cpp / MLX / Ollama 等) + llmfit --+
LLM Node N (...)                        + llmfit --+
                                                   |
                                                   v
RenCrow CORE
  LLMFit Adapter (Local CLI / REST)
    -> Hardware Capability Service
         |-> Node Hardware Profile
         |-> Model Fit Assessment
         `-> Benchmark Observation
    -> Observability Layer (既存Event + Read Model)
    -> Viewer / Ops (Node Overview / Model Fit Matrix / Model Detail)
```

### 接続方式

| 配置 | 方式 | 入口 |
| --- | --- | --- |
| 同一ホスト（Local Node） | Local CLI | `llmfit --json system`、`llmfit recommend --json --limit 20` |
| リモートノード（Remote Node） | REST | `llmfit serve`が公開する`GET /health`、`/api/v1/system`、`/api/v1/models/top`、`/api/v1/models` |

原則としてLocal NodeはCLI可、Remote NodeはREST推奨とします。Adapterの内部interfaceは両方式で共通化し、
Hardware Capability Service以降は接続方式を意識しません。

### 責務境界

llmfitはCapability Sensor、RenCrowはCapabilityを理解して利用するSystemです。

| 担当 | 責務 |
| --- | --- |
| llmfit | Hardware detection、Model catalog、Fit calculation、Runtime recommendation、Quantization recommendation、Performance estimation |
| RenCrow | 複数Nodeの統合、実測データとの比較、Observability、Viewer表示、将来のScheduling判断 |

RenCrow自身がHardware適合度計算を抱えません。

### データ境界

llmfit固有JSONをDomainやUIへそのまま露出させません。Adapterが受け取ったDTOをmapperで
RenCrow Domain Model（Node Hardware Profile、Model Fit Assessment）へ変換してから後段へ渡します。
推定値と実測値、信頼度（`EstimateConfidence`）、Native／Usable／Evaluated Contextは別fieldとして
保持し、同じ数値へ丸めません。

### Observability境界

新しいEvent Systemを作らず、既存Eventを使います。全モデルの巨大JSONをEvent Logへ保存せず、
Eventは何が起きたか（取得成功、取得失敗、offline、stale、manual refresh等）だけを残し、
実データはRead Model側に保持します。既存Observability Eventを二重化しません。

### 標準Go配布境界との関係

llmfitはRenCrowシステムへ必ず導入する外部の観測ツールです。LLM実行ノードおよびCORE hostの標準導入手順に
llmfitを含め、未導入は構成不備として扱い、導入手順と運用点検で検出します。一方でruntimeとしてはfail-safeで
あり、llmfitのprocess停止・応答不能時もCOREのGo binaryは停止せず、LLM Ops画面だけが`OFFLINE`／`STALE`に
なります。これは安全性の要件であり、導入要件の必須化によって弱体化しません。COREはllmfitの有無を起動時の
fail closed条件にしません。

llmfitはRust製の単一binaryであり、Python／Node.js／Docker／WSL／外部database等のruntimeを持ち込みません。
[標準Go配布境界](#標準go配布境界)が標準起動条件への追加を禁じる対象は、別に導入・起動・監視が必要な重い
外部systemであり、llmfitはその趣旨に反しません。本章は同章の方針を再定義せず、次の標準構成の例外として
記録します。machine-readable deployment policyへの定義と起動時検証は実装時に行います。

| 項目 | 記載内容 |
| --- | --- |
| 対象 | llmfit（Rust製CLI、単一binary。Python／Node／Docker runtimeを持ち込まない） |
| 理由 | Hardware Capability／Model Fitの観測をRenCrow Goへ再実装しないため。責務境界はCapability Sensor |
| OS | Ubuntu／macOS／Windowsの各LLM実行ノード。配布はcrates.io／Homebrew／install script |
| 影響 | LLM Ops画面のHardware／Model Fit表示のみ。会話、routing、Memory、LLM Runtimeの経路に影響しない |
| 失敗挙動 | 未導入・停止・応答不能時はfail-safeに縮退し、`OFFLINE`／`STALE`を明示する。COREは停止しない |
| 再評価条件 | llmfitの配布停止、Rust以外への実装変更、同等機能のCORE内製化を決めた場合 |

配布元、導入手段、導入確認手順は
[設定リファレンスのLLM Ops / llmfit 設定](05_設定リファレンス.md#llm-ops--llmfit-設定)を参照します。

### PORTAL Chat／IdleChat排他ライフサイクル

PORTALは画面ごとに`viewer_client_id`を持ち、top-level documentが可視の間だけCOREへ
`chat`または`idlechat`のsurface在席を通知します。COREは期限付きleaseとして在席を保持し、
次の優先順位でIdleChat runtimeの有効状態を一元決定します。

```text
可視Chatが1つ以上                         -> IdleChat停止（最優先）
可視Chatなし、可視IdleChatが1つ以上       -> IdleChat開始
可視Chatなし、可視IdleChatなし             -> PORTAL起因では開始しない
```

`claim`は表示開始、`heartbeat`は可視状態の継続、`release`は非表示または終了を表します。
`pagehide`／`visibilitychange`でreleaseできない異常終了はlease失効で回収します。同じ
`viewer_client_id`、surface、actionの再送は冪等です。複数tabや複数browserが競合しても
client側で開始／停止を奪い合わず、COREの集約結果だけを正とします。

Chat在席中は自動schedulerや他のPORTAL画面による開始要求もIdleChatを再開できません。
Chatの最後の在席がなくなった時、可視IdleChatが残っていれば開始し、残っていなければ
自動再開しません。CMD等の明示的な開始／停止APIは別の操作契約として維持しますが、
Chat在席による安全側の停止が優先します。

PORTALは在席通知の応答で`effective_mode=chat`かつ`idlechat_active=false`を確認してから
Chat入力をreadyにします。IdleChat画面は`effective_mode=idlechat`かつ
`idlechat_active=true`を確認してから「実行中」と表示します。通知失敗、期限切れ、
期待状態との不一致を成功へ丸めず、画面を`unavailable`または再接続中として表示します。
会話eventとTTSの表示境界もmodeごとに分け、Chatへ`idlechat.message`とIdleChat音声を
流さず、IdleChatへ通常Chatのmessageと音声を流しません。

#### 現状の実装境界と将来方針（memo）

ChatとIdleChatは本仕様では横並びの兄弟surfaceであり、`/viewer/surface-presence`は
どちらにも属さない共有のPORTAL排他ライフサイクル用APIです。本稿更新時点の実装では、
`/viewer/surface-presence`のhandlerとlease集約controllerは`RenCrow_CORE`配下に存在し、
PORTALはreverse proxyでCOREへ中継しています。短期的にはCORE内で、surface-presenceを
IdleChat feature配下から兄弟中立な`features/presence`へ分離し、IdleChat無効化時でも
Chatが正常にreadyへ遷移できる状態に保ちます。

将来の中長期方針（memo、本リリースでは未実装）として、Chat／IdleChatの各surfaceに属する
backend logic（handler、session、lease集約など）を`RenCrow_PORTAL`へ移管し、COREには
Viewer層とcross-cutting runtime（LLM、TTS、STT、Vision、Memory等）のみを残す方向を検討
します。COREが所有するのはsurface横断の正本と共通runtimeで、surface固有のライフサイクル
制御はPORTALが自前で終端し、必要な部分だけCORE APIを呼ぶ構造へ寄せる想定です。
`RenCrow_CMD`は本件に関わらずCORE APIのCLIクライアントであり、移管対象ではありません。

### IdleChat Episodeの制作／再生境界

IdleChatは再生中に会話を生成するruntimeではなく、COREが事前制作した会話episodeを
PORTALで連続再生する読み取りsurfaceとします。台本生成と朗読を次の失敗境界へ分けます。

1ワード／2ワードtopicとForecast topicはepisode制作の前段で、Shiro帰属の
side-effectなしCodexExe requestとCOREの契約検証を経てTopic Stockへatomicに公開します。
1ワード／2ワードではCOREが固定コアと日次最新語からseedを選び、CodexExeが最大3候補と
Judgeを生成します。ForecastではCOREが収集・選定したtrendとnews seedからCodexExeでキーワードを
抽出し、COREが関連ニュースを拡張した後にCodexExeの最大3候補とJudgeを実行します。Forecastの未来範囲は
AI技術が1〜2年、その他技術が2〜3年、医療・社会保障・政治・経済が3〜5年です。
Worker LLM、ChatWorker、Coder系provider、別Model、固定文を1ワード／2ワードまたは
ForecastのStock生成fallbackにしません。COREはワード選択、source provenance、永続化、
消費、補充と、1ワード、2ワード、Forecast、直近topic履歴を横断する重複排除を所有します。

```text
IdleChatTopicSeed / Topic Stock item / story source
        ↓
CORE IdleChat Episode Producer
        ├─ CORE正本のMio／Shiro character context
        ├─ topic、source context、直近topic、禁止事項
        ├─ content mode判定（serious > assertive > free）
        ├─ story: 改変軸、genre、面白さ契約、物語台帳
        ├─ story: 固定reader＋listenerの合いの手契約
        └─ structured script request
        ↓
CodexExe（read-only / ephemeral / side effectなし）
        ↓ Mio／Shiroの全turnを一括生成
CORE Episode Validator
        ├─ 最初のNG turn k
        │     ↓ prefix 1..k-1を固定
        │  suffix k..endをCodexExeで再生成
        │     └──────────→ Episode Validatorへ戻る
        ├─ NG／不確実 ─→ needs_repairとして保持
        │                    └─ 別episodeを補充生成
        └─ 全turn合格
        ↓ atomic publish
IdleChatEpisodeArtifact（完成台本、CORE正本）
        ↓
CORE IdleChat Playback Coordinator
        ├─ 朗読時のTTS先読み ─→ RenCrow_TTS Gateway
        └─ 字幕／音声queue  ─→ RenCrow_PORTAL IdleChat
```

1ワード、2ワード、Forecastの`dialogue` episodeにも同じ境界を適用します。CodexExeは
CORE正本のMio／Shiro SystemPrompt、topicとseed context、`content_mode`、確定済みprefixを入力とします。
Forecastではさらに対象ドメインの未来範囲とsource contextを入力しますが、その未来範囲を
1ワード／2ワードの制約にしません。COREはturnごとに話者帰属、Persona、文脈、反復、事実性、
seedとtopicの整合、content modeを判定し、Forecastでは未来範囲も判定します。最初のNG turn以降だけを
CodexExeでsuffix再生成し、合格済みprefixのAgent identityと`message_id`は変更しません。

1ワード／2ワードのtopicは、seedの意味を満たすだけでは合格にしません。`single`はseedの
`genre_1`の値そのものをtopic文字列へ1回以上含め、`double`は`genre_1`と`genre_2`の値そのものを
それぞれ1回以上含めます。語の言い換え、上位語、関連語だけではこの契約を満たしません。生成promptも
「seed.genre_1を中心にする」「seed.genre_1とseed.genre_2を使う」という抽象的な指示だけにせず、
requestごとのseed値を埋め込んだ必須文で同じ値を明示します。例えば`genre_1=生成AI`なら
「topic文字列には『生成AI』をそのまま1回以上含める」、`genre_1=生成AI`かつ`genre_2=防災`なら
「topic文字列には『生成AI』と『防災』をそれぞれそのまま1回以上含める」となります。promptの
`{genre_1}`／`{genre_2}`はCodexExeへ渡す前に現在のseed値へ展開し、seed JSONを渡すだけで代用しません。

`IdleChatEpisodeArtifact`はCOREが所有し、PORTAL、RenCrow_Tools、RenCrow_TTSは台本や
episode状態の正本を持ちません。episode producerはCORE正本のMio／Shiro character contextと
生成条件をCodexExeへ渡し、全会話を構造化scriptとして受け取ります。CodexExeの内部thread、
working directory、Model contextをAgent Memoryやepisode正本へ昇格しません。全台本と品質判定が
完了するまで`ready`へ遷移せず、部分台本を再生系へ公開しません。再生系は`ready`な台本を
読むだけで、LLMやCodexExeを呼びません。前景Chatが始まった場合はproducer、TTS先読み、再生の
順にcancelし、生成／TTS capacityを前景へ返します。

episode producerはtopicとsource contextから`content_mode`を決定的に分類し、判定理由とともに
artifactおよびCodexExe入力へ保持します。戦争、武力衝突、災害など人命・被害・喪失を直接扱う
話題は`serious`、それ以外の政治・思想は`assertive`、その他は`free`とし、条件が重なる場合は
`serious > assertive > free`を適用します。このmodeは会話内容の姿勢であり、Mio／ShiroのPersonaや
口調を切り替える別character profileではありません。

`story_reading`は通常のMio／Shiro対話とは出力契約を分けますが、別runtimeや別正本を作りません。
CORE Episode Producerが`transformation_axis`、`genre`、`interest_direction`、`interest_contract`、
entity／関係／時系列／世界規則／読み／造語を持つ物語台帳、固定readerとlistenerを同じCodexExe
requestへ渡します。CodexExeは物語本文と短い合いの手を一括生成し、COREは`narration`と
`interjection`の構造化roleを検証します。読み手の途中交代や、聞き手が物語本文を乗っ取る出力を
許可しません。表示本文とTTS本文を分け、episode台帳の読みをRenCrow_TTS入力へ反映します。

turn validatorはpromptへの注意書きだけに依存せず、話題の直近重複、発話の同文・交互・template・
高類似反復、話者勘違い、Persona逸脱、meta漏れ、category固有の事実・表現違反、content mode違反を
決定的に検査します。
最初のNGが`turn k`なら、`turn 1..k-1`とその`message_id`を保持し、`turn k`以降の本文、identity、
検証結果、TTS派生物を破棄します。CodexExeには固定prefix、NG理由、残りturn数を渡してsuffix全体を
再生成させます。再検証で次のNGが見つかった場合も同じsuffix規則を有限回繰り返し、上限到達時は
episodeを`needs_repair`または終端`failed`にします。NGまたは意味検査が不確実なepisodeはreadyへ
公開せず、自動削除もしません。検出codeと修復起点を保持したまま、修復／破棄判断とは独立して
別`episode_id`を補充生成します。補充はready在庫だけを数え、有限件のbackground cycleとして
動かします。公開済みepisodeは直接変更せず、新revisionで同じ修復を行います。

音声は永続episode artifactの必須要素にせず、朗読時に最初の1〜2発話を準備してから開始し、
再生と並行して2〜3発話先、15〜30秒を目安にbufferします。音声cacheは台本文、voice revision、
message identityに従属する派生物です。COREは既存の
`CORE -> RenCrow_TTS Go Gateway -> RenCrow_Irodori_TTS`境界だけを使い、PORTALはCOREから
受けたchunkを`turn_index`順に再生します。browserの再生完了ACKは再生結果の観測とcache解放に
使いますが、次の合成開始を待たせる同期gateにはしません。これにより、TTS合成と再生を
overlapしつつ、ACK欠落をepisode全体の直列停止へ波及させません。

IdleChatの1発話は、`Ready`（最初の音声chunkが利用可能、または合成がterminalへ到達）と
`Done`（その発話の全chunk合成sessionがterminalへ到達）を別の状態として追跡します。
発話単位の進行は`Ready`だけを待ち、episode終了時のdrainは`Done`だけを待ちます。
browser playback ACKはこのどちらも確定せず、再生結果の観測とcache解放だけを行います。
timeout、前景処理による中断、runtime resetでは、待機だけを解除せず、同じ発話のcancelを
COREからGateway request contextまで伝播して`Done`を一度だけterminalへ確定します。cancel後に
到着したchunk／completionは状態を復活させず、stale receiptとして破棄します。

TTSへ渡すspeech chunkはtopic、通常発話、summary、prefetchの別を問わず同じCORE正本の
chunk規則（目標34 rune、本文最大42 rune）を通します。句点とemotion prefixを含むGateway
payload全体は最大44 runeです。長文発話は複数requestへ分割しますが、
発話全体を一つの短い固定timeoutへ押し込めず、first chunk、各request、全sessionの期限と
receiptを区別します。`Ready`待ちとsession drainを持つorchestratorをdeadlineの唯一の正本とし、
queue投入時やprefetch stream作成時に同じ発話へ別の固定deadlineを開始しません。COREより長い下流timeoutによって、CORE timeout後も新しいchunk生成を
継続する状態は禁止します。

IdleChatのTTS requestでは、発話の`character_id`／話者帰属をMioまたはShiroのまま保持し、
RenCrow_TTS Gatewayの公開`voice_id`だけを正規化します。Mioの`voice_id`は`mio`、Shiroの
`voice_id`は`shiro`です。voice選択でcharacter identity、`from`、字幕の話者、message identityを
別characterへ置き換えてはいけません。旧実装の`male_01`／`female_01`はGatewayのvoice IDではなく、
IdleChatの正規requestへ送信・保存・health上のavailable値として扱いません。Gatewayが返す公開voice
一覧とrequestの`voice_id`が一致しない場合はTTSを成功へ丸めず、`VOICE_NOT_FOUND`等の失敗境界を
保持してCOREのTTS error／receiptへ返します。

RenCrow_Toolsの`rencrow-idlechat`はepisodeのprepare、status、validate、expireを操作する
native Go CLIとします。ただしCLIはCOREのallowlist済みoperationを呼ぶclientに限定し、
COREのproduction DB、Agent Memory、RenCrow_LLM Gateway、RenCrow_TTS Gateway、物理backendへ
直接接続しません。RenCrow_CMDへ同じepisode制作runtimeを複製せず、PORTALはprepareやexpireを
公開操作にしません。

ASSISTANTもCORE Public APIを利用しますが、単なるclientではなく別domainの常駐serviceです。personal／family scope、生活Routine、PUSH、端末deliveryはASSISTANTが所有し、Agent、Memory、Knowledge、複雑なTaskはCOREが所有します。PORTALはASSISTANTの状態を表示・操作できますが、Routineやdelivery状態の正本にはなりません。

## ニュースデータの責務境界

ニュース処理は、IdleChatの画面やAgent人格へ直接所有させず、共有NewsBrief境界で分けます。

```text
04:00 JST Scheduler
        ↓
RenCrow_Tools rencrow-news collect
        ↓
NewsCollectionArtifact (immutable)
        ├─ IdleChatTopicSeed  ─→ IdleChatのお題生成
        └─ CORE-owned analyze port
                ↓
           Shiro / Worker
                ↓
        NewsAnalysisArtifact  ─→ DailyNewsBrief ─→ Chat/Mio・ASSISTANT

既定14 RSS/Atom定義 ─→ L1 Source Registry登録
                         ├─ Sports: 既定disabled、収集対象外
                         └─ 他13: enabled ─→ sweep ─→ l1_news_item
                                                   └─→ DailyNewsBriefReaderの永続fallback

一般検索 ─→ bing_rss ─→ web_gather.search_and_fetch
最新・速報の要求 ─→ bing_news_rss ─→ LiveNewsSearch ─→ Chat/Mio
```

`IdleChatTopicSeed`は会話のお題候補であり、SNS投稿やWikipedia項目を確認済みニュースとして扱いません。`DailyNewsBrief`は対象日、取得時刻、source、本文取得状態、原文翻訳、サマリ、Shiroの見解、用語補足を持つユーザー向け朝刊データです。`LiveNewsSearch`は準備済み朝刊より新しい情報を求める明示要求だけに使います。

CORE内部では`DailyNewsBriefReader`を読み取りポートとして定義し、ChatやASSISTANTがIdleChat内部のcache変数やViewer endpointへ直接依存しないようにします。`GET /viewer/idlechat/collection`はDebug Viewerの観測用snapshotに限定し、ユーザー向けニュース取得のAPIへ転用しません。利用者別の選定、既読、配信、PUSH、deliveryはASSISTANTが所有します。

収集と考察は別process／別失敗境界です。収集phaseはfeedと元記事本文を取得してimmutableな`NewsCollectionArtifact`を確定し、LLMを呼びません。考察phaseはそのartifactとSHA-256を入力にし、元ニュースを再取得せず、翻訳、用語補足、事実サマリ、Shiroの見解を`NewsAnalysisArtifact`へ出力します。不明語の確認先URLだけは考察中に追加取得できますが、そのevidenceは分析artifactへ記録し、収集artifactを変更しません。同じ収集artifactへの考察再実行を許可し、`collect`と`analyze`を暗黙に結合しません。

| module | ニュースworkflowで所有する責務 |
| --- | --- |
| RenCrow_CORE | schemaと意味、source policy、上限、artifact検証、Agent／Worker routing、Shiro帰属、状態import／公開 |
| RenCrow_Tools | native Go CLI `rencrow-news`、HTTP／RSS取得、atomicなartifact出力、tool固有validation |
| RenCrow_CMD | 所有しない。COREの一般terminal facadeへニュース専用CLIを複製しない |
| RenCrow_LLM | COREから受ける論理role requestを正規Gateway／Runtime経路で処理する。Toolsから物理targetを指定させない |
| RenCrow_ASSISTANT | 利用者別の選定、既読、配信時刻、PUSH、deliveryを所有する |

`rencrow-news analyze`はCORE所有の考察portへrequestを渡すworkflow専用clientであり、第二のTool Registryや独立したAgent runtimeではありません。考察portが利用不能なら明示的に失敗し、Tools内の任意LLMやbackend直結へfallbackしません。標準実装はWindows、Linux、macOSで同じartifact契約を扱うnative Go binaryとし、Python、Node.js、Docker、WSL、外部databaseを起動条件へ追加しません。

`DailyNewsBriefReader`は04:00の準備済みcacheを先に読み、対象日のcacheが空または古い場合は、
Source Registryで検証・昇格済みの`l1_news_item`を同じ読み取りcontractへ写像します。CORE起動時は
既定14 sourceのうちsource IDまたはURLが存在しないものだけを登録します。新規登録時はSportsを既定disabledで収集対象外、他13 sourceをenabledとします。既存行の有効／無効、
trust、interval、metadataは上書きしません。収集、SQLite、検索providerはいずれもnative Goで、
WSLへ配置しません。

観測sourceは、04:00処理済みcacheを`scheduled_daily_cache`、L1 fallbackを
`persistent_news_db`、前景検索を`live_news_search`として区別します。

一般`web_gather.search`の既定providerは`bing_rss`、前景ニュースの既定providerは
`bing_news_rss`です。どちらもGoの`net/http`と`encoding/xml`で同じ契約を実装し、
ニュースはpublication timeで`day`／`week`／`month`の鮮度を判定します。SearXNG／YaCyを
設定した場合はニュースCollectorがその明示providerを優先します。remote検索不能、本文取得不能、
cache missは成功扱いにせず、Tool errorとdiagnosticsへ残します。

04:00 JSTの`DailyNewsBrief`が利用できない場合、Mioはニュース収集を直接実行せず、`agent.progress`でShiroへ収集Workerの実行を依頼します。Shiroは検索源の確認、候補記事の取得、重複確認などの作業状況だけを同じイベント種別で返し、WorkerのTool境界で収集した結果は構造化された`Source=live_news_search`の`DailyNewsBrief`としてMioへ渡します。進捗発話には記事の事実を混ぜず、最終的な要約・朗読・TTSはMioが担当します。

## Interaction client profile

COREはPORTAL、CMD、ASSISTANTごとに別の会話systemを作りません。次の意味をPublic API
contractとして共通化し、surface差はclient profileへ閉じ込めます。

| 共通意味論 | COREの責務 |
| --- | --- |
| Chat | 明示recipientと利用者scopeでmessageを処理し、responseを相関する |
| IdleChat | event、status、開始・停止の意味と権限境界を定義する |
| recipient選択 | client-localな表示選択と実messageの`to`を分ける |
| event／session | 再接続、重複、順序、request／response／task相関を扱う |
| STT／TTS | input ownership、合成、audio取得、端末再生を別の成功条件にする |
| Task | 通常会話と複雑な継続作業を分け、状態とprovenanceを返す |
| error | unavailable、degraded、denied、expired、failedを成功へ丸めない |

長時間Taskの再開経路は
`resume request／startup scheduler -> SuperAgent durable run + queue -> atomic lease claim -> same run_id/task_id -> orchestrator -> checkpoint commit`
とします。Run Controllerのmemory内pause marker、Viewer表示、Conversation Recallは補助projectionであり、resume正本では
ありません。schedulerはheartbeat中のclaimへ割り込まず、期限切れclaimだけを回収します。旧runnerがlease失効後に返した
結果はlease token不一致としてcommitを拒否します。

```text
PORTAL    = CORE Interaction Client + Web Renderer
CMD       = CORE Interaction Client + Terminal Renderer + Operations
ASSISTANT = CORE Interaction Client + Proactive Trigger + Device Delivery
            + Assistant-owned personal / family / routine state
```

これは同一UI、同一transport、共有database、または共通SDKの先行作成を意味しません。
実caller間でDTO、再接続、error処理の重複が確認された時だけ、安定したcontractを
`modules/*`へ昇格します。公開可否はclient profile、認証scope、PORTAL mode、Device
capabilityで制御します。

COREへ接続する既知clientは`X-RenCrow-Client`と
`X-RenCrow-Interaction-Profile`を組で送ります。現行profileは
`portal-chat`、`portal-idlechat`、`portal-games`、`cmd-chat`、`cmd-idlechat`、
`cmd-diagnostics`、`cmd-control`、`assistant-core`です。COREのprofile guardは
client/profileの組、method、pathを検証し、
profile外の操作を403で拒否します。これらのheaderは認証credentialではなく、
既存のTLS、network境界、認証scopeを置き換えません。

PORTAL Gamesの表示経路は次で固定します。

```text
User -> PORTAL /games
     -> CORE /viewer/games/status
     -> CORE /viewer/games/launch
     -> GAMES Agent-owned session
     -> PORTAL iframe /viewer/games/observer
     -> CORE /viewer/games/observer-api/*
     -> GAMES Observer / frames
```

COREはAgent identity、launch、decision、result callback、同一origin proxyを所有し、
GAMESはworld、rules、Executor、Replay、Observerを所有します。PORTALは選択UI、
session lifecycle UI、iframe配置、将来のPuruPuru発話overlayを所有します。
ObserverのCSS／JavaScriptはGAMESが同一origin proxy可能なassetとして配信し、
PORTALはObserver responseだけを`SAMEORIGIN`／`frame-ancestors 'self'`とします。
タイトル描画に必要な動的style属性はObserver responseの`style-src`だけで許可し、
inline scriptは許可しません。PORTAL本体とPuruPuru assetは引き続きframe不可です。

## コード上の境界

| path | 責務 |
| --- | --- |
| `modules/*` | 外部利用可能な DTO、event、純粋 policy、安定 contract |
| `internal/features/*` | feature ownership、route registrar、dependency handoff |
| `internal/domain/*` | domain value、state、validation |
| `internal/application/*` | use case、orchestration |
| `internal/adapter/*` | Viewer、channel、provider、module adapter |
| `internal/infrastructure/*` | persistence、transport、外部技術実装 |
| `cmd/rencrow` | config load、依存組立、server 起動を行う composition root |

## 依存方針

- domain と public contract は特定 UI、DB、外部 provider に依存しない。
- adapter と infrastructure は contract を実装し、composition root が接続する。
- 新しい public package は複数 adapter で安定した契約だけを昇格する。
- route、provider、store、CLI、background job の二重登録・二重起動を防ぐ。
- portableなAgentProfile、routing表、handoff contract、Tool選択姿勢は実行時の
  `~/.rencrow/workspace`を宣言元とし、COREがload、schema検証、production wiring整合検証、
  SystemPrompt注入を担う。
- RenCrow_Workspace repositoryはMigration Snapshot契約と、`~/.rencrow/workspace`等から取得した
  portable non-secret Git snapshotを所有する。durable Stateとsecret実値はGitへ置かず、整合性を
  検証した暗号化Migration Artifactだけで扱う。外部runtime module、service、または実行時依存として
  扱わない。
- endpoint、secret、Tool availability、side effect、実行policyはCOREの実行責務であり、
  `~/.rencrow/workspace/control`へ移さない。

## Policy階層とmodule build境界

> 状態: schema v1、起動時read-only loader、hash／path／strict field検証、
> `/viewer/policy/status` projection、append-only共通Policy Decision storeを実装済みです。
> TRADEについては、Global Policy snapshotをmoduleのbinary／module policyへ渡す純粋評価経路を
> 採用します。module build検査と、注文を含む各side effect直前のenforcement wiringは未実装です。
> 現在の`control/`、policy file配置、または診断評価の`allowed`だけを実行許可として扱いません。

RenCrowのルールを、文章指示だけで実行権限へ変換しません。製品上の意味、実行時の全体方針、
module固有契約、越えられない安全上限、実行証拠を次のplaneへ分離します。

```text
CORE product contract / deployment policy
                 |
                 v
Global Policy Plane
  ~/.rencrow/workspace/policies/       active runtime policy
                 |
                 v
Module Contract Plane
  module docs / module policy / deployment config
                 |
                 v
Binary Enforcement Plane
  validation / allowlist / sandbox / domain gate
                 |
                 v
Evidence Plane
  Policy Decision / audit event / status / contract test
```

- CORE product contractは製品の意味と越えられない境界を定義します。開発時の`AGENTS.md`は
  Codex等の作業者向けbootstrapであり、RenCrow runtimeの権限根拠や人待ちgateにしません。
- Global Policy Planeは複数moduleに共通するcapability上限、authenticated request scope、外部action、data取扱い、
  deployment別の制限を宣言します。endpoint、credential実値、物理model path、runtime stateは
  保存しません。
- Module Contract Planeは各moduleだけが理解するdomain rule、入出力、状態、失敗条件を所有します。
  兄弟moduleのpolicyはCORE正本を上書きせず、global policyより権限を広げません。
- Binary Enforcement Planeは副作用の直前で判定する最終境界です。Workspace、prompt、request、
  module configから無効化できないhard limitを持ちます。
- Evidence Planeは、採用されたpolicy revisionと実際の判断・結果を追跡可能にします。

実効capabilityは和集合ではなく、次の積集合で求めます。

```text
effective_capability
  = binary_hard_limit
  ∩ global_workspace_policy
  ∩ module_policy
  ∩ deployment_config
  ∩ authenticated_request_scope
```

### TRADE純粋Policy評価境界

COREからTRADEへのPolicy評価は、Global Policy Bundle、deployment、request scopeの各revisionと
明示boolを`POST /v1/policy/evaluate`へ渡します。TRADEはbinary hard limit、module policyを含む
積集合を決定論的に評価し、reason codeと採用revisionを返します。未知capability、欠落field、
contract revision不一致はfail closedです。

COREは評価入力のSHA-256、TRADEが返したbinary／module policy revision、Global Bundle revision、
deployment revision、結果を共通Policy Decision storeへappendします。Viewerの
`POST /viewer/trade/policy/evaluate`はこの経路を観測する診断APIであり、Portfolio、Proposal、
Intent、追加の人間判断artifact、Orderを作成せず、応答の`authorizes_execution`は常に`false`です。実際の
side effect境界は診断結果や過去のdecision IDを再利用せず、その時点の入力で再評価しなければ
なりません。

下位層は権限を狭められますが、上位層またはbinary上限を広げられません。未分類の書込み、
外部送信、公開、課金、Git remote変更、credential変更、金融取引は既定拒否とします。
読み取りや純粋計算も、data scopeまたはprivacy契約を満たさない場合は拒否します。

各moduleは仕様をmodule repositoryに置き、必要な場合は機械可読module policy、domain gate、
contract testを同じrepositoryで所有します。標準的な配置候補は`docs/`、`policy/`、
`internal/policy/`、`tests/`ですが、物理directoryを増やすこと自体を目的にしません。
二つ以上のcaller、変更隔離、純粋policyの単体testのいずれかに実益がある場合だけ切り出します。

Buildはrepository内のsource、schema、module policy、testだけを入力とし、
`~/.rencrow/workspace`を読んでhost依存binaryを作りません。Build／CIは少なくとも次を検査します。

- module policyのschemaとpolicy ID
- CORE contract versionとの互換性
- hard limitを緩和する宣言の拒否
- side effect capabilityに対応するdomain gateと拒否test
- 埋め込むpolicy contract revisionまたはmanifest hashの決定性

MarkdownやYAMLをbinaryへ同梱しただけでは安全柵が実装されたことになりません。実装済みとするには、
型付き検証、最終副作用境界の拒否、contract test、Policy Decision、production wiringが必要です。

実行時のactive policyは`~/.rencrow/workspace/policies/`から読みます。portableかつnon-secretな
bundleはRenCrow_Workspace repositoryのsnapshot対象にできますが、snapshot、review、runtimeへの
promotionは別操作です。module buildはsnapshot repositoryにもruntime homeにも依存しません。
policy変更は一括検証後にatomicに切り替え、部分適用しません。

## Durable Store追加の責任境界

新しいdata要件が発生しても、新しいDBを自動的に作りません。DB file、外部database、
object store、append-only ledgerなど、独立したschema、migration、backup、restoreを持つ保存先を
総称して`Durable Store`とします。Durable Storeの追加は実装詳細ではなく、所有権、障害範囲、
復旧単位、privacy、運用依存を増やすarchitecture変更です。

判断主体は次のとおりです。ここでOrchestratorとExecutorは開発作業上のroleであり、RenCrow世界の
Agent identityやLLM／Model identityではありません。

| 主体 | 責任 | 禁止事項 |
| --- | --- | --- |
| Domain Owner | 保存する事実の意味、正本、writer、利用者、更新・削除条件を定義する | 他moduleのstoreを自moduleの正本にしない |
| Engineering Orchestrator | 既存store再利用、artifact、cache、新storeを決定規則で分類し、設計票の完全性とmodule境界を機械検証へ渡す | 人の判断待ちや別名のgateを追加しない |
| Executor | `validated`になったschema、Config、migration、backup、test、manifestを実装する | 保存topologyや検証済み範囲を独自判断で拡張しない |
| CORE | cross-module contract、判断規則、Manifest schema、物理配置、fail-closedを正本化する | 兄弟moduleの内部data意味や実値Configを所有しない |
| 各module | 自身が所有するstore manifest、schema、migration、backup／restore実装を所有する | 別moduleのsubtreeやDBへ直接read／writeしない |
| EcoSystem | 全module manifestの一意性、path衝突、contract version互換を統合検証する | runtime DBまたはmanifestの内容を正本として所有しない |

標準フローは次です。

```text
authenticated Chat／runtime data requirement
  -> MioがStorageRequirementとrequested_outcome=assess|implementを確定
  -> COREがowner候補と既存Memory／store／artifactを解決
  -> Domain OwnerがStorage Proposalを作成
  -> Orchestratorが既存store／artifact／cache／新storeを決定規則で分類
  -> impact classと必要validatorを確定
  -> schema／path／privacy／recovery／三OS契約を機械検証
  -> rejectedなら理由からproposalを再考して新revisionを作成
  -> assessならside effectなしで分類結果またはproposalを返す
  -> validatedならCORE正本とowner module manifestへ結果を反映
  -> implementならCoderがplan／patchを生成し、Executorがschema／Config／migration／backup／restore-check／testを実装
  -> CIとdeployment preflightが機械検証
  -> provision、migration、integrity、backup dry-run、scratch restore、health成功後だけactiveへ昇格
  -> Mioが同じtrace_idで利用者へ結果を返す
```

Chat routeはStorage Proposalそのものを自由文で生成して直接実行する経路ではありません。
会話層は利用者の目的と認証済みscopeを`StorageRequirement`へ変換し、保存方式、owner、impact class、
Manifest、migrationは型付きartifactと決定論的validatorへ渡します。通常の`CODE` Proposalは
Storage Proposalの代用にならず、Durable Store変更では両方が必要です。Chat起点の入力、状態、冪等性、
利用者向け結果は[機能仕様の「Chat起点のDurable Store構築」](02_機能仕様.md#chat起点のdurable-store構築)を
正本とします。

Mioが保存要件を検出したrequestは、一般`OPS`／`CODE`へ直接dispatchせず、内部capability
`durable_store_change`としてStorageRequirement workflowへ渡します。`assess`はside effectなしで閉じ、
`implement`はStorage Proposalがvalidatedになった後だけCODE生成とWorker実行を子工程として使用します。
このcapabilityは新しいAgent identityや外部moduleではなく、CORE Orchestrator内のdomain workflowです。

判定ロジックはChat I/O、LLM生成、filesystem／database I/Oから分離した純粋policyとしてCOREに置きます。
この分離により、同じ`StorageRequirement`、既存Manifest集合、Config能力、policy revisionから同じ分類、
change class、validator要求、reason codeを返すcontract testを実行できます。owner moduleのschemaやmigrationを
COREへ集約せず、COREはcross-module contractとgateだけを所有します。

文字列結合、path範囲、一意性、manifest completeness、backup有無、contract revisionなど機械で
判定できる事項へAIを使用しません。AIはdata意味や将来の利用関係が曖昧な場合にproposalを補助できますが、
AIだけでvalidation結果、provisioning、migration実行、production接続を確定しません。詳細な分類、impact class、
Manifest契約は[設定リファレンス](05_設定リファレンス.md#durable-store追加ガバナンス)に従います。

## 保存host分離（storage host）

> 状態: 実装中（2026-10-04）。`storage.host` config validation、`host` group
> （`host.contract`／`host.result`／`host.journal`）、idempotency journal、単調writer epoch、認証・
> contract version・冪等・通信断のtyped errorに加え、`durable_store_workflow_runtime_tool` の
> remote責任境界と同一processのcomponent integration evidence（実SQLite owner→認証済みHandler→typed client→
> runtime builder→登録済み`data.write`→workflow）を確認した。ただしこれはproduction
> Message／DistributedOrchestrator route、別host・実認証request provenance、A7–A9の代替ではなく、coverage gateは
> 開いたままとする。残るstore group、runtime consumer、remote profile全体は未完了であり、未実装または未配線の
> storeを完成扱いしない。

### 目的

保存媒体を保持するhost（storage host）とCOREを実行するhost（CORE実行host）を分けても、実Agentの
記憶・会話・Task/Run・所有権・認証を保って利用できるようにする。パス置換、backupコピー、手順書、
local fallbackだけをもって完了としない。

- local標準profile（`storage.host.mode: local`、既定）: 現行どおりCORE processが
  `storage.databases`／`storage.memory`／`workspace_dir`が指すファイルを直接開く。native Go binary
  だけで起動し、Python／Node／Docker／WSL／外部DB／queueを必須にしない。
- remote保存profile（`storage.host.mode: remote`）: CORE実行hostのCOREはdurable fileを開かず、
  storage host上で動くCORE所有の保存serviceに対して型付き操作APIだけを呼ぶ。

SQLiteのpage／VFSをネットワーク越しに共有する独自filesystem、SMB／NFS上のSQLite、文字列SQL、
任意pathのread／write、認証を迂回するfile APIは本契約では採用しない。

### 構成

| 要素 | 実body | 責務 |
| --- | --- | --- |
| CORE実行hostの`rencrow run` | CORE binary | 意味判断・policy判定・状態変更の提案。remote modeではdurable fileを開かない |
| storage hostの`rencrow storage-host serve` | 同じCORE binaryのsubcommand（owner group単位で実装） | durable fileへの唯一のwriter。登録済みの既存owner実装（SQLite／JSONL batch／content-addressed object）をstorage hostのローカルディスク上で開く |
| `internal/infrastructure/persistence/storagehost` | CORE | 閉じた操作契約のserver／clientと型付きerror。未対応操作・未対応storeはfail closed |

storage hostは新しいmodule、外部system、常駐daemonの追加ではなく、COREが永続化ownerであることに
変わりはない。listenerはstorage host上でのみbindし、既定は`127.0.0.1:18820`。PORTは固定で、
`port=0`・空きPORT scan・`port+1`・random PORTをproductionとRenCrow E2Eのfallbackに使わない。

### 転送と認証（transport）

- `storage.host.transport`は`tunnel`（既定）と`tls`。`tls`は未実装であり指定時はstartup config errorで
  閉じる（httpへ無言downgradeしない）。
- `tunnel`ではCORE実行hostの`endpoint`がloopback（`127.0.0.1`／`localhost`／loopback IP）でなければならない。
  LAN／Tailscaleを跨ぐ実bodyは認証済SSH tunnel（既存user SSH認証）とし、http-onlyのBearerをLANへ裸で
  公開しない。運用とE2Eはこの構成に固定する。
- `storage.host.token_file`は絶対path必須で、platform nativeの秘密性検証を通す。POSIXではgroup／otherの
  許可bitを拒否、Windows nativeでは既存のACL検証と同じ方式でowner＝現userかつ許可ACEが
  {現user, SYSTEM, Administrators}に限る（POSIX perm検査をWindowsへそのまま適用しない）。
- requestごとのBearer tokenをconstant-timeで比較し、`401 unauthorized`を返す。Authorizationヘッダが
  2つ以上、`Bearer `以外のscheme、token内のcommaは拒否する。scope外の操作は`operation_unsupported`／
  `store_unavailable`で閉じ、local file accessへの迂回経路を持たない。
- token・endpointの実値（userinfo・passwordを含むURL）をlog・error message・docs・commitへ出さない。
  endpoint解析失敗はraw URLをechoしないsentinel errorで返す。

directory listingを取らず、未知の操作・storeは即座に拒否する。唯一のpathは`POST /v1/rpc`（query付きは
404）で、envelopeは`contract`／`op_id`／`group`／`op`／`generation`／`payload`のみ（unknown fieldと
末尾byteを拒否）。contract revisionは`rencrow-storage-rpc/v1`とし、client／serverのrevision不一致は
`400 contract_version_mismatch`で閉じる。

| `event` | `modules/core.EventStore`（`EventAppender`／`SequencedEventAppender`／`EventReader`） | `event.append`／`append_sequenced`／`get`／`list_component` | owner／RPC／serve契約実装済み。runtime consumer未完 |

### `durable_store_workflow_runtime_tool` のremote責任境界

remote profileでDurable Store ownerが選択された場合、実行hostのCOREは
`storage.databases.durable_store_workflow`を開かず、local fallbackも行わない。実行host上で読めるのは、
secretを含まないcanonical Manifestをvalidation入力として扱う場合だけであり、SQLiteの正本はstorage hostに残す。
正規routeは次の一方向とする。

```text
実SQLite owner
  -> authenticated storage-host Handler
  -> typed DurableStoreWorkflowClient
  -> buildDurableStoreRuntime
  -> Orchestrator.Handle
```

このrouteは`ActionID`、authenticated `UserScope`、`RequirementID`、owner receipt、idempotent replayを
各段で保持する。storage hostとownerを再openした後も同じActionをreplayした場合は既存receipt／canonical rowを
返し、新しいrowを増やさない。storage host unreachable、authentication拒否、contract version不一致、schema拒否、
`outcome_unknown`はすべてfail closedとし、結果不明のままownerを再実行しない。`storage.host.mode: local`の
既定挙動と`storage.databases.durable_store_workflow`のlocal ownerは変更しない。

これは将来のremote受入契約であり、現在のtest evidenceは同一processのhttptest／component integrationに限る。
productionのMessage／DistributedOrchestrator route、別host・実認証request provenance、A7–A9は未確認で、
このcoverage entryを削除する根拠にはしない。

error codeとHTTP status（実装値）:

| code | status | 意味 |
| --- | --- | --- |
| `unauthorized` | 401 | Bearer拒否 |
| `contract_version_mismatch` | 400 | contract revision不一致 |
| `operation_unsupported` | 404 | 未登録のgroup／op |
| `schema_rejected` | 400 | envelope・payload・method不正 |
| `duplicate_op_conflict` | 409 | 同一op_idでpayload／credential scopeが別 |
| `writer_generation_stale` | 409 | client epochとstorage host epoch不一致 |
| `store_unavailable` | 503 | store未開通・remote対象外・owner失敗 |
| `outcome_unknown` | 503 | commit有無が確定できない |
| `storage_host_unreachable` | 503 | 通信層の失敗（client側で生成） |

### 原子性・冪等性（3段journal）

mutating操作は保存hostのprivate 0700 directoryにあるappend-only `journal.jsonl`（record毎fsync）へ
次の順で記録する。

1. `begin`（status `begun`）をfsyncしてからowner storeを呼ぶ
2. owner storeのcommit成功後に`complete`（status `done`＋result）をfsync
3. opがerrorを返した場合は`abort` recordでentryを消し、同じop_idの再試行を可能にする

journalはstore本体（SQLite／JSONL batch）と同一atomic unitではない。そのため「本体commit後・
`complete`保存前にprocessが死ぬ」窓では、commit済みなのに記録が無い状態が起こる。記録の欠落を
未実行と推定できないので、本契約はこの窓を次のとおり閉じる。

- 同一op_idの再送でentryが`begun`のままなら再実行せず`outcome_unknown`を返す（盲目再実行禁止）。
- `host.result(op_id)`がnot-foundの場合も`outcome_unknown`とし、clientはstore側のnatural key
  （`event.append`はevent_id、`raw`はobject id、`task`はtask_id／run_id、`session`はsession id）で
  read-your-writes照会してcommit有無を確定してから、完了させるか新しいop_idで実行する。
  natural key照会を公開していないstoreのmutating操作は`store_unavailable`で閉じ、推定で再実行しない。
- 同一op_idでpayload hashが違う、または発行credential（scope fingerprint）が違う場合は
  `duplicate_op_conflict`で拒否する。
- response loss（transport error・切断）はclientが`host.result(op_id)`で解決する。`done`の記録が
  あればそのresultを採用し、`begun`・不在は`outcome_unknown`。新しいop_idでの盲目retryは禁止する。

### 単一writer・writer generation

- storage host processだけがdurable fileを開く。SQLite WAL／`busy_timeout`、JSONL batchのOS lockと
  journal、`task.Store`の`WriterGeneration` fenceはstorage hostのローカルディスク上で成立し、
  跨hostのSQLite lock共有を生まない。
- protocol側のwriter epochは保存hostの`generation` file（fsync、storage host起動ごとに単調増加）。
  `host` group以外の操作はclientの`generation`が現epochと厳密一致しなければ`writer_generation_stale`で
  拒否し、遅延epochも先行epochもstoreに到達しない（test確認済み）。
- task store自身の`WriterGeneration()`、新Runの現epoch必須、既存Runの開始identity・世代不変は
  保存host側で検証する（既存owner実装が正本）。
- 変更操作の直列化は保存hostの単一writer lockとowner store自身のtransaction lockが担う。

### Task/Run transactionとfenceのremote意味（設計確定・未実装）

`task.Store`はcallback取引なので、単なるCRUD RPCではread-your-writes・rollback・view失効を再現できない。
remoteでは保存host側のtransaction sessionで同じ保証を実装する。

- `task.tx.begin`（scope taskID、mode `task`／`global`／`read`）は保存host側で既存owner取引を開始し
  `tx_id`を返す。取引は保存host process内のpending overlayを持つため、session内の後続readは
  自分のwriteを観測する（read-your-writes）。
- `task.tx.op`は`tx_id`の取引view上で`task.save`等を実行し結果を返す。scope外taskへのwriteは拒否する。
- `task.tx.commit`はcallback成功経路と同じvalidate→atomic commitを実行し、commit時にもscope／fenceを
  検証したうえで`tx_id`を失効させる。`task.tx.abort`・client切断・idle deadline超過はpendingを破棄して
  rollbackする。
- `task.fence.acquire`は`WithTaskExecutionFence`のleaseを保存host側で取得し`fence_token`を返す。
  既存実装どおり短いvalidation取引の後でglobal取引lockは释放し、外部effectの実行中もper-Task fenceだけ
  を保持する。外部effectはCORE実行host側で実行し、完了を`task.fence.release`で返す。
- 外部effectはCORE実行host側で走るため、保存hostの再起動・通信断中に古いCOREの外部effectが生存しうる。
  その結果を書き込むには現epochで新たにfenceを取得する必要があり、旧epochのwriteはすべて
  `writer_generation_stale`で拒否される。保存hostが外部host上の実行そのものをkillできる保証はないため、
  effect自体の外部冪等性は既存の呼び出し側contractに従う。
- 全storeを横断する2PC／CompositeTxは作らない。store間の整合は既存どおり呼び出し側の取引順と
  event storeの正本性に依存する。

### 通信失敗・起動・readiness

- `mode: remote`で`endpoint`／`token_file`未設定、相対path、scheme不正、portが1〜65535の範囲外、
  userinfo／query／fragment／path付き、負の`timeout_sec`／`startup_wait_sec`、`transport: tls`指定は
  startup config errorで閉じる。
- 起動時にstorage hostへ到達できない場合は`storage_host_unreachable`でstartupを失敗させる。
  repository、`~/.rencrow`、OS temp、backup媒体、local file openへの無言fallbackを禁止する。
- 操作ごとの失敗は上のtyped errorとして呼び出し元とViewerへ提示し、0件やempty resultを成功として
  隠さない。
- timeoutは操作別（既定`storage.host.timeout_sec` 30秒）で、20秒で故障判定しない。production startupの
  reconcile時間（実測約192秒、ChatGPT／raw reconcile約100秒。旧版も約210秒）を踏まえ、readiness待機は
  Configで明示した上限（既定300秒）まで待つ。
- storage hostのhealthは`host.contract`（contract revision・writer epoch・提供operation一覧）を正とし、
  store別integrity・容量・journal状態の詳細は未実装である。CORE自身のhealthと区別して表示する。

### 保存状態coverage

remote保存profileで扱うdurable stateのcoverage、対象外の状態、およびremoteで利用不能になる製品機能の
一覧は[設定リファレンスの保存host分離](05_設定リファレンス.md#保存host分離の設定storage-host)を正本とする。
実Agentの生活状態（Conversation L1／archive、Event store、session／operation memory、Task／Run、
Common Raw object／asset）がremoteで動かないまま配備することは認めない。対象外にする状態は、対応する
製品機能を起動時／利用時に`store_unavailable`で拒否として実装し、黙ってlocal fileを開かない。

### 三OS・移行・復旧

Ubuntu／Windows／macOSで同じ操作契約・error code・fail closed挙動を維持する。storage hostは
OS-native filesystemと絶対pathを使い、Ext4／LUKSを必須としない。token fileの秘密性検証はplatform
native（POSIX perm／Windows ACL）で実装し、Windows native E2Eで確認する（安全検査をskip・弱体化しない）。
保存媒体の物理移動・再設定は既存`rencrow-storage-configure`のlabel identity契約を正とし、本契約はその上で
CORE実行hostを保存hostから切り離す。backup媒体とMigration Artifactはstorage host側に留め、backup copyを
remote保存の代替にしない。

### 受入条件

1. local標準profileで既存データ・owner・IDが不変であること（同一Config、同一store、既存test維持）。
2. remote保存profileでCORE実行hostがdurable fileを開かず、Conversation／Memory／Task/Run／
   Common Raw参照がstorage host上の実データに対して成立すること。
3. 認証拒否、path指定拒否、不正schema／contract version、通信断がtyped errorとして現れ、
   無言のlocal fallbackが起きないこと。
4. 単一writer・冪等retry・`outcome_unknown`照会がtestで再現できること。
   `durable_store_workflow_runtime_tool` は、remote owner選択時のlocal DB open／fallback禁止、canonical Manifestの
   validation入力、正規runtime route、ActionID／UserScope／RequirementID／receipt保持、storage host／owner再open後の
   同一Action replayでのrow非増加、unreachable／auth／contract／schema／`outcome_unknown`のfail closedを同じ
   production Message／DistributedOrchestrator、別host・実認証request provenanceを含むintegration test／E2EでGreenにすることを
   将来の受入条件とする。現在は同一process component integration evidenceだけであり、当該coverage entryは開いたままにする。
   A7–A9 E2E、remote profile全体も未確認である。
5. 実行hostの異なるCORE／clientがstorage hostを認証付きで利用するE2E（同一process、loopbackだけ、
   test doubleだけの代替を禁止）。
6. CORE→LLM Gateway→Runtime→Backend→Modelの実会話で保存と再起動後の履歴・Task/Runを確認すること。

受入ID別のstatusと証拠pathは`docs/調査/20261003_storage_host_separation_受入記録.md`を正本とする。

### Failure Knowledge

- Failure: 「journalに記録がなければ同じop_idで安全に再送してよい」と書き、commit済み操作の
  重複appendを許容する契約になった。
- Problem: idempotency journalはstore本体と同一atomic unitではなく、commit後・outcome保存前のcrash窓では
  「記録が無い＝未実行」が成り立たない。
- Cause: 冪等性を記録の有無だけで定義し、store側のnatural key照会を契約に含めなかった。
- Lesson: crash窓はnatural keyのread-your-writes照会か、そのstoreの明示的拒否でのみ閉じられる。
- Invariant: `begun`・journal不在のmutating操作を盲目に再実行しない。durable fileを開くのはstorage host
  processただ一つ。跨hostは閉じた型付き操作だけ。
- Enforcement: `begin` fsync→store→`complete`の3段、`begun`時の`outcome_unknown`、payload hashと
  credential scopeのバインド、writer epochの厳密一致、closed operation set、`store_unavailable`のfail closed。
- Tests: `internal/adapter/config`のremote mode validation、
  `internal/infrastructure/persistence/storagehost`のcontract／冪等／commit直後crash／通信断test、
  跨host E2E script。

## 状態と観測

操作 API は REST、継続状態は SSE と MonitorStore、永続履歴は各 store が担います。TaskID、EventID、from/to、route、provenance、policy decision、結果を追跡可能にし、外部 runtime の health と CORE 自身の health を分けて表示します。

### Check Plan owner実行境界

検査経路は`owner manifest -> RenCrow_Tools planner -> immutable Plan -> owner runner ->
owner route -> receipt`の一方向とします。横断schemaとpruning判断はRenCrow_Tools、
CORE固有checkとallowlist、実行結果はCOREが所有します。EcoSystemはcross-module契約と
配備整合だけを所有し、check意味論やruntime状態を複製しません。

COREのreference runnerはplannerをsubprocessとして呼び、Planのpurpose、phase、評価時刻、
全manifest itemの一意な分類を検証した後、allowlist済みloopback GETだけを実行します。
高コストという理由ではcheckを削除せず、Conversation L1の完全integrityはoffline snapshot用
backup phaseへ分離します。通常runtime routeはlive DBを全走査しません。

会話IDは`modules/core`の安定contractで生成し、adapterごとに独自generatorを作りません。Viewer入力ではHTTP受付時に独立した`turn_id`、`trace_id`、`root_task_id`、利用者発話とactual Agent発話の`message_id`を生成し、同じ値をorchestrator、Task carrier、会話commitへ渡します。multi-Actor routeの別発話は同じMessageIDを流用しません。IdleChatも通常会話と同じUUID contractを使い、LLM token prefetch、timeline、memory、TTSへ同じIDを渡します。Character Runtimeは1 Roundごとにroot `trace_id`と利用者発話の`message_id`を生成し、各Character発話へ別の`message_id`と共通`trace_id`を割り当てます。session logとSSE eventはこの値を保存し、`turn_index`から復元しません。

通常会話の`turn_id`、root `trace_id`、`root_task_id`はHTTP受付時に別々のCanonical IDとして一度だけ生成します。`trace_id`は`NewEventWithTraceID`、MessageOrchestrator、DistributedOrchestrator、SuperAgent、AI Workflow、TTS callback、session log、HTTP受付responseを通して保持し、Turn／RootTaskはTask carrierからEndTurn、receipt、outbox、recall traceへ同じ値を渡します。`TurnID == TraceID`、`TurnID == RootTaskID`、`TraceID == TaskID`は禁止し、adapterはTaskID、ResponseID、SessionIDまたは別種IDからこれらを推測しません。実行を分割するときは別のchild `task_id`を作り、`parent_task_id=root_task_id`とroot `trace_id`を明示伝播します。routingとAgent assignmentは各TaskへCanonical Eventとして記録し、そのEventIDをTaskから逆参照できます。

Economic chainは会話のroot jobとは独立して長期間継続できるため、Opportunity作成時に専用の`trace_id`を生成します。`Opportunity -> EconomicTask -> Workstream Goal / Artifact -> Policy Decision -> Delivery -> RevenueEvent -> Reflection`はentity固有IDを維持しながら同じ`trace_id`を共有します。Deliveryは成果物そのものや外部adapterの低水準logではなく、成果物を誰に・どの形で・どの状態まで届けたかを表すdomain entityです。

## 記憶ストレージ

COREの常時稼働する記憶ストレージはGoから利用できる次の構成を正本とします。

物理配置は[設定リファレンスの「DB物理配置とbackup」](05_設定リファレンス.md#db物理配置とbackup)に
従います。Ubuntuのproduction基準ではCOREの永続情報を`/srv/rencrow/db/core`配下へ集約し、
兄弟moduleの情報をCOREのSQLiteへ混在させません。物理媒体が利用できない場合もrepository内や
一時directoryへ暗黙fallbackせず、storage unavailableとして停止または対象機能を失敗させます。

| 用途 | 技術 | 主な内容 |
| --- | --- | --- |
| 短期会話 | Redis | active thread、直近会話 |
| L1 hot store | SQLite | 会話event、UserMemory、Knowledge候補、Recall trace |
| L2 archive | SQLite | thread summary、中期会話、L1 archive |
| 意味検索 | Qdrant | 会話要約・Knowledgeのvector検索 |
| cold export | Parquet | Goライブラリによるバックアップ・オフライン分析用出力 |

Redisのhost公開境界はloopbackに限定します。標準Compose構成ではhost portを
`127.0.0.1:6379:6379`へ固定し、全interface（`6379:6379`、`0.0.0.0`、IPv6 wildcard）へ公開しません。
COREのactive-thread接続はhost側の`redis://localhost:6379`を使います。hostのbackup runnerは
host portへの別経路を作らず、設定済みcontainer名`rencrow-redis`を対象に`docker exec`でRedisの
snapshot機能を実行します。RedisはCOREのloopback boundary外へ直接公開せず、外部moduleや
LAN clientからhost portへ接続する経路は提供しません。

### Common Raw Dataのsource-of-truth境界

Common Raw Dataは上表に追加する21番目のcatalog DBでも、新moduleでも、外部systemでもありません。
COREが所有する論理source-of-truth層であり、Conversation、UserMemory、Knowledge Memoryへ投影する
入力だけを対象にします。台帳は既存の`storage.databases.conversation_l1`へ追加し、bounded inlineを
超えるimmutable payload／assetは`storage.memory.raw_source_dir`のcontent-addressed objectへ置きます。
台帳とobjectは同じbackup／restore cohortとして扱い、repository、runtime home、temporary directory、
backup媒体への暗黙fallbackはありません。TRADE、GAMES、Imageなど兄弟moduleの独立domain原本は、各owner
moduleのDB／artifact正本を維持します。

source adapterからRecallまでの責務は次の一方向です。

```text
source adapter (ChatGPT export / Chat / news-web / upload / X Bookmark / observation)
  -> CORE immutable Raw intake
     manifest -> record -> append-only state event
  -> domain projection
     Conversation L3 / UserMemory candidate-confirmed / reviewed Knowledge + search index
  -> projection receipt
  -> RecallPack (confirmed | pinned / reviewed projection only)
```

`l1_raw_source_manifest`はsource identity、manifest hash、件数、asset、schema／converter version、
scope、checkpointを、`l1_raw_record`はrecord／parent／thread ID、owner／sensitivity／role、content type、
occurred／ingested time、payload reference、content hash、asset／provenance／rightsを保持する概念tableです。
`l1_raw_state_event`はforget、supersede、reject、訂正を追記し、`l1_raw_projection_receipt`はprojection
type、output store／record、Raw IDs、revision、hash、status、時刻を追跡します。Common Rawのbase schema／intake／object／
runtime／backup-restore契約はsource-focusedに揃っていますが、installed binary、production config／migration、rebuild／restart、
live API／Agent E2Eは未確認です。source-focusedな契約だけで配備済みやimport完了を主張しません。

Toolsはlocal native Goのinspect／convert／verifyだけを担当し、COREのSQLite、Redis、Qdrantを開きません。
COREはauthenticated scope、schema／asset／provenance検証、atomic commit、checkpoint、idempotency、
projection、forgetを所有します。raw payloadを直接検索、prompt注入、Recallしてはならず、同じmanifest hash、
source record ID、content hashのreplayは同じreceiptへ収束し、同一IDでhashが異なる入力は
`rejected/source_changed`にします。missing root／manifest、count／hash mismatch、asset欠落、unsupported
schemaは0件readyに変換しません。`allow_empty=true`をsource contractが明示した場合だけ空sourceを完了に
できますが、ChatGPT exportとKnowledge production migrationは`allow_empty=false`です。

Raw本文を利用者へ返すreadは通常Recall routeではなく、認証済みownerのexact-ID inspect／export／delete routeに限定します。CategoryRecall producerによる内部byte verificationは別のread-only owner checkであり、Raw本文を返却、検索、Recall、prompt注入するrouteではありません。
`forget`はRawを保持してprojection／Recallから除外し、`delete`完了時はpayload／assetを物理削除して、
再import防止に必要な最小tombstoneだけをledgerへ残します。任意SQL、全件raw scan、LLMへのraw payload渡し、
削除済みpayloadの別sourceからの自動復活を許可しません。

映画・人物ViewerのD0/D1の`depth`は、映画catalogの直接関係を基にした派生値です。L1 hot storeの
Memory階層へ保存する値ではなく、複数rootから同じカードへ到達した場合も読み取り時の最小depthを
返します。

DuckDBはCORE runtimeの依存から廃止済みです。L2 archiveは純Go SQLite driverを使い、Parquet出力もGo実装で行います。
旧DuckDBファイルをrollback調査用に保持することはありますが、Configやruntime routeからは参照しません。

SQLiteをpersistent Owner storeとして使う場合、Ownerは`sql.Open`直後かつmigration／init前にprocess内poolを
`MaxOpenConns=1`、`MaxIdleConns=1`へ固定し、modernc SQLiteの`busy_timeout=5000ms`を適用します。read-only
Owner adapterも同じbounded poolとtimeoutを使用します。rows走査中の同一poolへnested query／execを発行せず、
必要値をmaterializeしてrowsをcloseしてから次のI/Oへ進みます。これは単一Ownerのprocess内I/Oを直列化する契約であり、
cross-process共有を許可しません。既存journal mode（WALを含む）は維持しますが、全DBへWALを新規義務化しません。
Conversation L1のlifecycle candidate探索とProfilePromotion contextは2接続に固定したread-only WAL poolで実行し、
ProfilePromotion job一覧、diagnostics、ChatGPT import progressはさらに独立した1接続のoperator用read-only handleで実行します。
job一覧の最新順取得は`created_at DESC, evidence_event_id DESC`のindexでboundedに読み、cold cacheやstartup I/O中の全件sortを禁止します。
lifecycleのwrite transactionはsnapshot対象を再検証した後のoutbox／audit更新だけを所有し、重い候補探索中に
ProfilePromotion claim、Chat保存、明示retry等のOwner write routeを占有しません。

### 記憶backupアーキテクチャ

記憶は一つの復旧単位として扱います。CORE管理下のSQLite、Common Raw ledger、
`storage.memory.raw_source_dir`のcontent-addressed object、session、運用記憶、Parquet cold exportに加え、
Redis active threadとQdrant vector indexを同じsnapshotへ格納します。RedisとQdrantのlive volumeを直接
コピーせず、それぞれの整合性を保証する`SAVE`／snapshot APIから可逆exportを取得します。

```text
CORE停止
  -> Redis SAVE + redis-check-rdb
  -> Qdrant full snapshot API
  -> core_source + Common Raw objects + external-memory をtar.gz化してgzip簡易検査
  -> CORE再開
  -> manifest / SHA-256作成
  -> gzip / archive path / SQLite integrity / export存在restore-check
  -> 検査済みsnapshotだけを世代化
  -> Knowledge mirrorと変更前version保存
```

`backup.memory.require_exports: true`の運用では、RedisまたはQdrantのexportが一つでも失敗した実行を成功扱いしません。古いsnapshotを残したまま当該実行を失敗させ、COREはtrapにより再開します。正常系では可逆archive作成後にCOREを再開し、停止時間外でrestore-checkと世代化を完了します。圧縮は情報を欠落させない可逆形式に限り許可し、現行形式は`tar.gz`です。

保護目標は次のとおりです。

| 項目 | 目標 |
| --- | --- |
| RPO | 最大24時間。timerをJST 03:00から1日1回起動する |
| RTO | 正常なsnapshotと交換用backendがある前提で60分以内を運用目標とする |
| 直近世代 | 28世代（日次で約28日） |
| 長期世代 | 日次14、週次8、月次12 |
| 完了条件 | SHA-256、gzip展開、SQLite `integrity_check`、Redis RDB header、Qdrant snapshot存在が全て正常 |

ParquetはSQLiteから再生成可能な派生物ですが、長期分析の再現性と復旧時間短縮のため同じ`core_source`へ保存してsnapshotへ含めます。Common Raw ledger、object、projection receiptは同じcohortを復元できることを検査し、Knowledgeのlegacy JSONLは移行入力／rollback evidenceとしてmirrorと変更前versionを保持しますが、将来のactive Raw正本とはしません。秘密や個人記憶を別host／cloudへ複製する場合は、保存前暗号化と鍵の別管理を必須とします。

backup媒体はlive storeの代替やfailover先ではありません。通常はunmountし、backup windowだけ
mountして整合snapshot、manifest、checksum、restore-checkを作成します。backup失敗時もlive dataを
backup媒体へ直接書き始めず、直前の検証済み世代を保持したまま失敗を通知します。

### UserMemory自動昇格

UserMemoryの自動抽出は次の非同期経路を現行実装とtargetの共通境界として扱います。ConversationEngineの
Raw保存後に独立したMemoryPromotionWorkerを起動し、通常応答を待たせません。CLI、validator、receiptの
targetは02、06、08に記す採用済み・未実装の契約です。

```text
ConversationEngine
  -> L1 Raw conversation event (observed)
  -> 利用者への応答完了

LLM activity tracker (non-IdleChat sources idle; reservation before lease)
  -> low-priority idle lease
  -> MemoryPromotionWorker
  -> ProfileExtractor via configured RenCrow_LLM conversation.summary_model role
  -> L1 UserMemory (candidate + evidence event IDs)
  -> explicit UserMemory command
  -> confirmed / pinned
  -> Recall prompt injection
```

`ConversationEngine`はRaw保存までを所有し、ProfileExtractorを同期呼び出ししません。`MemoryPromotionWorker`はL1上の未処理範囲、再試行、重複排除、状態遷移を所有します。`ProfileExtractor`はRaw入力から型付き候補を返すLLM変換componentに限定し、queue、永続化、確定昇格を所有しません。LLM利用のIdle判定は既存の共通activity trackerを再利用し、IdleChatの無活動判定や別のGPU監視状態をUserMemory用に複製しません。idle grace後のworkerは同じtracker上で単一の内部reservationを先に取得し、実行中のIdleChatをcancelせず、新しいIdleChatの原子的admissionだけを拒否します。IdleChatを含む既存sourceが空になったとき、reservationは同じsourceのidle leaseへ原子的に変換されます。取得中のidle leaseも同じtrackerの外部busyへ投影し、IdleChat schedulerはその間に新しい生成を開始しません。scheduler確認とprovider開始の間にleaseが取得されても、tracked providerの原子的admissionがIdleChat要求をbackendへ渡しません。foreground要求はreservationまたはleaseをpreemptしてProfilePromotionを延期でき、worker cancel時もreservationを解放しますが、lease contextを引き継ぐProfileExtractor自身はpreempt対象になりません。

L1 Raw event IDを抽出根拠と冪等性の基礎に使い、profile処理専用の公開IDを追加しません。処理状態はL1へ永続化し、インメモリmapまたはgoroutineだけを正本にしません。通常LLM要求はbackground昇格より常に優先し、background処理の開始中に通常要求が到着した場合はcancelして次回Idleへ戻します。batch選択は`chatgpt_export`以外を優先クラス0、`chatgpt_export`を優先クラス1とし、同じ優先クラス内を作成時刻とevidence event IDで決定します。有限retryを使い切ったfailedを再実行できるのは、evidence eventが現存するjobだけをpendingへ戻す明示的なcmd-control APIです。evidenceのないorphan failedは変更せず診断へ残し、job詳細上限に隠れない全row state countとDB pool snapshotを別集計で返します。

Conversation所有のsource registry sweeperとmemory lifecycle jobは一つのcancelable owner contextで動かし、`Dependencies.Shutdown`はIdleChatの停止後に両jobをjoinしてからConversation Archive／L1 storeを閉じます。owner cancellation中のエラーだけはshutdown由来の失敗Taskを作らずに収束させ、実行中のcontextが健全な場合のbackgroundエラーは既存のfailure reporterへ渡します。新しいTaskや別の状態正本は追加しません。

### 外部会話履歴のL3 import境界

ChatGPT export等の外部会話履歴は、Common Rawのsource adapterとして次の一方向境界で取り込みます。これは
COREのartifact serviceとPublic APIを先に定義するtargetであり、source-focusedなCommon Raw基盤、installed
binary、production config／migration、live E2Eを同じ完了状態とは扱いません。

```text
local regular files selected by Ren
  -> RenCrow_Tools native Go local inspect / convert / verify
  -> rencrow.chatgpt_common_raw_bundle.v1 deterministic TAR
  -> RenCrow_CMD one authenticated multipart request
  -> CORE owner / scope validation
  -> private staging under configured raw_source_dir
  -> full manifest / TAR / record / source-file / object / reconstruction verify
  -> Common Raw batches (max 100 source records, max 64 MiB decoded payload)
  -> L3 / UserMemory candidate / reviewed Knowledge projection
  -> export-scoped progress / retry / deterministic finalize receipt
  -> exact-ID UserMemory confirm / pin
```

Toolsはlocal native Goの`inspect`／`convert`／`verify`だけを所有します。`verify`はbundleの形式、hash、TAR EOF／
trailing bytes、counts、safe path、source-file reconstructionを検査します。Toolsはnetwork、CORE API／DB、owner／scope、
request ID、batch、checkpoint、state、policy、receiptを扱いません。CMDはfile preflight、multipart構築、CORE APIへの
一command一request、boundedな単一JSON responseの原文relayだけを行い、hash／schema／batch／checkpoint／state／policy／DB意味論を持ちません。
COREはartifactの意味、authenticated owner／scope、原子的batch commit、checkpoint、Common Raw ledger、projection、
Recall policy、export-scoped progress／retry／finalize、receiptを所有します。finalizeはLLMを呼ばず、取込時に検証済みのimport hash binding、Raw／projection counts、projection receipt、ProfilePromotion終端を機械的に再照合します。それとexact-ID UserMemory `confirm | pin`を別use caseとし、export全体のcandidateをfinalizeで確定しません。原文保存と想起用projectionを分け、projectionの更新や削除でsource原文を変更しません。

Tools bundleはmanifest format `rencrow.chatgpt_common_raw_bundle.v1`、message schema `rencrow.chatgpt_l3.v1`、
converter `chatgpt-export-memory-go/v2`を使います。deterministic uncompressed TARのentryは`records.jsonl`、
`source-files.jsonl`、`objects/sha256/<2>/<hash>`です。`source-files.jsonl`はexportの全元相対fileをbytes／SHA-256と
ordered 32 MiB chunksで索引し、content objectをdedupeしつつ元fileを完全再構成できることを束縛します。manifestは
sorted source metadata、source／message／file／chunk／object counts、source chunks、artifact bytes／hash、schema／converter
version、canonical manifest hashを束縛し、`generated_at`をcanonical hashから除外します。absolute host path、unsafe／non-UTF-8 path、
Python fallbackは許可しません。

ProfileExtractorのLLMはtyped candidateの意味抽出だけを担当し、queue、job state、retry、validation、dedupe、receipt、finalize、確定昇格を所有しません。決定的な取得・検証・変換・状態遷移・終端判定はCORE owner use caseに保ち、LLM出力はstrict validation後も`candidate`以外の効果を持ちません。

通常のProfilePromotionは新しいL1 Raw会話を対象とし、外部履歴importはmanifestとCORE checkpointを持つbounded batch処理として分離します。両経路は同じUserMemory状態契約、private scope、Recall filterを共有します。外部履歴からの抽出だけで`confirmed | pinned`へ自動昇格せず、assistant発言単独を利用者の事実根拠にしません。legacy経路の過去の成功は、Common Raw target、installed binary、production migration、authenticated CMD->CORE E2Eの証拠ではありません。既存event、evidence、confirmed、forget、supersede、Recallを保持したままcutoverすることを採用し、詳細手順と受入条件は[ChatGPT会話exportのL3長期記憶取込](02_機能仕様.md#chatgpt会話exportのl3長期記憶取込)と[Public API](06_Public_API仕様.md#chatgpt-common-raw-import-owner-api)を正本とします。

## Atlas Control Plane

Atlas runtime、Concept／Delivery state machine、Implementation Unit、Evidence Gate、WIP lease、
Workstream接続、Viewer projection、owner APIはCOREが所有します。主要経路は
`owner request -> Atlas service -> state/evidence decision -> Backlog append revision -> Workstream/lease -> projection`
とし、状態判断をViewer、CMD、LLMへ分散しません。

Evidence Refはclaimではなくowner artifactへのaddressとして扱い、COREのkind別verifierがrevision、hash、
receipt、result、鮮度を検証してruntime statusを導出します。Implementation Unitの再実行は
`unit + implementation_revision + target_stage`を冪等keyとし、失敗時は履歴を巻き戻さず新revisionへ
`invalidated_from_stage`を記録します。

Revision 2のverifier入力は`item_id`、`implementation_unit_id`、`implementation_revision`、
`target_delivery_state`を持つtyped Evidence contextです。外部`passed` claimとCORE-owned verified resultを
分離し、固定source（embedded Specification、stage-bound ExecutionReport、固定deployment receipt、cleanな
現行executable revisionを検査するloopback `/ready` とAtlas item smoke）以外はEvidence Gateへ接続しません。
検証不能・scope不一致・stale・hash不一致はsuccessへ丸めずfail closedです。

Execution LeaseとQueue Freezeは別状態です。`DONE`ではclosure receiptを正本にCurrent／Workstream更新と
Lease解放を冪等完了します。`BLOCKED`では失敗終端とdurable Queue Freezeを保存してからLeaseを解放し、
再起動後もFreezeを維持します。新revisionとblocker解消Evidenceを伴う認証済みrequestをCOREが同期検証した
場合だけFreezeを解除し、単なるLease不在から後続Unitを開始しません。

Backlogは既存append-only JSONLをSchema v2へ拡張し、Workstreamの既存物理store内にsingleton
implementation leaseを保持します。EcoSystemはrepository pin、artifact、deployment整合を提供しますが、
Atlas runtime stateを所有しません。CMDはCORE APIへの一request facade、Debug Viewerはread projectionです。
PORTALへAtlasを配置しません。

JSONLの履歴はrewrite/deleteせず、Backfillは全件検証後に差分revisionだけをappendします。Stage／Closure／Freeze
receiptはprepared状態を再起動後に再実行でき、lifecycle JSONLの読込・書込・不正statusは実行可能と推測せず停止します。
Freeze解決は旧blocked Unit、supersedes、blocker Evidence、dependency、他Lease不在を同じCORE decisionで確認し、
pending Freeze→replacement lease→resolved Freezeをowner storeの一操作として確定します。途中停止時はactive Freezeを
維持するため、Lease不在だけでqueueを再開しません。LIVE_VERIFIEDは自動的にclosure receipt付きDONEへ進み、
Currentはcompleted closureを持つDONEだけを返します。

初期Backfill packageはCORE sourceへimmutable artifactとして取り込み、embedded canonical Datasetからだけ
既存Backlog JSONLへreconcileします。`feature_id`から`atlas:<feature_id>`を決定的に導出し、既存Itemがある場合は
Concept／Delivery、Evidence、Implementation Unit、Workstream、owner、priority等のruntime overlayを維持したまま
Design Cardだけを更新します。Specification本文はembedded allow-listを`spec_id`で解決し、request pathや
staging filesystem pathから読みません。Static seedとruntime stateは別projectionであり、EcoSystemをstate storeにしません。

Owner intakeはSchema v2 Design Cardの`feature_id`、`problem`、`idea`、`background`、`expected_effect[]`、
`relation_refs[]`、`specification_refs[]`を任意で保持し、fixed embedded Backfill packageのIDだけを保存前に検証します。
Radar／Candidateのpartial inputへ内容を補完しません。起動時はcanonical reconcile後・Recover前に、完全一致する
legacy `atlas:atlas.lifecycle`／`atlas-lifecycle-v1`（ADOPTED、LIVE_VERIFIED、revision未満2）だけをrevision 2の
QUEUEDへappend migrationし、旧claimを自動verifyしません。migration／Recover failureはAtlas exposureを停止します。
