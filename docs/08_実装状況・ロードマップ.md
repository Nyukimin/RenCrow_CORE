## Kuro / Heavy Codex Execの確定済みside effect境界

KuroをMio、Shiro、Midoriと同格のAgentとし、Persona、Memory、会話SessionをCOREに
保持する設計を採用しました。HeavyはKuroと推論Targetの間に置くExecution Roleとして
維持します。CORE `main`と現行deploymentでは、Kuroの通常応答を
`Heavy provider -> RenCrow_LLM kuro alias -> kuro_codex -> codex_cli`へ接続し、
`codex exec --json --sandbox danger-full-access --cd <CORE workspace> --ephemeral`を実行します。
2026-07-25の実requestでCOREの`recipient=kuro`、Gatewayの`agent_id=kuro`
`target_id=kuro_codex` `adapter=codex_cli`、Codex Exec process、応答返却を連続して確認済みです。
したがって、この経路自体は実装済みであり、未実装課題ではありません。

通常Kuro推論は`danger-full-access`を正式採用します。RenCrow_LLMはKuro／Heavy bindingの
Role profileを`agent_runtime`かつ`danger-full-access`に固定し、target sandboxにも
`danger-full-access`を要求します。`none`／`read-only`への設定変更はvalidation errorです。
COREの`codex.run` Toolは別経路で、引き続き`danger-full-access`を拒否し、
`read-only`または`workspace-write`だけを受理します。
Host Node導入やCodex thread継続はtarget側の変更であり、KuroのAgent identity、
HeavyのRole identity、COREのMemory、Tool承認を移動しません。

## Deployment またはライブ検証に依存するもの

外部 LLM/STT/TTS/Vision/GAMES runtime の起動、実ブラウザの responsive 表示、実音声再生は環境依存です。コード実装済みでも、各 deployment では health、実 request、実表示・再生を別々に検証してください。

GPU、model、port、常駐方式、ある時点の起動・停止状態は各deploymentの観測情報であり、
この文書の実装済み判定へ固定しません。必要な時点で各moduleのhealth、実request、実表示・再生を
再確認し、日時付き証跡は`docs/調査/`へ保存します。

## 現在仕様に含めない旧構想

- 旧 `pkg/*` package path を前提にした architecture snapshot
- 旧 `/deliberate` と agent heartbeat protocol
- Advisor、Knowledge、Economic、To-Be Ops を全面未接続とする古い状態記述
- 無審査の memory promotion、承認なしの公開・送信・請求
- CORE が外部 module の実装本体を再び所有する構成

これらは現在の未実装 backlog ではありません。再採用する場合は、現行の Mio/Shiro/Coder/Advisor 境界、安全条件、cost、timeout、trace を先に再定義します。
