# RenCrow_Harness仕様v0.1 と現行コードの照合

## 概要

提案仕様パッケージ `RenCrow_Harness_Specification_Package_v0.1`（2026-10-06、RH-SPEC-001 / RH-IMPL-001）が現状として記述した内容を、現行のCORE・LLM・external-runtime profileと照合した。仕様の採否・実装は扱わない。

- 判定: 仕様の現状記述はおおむね正確。ただし、Harness bridge設計に影響する未記載事実と記述の補正点がある（「仕様の補正候補」参照）。
- 状態: 読み取り照合のみ。build・test・実機・実Model試験は行っていない。

## 発生条件

- 照合時のHEAD: RenCrow_CORE `e2dd0b16`、RenCrow_LLM `d2166b4d`、RenCrow_Qwen38_Flash `22bb434`。CORE/LLMは仕様の基準commitと同一で、remote mainとも一致（2026-10-06 18:30 JST時点）。
- RenCrow_Switch_Core（Codex fork、Rust）はこの端末にcloneされていない。仕様の根拠D01〜D03（COMPACTION_SPEC.md等）は照合範囲外。

## 手順

1. CLI: パッケージのSHA256SUMSを検証し、BASELINE.jsonの各source blob SHAとHEADの`git rev-parse HEAD:<path>`を比較した。
2. LLM: 主張を3領域（CORE実行経路 / CORE契約・保存・正本 / LLM・Switch・profile）に分け、反証を探す方針で読み取り照合した。
3. 親で主要な根拠をspot-checkし、誤った指摘を棄却した。

## 結論: 仕様の補正候補

重要度順に並べる。

1. **CORE経路ではLLM側のtool-call記法検出が効かない。** CORE providerは`/v1/chat/completions`だけを使う（`internal/infrastructure/llm/providers/rencrowllm/provider.go:166,335`）。raw tool markup検出とplain-text再送は`/v1/responses`経路に限られる（RenCrow_LLM `converter.go:1429,2024`、`handler.go:504-514`）。仕様IMPL §7.4は「Model固有XMLの分解はRenCrow_LLMが行う」を前提にしており、H01/H12の再現条件に直結する。LLM owner側で`/v1/chat/completions`へ適用するか、契約違反を明示するかを決める必要がある。
2. **Shiroのsubagent経路で5区分が失われる。** `shiro.go:115-116`で組み立てたPromptを`renderSystemMessages`（`prompt_context.go:128-136`）がsystem文字列1本へ潰す。PromptContextTypeとuser/historyは落ち、Recall（BeginTurn）も投入されない。仕様のprompt_blocks保持とA03のgolden比較の前提と食い違う。
3. **Actionなしで走るtoolloop経路がある。** taskScopedでない呼出し（例: worker Tool `subagent`のネスト、`internal/infrastructure/tools/subagent.go:39-49`）はAction/Attemptを作らない。`WithSuperAgentRuntime`のproduction callerは`internal/application/orchestrator/message_orchestrator.go:776`と`distributed_orchestrator_process.go:312`の2箇所。A09/A10/RH-010の適用範囲をP0で確定する必要がある。
4. **Gateway内の自動再送はHarnessから見えない。** raw markupとreasoning-only stopのとき、Gatewayが再送する（RenCrow_LLM `handler.go:504-520,1692-1723`）。仕様§8.3と§10.2の「論理要求数と物理attempt数を分けて記録」には、LLM側の計上公開が必要。
5. **「Kuro/Heavy等のCodex Agent Runtime route」という記述はCORE内の実態と合わない。** HeavyはGenerateだけを使う（`heavy.go:42`）。CORE内のCodex利用は、`codex.run` Tool（`internal/infrastructure/tools/runner_codex.go`）、Advisor（`internal/application/advisor/service.go:76-156`）、ShiroのCodexWorkPathである。Kuro側にCodexへの分岐はない。
6. **P0の反映範囲が足りない。** 「COREの01〜10正本」ではなく、Identity CanonicalとAtlasを含む12本を対象にする。
7. **予算算出は全bindingで`budget_unverified`が既定になる見込み。** tokenizer APIがなく、capabilityはdeclaredだけのため。自動圧縮をproductionで有効化する条件に影響する。
8. **既存の名前と衝突しやすい。** `ToolHarness`（`cmd/rencrow/runtime_tool_runtime.go:357-365`、`internal/infrastructure/persistence/toolharness`）と`super_agent_harness`（`runtime_storage_owners.go:30`）が既にある。`harnessbridge`を命名するときに区別が要る。
9. **既存の固定値と所有。**
   - loopのChatは`ReasoningEffortLow`とMaxTokens 4096が固定（`loop.go:38,83`）。
   - thinkingはexecution role profileが権威で、Harnessからは切り替えられない（RenCrow_LLM `handler.go:1567-1644`）。
   - RequestIDとResponseIDの型は内部provider応答に既にある（`provider.go:86-87,156-157`）。ModelActionLinkのkeyはこれを使い、再発行しない。
