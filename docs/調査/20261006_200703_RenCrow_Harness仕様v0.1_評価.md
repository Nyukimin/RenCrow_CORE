# RenCrow_Harness仕様v0.1 の評価

## 概要

提案仕様パッケージ `RenCrow_Harness_Specification_Package_v0.1`（2026-10-06、RH-SPEC-001 / RH-IMPL-001）を、確定した目的に照らして評価した。

- 結論: kernel・Compaction・不変条件・試験台帳は使える。ただし、仕様はHarnessを「COREに組み込む部品」として設計しており、確定した目的（COREの所有物ではない、Codexのような独立Harness）と合わない。v0.2で所有権と配置を書き直す必要がある。
- 状態: 評価だけを行った。仕様の改訂と実装は未着手。
- 現行コードとの照合結果は、別記録 `20261006_183358_RenCrow_Harness仕様v0.1_現行コード照合.md` にある。

## 確定した前提

2026-10-06にユーザーへ確認した内容。以後の評価はこれを前提にする。

1. 最終目的は、CodexのようなHarness「RenCrow_Harness」をGoで作ること。LLMは入れ替え自由にする。
2. RenCrow_HarnessはCOREの所有物ではない。
3. 現在のcodex-switch（RenCrow_Switch_Core、CodexのRust fork）は、そのためのデータ集めである。Harnessの本体にはしない。
4. データ集めは完了している。仕様v0.1は、その結果を踏まえて書かれた。

## 評価

### 目的と合っている点

- **Goで新しく作り、Switchを参考資料にする判断。** 前提1・3と合う。
- **モデル差をHarnessに持ち込まない方針。** 「モデル名での分岐を置かない」「共通化された結果だけを受け取る」は、LLM入れ替え自由と合う。
- **データの使い方。** 試験H01〜H26は履歴26件と行番号・hash付きで1対1に対応する。過去の合格や成功率は持ち込まず、失敗の型だけを試験にしている。要約を隔離要求の既定にした判断も、履歴16・18行目に根拠がある。
- **kernelの設計。** kernelはport越しにしか外を見ない。portの実装者を入れ替えれば、状態遷移・Context・Compaction・失敗分類はそのまま使える。
- **契約。** 不変条件RH-001〜016の大半、RunResultの7分類（`completed` はTask達成を意味しない）、根拠の扱い（現状・提案・未確認の区別）。

### 目的と合っていない点

repositoryとGo moduleは独立させているが、動かすのに必要なものの正本をすべてCOREに置いている。

| 項目 | 仕様v0.1 | 独立したHarnessの場合 |
|---|---|---|
| 起動 | COREのprocessへ組み込む。単体CLIはfixture検査だけ | 自分のCLIやTUIで起動する |
| ID（Run・Actionなど） | COREが発行。Harnessに生成器なし | Harnessが発行する |
| 状態・checkpointの保存 | COREのstore。「独自DBを持たない」 | Harnessが自分の保存先を持つ |
| toolの実行と認可 | COREのPolicyとActionManager | Harnessがshell・ファイル編集・sandbox・許可設定を持つ |
| LLMへの接続 | COREのprovider経由 | Harnessが直接つなぐ |
| 設定・health・正本文書 | COREの設定、COREのhealth、COREのdocs | Harnessのもの |
| 受入の判定者（G01〜G05） | ほぼCORE | Harness |

仕様の冒頭には「新しいTool実行serverは作らない」「Codexを小さく複製する計画ではない」ともある。standalone利用は「将来。そのときに改めて定義する」という扱いである。

### 書き直しと追加が要る部分

- **書き直し:** 仕様書の§0・§3・§4（所有権の表）・§11・§13。実装仕様書の§0〜§4・§13・§17・§19（工程）・§22（gate）。
- **追加:** 仕様が「COREが持つから作らない」とした機能。IDの発行、状態の保存形式、toolの実行とsandbox、許可の判定、起動の入口、設定とLLM接続。役割ごとのtool許可は、codex-switchで得た知見を使える。
- **不変条件の言い直し:** RH-002（AgentやPolicyはCOREが確定）とRH-003（入力の由来はCOREの認証済み受付から）は、主語を「host」または「Harness自身」に直す。

### COREとの関係

独立させると、COREはHarnessを呼ぶ利用者の1つになる。COREは現在、Codexを外部tool（`codex.run`、`internal/infrastructure/tools/runner_codex.go`）として呼んでいる。その呼び先をHarnessに替える形で接続できる。

この形なら、仕様が前提にしていたCORE側の大改修（toolloopの置き換え、Actionの冪等結合、4種のrevisionのCAS）は初回には不要になる。照合記録で挙げた補正候補のうち、CORE内部の3点（ShiroのPrompt、Actionなしの経路、正本12本）も初回の対象から外れる。

### 残っている指摘

次の2点は、独立Harnessの前提でまだ見直していない。

1. **Gatewayの経路の差。** codex-switchは `/v1/responses` 経路を使う。tool記法の検出と自動再送はこの経路にだけある。Harnessがどの経路でLLMにつなぐかで、同じ保護を受けられるかが変わる。
2. **Compaction以外の知見。** 試験台帳はCompactionの26件とkernelの契約18件だけである。実行ループ側の失敗（宣言だけして終了する、出力上限に連続で当たり会話が前進しない、履歴にあるtool名が宣言から欠ける、並列の助言で1件の失敗が全体の失敗扱いになる）が入っていない。advisor・MCP・役割ごとのtool許可にも触れていない。

## 取り下げた評価

経緯を残す。同じ議論を繰り返さないための記録である。

- 「仕様の中心判断（Goで新規作成）は方針と逆」という評価は取り下げた。Switch_Core自体をHarness本体にする、という読み違いに基づいていた（前提3で否定）。
- 「codex-switchからデータを取る計画がない」という指摘は取り下げた。データ集めは完了している（前提4）。仕様のP7にあるexportは稼働中threadの移行用で、データ集めの手段ではない。
- 同じ入力をRustのV2とGo版に通して比べる差分試験は、必須ではなく任意の提案に格下げした。
