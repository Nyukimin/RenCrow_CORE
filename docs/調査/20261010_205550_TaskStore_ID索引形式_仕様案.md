## 1. 目的・非目的・受け入れ基準

### 1.1 問題（現状のbaseline）

1. **tx時間が履歴量に比例する [事実]**。`loadTransactionTaskRunBase`（`internal/infrastructure/persistence/task/transaction_snapshot.go:84`）が`task_state.jsonl`と`task_run.jsonl`を毎tx全件decodeし、`validateTaskTransaction`（`transaction.go:193`）が書込みごとに全RunのTask存在を全件で再検査する。
2. **commitも履歴量に比例する [事実]**。`jsonlbatch.Store.preparePayloads`（`jsonlbatch.go:444`）が追記対象fileの先頭からの全体SHA-256を、`appendPrepared`（`jsonlbatch.go:485`）がもう一度計算する。95MBのstate+runなら1 txで約190MBをhashする。
3. **lock待ちが飽和している [事実+推定]**。読取txも同じ排他flockを取る（`jsonlbatch.go:235`）。state追記は1日8.9k〜12.1k行（10/2〜10/8、読取コピーの集計）で、1 tx約8秒なら容量と同水準になる。
4. **本番baseline [事実]**（10/10配備の`[TaskStore] tx summary`）: write exec p50 5.9s / p95 8.0s、write commit p50 2.0s、write lock_wait p95 20.6s。1 write txの所要はp50で約7.9s。
5. 起動時の`startup_total`は約263秒 [事実]。内訳は未分解で、Task store txの積み上げ（1 tx約8〜11秒の連続）が大きいと推定するが **[未確認]**（IU-0で計測する）。

### 1.2 ユーザーの決定（本書の前提）

1. 毎回の全件読み（全文の走査）をやめる。
2. 履歴は何も捨てない。圧縮しない（処理時間を圧縮率より優先する。ベンチでは圧縮なしが最速）。
3. ID・サマリのリストで「どのIDを読むか」を決め、全文はIDで参照する。
4. 履歴は24時間・3日・30日などの経過で分かれて見えるが、すべて残り、すべてIDで読める。
5. 別のハッシュは作らない（ユーザーの解釈: 索引の各行に持つCRC32Cはこれに含めない。D2）。
6. TaskのIDはユニークにする。最悪でも直近30日以内のIDとは衝突しない設計にする。`Create`は既存IDを拒否する（D8）。
7. 本番は、現在の本番ホストから最終的に移行先ホストへ移す（D12）。受け入れ基準は比率を主にし、履歴への非依存（AC-5）をホストに依らない主基準にする。

### 1.3 目的と非目的

- 目的: tx時間と起動時間を**履歴量から切り離す**。履歴は移動・削除・圧縮・書き換えをせず、全IDが常に`GetTask`系で引ける状態を保つ。
- 目的（ID一意性、決定D8）: TaskのIDをユニークにする。`Create`は既存IDを`ErrTaskExists`で拒否し、最悪でも直近30日以内のIDとは衝突しない。本設計は全期間の鍵mapを持つので全期間で判定できる（5.9）。
- 非目的: (c) Memory Promotionの軽量化（次の段階として検討する、決定D11。9.3）、滞留queued Task（約1.8万件）の整理（本仕様の範囲外。別途、原因の調査と一度きりの整理の計画を作り、ユーザー承認の上で実行する、決定D10。9.2）、Action store等ほかのstoreの肥大、圧縮・削除・退避、移行先ホストへの本番移行そのもの（本書は前提と依存だけを書く、決定D12。10.5）、`domaintask.Store`のinterfaceとremote RPC payloadの変更（変えない）。

### 2.2 `jsonlbatch`のprefix hashを変えずに済むか [事実+推定]

結論: **変えずに済む**。ただしhash量は「当日のsegmentの累計サイズ」で決まり、日平均で数十ms、重い日の日末で約0.2秒になる。サイズ弁（5.3）で上限を約0.18秒に抑える。

- 1 txが追記するfileごとに、`preparePayloads`と`appendPrepared`で**先頭から現在の末尾まで**を2回hashする（コード確認）。hash量 = 2 × Σ（追記したfileの現サイズ）。segmentが当日分だけなら小さい。
- 当日分の量（読取コピーのUTC日別集計。state / run / context / notificationsの合計）: 10/2〜10/8は **6.4〜8.8MB/日**（state 3.5〜4.8MB、run 1.6〜2.2MB、context 0.5〜0.6MB、通知0.8〜1.1MB）、全88日の最大は14.8MB（9/17）。
- 1 txが触るfileの平均は、stateは必ず、runは約65%、contextは約35%、通知は約32%（行数比から）。日平均の累計サイズで、tx平均のhash量は約6MB、日末で約12MB、最大日（14.8MB）の日末で約23MB。
- 本番ホストのSHA-256実効速度は**95〜150MB/s [推定]**。根拠: 現状commit p50 2.0sは約190MBのhash + fsync + 検証を含むので、hash速度は95MB/s以上。CPUはSandy Bridge世代でSHA-NI・AVX2が無い（読取で確認）。移行先ホストにはSHA-NIがあり、実効速度が上がる見込みだが [推定・未測定]、本書の見積りは現在の本番ホストの値（保守側）で行い、移行後に測り直す（1.5）。
- 結果: 日平均 約40〜63ms、日末 約80〜125ms、最大日の日末 約155〜245ms。サイズ弁（当日の6ファイル合計 8MiB超で追加segmentへ切替）を入れると、1 txの最大hash量は約17MBで **約110〜180ms以下**。
- 代替（jsonlbatchのprefix hashを末尾窓に限定する変更）はWAL書式のversionを上げる必要があり、既存の保証を変える。本書では採らない。
- 残る固定費: WALの読み+解析（settle）。WALは256KB超で自動checkpointされるので上限がある。baselineの`write_settle_p50`は要約行から転記が必要 **[未確認]**。

```text
    seg-legacy.tsi        seg0の索引sidecar
    seg-20261011-01.tsi   segmentごとの索引sidecar（閉じたら不変。開いているものは定期的に原子的に置換）
```

| 概念 | 役割 | 主たる真実か |
| --- | --- | --- |
| ログ（seg0 + 各segment） | 行の正本。追記専用、書式は現状と同一 | **正本** |
| 索引（メモリ） | ID・サマリ・全行の位置。読み書きの入口 | 派生物（ログから決定的に再構築できる） |
| sidecar / checkpoint | 索引の永続化。起動時間の短縮のためだけにある | 派生物（消しても正しさは変わらない。再構築時間が延びるだけ） |

設計の要点:

1. **作業集合を履歴から切り離す**: txが読むのは「触ったID」の最新行（pread 1〜数回）で、書くのは当日のログだけ。
2. **何も移さない・消さない**: 終端Taskも元のログに残り、索引に載る。退避パスも保持規則も存在しない。
3. **索引は派生**: 壊れても欠けてもログから作り直せる。作り直しは起動時の1回（seg0は約6.5s [推定]）。
4. **正しさの要は「索引 ⊇ ログ」**: 索引が存在するIDを知らないと`NotFound`になり、`NotFound`なら新規作成する経路（`AdmitAcceptedOPS`、orchestratorのrepair Task）が二重作成する（7.2 C10）。

用語: **segment**=日ごとのログdir（seg0は例外的にroot直下）。**ordinal**=segmentの順序番号（seg0=0、`logs/`の昇順で1,2,…）。**sidecar**=segmentごとの索引file。**位置**=(ordinal, ファイル種別, offset, length)。

### 4.2 segmentの規則

- **名前**: `logs/<YYYYMMDD>-<NN>`。`YYYYMMDD`はUTCの日、`NN`は固定幅2桁（01から）。昇順の辞書順=作成順。99を超える場合はfail closed（日にそれほど多くのサイズ弁切替が起きる状況は異常）。dir名は数字とハイフンだけ（大文字小文字を区別しないFSでも衝突しない）。
- **ordinal**: seg0=0、`logs/`の昇順で1,2,…。segmentは**追加のみ**で、削除・改名・並べ替えをしない。sidecarの位置はordinalで持つ（u16。65,535 segmentは日1個で約179年分。超過はfail closed）。
- **書込み先の選択**: 常に「`logs/`の辞書順最後」（なければseg0）。`max(既存の最後, 今日)`を使い、**過去のsegmentへ戻らない**。時計が逆行しても、新しい日付のdirが既にあればそこへ書く（INV-6）。
- **切替の契機**（5.3）: (1) 最初のwrite時に`utc日(now) > 最新segmentの日`、(2) サイズ弁: 最新segmentの6ファイル合計が **8MiB** を超えた（同じ日の次の`NN`へ）。弁は**6ファイル合計**で判定する（prefix hashの量は追記したfile群の合計に比例するため。2.2）。
- **seg0の扱い**: 段階2以降は読取専用。open時にseg0の各ファイルのsizeがsidecarヘッダの記録（`applied_bytes`）と一致することを検査し、**不一致はfail closed**（旧版の誤起動によるfork検知。INV-7）。
- **ファイル数**: 1日1 segment（8ファイル）+ sidecar 1 → 年約3,300ファイル。許容 [推定]。

### 4.3 sidecar（`.tsi`）の形式

長さ付きbinary、little-endian、固定幅の整数。文字列は`u32長 + bytes`。ベンチの`binary-lenprefix`（72,060件を本番で 11.9ms で読込）と同型で、JSONLにしない。**版**は`format_version`（現在1）。読み手は**完全一致の版だけ**を受け入れ、それ以外は「無い」と扱ってそのsegmentのログから再構築する（派生物なので版上げは再構築で足りる）。

**ヘッダ（固定長）**

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `magic` | 4B | `RTSI` |
| `format_version` | u16 | 1 |
| `flags` | u16 | bit0=`sealed`（閉じたsegmentの最終版） |
| `own_ordinal` / `own_name` | u16 / 24B | 自分のordinalと名前。open時に現在のsegment一覧と照合し、不一致なら再構築 |
| `applied_bytes[6]` | u64×6 | 6ファイルそれぞれについて、**commit確定済みで索引に反映済みのbyte数**。sealedならファイルの最終size |
| `lines[6]` | u32×6 | 6ファイルそれぞれの、このsegment内の行数 |
| `n_tasks, n_runs, n_notifs, n_receipts, n_fences` | u32×5 | 各セクションの件数 |
| `max_run_generation` `max_receipt_generation` `max_fence_generation` | u64×3 | writer generation検査用（INV-5） |
| `max_updated_at` | i64 | このsegment内のTask更新時刻の最大（Phase Bの打切り判定用） |
| `section_offset[]` | u64×N | 各セクションの先頭 |

**セクション**（いずれも「このsegmentのログ内の行」だけを持つ。segmentをまたぐ履歴は`prev_ordinal`で後ろ向きにたどる）

| セクション | レコード | 主な項目 |
| --- | --- | --- |
| 文字列表 | 重複排除した文字列 | status / route / assignee / module / title / start_reason など。レコードは`u32`の添字で参照する（titleはMemory Promotionなど59種類しかなく（試作の実測）圧縮効果が大きい） |
| Task鍵表 | `key16`昇順（UUID 16B） + `flags u8` + `record_offset u32` | flags: bit0=封印時点で終端、bit1=前版あり。Phase Bで「詳細を読まずに」候補を絞るため |
| Taskレコード | `key16`、`prev_ordinal u16`（無ければ0xFFFF）、**このsegment封印時点の最新サマリ**（status, route, priority, interrupt_policy, assignee, module, title, created/updated/started/finished の i64 unix-nano（無ければ0）、read_only、parent `key16`、supersedes `key16`、dependency `key16`の配列）、**このsegment内のstate行とcontext行の位置の列** | 位置=`offset u64, length u32, crc32c u32`（CRC32C採用、D2） |
| Runレコード | `run key16`、`task key16`、`prev_ordinal`、`writer_generation u64`、status, start_reason, assignee、started/completed i64、**このsegment内のrun行の位置の列** | Runの最新版は、そのRunの最後のsegmentのレコード |
| 通知レコード | `task key16`、`created_at i64`、`interrupt u8`、位置 | 全期間の新しい順の一覧に使う |
| receiptレコード | `operation_id`（文字列）、`task key16`（globalなら空）、scope、`writer_generation`、位置 | 冪等操作のreplay判定に使う |
| fenceレコード | event（acquire / release）、`task key16`、`fence_id`、`writer_generation`、位置 | 現状と同じ畳み込みで`persistedTaskFence`を復元する |

**末尾**: `crc32c u32`（先頭から末尾直前までのCRC32C）+ 末尾magic `ISTR`。sidecarの破損・torn writeの検出に使う（ログの行の検証とは別。8.2）。

**不変の約束**: sealedのsidecarは作成後に書き換えない。開いているsegmentのsidecarだけが`tmp + rename`で置換される。いずれも**派生物**であり、消えてもログから再構築される。

### 4.4 メモリ上の索引

#### 構造

試作（付録A）の構造。pointerを含まない配列と、pointerを含まない鍵・値のmapだけで構成する（GCがスキャンしない）。

| 構造 | 内容 | 実測サイズ（本番コピー 72,060 Task） |
| --- | --- | --- |
| `taskRec[]` | key16、created/updated/started/finished、title/assignee/module/route/status/priority、親のslot、state・context・通知の行chainの先頭と末尾、Runのchain | 104B × 72,060 = 7.5MB |
| `runRec[]` | key16、task slot、generation、started/finished、status/reason/assignee、行chain、同Taskの次のRun | 64B × 53,917 = 3.5MB |
| `lineRec[]` | offset u32、length u32、crc32c u32、次の行のindex u32、ordinal u16、種別 u8 | 20B × 388,253 = 7.8MB（CRC32C込み。なしなら16B = 6.2MB） |
| `notifRec[]` | created i64、task slot、行index、interrupt | 24B × 47,956 = 1.2MB |
| 鍵map（Task / Run） | `map[key16]uint32` | 合計 7.9MB |
| 文字列表 | titleは59種類で 2.8KB、assignee / module / route は添字化 | 約0 |
| **合計** | | **27.7MB = 385B/Task**（Mac arm64。amd64でも同じ構造。Go mapの内部overheadで±10%[推定]） |

- 1 Taskあたり平均 5.39 行（state 2.36 / run 1.42 / context 0.94 / 通知 0.67）。
- 任意項目（親・依存・supersedes）は少数（親あり99件、依存・supersedesは0件）なので側表に置き、`taskRec`を太らせない。
- 開いているsegmentで触れたslot（Task / Run / 通知 / receipt / fence）の集合`openTouched`を持つ。`applyPayload`のたびに追加し、回転でリセットする。checkpointと封印はこの集合のレコードだけを書く（segment全体を走査しない）。
- `key16`は`tsk_` / `run_`を除くUUIDの16B。**索引に入れる前にcanonical文字列形（小文字・ハイフン付き）であることを検証**する（`modulecore.validateCanonicalID`は`uuid.Parse`で他の表記も通すため、別表記のIDが同じ16Bに潰れうる）。読取コピーでは非canonical形は0件（試作でparse失敗0）だが、本番store全体は **[未確認]**（IU-0で確認）。

#### メモリの増え方と上限の設計

流入は 1日2,800〜3,800 Task（10/2〜10/8の読取コピー。Memory Promotionが約9割）。

| 段階 | 常駐するもの | 現在（7.2万Task） | 年間の増加 | 上限の考え方 |
| --- | --- | --- | --- | --- |
| **Phase A（v1）** | 全Taskの詳細（385B/Task） | 27.7MB | 約**0.49GB/年**（3,500 Task/日 × 385B = 1.35MB/日） | 現ペースで **約74日後に128MB**に達する |
| **Phase B** | 詳細は「**非終端Task + 直近30日に更新があったTask**」だけ（定常で約12.4万件 = 約47.6MB）。それ以前は `key16 → 最後のsegmentのordinal`（36B/Task、試作の実測）だけ | 約28MB（現在は窓内が全件にほぼ等しく、Phase Aと同じ） | 定常の窓は約48MBで頭打ち。窓の外は約**46MB/年**（古いTaskの36B × 約128万件） | 1年後 約94MB、3年後 約185MB |

- Phase Bは、詳細を失うのではなく**メモリから降ろすだけ**で、ログとsidecarには全て残る。降ろしたTaskを読む時は、sidecarの鍵表を二分探索（`ReadAt`）してレコードを読み、`prev_ordinal`を後ろ向きにたどって全行の位置を得る（コスト: segmentごとに数回の`ReadAt`）。
- 降ろしたTaskへの書込み（`explicit_rerun`など）は、いったん詳細をメモリへ**昇格**してから通常のtxを行う（余計に数ms）。
- **全IDの鍵mapは降ろさない**: Phase Bで降ろすのは詳細（サマリ・行chain）だけで、`key16 → ordinal`は全期間の全IDについて常駐する（36B/Task）。`Create`の既存ID判定（決定D8、5.9、INV-10）の根拠になる。「直近30日のIDは鍵mapと詳細の両方、それ以前のIDも鍵mapで判定できる」を下限として保つ。
- **着手条件**: 索引のheapが **128MB** に達する、またはTask数が30万を超える（どちらか早い方）。現ペースだと約74日後なので、IU-6（15章）は段階2の配備から**約2か月以内**に着手する。(c) Memory Promotionの削減（9.3）が実現すれば増加が約1/10になり、Phase Bは数年先送りできる。
- 監視: 索引のheap、Task数 / Run数 / 行数をhealthに出す。**96MB超でdegraded**（Phase B着手の警告）。プロセス全体の上限（`GOMEMLIMIT`）は運用設定の別件で、本仕様の必須要件にしない。現在の本番ホストはRAM 7.85GB（available 5.4GB）でswapを約3.3GB使用中、COREのRSSは約490MB（読取で確認）。移行先ホストはRAM 30GBで余裕がある。swapと`GOMEMLIMIT`の設定は移行先ホストへの移行の計画で扱う（決定D12、10.5）。Phase Bの着手条件（heap 128MB）はD4のまま変えない。

#### 経過区分（24時間・3日・30日）

履歴は物理的には日ごとのsegmentに分かれるが、**利用者から見える区分は`updated_at`の経過で決まる論理的な区分**で、segmentの境界とは一致しない（Taskは複数のsegmentにまたがる）。

| 区分 | 定義（`now - updated_at`） | 使われ方 |
| --- | --- | --- |
| 24時間以内 | ≤ 24h | healthの件数、`ListTasks`の新しい側の上位K |
| 3日以内 | ≤ 72h | 同上（Memory Promotionのような周期処理の観測） |
| 30日以内 | ≤ 30d | **Phase Bの詳細常駐窓**（設定値。既定30日） |
| それ以前 | > 30d | Phase Bでは詳細をsidecarから引く。IDで常に読める |

## 5. 操作の手順

### 5.1 読む

in-processの読み（`GetTask`ほか）は**OS flockを取らず**、索引の`RWMutex`の読み側だけを取る（5.2、決定D6）。別プロセスのreaderは従来どおりflock + WAL検査（5.7）。

共通手順（IDを引く）: ① 索引のRLock → ② 鍵mapでslotを得る（無ければ`ErrNotFound`）→ ③ 目的の行の位置を選ぶ（最新のstate行など）→ ④ segmentのfile handle（LRUキャッシュ、既定64。無ければopen）に`ReadAt` → ⑤ **読出し検証**（長さが一致、末尾が`\n`、strict JSON decode、行の`task_id`/`run_id`が期待IDと一致、CRC32Cが一致）→ ⑥ 値を返す（防御的コピー）。⑤で失敗したら**`ErrNotFound`にせず**、そのIDについてfail closed（型付きの`ErrRecordCorrupt`）し、healthを異常にする。

| API | 索引で行うこと | ログから読む行 | 結果の並び・Limit（現状と同一） |
| --- | --- | --- | --- |
| `GetTask(id)` | slot引き | 最新のstate行 1 | — |
| `GetContext(id)` | slot引き | 最新のcontext行 1 | 最後の行が有効 |
| `GetRun(runID)` | Run鍵map | そのRunの最新のrun行 1 | — |
| `ListRuns(TaskID)` | そのTaskのRun chain | 各Runの最新行 | `StartedAt`昇順、同値は`RunID` |
| `ListRuns(Status=running)` 等 | `runRec[]`を線形走査して絞り込み（ベンチ: 絞り込み 0.5〜2.7ms） | 結果のK件だけ | 同上。`Limit`は並べ替えの後 |
| `ListRuns(全件)` | 全`runRec`を走査 | 全件を読む（約5.4万件 × 約15µs）。**本番コードからの呼出しは7.4で有界にする** | 同上 |
| `ListTasks(Filter)` | `taskRec[]`を走査して絞り込み、`UpdatedAt`降順・同値は`TaskID`昇順のtop-K（heap選択、ベンチ 4.7ms） | top-K件の最新state行 | `Limit`は並べ替えの後（現状と同一） |
| `ListNotifications(limit, interruptOnly)` | `notifRec[]`をtop-K選択 | K件の通知行 | `CreatedAt`降順、同値は`TaskID` |
| 全行の取得（履歴） | Taskのchainの全位置 | 全行 | CLI `rencrow tasks history <id>`（readerで動く）。`domaintask.Store`には入れない（追加のみ） |

- 返す件数Kの上限が無い呼出し（`Limit==0`の`ListTasks`など）は、全件をdecodeする。**productionの呼出しはallowlistで固定**し、新規の無制限呼出しをarchitecture testで拒否する（INV-8）。
- Phase Bでは、窓外のTaskは鍵mapの`ordinal`からsidecar経由で読む。一覧は新しいsegmentから順に走査し、`max_updated_at`が「集めたK件目のUpdatedAt」より小さくなったsegmentで打ち切る（結果は全件を持つ場合と同一）。

### 5.2 書く（トランザクション）

`jsonlbatch.Write`の骨格（flock → settle → callback → prepare → append → commit）は**変えない**。callbackの中身と、commit直後の1フックだけが変わる。

| 手順 | 内容 | 現状との差 |
| --- | --- | --- |
| W0 | `transactionWithScope`の先頭（`s.mu.RLock`の前）で回転の要否を判定し、必要なら5.3を実行 | 新規 |
| W1 | admission、per-Task lease（`executionFence`）、`s.mu.RLock` | 変更なし |
| W2 | `jsonlbatch.Write`でsegmentのflock取得 → WAL `recoverLocked` → checkpoint → **`ensureSynced`**（索引が`dirty`なら、当日のログを`applied`から実ファイル末尾まで再生。5.4と同じ関数） | `ensureSynced`が新規 |
| W3 | callback。読みは「txのoverlay → 索引 + pread」。書きは現状どおり`json.Marshal`して`pending`に溜め、そのTaskを`touched`に記録。`Create`では同じtxの`GetTask`で既存IDを確認する（5.9） | **`loadTransactionTaskRunBase`の全件decodeと`deriveTransactionTaskRunView`が不要になる** |
| W4 | **触ったIDの検証**（下表） | `validateTaskTransaction`の全件`validateRunOwners`を置換 |
| W5 | `preparePayloads`（当日fileのprefix hash）→ WAL prepare → 各file append + fsync → WAL commit | **変更なし**（hashは当日分だけなので小さい） |
| W6 | **commit確定後、flock保持のまま**、追記範囲（ファイル種別・offset・長さ）をフック経由で受け取り、`applyPayload`（5.4の再生と**同一の関数**）で索引を更新。`applied`を進める | 新規（`jsonlbatch`にadditiveなpost-commitフックを1つ追加） |
| W7 | 戻り値。flock解放 | 変更なし |

- **フックの契約**（`jsonlbatch`への追加は後方互換）: `Write`に任意のcallback（commit record永続化後・flock解放前に、各fileの`(name, offset, appendLength)`を渡す）を渡せる。WAL書式・journal version・prefix hashは不変。
- **索引の更新は1経路**: フックが渡された範囲のbyteを、末尾再生と同じ`applyPayload`でdecodeして適用する（別経路の更新コードを作らない。Semantic Duplicationの回避）。追加decodeは1 txあたり数行（数十µs）。
- **`ErrCommitUncertain`、その他`Write`のエラー**: 索引を更新しない。`dirty`を立てる。次のtxのW2（`recoverLocked`がrollbackまたは確定を終えた後）に、`applied`から実ファイル末尾まで再生して追いつく。**`applied`はcommit確定境界だけを指し、ファイルsizeを信用しない**（INV-4）。ファイルが`applied`より短い場合は不変条件違反として全再構築（5.6）。
- **読みの整合**: 索引の更新（W6）は`index.mu.Lock`の下で原子的に行い、in-processの読みは`RLock`の間は更新を見ない。単発のAPI（`GetTask`など）は`RLock`を**位置の取得まで**で解放し、`pread`とdecodeはlock外で行う（commit済みの行は不変なので安全）。`ReadTransaction`のcallbackは、複数の読みの間で整合を保つため`RLock`を保持する（callbackは外部作用を持たない契約。短い。`ListTasks(Limit 200)`のdecodeを含めても約12ms）。writer-preference（Go標準のRWMutexは待機中のwriterがいると新しいRLockを止める）で、書込みが読みに飢えない。
- **フック内の失敗**（commit確定済みのbyteをdecodeできない等）: 索引を更新せず`dirty`を立てる。次のtxのW2の再生が同じ関数で再試行し、それでも失敗すれば不正行としてfail closed（5.4）。
- **未commitのデータが読まれない**: 索引に入るのはcommit確定後の行だけ。pendingは索引に出ない（txのoverlayだけが見る）。

**W4: 検証の置換**（旧: 毎tx全件で再構築して検査 → 新: 触ったIDと参照閉包）

| 旧（全件） | 新 | 全件の不変条件はどこで守るか |
| --- | --- | --- |
| 全RunのTaskが存在する（`validateRunOwners`） | 書いた各Runについて、そのTaskが索引またはoverlayに存在する（`SaveRun`で既に検査） | 起動時 / 再構築時に全Runを1回検査（Run→Task） |
| 同一Taskにactive Run 1つ | 書いたRunのTaskのactive Runを索引で調べる | 起動時に全件の畳み込みで検査 |
| 既存Runの開始field不変（`validateRunUpdate`） | 同じRunの最新版を索引 + preadして比較 | 再構築時に全版を再畳み込み |
| 新Runは現writer generationを要する | 変更なし | 起動時に`max世代 < 新世代` |
| 親・依存先・supersedes元の存在 | Manager層の`validateRelationships`（変更なし）が`GetTask`で確認 | 同上（storeは強制しない。現状と同じ） |
| execution fenceの衝突 | 変更なし（`touched`で検査） | — |

**落ちる保証**: 現行は読取のたびに全件の整合を再検査するため「ログが外部から改ざんされた時、次の読取で検知する」性質があった。新方式では、改ざんの検知は起動時・再構築時・touchしたIDの読出し検証になる。この差は**受容する残余リスク**で、`rencrow tasks verify`（全segmentの再畳み込み）を定期監査（Check Plan, backup phase）に置いて補う。

**並行性**: 索引の更新はflock保持中の1箇所だけ。別プロセスのwriterは`.writer.lock`で排除済み。in-processの複数goroutineはflockで直列化される。

### 5.3 日の切り替え

契機と判定: W0で、`utc日(now)`が最新segmentの日より新しい、または最新segmentの6ファイル合計が8MiBを超えた場合。判定は**`s.mu`を排他取得した後に再判定**する（check-then-actの分離を避ける）。

| 手順 | 内容 | 途中で落ちた場合 |
| --- | --- | --- |
| R1 | `s.mu.Lock()`（in-flightのtxが全て完了するまで待つ。新しいtxは待たされる）。再判定して不要なら即解放 | メモリのみ |
| R2 | 旧Storeを`Recover`（WALをsettle、必要なら256KB超のWALをcheckpoint）。**失敗したら回転を中止**し旧segmentに書き続ける（WARN、次のtxで再試行） | 旧segmentのまま。データ損失なし |
| R3 | `logs/<新名>/`を作る（`jsonlbatch.New`が6ファイル・WAL・lockを作りdirをfsync）。続けて`logs/`をfsync | 空のdirが残る。次回openで「最後のdir」として採用される（害なし） |
| R4 | 書込み先を新Storeへ切替（メモリ）。索引に新しいsegmentを開く。旧segmentの封印用スナップショットを**メモリ内でコピー**（約1MB、数ms） | メモリのみ |
| R5 | `s.mu.Unlock()`。ここまで（R1〜R5）が書込み停止時間（目標 p99 200ms以下） | — |
| R6 | **lock外**（checkpoint goroutine）で旧segmentのsidecarを`sealed`で書く: `.tmp`に書き → fsync → rename → dirをfsync | `.tmp`が残る、またはsealedが無い。次回openで**そのsegmentだけ**ログから再構築（約6MB、数十〜百ms） |

- 切替で**過去segmentのデータファイルへは何も書かない**（R2のWAL settleはWAL fileであって、データファイルではない）。
- 時計逆行: 新しい名前の候補が既存の最後より小さい（過去の日）場合は回転しない。時計が大きく進んで未来の日付のsegmentが作られた後に時計が戻っても、そのsegmentへ書き続ける。この状態を検知したら`[WARN]`をlogに出す。
- 閉じたsegmentの非settle検知: open時に最新でないsegmentのWALがpending / tornなら、writerは標準の`Recover`を1回だけ適用し（未commitのprepareのrollbackだけで、commit済みのデータは変えない）、監査logを残す。readerは`ErrRecoveryRequired`でfail closed。

### 5.4 チェックポイントと末尾再生

**チェックポイント**（開いているsegmentのsidecarの定期置換）

- 担当: writerが開く**1つのbackground goroutine**（`checkpointLoop`）。起動はopen成功後、停止は`Close()`で行い、**start/stopを対にする**。`Close()`は冪等（`sync.Once` + done channel）で、二段階にする: ① 新規admissionを止め、in-flightのtxを待つ（既存の`lifecycle`）、② goroutineを止め、最後のcheckpointを試み（失敗しても続行）、writer lockを解放する。
- 契機: 前回から **10分** 経過、または新しい行が **5,000** 件以上、または回転（R6）、または`Close()`。値は定数（Configにしない）。
- 手順: ① 索引の`RLock`下で、`openTouched`が指すレコード（約1MB）を**メモリ内でコピー**（ms）→ ② lock外で`.tmp`へ書く → ③ `fsync` → ④ `rename`（置換）→ ⑤ dirを`fsync`。`applied_bytes`には、**コピー時点のcommit確定境界**を入れる。
- **失敗は致命的でない**: ENOSPC、Windowsのrename失敗（他のprocessが開いている場合。sidecarはメモリに読み切ってから閉じる運用にして、有界リトライ）、fsync失敗はいずれも「checkpointが古いまま」になるだけで、正しさは変わらない。連続失敗はhealthに出す。
- 段階1では「開いているsegment」がseg0なので、checkpointは索引全体（binaryで約12MB [推定]）。10分ごとの書込みは約0.1秒 [推定] で、tx経路に載らない。

**末尾再生**（`applyPayload`の呼出し）

- 入力: segmentのファイル種別ごとの`applied_bytes`から実ファイルの末尾まで。完全な行（`\n`終端）だけを順に適用する。
- 行の適用規則（`foldTaskRecords` / `runRecordFold`と同じ）: Taskは最後の版が有効、`Validate()`。Runは版ごとに`validateRunUpdate`と「同一Taskにactive Run 1つ」。Contextは最後の版。通知は追加。receiptは`operation_id`重複で内容が異なれば`ErrTaskOperationReceiptCorrupt`。fenceは現状の`readTaskExecutionFences`と同じ畳み込み。
- 不正な行（decode失敗、検証失敗、末尾に不完全な行がある）は**fail closed**（修復しない）。writerがsettle済みのため、正常運用で不完全な末尾行は現れない。

### 5.5 起動時の復元

writerのopen（`openJSONLStore`）の順序。既存の順序は writer lock → `batch.Recover` → receipts / fencesの全件読み → generation → `loadRuns`による全Run検査。**置き換わるのは、このうち全件を読む部分**（receipts / fences / 全Runの読み込みと検査）で、writer lockとgeneration counterの扱いは変えない。

| 手順 | 内容 | 失敗時 |
| --- | --- | --- |
| S1 | `.writer.lock`を取得、generation counterを進める（現状どおり） | 現状どおり |
| S2 | `LAYOUT`を読む（無ければ旧レイアウト = seg0のみ）。`logs/`を列挙してsegment一覧（ordinal）を作る。seg0のサイズを確認（段階2以降） | 版が未知 / seg0サイズ不一致は **fail closed**（起動しない、原因を明示） |
| S3 | **最新segment**のStoreを`jsonlbatch.New` + `Recover`（現状のroot直下に対する処理と同じ）。最新でないsegmentは5.3末尾の検査 | `ErrRecoveryRequired`は現状どおり |
| S4 | sidecarを読む: 各segmentについて、sealedなら検証（magic、`format_version`、CRC32C、`own_ordinal`/`own_name`、ファイルsize = `applied_bytes`）。**開いているsegment**は、checkpointを読み、無い・不正なら再構築 | 不一致は**そのsegmentだけ**再構築（5.6） |
| S5 | segment順にレコードを索引へ流し込む（後のsegmentが最新サマリを上書き、行chainは連結） | — |
| S6 | 開いているsegmentの`applied`から末尾まで**再生**（5.4） | 不正行はfail closed |
| S7 | **検証**: ① 開いているsegmentと封印されていないsegmentは、ファイルごとの**改行数 = 索引の行数**。② 封印されたsegmentは`sizeとヘッダの一致`のみ（seg0（95MB）を毎回走査しない）。③ 全Run→Task存在、1 Taskにactive Run 1つ、既存の畳み込み検査（いずれも**索引上**で行い、ログは読まない）。④ **世代検査**: `max(全sidecarヘッダとtailのmax_run_generation) < 新世代`、receipt・fenceも同様 | 不一致は fail closed。①の不一致は索引の不完全の疑い（INV-2）として該当segmentを再構築し、再検査 |
| S8 | `checkpointLoop`を開始し、`[TaskStore] index loaded segs=.. tasks=.. runs=.. lines=.. heap=.. dur=..`を出す | — |

- **世代検査の保持**: 「open時に全Runの世代を見る」は、ヘッダの`max_run_generation`で保つ。sidecarが無い・壊れていればそのsegmentを再構築する時にログから最大値を再計算するので、counterが欠落・切り詰められても世代を再利用しない性質（最後の砦）は同じ。
- 索引のヘッダの最大世代が**実際より小さい**（sidecar破損）可能性は、CRC32C trailerとサイズ照合で検知する。それでも通る誤りは再構築でしか見つからないため、`rencrow tasks verify`を定期監査に置く。

### 5.6 作り直し

| 契機 | 範囲 | 手順 |
| --- | --- | --- |
| sidecarが無い・破損・版違い・サイズ不一致 | そのsegmentだけ | segmentの6ファイルを先頭から走査し、5.4の行の適用規則で索引を作り、sidecarを書く |
| 開いているsegmentの行数不一致、`dirty`中にファイルが`applied`より短い | そのsegment、または全体 | 同上 |
| `rencrow tasks rebuild-index`（オフライン、writer lockが取れる時） | 全segment | 全segmentを順に再構築し、sidecarを置換 |
| 初回起動（段階1） | seg0 | seg0を走査して索引を作る（約95MB・27万行。試作 Mac 1.42s、本番 約6.5s [推定]。起動時に1回だけ） |

- 再構築は**ログを一切変更しない**。起動中はlistener開始前に実行し、リクエストを受けない。
- 再構築した時は`[TaskStore] index rebuild seg=.. lines=.. dur=.. reason=..`を残す。再構築はCRC32C（採用時）を**ログの現在の内容から作り直す**ため、再構築時点より前に起きたログの静かな破損は追認する（8.2）。

### 5.7 readerプロセス（`NewJSONLReader`、CLIの`list / show / notifications / history`）

- 書かない（sidecar・checkpointを作らない、segmentを作らない）。
- 手順: ① `LAYOUT`とsegment一覧を読む（最新のdirがまだ開けない場合は1つ前を最新とみなす）→ ② sidecarを読む。無い・不正なsegmentは**メモリ内だけ**で再構築する → ③ 最新segmentに対し`jsonlbatch.Read`（flock + WAL検査）の下で`applied`から末尾を再生する（スナップショットの整合を保つ）。
- readerの索引は**openした時点のスナップショット**で、その後のwriterの追記は見えない（CLIは短命。現状も1回のReadがスナップショット）。
- 旧版のCLIは新レイアウトを読めない。`LAYOUT`があるのに旧版が開く経路を残さないよう、版検査でfail closedにする（旧版側の変更が不要な範囲では文書化のみ。10.3）。

### 5.8 並行性レビュー（`30-coding-and-architecture.md` 3章）

| 観点 | 設計 |
| --- | --- |
| lock順序 | `s.mu`（RWMutex。回転とCloseが排他、txが共有）→ per-Task lease → segmentのflock → `index.mu` |
| TOCTOU | 回転の要否は`s.mu`排他の下で再判定。`Create`の既存ID判定は`createInTransaction`の同一tx内（flock下）で行うので、判定と実行の間に索引は変わらない（5.9）。呼出し元がtx外の`Get`→別txの`Create`で判定する経路（repair Task。7.7 K3）には隙間があったが、D8で`Create`自身が拒否するので閉じる。**ただし索引が欠落していると判定自体が誤る**（INV-2） |
| 停止 | `Close()`は冪等・二段階（5.4）。回転とCloseは`s.mu`を排他で取るため同時に走らない |
| 再入 | tx callback内で**親storeを直接呼ばない**（既存の規約。`RLock`の入れ子 + 待機中の排他取得でdeadlockする）。回転が`s.mu`排他を取るため、この規約の重要性は増す。arch testでの強制はIU-1で評価 |
| タイマー | `checkpointLoop`の1つだけ。start / stopを対にする（Closeで停止） |
| 別プロセス | writerは`.writer.lock`で1つ。readerはflockとWAL検査で整合したスナップショットを得る |

### 5.9 IDの一意性: `Create`の既存ID拒否（決定D8）

ユーザー決定: IDはユニークにする。最悪でも直近30日以内のIDとは衝突しない設計にする。`Create`は既存IDを拒否し、`ErrNotFound`などの別名にしない。これは既存挙動（同じIDの`Create`は新しい版を追記して上書きする）の変更である。

**設計との整合**: 本設計は全segmentの全IDを鍵mapに持つので、判定範囲は直近30日ではなく**全期間**で、要件を上回って満たす。30日の窓（4.4）は詳細の常駐範囲（Phase B）で、一意性の判定範囲ではない。下限として「直近30日のIDは鍵mapと詳細の両方、30日より前のIDも鍵mapで判定できる」を不変条件INV-10にする。

| 項目 | 内容 |
| --- | --- |
| 強制の場所 | `Manager.createInTransaction`（`internal/application/taskmanager/manager.go`）。`Validate`と`validateRelationships`の後、`SaveTask`の前に、**同じtxの**`GetTask`を呼ぶ。成功なら`ErrTaskExists`を返し、`ErrNotFound`なら続行し、それ以外のerrorはそのまま返す（fail closed）。`SaveTask`は更新にも使うので、store層では作成と更新を区別できない。`domaintask.Store`のinterfaceは変えない |
| error | `ErrTaskExists`を`internal/domain/task`の**新規file**に定義する（`task.go`はCodexの変更と衝突するため触らない）。`errors.Is`で判別でき、`ErrNotFound`・検証error・`ErrCommitUncertain`のいずれとも別。メッセージにtask_idを含め、record本文は含めない |
| 原子性 | 判定と作成は同じtx（同じflock・per-Task lease）の中にあり、TOCTOUが無い。同じtx内の2回目の`Create`は、pendingを見るoverlay経由の`GetTask`で拒否される（transactionStoreの`GetTask`がoverlayを見ることは [未確認]。U16、R-13で試験） |
| 判定の根拠 | 索引の鍵map。判定は**canonicalなkey16**で行い、大文字などの非canonical表記が別IDとして通らないようにする。canonical形でないTaskIDの入力はcanonical検証（4.4）で拒否する（本番に非canonical形があるかはU4） |
| 前提 | 索引が完全であること（INV-2）。鍵mapが全segment分そろうまでlistenerを開始しない（5.6）。`dirty`中・再構築中の`Create`は`blocked`にする（復旧中は書込みを受け付けない、4.5）。判定は書込み主体のprocess（remote profileでは保存host側）の索引だけで行い、readerの索引では行わない |
| Phase B | 降ろすのは**詳細だけ**。全IDの鍵mapは降ろさない（4.4）。30日の窓外のIDへの`Create`も拒否される（IU-6の試験） |
| remote profile | `ErrTaskExists`が呼出し元で`errors.Is`により判別できる必要がある。判定をCORE側のManagerで行う場合はwire codeの追加は不要。保存host側で行う場合はwire codeの追加が必要で、これは「payloadを変えない」方針の**additiveな例外**として明記する（U14。IU-3で確認 [未確認]） |
| `ErrCommitUncertain`後 | `Create`を再試行しない。`GetTask`で確認し、存在すれば前回成功とみなす（既存Taskの内容が要求と一致することを確認する）。盲目的に再試行すると、`ErrTaskExists`が「前回成功」を意味しうる |
| 既存データ | 過去に同じIDで`Create`が繰り返されたTaskは、既に複数の版として存在しうる（最後の版が有効）。D8は将来の`Create`だけを対象にし、起動時にはこれを拒否しない。実績はIU-0で数える（版間で`created_at`が異なるTaskIDの数。U15） |
| 配備と戻し | 新しいConfig値は作らない（呼出し元の修正と同じreleaseで有効）。F-5は索引に依存しない（旧経路でもtx開始時に全件を読んでおり、追加の費用はほぼ無い [推定]）ので、IU-3の中で先行して配備できる。F-5を含むreleaseを旧binaryへ戻すと一意性が消える。ログ書式は変わらないので戻せる |

呼出し元ごとの扱いは7.7。

## 6. 障害時の挙動

方針: **ログは`jsonlbatch`のWALが守り、索引は派生物としてログから復元する**。復元できない状態（ログの欠損・改ざん）はfail closedにして、修復を自動化しない。

### 6.1 txの途中で落ちた場合（段階1・2共通）

| 停止の地点 | ログの状態 | 索引 | 再起動後 |
| --- | --- | --- | --- |
| WAL prepareの前 | 変更なし | 変更なし | 影響なし |
| prepare後〜各file append中 | 一部のfileに未commitのbyte | 未更新 | 既存の`recoverLocked`がrollback（`Truncate(offset)`）。索引は元から未更新 |
| 全append後〜commit record前 | 全fileに未commitのbyte、commit無し | 未更新 | 同上（rollback） |
| commit record永続化後〜フック前 | 確定 | **未更新（checkpointは古い）** | 末尾再生が`applied`から実末尾までを適用して追いつく |
| フック後〜checkpoint前 | 確定 | メモリのみ更新 | 同上 |
| `ErrCommitUncertain` | WALの形状で結果が決まる | 更新しない、`dirty` | 次のtxのW2（`recoverLocked`の後）で再生。`applied`はcommit確定境界のみ |
| ENOSPC / fsync失敗（append中） | 既存の`rollbackFailedTransaction`がdata fileを切り戻しrollback recordを追記する。切り戻しも失敗した場合は`ErrRecoveryRequired` | 未更新 | 後者は次のtxの`recoverLocked`または次のopenが回復する（既存の挙動）。txは呼出し元へエラーを返す |
| 電源断 | `File.Sync`の保証水準は現状と同じ（強化も弱体化もしない） | 同上 | 同上 |

### 6.2 日切替の途中で落ちた場合

5.3の表を参照。要点: R2〜R3の間は旧segmentが唯一の書込み先、R3後の空dirは次回「最後のdir」として採用される、R6の失敗はそのsegmentの再構築だけで済む。**どの地点でも過去segmentのデータファイルは変わらない**。

### 6.3 checkpoint・sidecarの途中で落ちた場合

| 停止の地点 | 状態 | 再起動後 |
| --- | --- | --- |
| `.tmp`書込み中 | 旧sidecarが残る、`.tmp`が孤児 | `.tmp`を整理。旧sidecar + 末尾再生 |
| `rename`の前後 | 旧または新のsidecar（どちらも整合） | そのまま使える。新が古いsidecarより`applied`が進んでいる |
| dir `fsync`前 | renameが電源断で巻き戻る可能性 | 旧sidecar + 末尾再生 |
| sidecarのbit反転・切り詰め・欠落 | CRC32C trailerまたはサイズ不一致 | そのsegmentだけ再構築。正しさは変わらない |
| Windowsでrename失敗 | 旧sidecarのまま | 有界リトライ後に諦め、次回に再試行（致命的でない） |

### 6.4 起動時の回復中に落ちた場合

再構築は何も変更しないので、中断は「次回の起動で最初からやり直す」だけ。sidecarの置換は6.3と同じ。

### 6.5 段階2への切替（10.3）の途中で落ちた場合

| 手順 | 停止後の状態 | 再起動後 |
| --- | --- | --- |
| M1 seg0をsettle | 変更なし | 続行 |
| M2 seg0のsidecarを`sealed`で書く | sealedが無い | 再作成 |
| M3 `logs/<初回>`作成 | 空dir | 続行（冪等） |
| M4 `LAYOUT`を原子的に作る | 無い | M3の完了後に再実行 |
| M5 seg0を0444にする | 一部だけ0444 | 再実行（冪等） |

各手順は状態を確認してから行う冪等操作で、**書込みの開始はM5の完了後**。

### 6.6 破損・改ざん・欠損

| 事象 | 検出 | 挙動 |
| --- | --- | --- |
| 行のbit反転（ログ） | 読出し検証（decode / ID一致 / CRC32C一致） | そのIDだけ`ErrRecordCorrupt`（`ErrNotFound`にしない）、healthを異常にする。他のIDは動作継続 |
| 封印済みsegmentのファイルsizeが想定と違う | open時の`applied_bytes`照合 | **起動しない（fail closed）**。旧版の誤起動によるforkや手編集の疑い |
| segment dirの欠損 | ordinal照合（sidecarの`own_name`とdir列挙） | **起動しない**。履歴が失われているため修復しない |
| 索引の行数 < ログの行数（開いているsegment） | 改行数照合 | 再構築して再検査。再構築後も不一致ならfail closed |
| 時計の逆行・大幅な進行 | 5.3 | 過去segmentに戻らない。`[WARN]` |
| 2つ目のwriter | `.writer.lock` | `ErrTaskWriterBusy`（現状と同じ） |
| readerが回転・checkpoint中に開く | 最新dirが開けなければ1つ前を使う | 整合したスナップショットを得る |

### 7.5 前案から消える危険と新たに増える危険

**消える（新方式では存在しない）**

| 前案の危険 | 理由 |
| --- | --- |
| 退避パスの中間状態（P4 intent・P5 4ファイルrename・roll-forward・SHA判定）の障害窓 | 何も移さない。過去segmentを書き換えない |

| 退避中にwriter lockを10〜300秒保持 | 退避が無い。最長でも日切替の約数十ms |
| 保持規則の誤分類、E1〜E6の例外条件、時計異常の閾値判定 | 保持規則が無い |

## 8. 選択肢の比較と推奨

### 8.1 行の置き方: (a) 現位置のまま + 索引が全行の位置を持つ / (b) 終わったTaskの行をID単位の連続した1単位へ書き直す

ユーザーは圧縮の話の中で「IDごとに圧縮するのが普通」と言った。圧縮しないことになったので、IDごとにまとめる意味があるかを比べる。

| 観点 | (a) 現位置のまま | (b) ID単位へ書き直す | 判定 |
| --- | --- | --- | --- |
| 読み出し（最新の1行） | pread 1回（37µs） | pread 1回 | 同じ |
| 読み出し（Taskの全履歴5.4行） | pread 5.4回（warm約70µs、冷えたHDDならシーク）。SSDなら問題にならない（`/`のdisk種別は[未確認]） | pread 1回（37µs） | (b)が有利だが、全履歴を読む経路はhot pathに無い |
| 書き込み | 追加の工程なし | 終わったTaskの行を新しい連続領域へ書く工程が増える（約6.6MB/日、fsync込み 約50〜100ms/日 [推定]） | (a) |
| 障害時の安全性 | 書き直しが無い。過去ログは不変 | 書き直し中の途中停止に対するintent・roll-forward・二重行の整理が必要（前案のP2〜P6と同種） | (a) |
| 過去ログの不変性 | **満たす** | 旧位置の行を残すとディスクが2倍、消すと「何も捨てない・過去ログを書き換えない」に反する | (a) |
| ロールバック | 連結のみ（逐語・順序どおり） | ID単位に並べ替えられるので、連結しても元の**ファイル内順序とは別**になる（畳み込み結果は同じでもバイト列は同じにならない） | (a) |
| 索引メモリ | 20B × 5.39行/Task | 終端Taskは位置が1つ（約−88B/Task、約−23%） | (b)が有利だが、Phase Bで窓外はsegment単位に降りるため差は縮まる |
| 単純さ | 書き直しの工程・その障害時の回復が不要 | 工程と回復が増える | (a) |

**推奨: (a)**。(b)の利点（全履歴の読み出しが1回、約23%のメモリ削減）は、hot pathに無い読み方と、Phase Bで解消される量にすぎず、(b)の費用（書き直しの工程とその障害時の回復、過去ログの不変性とロールバックの逐語性の喪失）に見合わない。**ユーザーが(a)を採用した**（2026-10-10、17章 D1）。

### 8.2 チェックサム（読むときの破損検出）

別のハッシュは作らない。過去のsegmentは書き換えない。当日のログは`jsonlbatch`のWAL（prepare / commitとprefix hash）が守る。残るのは**読むときの破損検出**。

| 案 | 検出できるもの | 見逃すもの | 費用 |
| --- | --- | --- | --- |
| (i) length + strict JSON decode + 行のIDが期待IDと一致 | offsetのずれ、切り詰め、ゼロ埋め、構造を壊すbit反転、別行への誤参照 | **文字列の内部のbit反転**（titleやsummaryの1文字の変化） | 追加費用なし（decodeは既に行う） |
| (ii) (i) + 索引の各行位置にCRC32C（4B/行） | (i)に加え、**書込み時に作ったCRC**とのずれ（書込み後にディスク上で起きたあらゆる変化） | 再構築より**前**にログが変質し、再構築後にCRCがそれを追認する場合（CRCは再構築時にログの現在の内容から作り直される） | メモリ +4B × 5.39行/Task = **+22B/Task（+5.6%、1.6MB）**。計算は約0.2µs（CRC32C命令。本番CPUはSSE4.2対応） |
| (iii) SHA-256など暗号学的hash | (ii)と同等 | 同上 | 禁止（ユーザー決定） |

- (ii)の価値の大部分は、**書込み時にメモリ上のbyte列から作ったCRC**がsidecarに残り、以後の読みで端から端まで検証できる点にある（新版が書いた行すべて。段階1の稼働中に書かれた行から対象）。seg0の既存データは初回の再構築でCRCをその時点の内容から作るので、追認になる。
- アドバイザの指摘: (ii)の最大の価値は「索引とログのoffset不整合の検出」だが、これは(i)のID一致検査でも拾える。差は文字列内部のbit反転。
- **(ii)を採用する**（ユーザー決定、2026-10-10、D2）。CRC32CはSHAではなくチェックサムで、ベンチの37µsに既に含まれている。ユーザーは「別のハッシュは作らない」にCRC32Cを含めない解釈とした。参考: (i)で運用する場合の残余リスクは文字列内部のbit反転で、sidecarの版を上げずに後から追加できる（CRC領域は派生物の一部のため再構築で足りる）。

### 8.3 索引の永続化構造

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **I-1 segment別の不変sidecar + 開いているsegmentのcheckpoint（推奨）** | 5.4 | 書き直すのは開いているsegment分だけ（約1MB）。壊れても再構築はそのsegment分（数十〜百ms）。Phase Bの足場になる | レコードがsegmentをまたぐので`prev_ordinal`のたどりが必要 |

## 9. 保持期限・cold退避が不要になること

### 9.1 理由

1. **tx時間が履歴量に依存しない**。読みは触ったIDの数行のpreadで、書きは当日分のfile（hash量 約6MB/tx）だけを見る。履歴に比例するのは「ディスク（約6.4〜8.8MB/日）」と「索引メモリ（385B/Task）」で、前者はtx時間に出ず、後者はPhase Bで有界。
2. **全IDが常に引ける**ので、hot missという概念が無い。前案の契約変更（read-through、`ErrTaskArchived`、一覧はhotのみ）は不要。
3. **何も移さない**ので、退避パス・intent・roll-forward・restore・退避中のlock占有が存在しない。
4. 履歴の「見え方」（24時間 / 3日 / 30日）は**論理的な区分**で、保存の形に影響しない（4.4）。

### 9.2 滞留したqueued Task（約1.8万件）

- **性能の問題ではなくなる**: 前案ではhotの床（6.9MB）として残ったが、新方式では索引7MB（18,655 Task × 385B）に収まり、tx時間に出ない。Phase Bでも「非終端は常に詳細常駐」なので約7MBが増え続ける程度（atlas_acquireだけで約280件/日 → 約0.1MB/日）。
- **データの問題としては別件で残る**: Runを持たない`queued`が約1.8万件、実行されずに積まれている。一覧のノイズ、実行枠の判断への影響がある。ユーザーはこれを**一度まとめて整理したい**とした（決定D10、2026-10-10）。**本仕様の範囲外**のままとし、**別途、原因の調査と一度きりの整理の計画を作り、ユーザー承認の上で実行する**。整理の方法は調査と計画で決め、IdleChat・Atlas・background jobの各ownerの判断（S1）に関わる。承認前には何も変更しない。**本仕様は性能の前提にしない**（前案D6の「別S1を期限付きで起案」は、この調査と計画に置き換える）。

### 9.3 (c) Memory Promotionの扱いとの関係

Memory Promotionは流入の約9割（Task件数）を占める。本方式ではtx時間を下げる効果は(c)なしで得られるが、**メモリ増加はMemory Promotionに比例する**。(c)（canonicalなTaskにしない／集約する）が実現すると増加が約1/10になり、Phase Bの着手が数年先送りできる。ユーザーは(c)を**詳細に軽量化させる**方針とし、**次に検討する**（本仕様の次の段階。決定D11、2026-10-10）。本仕様の範囲外で、検討の入力（流入の内訳、Phase Bの着手時期への影響）は4.4と付録A.4にある。

### 11.1 変更区分

**S1**。`docs/05_設定リファレンス.md`のimpact class表で、S1は「owner moduleの既存subtree内へ新しいSQLite file、object store、append log等の物理storeを追加」、さらに「retention、削除、RPO／RTO、backup範囲を変更する場合は同じstore内でもS1」。本案は`logs/`（日ごとのappend log）と`index/`（派生物）を同じowner subtree内に追加し、backup単位が「不変segmentの追加」に変わる。**retention・削除の方針は変えない**（現状も無期限、削除なし）。S2（新DB engine・外部service・remote database・mount・cross-module access）には当たらない（Go標準APIのみ、同じmodule、同じ`workspace_dir`配下）。

### 11.4 Failure Knowledge（実装時に`docs/調査/`へ記録）と不変条件

- **Failure**: 履歴量に比例するtx時間でグローバルlockが飽和し、終端書込みの期限切れ・枠占有・chatのCORE内待ち・起動時間の増大が発生した。
- **Problem**: task storeは「全履歴 = 作業集合」を前提に、毎txで全件をdecodeしhashしていた。保持期限も圧縮も索引も無かった。
- **Cause**: 追記専用JSONLの設計が、IDによる参照の経路を持たなかった。高頻度の周期処理（Memory Promotion）をcanonicalなTaskにしたため流入が支配的になった。また`Create`が既存IDを拒否せず上書きできたため、冪等性が呼出し元の事前`Get`（tx外のcheck-then-act）に依存していた。
- **Lesson**: 履歴は動かさず、**IDで参照するための派生索引**を持ち、書込み先を日次に分けて「触るファイル」を有界にする。派生物は決定的に再構築でき、正本はログだけにする。
- **Invariant / Enforcement / Tests**:

| ID | Invariant | Enforcement | Tests |
| --- | --- | --- | --- |
| INV-1 | 閉じたsegmentのデータファイルは書き換え・削除・移動をしない。書込み先は最新segment 1つ | 書込み経路の限定、seg0 0444、過去segmentのsize照合（open時） | R-5、過去ファイルのsize / mtime不変試験 |
| **INV-2** | **索引 ⊇ ログ**: ログに現れる全ID・全行が索引に存在する | 開いているsegmentの改行数 = 索引の行数（open時）、`verify`、再構築、単一の`applyPayload` | R-9（oracle差分）、R-3、障害注入 |
| INV-3 | 索引・sidecarは派生物。削除しても再構築で全IDが復元し、再構築結果 = 読込結果 | `rebuild-index`と`verify`の比較 | R-8 |
| INV-4 | `applied`はcommit確定境界のみ。`ErrCommitUncertain`で索引を更新しない | `dirty` + 末尾再生 | 障害注入（commit前後） |
| INV-5 | writer generationの単調性は全segmentのRun・receipt・fenceに対して保たれる | ヘッダの最大世代、open時の検査 | R-6 |
| INV-6 | 書込み先は`max(既存の最後, 今日)`。時計が逆行しても過去segmentへ戻らない | 回転の判定 | R-5（時計逆行） |
| INV-7 | 封印済みsegment（seg0含む）のsizeが想定と一致しない場合は起動しない | open時の照合 | R-10、旧版誤起動の試験 |
| INV-8 | productionの無制限list呼出しをallowlistで固定する | architecture test | F-4 |
| INV-9 | 読出しで検証に失敗したIDは`ErrNotFound`にせず、そのIDだけfail closed | 型付きerror | R-2、bit反転試験 |
| **INV-10** | **IDの一意性**: 全期間の全TaskIDが鍵mapで判定でき、`Create`は既存IDを`ErrTaskExists`で拒否する。下限として、直近30日のIDは鍵mapと詳細の両方、30日より前のIDも鍵mapで判定できる。Phase B・再構築・sidecar破損時も保つ | 鍵mapは詳細を降ろしても保持する、索引が完全になるまでlistenerを開始しない、`dirty`・再構築中の`Create`は`blocked`、`createInTransaction`の同一tx内`GetTask`、canonicalなkey16で判定 | R-13、R-14、IU-6のPhase B試験 |

### 14.2 障害注入

- **強制終了点**（子processへSIGKILL。WindowsはTerminateProcess）: tx（WAL prepareの前後、各file appendの後、commit recordの前後、フックの前後）、回転（R2〜R6の各前後）、checkpoint（`.tmp`書込み中、fsync後、rename前後、dir fsync前後）、再構築（途中）、段階2切替（M1〜M5の各前後）、`concat`（種別・segment境界の途中）。各点で再openし、(a)全IDが読める、(b)ログの全行が不変（行数・サイズ）、(c)索引 = 全再構築、(d)世代検査が成功、を検査する。
- 資源障害: ENOSPC（小容量FSまたはsize制限seam）、fsync失敗（既存の`syncFn` seam）、torn `.tsi`、sidecarの切り詰め・欠落・bit反転、segment dirの欠損、seg0のsize不一致、時計の逆行・大幅な進行。
- 並行: 100 goroutineのtx + 回転 + checkpoint + readerの同時実行（`-race`）。

### 14.3 性能

- 1.4の各ACを`Benchmark`として恒久化する。本番データそのものはrepositoryに入れず、状態比・版数・行byte数が本番の分布に一致する合成生成器を使う（試作の`idx-proto`相当の生成を取り込む）。
- 絶対秒はhostで揺れるため、CIの判定は「**旧実装に対する比**」（例: 7.2万Task、当日の1 txが旧実装の5%以下）。絶対値は観測目標。
- 本番: IU-1のbaseline比（AC-1〜AC-4、AC-9、AC-10）。**SHA-256の実効速度（95〜150MB/s）は本番ホストで未測定**で、IU-0で測る（現在の本番ホストと移行先ホストの両方。ホストを移したらbaselineを取り直す、1.5）。

### 14.4 三OS

Linux amd64 / Windows amd64 / macOS arm64のCIで、unit・障害注入・`-race`（Linuxのみ）を実行する。固有: (1) Windowsのsidecar置換は他のprocessが開いていると失敗するため、読み切って閉じる + 有界リトライ + 失敗は非致命、(2) 0444相当（読取専用属性）で`O_RDWR`のopenが失敗すること、(3) dir fsyncがWindowsでno-op（`jsonlbatch/directory_sync_windows.go`が記すとおり電源断時の挙動は未検証。既存の保証水準と同じ）、(4) 改行変換が起きない（LF固定、binary open）、(5) path区切りとUTF-8 path、(6) 大文字小文字を区別しないFS（dir名は数字とハイフンのみ）、(7) file handleの上限（macOSの既定soft limit 256）とLRUキャッシュ。

### A.2 hash量のモデル

`hash量/tx = 2 × Σ（そのtxが追記するfileの、現時点のsize）`（`preparePayloads`と`appendPrepared`の各1回）。stateは全txが追記し、runは65%、contextは35%、通知は32%のtxが追記する（10/2〜10/8の行数比）。日の経過割合x（0〜1）で、file sizeは1日の合計 × x。

| 場面 | 当日合計 | 平均hash量/tx | 95MB/s | 150MB/s |
| --- | --- | --- | --- | --- |
| 通常日の平均（x=0.5） | 約7.2MB | 約6.0MB | 63ms | 40ms |
| 通常日の日末（x=1.0） | 約7.2MB | 約11.8MB | 124ms | 79ms |
| 最大日（14.8MB）の日末 | 14.8MB | 約23MB | 242ms | 155ms |
| サイズ弁（8MiB）の上限 | 8MiB | 約17MB（全fileを追記するtx） | 177ms | 112ms |

これにfsync約5回（WAL prepare、各file、WAL commit。本番ベンチ 1.34ms/回で約7ms）とWAL解析を加える。baselineの現状commit p50 2.0sは190MBのhash + fsync + 検証で、hash速度は95MB/s以上と逆算した。

- 結果（Mac arm64、本番コピー、2回とも同一）: 行数 state 170,130 / run 102,552 / context 67,615 / 通知 47,956、decode失敗0。Task 72,060、Run 53,917、行 388,253、通知 47,956。distinct title 59（計2.8KB）。**構築 1.42s、heap 27.7MB（385B/Task）**。内訳: `taskRec` 104B × 72,060 = 7.5MB、`runRec` 64B × 53,917 = 3.5MB、`lineRec` 20B × 388,253 = 7.8MB（CRC32C込み）、`notifRec` 24B × 47,956 = 1.2MB、鍵map 7.9MB。Phase Bの`map[key16]uint16`は **36B/entry**（72,060件で2.6MB）。
- 試作はサイズの見積り用で、製品の構造ではない（任意項目の側表、sidecar形式、`applyPayload`の検証規則は含まない）。

### A.4 増加の見積り

3,500 Task/日 × 385B = 1.35MB/日 = 約0.49GB/年（Phase A）。128MB到達まで (128 − 27.7) / 1.35 = 約74日。Phase B: 窓内 (30日 × 3,500 + 非終端18.7k) = 約12.4万件 × 385B = 約48MB + 窓外 36B/Task（1年で約128万件 = 約46MB）。

### A.5 換算

Mac→本番の係数 ×4.6 は前案の単点（本番tx約11秒 ÷ Mac Create 2.39秒）。本番のベンチ値（pread + decode 37µs、リスト読込 11.9ms、絞り込み 0.5〜2.7ms、1件fsync 1.34ms）は本番ホスト実測。

## 付録B. 設計判断の記録（アドバイザ相談）

方針（日次segment、索引、tx、行の置き方、チェックサム）を確定する前に、読み取り専用のアドバイザへ相談した。要旨と採否:

| 論点 | 助言の要旨 | 採否 |
| --- | --- | --- |
| 回転の手順 | 旧Storeを`Recover`でsettle → 新dir作成 → dir fsync → 切替。冪等。時計逆行に備えて`max(既存の最後, 今日)`、`-NN`は固定幅2桁で99超過はfail closed | 採用（5.3、4.2） |
| seg0の凍結 | chmod前にsettle済みを確認。rootでは0444が効かないので、索引ヘッダのsize照合を必須にする | 採用（10.3、INV-7） |
