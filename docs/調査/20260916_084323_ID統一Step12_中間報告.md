## Failure / Problem / Cause / Lesson / Invariant / Enforcement / Tests

- Failure: 配備後の CORE `:18790` が長時間 listen せず、TTS Gateway `:7870` も落ちたまま。Step 12 TTS receipt E2E を閉じられない。
- Problem: source 側の RequestID echo 契約は直したが、実 Actor 経路の TTS 合成と CORE 再起動後利用が同時に欠けている。
- Cause:
  1. `recoverActionRunsAfterRestart` が Action 835件それぞれで Task `GetRun` を呼び、毎回 `task_run.jsonl`（9371行）と `task_state.jsonl`（23512行）を全件 load / owner 検証する。PID 670985 では `llm_gateway` から次の起動ログまで約16分かかった。
  2. `rencrow-resilience.timer`（2分間隔、`AUTO_REPAIR=true` / `CODE2`）が `:18790` 未 listen を修復とみなし、約6分10秒ごとに `systemctl stop` 相当で CORE を巻き戻していた。復旧ループを止めるため timer は inactive にした。
  3. TTS Gateway 新binary（`70c1220`）は Irodori `:7880` warmup を fail-closed にする。Gemma4 復旧後は Irodori Disabled のため `:7870` は Connection refused。
  4. 承認済み GPU 一時切替は Gemma4 側へ戻済み。IdleChat TTS は Gemma 停止中に到達できず、Gateway echo 修正後も実合成経路が無い。
- Lesson: Step 12 の TTS Gate は Gateway echo 契約・Irodori 稼働・CORE listen の三点同時が必要。resilience は listen 前の長い `buildDependencies` と排他になる。
- Invariant: RequestID は CORE が mint する。provider `tts_*` は echo 失敗時に RequestID へ昇格させず ExternalRef / `target_request_id` に隔離する。
- Enforcement: CORE `postSynthesisWithRetry` の identity mismatch。TTS Gateway `projectCallerRequestID`。resilience は liveness 前提なので、起動完了前に自動再起動してはならない。
- Tests: CORE TTS retry package test と TTS `TestSynthesisEchoesCallerRequestIDAndPreservesTargetRequestID` は通過。実 TTS receipt E2E と Golden / Restart の TTS 分は未取得。
