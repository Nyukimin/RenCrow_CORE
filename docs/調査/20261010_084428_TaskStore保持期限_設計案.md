## 1. 問題と目的

### 1.1 問題

1. **tx時間が履歴量に比例する [事実]**。`loadTransactionTaskRunBase`（`internal/infrastructure/persistence/task/transaction_snapshot.go:84`）は`task_state.jsonl`と`task_run.jsonl`を毎回全件読み、1行ずつJSON decodeする。書込みtxは、さらに追記前に対象file全体のSHA-256を2回計算する（2.2）。
2. **保持期限も圧縮もない [事実]**。72,060 Task、state 170,130行、run 102,552行。Memory Promotionは1日2,830〜3,826 Task（10/3〜10/8）。state+runは1日5.1〜7.0MB増える。
3. **本番ホストの実測**: 1 txが約11秒、Heartbeatの終端書込みが約39秒、2026-10-09のE2Eではchat 1件132秒のうち約94秒がLLM呼出し前のCORE内待ち（いずれも調査記録の値）。
4. **lockはほぼ飽和している [事実+推定]**。task_stateへの追記は1 write txにつきほぼ1行で、10/2〜10/8は11,092 / 12,114 / 9,991 / 10,550 / 10,130 / 9,308 / 8,879行/日。1 tx 約7〜11秒なら容量は約7.9k〜12.3k tx/日で、観測された追記件数とほぼ同じである。lockは10ms間隔のtry-lock（`internal/infrastructure/persistence/jsonlbatch/lock.go:60`）で公平性がなく、Readも同じ排他lockを取る（`jsonlbatch.go:232`）。
5. 緩和策（終端書込み予算60秒、有界backoff、commit `ca1d7685`）は延命であり、tx時間そのものは変わらない。

### 1.2 目的と非目的

- 目的: hotの規模を保持規則で**有界**にし、tx時間を履歴量から切り離す。退避は**削除ではなくcold退避**とし、退避済みTaskをIDで取得できる状態を保つ。
- 非目的（本提案に含めない）: (c) Memory Promotionの扱い、(d) 索引化・常駐、滞留queued Taskの終端化、coldの削除・圧縮、Action store等ほかのstoreの肥大、`task_operation_receipts.jsonl`／`task_execution_fences.jsonl`の肥大（現状はコピー上0 byte、remote profileで増える可能性があり関連リスクとして12章に記す）。

### 2.2 txの経路とコストの内訳

1. `transactionWithScope`（`transaction.go:93`）/ `ReadTransaction`（`transaction.go:122`）が`jsonlbatch.Store.Write / Read`でflockを取る（Readも排他）。
2. callbackが最初にTask/Runを読む時、`loadTransactionTaskRunBase`がstate・runを全件decodeし、`foldTaskRecords`/`foldRunRecords`で最新版へ畳む。tx内では同じbaseを使い回す。
3. commit前に`validateTaskTransaction`（`transaction.go:189`）がpending追記を重ねたviewで`validateRunOwners`（全RunのTaskがhotに在ること）を再検査する。
4. `jsonlbatch.preparePayloads`（`jsonlbatch.go:452`）が**対象file全体のSHA-256**を計算し、`appendPrepared`（`jsonlbatch.go:492`）が追記前にもう一度計算する。書込みtxでstateとrunに追記すると、95MBを2回ハッシュする。

実測（Mac、本番コピー全量、中央値、秒）:

| 操作 | Create | StartRun | Succeed | Get（read tx） | List(running) |
| --- | --- | --- | --- | --- | --- |
| 現状（95.2MB） | 2.39 | 2.81 | 2.81 | 1.91 | 1.93 |

内訳 [事実]: decode + fold（state+run）は1.59秒で、Getの83%、Createの66%を占める。SHA-256は1 passあたりstate 0.047秒 + run 0.021秒（Macはハードウェア命令）。旧世代CPUの本番では1 txあたり約1秒に達する可能性がある **[推定]**。open時の全run foldは0.42秒。

### 2.3 状態の畳み込み [事実]

- Task: TaskIDごとに**最後の行が有効**。`foldTaskRecords`が`UpdatedAt`降順（同値はTaskID）に整列する。`ListTasks`はfilterの後に`Limit`を切り、offset/pagingはない。
- Run: `foldRunRecords`が行ごとに`validateRunUpdate`（identity・開始field不変、`CanRunTransition`）を検証する。同一Taskにactive Runは1つ。
- 終端Task: `CanTransition(from, to)`は終端からの遷移を禁じるが**同一状態への再書込みは許す**（Heartbeat終端再試行の冪等性の基礎）。`explicit_rerun`だけが終端Taskを`running`へ戻す（`manager.go:378`の`reopenTerminalTask`）。
- Taskは物理的に重複登録を拒否しない。`Create`はexistence checkをせず`SaveTask`が追記するだけで、同一TaskIDの再作成は既存を上書きする（`manager.go:106`）。

### 2.4 lockとwriter generation [事実]

- `.writer.lock`: writerプロセス寿命のOS advisory lock。open時にcounterへ追記して世代を進める。
- `.jsonlbatch.lock`: 操作単位のflock（Linux/macOS `flock`、Windows `LockFileEx`）。WALをsettleしてから実行する。
- open時の整合検査（`jsonl_store.go:123-136`）: 保存済み**全Run**の`WriterGeneration`が新世代より小さいことを要求する。counterが欠落・切詰めされても世代の再利用を防ぐ最後の砦である。**coldに退避したRunもこの検査から外れてはならない**（6.2、Invariant INV-6）。
- remote profileでは同じ`JSONLStore`を保存host側processが開き、CORE側は`task` groupのtx sessionで操作する（`docs/04_アーキテクチャ概要.md`「Task/Run transactionとfenceのremote意味」）。

## 4. 選択肢の比較と推奨

### 4.1 評価軸

1. 効果: 1 tx時間の短縮と、**時間とともに再悪化しない（有界性）**こと。
2. 契約への影響: `domaintask.Store`、Public API、remote RPC、利用者の修正量。
3. 障害時の挙動: クラッシュ、部分書込み、破損、容量不足。
4. 三OSの可搬性: Linux / Windows / macOSで同じ契約（`AGENTS.md`「共通の検証・可搬性」）。
5. 規約: 外部DB・Python・Docker・WSLを標準起動条件に加えない（`AGENTS.md`「製品の共通境界」）。

### 4.2 案

**案A: hot/cold分割（推奨）**。期限を過ぎた終端Taskの全レコード（state / run / context / notifications）を、**逐語の行のまま**不変segmentへ移し、hotを書き直す。IDによる取得はcoldへread-throughする。

**案B: snapshotと末尾読み**。全Taskの畳み込み済み最新状態を`task_snapshot`に持ち、txはsnapshot + 前回offset以降の末尾だけを読む。

**案C: writer process内の常駐状態**（(d)に近い）。畳み込み済みのTask/Runをプロセス内に保持し、commit時に更新する。txはdecodeしない。

**案D: 最新版への畳み込みだけ**。全Taskを残し、各Task/Runを最新1行へ圧縮する（Bのsnapshotの下限でもある）。

**案A′: coldをSQLiteにする**。cold segmentの代わりに埋込みSQLite（`modernc.org/sqlite`は既にCOREの依存）へTaskを入れる。ID引きとatomic commitは容易だが、(i) hotはJSONL + WAL + flock、coldはSQLiteと、1つのowner storeに別の耐久性モデルが混在する、(ii) 逐語行の保持と「cold segmentを順に連結すれば旧形式へ戻る」というrollback容易性を失う、(iii) 旧世代CPUでの純Go SQLiteの性能が未確認。案Aのindex実装が過大と分かった場合の代替として保持するが、第一候補にはしない。

**除外する案（規約による）**: PostgreSQL・Redis・Elasticsearch等の外部DB／queue／検索基盤、Python／Node.js製の集計・索引、Dockerやsidecar前提のstore、WSL前提の保管。`AGENTS.md`が標準runtimeをnative Go binaryとし、Python・Node・Docker・WSL・外部DB／queue／vector storeを標準起動条件に追加しないと定めているため採れない。Parquet cold export（`storage.memory.cold_export_dir`）の契約は「派生物・再生成可能」（`docs/05_設定リファレンス.md`保存状態coverage）で、Task coldは**正本の履歴**そのものなので流用しない。

### 4.6 推奨と根拠

**案Aを推奨する。**

1. 有界性を持つ唯一の案である。B・C・Dはいずれも件数に比例してtx時間が戻り、Cはメモリも増える。時間と履歴量の切り離しという目的を満たすのは、履歴の一部をhotから外すAだけである。
2. 実測で目標を満たす。本番コピー由来の合成hotで、tx中央値が約1/3（Succeed 2.81 → 0.96秒）。hotの床（非終端のみ）まで下げても0.38秒で、これ以上はAでは動かない。
3. 既存の追記・WAL・flockの仕組みを変えずに載せられる。coldは不変のsegmentで、hotは今のfile名・今の書式のまま小さくなる。`domaintask.Store`のinterface（remote RPC payloadを含む）は変えない（一覧のfilter型も変更しない）。
4. 逐語行で保存するので、(i)完全性が行のSHA-256で機械検証でき、(ii)旧書式への復元（`restore-all`）がsegmentの連結で済み、(iii)Task schemaが変わっても再エンコードによる欠落がない。
5. 外部DB・Python・Docker・WSLを要さない。三OSのGo標準APIだけで書ける。

Aの弱点と、その扱い:

- 契約が1つ変わる（hot missはNotFoundではない）。これは3.2の利用者表で網羅し、F-1〜F-6を前提条件にする。
- 非終端Taskには効かない。滞留queued（18,248件）が「床」として残るので、5.4で別提案にする。
- cold lookupのindexを自前実装する。過大なら案A′（coldをSQLite）へ切り替える余地を残す。
- 案Cは「Aと排他ではない」。A後の残余（decode約0.5秒、SHA 28MB × 2 pass）が旧世代CPUで問題なら、常駐indexを後段候補として起案する。

## 5. 保持の規則

### 5.1 原則

1. **終端Taskだけ**を対象にする。`queued / running / waiting / blocked`は退避しない。
2. 長い側を既定にする。新しい種別や未知の種別は既定（長い側）に落ち、誤分類しても「退避が遅れる」だけで壊れない。
3. 種別は**Taskの属性（route・assignee）**で判定し、titleには依存しない。titleは表示文字列で、正本の属性ではない。
4. 日数は設定値（ユーザー判断）。下限とクラスの判定ロジックはコード（INV-8）。

### 5.2 値

| クラス | 判定 | 退避までの日数（終端時刻`FinishedAt`から。無ければ`UpdatedAt`） | 根拠 |
| --- | --- | --- | --- |
| 周期処理（Memory Promotion） | `route=RESEARCH` かつ `assignee=midori` | **3日** | 流入のbyteで約96%（1日5.0〜6.7MB）を占め、hotサイズをほぼこの日数が決める（hot ≒ 床 + 日数 × 約5.5MB）。3日は再試行窓24時間の3倍で、下限2日に対し1日分の余裕を持つ。Memory PromotionのTaskIDはprofile promotion jobに属性として保存されるだけで、Task実体を引く経路は確認できていない（形式検査のみ） |
| 既定（利用者のTask、OPS、IdleChat、移行履歴ほか） | 上記以外 | **30日** | 流入が1日0.14〜0.37MBと小さく、30日保持の追加負担は一律3日比で+5.8MB（本番換算で約+0.9秒）。障害解析で一覧から到達できる期間を残す。IdleChatと移行履歴の大半（14日〜90日超）は初回の退避で対象になる |
| 下限 | 全クラス | **2日**（設定検証で拒否） | Heartbeat終端書込みの再試行窓24時間（`docs/02_機能仕様.md`のFailure Knowledge、Invariant 4）が冪等な再書込みを行うため、窓の2倍を最低にする |

候補値の感度は4.3の表を参照（3日/30日: 28.0MB・本番換算4.4秒、3日/14日: 24.1MB・3.9秒、2日/14日: 18.6MB・3.2秒）。**推奨は3日/30日**。ACを満たしつつ、種別の誤判定リスクが最小で、利用者向けの保持が長いため。

### 5.3 退避しない例外

| ID | 条件 | 理由 | 判定 |
| --- | --- | --- | --- |
| E1 | 非終端（`failed / succeeded / cancelled / superseded`以外） | 実行・再開の対象 | 最新版の`Status` |
| E2 | Runに`running`が1つでもある | 孤児回収・admission・枠判定がhotに依存する。open Actionを持つRunは`running`なのでこれで足りる | foldしたRun |
| E3 | 親・依存先・supersede元として**非終端Taskから参照されている**（active な子を持つ親） | 子の`Create` / `Start`のたびに親・依存先を引くため、hotに置く。参照元が全て終端・退避済みになってから退避する | foldしたTask群の逆引き（閉包を固定点まで反復） |
| E4 | execution fenceが`active`または`uncertain` | fenceはTask単位で排他を取る（`task_owner_durability.go`） | fence snapshot |
| E5 | 経過日数が未満 | 保持 | 時刻 |
| E6 | 時計異常: 現在時刻がstore内の最大`UpdatedAt`より1時間以上過去 | 時計が巻戻った状態で閾値判定しない（逆方向の大幅進みは1パスの件数上限が被害を限定する） | パス開始時の検査 |

退避済みTaskが`explicit_rerun`でreopenされる場合、v1は`ErrTaskArchived`で拒否する（12章 D4）。再開時に`FinishedAt`が`nil`になり非終端となるため、reopenされたTaskはhotに残る。

### 5.4 滞留した非終端Task（本提案の範囲外）

queued 18,248件はRunを1つも持たず、終端しないので退避できない。これがhotの床6.9MB（Task 18,656件）を作る。内訳は、IdleChat 11,997件、Background job failure 2,024件、Memory Promotion 2,022件、atlas_acquire 1,927件ほか。

- 床は**単調に増える**。atlas_acquireのqueuedだけで約280件/日（概算で約0.2MB/日）が積まれており、AC-1の余裕7MB（35MB − 28MB）は約5週間で使い切る **[推定。leak修正後の増加率は未計測]**。
- 終端化（期限切れのcancel等）は状態を変えるpolicy判断で、IdleChat・Atlas・background jobの各owner判断になるため、**本提案には含めない**。別のS1提案（「Runを持たないqueued Taskの期限切れ終端化」）を**期限付きで**起案する。保持期限（本提案）と併せて初めて床も有界になる。

### 5.5 coldの保持

- 当面は**無期限**。削除・圧縮は別のS1判断（`docs/07_安全・自動実行・データ方針.md`のtombstone規則に準ずる別提案）。
- 増加見込みは約7MB/日（state + run 5.5MB、context 0.5MB、notifications 0.8MB。無圧縮）で、約2.5GB/年 **[推定]**。`workspace_dir`を置くdiskの空き容量は[未確認]。

### 5.6 利用者から見える変化

- 一覧（`/viewer/tasks`、`rencrow tasks list`）と通知はhotだけを返す。保持期間（Memory Promotion 3日 / 他 30日）より古いTaskは一覧に出ず、`task/detail?task_id=` と `rencrow tasks show <id>` で取得する。
- 現状の一覧は最新順・既定limit 200・pagingなしで、実質は最新数時間分しか見えていない。到達できる範囲が狭まる影響は限定的である。

## 6. 退避処理の設計

### 6.1 データ配置

hotは現在のfile名・書式のまま小さくする。coldは同じ`<workspace>/tasks/`の下に置く（同一filesystemなのでrenameが原子的であり、Configの物理pathを増やさない）。

```text
<workspace>/tasks/
  task_state.jsonl  task_run.jsonl  task_context.jsonl  task_notifications.jsonl   (hot。現状どおり)
  cold/
    archive.log            追記専用JSONL。intent / done / restore の記録。segmentの有効性の正本
    seg-000001/            不変。archive.logにintentとdoneがあるものだけが有効
      task_state.jsonl     退避したTaskの全state行（逐語。Taskごとに連続し、元の順序）
      task_run.jsonl       同 run
      task_context.jsonl   同 context
      task_notifications.jsonl 同 notifications
      index.task           TaskID昇順の固定幅binary（task uuid + 4 fileのoffset/length）
      index.run            RunID昇順の固定幅binary（run uuid → task uuid）
      segment.json         schema_version、Task/Run件数、各fileのbyte数とSHA-256、
                           min/max TaskID、max_created_at、max_writer_generation、archived_at、bloom(TaskID, RunID)
```

- **逐語行**: 元の行のbyte列をそのまま移す（再エンコードしない）。完全性を行のSHA-256で検証でき、将来のTask schema変更で欠落せず、`restore-all`が連結で済む。
- indexは固定幅・ビッグエンディアン・O(log n)の`ReadAt`で引ける形にする（全segmentをメモリへ常駐させない。実装時にbyte配置を確定する）。bloomは`segment.json`に持ち、openで読む（1segmentあたり数KB）。
- 同じIDが複数segmentにある場合（restore後の再退避）は**最新seqを正**とする。
- 共有する純関数（行の読取・`foldTaskRecords`・`foldRunRecords`・検証）は既存のものを再利用し、cold専用の第二の畳み込み実装を作らない（Semantic Duplicationの回避）。

### 6.2 契約

| 操作 | 挙動 |
| --- | --- |
| `GetTask(id)` | hotに在れば返す。hot missならcoldを引く。見つかれば現行schemaでdecode・検証して返す。cold側が「存在しない」と確定した時だけ`ErrNotFound` |
| `GetRun(runID)` | hot → miss時は`index.run`でTaskIDへ逆引き |
| `ListRuns(TaskID)` | そのTaskがhotに在ればhotのRun、無くcoldに在ればcoldのRun |
| `GetContext(id)` | `GetTask`と同じ規則 |
| `ListTasks` / `ListNotifications` / `ListRuns(全件・状態指定)` | **hotのみ**。filter型（remote RPC payload）は変更しない |
| `SaveTask / SaveRun / SaveContext / SaveNotification` | IDがhotのTask集合に無く、cold側に在る場合は`ErrTaskArchived`（`ErrNotFound`の別名にしない）。hotに在るTaskは通常どおり |
| coldの読出しエラー（segment欠損・サイズ不一致・decode失敗） | `ErrNotFound`にしない。そのIDについてfail closed（`ErrColdUnavailable`相当）し、healthを異常にする |

- **cold存在確認の費用**: 新規IDは`NewTaskID()`のUUIDv7で、埋め込み時刻が「退避済みTaskの最大`created_at` + 1時間」より新しければcoldを引かない（O(1)）。時刻差は実測でp99 10.4秒、最大552秒なので1時間の余裕で足りる。UUIDv5（移行由来）や古いIDだけsegmentごとのbloom → index検索を行う。結果は1 tx内でメモ化する。
- **整合**: coldの一覧（segment集合）は、各tx開始時にflockの下で`archive.log`の末尾を確認して同期する。別processのreader（CLI）も同じ規則でcoldを読み、読取専用handleでも動く。
- **writer generation（INV-6）**: open時の整合検査（`jsonl_store.go:123-136`）は`max(hot全Runの世代, 全segmentの max_writer_generation) < 新世代`とする。counterの欠落・切詰めでも、coldに退避したRunの世代を再利用しない。
- **remote profile**: read-throughと`ErrTaskArchived`は保存host側processで実装され、`archived`のwire codeで返す（F-5）。`domaintask.Store`のinterfaceとRPC payloadは変更しない。

### 6.3 退避パス（writer lockの下）

`JSONLStore`の1メソッド（`ArchiveOnce`）として実装する。writerとして開かれたstore（`.writer.lock`を保持）だけが実行でき、`jsonlbatch`に追加する**公開API 1つ**（`Store.Exclusive(ctx, fn)`：flockを取り、`recoverLocked`でWALをsettleし、fnを実行する。既存API・WAL書式・journal versionは不変）の中で動く。

| 手順 | 内容 | 失敗時 |
| --- | --- | --- |
| P0 | 前提検査: 未完のintentが無い、`cold/`が書込み可能、空き容量が必要量（旧hot + 新hot + cold予定 + 余裕）以上、時計検査（E6）。**WALを長さ0へcheckpoint**する（settle済みなので無害。旧offset・prefix SHAを含む履歴を残さない） | `blocked(reason)`で何も変えずに終了 |
| P1 | 計画: 4 fileを逐語行のまま1回走査し、slim decode（task_id、status、finished_at/updated_at、route、assignee、parent/dependency/supersedes、Runのstatus/id）で最新版を畳み、E1〜E6と保持クラスを評価して退避集合を確定する（上限と時間予算を適用）。空なら終了 | 予算超過なら何も書かずに終了 |
| P2 | cold segmentを`cold/.tmp-<seq>/`へ書く。各fileをfsync、dirをfsync、読み戻して件数とSHA-256を検証、`seg-<seq>/`へrename、親dirをfsync | 例外時は`.tmp`を残して中断（hot不変） |
| P3 | **新hotを全て書く**: 退避集合の行を除いた4 fileを`<name>.archive.new`として書き、fsyncする（mode・所有は元file同じ） | 中断（hot不変。coldは孤児） |
| P4 | **commit点**: `archive.log`に`intent{seq, segment, 件数, 新hot 4 fileのSHA-256とsize}`を追記してfsync | torn tailは切詰め、intentは無効 |
| P5 | `.archive.new`を`task_context → task_notifications → task_run → task_state`の順にrename（置換）。dirをfsync（Windowsはno-op） | 失敗時は有界リトライ（Windowsのrename置換は他handleに弱い）。残れば次回openのroll-forwardで完了 |
| P6 | `archive.log`に`done{seq}`を追記してfsync。件数・byte・所要・新hotサイズをlogへ | doneが無ければ次回openで補完 |

**順序の理由**:

- P4（intent）の時点で、roll-forwardに必要な全byte（cold segmentと新hot 4 file）がdisk上に揃っている。intent後にENOSPCで新hotが作れず前にも後ろにも進めない状態を作らない。
- P5の途中状態でも読める。context・notificationsはTask整合検査の対象外であり、runを先に消すと退避対象のTaskは「Runなしでstateに残る」だけである（`validateRunOwners`は「Runに対するTaskの存在」だけを要求する）。最後にstateを置換して消す。
- jsonlbatchを通る正規の読取はflockで中間状態を見ない。この順序は、jsonlbatchを通らない読取（rsync等のbackup、`tail`）への保険である。代替としてhot側を世代別ディレクトリ＋pointer fileの1回のrenameにする案があるが、既存のfile名（`jsonlbatch`の固定file名、CLI、runbook、cutover手順が前提とする）を変えるため採らない。

**2つのlockの区別**: `.writer.lock`（プロセス寿命・generation）と`.jsonlbatch.lock`（操作単位のflock）は別物である。退避は両方を保持する前提で、writerでないhandle（`NewJSONLReader`）からは実行できない。

### 6.4 障害時の挙動と回復

| 停止・失敗の地点 | hotの状態 | 再起動後の回復 |
| --- | --- | --- |
| P0〜P3 | 不変 | `archive.log`に無い`cold/.tmp-*`・`seg-*`は無効。open時に自分の失敗物として整理する |
| P4のtorn tail | 不変 | `archive.log`末尾の不完全行を切詰める（WALと同じ規則）。segmentは孤児 |
| P4後〜P5途中 | 一部のfileが新hot | **writer openで、`jsonlbatch.Recover`と世代検査（`loadRuns`）の前に**roll-forward。各fileを、現fileのSHA-256が新hotに一致なら済、`.archive.new`が新hotのSHA-256に一致ならrename、どちらでもなければ**破損としてfail closed**（自動修復しない）。完了後に`done`を追記 |
| P5後〜P6前 | 全て新hot | `done`を補完 |
| 読取専用handle（CLI等）が未完intentを見る | — | `ErrRecoveryRequired`でfail closed（jsonlbatchのWAL規則と同じ）。修復はしない |
| ENOSPC・fsync失敗 | P3までは不変 | 中断して次回再試行（backoff）。P4後はroll-forward可能（必要byteは既に書いてある） |
| segmentの欠損・サイズ不一致 | — | open時にstat検査。該当segmentのIDは`ErrColdUnavailable`、healthを異常にし、他のIDは動作継続 |
| intentと実fileが不整合（手編集など） | — | fail closed |

- **冪等性**: パスは何度実行しても収束し、退避集合が空ならno-op。roll-forwardもSHA-256で判定するので冪等。
- **CLIとの競合**: 稼働中のwriterがwriter lockを保持するため、変更系CLIは従来どおり`ErrTaskWriterBusy`で拒否される（既存仕様）。`archive run / restore-all`は**サービス停止中のオフライン操作**に限る。

### 6.5 実行契機と上限

| 契機 | 条件 | 上限 |
| --- | --- | --- |
| 起動時（初回移行を兼ねる） | writer open直後、listener開始の**前**に1回 | 件数は無制限、時間予算300秒。予算超過（P4前）は中断してそのまま起動する（退避の失敗でサービスを止めない）。P4後はroll-forwardを必ず完了 |
| 定期 | 既定24時間ごと（Config）。最終成功から間隔以上経過した時 | 1パス20,000 Task以下、lock保持の時間予算15秒（P0〜P4）。1日の流入は約3,500 Taskなので定常は1パス数秒 |
| 手動 | `rencrow tasks archive run`（オフラインwriter） | rehearsal・保守用。同じ`ArchiveOnce` |

- 結果は`completed | skipped(reason) | blocked(reason) | failed`で確定し、人の返答を待つ状態を作らない（No-Human-Gate）。
- 24時間間隔にする理由: 6時間ごとだとsegmentが年1,460個に増え、openで読む`segment.json`・bloomが過大になる。24時間なら年約365個。segmentが1,000個を超えたら統合パスを別提案する。

### 7.4 Failure Knowledge（実装時に`docs/調査/`へ記録）

- **Failure**: 履歴量に比例するtx時間でグローバルlockが飽和し、終端書込みの期限切れ・枠占有・chatのCORE内待ちが発生した。
- **Problem**: task storeに保持の概念がなく、全Taskを毎txで走査する。緩和（予算・backoff）は延命にしかならなかった。
- **Cause**: 追記専用JSONLの設計が「全履歴＝作業集合」を前提にし、終端Taskを作業集合から外す境界がなかった。高頻度の周期処理（Memory Promotion）をcanonicalなTaskにしたため流入が支配的になった。
- **Lesson**: 作業集合（hot）と履歴（cold）を境界で分け、hotの規模を保持規則で有界にする。履歴は削除せず逐語で保存し、IDでの解決を契約にする。
- **Invariant / Enforcement / Tests**:

| ID | Invariant | Enforcement | Tests |
| --- | --- | --- | --- |
| INV-1 | hotの規模は保持規則で有界（終端Taskは保持日数後にhotから外れる） | 退避パス + health check（hotサイズ閾値） | R-1の規模・時間比、benchmark |
| INV-2 | hot missは`NotFound`ではない。全Task列挙を前提にした結合を新設しない | storeのread-through。列挙API呼出し元のallowlist architecture test（F-6） | R-2 / R-4 / R-5、architecture test |
| INV-3 | archiveは逐語・不変・追記のみ。hot ∪ cold = 元データ | segmentの不変化、`verify`（行のSHA-256多重集合） | AC-6、`restore-all`往復 |
| INV-4 | 退避のどの中間状態も読め、再起動でroll-forwardにより収束する。破損は修復せずfail closed | intent + SHA判定、reader側のfail closed | 障害注入（10.2） |
| INV-5 | coldに在るIDへhotから書かない（影子レコードを作らない） | `ErrTaskArchived`、型付きerror | R-3 |

### 10.2 障害注入

- **強制終了点**（子processへSIGKILL。WindowsはTerminateProcess）: P2の各file書込み後・rename前後、P3の各`.archive.new`のfsync後、P4のintent追記の前後、P5の各rename（context / notifications / run / state）の前後、P6のdone前後、WAL checkpointの前後。各点で再openし、(a)全Taskがhot ∪ coldで読める、(b)全行のSHA-256多重集合が不変、(c)次のパスで収束、(d)世代検査が成功、を検査する。
- 資源障害: ENOSPC（小容量のfilesystemまたはfile size制限のseam）、fsync失敗（既存の`syncFn`と同種のseam）、torn `archive.log`、segmentの切詰め・欠損・bit flip、intentと実fileの不整合。
- 並行: CLI readerとwriterとtxの同時実行（`-race`）、未完intent中のreaderのfail closed。

### 10.3 性能

- 4.3の合成hot計測を`Benchmark`として恒久化する（AC-2）。本番データそのものはrepositoryに入れず、状態比・版数・行byte数が本番の分布に一致する合成生成器を使う。
- 絶対秒はhostで揺れるため、CIの判定は「現状構成に対する比」（hot 28MBでSucceedが現状構成の40%以下）とし、絶対値は観測目標とする。
- 退避パスの所要（AC-10）とcold 1件の読出しp95（AC-5）。
- 本番: IU-1のbaseline比（AC-3 / AC-4）。

### 10.4 三OS

Linux amd64 / Windows amd64 / macOS arm64のCIで、unit・障害注入・`-race`（Linuxのみ）を実行する。Windows固有: (1)開いているfileを置換するrename、(2)dir fsyncがno-opで、`jsonlbatch/directory_sync_windows.go`が記すとおり電源断時の挙動は未検証であること、(3)改行変換が起きないこと（逐語行はLF固定、binary open）、(4)path区切りとUTF-8 path。大文字小文字を区別しないFSを想定し、segment名は小文字の英数字とハイフンだけにする。耐久性の保証水準は既存の`jsonlbatch`（`File.Sync`）と同じで、本設計は強化も弱体化もしない。
