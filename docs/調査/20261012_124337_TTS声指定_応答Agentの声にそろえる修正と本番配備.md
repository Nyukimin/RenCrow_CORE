# TTS声指定: 読み上げの声を応答Agentの声にそろえる修正と本番配備

## 概要

TTSの読み上げが、実際に応答したAgentの声にならない経路があった。話者を「route名から推測する処理」と
「CHATの宛先から決める処理」が別々に存在し、さらに話者を解決できない場合は黙ってMioの声に落ちていた。
読み上げる声を、その発話を生成したAgentの声にそろえ、本番へ配備してE2Eで確認した。

## 発生条件

- WILD（話者名が`wild`でAgentではない）とANALYZEは、Midori／Kuroの発話がMioの声になる。
- OPSはGatewayの旧別名`male_01`を送っていた（仕様上、Gatewayのvoice IDではない）。
- CHATは宛先の声を使うが、emotion用voice profileとVTuberのcharacterはMio固定。
- 朝刊（daily news brief）は宛先（`to`）の声で読むが、実際に応答するのはMio（失敗時のみShiro）。
- session開始に失敗しても、bridgeが既定声（設定値のMio）で未開始のsessionを黙って作る経路が残っていた。
- 合成要求のログ`[TTS] synthesis request start`にvoiceが無く、どの声で要求したか監査できなかった。

## 事実

- 修正前のCHAT直接宛先（mio／shiro／midori／kuro）のsession voiceは、コード上は宛先のIDになっていた
  （`tts_chat_recipient_lifecycle_test.go`）。routeごとの食い違いは上記のWILD／ANALYZE／OPS／朝刊。
- 修正前の本番では、再起動から約10分後に`TTS route update degraded: parallel limit exceeded: global running task limit reached`が出て、
  TTS sessionが開始できなかった（実行枠の不足。TTS Action sessionは新しいTask／Runを作る）。そのため修正前のE2Eの声は採取できていない。
- Gateway側の設定（4 voice）と207のIrodori（4 voice、参照音声）は修正不要。Irodoriは未知のvoiceを404にし、既定へ落とさない。

## 結論と修正

不変条件: 読み上げる声は、その発話を生成したAgentの声である。TTS sessionの`character_id`とGatewayへ送る`voice_id`は
応答Agentの公開voice_id（`mio`／`shiro`／`midori`／`kuro`）そのもの。

- 正本は`modules/tts`の`VoiceForAgent`（Agent -> voice_id／profile）と`RespondingAgentForRoute`
  （CHAT=宛先、PLAN／RESEARCH=Mio、WILD=Midori、ANALYZE=Kuro、OPS／CODE系=Shiro）。旧`SpeakerForRoute`／
  `RouteVoiceForSpeaker`／`ChatVoiceForCharacter`と`male_01`定数は廃止。
- 委譲先の結果をMioが同一本文で中継する後続の`agent.response`は別発話ではない。読み上げは1回で、声は結果を返した委譲先。
  Mioが独自の要約を話す設計にする場合は「1 turn = 1発話」の前提を見直す。
- 解決できない話者は、別Agentの声で読まず、sessionを開始しない（または発話を読まない）。ログは`unresolved speaker`。
- stream forwarder／Push／VTuberは話者を引数で受け取り、routeから再導出しない。
- 朝刊は`agent.response`を返したAgentを記録し（`dailyNewsBriefResponderTap`）、応答者が確定してからsessionを開始する。
- 開始できなかったsessionにはpushしない（`ttsSessionID`を空にする）。
- `[TTS] synthesis request start`に`character`と`voice`を出す。
- IdleChatの`IdleChatVoiceForSpeaker`も、midori／kuroの声を返す。

## Failure Knowledge

- Failure / Problem: 読み上げの声と応答Agentの不一致。解決不能時に黙ってMioの声へ落ちる。
- Cause: 「誰が話すか」を、route名、CHAT宛先、stream hookの引数、VTuberで別々に決めていた（Semantic Duplication）。
  既定へ丸める分岐が正本の外にあった。
- Lesson: 話者の正本は1か所に置き、解決できなければ拒否してログに出す。声を決める値を、イベントの`from`と同じ値から作る。
- Invariant: 上記の不変条件（`docs/02_機能仕様.md`、`docs/06_Public_API仕様.md`）。
- Enforcement / Tests: `modules/tts/agent_voice_test.go`、`internal/application/orchestrator/tts_voice_invariant_test.go`
  （`ProcessMessage`経由でroute別・宛先別に、session voice・emotion profile・最初の`agent.response.from`の一致、朝刊、
  解決不能の拒否）、`rencrow_tts_bridge_test.go`（session voiceが合成要求の`voice_id`とログになる）。
  新しいrouteを追加して表を更新し忘れると、これらのテストが失敗する。

## 本番配備

- 配備前の本番は`main-93a0971f`（別の作業者が配備済み）。これに本修正の`3cc9bf0d`だけを載せたclean cloneからビルドした。
  ビルド元のGoソースは`origin/main`と同一（差分は`docs`と`scripts`のみ。`go:embed`の対象外であることを確認）。
  version文字列は`main-93a0971f+ttsvoice-3cc9bf0d`。
- 旧バイナリは`~/.local/bin/rencrow.bak-20261012-tts-voice`（sha256を確認して退避）。ロールバックは
  この名前を`rencrow`へ戻して`systemctl --user restart rencrow.service`。
- 再起動から`/health` 200まで約4分15秒。

## E2E（`POST /viewer/send`、`audio_output=requested`、SSEを先に購読）

| 宛先 | CORE `[TTS] synthesis request start` | TTS Gateway | 207 Irodoriの参照音声 | WAV |
|---|---|---|---|---|
| midori | `character=midori voice=midori` | `synthesis ok voice=midori` | `midori_reference.wav` | 3.16秒、48kHz |
| shiro | `character=shiro voice=shiro`（2 chunk） | `synthesis ok voice=shiro`（2回） | `shiro_02_seed_..._reference.wav`（2回） | 2.36秒／2.16秒 |
| mio | `character=mio voice=mio` | `synthesis ok voice=mio` | `mio_02_seed_..._reference.wav` | 5.00秒 |
| kuro（Gatewayへ直接） | （CHAT経路は未整備） | `synthesis ok voice=kuro` | `kuro_reference.wav` | 2.44秒 |

- 各宛先で`agent.start`／`agent.thinking`／`agent.response`の`from`も宛先と一致し、`tts.audio_chunk`の`character_id`も一致。
- shiroの最初の1回は`parallel limit exceeded: global running task limit reached`でsession開始に失敗した（実行枠の不足、既知の領域）。
  このとき`unresolved speaker`は出ておらず、session開始前の失敗で、開始失敗後のpushは行われなかった。約7分後の再試行で成功した。

## 未確認・残件

- Kuroの宛先CHAT経路（Codex CLI target、token切れで放置中）。KuroのCHAT経由のTTSは、単体テストと`TestBothLifecycles...`で確認し、
  実経路ではGateway直接合成までを確認した。
- WILD／ANALYZE／OPS／PLAN／RESEARCHの本番E2Eは未実施（単体・結合テストで確認）。
- `emotion_prefix.go`はmio／shiro系だけを分岐し、midori／kuroは既定分岐（声の識別には影響しない韻律の補助）。
- 声のID以外の旧別名の送出経路が残る: `DefaultRenCrowVoiceID = "female_01"`（`tts.voice_id`未設定時の既定）と
  `FallbackVoiceID`（4 Agent以外のvoice IDとprofileからの別名生成）。Agentの応答経路は通らない。
- `/entry`のローカル再生（`tts-synthesize`）は設定の`tts.voice_id`で合成し、応答Agentを使わない。
- `core.yaml`のネストされた`tts.voices`はGoが読まない死んだ設定。
