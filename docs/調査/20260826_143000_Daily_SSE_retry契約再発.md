## 概要

CORE側で`retryable`を保持して有限再試行する修正後も、RuntimeがHTTP 200のSSE内で返す
数値errorはRenCrow LLM Gatewayがそのまま転送していた。この経路には`retryable`がなく、
COREは正しく非retryableとして扱っていた。GatewayがRuntime固有SSE errorをPublic APIの
canonical errorへ正規化する契約を追加した。model固有messageの文字列判定は行わない。

## 仮説と検証

1. **GatewayのSSE proxyがretryabilityを落とす — confirmed**
   - `proxyStream`は通常chunkとRuntime error objectを区別せず転送していた。
   - 実ログではGateway requestが`failed`となり、COREは`gateway stream error 500`を受信したが
     `retrying retryable LLM boundary failure`を記録しなかった。
2. **Runtimeの失敗分類だけが原因 — refuted**
   - RuntimeはSSE errorに数値500とmessageを返しており、失敗種別の証拠は存在した。
   - 欠落したのはGateway Public APIへの正規化だった。
3. **CORE Daily retry実装が再度壊れた — refuted**
   - CORE providerはcanonical SSE errorの`retryable`をtyped errorへ保持するtestが成功し、
     Dailyはretryable errorだけを1回再試行するtestが成功している。

## バイアス・ライフサイクル確認

- 確証バイアス: `peg-native`文字列だけを特例化せず、数値4xx、数値5xx、既存canonical error、
  通常deltaを同じ境界で検証した。
- 頻度制約: 数十件中に散発する一時的500だけが未retryになる観測と一致する。
- ライフサイクル: Runtime SSE error → Gateway正規化 → CORE typed error → Daily有限retry →
  successまたは記事単位failureの終端を追跡した。
- 既存知見: Runtime／Backend差の正規化はRenCrow LLMの所有であり、COREへbackend固有判定を
  追加しない責務境界を維持した。

## 修正契約

- Runtime SSE数値4xx: `INVALID_REQUEST`, `retryable=false`。
- Runtime SSE数値5xx: `NORMALIZATION_ERROR`, `retryable=true`。
- canonical error: code、message、明示`retryable`を維持。
- Gatewayはrequest IDと解決済みexecution contextを付与し、error後の`[DONE]`を1回にする。
- COREは機械可読`retryable`だけを消費し、最大1回だけ再試行する。
