# 手順上の不備

## 1. 小作業の完了と運用上の完了が結び付いていない

正本879–966行は各StepのGate1–7、特に実経路と旧経路削除を必須とする。一方、`docs/調査/20260907_ID統一Step20_全体Cleanup_check_plan.json:9`はbounded ownerだけを対象にし、全体Golden matrixをdeferredとしている。コード側も`modules/core/identity_architecture_test.go:1695`の限定owner一覧である。

## 2. 現行仕様・履歴・残件の読み分けを毎回LLMに負担させている

正本3350行はprogressOpenJobs等を残件とし、3360–3365行は後段で解消したと説明する。実コードは`viewer.js:242`でprogressOpenTasks。後段に解消記録があるため論理的な無説明矛盾ではないが、現在の未完了一覧を得るには履歴を再解釈する必要がある。

履歴は保存し、現行の要求ID→Gate→有効receipt→残件の投影を一つにする。後段追記からの再推測や、resolved項目の再実装を防ぐ。

## 3. 共通owner契約が閉じる前に各consumerへ展開している

Task/Run、Action/Attemptのadmission・終端・耐障害性が継続修正される中で、Tool、DCI、Scheduler、Heartbeat、Voice、Atlasへ展開している。F02–F05のようにconsumerごとに接続の抜けが生じる。

意味の一部だけを直すpacketではなく、同一ownerの「発行→保持→実行→終端→再開」を契約として固定する。各consumerはその契約に従うadapterに限定し、IDの独自発行を機械検査する。

## 4. Golden基準と配備終端が後段に集まりすぎる

Step00 baselineのGolden traceはpartial、Code/DCI/Memory/Scheduler/Voice/IdleChat/Atlasはunverified（`20260829_221132_ID統一Step00_baseline.md:114`）。現sourceテストは成功したが、それは新旧runtimeやデータの一致を証明しない。Push依頼をPushで閉じることは正しいが、Identityプログラムの運用受入を閉じる別工程が必要。

代表となる正規Tool経路を先に一往復閉じ、以降も経路単位で移行・配備・結果・再起動まで証明する。全consumerをsource-onlyで直し終わるまで実経路を待たない。

## 5. Check Planを機械的に一意に追えない記録がある

Step20計画には`s20_backlog_item_id_offline_remapper`が2回あり、pre-liveとpost-deployで意味が違う。現在のrunnerがこの履歴Planを実際に消費するかは未確認であり、検査迂回が起きたとは断定しない。しかし要求とreceiptの一対一対応には不適切である。phaseを含む一意check_idとschema検証に正規化し、既存Tools ownerを使う。

## 対応中に確認した実行枠の残留（R1）

- **Failure:** service起動後も古い3件のrunning Taskがglobal limitを占有し、IdleChat stock refillとSuperAgent recovery jobが開始できない。
- **Problem:** source検査の成功と、生成処理が実行枠を返すことが別々に扱われていた。
- **Cause:** IdleChat producerのRun発行経路に完了owner呼出しがなく、background failure reporterは通知だけの処理でRunを開始していた。加えて古いSuperAgent projection 316件のTaskID欠落がstartup recoveryを拒否させている。
- **Lesson:** 通知・依頼のTask作成と実Actorの実行開始を分ける。producerのsuccess/error/cancelとcheckpoint再開を一つの契約で扱う。
- **Invariant:** 実行前の通知はRunや実Actorによる実行を主張しない。非同期完了は発行時のTask/Run/Actorとcurrent writerを照合し、旧callbackで新Runを閉じない。
- **Enforcement:** Task ownerのCompleteRun transactionと、通知ownerのCreate-only境界で強制する。IdleChat consumer接続とlive recoveryは未受入。
- **Tests:** exact Run completionのstale/foreign拒否、waitingからの新Run再開、通知後のqueued Task・Run zero・並列枠維持を検証対象とする。実serviceの残留3件解消は別の配備後証拠を要する。

保存原子性のcheckpoint `2981ee7` は2026-09-08 03:44 UTCに正規Linux全20検査が成功しPush済み。これは配備・実Actor・再起動の受入を意味しない。検査の固定sourceと結果は台帳から参照する。

## 検査前処理の反復（R0の手順対策）

- **Failure:** canonical Fullの各stepで、検査対象外のcacheを含むruntime directory走査が繰り返される。
- **Problem:** 内容が小さい検査にも共通の準備費用が掛かり、修正・検証の反復を重くしている。
- **Cause:** `Assert-TestRuntimeLayout` は `Get-ChildItem -Recurse` で全fileを列挙してから、Goが無視する `_`／`.` で始まるpath segmentを除外していた。

- **Enforcement:** 既存のlayout検査内だけでdirectory traversalを制限する。plan検証、environment隔離、resource lock、各stepの実行内容は維持する。
- **Tests:** 実関数を使うfilesystem fixtureと列挙呼出しの記録で、通常・入れ子・除外・大小文字・件数上限・symlinkの判定を検証する。実行時間を不安定なtest閾値にはしない。

- **Problem:** stock、Task/Run、checkpointの三つの保存先を単一transactionと見なすことはできない。
- **Cause:** 保存APIが失敗を返さず、checkpoint削除と生成成功だけでproducerを終了していた。
- **Lesson:** 保存、owner完了、checkpoint削除の順を固定し、各失敗境界から再試行する。保存済みResultを再生成しない。
- **Invariant:** stock保存失敗ではメモリ変更も戻す。checkpointが指す同じRunのstockは公開しない。完了済みRunの再確認はownerのread transactionでTask/Run/Actorと最新状態を照合する。
- **Enforcement:** Word stockのerror返却、producerのCompleteRun、VerifyRunCompletion、再生入口のcheckpoint確認で強制する。Run再発行前にはresume_pendingを保存し、ID保存失敗後も正規ownerの履歴で後続Runを照合する。満杯の在庫でもcheckpoint回復を優先する。
- **Tests:** 実TaskManagerとdisk storeによる保存済みResult再開、保存失敗、完了失敗、checkpoint更新・削除失敗、満杯時回復を対象とする。固定sourceの正規Full結果は台帳のidlechat receiptを参照する。

対象はWord（single/double）producerであり、Forecast、Story、Dialogueの全lifecycle、外部効果fence、三OSの電源断耐性、本番移行と実Agentの再起動受入はこのsource変更だけでは完了しない。
