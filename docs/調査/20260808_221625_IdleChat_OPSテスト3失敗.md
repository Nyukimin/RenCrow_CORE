# IdleChat／OPSテスト3失敗の調査

## 概要

2026-08-08、全体テストでIdleChat 2件とOPS 1件が失敗した。3件とも実行機能の欠落ではなく、Prompt Context統一後も旧メッセージ配置を前提にしていたテストの契約ずれだった。

## 症状

- `TestGenerateResponseFirstTurnUsesActualSpeaker` は現在時刻が先頭SystemPrompt末尾にあることを期待した。
- `TestGenerateResponseSelectsMoreFunCandidate` は第一候補のassistantメッセージが末尾から2番目にあることを期待した。
- `TestOPSRoute_WithoutSubagentManager_UsesFallback` は日本語応答ガードが先頭Character SystemPromptへ連結されることを期待した。

いずれも毎回再現し、起動停止、ロック、外部リソースなどのライフサイクル要因は関与しない。

対象3件の修正後にIdleChatパッケージ全体を再実行すると、同じ旧契約を持つ `TestGenerateResponseKeepsOnlyFirstMessageAsSystem` も表面化した。この潜在失敗も同一根因として扱った。

## 仮説と検証

### 仮説1: IdleChatで時刻注入が欠落した

反証された。`internal/application/idlechat/orchestrator_response_llm.go` は全リクエストへ `WithCurrentJSTTimeNow` を適用している。時刻は固定SystemPromptを汚染せず、`variable_runtime_context` として最後のuserメッセージ直前へ挿入される。

### 仮説2: 第二候補から第一候補の文脈が失われた

反証された。実測リクエストには第一候補がassistantメッセージとして残り、その直後に時刻のVariable RuntimeContext、その後に別候補のuser指示が並ぶ。旧テストだけが時刻メッセージを考慮していなかった。

### 仮説3: OPSフォールバックで日本語応答ガードが欠落した

反証された。`internal/domain/agent/shiro.go` は日本語応答ガードを `variable_runtime_context` として組み立てている。Character SystemPromptと可変実行制約を分離する現行契約に対し、統合テストが先頭メッセージだけを検査していた。

## 根本原因

Prompt Context統一により、固定Character Prompt、安定Runtime Context、可変Runtime Context、userメッセージが責務別に分離された。一方、次の古い位置依存アサーションが残存していた。

- 動的時刻を固定SystemPromptの一部として検査する。
- 第一候補を「末尾から2番目」という相対位置だけで検査する。
- 日本語ガードをCharacter Promptの連結文字列として検査する。
- 先頭以外のSystemロールを一律禁止し、型付きVariable RuntimeContextも拒否する。

## 修正方針

- IdleChatの固定SystemPromptに時刻が混入しないことと、型付きVariable RuntimeContextに時刻が存在することを別々に検証する。
- 第二候補では、第一候補assistant、時刻Variable RuntimeContext、別候補user指示の責務順を検証する。
- OPSではCharacter SystemPromptと日本語応答のVariable RuntimeContextを別々に検証する。
- IdleChatの永続文脈は先頭SystemPromptへ集約しつつ、後続Systemロールは型付きVariable RuntimeContextだけを許可する。

本番コードを旧配置へ戻す変更は行わない。これにより固定prefixの安定性と型付きPrompt Context契約を維持する。

## 再発防止

Prompt Contextの内容を検査するときは、単一のSystemPrompt文字列や無型メッセージの相対位置に依存せず、`PromptContextType` と責務を併せて検証する。
