## 概要

Dailyは取得本文が既に日本語でも、全件を翻訳LLMへ送っていた。日本語と明確に判定できる
本文だけを決定的にそのまま採用し、非日本語または曖昧な本文だけをWorkerへ残した。

## 調査経緯

### 仮説1: 長時間占有はWorkerの初回token停止である

- **根拠**: 過去にはfirst token 0の長時間失敗があった。
- **検証結果**: 棄却
- **証拠**: 今回のlive requestはfirst token 242〜1,944msで、生成全体が約40〜112秒だった。
- **反証確認**: Worker全面停止ではなく、通常応答とstage完了が存在した。

### 仮説2: 日本語本文にも翻訳LLMを必ず実行する構造が占有を増やす

- **根拠**: `translateDailySourceBodies`は本文言語を分類せず全入力をproviderへ渡していた。
- **検証結果**: 確認
- **証拠**: 日本語fixtureでもprovider呼び出しが発生するRedを確認し、修正後は0回となった。
- **反証確認**: 英語、短文、英日混在、中国語は決定的bypassせずWorkerへ残る。

### 仮説3: 長いTTS chunkがDaily Workerを占有する

- **根拠**: 同時期にTTS遅延も観測された。
- **検証結果**: 棄却
- **証拠**: Daily翻訳はLLM Workerのrequestであり、TTS targetとは別の所有経路である。

## 根本原因

- **原因**: 「日本語本文は内容を変えず保持する」という決定的工程までLLMへ委譲していた。
- **メカニズム**: 各記事で不要な翻訳requestが1本増え、単一Workerの占有時間とDaily完了時間を増やした。
- **影響範囲**: Daily source briefの翻訳stage。用語抽出、意味補足、summary、見解は意味処理のためLLM残余のまま維持する。

## 修正

1. Unicode letterの60%以上がHan/Hiragana/Katakana、該当文字20以上、仮名5以上の場合だけ日本語と確定する。
2. 確定した日本語本文は`TranslatedBody`へ同一内容で投影する。
3. 残余入力だけを再indexしてWorkerへ送り、結果を元indexと入力順へ戻す。
4. LLM stageは本文を出さず、purpose、input rune数、経過時間、terminal、attempt数を記録する。

## Invariant

- 中国語のHanだけ、短文、英日混在は日本語確定として扱わない。
- prompt、schema、retry、timeout、routingを変更しない。
- 翻訳不要の決定はCLI/Boundary、翻訳・用語抽出・summaryはLLM残余とする。

## Tests

- 日本語本文ではprovider呼び出し0回。
- 英語、曖昧な混在、中国語はproviderを使用。
- bypassとLLM入力が混在してもindexと順序を維持。
- stage receiptにbounded metadataだけを記録。
- package test、race、vet、build、diff checkを実行する。
