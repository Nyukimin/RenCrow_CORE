## 2. 現状の構造 [事実]

- 2 file + `jsonlbatch`（root直下に1組のWAL `.jsonlbatch.wal`・OS lock `.jsonlbatch.lock`）。行はJSONL（`json.Marshal` + `\n`）、Action・Attemptとも**追記のみ**で、同じIDの最後の行が最新（1 Actionは作成と終端の最低2行）。
- 層: `Manager.mu` → `JSONLStore.mu` → OS flock。**readも排他flockを取る**（`jsonlbatch.Read`）。単一プロセス内ではmutexが先に直列化するので、flockのlock_waitは0.1ms（観測値）で、競合はwallに現れる。
- 全txの流れ: `loadActions`+`loadAttempts`（全行decode、1行ごとに`Validate`、不変条件の畳み込み）→ `validateSnapshot`（全件）→ `newTransactionStore`（mapへclone）→ callback → `finalize`でもう一度`validateSnapshot`（全件）→ `jsonlbatch`: prepareで追記先fileの**先頭から全体SHA-256**、`appendPrepared`でもう一度全体SHA-256 → 追記 → fsync → 追記分のhash → WAL commit（fsync）。CreateAction・CompleteAttemptは両fileへ追記するので、毎回 **2 file × 2回 = 約154MB** をhashする。
- 検証の性質: 全件再検証は毎tx、過去行の破損・改竄もfail closedで検出する副作用を持つ（A導入後はここが変わる。5.4）。
- Action storeを開くのは本番では`cmd/rencrow`のmainプロセス1つ。readerプロセス・CLI・Viewerの一覧は無い（repo内grep）。ただしこれは現状の事実であって不変条件ではない（5.4で強制する）。
- 本storeには`SetTxObserver`が配線されていない（task storeだけ配線済み）。本番のtx分布は未観測で、本書の値は複製上の実測。
- `docs/05` の保存状態coverage表にAction storeの行が無い。`config/durable-stores.json`にも未登録 [事実]。

### 4.2 MPの空振り（Cの根拠）[事実+推定]

- `cmd/rencrow/memory_promotion_action_runner.go`の`RunOne`は、**先に**`CreateAndStartRun`（Task+Run）と`CreateAction`を行い、その後で`inner.RunOne`が`ClaimProfilePromotionBatch`を呼ぶ。対象が無ければclaimは`nil`を返し`Processed=false`で終わる。つまり空振りでもTask+Run+Actionが残る。

- 正本の規則: 「Taskは実行するために作る。作成と最初のRun開始は一つのtransactionにして拒否は何も残さない」（`docs/02_機能仕様.md`、Run無しqueued Taskの滞留のFailure Knowledge）。`docs/architecture/identity/IDENTITY_CANONICAL.md`はActionの例に「Memory promotion」を挙げるが、**空の巡回を記録せよとは書いていない**。空振りの行は情報を持たない（MP Actionは名前が全件`memory_promotion`で、終端は`succeeded`が99.9%）。

### 5.2 (A) メモリ上の索引で全件読みをやめる

- **A2（推奨）常駐snapshot**: 起動時に1回、2 fileを読んで検証し、decode済みのAction・Attemptをmapに常駐する。commitが確定したら**書いたbytesから**差分を適用する（task storeの`jsonlbatch`のpost-commitフックを使う）。副次mapに (TaskID,RunID)→Action、ActionID→Attempt、open集合、Native委譲の(Task,Run)→Action、Kind+Name→Actionを持つ。tx内は触ったIDだけ検証する。
- A1 ID+位置のコンパクト索引（task store方式、`pread`+CRC32C、sidecar任意）: 約15〜20MB [推定。試作なし]。Actionのクエリは全部mapで足りる、Task側の鍵構造（Taskが1級、Runが従属）をActionの(Action→Attempt)にそのまま流用できない、index_*の汎用化は2つ目の使い手が実質いない、の3点でA2を選ぶ。
- 効果 [推定]: exec 2.7s → ms、read tx 2.5s → 1ms以下、write txは commit 1.9sだけが残る（4.7s → 約1.95s、−59%）。起動時のAction関連処理は 約10.6s → 約2.3s（open時の構築1回のみ。K2,K3,K5が索引問合せになるため）。MP同居のlock占有 46% → 約26%。
- 変更の大きさ: 新規 約1,000〜1,500行+試験 [推定]（索引エンジン、増分検証、差分適用、フラグ）。`domainaction.Store`は追加のみ（`Filter`に`Kind`/`Name`、`RunID`の存在確認）。K2,K3,K5を問合せへ置換。
- 障害時: ログが唯一の正本で、snapshotは派生物。(1) tx途中で落ちる→`jsonlbatch`が従来どおりWALで回復、起動時にsnapshotをログから再構築。(2) `ErrCommitUncertain`→適用せず、次のtxがlock内で2 fileのサイズと適用済み長を照合して末尾から再生（task storeの`requireAppliedEquals`と同じ）。(3) サイズ不一致（別プロセスの追記など）→fail closed。(4) 適用失敗→fail closedして再構築。
- 移行と戻し: file形式を変えない。フラグ`action_store.index.enabled`（既定false）で1 release併存し、falseで旧全件経路に戻る。

### 5.3 (B) 日次回転（commitのprefix hashの解消）

- **要否の判定 [事実]**: commitの95%以上がprefix hashで、write txの約41%を占め、(A)後に残る唯一の履歴比例コスト。**hashが支配的なので要る**。
- 方式: task storeと同じ。UTC日の`logs/<YYYYMMDD>-<NN>/`にsegmentを作り、現在の2 fileを「seg0」として読取専用に凍結する。書込み先は当日のsegmentだけ（サイズ弁8MiB）。A2は起動時に全segmentを順に読む。
- 効果 [推定]: 当日segmentの累計サイズ分だけをhash。平均は2×(3.9MB÷2)=3.9MB÷81MB/s ≒ **48ms**、最大日（5.3MB）の日末で約130ms、弁（8MiB）で約210ms。(C)後（約0.5MB/日）は約6ms。write tx 4.7s → A+Bで約0.05〜0.13s。
- 変更の大きさ: 約500行+試験（segment選択・切替・封印・`LAYOUT`・size照合・連結ロールバック）。task storeの回転は10/12に配備、10/13 00:00Zの日切替を本番で観測済み（pause 21ms）。
- 障害時: 切替失敗→旧segmentで継続。旧binaryの誤起動→seg0が0444で`jsonlbatch.New`が失敗し、size照合でも拒否。**過去segmentのprefix hashによる改竄検知は、封印後のsize照合に狭まる**（task storeと同じ判断。D8）。
- 移行と戻し: A（段階1）の後に段階2として有効化（task storeのD5と同じ）。戻しは日ごとのlogをseg0へ連結し直す（オフライン）。

### 5.4 (A) の意味変化と守る不変条件

- 全txの全件再検証は、**過去行の破損・不整合の検出**を毎txで行っていた。A後は検証を (1) tx単位の増分不変条件（触ったAction・Attemptの群と、Nativeの(Task,Run)一意）、(2) 起動時の全件構築検証、(3) `verify`コマンド（全件、旧`validateSnapshot`を再利用）に置く。増分検証が旧全件検証と等価であることはoracle試験（ランダムtx列で両方を比べる）で示す。
- K2の「存在しないRun参照はエラー（起動失敗）」: **回復が作用する範囲**（open Actionと、running Runに紐づくAction）は従来どおり検査する。全Actionの参照検査は起動のcritical pathから外し、`verify`とopt-inの起動時オプションにする（起動失敗の原因を全件整合の1件に依存させない）。
- 単一プロセス前提は現状の事実であって不変条件ではない: 各txのlock内で2 fileのサイズをsnapshotの適用済み長と照合し、不一致はfail closedにする（強制）。commit→適用は`Manager.mu`配下の同一臨界区域で順序固定する。
- 旧全件経路は、Hard Invariantの「同じIUで削除」の**例外**としてフラグ下に1 release残し、観測後のIU（IU-7）で削除する。理由はロールバック能の確保。

### 5.5 (C) MPの空振りで実行主体を作らない

- 方式: wrapperが`CreateAndStartRun`の**前に**、read-onlyの「claim可能か」判定を行い、無ければ`Processed=false`を返す（Task・Run・Actionを作らない）。判定述語はclaimの対象より**狭くしない**（偽陰性禁止）: `pending`（`attempt_count<max`）、`retry_wait`で`next_attempt_at<=now`、`running`で`lease_expires_at<=now`（claimが回復して取る対象）、さらに`attempt_count>=max`の`pending/retry_wait`（claimの「使い切り→failed」更新を残すため）。偽陽性は従来どおりTaskを作るだけで無害。判定とclaimの間のTOCTOUはclaim側が権威なので害が無い。判定のエラーは握りつぶさず従来どおり`reporter.Failed`へ。
- **実装での最終形（IU-1、`2306c906`）**: 述語は「`pending`で（`attempt_count>=max` または 対応するevidence行がある）」「`retry_wait`で（`next_attempt_at<=now` または `attempt_count>=max`）」「`running`で`lease_expires_at<=now`」の和集合。claimの4段（lease回復、due解除、上限到達のfailed化、pendingの選択）が読む・書くjobを、狭めない。上の草案との違いは1点: evidenceのeventが無く上限未満の`pending`は、claimが選ばず何も変えないので含めない（含めると、その1行で述語が恒久的に真になり、空振りのTaskが再び作られる）。判定は`readDB`（読み取り専用）で行い、`now`はclaimと同じUTCで束縛する。試験はclaimをoracleにし、「判定が偽なら、claimはbatchも行の変更も出さない」を全場合（NULL・境界・上限・孤児・非UTCのnow）で確かめる。件数のカウンタは`Memory ProfilePromotion run summary window= idle= started= refused= processed= probe_errors=`（10分に1行）。
- 効果 [推定]: Action増加 −約95%（1日約2,700 → 実処理の最大17件+非MP約170〜300件）、store増加 3.9 → 約0.5MB/日以下、MPのlock占有 46% → 0、Tool同居の悪化 20.9s → 11.8s（−44%）。**Task store側の流入も約9割減る**（MPはTask件数の約9割。task store仕様 9.3、決定D11の「MPの軽量化」の一手）。既存の77MBの履歴は残るので、tx時間（4.7s）自体は変わらない。(A)+(B)の前提でもある（A2の常駐メモリの増加を年約1GB → 約0.1GBに抑える）。
- 変更の大きさ: 小（wrapperと`memorypromotion.Store`に問合せ1つ、約100〜200行+試験）。旧経路（常にTask生成）は同じIUで削除する。
- 障害時: 判定が偽陽性→従来どおり。判定がDBエラー→エラー返却（従来のclaimエラーと同じ扱い）。
- 移行と戻し: データ移行なし。戻しはrelease戻し。「MPが走って対象なしだった」事実の観測先がActionから消えるので、ログ（件数のカウンタ）で代替する。MPのTask・Actionを読む表示・liveness・reapの消費者は生成側とreap分類のみで、空振りの記録に依存する使い手はrepo内に無い（grep）[未確認: 本番ホスト上の外部script]。
- 規則との整合: 「Taskは実行するために作る」。既存挙動の変更なので明示承認が要った（6.2のD1。2026-10-13にユーザーが採用を決定）。

### 5.6 (D) task storeのindex・segmentを共通部品にするか

`40-modularization`（根拠1: 今日2+ callers、根拠2: 変更隔離、根拠3: 純粋ロジック）とConceptual Integrity（正本は1つ、Semantic Duplication回避。ただしowner・lifecycle・failure domainが異なる重複は理由と検証を残して許容）に照らす。

| 部分 | task storeでの規模 | 判定 | 理由 |
| --- | --- | --- | --- |
| segment名・UTC日・一覧・連結順（`formatSegmentName`、`segmentDay`、`utcDay`、`listSegmentDirs`、名前のpattern） | 約100行、`domaintask`参照0 | **共通化する** | Task+Actionの2 caller（根拠1）、純粋（根拠3）。同じ規則を2か所に逐語コピーするとSemantic Duplication |

### 7.1 実装での仕様との差（IU-2〜IU-4）

1. **サイズ不一致は末尾再生ではなく全件の読み直し**（5.2の(2)は末尾再生）。ログの先頭が変わった場合を末尾再生では見逃すため。同一processが同じstoreを2回開く構成（lifecycle ownerとTool runtime）は、旗がtrueのときだけ cmd/rencrow で1つに共有して、読み直しが常態化するのを避ける（旗がfalseのときは従来どおり2回開く）。
2. **索引は ActionID→Attempt 一覧、RunID→Action 一覧、open 集合、(Task,Run)→native委譲**。TaskIDだけ、Kind+Name、open以外のStatusは全走査（本番コピーで約8.5ms。playback receiptの`Kind`+`Name`もこれ）。5.2が挙げた Kind+Name→Action の索引は作っていない（playbackは本番で0件、MPが大半で索引の効果が無い）。
3. **読みは OS lock を取らず、2つのログを stat して snapshot が覆う長さと照合する**（5.2は「各txのlock内で照合」）。不一致、commit成否不明のmark、適用未完のmarkのどれかがあれば、OS lock の下で読み直してから答える。WAL が未確定のとき、長さが一致していれば commit 済みの内容を返す（旧経路は `ErrRecoveryRequired`）。**同じ長さのまま過去のbytesが書き換えられた場合は、次の再起動か`verify`まで気付かない**（D8と同型の検知範囲の縮小。5.4に追記する扱い）。
4. **増分検証は tx の finalize で1回だけ**、触った Action とその Attempt の群（および Task Run ごとの native 委譲の一意）に対して行う。群の規則は `validateActionGroup` で、`validateSnapshot` と任意の状態で受理・拒否が一致することを4万状態で示した。旧経路の `loadActions`／`loadAttempts` の畳み込み規則は `fold.go` に純関数として抽出し、旧経路とsnapshotが共有する。
5. **hook の適用は Action→Attempt の順**（jsonlbatch が渡す順はファイル名順で Attempt が先のため）。hook が失敗または panic したときは「適用未完」のmarkが残り、次の操作がログから読み直す。
6. **Filter に `Kind` と `Name`（完全一致）を追加**し、`validateActionFilter` に Kind の検証を足した。旧経路でも有効。`Manager` に `ReadTransaction` を追加した（複数の問合せを1回の読みで行うため）。
7. **`verify` は `VerifyOptions.CheckRuns`** で、全 Action の参照先 Run の有無を呼出し側（cmd/rencrow が Task store を読取専用で開いて答える）に尋ねる。出力は件数のみ（IDはマスク）。
8. **D5**: 起動時の回復（K2）は、まだ open の Action、native 委譲、running な Run の Action にだけ作用する。範囲内の Action の Run が無ければ従来どおり起動を止める。範囲外の全 Action の参照検査は、`action_store.verify_run_references_at_start`（既定false）と `rencrow actions verify --check-runs` に移した。
9. **K2/K3/K5 の置換は旗に関係なく効く**。旗を外す（配備手順のロールバック1段目）と store の読み方は旧経路に戻るが、回復が確かめる範囲は D5 のまま。全体を戻すには binary を戻す（2段目）。旗を外した新 binary の起動時の Action 関連処理は、1回の read tx で済む分、旧 binary より速い（本番コピーで約6〜7秒、旧binaryは約10.6秒）。
10. 既存の `runtime_recovery_bounded_test.go` の2件を、D5 に合わせて更新した（回復が読む Run の数。参照切れの Action は open のものだけが回復を失敗させる）。
11. 障害注入の「prepare後」「追記後commit前」は jsonlbatch の内部の停止点で、process の外から置けないため、WAL の形を手で作って再現した（task store の `craftWAL` と同じ方法）。callback、hook 開始、適用の途中、適用後は子 process を `os.Exit` で止めた。

### 7.3 実装での仕様との差（IU-5）

1. **閉じたsegmentのsize記録は、segmentごとの不変file `SEALED` に持つ**（5.3は「size照合」とだけ書いた。task storeはsidecarに持つが、本storeはD7でsidecarを作らない）。2 logの最終sizeを3行で記録し（`actions-segment/v1`）、tmp＋rename＋dir fsyncで原子的に作る。記録の無い閉じたsegment、sizeの違う閉じたsegment、`LAYOUT`・`SEALED`の未知の版・欠け・切り詰めは、いずれも起動しない（`ErrSealedSegmentChanged` / `ErrUnknownLayout`）。**記録を後から補う（初回に読んだ値を信じる）経路は作っていない**。
2. **回転の順序は「settle → `SEALED`を書く → 次のsegmentを作る → 切替」**（task storeは「settle → 作る → 切替」で、閉じたsegmentの記録は後からsidecarに書く）。`SEALED`が回転のcommit pointで、書いた後に止まった回転は、次のopenが「最新のsegmentが封印済み」を見て続きのsegmentを作って終える。**代償**: `SEALED`を書いた後に次のsegmentを作れなければ、次を作れるまで書込みがエラーになる（task storeは旧segmentで書き続ける）。次のsegmentの作成は同じfilesystemへのdir作成で、これが失敗する条件（空き容量・I/O障害）では追記も失敗するので、可用性の差は実質無いと判断した。`SEALED`を書く前の失敗は従来どおり旧segmentで書き続け、30秒後に再試行する。
3. **回転はwrite txの`s.mu`保持下で判定・実行する**（task storeは`TryLock`＋gate）。Action storeのwriterは`s.mu`で直列で、snapshotの読みは`s.mu`を取らないため、判定と実行の間に別のwriterが入らず、gateは要らない。読みは`segMu`（`stale`判定から答えまで）で包み、回転の切替と排他する。**回転は`segMu`をブロッキングで取る**: 初版の`TryLock`＋250ms待ちは、読みが常に重なる負荷（`TestRotationUnderConcurrentReadersAndWriters`）で一度も取れず回転が起きなかった。待ちは実行中の読みの長さ（通常はマイクロ秒。snapshotを作り直している読みがあればその間）。
4. **別のwriterが既に封印したsegmentには書かない**: 書込みごと（OS lock下）に現segmentの`SEALED`をstatし、あれば`ErrSegmentMissing`で失敗する。回転の最初にも同じ検査をして、他のwriterの封印を上書きしたり、自分だけの次のsegmentを作ったりしない。読みでは見ない（同一process内でR2〜R4の途中を誤検知するため）。5.4の「単一プロセス前提は不変条件ではない」の、回転後の強制である。
5. **閉じたsegmentも2 logとWALを0444にする**（task storeはsegment 0だけ）。`SEALED`を書いた直後に行う。失敗はWARNで、防御はsize記録の照合。
6. **`layout concat`のwriter排他**: Action storeには`.writer.lock`が無い。最新segmentのOS lockを最大5秒で取り（取れなければ`ErrStoreBusy`）、取れている間に全segmentの全fileを0444にしてからコピーを始める。稼働中のCOREが追記しようとしても、WALを開けずに失敗する。連結の前に、閉じたsegmentの`SEALED`と実sizeの照合を行い、違えば何も変えずに止まる。それ以外（再実行で再開、`logs/`と`LAYOUT`を`.rolled-back-<時刻>`へ改名、削除しない）はtask storeと同じ。
7. **閉じたsegmentのWALがpending/tornなら修復せず起動しない**（task storeと同じ判断）。最新のsegmentの回復は従来どおりopen時の`Recover`。
8. **snapshotの作り直し（`ensureSynced`のdirty時など）は全segmentを読み直す**（本番で約2.4秒、履歴に比例）。閉じたsegmentの畳み込み結果を不変のbaseとして保持し、現segmentだけ読み直す最適化は、再構築が常態化しない限り入れていない。
9. **旧版の`rencrow actions verify`は、回転後のstoreでsegment 0しか読まず、最新の履歴を含まないまま`ok`と報告する**（読取専用で、writerではない）。5章の旧binary対策（0444）はwriterにだけ効く。戻す前に旧版の読取コマンドを使わない（運用注意。`docs/05`に記載）。
10. 日が変わっても、現segmentが空でも回転する（空のsegmentが1つ残る）。同じ日のsegmentは99まで。超えたら現segmentで書き続けてWARNを1回出す。
11. 障害注入の「prepare後」「追記後commit前」は、7.1の11と同じく、WALの形を手で作って再現した（新segmentのWALに対して）。回転・移行・concatの途中は、failpointでpanicさせ（同一process内）、子processの`os.Exit`は回転4段とcommit内4段で行った。

## 付録A. 計測の方法と再現

- 複製: 稼働storeを`nice -n 19 ionice -c3 cp -a`で使い捨て領域へ（所要0.1秒）。複製で`NewJSONLStore`が検証に通ったので、tx途中の複製ではない。
- harness: 複製に対する試験用の`go test`（package内、repoには含めない）。`jsonlbatch`の`SetTxObserver`でlock待ち・settle・exec・commitを採り、phaseは`readJSONLLines`、`loadActions`、`loadAttempts`、`validateSnapshot`、`newTransactionStore`、`validateSnapshotLocked`、全体SHA-256、fsyncを個別に計時。7回のmin/p50/p90/max。操作は`actionmanager.Manager`経由で10回ずつ。MP同居は100〜150秒の試験（MP形: 作成+終端を11秒周期、前景: 作成+検査+終端を3秒間隔）。
- 条件: 稼働中の本番ホスト（負荷平均4〜8、4コア）、`GOMAXPROCS=2`、nice 19。min値は競合が少ない時、p50は通常の揺れを含む。
- 発生量: 複製のJSONLをstreamで読み、kind・日別の件数とbyteのみ集計（本文・IDは出力していない）。harnessが追加した行は名前で除外。
- 後始末: 本番ホスト上の複製・ソース・ビルドキャッシュ・出力は作業の最後に削除した。
