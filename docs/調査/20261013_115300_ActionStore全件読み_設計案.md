## 2. 現状の構造 [事実]

- 2 file + `jsonlbatch`（root直下に1組のWAL `.jsonlbatch.wal`・OS lock `.jsonlbatch.lock`）。行はJSONL（`json.Marshal` + `\n`）、Action・Attemptとも**追記のみ**で、同じIDの最後の行が最新（1 Actionは作成と終端の最低2行）。
- 層: `Manager.mu` → `JSONLStore.mu` → OS flock。**readも排他flockを取る**（`jsonlbatch.Read`）。単一プロセス内ではmutexが先に直列化するので、flockのlock_waitは0.1ms（観測値）で、競合はwallに現れる。
- 全txの流れ: `loadActions`+`loadAttempts`（全行decode、1行ごとに`Validate`、不変条件の畳み込み）→ `validateSnapshot`（全件）→ `newTransactionStore`（mapへclone）→ callback → `finalize`でもう一度`validateSnapshot`（全件）→ `jsonlbatch`: prepareで追記先fileの**先頭から全体SHA-256**、`appendPrepared`でもう一度全体SHA-256 → 追記 → fsync → 追記分のhash → WAL commit（fsync）。CreateAction・CompleteAttemptは両fileへ追記するので、毎回 **2 file × 2回 = 約154MB** をhashする。
- 検証の性質: 全件再検証は毎tx、過去行の破損・改竄もfail closedで検出する副作用を持つ（A導入後はここが変わる。5.4）。
- Action storeを開くのは本番では`cmd/rencrow`のmainプロセス1つ。readerプロセス・CLI・Viewerの一覧は無い（repo内grep）。ただしこれは現状の事実であって不変条件ではない（5.4で強制する）。
- 本storeには`SetTxObserver`が配線されていない（task storeだけ配線済み）。本番のtx分布は未観測で、本書の値は複製上の実測。
- `docs/05` の保存状態coverage表にAction storeの行が無い。`config/durable-stores.json`にも未登録 [事実]。

### 5.2 (A) メモリ上の索引で全件読みをやめる

- **A2（推奨）常駐snapshot**: 起動時に1回、2 fileを読んで検証し、decode済みのAction・Attemptをmapに常駐する。commitが確定したら**書いたbytesから**差分を適用する（task storeの`jsonlbatch`のpost-commitフックを使う）。副次mapに (TaskID,RunID)→Action、ActionID→Attempt、open集合、Native委譲の(Task,Run)→Action、Kind+Name→Actionを持つ。tx内は触ったIDだけ検証する。
- A1 ID+位置のコンパクト索引（task store方式、`pread`+CRC32C、sidecar任意）: 約15〜20MB [推定。試作なし]。Actionのクエリは全部mapで足りる、Task側の鍵構造（Taskが1級、Runが従属）をActionの(Action→Attempt)にそのまま流用できない、index_*の汎用化は2つ目の使い手が実質いない、の3点でA2を選ぶ。
- 効果 [推定]: exec 2.7s → ms、read tx 2.5s → 1ms以下、write txは commit 1.9sだけが残る（4.7s → 約1.95s、−59%）。起動時のAction関連処理は 約10.6s → 約2.3s（open時の構築1回のみ。K2,K3,K5が索引問合せになるため）。MP同居のlock占有 46% → 約26%。
- 変更の大きさ: 新規 約1,000〜1,500行+試験 [推定]（索引エンジン、増分検証、差分適用、フラグ）。`domainaction.Store`は追加のみ（`Filter`に`Kind`/`Name`、`RunID`の存在確認）。K2,K3,K5を問合せへ置換。
- 障害時: ログが唯一の正本で、snapshotは派生物。(1) tx途中で落ちる→`jsonlbatch`が従来どおりWALで回復、起動時にsnapshotをログから再構築。(2) `ErrCommitUncertain`→適用せず、次のtxがlock内で2 fileのサイズと適用済み長を照合して末尾から再生（task storeの`requireAppliedEquals`と同じ）。(3) サイズ不一致（別プロセスの追記など）→fail closed。(4) 適用失敗→fail closedして再構築。
- 移行と戻し: file形式を変えない。フラグ`action_store.index.enabled`（既定false）で1 release併存し、falseで旧全件経路に戻る。

### 5.3 (B) 日次回転（commitのprefix hashの解消）

- **要否の判定 [事実]**: commitの95%以上がprefix hashで、write txの約41%を占め、(A)後に残る唯一の履歴比例コスト。**hashが支配的なので要る**。
- 方式: task storeと同じ。UTC日の`logs/<YYYYMMDD>-<NN>/`にsegmentを作り、現在の2 fileを「seg0」として読取専用に凍結する。書込み先は当日のsegmentだけ（サイズ弁8MiB）。A2は起動時に全segmentを順に読む。
- 効果 [推定]: 当日segmentの累計サイズ分だけをhash。平均は2×(3.9MB÷2)=3.9MB÷81MB/s ≒ **48ms**、最大日（5.3MB）の日末で約130ms、弁（8MiB）で約210ms。(C)後（約0.5MB/日）は約6ms。write tx 4.7s → A+Bで約0.05〜0.13s。
- 変更の大きさ: 約500行+試験（segment選択・切替・封印・`LAYOUT`・size照合・連結ロールバック）。task storeの回転は10/12に配備、10/13 00:00Zの日切替を本番で観測済み（pause 21ms）。
- 障害時: 切替失敗→旧segmentで継続。旧binaryの誤起動→seg0が0444で`jsonlbatch.New`が失敗し、size照合でも拒否。**過去segmentのprefix hashによる改竄検知は、封印後のsize照合に狭まる**（task storeと同じ判断。D8）。
- 移行と戻し: A（段階1）の後に段階2として有効化（task storeのD5と同じ）。戻しは日ごとのlogをseg0へ連結し直す（オフライン）。

### 5.4 (A) の意味変化と守る不変条件

- 全txの全件再検証は、**過去行の破損・不整合の検出**を毎txで行っていた。A後は検証を (1) tx単位の増分不変条件（触ったAction・Attemptの群と、Nativeの(Task,Run)一意）、(2) 起動時の全件構築検証、(3) `verify`コマンド（全件、旧`validateSnapshot`を再利用）に置く。増分検証が旧全件検証と等価であることはoracle試験（ランダムtx列で両方を比べる）で示す。
- K2の「存在しないRun参照はエラー（起動失敗）」: **回復が作用する範囲**（open Actionと、running Runに紐づくAction）は従来どおり検査する。全Actionの参照検査は起動のcritical pathから外し、`verify`とopt-inの起動時オプションにする（起動失敗の原因を全件整合の1件に依存させない）。
- 単一プロセス前提は現状の事実であって不変条件ではない: 各txのlock内で2 fileのサイズをsnapshotの適用済み長と照合し、不一致はfail closedにする（強制）。commit→適用は`Manager.mu`配下の同一臨界区域で順序固定する。
- 旧全件経路は、Hard Invariantの「同じIUで削除」の**例外**としてフラグ下に1 release残し、観測後のIU（IU-7）で削除する。理由はロールバック能の確保。

### 5.5 (C) MPの空振りで実行主体を作らない

- 方式: wrapperが`CreateAndStartRun`の**前に**、read-onlyの「claim可能か」判定を行い、無ければ`Processed=false`を返す（Task・Run・Actionを作らない）。判定述語はclaimの対象より**狭くしない**（偽陰性禁止）: `pending`（`attempt_count<max`）、`retry_wait`で`next_attempt_at<=now`、`running`で`lease_expires_at<=now`（claimが回復して取る対象）、さらに`attempt_count>=max`の`pending/retry_wait`（claimの「使い切り→failed」更新を残すため）。偽陽性は従来どおりTaskを作るだけで無害。判定とclaimの間のTOCTOUはclaim側が権威なので害が無い。判定のエラーは握りつぶさず従来どおり`reporter.Failed`へ。
- 効果 [推定]: Action増加 −約95%（1日約2,700 → 実処理の最大17件+非MP約170〜300件）、store増加 3.9 → 約0.5MB/日以下、MPのlock占有 46% → 0、Tool同居の悪化 20.9s → 11.8s（−44%）。**Task store側の流入も約9割減る**（MPはTask件数の約9割。task store仕様 9.3、決定D11の「MPの軽量化」の一手）。既存の77MBの履歴は残るので、tx時間（4.7s）自体は変わらない。(A)+(B)の前提でもある（A2の常駐メモリの増加を年約1GB → 約0.1GBに抑える）。
- 変更の大きさ: 小（wrapperと`memorypromotion.Store`に問合せ1つ、約100〜200行+試験）。旧経路（常にTask生成）は同じIUで削除する。
- 障害時: 判定が偽陽性→従来どおり。判定がDBエラー→エラー返却（従来のclaimエラーと同じ扱い）。
- 移行と戻し: データ移行なし。戻しはrelease戻し。「MPが走って対象なしだった」事実の観測先がActionから消えるので、ログ（件数のカウンタ）で代替する。MPのTask・Actionを読む表示・liveness・reapの消費者は生成側とreap分類のみで、空振りの記録に依存する使い手はrepo内に無い（grep）[未確認: 本番ホスト上の外部script]。
- 規則との整合: 「Taskは実行するために作る」。既存挙動の変更なので**明示承認が要る**（6章D1）。

### 5.6 (D) task storeのindex・segmentを共通部品にするか

`40-modularization`（根拠1: 今日2+ callers、根拠2: 変更隔離、根拠3: 純粋ロジック）とConceptual Integrity（正本は1つ、Semantic Duplication回避。ただしowner・lifecycle・failure domainが異なる重複は理由と検証を残して許容）に照らす。

| 部分 | task storeでの規模 | 判定 | 理由 |
| --- | --- | --- | --- |
| segment名・UTC日・一覧・連結順（`formatSegmentName`、`segmentDay`、`utcDay`、`listSegmentDirs`、名前のpattern） | 約100行、`domaintask`参照0 | **共通化する** | Task+Actionの2 caller（根拠1）、純粋（根拠3）。同じ規則を2か所に逐語コピーするとSemantic Duplication |
| `LAYOUT`書式・凍結・size照合 | 約250行。版標識と固定file表（6 file）がTask専用 | **今は共通化しない**（許容する重複として記録） | Task側を触るリスク（10/12配備直後）。file集合・版標識・failure domainが異なる。Action側にも同一の障害注入試験を課して検証し、3つ目の使い手か規則変更が出たら共通化する |
| 回転の協調（`rotateIfDue`ほか） | 約500行 | 共通化しない | `taskIndex`に依存 |
| `index_*`・sidecar・checkpoint | 約4,300行 | 共通化しない | 鍵・レコード構造が異なり、A2はsidecarを使わない。2つ目の使い手が実質いない（根拠1が成立しない） |
| `jsonlbatch`のpost-commitフック・tx observer | 既存（additive） | 既に共通 | 変更なし |

案: (i) 純粋な名前規則だけを共通化（推奨）/ (ii) さらに`LAYOUT`・凍結・size照合を共通化 / (iii) 全部別実装（逐語コピー）。Task側の変更は(i)で小さな純粋移動（segment名のゴールデンテストで固定）、(ii)は固定file表の汎化を伴う。

## 6. 推奨と決定項目

### 6.1 推奨

**(C) → (A)+(B)**。(D)は純粋な名前規則だけを共通化する。

- (C)は最小差分で最大の効果（lock占有46%の解消、Task store流入の約9割減、Aの常駐メモリ増の抑制）だが、**既存77MBの履歴のtx時間は直らない**。(A)だけではhash 1.9sが残り、(B)だけではexec 2.7sが残る。したがって(A)と(B)は同じ計画で決め、段階（索引→回転）で配備する。
- Aは常駐snapshot（A2）。A1への段階案は採らない（2実装になる）。再評価条件（ヒープ>128MB、起動時構築>5s、write tx p50が悪化）をADRに記録する。
- 起動時の整合検査はcritical pathから外す（5.4）。

## 9. 試験計画

1. **Red再現（実装前）**: 本番コピーに対し実際の`JSONLStore`+`Manager`でwrite/read txの所要を測る比較試験。履歴1倍/10倍（合成）でtx時間の比が1に近づかないこと（AC-9）。MP同居のlock占有。
2. **oracle差分**: 旧全件経路を基準に、ランダムなtx列（作成・終端・再試行・Native委譲・失敗）で全問合せ・全fieldを比較（AC-12）。増分不変条件が旧`validateSnapshot`と等価なこと。本番コピーでの全件比較。
3. **障害注入**: 8章の強制終了点。サイズ不一致のfail closed。破損行の起動時拒否。
4. **性能**: 旧実装に対する比（AC-1〜AC-6, AC-10, AC-11）。CIは比で判定する。
5. **呼出し元**: K2,K3,K5が置換前後で同じ結果を返すこと。`ListActions{}`の無制限呼出しをarchitecture testで拒否。
6. **(C)**: 対象なしでTask・Run・Actionが0件増える。claim可能（pending、due済みretry、期限切れlease、使い切り）では従来どおり作る。判定の偽陰性が無いこと（claim可能なすべての状態で判定が真）。
7. **三OS**: UTF-8 path、dir fsync、Windowsでの凍結（0444）とrename。Check Plan（`config/checks/core.json`）へ追加。

## 付録A. 計測の方法と再現

- 複製: 稼働storeを`nice -n 19 ionice -c3 cp -a`で使い捨て領域へ（所要0.1秒）。複製で`NewJSONLStore`が検証に通ったので、tx途中の複製ではない。
- harness: 複製に対する試験用の`go test`（package内、repoには含めない）。`jsonlbatch`の`SetTxObserver`でlock待ち・settle・exec・commitを採り、phaseは`readJSONLLines`、`loadActions`、`loadAttempts`、`validateSnapshot`、`newTransactionStore`、`validateSnapshotLocked`、全体SHA-256、fsyncを個別に計時。7回のmin/p50/p90/max。操作は`actionmanager.Manager`経由で10回ずつ。MP同居は100〜150秒の試験（MP形: 作成+終端を11秒周期、前景: 作成+検査+終端を3秒間隔）。
- 条件: 稼働中の本番ホスト（負荷平均4〜8、4コア）、`GOMAXPROCS=2`、nice 19。min値は競合が少ない時、p50は通常の揺れを含む。
- 発生量: 複製のJSONLをstreamで読み、kind・日別の件数とbyteのみ集計（本文・IDは出力していない）。harnessが追加した行は名前で除外。
- 後始末: 本番ホスト上の複製・ソース・ビルドキャッシュ・出力は作業の最後に削除した。
