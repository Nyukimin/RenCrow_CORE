## 概要

ChatGPT export の欠落原因は、L1 raw 用 lifecycle compact が `layer` を制限せず、古い `conv:*` の L3 export まで削除していたことだった。L1 のみを compact するよう修正し、54,032 件を再投入した。レビュー済み normal UserMemory 11 件を confirmed にし、4 Agent の実 Chat で prompt 注入と想起応答を確認した。

---

## 調査経緯

### 仮説1: lifecycle compact が import 済み L3 を削除している

- **根拠**: manifest は 54,032 件、import event も全件成功だが、live DB は 25,032 件だった。起動 log に `raw_compacted=1000` が繰り返し記録されていた。
- **検証結果**: 確認
- **証拠**:
  - 旧 SQL は `namespace LIKE 'conv:%'` と `memory_state=observed` のみで、`layer='L1'` 制約がなかった。
  - `AND layer = MemoryLayerL1` 追加後の回帰 test で、古い L1 は削除され、同じ古さの ChatGPT L3 は残った。
  - 修正 binary の lifecycle 結果は `raw_compacted=0`。再投入後の再起動で 54,032 件が維持され、`PRAGMA quick_check=ok`。
- **チェックリスト結果**:
  - ☑ 確証バイアス: import 失敗と対比し、manifest、import 履歴、DB 件数が初回 import 成功を支持することを確認した。
  - ☑ 頻度制約: 1,000 件ずつの減少と compact limit が一致した。
  - ☑ ライフサイクル: import → restart/maintenance →減少の順と修正後の再起動を確認した。
  - ☑ 既存知見: L3 を immutable provenance とする CORE 仕様と整合する修正である。

### 仮説2: ProfilePromotion の 45 秒 timeout が Worker の完了より先に到達する

- **根拠**: ChatGPT 由来 failed 1,067 件のうち1,062 件が `context deadline exceeded`。Gateway の処理時間は約44〜45秒だった。
- **検証結果**: 確認（新規 job の継続消化は残課題）
- **証拠**:
  - live config の `profile_promotion_timeout_seconds` を45秒から180秒へ変更した。
  - job 現状は completed 555 / failed 1,222 / pending 17,704。ChatGPT 由来は completed 448 / failed 1,067 / pending 17,694。
  - foreground Chat/IdleChat が Worker を使うと実行中 promotion が `context canceled` になる場合がある。今回の即時想起は、既存のレビュー済み candidate を正規 state API で confirmed 化して成立させた。
- **チェックリスト結果**:
  - ☑ 確証バイアス: JSON schema error 5 件は timeout と分離した。
  - ☑ 頻度制約: failed の大多数が deadline である集計と一致する。
  - ☑ ライフサイクル: queue、lease、retry、foreground cancellation を別々に確認した。
  - ☑ 既存知見: candidate の自動 confirmed 化を禁じる仕様は維持した。

### 仮説3: confirmed UserMemory は実 Agent prompt に入っていない

- **根拠**: `recall_trace_item` に UserMemory 行が現れなかった。
- **検証結果**: 棄却（trace の観測欠落は確認）
- **証拠**:
  - prompt-debug で Mio/Shiro/Kuro/Midori それぞれの実 request に `prompt_context_type=recall_pack`, `recall_section=user_profile` の 560 文字 block があった。
  - 4人の block SHA-256 は全て `ad50a1d58ac8ffd665eaa1d89d64d50fb75f6609250c78721bf3c93bf962af9f` で、対象の想起記憶を含んでいた。
  - 4人とも正規 `RenCrow_CMD -> CORE Viewer -> CHAT -> Agent -> LLM` 経路で、関連場面で連想的に想起・活用する旨を回答した。
  - `RecallPack.ToTraceItems()` は L0/L2/L3/Knowledge 系を記録するが `UserProfile.Facts` を trace item へ変換しない。
- **チェックリスト結果**:
  - ☑ 確証バイアス: Agent の回答文だけでは合格にせず、実際の prompt block を確認した。
  - ☑ 頻度制約: 4 Agent すべてで同じ block と回答を確認した。
  - ☑ ライフサイクル: candidate は非注入、confirmed normal は注入、private candidate は非注入とした。
  - ☑ 既存知見: UserMemory は Knowledge Memory ではなく RecallPack UserProfile へ入るという正本責務と一致した。

## 根本原因

- **原因1**: L1 raw compact SQL の `layer` 制約漏れ。
- **メカニズム1**: `conv:* + observed + old` に一致する ChatGPT L3 を L1 raw と誤認し、1回に最大1,000件削除した。
- **原因2**: ProfilePromotion の CORE timeout 45秒が実 Worker latency とほぼ同じで、完了余裕がなかった。
- **影響範囲**: ChatGPT L3 episode の完全性、プロファイル投影率、UserMemory の想起可能な範囲。

## 修正内容

1. lifecycle compact 対象を `layer='L1'` に限定し、L3 保存の回帰 test を追加した。
2. 修正 binary を build/install し、CORE を再起動した。旧 binary と DB の consistent backup を保存した。
3. ChatGPT export artifact 54,032 件を idempotent 再投入した。
4. live ProfilePromotion timeout を180秒に延長した。
5. 証拠済み normal candidate 11 件を `/viewer/memory/user/state` で confirmed 化した。private 3 件は candidate のまま維持した。
6. 4 Agent の実 Chat と prompt-debug で UserProfile 注入・想起を検証した。

## 残課題

- ChatGPT 由来 ProfilePromotion job は completed 448 / failed 1,067 / pending 17,694。全会話から追加 UserMemory candidate を生成する background backfill は未完了。
- failed job を正規に reset/retry する運用 API がない。直接 DB 書き換えは行っていない。
- foreground/IdleChat と ProfilePromotion の Worker 競合による cancellation を、長時間 backfill 制御として整理する必要がある。
- Recall trace に UserProfile/UserMemory の memory ID が出ないため、現状の厳密な注入証拠は prompt-debug に依存する。
