## 2. 実行分類とowner

| 分類 | 入力 → 出力 | owner | 失敗status / 証跡 |
| --- | --- | --- | --- |
| CLI | source、DB snapshot、固定Plan → build、migration、整合性結果 | CORE owner CLI / Tools Check Plan CLI | 非zeroで停止。JSON receipt |

## 3. 全Step共通の固定サイクル

Step 10から20まで、次の順序を変えない。前工程の9を終える前に次工程へ着手しない。

1. **仕様固定**: 対象、owner、正本、旧語彙、migration、runtime route、受入条件を更新する。
2. **Check Plan固定**: purpose、phase、check、consumer、failure actionをowner manifestと対応させる。
3. **RED**: 欠ける不変条件を再現するtestを先に追加し、期待理由で失敗することを確認する。
4. **GREEN**: 最小のowner実装でREDを通す。旧新併存の互換layerを作らない。
5. **Gate 1–5**: Compile、Unit、Migration、Referential Integrity、Integrationを固定Planで通す。
6. **配備**: clean sourceからbuildし、artifact revision/hashを確認してbackup後に既存unitへ配置する。
7. **Gate 6**: 認証済み正規routeの実Actor、利用者に見える結果、Viewer/Event/receiptを確認する。
8. **Restart / Recovery / Gate 7**: 再起動後維持、rollback可能性、当該scopeの旧型・field・key・column・generator・query・runtime変換zeroを確認する。
9. **Commit / Push**: 当該Stepだけを日本語メッセージで論理的にcommitし、追跡branchへPushする。remote一致を確認して台帳を更新する。

test失敗、migration不整合、dirty artifact、readiness失敗、E2E不足、legacy非zeroのいずれかがあればStepは未完了のまま停止する。配備後の失敗は旧binary／snapshotへrollbackし、次Stepへ進まない。

## 6. Step 11: ActionID / AttemptID

**owner:** CORE Action owner。
Tool、DCI、LLM、STT、TTS、Playback、Patch apply、External send、Verification、Memory promotionをActionへ統一する。Action作成とfirst Attempt、retry、終端をowner transactionで確定し、異なるManager/store instanceの競合とstale completionをREDで固定する。

E2Eは実Toolのsuccess、retry、timeout、cancel、side-effect failureを同一Task/Run上で確認する。同じActionのretryでActionID不変、AttemptID更新、`ApplyID`／`SubmitID`／内部RequestID zeroを確認してPushする。

## 7. Step 12: RequestID / ResponseID

**owner:** transport adapterとAction owner境界。
RequestIDを一回のtransport callだけに限定し、Provider固有IDはExternalRef、ToolCallIDはProviderToolCallIDへ置換する。streaming、no-response terminal failure、provider retry、multi-request AttemptをTDDする。

実Provider／Tool routeでAttempt→複数Request→terminal Responseを確認し、内部CommandのRequestID利用とProviderToolCallIDのActionID利用がzeroになった後にPushする。

## 8. Step 13: ArtifactID

**owner:** CORE Artifact owner。
Report、Draft、ContextPack、Image、Patch、Specification、Transcriptの生成物をArtifactID + ArtifactKindへ統一する。domain entity IDは意味が異なる場合だけ保持する。

create、update、supersede、content hash、source Event、Workstream relationをTDDし、正規生成routeとViewerで追跡する。Generic ReportID／DraftID／ContextPackID zero後にPushする。

## 9. Step 14: EvidenceID / MemoryID

**owner:** Evidence、Memory、Verification owner。
Evidenceを独立entityへ統一し、MemoryにCreatedByEventID／UpdatedByEventIDを持たせる。Profile promotionをTask/Run/Action、Verification ReportをArtifactで表す。

observed→candidate→confirmed→pinned、sensitive reject、missing evidence reject、recall、supersede、decayをTDDする。実Memory promotionでTask/Run/EventとViewerを確認し、文字列派生EvidenceIDとorphan zero後にPushする。

## 10. Step 15: Scheduler

**owner:** Scheduler domainとTask owner。
`scheduler.JobID`をScheduleIDへ置換し、発火時だけ新Task/Runを作る。manual/due/deferred/retry/disable/next-run/duplicate fireをTDDする。

実Schedule発火を再起動前後で確認し、Scheduler domainのJobIDとSchedule定義・Task実行間のID共有zero後にPushする。

## 11. Step 16: QueueItemID / CheckpointID / ReceiptID

**owner:** Queue、Checkpoint、Receipt owner。
QueueID、generation checkpoint、汎用Receipt、Resolution/Stage Requestを正規IDへ置換する。claim、lease、expiry、reclaim、checkpoint resume、receipt replay、idempotency conflictをTDDする。

実queue/restart recoveryを確認し、Generic QueueID、GenerationID checkpoint参照、ReceiptIDのEventID流用zero後にPushする。

## 12. Step 17: Voice / IdleChat

**owner:** Voice、Conversation、IdleChat owner。
Voice input→STT→Mio→TTS→Playbackを同一TraceのAction/Attempt/Request/Responseへ接続し、IdleChatをSession/Thread/Turnへ統一する。generation制御値はIDにしない。

実音声、interrupt、cancel、drain、timeout、Viewer absent、old/new generation境界とIdleChat再起動をE2Eする。ChatID、GenerationID、generationのID利用、古い音声復活、新音声誤停止zero後にPushする。

## 13. Step 18: Workstream / Atlas / Backlog

**owner:** Atlas / Backlog / Implementation Lifecycle owner。
Generic ItemIDをdomain-qualified IDへ置換し、状態遷移をEvent、生成物をArtifact、Stage操作をTask/Run/Action/Receiptへ接続する。

maturation、revalidation、promotion、implementation stage、freeze、resolution、closure、replay、duplicate preventionをTDDし、実Gmail/X等のsourceから正規Atlas/Backlog routeを確認する。Generic ItemID/ResultID/RecordIDとReceipt/Event意味共有zero後にPushする。

## 14. Step 19: Viewer / OTel / Graph

**owner:** CORE Viewer、Canonical Event projection、OTel adapter。
ViewerをCanonical Event projectionへ変更し、OTel TraceIDをCanonical TraceIDへ接続し、Event/Task/Communication Graphを正規IDから生成する。

SSE disconnect/reconnect/backfill、graph reconstruction、ordering、redaction、Viewer unavailableをTDDする。認証済みViewerの全対象画面をChrome DevToolsで確認し、旧ID fieldとLegacy lookup zero後にPushする。

## 15. Step 20: 全体Cleanup

**owner:** COREと直接依存owner。
runtime migration map、compatibility adapter、dual read/write、deprecated alias/key/column/fixture/parser、旧generator、旧Viewer query、旧Graph projectionを削除する。隔離は正本のretain-and-quarantine契約を満たす保存証拠であり、legacy runtime経路とは区別する。

全Golden flow、Restart、Recovery、Retry、long-running/background Task、Voice、Atlas、Memory、Viewer、全ID integrity scanを固定Planで通す。正本に列挙された旧IDがsource、新規runtime write、active DB schema、API、Viewerでzeroであることを確認する。全owner receiptを集約し、台帳を`completed`へ更新し、最終commitをPushする。この後にだけ`main`統合を別作業として判断する。

## 16. 進捗台帳の更新規則

各Stepのcommit前に`identity-remediation-ledger.json`の当該requirements/gatesだけを更新する。historical evidenceをcurrent evidenceへ昇格しない。各Gateはsource revision、artifact hash、active config、runtime PID、receipt、無効化条件を対応させる。

状態は次に限定する。

- `pending`: 未着手
- `in_progress`: REDまたは実装中
- `blocked`: fail-closedな前提不足
- `passed_source`: Gate 1–5のみ
- `passed_runtime`: Gate 6まで
- `completed`: Gate 1–7、Restart/Recovery、Push/remote一致
