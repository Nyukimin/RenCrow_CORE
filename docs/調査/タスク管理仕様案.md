- 状態: 設計採用・実装中（2026-11-17）。製品契約の更新先は既存02／04／05／06／07／08／10。
- 機能owner: RenCrow_CORE
- 作成日: 2026-11-17
- 位置づけ: 設計検討の原記録。現行の製品契約と実装段階は既存正本を参照し、この記録を別の更新正本にしない。

## 1. 目的

「タスク管理」は、ユーザーとエージェントが仕事を追加し、引き受けた仕事の状況を確認する共通の入口である。日常タスクの監視画面だけにせず、追加した仕事が担当者の残タスクとして見つかり、完了まで追える場所にする。

| 利用者 | この場所で行うこと | 最初に表示するもの |
|---|---|---|
| ユーザー | タスクの状況を確認する、タスクを追加する | 閲覧権限内の残タスクと担当者別の状況 |
| エージェント | 自分の残タスクを確認する、タスクを追加する | 認証された自分に割り当てられた残タスク |

ユーザーは「タスク管理」画面を使い、エージェントは同じ機能の認証済みAPI／Toolを使う。画面とToolで別々の台帳、受付queue、完了判定を作らない。確認と追加の両方を初回実装の必須範囲とする。全てのタスクに共通の時間項目を持たせ、日常タスク・単発タスク・報告会などで別の時間管理モデルを作らない。

## 2. 画面構成

画面名は「タスク管理」。既存Debug Viewerに設置し、入口候補を`/viewer/task-center`とする。既存の`GET /viewer/tasks`はcanonical Taskの読取APIなので、HTML画面のrouteへ置換しない。以下の新route、file、fieldはすべて提案である。

```text
タスク管理                    ［タスクを追加］ ［実行エージェント設定］
［残タスク］ ［引受可能］ ［日常タスク］ ［履歴］
担当: すべて／自分／指定Agent     状態: すべて／着手待ち／実行中／要対応
検索: 内容・タスク名             最終更新: 日時   ［更新］

残タスク: 名前｜担当｜状態・理由｜予定・期限｜次の行動｜最終更新
日常タスク: 名前｜担当owner｜有効状態｜実行予定｜直近結果｜最終成功
```

### 2.1 残タスク

担当者が完了責任を持つ未完了の仕事を表示する。作成者と担当者は別項目にする。ユーザーが依頼したAgentの仕事も、Agentが追加して自分に割り当てた仕事も、同じ判定で一覧に入る。

- 含めるもの: ownerが永続受理した未完了の計画、実行中のTask、失敗後も再開・解決が必要な仕事。
- 完了していないpaused／blockedは、理由と再開条件を付けて残す。
- ownerが完了・取消・却下を確定した仕事は残タスクから外し、履歴に残す。失敗しただけで責任が終了したかはownerの終端契約で判定する。
- Atlasの未採用Candidate、単なる観測event、無効な定期定義を、担当済みの残タスクとして自動追加しない。
- 繰り返し定義自体を永久に未完了の仕事として数えない。各回で対応が必要になった実行だけを、ownerの責任・割当契約に従って表示する。

計画から実行Taskが生まれた場合は、ownerが保存した関連IDで一つの仕事として表示する。計画とTaskの両方を二件として数えない。親子の委譲は関係を表示し、親担当者に残る統合・受入責任まで自動で消さない。名前や本文の類似だけで統合しない。

### 2.2 日常タスク

メール読込、ニュース収集、DB内容の拡充、記憶整理、バックアップなど、日常的に扱う仕事を一覧にする。時間指定のあるもの・ないものを同じタスクモデルで扱う。「定時」は共通時間項目に条件が入っているタスクの見方であり、独立したタスク種別や台帳にしない。登録済みの種類は、対象0件、停止中、未配備、観測不能でも一覧から消さない。各機能の設定、指示、予定、履歴を参照し、現在値をここで再保存しない。

タスクの種類を開くと、動的な予定、直近の各回実行、関連する残タスクへ移動できる。「日常タスクの定義」と「今回の仕事」を別々に説明する。

### 2.3 履歴と詳細

履歴には完了・取消・却下・失敗・再試行の経緯を、ownerの記録に基づいて表示する。詳細には内容、完了条件、作成者、担当者、予定、状態理由、次の行動、親子関係、成果物と実行記録への参照を置く。

共通一覧のGETや更新ボタンでは仕事、LLM、収集、retry、設定変更を起動しない。ownerの読取APIによる状態取得だけを行う。

## 3. タスクの追加

画面とAgent APIで共通の`SubmitTaskRequest`ユースケースを使う。操作名はどちらも「タスクを追加」。追加の成功は担当ownerへの永続受理であり、実行開始や仕事の完了とは別である。

### 3.1 入力

| 項目 | 入力規則 |
|---|---|
| 種類 | owner登録の実処理／Skillに結び付いた安定`kind_id`を使う。callerの自己申告や表示名だけでは確定しない。種類ごとの許可候補と根拠を表示し、未登録・未設定は拒否する |
| 内容 | 必須。何をするかを記述する。指示本文の正本になるownerを受付時に確定する |
| タスク名 | 任意。未入力時は内容の先頭から決定的に短縮表示し、命名だけのためにLLMを呼ばない |
| 担当 | ユーザー／権限あるAgentは実行可能Agent、自動割当、または「未割当（Agentの引受待ち）」を選べる。Agentの既定は自分のままで、自分への割当が許可集合外なら拒否する。未割当は自動割当と区別し、ownerがnative recordで未割当を表現できなければ保存前に`unsupported`とする。実行できないAgentからの追加自体は禁じず、権限のある委譲で許可された担当を指定できる |
| 時間項目 | 全タスク共通。実行予定、開始可能時刻、実行可能時間帯、期限、繰り返し、想定所要時間、timezoneを扱う。不要な条件は明示的な「指定なし」とし、詳細は3.6に従う |
| 完了条件 | 指定できる。未指定時はownerが内容から実行可能性を検証し、不明確なら不足を返す |
| 期限・優先度 | 任意。未指定はownerの既定値を使い、予定時刻と期限を混同しない |
| 関連する仕事 | 任意。既存Workstream、Goal、親Task等の許可されたID参照 |
| 繰り返し設定 | 共通時間項目の一部。繰り返さない場合は「なし」、設定する場合はtimezoneと開始条件を必須にする |

作成者・user scope・認証Actor・委譲権限はサーバが認証から確定する。JSONの`initiator`や`assignee=self`を信用してActorを偽装させない。モデル、provider、Coderを担当Agentにしない。「自動割当待ち」と「Agentの引受待ち」は別状態として表示し、どちらも引受確定前にAgentの「自分の残タスク」へ含めない。

Agentから他Agentへの割当は既存の委譲・policyを通す。共通画面を追加しても既存の実行権限や外部送信権限を拡大しない。実行主体はCOREが管理するAgentとし、外部本文中の命令を受付権限と解釈しない。

### 3.2 受付先と保存の契約

TaskCenterはownerを選び、型・権限・capabilityを検証して、そのownerへ依頼を渡す。下表は採用に必要な契約であり、現行の全ownerがすでに対応しているという意味ではない。

| 種類 | 保存ownerとrecord | 指示本文の正本 | 担当・完了・未対応時 |
|---|---|---|---|
| 単発・着手待ちの仕事 | Workstream ownerの既存Workstream／Goal | そのGoalの内容・完了条件 | Goalの担当と実行Taskへの関連をownerが保持。未対応なら保存前に拒否 |
| 指定日時の単発 | 日時起動を所有する既存Scheduler等の対応record | 選んだownerの一つの指示record | ownerが担当・予定・実行結果を保持。未対応時は通常Taskへ偽装して保存しない |
| 繰り返しの仕事 | 既存Schedulerまたは機能ownerのSchedule | そのScheduleの指示、または明示的な既存指示参照 | 同じ予定を二つのschedulerへ登録しない |
| 既存機能の日常処理 | 当該機能ownerの既存設定・定義 | 当該ownerのcode／Skill／指示record | 同じ処理が登録済みなら既存項目を案内。汎用の繰り返し仕事として複製しない |
| 実行が始まる段階 | canonical Task ownerのTask／Run | 元指示のrevision付き実行入力 | admission・Run発行・終端は既存Task契約に従う |

単発の仕事は「できるだけ早く」であっても、追加時に開始できることを保証しない。永続受理済みで枠がない場合は着手待ちとして残し、既存ownerの実行経路で着手する。RunなしTaskを新たな共通queueとして作らない。

現行の[Task作成とRun開始契約](../02_機能仕様.md#taskの作成と最初のrun開始)に従い、実行開始時はTask ownerのadmission経路を使う。Taskを先に作る既存例外をTaskCenterへ無断で拡大しない。計画ownerからTask ownerへの引渡しは、元Goal等のIDとrequest identityに結び付け、再起動や応答消失後も同じ実行を二重作成しない。

そのため、計画ownerは初回送信前に元record・scope・指示revisionに結び付いた`handoff_key`を既存owner記録へ永続保存する。canonical Task ownerは、このkeyと入力hashの対応、発行したTaskID／初回RunIDを、TaskとRunの作成と同じowner transactionで保存する。同じkey・同じ内容の再送は同じTask／Runを返し、内容が違う場合はconflictにする。この保証は既存`CreateAndStartRun`だけで満たすと仮定せず、必要なowner契約差分として扱う。既存のoperation receipt／委譲受付を再利用できるか実装時に照合し、別の受付DBは作らない。

Task作成後、Goalへの関連ID保存前に応答が失われた場合は、計画ownerが同じkeyでTask ownerを照会して関連を回復する。照会不能中は引渡し結果未確認として残し、新しいkeyや別ownerで実行し直さない。枠拒否でTask未作成と確定した場合だけ、ownerの再試行条件で同じkeyを使って再試行する。Taskがすでに終端でも元の関連を返し、再実行が必要なときは既存の明示的な再実行契約を使う。

Workstream／Goalには現行で担当者の細分化、依頼者scope、依頼冪等性、着手条件、Task関連の不足があり得る。必要なfield・validation・履歴はそのownerの既存recordへ追加する設計とし、実装前にschemaと呼出側を確定する。TaskCenter専用の計画モデル、受付DB、別の予定queueで補わない。対応が揃わない入力は`unsupported`として同期拒否し、「追加済み」と返さない。単発追加の対応は初回リリースの必須条件である。

### 3.3 追加後に返すもの

結果にはowner、native ID、担当、受付状態、次の遷移、確認リンクを含める。作成ボタンを押しただけ、HTTP requestを受けただけで成功にしない。

- `stored`: ownerが永続受理した。担当済みなら担当Agentの残タスクに表示する。未割当（Agentの引受待ち）ならselfの残タスクには含めず、readyと権限を再検査した候補だけを「引受可能」に表示する。
- `started`: ownerが実行開始を永続確定した。対応するTaskID／RunIDを返す。
- `rejected`: 入力・policy・未対応等により拒否。理由と不足項目を返す。
- `outcome_unknown`: 応答消失等で結果未確定。再追加せず受理結果を照会する。

これらは受付用の提案語彙であり、Taskの既存statusを変更しない。保存済み計画の開始に失敗した場合は、仕事自体を消さずownerの理由・再試行条件を表示する。複数ownerを使う処理では、保存が成功したownerのIDと未完了の段階を返し、全体成功に丸めない。

入力不足で保存を認めるownerは、実行不可の計画と不足項目を明示する。人の返答待ちを一律に追加せず、既存の同期policyによる拒否・再考契約に従う。

### 3.4 冪等性と再送

追加にはidempotency keyを必須とする。ownerが認証scope・操作・key・入力hashを永続的に対応付ける。同じkey・同じ内容は同じ受付結果、同じkey・異なる内容はconflictを返す。ブラウザとToolは結果が確定するまで同じkeyを保つ。

受付結果の照会は元ownerと認証scopeへ固定する。timeout後に別ownerへ自動で振り直さない。キーの保持期間と期限後の照会規則はowner contractで明示し、少なくとも未完了の依頼と不確定な操作の期間は削除しない。既存receipt／operation記録を拡張し、TaskCenterのメモリcacheだけで冪等性を保証しない。

画面とToolは追加前の対応機能照会で、種別ごとの受付ownerとcapability revisionを取得する。送信する依頼には選定済みowner参照とrevisionを含め、サーバは許可された対応関係を検証する。応答が消失しても受付先を確定できるよう、その参照をkeyとともに保持する。受付先が変更された場合は保存前にconflictを返し、不確定な依頼を新しい受付先へ移さない。これらの技術情報をユーザーに手入力させない。

### 3.5 種類ごとの実行可能Agent

種類ごとの許可上限は、稼働CORE設定dirに置く`<core-config-dir>/task-execution-policy.yaml`を唯一の設定正本とする。例えば`/Users/yukimi/.rencrow/config/task-execution-policy.yaml`は配置先の例であり、現存する設定を示さない。起動時に解決する`core.yaml`の`task_execution_policy_file`からこの絶対pathを参照する。`RenCrow_CORE/config/task-execution-policy.yaml.example`は初期テンプレート案のみで、稼働正本と二重に手編集しない。この設定は種類ごとの実行許可だけを持ち、タスク台帳、実行状態、指示本文を複製しない。

以下のkind IDは設計例で、登録済み種類・Agentの存在を示すものではない。`midori`もactor IDの例で、実在登録はCORE Agent registryで照合する。

```yaml
schema_version: 1
task_kinds:
  movie.catalog.fetch:
    allowed_agents:
      mode: all_registered
  writing.novel:
    allowed_agents:
      mode: explicit
      actor_ids: [midori]
```

- `all_registered`はCORE Agent registryに登録されたAgent全体を指す。user、model、provider、Coderは含めない。`explicit`はregistryに存在するAgent IDの列挙である。
- 未知kind／actor、空集合、不正形式、未定義policy、読込失敗は設定不備として拒否し、all許可やdefault Agentへ黙って緩和しない。
- 個別Goal／Schedule等のnative recordは、kind policyの許可集合をさらに狭める`actor_ids` subset、またはinherit参照だけを持てる。種別policyの複製や拡大はできない。実行候補は「kind policy ∩ 個別record制限 ∩ 呼出者の認可scope ∩ capability適合 ∩ runtime可用性」で決める。指定Agentが不在・利用不能でも別Agentへfallbackしない。
- 保存時の割当可能集合（kind許可・個別制限・認可）と、今すぐ着手可能な集合（さらにcapabilityとruntime可用性を満たすもの）を区別する。Midoriが一時offlineでも、ownerが計画を受理できるならMidori担当の着手待ちとして保存する。別Agentへ変更せず、開始時に可用性を再検査する。未登録Agentの指定や許可集合外の担当指定は、一時offlineと区別して拒否する。
- kind IDは表示名やcaller自己申告でなく、owner登録された実処理／Skillとの対応で検証する。小説作成を`movie.catalog.fetch`として送る迂回を拒否する。自由記述だけから種類を確定できない場合は、generic／allへfallbackせず分類不足を返す。
- 作成者、実担当、許可候補集合、委譲権限を別々に記録・表示する。「誰でも実行可能」は一件の仕事を全Agentへ複製する意味ではない。自動割当は許可集合から一人を選ぶ。Agentは自分を既定担当とし、自分への割当が許可外なら拒否する。他Agentへの割当は既存の委譲権限がある場合に限る。未割当候補を各Agentの「自分の残タスク」に含めない。
- 登録／追加／割当変更／実行開始／resume／retry／委譲のownerは、処理時点の有効policy revisionを再検証し、native receipt／runにkindと`policy_ref`・revisionを結び付ける。policy確認とadmissionは同じ境界でrevisionをbindし、保存競合中のrevision変更はconflictとして再評価する。過去の成功記録はpolicy変更で書き換えない。
- policy変更は以後の新規開始・resume・retry・委譲admissionへ適用する。すでに開始済みのRunは開始時policy revisionで継続し、policy変更だけで自動停止・再割当しない。即時停止は既存ownerのcancel capabilityによる明示操作に限る。既存の認証・Tool policy失効契約は別に適用する。
- COREの全ownerとTaskCenterは同じCORE policy resolverを使い、種別policyを複製しない。編集はユーザーの管理権限に限定し、正規policy ownerのwrite経路で競合・監査・有効revision／反映状態を管理する。通常Agentは参照のみで許可集合を拡大できない。追加画面では種類、許可候補と根拠、選択された実担当を区別して示し、タスク管理の日常画面から設定へ辿れる。

### 3.6 全タスク共通の時間項目

全てのタスクに同じ`timing`項目群を設ける。時間設定のあるタスクだけに後付けする方式にはしない。タスク追加、詳細表示、Agent API、引受・実行判定で同じ意味を使い、必要な条件だけ値を設定する。

| 共通項目 | 提案field | 内容と「指定なし」の意味 |
|---|---|---|
| 基準timezone | `timezone` | 日時・時刻・時間帯の解釈元。現地時刻や繰り返し条件があれば必須。時刻条件がなければ適用なしにできる |
| 実行予定 | `scheduled_start_at` | この仕事／実行回を開始したい日時。指定なしなら時刻を理由に開始を待たせない |
| 開始可能時刻 | `not_before` | この時刻より前には開始できない。指定なしなら追加の下限なし |
| 実行可能時間帯 | `allowed_windows` | 夜間のみ等の許可された時間帯。指定なしならこの項目による追加制限なし |
| 期限 | `deadline_at` | 完了目標・締切。実行予定や開始時刻と区別し、指定なしなら締切未設定 |
| 繰り返し | `recurrence` | 毎日、曜日、間隔、複数の開催時刻など。なしなら時間指定だけを理由に次回を自動生成しない |
| 想定所要時間 | `estimated_duration_seconds` | 計画の目安。指定なしなら見積りなし。指定しただけで強制終了deadlineに変換しない |

上記は共通契約として追加するfield案で、現行の全ownerに存在するという意味ではない。各fieldは「指定済み」「指定なし／適用なし」「未確認」「owner未対応」を区別する。APIは項目そのものを省略して区別を失わせず、値と状態を返す。新規追加で不要な条件は検証後に「指定なし」として保存し、既存データの欠落・読取失敗を「指定なし」へ推測変換しない。

時間項目の正本は仕事・予定を所有する既存ownerに置く。既存fieldと対応する場合は参照・投影し、不足するfieldだけそのownerのrecordへ追加する。TaskCenter専用の時間設定ファイル、第二のschedule、mirror DBは作らない。定義の繰り返し条件と各回の実行予定はownerが関連付け、各回に別々の編集可能なscheduleを複製しない。

実際の開始・完了、次回予定、retry予定は実行記録から投影する別の時間項目とする。予定時刻を過ぎただけで実行済みにせず、完了時刻の不在を期限なしと解釈しない。計画ownerからTask／Runへの引渡しでは、時間条件の参照とrevisionを既存handoffに結び付け、独立した変更正本にしない。

- 時刻条件が全て指定なしでも、担当・許可・依存条件が整った仕事は追加できる。未割当なら引受候補になり、担当済みなら既存の着手経路へ進む。時間指定なしは停止や設定漏れを意味しないが、無制限な即時実行・自動反復も意味しない。
- 定時の仕事は同じ追加・割当・claim経路を使い、実行予定・開始可能時刻・時間帯をownerが確認する。未来の仕事を予約する権限と、今すぐ着手できる候補の公開は分ける。
- 完了後に新しい入力event等で再発する仕事は、既存ownerの明示的な発火条件と実行回identityを使う。「指定なし」だけから反復を補わない。
- 引受直前と実行開始時に有効な時間条件・revisionを再確認する。時間帯や期限の変更と引受・開始が競合した場合は、ownerの同じadmission境界で再判定し、古い条件で開始しない。
- 実行予定が期限より後、開始可能時刻が期限より後、必要なtimezone欠落、不正な繰り返しは保存前に拒否する。期限超過の扱いはownerの契約で明示し、設定だけで実行中Runを強制終了しない。
- 「追加の時間制限なし」は、既存ownerの夜間制作gateやforeground policy、安全制約を解除しない。画面は個別指定とowner由来の有効制限を分けて示す。

| タスク例 | 共通時間項目の設定例 | 実行候補・参加者 |
|---|---|---|
| 映画情報の取得 | 実行予定・繰り返しは指定なし。必要なら期限のみ指定 | 種類policyを満たすAgentが引受 |
| 小説の執筆 | 実行予定なし、必要なら期限と想定所要時間を指定 | 種類policyがMidori限定ならMidori |
| 全員の定時報告会 | timezone=Asia/Tokyo、毎日08:00・12:00・17:00を繰り返しに設定 | 進行責任者一人、参加者8人。詳細は9.1 |

報告会の設定例は、既存の提案節`heartbeat.routine.daily_report_meetings`をownerが共通時間項目へ投影するものであり、同じ開催時刻を別の台帳へ手入力し直す意味ではない。

## 4. Agentの残タスクと未割当仕事の引受

### 4.1 自分の残タスク

Agentの既定照会は`assignee=self`、`view=remaining`とする。selfは認証されたAgent identityから解決する。作成した仕事の一覧と、自分が担当する仕事の一覧を分ける。

- 担当の正本はTask／RunやGoal等のownerが返す有効割当である。Task.OwnerIDを認証userの所有scopeへ流用しない。
- 自分に割り当てられた未完了の仕事だけを返す。再割当後は旧担当者の一覧から外し、新担当者へ反映する。
- blocked／paused／開始待ちも残す。「今着手できるもの」と「残っているもの」は別filterにする。
- 複数RunがあるTaskの現在担当、共有作業、委譲後の親責任はownerの規則で決定する。
- 他Agentや他userの仕事は、query条件ではなくサーバ側認可で制限する。userの「すべて」も閲覧権限内に限る。

Agentは毎回全ログを読み直さず、ownerの索引付き・bounded APIで必要な残タスクと次の行動を取得する。確認API自体は自動着手しない。着手は既存のowner実行経路とadmissionで行う。

### 4.2 実行可能な未割当候補

- Agent用の候補照会は`view=claimable`、`assignee=unassigned`とし、認証されたselfに許可された候補だけを返す。候補集合はkind policy、個別record制限、認可scope、capability、runtime可用性を現在値で交差し、依存条件と予定時刻を満たすowner native record上の未着手・未割当仕事に限る。
- 候補の粒度はkindや一覧行ではなくownerの一つの実行対象native recordとする。定期処理の場合はownerが各occurrenceに安定IDを付けている場合だけ対象にできる。ownerがoccurrence IDを持てない種類はclaim未対応とし、繰り返し定義そのものを奪取可能にしない。
- 候補取得は読取専用で、予約・担当変更・実行開始を行わない。表示後に状態やpolicyが変わり得るため、引受時にownerが全条件とrevisionを再検証する。
- 「未割当で保存済み」はどのAgentの`self/remaining`にも含めず、readyで権限を満たす間だけ`claimable`に出す。種類policyがMidori限定なら候補もMidoriだけに見える。
- 繰り返し定義、まだ実体化していない予定回、Atlasの未採用Candidate、単なるeventを候補にしない。ownerが未着手の実仕事として永続受理したものだけを対象にする。

### 4.3 原子的な引受

- 提案APIは`POST /api/v1/task-center/claims`とし、要求にはowner、native record ID、`expected_revision`、policy revision、idempotency keyを含める。実Actorは認証から固定し、要求本文のactor／assigneeで変更できない。
- ownerは永続transaction内で、対象が未割当・非終端・未着手のclaimable仕事であること、依存／予定条件、現policy、個別制限、caller scope、capabilityを再検証する。条件付き更新（CAS）でassigneeをselfにし、`assignment_epoch`／record revisionとclaim受理receiptを同じtransactionで保存する。
- 同じ仕事の競合要求は一件だけ成功する。他の要求は個人情報や割当先を漏らさず`409 already_claimed`または`409 conflict`を返す。同じAgentの異なるkeyからの同時要求も二重成功させない。
- 同一key・同一payloadの再送は同じreceiptを返し、同一key・異なるpayloadはconflictにする。claim結果はownerとkeyで`GET /api/v1/task-center/claim`から照会できる。
- 排他の正本はownerの永続状態とし、TaskCenter、SSE、cache、各Agent memoryのlockに依存しない。複数host／processにまたがる全割当経路を同じowner admissionで直列化する。手動割当、自動割当、委譲、Agent claimも同じnative recordとepochを使ってこの経路を通す。
- 引受が永続確定した後だけ仕事をassignee=selfの残タスクへ移す。claimはTask／Runの作成・開始・完了を意味せず、claim時にRunなしTaskを別途作らない。開始時は既存Task admissionとhandoff idempotencyを使い、`assignment_epoch`をnative recordからhandoff／Taskへbindする。古いepochの開始・変更要求は拒否する。
- slot不足時は担当を保持して着手待ちにする。枠不足を理由に自動releaseや別Agentへの再割当をしない。

### 4.4 回復と再割当

- 初版では引受後の担当は期限だけで自動解放しない永続割当とする。Agent断、timeout、再起動は引受失効や他Agentへの引渡し根拠にならない。claim応答消失は同じkeyで照会し、結果不明またはowner unreachable中はunknownのまま保持し、実行開始も再claimもしない。
- 明示release／reassignは既存ownerの権限でのみ可能とし、現在の`assignment_epoch`をCAS条件にする。成功時に開始gateを閉じてepochを更新し、旧Agentの遅延要求を失効させる。旧epochのRun状態が未確認、またはhandoff pending／結果不明／active Runがある間はreleaseを拒否する。確定済みの終端履歴が存在すること自体は拒否理由にしない。
- 計画ownerは開始可能状態からTaskへの送信前に「handoff準備中」を永続確保する。release／再割当との競合はownerの同一排他境界で一方だけを成立させ、未確定handoff中に次Agentへ候補を渡さない。
- release後に旧start要求が遅れて到着しても開始できないよう、実行owner側で旧epochの受付を永続closeするか、Task admission時に計画ownerのcurrent epochを権威的に検証する。Run検索で該当Runが見つからないだけでは未実行確定にしない。
- 旧Runがある場合はownerが停止と終端を確認するか、Run未開始を権威的に確定した後だけ再割当する。timeoutだけを未開始・停止済みの証拠にしない。再割当時はepochを更新し、旧要求を拒否する。外部副作用のexactly-onceまではclaim保証として断定しない。

## 5. 共通台帳と正本の分担

台帳は、既存の仕事と日常タスクを辿る「参照索引と読取集約」である。TaskCenterは認証済み入力の受付・振分け・検索集約、各ownerは検証・保存・実行・完了・再試行を担当する。

| 情報 | 正本 | 共通機能が保持するもの |
|---|---|---|
| 共通時間項目 | 各仕事・予定を所有する既存ownerのrecord／設定 | `timing`への型付き投影とsource revision。共通の第二scheduleを保存しない |
| 単発の仕事の指示・担当・完了条件 | Workstream／Goal等の選定済みowner | native IDとrevisionへの参照 |
| 担当割当、claim receipt、`assignment_epoch`、handoff gate | 対象ownerの同じnative execution record／occurrence | record参照。TaskCenterは割当状態・排他を複製しない |
| 実行Task、Run、Trace、成果物 | canonical Task等の既存owner | 関連ID、ownerが認める完了根拠への参照 |
| 日常処理の有効設定・間隔 | 各機能のruntime config／Scheduler／OS管理 | ownerが解決した有効値の投影 |
| code、Skill、既存指示本文 | 当該機能の既存管理場所 | 正本の種類・所在・revision |
| 画面名・分類・種別metadata | 既存feature／owner登録へ一度追加 | 登録されたdescriptorの集約 |
| kindごとの実行許可上限 | 稼働CORE設定dirの`task-execution-policy.yaml`。CORE共通resolverが`core.yaml`の参照を解決 | `kind_id`とpolicy revision参照。許可集合を再保存しない |

新しい手編集の`tasks.json`や`daily-tasks.json`、タスク履歴DB、共通指示フォルダは作らない。実行入力のrevision付きsnapshotは既存ownerの監査用途に限り、別編集可能な指示正本にしない。

日常タスク種別は安定した`kind_id`で識別する。個別仕事は既存GoalID／ScheduleID／TaskID等を使い、共通の永続TaskIDを再発行しない。参照keyはowner・resource種別・native ID・scopeから作る。actorやhostを無条件にidentityへ追加せず、同じ仕事の複数host観測を二重計上しない。ID移行時の対応はownerが明示する。

## 6. 状態と根拠

「設定が有効」と「仕事が成功した」は分ける。現在の実行と前回の終端結果も分けて表示する。

| 軸 | 表示する内容 |
|---|---|
| 仕事の状態 | 着手待ち、実行中、延期、停止、要対応、完了等。ownerのraw statusと対応表を保持 |
| 日常処理の実装・配備 | 実装済み／未実装／不明、利用可能／未配備／不明 |
| 制御状態 | 有効／無効／停止／未設定／不明。未設定キーは既定値・親設定をownerが解決 |
| 観測状態 | 新しい情報／古い情報／取得不能／観測未対応 |
| 設定反映 | desired revisionとeffective revision。再起動待ちはpending_activation |

実行開始、元event発生、永続終端、最終成功、観測、次回定期予定、retry予定は別の時刻にする。timezoneを表示し、cadenceと猶予はownerごとに定める。履歴保存の上限に達した場合は取得範囲を明示する。

対象0件は正常な`no_work`になり得る。証拠がない場合は未確認、APIやDBが不通なら取得不能とし、無効・未実装・失敗へ推測で変換しない。ownerが定める永続終端記録、Artifact、VaultUpdateLog等を成功の根拠にし、新たな共通receipt形式は要求しない。

再起動で失敗履歴を消さず、EventHub replayの時刻を新しい成功と数えない。旧revisionの成功は履歴として残し、現revisionの健康の根拠にしない。未配備は配備情報、未実装はownerの明示情報に基づき、HTTP 404だけで断定しない。

## 8. APIとAgent用Toolの提案

以下は新設案。既存のcanonical Task API・ID・認証を置換しない。

| 操作 | 共通入口案 | 内容 |
|---|---|---|
| 対応機能の照会 | `GET /api/v1/task-center/capabilities` | 認可済みの追加種別、受付owner、policy revision、許可候補Agentと根拠、入力条件を返す |
| 状況確認 | `GET /api/v1/task-center/items` | `view=remaining/claimable/daily/history`、`assignee=unassigned`、scope、期間、cursorで検索。claimableは読取専用 |
| 未割当仕事の引受 | `POST /api/v1/task-center/claims` | owner/native ID、expected revision、policy revision、idempotency keyを指定し、認証Agent自身がowner admission経由で引き受ける |
| 引受結果の照会 | `GET /api/v1/task-center/claim` | ownerとidempotency keyでclaim receiptを照会。結果不明時に同じkeyで再claimしない |
| 詳細確認 | `GET /api/v1/task-center/item` | 型付きowner/resource/native ID参照で取得 |
| タスク追加 | `POST /api/v1/task-center/requests` | 同じSubmitTaskRequestをuser／Agentから使用 |
| 受理結果の照会 | `GET /api/v1/task-center/request` | 認証scopeとidempotency key、owner参照から照会 |

Agent用Toolは「自分の残タスクを確認」「実行可能な未割当taskを確認」「taskを引き受ける」「タスクを追加」の入口とし、正式なTool ID・metadataは既存capability登録へ一度登録する。Toolの中に別の振分け・完了判定・排他を実装しない。

responseはowner、resource種別、native ID、revision、観測時刻、scope、権限内の担当、共通時間項目`timing`、状態、理由、完了根拠参照、次の行動、次pageを含める。時間指定なしのタスクも同じ`timing`の項目群を返す。source別の部分失敗・取得範囲を返し、取得不能を空一覧の成功へ変換しない。rowの表示用参照を新しい永続TaskIDとして扱わない。

すべての参照は応答直前にも認可する。Agentの自己確認とuserの全体確認は同じquery処理とownerデータを使い、callerに応じた権限を適用する。個人会話、メール原文、credentialを共通snapshotに複写しない。仕事本文は正当な権限のある詳細画面／APIで取得可能とし、一覧やerrorへ無制限に出さない。

| 継続作業 | Backlog runner、Atlas再評価、Workstream heartbeat |
| 収益 | 経済機会発見、日次レポート |
| 品質・運用 | TTS発音チェック、backup、ログ保守、resilience、IdleChat watchdog |
| 個別指示・行動 | HEARTBEAT.md、Agentの日常行動routine |
| 定時会議 | 全員の定時報告会（living主会場、dining接続会場） |

既存の仕事は自動投影し、user／Agentへ再登録を求めない。OS service/timer等を観測できない場合は、そのownerと未確認理由を表示する。起動やSSH接続の自動変更で不足を埋めない。登録済み種別とownerが列挙する予定・仕事を照合し、重複と登録漏れを検出する。

### 9.1 全員の定時報告会

#### 開催時刻と一意性

- 「全員の定時報告会」を一つの日常タスク定義とし、毎日08:00、12:00、17:00にAsia/Tokyoで一occurrenceずつ開催する。各occurrence内に8人の集合、順番報告、悩みへの回答、議事保存を含め、8人が同じ親taskをclaimしない。
- 会議のtimezoneはAsia/Tokyo（JST）を明示し、hostや別ownerのtimezoneへ暗黙変更しない。開催時刻の変更はこの会議設定への明示変更として扱う。
- occurrence identityは安定したSchedule ID、local date、slot、timezoneから作る。同slotの再送や再起動で同一会議を二重生成しない。
- Schedule revisionは会議設定のsnapshotに記録するが、occurrence identityには含めない。時刻設定のrevision更新で同じ08時slotを再作成しない。
- 招集・発言・回答は各occurrence native recordのcheckpointへ順に永続化し、再起動後は確定済みの位置から再開する。

#### 会場と参加者

- livingを主会場、diningを同じ会議の接続会場とし、両方で一つの`meetingID`を共有する。座席は両会場に分けられるが、同時発話はさせない。
- 物理配置だけで相互発言の到達を仮定しない。Worldの既存会話／公開scopeで8名全員が同meetingの発言を受信できる範囲を保証する。
- 実room IDは未確定なら未設定と表示する。既存registryや部屋の現在数からroom IDを推測・作成しない。
- 参加Agentは重複しない8名の登録済みCORE Agentとする。現在のregistry総数から8名を自動選定しない。
- 開催設定の正本は稼働COREの`core.yaml`内に新設する`heartbeat.routine.daily_report_meetings`節とし、時刻・名簿・報告順・room参照・期限を一度だけ定義する。これは未実装の提案keyであり、採用時に8名とroom参照を確定する。CORE Agent routineが会議の進行を所有し、Schedulerは開催通知、Worldは移動・在席・会話到達を所有する。各ownerへ開催設定を複製しない。
- 進行ownerは一つ、親occurrenceの責任Agentも一人とする。Agent議長を置く場合も8名内から選び、9人目を追加しない。
- 8名の発言責務は8つの親task claimを意味しない。同じ親occurrenceを複数Agentがclaimしない。

#### 招集と報告

- ownerはその回の名簿と順番snapshotを固定し、招集後、room移動・在席確認を行ってから発言を始める。
- 各参加者に一人ずつ順番に発言を求め、同時発話は認めない。次の話者へ進む前に、その話者の報告と必要な回答turnを処理する。
- `current`には進行中／完了／blockedとnative task参照、または本人明示の「なし」を記録する。
- `next`には次の予定とnative参照を記録する。未引受の仕事は予定として明記し、予定なし・次は未定も本人の明示で表す。
- `concern`には困りごと、または本人明示の「なし」を記録する。欄欠落や取得失敗を「なし」に読み替えず、本人に代わる報告内容の生成・捏造もしない。
- 不在、到着timeout、既存foreground／policy／安全checkpointにより参加できないAgentは未出席として記録し、報告完了8人に数えない。
- 通常Taskのactive Runを強制終了して会議に参加させない。参加不可は欠席またはpartial理由として残す。

#### 困りごとへの回答と完了

- 各concernには本人以外の参加Agentが同meeting内で少なくとも一件回答する。悩みなしの報告には回答turnを要求しない。未回答なら進行ownerが本人以外の参加者へ順に回答turnを要求し、人の承認待ちにせず設定した期限内で進める。
- 報告／回答turnは`meetingID`、`utteranceID`、actor、`progression_revision`、`sourceTaskRef`に相関させる。回答には`concern_id`、報告Agent、回答Agent、内容を含め、他の悩みへの回答を流用しない。
- 複数回答を許可し、順序を管理する。単なる相槌は回答に数えず、助言、確認質問、具体的支援などの実質内容を求める。
- 発言再送には同じ`utteranceID`を用い、同じ内容を二重保存・再発話しない。Agent runtimeの再入場通知もowner契約上idempotentにする。
- ownerがbounded deadlineで終端を確定した後の遅延発言で会議をreopenしない。時間切れ後に回答turnを無限に要求し続けない。
- 完了条件は8名全員の3項目報告、全concernへの他者回答一件以上、ownerの永続終端記録とする。回答済みは悩みの解決済みを意味しない。
- 欠席、未回答、発言失敗はpartialと理由・未完了項目を残す。owner保存失敗は完了未確定として表示し、再照会で確定するまで永続完了を報告しない。招集・発言・会議全体のbounded deadlineはowner設定で定め、数値は本案で新たに断定しない。
- CORE停止中にslotを過ぎたoccurrenceはmissed／partialとして表示し、3回分を一度にcatch-upせず次のslotへ進む。
- 議事recordと進行checkpointは既存Workstream ownerのArtifact等に保存する連携契約を設け、開催回の更新先を一つにする。必要なfollow-upは既存Goal等のnative参照で管理する。meeting専用DB・指示fileは作らず、悩みを他Agentへ自動担当割当しない。follow-up化は既存ownerの追加・claim契約を通す。
- この案は報告会が実装済み・本番稼働中であることを示さない。

## 10. 初回実装の受入条件と移行

確認だけの画面を完成扱いにしない。初回リリースは次の一連の操作が成立することを必須とする。

1. ユーザーが単発タスクを追加し、ownerの永続受理IDで再取得でき、対象Agentの残タスクに一件だけ表示される。
2. Agentが自分の残タスクを取得し、自分のタスクを追加できる。他者のActor偽装、権限外担当指定、他user情報取得は拒否される。
3. 作成者と担当者が異なる例、再割当、未割当、委譲・親子責任で正しく表示される。
4. 着手待ちの計画がTask／Runへ移り、保存・開始の間や再起動を挟んでも二重実行・二重集計されない。
5. 正常完了で残タスクから外れ、履歴・成果物へ辿れる。失敗・blocked・pausedはownerの責任終端規則どおりに残る。
6. 枠不足、依存未達、保存失敗、完了保存の再試行、応答消失、同じkey再送、同じkeyで内容変更を検証する。
7. 日常タスクは設定・指示の正本へ辿れ、既存成功・失敗・対象0件・無効・未配備・観測不能を区別する。
8. 設定変更と有効値の差、再読込・再起動待ち、古いrevision、EventHub replay、timezone、retry予定を誤表示しない。
9. 部分取得失敗、scope内pagination、複数host、履歴期間制限が件数・根拠とともに分かる。取得不能を成功件数へ含めない。
10. 閲覧GETで実行が起動せず、追加以外の停止・再開・再試行・指示編集は対応ownerの明示capabilityとpolicyだけを使う。
11. `movie.catalog.fetch`を`all_registered`に設定した場合、登録済みCORE Agentが候補になり、一件の仕事は一人にだけ割り当たる。`writing.novel`を`explicit: [midori]`に設定した場合、midoriだけが候補となり、他Agentへの割当・実行は拒否される。他Agentが既存の委譲権限でmidoriを担当として追加することは妨げない。
12. actor未登録・kind未設定・空／不正policy・policy読込不能では全許可にならず、指定Agentのoffline時もfallbackしない。小説作成を映画取得kindとして送る誤分類は拒否し、自由記述からkindを決められない場合は分類不足を返す。個別Goal／Scheduleのsubsetはkind許可を狭められるが広げられない。通常Agentからのpolicy拡大は拒否される。
13. 登録、追加、割当変更、開始、resume、retry、委譲でpolicy revisionを再検査する。revision競合はconflictとなり、開始済みRunは開始時revisionを保持してpolicy変更だけでは停止・再割当されない。個別recordの許可制限、実担当、未割当状態が各Agentの残タスク表示に正しく反映される。
14. owner native recordが未割当を表せる場合だけ「Agentの引受待ち」を受理する。stored unassignedはどのself/remainingにも表示せず、readyな実行対象だけclaimable候補になる。種類policyに従い映画取得は全登録Agent、小説はMidoriだけが候補となる。ownerがoccurrence IDを持たない定期定義は候補にしない。
15. 同じnative execution recordを複数Agent／複数hostから同時claimした場合は一件だけ永続成功し、他は409となる。同じAgentから異なるkeyを同時に送っても二重成功せず、同じkey・同じpayloadの再送だけが同一receiptを返し、payload違いはconflictになる。
16. 候補表示後のpolicy／record revision変更、手動割当とclaim、自動割当／委譲とclaimの競合を検査する。古い候補からの要求は再認可され、claim GETで実行が起動せず、完了済みrecordは候補に戻らない。
17. claim receipt応答消失、Agent停止、owner停止、プロセス再起動後も永続状態から結果を照会できる。timeoutやowner unreachableだけではassignmentを解除せず、unknown中の実行開始・再claimを拒否する。
18. handoff準備とrelease／reassignの競合では一方だけが成立し、pending／結果不明handoffやactive Runがある間はreleaseできない。release後に遅れて届いた旧epochのstartも実行ownerで拒否し、current epoch更新と明示release確認後だけ次Agentがclaimできる。Run未発見だけを未実行証拠としない。未完了の仕事についてownerが再割当を認める場合、旧epochのRunが停止・終端確定済みなら、履歴の存在だけではrelease／reassignを拒否しないケースも検証する。仕事自体が完了・取消済みならclaim候補へ戻さない。
19. 毎日08:00／12:00／17:00（Asia/Tokyo、JST）のslotが一度ずつ作られ、8人の固定名簿・報告順、同一meetingID、living／dining間の発言到達を確認する。Schedule revision変更、通知再送、再起動でも同じlocal date／slotの会議を二重生成しない。
20. 8人が順番にcurrent／next／concernを報告し、次の話者へ進む前に各悩みへ本人以外から一件以上の実質回答が付くことを確認する。複数回答は順序保持し、悩みなしは本人の明示のみ有効、欠落／失敗は未回答として扱う。報告なし・次予定なしも本人が明示した場合だけ有効とする。
21. 欠席、未回答、発言失敗は部分理由と未完了項目を記録し、owner保存失敗時は再照会まで完了未確定として表示する。他の未回答については、他の参加Agentへの回答依頼をboundedに続ける。ユーザー返答待ちや期限後の無限会議を作らず、Core停止中のslotをmissed／partialにして未実施分をまとめてcatch-upしない。
22. checkpointからの再開、同じutteranceIDの再送、deadline確定後の遅延発言を検査し、重複保存・再発話・会議reopenがないことを確認する。共有scope外の個人情報を他の参加者へ出さず、親occurrenceは一つのowner責任Agentだけが持ち、8人の発言を8つの同一task claimにしない。

23. 全タスクに共通時間項目があり、映画取得の時間指定なし、小説の期限だけ指定、報告会の毎日3時刻を同じ追加・照会・割当契約で扱う。指定なし、未確認、未対応を区別し、指定なしを設定漏れ・停止にしない。時間条件の競合、未来候補、期限超過、timezone、時間帯gate、完了後の意図しない自動反復、二重scheduleがないことを検証する。

指定日時・繰り返しの追加は既存ownerの能力を照合して順次提供する。対応がない種類は追加フォームで理由を示し、送信時にも拒否する。すでに存在する日常タスクの確認範囲を、それらの追加対応まで狭めない。

導入は、既存正本への契約反映 → ownerごとの受付・割当・冪等性・照会契約の不足解消 → 共通query／submit／claim → user画面とAgent Tool → 正規owner経由の実測検証の順に行う。既存Taskや予定の全件複製、指示の一括移動、新しい常駐scheduler追加は行わない。

実装後は宣言・呼出側・値の利用先、schema、認証scope、API、関連テストの型・コンパイルを照合し、error 0・warning 0の静的確認を通過してからbuildへ進む。許可された配置後、実user／実Agentによる追加→再取得→残タスク→着手→完了→履歴を確認する。fixture、build、healthだけで完了にしない。

この仕様案の作成・更新は文書に限る。実装・稼働設定変更・本番配備・既存タスクの追加は行わない。
