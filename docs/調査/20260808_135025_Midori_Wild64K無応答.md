## 概要

PORTALとCOREはMidori宛てrequestを正常に受理していたが、Wild64K targetが複数の
`system` messageをHTTP 500 `System message must be at the beginning.`として拒否していた。
Prompt Context Assembly反映時に、従来のSystem message統合処理が削除されたことによる回帰である。

## 調査経緯

### 仮説1: Wild role proxyまたは物理backendが停止している

- **根拠**: COREはLLM Gatewayから`502 TARGET_UNAVAILABLE`を受信し、Gatewayの
  `/v1/status`は`midori_wild.usable=false`、`last_error=target HTTP status 500`だった。
- **検証結果**: 棄却
- **証拠**:
  - Mac LLM hostの`:8084`と`:18084`はTCP接続でき、`/health`と`/v1/models`がHTTP 200だった。
  - role proxyと物理backendの双方へ単一System messageの最小requestを送るとHTTP 200になった。
  - CORE、PORTAL、LLM Gatewayはいずれも`NRestarts=0`で稼働を継続していた。
- **チェックリスト結果**:
  - [x] 確証バイアス: `TARGET_UNAVAILABLE`だけで停止と断定せず、直接healthとcompletionを確認した。
  - [x] 頻度制約: 同じMidori送信が2回連続で失敗しており、一時的な接続断だけでは説明できない。
  - [x] ライフサイクル: request終了後はactive=0へ戻り、queueまたはrelease漏れはなかった。
  - [x] 既存知見: 過去には同じWild64K経路でcompletion成功実績があり、現在状態を再確認した。

### 仮説2: 新しいPrompt Contextのmessage配列をWild chat templateが拒否している

- **根拠**: 失敗したtarget送信Payloadは、3件の`system` messageと会話履歴を含む8 messageだった。
  新規Prompt Context Assembly反映コミット`072ba26`は、System message統合処理を削除し、
  時刻を独立したVariable RuntimeContextの`system` messageとして追加している。
- **検証結果**: 確認
- **証拠**:
  - 本番request `llmreq_630615b8-759c-4e08-863e-1a3d16e840f7`と
    `llmreq_39d46602-e800-457f-b5d8-e6e836a28d12`は113-173msでHTTP 500になった。
  - 同じrole順序を縮小した再現PayloadはHTTP 500
    `System message must be at the beginning.`になった。
  - Systemを前方へ移しても複数Systemのままでは同じHTTP 500になった。
  - Systemを1件へ結合するとHTTP 200になった。
  - 失敗した実Payloadの本文を変えず、Systemだけ1件へ結合したrequestもHTTP 200になり、
    Midoriの応答本文が生成された。
- **チェックリスト結果**:
  - [x] 確証バイアス: 後置Systemだけを原因とせず、複数System、単一System、実Payloadの3条件を比較した。
  - [x] 頻度制約: Wildは複数Systemで毎回失敗し、観測された2回連続失敗と一致する。
  - [x] ライフサイクル: streaming、queue、backend起動状態とは独立して同じ形式エラーを再現した。
  - [x] 既存知見: 過去の成功時に存在したSystem統合処理が`072ba26`で削除された差分と一致する。

### 仮説3: PORTALの宛先選択または結果配信だけが失敗している

- **根拠**: ユーザー観測は「Midoriから応答がない」であり、UI側だけの不具合でも発生し得る。
- **検証結果**: 棄却
- **証拠**:
  - PORTAL `/viewer/send`はHTTP 200で、COREは`recipient=midori`としてjobを開始した。
  - COREは同じjob IDでGatewayの502と`viewer.error`を記録しており、結果配信以前に生成が失敗した。
  - MidoriのPuruPuru assetとrecipient selectionもHTTP 200だった。
- **チェックリスト結果**:
  - [x] 確証バイアス: UI表示だけでなくPORTAL、CORE、Gateway、targetのrequest IDを連結した。
  - [x] 頻度制約: 2つの独立job IDで同じtarget failureを確認した。
  - [x] ライフサイクル: accept、async start、agent start、async error、viewer.errorまで追跡した。
  - [x] 既存知見: PORTALのrecipient固定契約と矛盾する宛先切替は観測されなかった。

## 根本原因

- **原因**: COREがLLM Gatewayへ複数の`system` messageを送り、Wild64Kのchat templateが
  単一の先頭System messageしか受理しないため、targetがHTTP 500を返した。
- **メカニズム**:
  1. WildAgentがCharacter SystemPromptを`GenerateRequest.SystemPrompt`へ設定する。
  2. Recall continuityが別の`system` messageとして追加される。
  3. `WithCurrentJSTTime`がVariable RuntimeContext timeをさらに別の`system` messageとして追加する。
  4. `convertMessages`は`072ba26`以降、これらを統合せずそのままGatewayへ送る。
  5. RenCrow_LLMのopenai-compatible経路もtarget固有のmessage正規化をせず転送する。
  6. Wild role proxyが複数Systemを拒否し、Gatewayが502 `TARGET_UNAVAILABLE`へ正規化する。
- **影響範囲**: 複数Systemを受理しないOpenAI-compatible targetを使用するMidori/Wildと、
  同じ制約を持つ将来のtarget。MioやShiroが現在応答できても互換性が保証されたことにはならない。

また、直近Midori PayloadはCharacter SystemPromptを4ブロックとして型付けせず、Stable RuntimeContextも
含まない。これは無応答の直接原因ではないが、Prompt Context Assemblyの全Agent適用状況として別途
是正対象である。

## 修正案

1. RenCrow_LLMのtarget adapterで、target capabilityに応じたSystem message正規化を行う。
   Wild向けには単一System制約を明示し、Context section順序とdebug metadataを保持したまま
   target wire payloadだけを互換形式へ変換する。
2. COREへ以前の無条件System統合をそのまま戻さない。Gateway受信時の型付きPrompt Contextと
   Viewer監査境界を維持し、backend固有差分はRenCrow_LLM側へ隔離する。
3. 複数System、履歴途中のVariable RuntimeContext、単一System targetを含む契約testを
   RenCrow_COREとRenCrow_LLMの双方へ追加する。
4. CORE `/health`がGateway processのreadyだけでMidoriを`ok`にしないよう、実targetの
   `usable=false`をreadinessまたは詳細healthへ反映する。
5. MioだけでなくShiro、Kuro、MidoriについてもCharacter SystemPrompt、Stable RuntimeContext、
   RecallPack、Variable RuntimeContext、User Messageの型付き順序を検証する。

## 教訓（将来の調査への知見）

- Prompt Contextの意味構造と、各backendが受理できるwire message形式を分離する。
- Gateway processのhealthと、aliasが実際にcompletion可能かを別々に観測する。
- Prompt構造変更はMioだけでなく全Agent aliasに対する実target E2Eで検証する。
- HTTP 500本文をGatewayの一般的な`TARGET_UNAVAILABLE`へ畳み込むだけでは形式エラーを見失うため、
  機密情報を除去したruntime contract errorを診断可能にする。
