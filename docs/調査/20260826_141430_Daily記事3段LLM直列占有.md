## Failure

Daily source briefは同じ記事本文を、翻訳、用語抽出、サマリと見解の3回に分けて
同じWorkerへ直列送信していた。検索が必要な用語では4回目の補足requestも発生した。

## Problem

配備後receiptでは1記事について、翻訳21〜48秒、用語抽出7〜12秒、サマリ8〜14秒を
記録した。本文は各promptへ重複し、記事単位でWorkerを最大約72秒占有した。

## Cause

利用者向け出力を翻訳、用語、要約、見解に分離する仕様を、物理LLM requestまで分離する
必要があると解釈していた。出力責務の分離と推論requestの分離を混同していた。

## Fix

- 本文を1回だけ渡す`記事統合分析`contractへ、翻訳、用語、要約、見解を別fieldで返す。
- 日本語確定本文は`translation_required=false`とし、LLMの翻訳fieldを採用せず決定的に
  原文を投影する。
- 外部本文が必要と判定された用語だけ、検索、本文取得、補足LLMを後段へ残す。
- source read、検索、状態更新、validation、retry、receiptはBoundaryのまま維持する。

## Invariant

- 1記事の初期semantic requestは1回だけ。
- 翻訳、用語、summary、perspectiveは別fieldでschema検証する。
- 日本語確定はLLM出力で上書きしない。
- 外部検索は`needs_lookup=true`の用語だけで、snippetを根拠にしない。
- foreground Chatのpreemptionと同じWorker canonical routeを維持する。

## Tests

統合分析と用語補足が必要なfixtureはLLM 2回、検索不要なら1回で完了する。統合分析の
欠落field、日本語以外の不正翻訳、index重複、非日本語summaryを拒否する。foreground
cancel後は記事を失わず統合分析1回だけを再実行する。
