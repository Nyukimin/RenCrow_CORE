# Failure

`input_audio`の`session.commit`後、Viewerへ返る`llm.delta`／`llm.final`に、受付ownerが確定した
`trace_id`、`job_id`、`message_id`が含まれず、Canonical Eventの受付・応答とViewer表示を同じreceiptで
追跡できなかった。

# Problem

LLM resultのraw本文をそのまま投影し、`ProcessVoiceDirect`を非同期goroutineで後から呼び出していた。
初回token metricも別Jobで`NotifyVoiceDirectFirstToken`へ記録され、owner finalizationの失敗が
利用者への成功表示を止めなかった。

# Cause

input_audio bridgeがLLM Gatewayのraw resultとCORE ownerの同期appendを別lifecycleとして扱い、
`ProcessVoiceDirect`の戻り値とowner確定本文をViewer eventへ伝播していなかった。JobIDからTraceIDを推測する旧経路を
残すと、CanonicalなTraceの一意性も検証できない。

# Lesson

音声入力の成功境界は`session.ready`やLLM応答の受信ではなく、既存ownerの
`ProcessVoiceDirect`がCanonical Event appendを完了して有効なreceipt identityを返した時点である。
クライアント本文はraw LLM resultではなく、ownerが返した`ProcessMessageResponse.Response`をtrimした値であり、
空なら成功投影してはならない。CanonicalなID契約の詳細は[Identity Canonical仕様](../architecture/identity/IDENTITY_CANONICAL.md)の
Step 02配備契約とVoice Input Triggerを参照し、ここで再定義しない。

# Invariant

`session.commit`からのinput_audio処理は、LLM result取得、同期`ProcessVoiceDirect`、返却された
Canonical `trace_id`／Job parser検証／Canonical `message_id`検証を行い、owner responseをtrimする順に進む。
検証成功後だけ同じ`ProcessMessageResponse`の3 IDと`Response`を`llm.delta`と`llm.final`へ投影し、
`trace_id != job_id`を維持する。owner error、不正・欠落identity、空responseでは
`VOICE_RESULT_PUBLISH_FAILED`を返し、成功`llm.final`を送らない。

# Enforcement

input_audio bridgeは`ProcessVoiceDirect`を同期呼出しし、別Jobの`NotifyVoiceDirectFirstToken`と
非同期finalize goroutineを使わない。`FirstTokenAt`は同一requestへ設定し、ownerがPublisher Job／Trace
でmetricを発行できるようにする。owner boundaryではutterance、返却ID、owner確定responseの長さを
長さ制限付きでlogする。

# Tests

blocking fakeでowner完了前のevent不在を検査し、完了後のdelta／finalがowner確定responseと3 IDすべて一致すること、
`NotifyVoiceDirectFirstToken`が0回でrequestの`FirstTokenAt`が非zeroであることを検査する。owner error、
invalid／missing identity、TraceIDとJobIDの衝突、空owner responseはtyped `VOICE_RESULT_PUBLISH_FAILED`
とし、成功finalがないことを検査する。raw structured LLM resultとowner responseの分離も検査する。
既存のGateway-only routeとno-thinking契約は回帰検査で維持する。
音声transcriptおよびsession user rowの欠落は本修正の対象外であり、このunitでは変更しない。
