# 調査 — Verification現行E2E再検証

status: resolved

symptom: ID統一Step 02 Gate 6でVerificationがHTTP 503だった
frequency: 2026-08-30の旧production状態では毎回。2026-08-31の現行runtimeでは再現せず
inputs: active config、systemd journal、Viewer API、Canonical Event Store snapshot
related: `20260830_Verification_production_policy_failure.md`

## 概要

旧HTTP 503は既知のactive policy欠落であり、現行productionでは修正済みだった。
active pipelineが実Actor応答からreportを保存し、同じJobの`verification.report`を
Canonical Event Storeへ同一Traceで発行し、Viewer recent／summaryがHTTP 200で返した。

## 調査経緯

### 仮説1: active configの`verification.enabled=false`が現在も503を発生させる

- **根拠**: 2026-08-30のcutover receiptではsummaryがHTTP 503だった。
- **検証結果**: 棄却。
- **証拠**:
  - active configは`enabled: true`、`mode: dry_run`、`default_level: low`。
  - 起動logはpipelineとMessageOrchestratorの統合を記録した。
  - `/viewer/verification/summary`はHTTP 200だった。
- **チェックリスト結果**:
  - 確証バイアス: 旧receiptだけをcurrent stateとみなさずactive configとlive APIで反証した。
  - 頻度制約: 旧runtimeでは毎回、現行runtimeでは再現しないため時間境界と一致する。
  - ライフサイクル: config load、store構築、pipeline統合、report保存、Viewer readまで確認した。
  - 既存知見: 既存Failure Knowledgeの原因と矛盾せず、修正後状態を確認した。

### 仮説2: enabledでもowner storeまたはruntime prerequisiteが欠けて別の503になる

- **根拠**: enabledでもreport store生成失敗時はViewer handlerがunavailableになる。
- **検証結果**: 棄却。
- **証拠**:
  - durable report pathは`/srv/rencrow/db/core/reports/verification_report.jsonl`。
  - Vision実Actor Job `20260831-095008-748db503`についてreport
    `verify_20260831-095008-748db503`が保存された。
  - Viewer recentとsummaryは同じreport storeをHTTP 200で読めた。
- **チェックリスト結果**:
  - 確証バイアス: healthやconfigだけでなく実reportとViewer readを確認した。
  - 頻度制約: 同一runtime generationで複数reportが継続生成されている。
  - ライフサイクル: store openからwrite、read、projectionまで欠落はない。
  - 既存知見: backup境界内の絶対pathという既存Invariantに一致する。

### 仮説3: summary endpointはGate 6の正規Verification結果を証明しない

- **根拠**: summary単体は集計projectionであり、実応答由来reportの生成を証明できない。
- **検証結果**: 棄却。summary単体では不足するが、実Actor Jobとの相関Evidenceが揃った。
- **証拠**:
  - 同じVision実Actor Jobのrecent reportが存在する。
  - Canonical Event Storeに同じJobの`verification.report`があり、Vision requestの
    Canonical Trace `trc_01a05739-e916-74e2-8c92-cc9c9d58bfbd`を保持した。
  - reportの`status=not_checked`は`skip_reason=no factual claims`による正規のlow-level結果で、
    pipelineまたはstoreのunavailableではない。
- **チェックリスト結果**:
  - 確証バイアス: HTTP 200だけを成功扱いせずJob、report、Event、Traceを照合した。
  - 頻度制約: 対象実Actor request一件に対する一件のreportである。
  - ライフサイクル: request、Agent結果、Verification、Event append、Viewer projectionを追跡した。
  - 既存知見: 既存調査が要求したactive policy、durable store、実応答、Viewer receiptの鎖と一致する。

## 根本原因

- **原因**: 現行不具合ではなく、2026-08-30時点のactive production configにVerification sectionが
  欠落していた旧状態をcurrent stateへ持ち越して判定していた。
- **メカニズム**: disabled policyではunavailable handlerがHTTP 503を返す。現行configでは
  `buildVerificationRuntime`がstoreとpipelineを構築し、Viewerをread handlerへ接続する。
- **影響範囲**: 古いfull-check receiptをcurrent runtimeの代用Evidenceにすると、修正済み境界を
  未達として誤分類する。

## 修正案

1. codeまたはconfigは変更しない。
2. Gate判定はactive config、現行service generation、実Actor Job、report、Canonical Event、
   Viewer responseを同じ時点のEvidence chainとして取得する。
3. 旧503 receiptは履歴として保持し、current resultへ上書きしない。

## 教訓（将来の調査への知見）

- policy依存機能の未達判定は、過去receiptではなくactive generationのEvidenceで更新する。
- typed 503もHTTP 200も単独では機能E2E証拠にならない。実Actor Jobからdurable report、
  Canonical Event、Viewer projectionまで相関させる。
- `not_checked`はunavailableと同義ではない。trigger policyとskip reasonを保持して判定する。
