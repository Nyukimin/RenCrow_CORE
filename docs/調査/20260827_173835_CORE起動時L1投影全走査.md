## 概要

COREの正規外部DB配置は維持したまま、起動時のL1 schema初期化が投影済みでも
1.63 GBの`l1_memory_event`を全走査していたことを特定した。投影表の存在を先に
判定し、空の場合だけ同一transaction内でbackfillするsource修正と回帰testを追加した。

## 調査経緯

### 仮説1: L1 schema初期化が投影済みでも元表を走査する

- **根拠**: 最新起動ではTool／MCP初期化からChatGPT reconcile完了まで169.7秒あり、同区間で`NewL1SQLiteStore`が同期実行されていた。
- **検証結果**: 確認
- **証拠**:
  - productionの`l1_memory.db`は約1.63 GB、`l1_memory_event`は76,594件、投影表とFTSは各22,219件だった。
  - 旧SQLのquery planは、非空投影を確認するscalar subqueryと同時に`l1_memory_event` scanを選択した。
  - 旧条件相当のread-only queryは30秒を超え、明示的な先行存在判定は0.01秒未満だった。
  - 旧backfillはschema batch内に埋め込まれ、起動ごとに実行されていた。
- **チェックリスト結果**:
  - 確証バイアス: USB配置、ChatGPT reconcile、LLM接続を別仮説として反証した。
  - 頻度制約: 複数世代で約3分の起動を再現し、単発I/O障害としなかった。
  - ライフサイクル: process開始、依存初期化、listener bind、readinessまで追跡した。
  - 既存知見: 外部HDDをKnowledge等DBの正規配置とする現行構成を維持した。

### 仮説2: ChatGPT startup reconcileが主因である

- **根拠**: 遅延区間の直後にreconcile完了logが出ていた。
- **検証結果**: 棄却
- **証拠**:
  - ledgerは12行で、同じrow列挙のread-only queryは0.01秒未満だった。
  - source上もstage namespaceとledgerだけを対象とし、1.63 GB元表を走査しない。
- **チェックリスト結果**:
  - 確証バイアス: logの隣接だけで原因としなかった。
  - 頻度制約: ledger件数と約170秒の反復が整合しなかった。
  - ライフサイクル: L1 store生成とreconcileを別phaseとして扱った。
  - 既存知見: ChatGPT importのprovenance／fail-closed契約は変更しない。

### 仮説3: 外部HDD配置自体が誤りである

- **根拠**: DB媒体の実リンクはUSB 2.0だった。
- **検証結果**: 棄却
- **証拠**:
  - CORE module実行体は内蔵媒体、Knowledge等DBとbackupは外部HDDという正規構成である。
  - USB 2.0は不要な全走査の時間を増幅するが、配置変更は本件の修正条件ではない。
- **チェックリスト結果**:
  - 確証バイアス: 媒体速度と配置契約を分離した。
  - 頻度制約: 同じ不要scanが毎起動で成立する実装と一致した。
  - ライフサイクル: DB owner／sourceとbackup destinationを混同しなかった。
  - 既存知見: ユーザー訂正を現行制約へ昇格した。

## 根本原因

- **原因**: backfill要否の判定を全表scanと同じSQLの末尾へ置き、SQLite optimizerの評価順に依存した。
- **メカニズム**: 投影済みでも元表scanとJSON評価が起動同期経路で発生し、listener公開を遅らせた。
- **影響範囲**: `NewL1SQLiteStore`を使うCORE起動とowner CLI。外部DB配置、ChatGPT ledger、LLM routeは変更対象外である。

## 修正案

1. 同一transaction内で投影表の非空を先に判定する。
2. 空の場合だけ既存backfill SQLを実行する。
3. 非空投影かつ元表不存在でも成功する実SQLite testで、元表非参照を機械的に強制する。
4. 固定phase名と`elapsed_ms`をjournalへ出し、listener bindと総起動時間を区別する。

## 教訓（将来の調査への知見）

- `NOT EXISTS`を同じSQLへ追加しただけでは、高コスト側より先に評価される保証にならない。
- 一回限りのbackfillはmigration markerまたは明示的な先行gateで拘束し、通常起動のquery planへ残さない。
- 正規の低速媒体配置と、不要な全走査という実装問題を混同しない。
- source修正後もproduction build／install／restart後の実測までは運用達成として扱わない。
