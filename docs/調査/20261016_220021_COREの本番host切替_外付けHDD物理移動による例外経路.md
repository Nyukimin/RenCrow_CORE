## 概要

COREの本番を、旧本番hostから別hostへ移した。DB用とバックアップ用の外付けHDD 2台を物理的に付け替え、`/srv/rencrow/db`と`/srv/rencrow/backup`のpathは変えていない。HOME側のstate、バイナリ、設定、unit、Redis、Qdrant、Giteaは別途複製した。

Workspaceの移行契約（Migration Owner Hook v1）では、COREのState export／importはまだ実装されておらず、hookは`config_validate`と`state_describe`だけである（`docs/06_Public_API仕様.md`）。このため、契約が定める完全な復元は使えず、本件は**契約の例外経路**（HDDの物理移動と手動複製）で行った。

移行後、CORE、PORTAL、Gateway、embed、vision、image、trade、games-observer、2つのcatalog、Gitea、Redis、Qdrantは新hostで動く。CORE経由のチャットは通った。一方、旧本番hostにだけあった環境依存が複数あり、起動して初めて判明した（「事実」の6〜10）。

## 発生条件

- 旧本番hostのUSB 3.0が故障し、全外付けディスクがUSB 2.0（480Mbps）で接続されていた。バックアップ用ディスクの交換もできなかった。
- ユーザーの指示（2026-10-16）で、新hostをCOREのメイン機にすると決定した。
- 移行は、`rencrow migration-hook`がStateの出力・取込みを持たない現状では、正規経路で完了できない。

## 手順

1. 事前（停止なし）
   - 新hostへ、RenCrowの全repositoryをcloneまたはfast-forwardで同期した。
   - Dockerを導入し、Redis 7.4.8とQdrant 1.17.0を起動した。Qdrantは、旧本番hostの9コレクションをsnapshot APIで複製し、件数・ベクトル設定・先頭5点の一致を確認した。Giteaは、データを複製して起動と停止を試した。
   - 旧本番hostの稼働中のバイナリ34個、lib、unitを、新hostの別ディレクトリへ複製した（sha256の全件一致を確認）。設定、state、workspace、x_bookmarks、modelsの約4.6GBを、live DBを除いてrsyncした。
   - ステージした設定で`rencrow health`を実行し、6項目中5項目がokだった（visionは未起動のため）。
2. 停止窓（2026-10-16 21:00〜21:30 JST）
   - 旧本番hostの移行対象のtimerとserviceを依存の外側から順に停止した（unitはenableのまま）。
   - 停止後に、live DBとwal／shmを含むデータを最終rsyncした。Qdrantを再複製し（9コレクションの件数が一致）、Giteaを最終コピーした。
   - HDD 2台を旧本番hostから外して新hostのUSB 3ポートへ挿し、`/srv/rencrow/db`をmountした（fstabの追加とDB用の`mount`は利用者がsudoで実施。バックアップ用は`user`オプションで通常権限でmountした）。
   - バイナリ、lib、設定、unitを本番の場所へ配置した。新host側で上書きされるファイルは、全て退避ディレクトリへ保存した。
   - 起動順は、embed、Gateway、vision、image、CORE、PORTAL、trade／games／catalog、Giteaとした。
3. 後続
   - 新hostのserviceとtimerをenableした。旧本番hostの移行対象はdisableし、RedisとQdrantのコンテナを停止して`--restart=no`にした（二重起動の防止。データは残してある）。
   - 音声系hostへのSSHトンネル3本を、接続先の`authorized_keys`の送信元制限（`from=`）に新hostを加えて起動した（利用者の承認を得て実施）。
   - Tailscale serveを、旧本番hostと同じ3つの割り当てで新hostに設定した（利用者が`tailscale set --operator`を実施）。
   - X BookmarkのログインをAuth Bridge（一回限りの暗号化cookie移植）で取り込んだ。

## 事実

1. 起動後の検証: `rencrow health`は6項目全てok（Gatewayの5 alias＋vision）。`rencrow-storage-backup check`は、マウント、Redis、Qdrantが使えること、dry-runの完了を確認した。
2. CORE経由のチャット（`rencrowctl chat`）: Mioから Shiroへの委譲は46秒、Shiroへの直接は19秒（12.1 tok/s）、Midoriは15秒。
3. Qdrantの9コレクションは、旧本番hostと件数・ベクトル設定・先頭5点が一致した（停止後の最終複製の後に再確認）。
4. 旧本番hostの`rencrow`バイナリは、別作業者の反映で、こちらの配備した版から更新されていた。移行用に複製した版と切替直前の版は、主要10バイナリのsha256が一致した。別作業者が配備を続ける環境では、切替直前にsha256を再照合する手順が必要である。
5. 新host側の既存ファイルと衝突したのは、`config/llm.json`、`rencrow-llm`バイナリの旧版、`~/.local/share/rencrow`配下の4ファイル、`rencrow-log-rotate`のunit（新host自身のGPU用）である。前3つは退避して置換し、log-rotateは別名（`rencrow-core-log-rotate`）でCORE用を導入した。
6. Gatewayが起動しなかった。設定`llms.kuro_codex.command`が`~/.nvm/versions/node/v22.22.0/bin/codex`を要求し、存在しないと`invalid config ... cannot be resolved`で起動を拒否する。同じpathへnodeの環境（約1.8GB、codex 0.162.1を含む）を複製して解消した。新hostの標準のcodexは0.153.4で版が異なる。
7. visionが`provider_token_file must reference a readable non-empty regular file`で起動しなかった。`~/.config/rencrow/`配下のノードトークンとTTSのowner tokenが新hostに無かった。同ディレクトリ（moca用の資格情報を除く）を複製して解消した。
8. SSHトンネルの専用鍵3本は、移行元のhostにしか無かった。鍵を複製しても、接続先の`authorized_keys`が`restrict,port-forwarding,permitopen=...,from="<旧本番hostのaddress>",command="/usr/bin/false"`であるため、新hostからは`Permission denied`だった。接続先で、この3鍵の`from=`へ新hostを加えて解消した（旧TTS用の鍵は変えていない、バックアップあり）。
9. X Bookmarkの収集が、起動時の実行で`exit status 1`になった。原因は2つ。Playwright 1.59.1が使うChromium（revision 1217）が新hostに無かった（複製して解消）。ログインcookieは、Chromiumのプロファイルを複製しても新hostでは無効だった（headedのログインは画面が無く不可）。Auth Bridgeで取り込み、ヘッドレス収集でBookmark 6件を取得できた。
10. portの衝突が2件あった。Gatewayの:8090は、新hostの旧SSHトンネル（旧本番hostのGatewayへの転送）が占有していた。person-related-catalogの:18087は、新hostのCoder（:18087）と同じだった。前者はトンネルを停止してdisableし、後者はunitとcore.yamlの`person_related_catalog.provider_url`を:18797へ変えた。
11. 新hostのユーザーsystemdマネージャは、dockerグループの追加より前に起動しており、unitから`docker`を呼ぶと`permission denied ... docker.sock`で失敗した。Giteaのunitは`sg docker -c`で包んで起動した。
12. X Bookmarkの収集テストで、既知IDが7579から7584へ進んだ。CORE定期の収集で5件を取りこぼすため、旧本番hostの状態ファイルに戻した。
13. 旧本番hostのTailscale serveは「tailnet only」で、funnelは無効だった。過去7日間のCOREログに`/webhook/line`へのアクセスは0件だった。

## 結論

- 事実: CORE本番は新hostで稼働し、health、チャット、backupのdry-run、Qdrantの照合を確認した。全unitをenableした。
- 事実: 本件はWorkspace移行契約の例外経路である。COREのState export／importが未実装であるため、正規の完全移行とは言えない。
- 原因（移行で起きた問題の共通点）: 旧本番hostにだけある環境依存（外部実行ファイルのpath、token、SSH鍵と接続先側の送信元制限、ブラウザの実体、ログインcookie）が、設定検証では列挙されず、起動して初めて判明した。
- 未確認:
  - 音声の実合成・実認識のE2E（トンネルの疎通確認のみ）。
  - CORE定期のX Bookmark収集（起動から6時間後の初回）。
  - 新hostでの毎日03:00 JSTの`rencrow-storage-backup`の初回実行（2026-10-17）。
  - LINE webhookの実到達（LINEコンソール側の設定は未確認）。
- 旧本番hostへ残したもの: openclaw-gateway、NTFSの外付けディスク2台、moca用のCIFSマウント。

## 再発防止の候補（未実装）

Failure Knowledgeの形式で、強制が未実装のものを分けて記録する。

- Failure: 移行先で起動してから、不足している実行ファイル、token、SSH鍵、ブラウザの実体が見つかった。
- Problem: 設定の検証が、設定が参照する外部の資源の存在を検査しない。接続先側の許可（`from=`）は、移行元のaddressに固定されている。
- Cause: `config_validate`は設定の構文と整合を見るだけで、設定とunitと環境変数ファイルが参照する絶対pathや資格情報の存在を見ない。
- Lesson: 移行先の本番の設定とunitから絶対pathを抽出し、存在を確認する走査を起動前に行うと、今回の問題の大半（事実の6、7、9）を事前に検出できた。接続先側の許可は、移行元のaddressの制限を移行計画に含める。
- Invariant（候補）: 移行先の起動前に、設定・unit・環境変数ファイルが参照するpathが全て存在する。
- Enforcement: 未実装。今回は手作業の走査スクリプトで代替した（リポジトリには含めていない）。
- Tests: 未実装。

## 調査上の副作用

- CORE経由のチャットのテストで、Mio、Shiro、Midoriへ、疎通確認の短い文を各1件送った（履歴に残る。個人情報は含まない）。
