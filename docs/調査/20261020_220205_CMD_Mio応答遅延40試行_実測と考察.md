- 契約正本：RenCrow_CORE の現行仕様。利用者の受入目標は「ユーザー入力から可視応答まで、Gemma4 の応答生成時間だけを許容する」

## 結論

**最優先の指標は、ユーザーが送信してから最初の応答本文を受け取るまでの時間。** 今回、成功した 38 試行では途中の応答本文がなく、最初に見える本文は最後の `agent.response` だった。CMD の送信から終端までは中央値 **21.167 秒**。Mio の応答生成に対応する Gateway の active generation 区間は中央値 **6.960 秒**、各試行で差し引いた生成以外の区間は中央値 **13.938 秒**だった。CMD 終端時間を応答待ち時間の代理指標とすると、今回の 206 配備状態は「Gemma4 の応答生成時間だけ」という目標から大きく離れている。

**計測上の区別：** 21.167 秒は CMD 終端までの値であり、`agent.response` が CMD に届いて表示された瞬間までの厳密な値ではない。イベント受信から終端までの差は今回の集計では独立に算出していない。次回の改善判定では、送信 → 最初の応答本文表示を直接測る必要がある。

最も大きく確認できた要因は、**スレッド終了時の要約が応答を返す前の commit に同期していること**。終了した 27 試行では commit 中央値 10.698 秒、終了しなかった 11 試行では 0.702 秒だった。終了した全 27 試行で `shiro_worker` の要約 Gateway 呼び出しと ThreadSummary receipt が確認され、要約の Gateway active generation 中央値は 8.137 秒だった。一方、分類 LLM の追加呼び出しは発生時でも中央値 0.217 秒であり、今回の主因ではない。

これは今回の入力列と配備版についての結論である。スレッド終了率 27/38 を通常利用時の発生率として扱わない。

## 計測方法と対象

- `rencrowctl chat --to mio --timings` で、短文 20 件・長文 20 件を交互に、同一セッションへ投入した。並行する読み取り専用 SSE subscriber で正規 `/viewer/events` の計測点を取得した。
- 成功は `agent.response` と CMD 終端が得られた試行。40 件中 38 件成功、2 件失敗。成功分だけを応答時間の分布に含めた。
- Mio 応答の Gateway call は trace ID で、要約 call は session ID と commit 区間で照合した。要約の trace ID は元の応答と異なる。
- Gateway の `generation_ms` は Gateway が観測した active generation 区間であり、Gemma4 の GPU decode 専用時間ではない。以下の「生成以外」は CMD 終端時間から**応答用** Gateway 区間を各試行で差し引いた値で、非 Gemma4 時間の保守的な下限に相当する。各列の中央値同士は加算できない。
- ユーザー体感の正規指標は「CMD で送信確定 → 最初の応答本文が CMD に表示される」。本表の CMD 終端はその代理指標であり、正規指標そのものの集計値ではない。
- この計測中に source 変更、再ビルド、再起動は行っていない。

### 分類呼び出しと失敗

成功 38 件中 18 件には Mio の Gateway 呼び出しが 2 回、20 件には 1 回あった。2 回のケースの最初の分類呼び出しは中央値 **0.217 秒**、範囲 0.203–0.239 秒。その後に応答生成が走っている。1 回のケースは決定的な route で分類呼び出しが省かれたものを含む。206 で「分類と応答生成が常に 1 回に統合済み」とは言えない。

失敗した短文 2 件（試行 8、17）は `viewer.error` で終了し、最終 `agent.response` と L1 receipt はなかった。分類呼び出しはそれぞれ約 0.214/0.241 秒で成功し、その後の Mio 応答 Gateway call が **53.646/54.864 秒**後に失敗した。両方とも queue 0 ms。この 2 件は成功分布から除外した。2/40 という比率は今回のプローブに限り、通常利用の障害率ではない。

## 考察

1. **優先して外すべき待ちは要約の同期実行。** スレッド終了時は応答 Gateway の中央値が終了なしと同程度なのに、commit 中央値が約 10 秒増えている。要約 Gateway の約 8 秒と、その前後の保存・後処理が応答後へ移れば、目標との差の大部分を減らせる可能性がある。ただし移動後も L1/Redis の確定、公開順序、失敗時の再試行・receipt を維持する必要がある。
2. **分類と応答を 1 回にする改善だけでは今回の遅延を解消しない。** 18 件で分類の追加 call が存在するため統合する価値はあるが、観測された分類時間は約 0.2 秒。commit と比較すると効果は限定的である。204 のローカル dirty source にある 1-call 統合や thread follower の応答後処理は、今回測った 206 へ配備済みとは扱わない。
3. **要約を外した後にも約 3.8 秒の中央値と長い尾が残る。** 終了なしの生成以外は中央値 3.764 秒。route 決定や dispatch までの遅れが一部で 5 秒を超える。ただし既存計測点では、Task/Run 保存、イベント追加、TTS などの個々の寄与は確定できない。`lead_agent.started` の EventStore timestamp による前後分割は概算で、単一操作の計測ではない。
4. **失敗 2 件は別の問題。** 分類後の Mio 応答 call が約 54 秒で失敗しており、成功時の同期要約とは異なる。タイムアウトや失敗理由をこの結果だけで断定しない。

## 優先順位の提案

1. 206 の正規 route に、応答公開後の thread follower を配備・検証する。最優先の受入指標として「送信 → 最初の応答本文表示」をスレッド終了の有無別に測り、commit と receipt の維持も確認する。204 のローカル変更をそのまま配備済みの証拠にしない。
2. 残る生成以外の時間について、route decided → dispatch started と commit 残差に owner 境界ごとの計測点を設け、正規経路で繰り返し測る。
3. 分類と応答の 1-call 化を別の差分として評価する。時間差だけでなく route 判定の品質と失敗時挙動を確認する。
4. Mio 応答 call が約 54 秒で失敗した 2 件の原因を、要約遅延とは分けて確認する。

## 未確認・限界

- CMD で `agent.response` の本文が実際に表示された瞬間までの時間、および表示から CMD 終端までの差。21.167 秒は CMD 終端時間の中央値。
- Gemma4 の GPU prefill/decode だけの時間。Gateway active generation はその代理指標であり、利用者の厳密な許容値との一致は未確認。
- 終了なし試行に残る約 3.8 秒、および終了あり commit から要約 Gateway 時間を引いた残差の工程別内訳。
- 短文・長文とスレッド終了率の因果関係。話題を変える合成入力を同一セッションに連続投入したため、短文の終了 17/18、長文の終了 10/20 を通常利用へ一般化できない。
- 2 件の Gateway 応答失敗の確定原因と再現率。
- 204 のローカル変更を 206 に配備した後の改善量。今回の数値は旧 206 配備状態の基準線である。
