# 機能仕様

## 会話とルーティング

通常メッセージの route owner は Mio です。処理順序は、明示 command、Mio の `DecideAction`、rule dictionary、classifier、決定 route の実行です。rule dictionaryは、明白な挨拶に加え、実装、運用、調査、設計などの作業意図を含まない高確度の質問と直接回答要求を `CHAT` に確定できます。描画、物語、文章作成、作文、執筆などの創作依頼は`WILD`へ確定し、Midoriが担当します。サービスの稼働確認やログ調査など作業の可能性が残る入力は、`CHAT` に短絡せずclassifierへ渡します。無効な判断や利用不能な runtime は、契約で定めた failure または CHAT fallback として扱います。

`Chat`は通常text会話と`input_audio`会話でthinkingを使用しません。COREはRenCrow_LLMへのChat requestで`think=false`と`chat_template_kwargs.enable_thinking=false`を設定します。`true`のChat設定は起動時validation errorとします。classifierの分類処理もthinking無効です。`Wild`も同じNoThink policyを使用し、通常WILD routeとMidori宛Chatの両方で`think=false`と`chat_template_kwargs.enable_thinking=false`を設定します。WILD routeは本文deltaをstreamingで受信し、逐次eventを発行してから完成本文を返します。`ChatWorker`は`think=low`、`reasoning_effort=low`、templateの`reasoning_effort=low`へ固定します。`Worker`はRenCrow_LLM側のRole設定を使います。

RenCrow_ASSISTANT、RenCrow_PORTAL、Debug Viewer、CLIの通常会話は`to=mio|shiro|kuro|midori`を受け付けます。明示commandは会話相手の選択より優先されます。選択したruntimeが利用不能な場合、Mioへ黙って切り替えません。

### Midori Chatからの画像生成

Debug ViewerのChatで会話相手にMidoriを選び、利用者が画像または絵の生成を明示した場合、
MidoriのWild Agentが画像生成要求を所有します。通常の文章生成LLMへ画像生成を依頼せず、COREは
`RenCrow_Image`の公開contractだけを呼びます。生成backend、model、checkpoint、workflow、LoRA、
生成parameterは`RenCrow_Image`が所有し、正規経路を
`RenCrow_CORE -> RenCrow_Image -> ForgeNeo / Z-Image`とします。COREまたはViewerからForgeNeoへ
直接接続しません。

生成成功時のMidoriの`agent.response`は、生成済みimage IDとCORE内の
`/viewer/image/result?id=<opaque-image-id>`を含みます。ViewerはこのCORE内部URLだけを画像として
解釈し、同じChat吹き出し内へPNGを表示します。外部URL、`javascript:`、`data:`、任意Markdownの
画像URLは自動読込せず、通常textとして扱います。画像の取得responseは`Content-Type: image/png`、
`X-Content-Type-Options: nosniff`を維持します。

`RenCrow_Image`が無効、未ready、timeout、生成失敗、またはPNG取得不能の場合、COREは失敗境界を
明示し、ForgeNeo直結、別model、ImageGen、placeholder画像へfallbackしません。Midori以外の会話、
画像promptだけの作成依頼、RenCrow_Imageの仕様質問は従来どおりtext会話として扱います。

受け入れ条件は、(1) `to=midori`の画像生成依頼だけがMidoriのWild AgentからRenCrow_Imageを1回
呼ぶこと、(2)生成成功時にMidoriから利用者への最終応答が1回発行されること、(3)同じ吹き出しに
CORE中継PNGが表示されること、(4)外部または不正な画像URLを自動読込しないこと、(5)画像生成失敗を
text生成成功として扱わず正規経路のerrorとして閉じること、(6)Mio、Shiro、Kuroおよび通常の
Midori text会話を変更しないことです。

### 会話IDと処理相関

COREは会話と実行を次の単位で識別します。

| ID | 単位 | 契約 |
| --- | --- | --- |
| `session_id` | 継続する会話 | 複数の入力、応答、Taskを含めてよい |
| `message_id` | 1つの利用者発話またはAgent発話 | `msg_` prefix付きUUIDとして一度だけ生成し、内容編集、再配信、再接続、CORE再起動で変更・再生成しない |
| `turn_index` | session内の表示順 | 順序の補助情報であり、一意性、重複排除、永続参照に使わない |
| `job_id` | 1つの実行単位 | 受付、route、実行、完了またはerrorを結ぶ |
| `trace_id` | 1つの入力から派生する処理全体 | 入力、応答、内部event、logを結び、途中で欠落させない |
| `request_id` | 1つのAgent間作業要求 | delegate、acknowledge、retry、reportで同じ値を維持し、重複実行の判定に使う |

`message_id`を`session_id + turn_index`から組み立ててはなりません。この方式はCORE再起動や複数processで同じ値を再生成できるためです。利用者入力とAgent応答は別のmessageであり、別々の`message_id`を持ちます。同じmessageをSSE再送や保存へ渡す場合は新しいIDを作らず、最初に生成した値を引き継ぎます。TTS eventは対応するmessageが確定済みの場合に同じ`message_id`を引き継ぎ、音声stream開始時点で未確定の場合は`response_id`と`trace_id`で相関します。`request_id`もretry時に再生成せず、同じ要求の重複排除と最終状態の一意な確定に使用します。

現行の通常会話は1入力につき1つのroot jobを作るため、rootの`trace_id`には`job_id`と同じopaque値を使用します。これはfieldの意味を同一化するものではありません。将来1つの入力から複数jobを派生させる場合、各jobは別の`job_id`を持ち、rootの`trace_id`を維持します。

## Worker、Coder、Advisor、Tool

- Worker は決定済み route の実行、状態、結果、side effect、実行policy境界を所有する。
- Coder は設計、差分、提案を返し、外部 side effect の最終責任者にならない。
- Advisor は専門的な助言を返し、採否と実行責任を持たない。
- Tool は明示された capability を実行し、人格、長期記憶、最終意思決定を持たない。

### Chat起点のDurable Store構築

利用者はChatから、今後も保持、検索、集計、更新または他機能から参照したいdata要件を指示できます。
指示に「DB」や特定engine名が含まれることは必須ではありません。Mioは発話を単なるコード生成要求として
直ちにWorkerへ渡さず、継続保存が必要な`StorageRequirement`として正規化します。既存DBのtable追加、
新しいSQLite file、object store、append-only ledger、外部databaseはすべて同じ経路で扱います。

次のように処理結果を区別します。

| 利用者の意図 | `requested_outcome` | 到達可能な終点 |
| --- | --- | --- |
| 現状確認、比較、設計、提案だけを求める | `assess` | 分類結果または`proposed`。repository、Config、runtime dataを変更しない |
| 保存できるようにする、構築、実装、移行、有効化を明示する | `implement` | validatorと実行条件を満たした場合だけ`active` |
| 一時出力、再取得可能なcache、既存Memory commandで足りる | `assess`／`implement` | `ephemeral`／`cache`／`artifact`／`existing_memory`。新しいDurable Storeを作らない |

「この会話を覚えて」のように既存UserMemory commandで意味を満たす指示、単発CSV export、download、
一時集計はDurable Store追加workflowへ昇格させません。反対に、利用者が「新しいDBを作って」と指定しても、
既存store拡張またはartifactで要件を満たせる場合は新しい物理DBを作りません。

#### 入力contract

COREはChat入力から次の`StorageRequirement`を作ります。LLMは曖昧なdata意味の整理を補助できますが、
owner、保存方式、impact class、validator結果を自由文だけで確定しません。

| field | 内容 |
| --- | --- |
| `requirement_id` | 1つのworkflowを識別するopaque ID |
| `dedupe_key` | owner解決後に、正規化したdata purpose、owner、user scope、契約revisionから作る再送検出key |
| `request_id`、`trace_id` | Chat受付から最終結果まで維持する相関ID |
| `requested_by`、`user_scope` | 認証済み利用者と許可されたdata scope |
| `requested_outcome` | `assess`／`implement` |
| `facts_to_store` | 保存する事実。推測したschemaやtable名ではなくdomain上の意味 |
| `source_systems` | 入力元とprovenance。未確定の場合もunknownを明示 |
| `read_patterns`、`write_patterns` | 検索、集計、更新、追記、同時writeの要件 |
| `retention_expectation` | 保持、削除、archiveに関する利用者要件または未指定 |
| `volume_expectation` | 初期量、増加率、最大object sizeの既知情報 |
| `sensitivity_hint` | 個人情報、secret、license、外部公開可否の既知情報 |
| `owner_hint` | 利用者が明示したmodule。最終owner決定を上書きしない |
| `acceptance` | 利用者が確認可能な完了条件 |

分類結果の`storage_class`は`ephemeral`／`cache`／`artifact`／`existing_memory`／`existing_store`／`new_store`の
いずれかに限定します。Chatの公開入口は既存の認証済み会話APIを使い、validatorを迂回する
`create database`専用Public APIや、自由なSQL／pathを受け取るAPIを追加しません。Mioが保存要件を
検出した時点で論理capabilityを`durable_store_change`へ固定し、一般`OPS`／`CODE`処理より先に
StorageRequirement workflowへ渡します。

入力にない技術値をLLMで補完しません。正本仕様、既存Manifest、runtime Config、実測容量から決定できる
項目は証拠付きで補完できます。安全に決定できない必須事実が残る場合、workflowは人の返答待ちを作らず、
不足fieldと影響を示して`blocked`で閉じます。利用者の追加発話は待機artifactを解除する返答ではなく、新しい事実を
持つrequestとして開始します。

#### 標準処理

```text
authenticated Chat request
  -> Mioがrequested_outcomeとStorageRequirementを確定
  -> COREがdomain owner候補と既存store／Memory／artifactを検索
  -> Domain OwnerがStorage Proposalを生成
  -> 決定論的classifierがephemeral／cache／artifact／existing store／new storeを分類
  -> S0／S1／S2 validatorがproposal、Manifest、policy、実path予定を検証
  -> rejectedならreasonを固定し、設計を変えた有限回の新revisionを再検証
  -> assessなら分類結果またはproposedを返して終了
  -> implementかつvalidatedならCoderがschema／migration／Config／backup／test差分を生成
  -> Shiro／Workerがowner module内へ検証済み差分だけを適用
  -> CIとdeployment preflightを実行
  -> versioned migration、provisioning、backup dry-run、scratch restore、integrity、healthを検証
  -> 全条件成功時だけactiveへ昇格
  -> Mioが利用者へ結果と証拠を返す
```

Domain Ownerはdataの意味とwriterを所有します。Mioは会話、目的、完了条件、最終報告を所有します。
Shiroは実行AgentとしてProposalの完全性確認、Coderへの設計依頼、Worker実行、証拠収集を調整します。
Coderはplanとpatchを生成し、migration、provisioning、production接続を直接実行しません。Workerは
`validated`なProposalとManifestが示すowner module、path、change classの範囲だけを実行します。
COREは共通contractとgate、各moduleは自身のschema、migration、backup、restore-checkを所有します。

物理保存先は利用者発話やCoder出力へhard-codeせず、`storage.databases`とmodule Configから解決します。
Ubuntu productionでは`/srv/rencrow/db/<owner-module-subtree>`を基準とし、外付け媒体、mount、root変更は
設定リファレンスの`S2`として扱います。configured rootが未mount、read-only、容量不足、permission不正、
またはbackup rootと同一媒体の場合、repository、`~/.rencrow`、system tempへfallbackせず`blocked`で閉じます。

#### 状態、冪等性、結果

Chat起点workflowはDurable Store lifecycleをそのまま使い、人の返答や許可を待つ状態を
追加しません。各requestは同一処理内または有限revision内で
`completed`／`rejected`／`blocked`を確定し、store lifecycleの現在位置を結果へ含めます。

`dedupe_key`は正規化したdata purpose、owner、user scope、契約revisionから決定論的に生成します。
同じ指示の再送、network再送、CORE再起動後のresumeはこのkeyで既存requirement、proposal、active storeを検索し、
同じDB、table、migrationを重複作成しません。data意味、owner、privacy、retention、recovery等が変わった場合は
既存結果を上書きせず、新しい`proposal_revision`として最初のvalidatorから再評価します。

最終的な`StorageWorkflowResult`は次を持ちます。

| field | 内容 |
| --- | --- |
| `status` | request終端の`completed`／`rejected`／`blocked` |
| `requirement_id`、`trace_id` | 入力と証拠を結ぶID |
| `requested_outcome` | 実行した`assess`／`implement` |
| `storage_class` | 判定した保存方式 |
| `owner_module` | dataとwriterのowner |
| `proposal_id`、`proposal_revision` | 使用したStorage Proposal。不要な分類では空 |
| `store_id` | 新規または再利用する論理store ID。store不要なら空 |
| `change_class` | `S0`／`S1`／`S2`。変更なしなら空 |
| `lifecycle_status` | Durable Store lifecycleの到達位置 |
| `evidence_refs` | validator、migration、integrity、backup、restore-check、healthの参照 |
| `reason_code`、`message` | rejected／blocked理由と利用者向け説明 |

credential、secret、個人data、物理device serialは結果へ含めません。

観測eventは少なくとも`storage.requirement.received`、`storage.owner.resolved`、
`storage.proposal.created`、`storage.proposal.validated`／`storage.proposal.rejected`、
`storage.implementation.started`／`storage.implementation.completed`、
`storage.provision.started`／`storage.provision.completed`、`storage.activated`、`storage.blocked`を
同じ`trace_id`へ記録します。
自由文の「完了」だけを成功証拠にせず、Manifest revision、migration revision、integrity結果、backup ID、
scratch restore結果、healthを機械可読に相関させます。

#### 失敗時契約

- ownerを一意に決められない場合はDBを作らず`blocked`とする。
- ProposalまたはManifestが不完全な場合は`rejected`とし、同じpayloadを再送しない。
- Coder出力がvalidated範囲を越える場合はWorkerが適用前に拒否する。
- migration失敗時は旧storeと旧writerを維持し、空DB作成やschema versionの読飛ばしを行わない。
- provisioning後のbackup、scratch restore、integrity、healthのいずれかが失敗したstoreは`active`にしない。
- Chat接続断やCORE再起動が発生しても、永続証跡から再開し、適用済みmigrationを再実行しない。
- `rejected`の有限revisionで適合案が得られない場合は、理由と試した変更軸を残して`blocked`とする。

#### 受け入れ条件

1. 「今後この情報を蓄積して検索できるようにして」という入力が、`DB`という語なしで
   `StorageRequirement`へ正規化される。
2. 設計・比較だけの入力は`assess`となり、repository、Config、runtime dataを変更しない。
3. 明示的な構築指示も保存方式classifierを迂回せず、既存storeで足りる場合は新DBを作らない。
4. UserMemory、cache、artifactで要件を満たす入力をDurable Store追加へ誤分類しない。
5. owner、writer、user scope、privacy、retention、backup単位が一意に確定するまで実装へ進まない。
6. `validated`前にはDB file、table、directory、mount、credential、production Configを変更しない。
7. Coderが差分を生成してもWorker gateを通らなければside effectが発生しない。
8. configured外付け媒体が利用不能な場合、別媒体へfallbackせず旧storeを維持して`blocked`になる。
9. versioned migration、backup dry-run、scratch restore、integrity、healthの全成功後だけ`active`になる。
10. 同一Chat requestの再送とCORE再起動resumeでDB、table、migration、backupを重複作成しない。
11. 成功、rejected、blockedの全経路が同じ`trace_id`と機械可読evidenceで利用者応答まで追跡できる。
12. Ubuntu、Windows、macOSで同じ論理contract、状態、failure reasonを返し、OS固有pathをChat契約へ露出しない。

## Agent間の協調と口頭移譲

Agentが別のAgentへ作業を移譲する場合、移譲元はAgent Registryから候補AgentのContractと自分向けのAgent Knowledgeを取得する。Routerは公開capability、委譲可能な仕事、制約、Role binding、runtime availabilityを使って候補を選ぶ。作業要求には、移譲元が受け取りたい成果物と移譲先が生成できるoutputの共通部分から確定した`expected_deliverable`を含める。明示的に指定されたAgentを、最適化を理由に別Agentへ黙って置換しない。

返却は全Agentへ同じpayloadを配る方式にしない。相関ID、送信元、送信先、双方のcontract revision、状態を持つ共通envelopeは維持し、成果物の内容、粒度、形式を受信AgentのAgent Contractに合わせる。会話ownerには進捗、利用者へ説明できる要約、次の行動を、実行ownerには実行結果、証跡、制約、未解決事項を、設計・実装・検証を担うAgentには各Contractが要求する差分、前提、test、edge case、risk等を返す。具体的なAgent名と期待成果物の対応はPersonaへ固定せずAgent Registryを正本とする。

協調を内部route、task payload、logだけで完了させず、共通Chat上で次の3発言を必須とする。

1. 移譲元は移譲先のAgent名を最初に呼び、移譲内容とその時点の会話内容を伝える。
2. 移譲先は移譲元のAgent名を最初に呼び、受け取った移譲内容と会話内容を必ず復唱する。復唱がない状態で作業開始扱いにしない。
3. 作業終了後、移譲先は移譲元のAgent名を最初に呼んでから、成果、失敗、未完了点を報告する。

これらは `agent.delegate` / `agent.acknowledge` / `agent.report` の会話eventとして同一sessionに残し、移譲先にも同じ移譲内容と会話内容をtask contextとして渡す。`agent.report`は成功だけでなく、失敗、部分完了、拒否を必ず閉じる。`POST /viewer/send`の開始時点で`audio_output=disabled`なら、そのrequestではTTS sessionを作成せず、合成を要求せず、TTS完了を待たない。TTSのON/OFFは音声出力だけを変え、会話eventの生成と表示を省略する理由にしない。Shiro内部のWorker実行器など、独立したAgentでない内部component呼び出しはこの口頭移譲の対象外とする。

移譲先が受領前に利用不能になった場合やtimeout／cancelで発言できない場合、COREはAgentを装った完了発言を生成せず、orchestrator起因のsystem failureとして同じ要求を閉じる。未応答のまま成功または作業中として残さない。

Agent Contract、Agent Knowledge、Interaction Policyの定義は「キャラクター・エージェント仕様」、Registry、Router、IPCの境界は「アーキテクチャ概要」を正本とする。

## Memory、Recall、Knowledge

- 会話履歴は発言ごとの `from` と `to` を保持する。
- RecallPack は複数の検索結果を budget、provenance、情報種別ごとの安全policyとともに組み立てる。
- Knowledge Relation は Entity、Topic、Project を制限付き 1-2 hop で横断し、採用理由を trace に残す。
- 外部検索結果、Advisor 出力、収益候補は、利用者確認なしに確定 Knowledge へ昇格しない。

### Common Raw Data intakeとdomain projection

`Common Raw Data`は、Conversation、UserMemory、Knowledge Memoryの投影に使う入力原本をCOREが
束ねる論理source-of-truth層です。21番目のcatalog DB、新しいmodule、外部databaseではありません。
台帳は既存の`storage.databases.conversation_l1`へ追加し、大きなimmutable bytesとassetは
`storage.memory.raw_source_dir`のcontent-addressed objectとして保持します。DB台帳とobjectは同じ
backup／restore整合単位であり、別の正本、暗黙fallback、兄弟moduleの独立domain原本の吸収は行いません。

対象sourceはChatGPT export、通常Chat event、news／web document、uploaded file、X Bookmark、
Agent observationなど、COREのConversation／UserMemory／Knowledge Memoryへ投影する入力です。TRADE、
GAMES、Imageなど兄弟moduleが所有する独立domainの原本は各owner moduleに残し、COREへCommon Rawとして
取り込む場合も、そのmoduleの正本を置き換えません。

処理は必ず次の一方向で追跡できる形にします。

```text
source adapter
  -> immutable Raw intake (manifest -> record -> state event)
  -> domain projection (Conversation L3 / UserMemory / reviewed Knowledge)
  -> projection receipt and named search index
  -> RecallPack (confirmed | pinned / reviewed projection only)
```

Toolsはローカルnative Goの`inspect`／`convert`／`verify`だけを担当し、COREのDBを開かず、network
import、owner scope、request ID、batch、checkpoint、state、policy、receiptを所有しません。COREは
authenticated user scope、schema／asset／provenance検証、atomic commit、checkpoint、receipt、
projection、forgetを所有します。raw payloadを直接検索、prompt注入、Recallしてはならず、Recall対象は
Conversation L3、UserMemoryの`confirmed | pinned`、Knowledge Memoryのreview済みprojectionに限ります。
Rawの原本確認、export、削除は、認証済みowner workflowがpurposeとscopeを検証し、exact
`raw_record_id`／`manifest_id`で行います。Agent／LLMへ物理path、任意SQL、全件scan、raw payloadを渡さず、
診断responseとlogには本文ではなくID、hash、件数、状態、redacted provenanceだけを返します。

採用するCommon Raw schemaの概念は次のとおりです。base schema／intake／object／config／runtime／backup-restoreは
source／focused completeとして扱いますが、installed binary、production config／migration、rebuild／restart、live API／Agent E2Eは
08に記す未確認gateです。source-focused契約だけでproduction import完了を主張しません。

| table | 最低限保持する契約 |
| --- | --- |
| `l1_raw_source_manifest` | source type／identity、manifest hash、source count、asset／schema／converter version、owner／scope、検証・checkpoint状態 |
| `l1_raw_record` | `raw_record_id`、`manifest_id`、source／parent／thread ID、owner user、scope、sensitivity、role、content type、occurred／ingested time、bounded inlineまたは`object_ref`、storage kind、content hash、asset refs、provenance URL／rights／license、schema／converter version |
| `l1_raw_state_event` | immutable payloadを変更せずに訂正、forget、delete適用／block、supersede、reject、再開を追記するstate event |
| `l1_raw_projection_receipt` | projection type、output store／record、raw record IDs、revision、input／output hash、status、created／updated time、失敗理由 |

payloadはbounded inlineまたは`raw_source_dir`内のimmutable content-addressed objectだけを使います。冪等性は
manifest hash、source record ID、content hashの組で判定し、同一replayは同じreceiptへ収束します。同一IDで
hashが異なる場合は`rejected/source_changed`、部分commitはcheckpointから再開し、projection rebuildは
Rawを変更せずrevisionとreceiptだけを追加します。
`manifest_id`と`raw_record_id`はadapterやLLMに指定させず、COREがcontract version、認証済みowner／scope、
source type／source record ID、canonical manifest／content hashから決定的に生成します。intake runは
`validating | committing`を過渡状態とし、各実行を`completed | rejected | blocked`のいずれかで閉じます。
過渡状態のままleaseを失ったrunはcheckpointとreceiptから再開し、人の返答で解除する状態を作りません。

source root／manifestの不在、manifest count／hash不一致、asset欠落、unsupported schemaは空成功にせず、
`rejected`または`blocked`で閉じます。`allow_empty=true`をsource contractが明示した場合だけ0件完了を
許可し、ChatGPT exportとKnowledge production migrationでは`allow_empty=false`とします。したがって
`source_count=0`、`imported_count=0`、`ready`だけでKnowledgeをactiveにしません。

ChatGPT_20260713は`user:ren`のprivate sourceであり、assistant発言単独をRenの事実、同意、経験として
確定しません。`forget`はpayloadを保持したまま全projectionとRecallから除外し、`supersede`は旧recordを
上書きせず新recordへ根拠linkを張ります。`delete`はpolicyを同期評価し、同じ実行を`completed | rejected |
blocked`のいずれかで閉じます。`completed`ではpayload／assetを物理削除し、ledgerには再import防止に必要な
最小のID、hash、scope、削除時刻、receiptだけをtombstoneとして残します。backup内copyもretention expiry後の
世代削除で復元不能にし、人の返答待ち状態を作りません。source、rights、scopeが不明なrecordは推測せず
`rejected`または`blocked`にします。

#### 実装と既存データcutoverの順序

1. `conversation_l1`のversioned migration、`raw_source_dir` validator、object writer、backup／scratch restore-checkを先に実装し、S1 validatorをすべて通す。
2. 既存の`l1_memory_event`、`l1_staging_item`、`l1_news_item`、`l1_knowledge_item`を削除・書換えず、既存IDとhashからRaw recordをbackfillし、既存rowをoutputとするprojection receiptを作る。ChatGPTは原export／asset manifestをobjectへ取り込み、既存L3 eventとevidenceへlinkする。旧L3 metadataはidentity／content hashを必須照合し、欠落したoptional fieldは互換として許可する。Knowledgeの既存row backfillは`allow_empty=false`で、0件やhash不一致をreadyにしない。legacy JSONL停止とlive E2Eは後段gateである。
3. sourceごとにcount、hash、scope、forget／delete状態、projection coverageを照合する。差分があるsourceは切り替えず、現行経路を維持したまま`blocked`にする。
4. 新規writeをsource adapter単位でRaw-firstへ切り替える。bounded inlineの通常ChatはRaw record、Conversation event、receiptを同じSQLite transactionでcommitする。object payloadはtemporary fileへ書いてhash／sizeを検証し、同一filesystemでatomic renameした後だけledgerをcommitする。失敗したtemporary／orphan objectはactive recordにせず、再照合可能なcleanup receiptへ隔離する。
5. UserMemory、Knowledge domain、search indexをRawから再投影し、既存output ID、confirmed状態、Recall結果が不変であることを確認する。直接L3／legacy JSONL intakeを停止するのは、source別parity、冪等再実行、backup restore、Agent-owned Recall E2Eがすべて成功した後だけとする。

#### Common Raw Dataの受け入れ条件

1. source manifestとrecordから、元のrecord、branch／thread、asset参照を再構成できる。
2. Raw recordからdomain projection、output record、Recall採用までをreceiptで一方向に追跡できる。
3. raw payloadが通常検索、prompt、Recallへ直接注入されず、許可済みprojectionだけが想起対象になる。
4. 同じmanifest／source record／content hashの再実行が同じreceiptへ収束し、重複行を作らない。
5. 同一source record IDでhashが変わる入力をconflictとして拒否できる。
6. source root不在、manifest不一致、asset欠落、未知schemaを0件readyに変換せず、理由付きで閉じる。
7. owner user、private scope、sensitivityをsource adapterの推測で拡張せず、利用者間の漏洩を防ぐ。
8. ChatGPT migrationが既存L3 event、evidence、confirmed 11件、Recall E2Eを保ったままRaw receiptへ接続できる。
9. Knowledge legacy JSONLの欠落をproduction Raw coverageと数えず、Common Rawからcandidate／reviewed projectionへ移行できる。
10. forget、supersede、delete後の再importで対象が復活せず、forgetはRecall除外、delete完了はpayload物理削除と最小tombstone保持として検証できる。
11. Common Raw ledger、object、projection receipt、backup／restoreを同じ復旧cohortとして検査できる。
12. authenticated production AgentのRecall E2Eで、confirmed／pinnedまたはreviewed projectionだけを正しいscopeへ渡せる。

### 全カテゴリの意味データと会話想起

永続DBはすべてRenCrowの広義のMemoryであり、Agent／workflowが必要な目的で想起する情報sourceとして扱う。RenCrowがDBを保持する目的は、各owner moduleがrequest purpose／role／authenticated scopeに応じてowner経路でデータを読み書きすることであり、Viewer表示、保管、owner service内部処理、Tool登録、catalog掲載だけでは完了としない。readは用途別のread-only Recall Adapterまたはnamed Tool、writeはowner moduleの検証済みcommand／workflowだけを通す。read projectionはprovenance、scope、freshness、validation、role、budgetを検証し、writeはschema、migration、validation、audit、idempotencyを検証する。物理DB、path、table／column、任意SQLをAgent／LLMへ渡さず、専用経路がないDBは未完了としてdata capability catalogで識別できるようにする。

#### Data Capability Catalogとinvestmentの固定契約

`storage.databases`のcatalog keyは次の20個に固定します。これはDB fileの配置や完了を宣言する一覧ではなく、同じData Capability Catalogを起動時にAgentのStable Runtime Contextと`data_capability`へ投影するためのlogical store一覧です。

`conversation_l1`、`conversation_archive`、`tool_registry`、`glossary`、`movie_catalog`、`hobby_graph`、`investment`、`advisor`、`sandbox`、`dci`、`skill_governance`、`workstream`、`revenue`、`persona_architecture`、`browser_trace_to_api`、`complexity_hotspot`、`super_agent_harness`、`ai_workflow`、`knowledge_memory`、`durable_store_workflow`

全persistent DBはMemoryであり、Ownerのread routeとwrite route、さらに認証済みproduction Agentの実証が揃うまで未完了です。routeが未登録、Owner serviceが未設定、statusが`ready`でない場合は`unavailable`または`blocked`として扱い、Viewer表示、catalog掲載、owner service内部処理、Tool登録を完了証跡にしません。

`investment`はcatalog上の一つのstoreで、正本Ownerは`RenCrow_TRADE`です。内部の論理domainは`source`、`learning`、`market`、`replay`、`portfolio`、`ledger`の6つに固定し、CORE Agentの操作名は次のとおりです。

| --- | --- | --- |

| recall | `learning_candidate` | exact learning candidate ID |
| recall | `market_snapshot` | exact market snapshot ID |
| recall | `replay_decision` | exact replay decision ID |
| recall | `portfolio_snapshot` | `query=current` for an independent current read, or the exact lowercase `sha256:<64 hex>` `audit_ref` from `ensure_portfolio_initialized` for write-to-read handoff |

COREはtrusted `ToolExecutionScope`からidentity、role、authenticated user delegation、parent request ID、purpose、policyを取得し、typed child scopeと同一turnのreceipt conflictを避ける決定的なsubrequest IDを作ります。これらをmodel、prompt、Tool payloadの自由入力にしません。readはexact／`limit=1`のOwnerEvidence、writeはstrict OwnerReceiptとidempotencyを必須とします。`record_shadow_observation`はmodelが市場値、action、policyを渡すwriteではなく、Owner replay／market record、fixed Outcome Label Contract hash、CORE Global Policyから観測を再構成します。

#### 認証済みShiro OPS入口

RenCrow_CMDから全DBのOwner routeを使うcanonical入口は、loopback限定の`POST /v1/agent/ops`です。
`local_agent_ops.enabled=true`のときだけrouteを登録し、COREは起動時にowner-only token fileを一度読み、
tokenへ対応する固定`user_id`を認証主体として確定します。request bodyは`message`だけを受け、利用者、Agent、
role、scope、route、modelをclientやmodelに選ばせません。COREは認証済みuser scopeから
Shiro／`worker`／`ops`のtyped child scopeを作り、実在するShiro Agentの`Execute`へ直接渡します。
認証済み`X-Request-ID`はこのShiro child scopeの`request_id`として保持し、task／responseの`job_id`は別に生成します。
同じ認証request IDとcanonical payloadの再送では下流child request／idempotency identityを再現でき、job IDは実行ごとに別です。
通常の`POST /viewer/send`は従来どおりpublic会話入口であり、private DB権限を追加しません。

この入口は`X-RenCrow-Client: RenCrow_CMD`、`X-RenCrow-Interaction-Profile: agent-ops`、
`X-Request-ID`、Bearer tokenをすべて必須とし、remote request、重複header、未知field、query、
非JSON、32 KiBを超えるmessageを拒否します。成功responseは`request_id`、`job_id`、
`agent_id=shiro`、`role=worker`、`route=OPS`、`output`だけです。token、入力本文、内部errorを返しません。

映画、ドラマ、人物、趣味、書籍、ゲーム、ニュース、投資などの意味データは、収集して
Viewerで閲覧するだけのデータではない。各カテゴリの正本DBは、検索、評価、表示、再利用に加えて、
利用者との会話で関連情報を想起することを基本目的とする。カテゴリ固有の収集経路、表示経路、
保存形式は分離してよいが、DBへ保存しただけ、またはViewerで検索できるだけでは、会話機能として
完了したとはみなさない。

Tool Registry、Sandbox、監査記録、Workflow、実行状態、process状態、credentialなどの運用・制御DBも
RenCrow Memoryのsourceである。ただし意味データDBではなく、通常の会話からRecallPackへ自動注入してはならない。
明示された運用操作、診断、監査表示で必要な場合だけ、認証済みscopeとrole policyに従うownerのread adapter／named Toolで
読み取り、状態変更はowner moduleの検証済みcommand／workflowで書き込む。

カテゴリ想起は、毎ターンに全DBを総当たりしてはならない。COREは発話、現在の会話scope、時点条件、
確定済みのrouteその他の機械的に判定可能な情報から関連カテゴリと関連sourceを決定し、該当する
sourceだけを検索する。通常の検索、候補抽出、score計算、鮮度判定に生成AIを使用しない。曖昧な
候補間の意味的なrerankだけを例外として許可し、採用理由をtraceへ残す。

検索sourceから得たrecordは、次の条件をすべて通過した場合だけ、利用者には直接見えないRecallPackへ
候補として渡す。

- provenanceが追跡でき、原資料、取得時点、検証時点、変換または派生関係を隠さないこと
- 認証済み利用者と許可されたscopeに属し、別利用者や未許可のprivate／family dataを越えないこと
- カテゴリのvalidation、record lifecycle、license／公開範囲、対象時点を満たすこと
- 時点依存データはfreshnessと再確認条件を満たし、stale、contradicted、unresolvedな情報を確定事実として扱わないこと
- 対象Agentのrole、source policy、sensitivity、prompt budgetを満たすこと

pending、未検証、反証済み、期限切れ、scope不一致、role不一致、budget超過のrecordは、通常会話の
事実として注入しない。想起したrecordは会話履歴へ保存せず、COREが実際に生成・発話した内容だけを
通常のassistant発言として履歴へ保存する。Recallの採用、除外、budget drop、role filter、source failureは
traceで後から検証できるようにする。

同じ認証済み利用者と許可scopeのChatでは、映画、ドラマ、人物、趣味、書籍、ゲーム、ニュース、投資を
含む確定済みの意味データ想起を、Mio、Shiro、Kuro、Midoriで共有する。ただし、Worker、Coder、運用・
診断経路では、実行目的、role、source policy、sensitivityに応じて個別の注入制限を適用し、Chatの共有を
そのまま拡大しない。投資など時点依存または高リスクなカテゴリは、検証時点と不確実性を保持し、未検証
の主張を推奨、助言、確定事実として想起しない。

sourceが利用不能、期限切れ、部分取得、検証失敗になった場合、COREは他sourceの実際に取得できた結果
だけで部分成功を返す。欠落した情報を推測、捏造、別sourceの結果として置換してはならない。sourceごとの
状態、失敗理由、取得時点、部分成功範囲をtraceへ残し、利用者向け応答で必要な場合は未取得または
部分結果であることを明示する。

新しい標準CLI、sidecar、collector、converterはnative Goで提供する。PythonやNode.jsを標準runtimeの
依存、隠れた起動条件、失敗時のfallbackとして追加してはならない。外部取得と会話想起は別の境界とし、
取得不能を理由に会話側で未取得データを生成しない。

映画.comを利用する映画、ドラマ、人物catalogでは、外部catalog取得とlocal catalogの会話想起を分離
する。外部取得は許可された範囲とアクセス条件に従い、robots.txtその他のアクセス制約で禁止された検索・
クロールを、別endpoint、別client、別言語へ迂回して実行しない。取得済みでvalidationを通過したlocal
recordだけを会話想起のsourceとし、外部取得の自動再実行を会話のlocal recallに混ぜない。外部取得が
利用不能でも、既存local recordの想起は独立して継続でき、localにない情報を外部結果として捏造しない。

カテゴリ追加およびDB capabilityの完了条件は、意味データをDBへ保存できること、Viewer表示、
`restricted`／`owner_service_only`、owner service内部処理、Tool登録、catalog掲載だけではない。対象DBについて、
認証済みproduction Agent／workflowがrequest purpose／role／scopeに応じて、readは用途別Recall Adapter／named Tool、
writeはowner moduleの検証済みcommand／workflowを通ることを確認し、read／write双方の`Agent-owned production E2E`を
成功させることを必須とする。read projectionのprovenance、scope、freshness、validation、role、budgetと、writeのschema、
migration、validation、audit、idempotency、source unavailable、trace、想起結果の履歴非保存も同じ証跡で確認する。

### 非同期Profile抽出とUserMemory昇格

この節は非同期Profile抽出の現行契約です。CLI、API、receiptの受入境界と残課題は
後述の「記憶処理のCLI-first／LLM-residual契約」および「実装状況・ロードマップ」を正本とします。

ProfileExtractorは利用者への応答生成に必要な処理ではなく、L1 Raw会話から永続UserMemory候補を作るbackground処理とする。通常会話の同期経路はユーザー発話とAgent応答をL1へ保存した時点で完了でき、ProfileExtractor、profile用LLM推論、候補の自動生成を待たない。明示的な記憶commandは、利用者が指定した内容をLLMで再解釈せず既存のUserMemory command契約で保存してよい。

ここでいうIdleはIdleChatではなく、COREが追跡するChat、ChatWorker、Worker、Coder、Heavy、Wild、IdleChatを含む全LLM生成の利用数が0である状態を指す。既定ではこの状態が10秒継続した後だけ、低優先度のMemory昇格処理を1件開始する。判定と開始は同じLLM利用tracker上のidle leaseとして原子的に行い、確認後から開始までの競合を作らない。idle leaseは取得中だけ共通tracker上の外部busyとして公開し、IdleChatは新しいLLM生成を開始しない。IdleChatがbusy確認を終えた後にleaseが取得された場合も、providerへ渡す直前の同じtracker上の原子的admissionで拒否し、実LLM要求を開始しない。leaseを引き継いだProfileExtractor自身はこのbusy判定で自己cancelしない。対話、ChatWorker、Worker、Coder、Heavy、Wildなどのforeground要求が到着した場合はidle leaseを取り消し、実行中のProfileExtractorをcancelして未処理状態へ戻す。foreground要求は常に優先し、busyまたはcancelは失敗回数へ数えず、次のIdle期間へ延期する。

Memory昇格の入力正本はRedisのactive threadやインメモリprofileではなく、L1 SQLiteに`observed`として保存済みのRaw会話eventとする。処理は未処理のユーザー発話を既存の利用者scopeとsession/thread境界で読み、複数batchに分かれても全件を順次処理する。Agent発話を文脈として参照してもよいが、Agent生成文だけをUserMemoryの根拠にしてはならない。各抽出結果には根拠となったユーザー発話の既存L1 event IDを付け、同じ根拠と正規化statementから同じ候補を重複作成しない。volatile queueを処理済み判定の正本にせず、処理状態と再試行情報をL1へ永続化する。

状態遷移は次を正本とする。

| 状態 | 意味 | 次の状態 |
| --- | --- | --- |
| `pending` | 未処理Rawが存在する | idle lease取得で`running` |
| `running` | 1つのbackground処理が抽出中 | commit成功で`completed`、通常LLM開始またはlease喪失で`pending`、処理失敗で`retry_wait` |
| `retry_wait` | LLM、parse、L1保存失敗後の有限backoff中 | 期限到達後`pending`、試行上限で`failed` |
| `completed` | 候補作成または「候補なし」の判定と処理位置をcommit済み | 終端 |
| `failed` | 有限再試行を使い切り、運用確認が必要 | 明示的な再実行で`pending` |

busy判定と通常LLM要求によるcancelは`retry_wait`や`failed`へ進めず、試行回数を増やさない。CORE停止で残った`running`はlease期限後に`pending`へ回収する。`chatgpt_export`以外を優先クラス0、`chatgpt_export`を優先クラス1として先に選び、同じ優先クラス内は`created_at`と根拠event IDの決定順で処理する。これによりChatGPT importのbackfillが新しい通常会話を奪わない。UserMemory候補の保存、根拠eventの対応付け、処理位置の`completed`更新は同じL1 transactionでcommitし、途中成功を作らない。

ProfileExtractorの出力先は既存のL1 UserMemoryであり、自動抽出結果は`candidate`に限定する。自動処理だけで`confirmed`または`pinned`へ昇格せず、`candidate`をAgent promptへ注入しない。確定、固定、訂正、無効化は既存のUserMemory commandと安全policyに従う。

ProfilePromotionでLLMが担当できるのは、根拠付き`ProfileCandidate`の意味抽出だけです。Raw列挙、sanitize、batch上限、job claim、lease、retry判定、exact JSONとschemaの検証、Evidence ID結合、owner／scope検証、deterministic ID、dedupe、candidate保存、状態遷移、receiptはCOREが決定的に所有する。LLMの返答、自然言語の成功報告、confidenceだけで確定状態へ進めない。

L1 Rawの保持・compact処理は`pending`、`running`、`retry_wait`または未確認の`failed`に対応する抽出対象を削除してはならない。LLM失敗、JSON不正、保存失敗は根拠eventを残して有限backoffで再試行し、上限後は`failed`として観測可能にする。terminal `failed`の再実行は、利用者の返答待ち状態を作らず、明示的に許可された`cmd-control`の`POST /viewer/memory/profile-promotions/retry`だけで行う。対応するL1 Raw eventが残るjobだけを`pending`へ戻し、evidenceのないorphan failedは不変のまま件数を報告する。CORE再起動後はL1の未処理状態から再開し、応答済み会話を再送させない。診断の`state_counts`、`failed_count`、evidence有無別の件数、DB pool統計はjob詳細の表示上限とは独立した全row snapshotとして扱う。

### ChatGPT会話exportのL3長期記憶取込

ChatGPT exportはCommon Raw Dataへ入るsource adapterの一つであり、認証済みownerの過去から現在までの
会話と元ファイルを、Raw intakeからConversation L3／UserMemoryへ投影します。初回対象`ChatGPT_20260713`
はRenのprivate sourceとし、後続exportにも同じ契約を適用します。legacy `Tools import/confirm` と
COREの直接L3 `/viewer/...` production routeは削除し、runtime入口を認証済みCORE owner APIと
RenCrow_CMDのone-request facadeに限定します。Tools bundle、CORE artifact service／API／progress／retry／finalize、
CMD facade、source-chunk ingestはsource／focused実装済みです。未完了のproduction backfill／cutover、
installed binary、production config／DB migration、live CMD->CORE／Agent E2Eを通すまでimport完了を主張しません。

採用するtargetは、次の順で一方向に流れます。

```text
local ChatGPT export
  -> RenCrow_Tools native Go inspect / convert / verify
  -> deterministic Common Raw bundle
  -> one authenticated RenCrow_CMD -> CORE upload request
  -> CORE staging / full artifact verification
  -> deterministic Common Raw intake batches
  -> L3 / UserMemory candidate / reviewed Knowledge projection
  -> export-scoped progress / deterministic finalize receipt
  -> exact-ID UserMemory confirm / pin（importとは独立）
```

Toolsの`verify`はローカルbundleの形式・hash・再構成を検査するだけです。network送信、CORE DBへの書込、
owner／scopeの決定、request ID、batch／checkpoint、state／policy、receiptはCOREが所有します。

#### Common Raw bundleとschema

Toolsが生成するbundleのmanifest formatは`rencrow.chatgpt_common_raw_bundle.v1`、message record schemaは
`rencrow.chatgpt_l3.v1`、converter versionは`chatgpt-export-memory-go/v2`に固定します。bundleは圧縮しない
deterministic TARで、entryは次の相対pathだけを使います。

```text
records.jsonl
source-files.jsonl
objects/sha256/<2>/<hash>
```

`records.jsonl`はcanonical Raw payloadを持つmessage recordです。`source-files.jsonl`はexport内の全ての
元の相対source file（conversation JSON、manifest、asset等）を一件ずつ索引し、相対path、bytes、SHA-256、
順序付き32MiB chunk列を記録します。chunk objectはcontent-addressedで重複排除しますが、source-files indexから
全元ファイルをbyte-for-byteに再構成できなければbundleは不正です。source pathはsafe／relative／UTF-8で、
絶対host path、`..`、NUL、未正規化のpathを含めません。Python fallbackは作りません。

manifestは、正規化してsortしたsource-file metadata、source／message／file／chunk／object counts、source
chunk index、artifact bytes／SHA-256、schema／converter version、canonical manifest hashを束縛します。
`generated_at`は表示・監査用に保持できますがcanonical hashの入力から除外します。manifest、record、source
index、TAR entry、全object、再構成結果のいずれかに不一致があればCOREは受け付けません。

`records.jsonl`のmessage recordは全canonical Raw payloadを保持し、元ファイルを部分的に要約したものへ置換
しません。元ファイルそのものはchunk-backed synthetic Raw source record（64 MiB境界に合わせて一つのchunk-ref recordを必要数）としてCommon Rawへ表現し、必要なら
一つのsource fileを複数recordへ分けます。後段の一internal batchはsource record最大100件かつdecoded Common
Raw payload合計64 MiB以下で、順序はartifact／source indexの安定順、batch indexはCOREが採番します。CMDや
clientはbatch size、batch index、checkpointを指定しません。

初回sourceのinspect基準は約2.1GB、conversation JSON 21ファイル、2,094会話、54,032 message、1,719 assetである。roleは`user | assistant`とmessageを持たないnode、content typeは`text | multimodal_text | reasoning_recap | thoughts`と未設定nodeを含む。件数はsource同一性の固定値ではなく、再実行時もinspectとmanifestで再計算する。production import receiptは原本不変、source ID／message ID／content hashによる冪等性、未変換・重複・candidate・confirmed・失敗件数を固定し、残りのProfilePromotion backfillは別の進捗として観測する。

#### 保存と投影の契約

1. export原本は読み取り専用とし、分割されたconversation JSON、export manifest、添付assetの相対path、byte数、SHA-256をsource manifestに固定する。取込は原本のrename、削除、書換えを行わない。
2. 全会話の全branchと現行branchの選択状態、message ID、会話ID、発言者role、作成時刻、content type、本文、添付参照、source内の順序を、再構成可能なL3長期エピソード原文として欠落なく保存する。削除済みbranchやexportが含まないデータを推測で補完しない。既存`EvidenceID`、legacy content hash／metadata、current-branch user job／candidate ID、confirmed／forget／supersede／Recall stateとのlinkを保持し、同じ意味の新IDやsynthetic evidenceを勝手に作らない。
3. 想起用projectionは原文を上書きせず、根拠message ID、source export ID、会話時刻、生成時刻、記憶種別、scope、sensitivity、confidence、有効期間を保持する。抽出ロジックを変更しても、原文から再投影できることを必須とする。
4. Ren本人の`user`発言をUserMemoryの主要根拠とする。ChatGPTの`assistant`発言は会話エピソードの文脈として保存できるが、Renの事実、同意、経験として単独で確定しない。system、tool、生成内部metadataも会話者の人格や事実根拠にしない。
5. 取込済みの長期エピソードはすべて`user:ren`のprivate scopeに置く。その中から作るUserMemoryは、明示的な直接記憶commandを除き、最初に`candidate`として保存する。`candidate`をRecallPackに入れず、`confirmed | pinned`だけをAgentへ供給する。
6. 重複exportと後続exportはsource ID、message ID、content hashで冪等にmergeする。矛盾、訂正、時系列変化は古い記憶を物理削除せず、`superseded`、有効期間、根拠linkで表現する。忘却された記憶と削除対象は再importで自動復活させない。
7. 添付assetは本文と別にhash、media type、source message ID、相対pathを検証する。画像・音声の内容を抽出する場合は正規のRenCrow_VisionまたはRenCrow_STT経路を使い、converter内で別backendを直接呼び出さない。assetはchunk ingestとsource reconstructionが完了するまで移行済みと数えない。

#### 取込手順

1. **inspect**: Toolsのnative Go local commandがsource directoryを読み取り専用で列挙し、export形式version、分割JSON数、会話数、message数、role別件数、asset数、時刻範囲、未知content type、parse errorをreportする。
2. **convert**: 同じTools local commandが`rencrow.chatgpt_common_raw_bundle.v1`のdeterministic TARを生成する。manifest、`records.jsonl`、`source-files.jsonl`、全object、source reconstruction、canonical hashを束ねる。Python fallbackは使わない。
3. **verify**: Toolsのlocal verifyはbundleのschema、UTF-8、safe path、TAR EOF／trailing bytes、hash、counts、全source file再構成を検査する。network request、CORE import、owner／request／batch／checkpointを行わない。
4. **upload／stage**: RenCrow_CMDがmanifest JSONとartifact TARを一つのauthenticated multipart requestでCOREへ渡す。COREは認証後にconfigured `raw_source_dir`配下へprivate stagingし、manifest、TAR、records、source index、objectsを全件検証する。
5. **raw intake**: COREがsource record最大100件かつdecoded Common Raw payload合計64 MiB以下の内部batchをstable orderで作り、batch index／checkpoint／state event／projection receiptを所有してcommitする。CMDやToolsはbatchを分割せず、partial requestの再送は一つのupload requestで行う。
6. **project**: 全manifest／TAR／record／source index／object／reconstruction検証後に、commit済みRawからL3長期エピソードとUserMemory candidateを作る。LLMは曖昧な意味抽出だけに使い、ID、hash、順序、scope、重複排除、状態遷移はCOREが機械的に決定する。
7. **receipt／progress**: COREはexport単位でsource／message／file／chunk／batch／Raw／projection counts、ProfilePromotionの状態内訳、evidence有無、hash／version binding、import state、warnings／audit referenceだけを返す。他exportのjobを混ぜず、Raw本文、物理path、statementを返さない。
8. **retry**: export IDで限定し、対応するimmutable evidenceが残るfailed ProfilePromotion jobだけを有限に再投入する。別exportとorphan jobは変更しない。CLIの再投入は決定的だが、その後の意味抽出だけはLLM residualである。
9. **finalize**: import applyの`completed`と取込時に検証済みのmanifest／artifact hash binding、Raw／L3件数、projection receipt、ProfilePromotion終端をCOREが機械的に再照合する。全objectの再hashをfinalizeで繰り返さず、永続済みledgerとreceiptを進捗正本にする。成功時はimmutable／idempotent receiptを保存し、不足時は理由付き`blocked`または`rejected`を返す。finalizeはcandidateを`confirmed`／`pinned`へ変更しない。
10. **UserMemory lifecycle**: 記憶の確定は既存のexact-ID `memory confirm | pin`とCORE policyだけが所有する。export全体のbulk confirmはproduction契約に含めない。
11. **Recall E2E**: Renが過去に述べた複数の異なる話題で、Mio、Shiro、Kuro、Midoriが同じprivate scopeから関連記憶だけをRecallできることを実会話で検証する。無関係な全履歴の注入、assistant発言のRen事実化、candidateの注入、別利用者への漏洩がないことをRecall traceで確認する。

#### ツール化と責務境界

ChatGPT exportは分割JSON、branch、添付asset、後続exportの差分を扱う大容量の外部形式であり、手作業での取込は再現性、冪等性、監査性を満たさない。そのため標準手順はツール化する。

- `RenCrow_Tools`: local native Goの`inspect`／`convert`／`verify`と、`rencrow.chatgpt_common_raw_bundle.v1`／`rencrow.chatgpt_l3.v1` bundleの生成・検査だけを所有する。ToolsはCORE API、DB、network、owner／scope、request ID、batch／checkpoint、state、policy、receiptを扱わない。
- `RenCrow_CMD`: CORE Public APIのterminal facadeだけを所有し、利用者が選んだprivate regular fileを開いてstreamしmultipartを組み立て、一commandにつき一つのrequestを送ってboundedな単一JSON responseを原文のままrelayする。hash、schema、batch、checkpoint、request ID、receipt、state、policy、DB意味論を持たない。
- `RenCrow_CORE`: artifact schemaの意味検証、認証owner／scope、private staging、whole-artifact verification、source reconstruction、原子的batch intake、L3・UserMemory投影、状態遷移、Recall、export-scoped progress／retry／finalize、receiptを所有する。Import finalizeとexact-ID UserMemory confirmを同一操作にしない。
- converterとCORE importerは独立してversioningし、未対応version、未知content type、manifest不一致、部分commitの不整合でfail closedする。削除済みのTools `import/confirm`とCORE直接L3 `/viewer/...`は新routeのfallbackや拡張に戻さない。

### 記憶処理のCLI-first／LLM-residual契約

この節を、記憶に関する取得、検証、変換、状態遷移、想起、外部exportの機能正本とします。実装済みの
現行経路と、採用済み・未実装のtargetを混同しません。`rencrowctl memory`は既存の`status`／
`retry-failed`を互換維持し、owner操作とChatGPT Common Raw importはCORE Public APIのterminal facadeとして定義します。
CORE／CMD focused testの成功だけでは、導入済みbinary、認証済みowner scope、配備DB migration、実際のRecall／import E2Eの証拠に
なりません。

標準経路は次のとおりです。

```text
terminal / operator
  -> RenCrow_CMD rencrowctl
  -> authenticated CORE owner API
  -> validation / policy
  -> owner transaction or durable outbox
  -> typed receipt
```

外部exportだけは次の経路を使います。ToolsとCMDはCOREのDBを直接開かず、identity、scope、state、ID、hash、
順序、重複排除、ranking、retention、receiptを決定しません。

```text
external export
  -> RenCrow_Tools native Go local inspect / convert / verify
  -> deterministic Common Raw bundle
  -> RenCrow_CMD one multipart request
  -> CORE artifact service / Common Raw intake
  -> L3 / UserMemory / reviewed Knowledge projection
  -> RecallPack
```

| 境界 | 決定的処理の所有者 | 許されるLLM residual | 成功・失敗の終端 |
| --- | --- | --- | --- |
| terminal／operator | RenCrow_CMD。command構文の解析、CORE APIへの一対一mapping、認証tokenのtransport、responseのstdout／stderr表示だけを行う | なし | COREが返したHTTP statusとboundedな単一JSON responseを意味解釈せずrelayする。ID、owner、policy、状態、dry-run／applyの意味、receiptを決定せず、DB・LLMへ直結しない |
| owner API／policy | CORE。認証user、scope、許可operation、request／idempotency identity、ID／hash／順序、dedupe、state、dry-run／apply、ranking、retention、receipt | なし | owner transactionまたはdurable outbox後に`completed`、拒否は`rejected`、不可用は`blocked` |
| external adapter | RenCrow_Tools。local native Goのread-only inspect／convert／verify、bundle／hash／reconstruction出力 | なし | immutable bundleをlocal filesystemへ出力・検査する。network、CORE DB、Redis、Qdrant、LLM、owner／request／batch／receiptを扱わない |
| ProfileExtractor／ThreadSummarizer | COREがL1 Raw、bounded projection、scope、schemaを準備し、RenCrow LLM正規routeを呼ぶ | 候補の意味抽出、要約、keywordsなどbounded semantic residualだけ | COREが検証してから保存。invalidは未保存の`failed`／retry receipt |
| Recall／Prompt Context | CORE。scope、state、sensitivity、freshness、budget、ranking、trace、注入を決定 | なし（要約生成を別途許可する場合を除く） | `confirmed | pinned`かつnon-sensitiveのbounded projectionだけを注入 |

通常Chatは`SaveMessage -> L1 Raw event -> ProfilePromotion -> candidate -> deterministic validation／dedupe ->
owner transaction／receipt`の順です。`captureUserMemoryCandidate`のように実L1 evidenceを通らないsynthetic
evidenceを生成してproduction candidateを保存する経路は禁止します。assistant発言だけをRenの事実根拠にせず、
通常Chatの応答完了をProfileExtractorの完了待ちにしません。

##### ProfilePromotionのbounded projectionと厳密LLM契約

`ProfilePromotion`は、extractor呼出前にCOREがowner namespaceのL1 UserMemory projectionを読みます。
SQLの時点で`namespace=user:<owner>`、`speaker=memory`、`layer=L1`、`active=1`、stateが
`candidate | confirmed | pinned`の行だけを選び、state優先度を`pinned -> confirmed -> candidate`、次に
`updated_at`、`rowid`の安定順とします。その安定順prefixから最大32件、各statementは512 rune以下、合計statementは8192 rune以下だけを
入力へ含め、valid rowの合計が超過してもfailureにせずprefixで打ち切ります。
選択された行がowner／state／active／statement／型付きmetadataの再検証に失敗した場合はskipせずfail closedし、
store read failureはLLMを呼ばずpromotion batchを`failed`へ送ります。

LLM responseは最大64KiBで、前後の空白も含めてJSON objectそのものとし、キーは`preferences`（string map）と
`facts`（string array）だけです。prefix／suffix／markdown、未知キー、number／object／array／bool／null、
空要素を受け付けません。raw candidateはdedupe前に最大16件、preference keyは64 rune、valueとfactは512 rune
以下（preference valueは448 rune）、CR／LF／NULは禁止です。COREがtrimと連続空白の縮約、case-foldした
`type + statement`で同じbounded projectionとwithin-outputをexact dedupeし、異なるstatementは保持します。未boundedな
全projectionをdedupe専用に追加取得する経路は持ちません。
preferenceの走査順はsort済みです。LLMは意味抽出だけを行い、COREが`type=preference|profile`、
`confidence=0.7`（`0 < confidence <= 1`）、`sensitivity=normal`、`scope=all_personas`、batch evidence binding、
`state=candidate`を決めます。candidateは自動で`confirmed`／`pinned`へ遷移しません。不正outputまたは不正candidateは
Completeせず有限failureとし、nil candidate listだけは有効な空completionとして扱います。

#### 現行と全targetの責務差分

この節はProfileExtractor、ThreadSummarizer、EndTurn、Recall、lifecycle、Parquetを含む記憶処理の
current／target境界です。Recall／Trace、archive、lifecycle、Parquet owner workflowはCORE sourceとfocused testが
実装済みですが、installed binary、production config／DB migration、authenticated live CMD->CORE route、rebuild／restart、
Agent／full DB E2Eは別の配備gateとして未確認です。Common Raw／import、ProfilePromotion／ThreadSummarizerの
LLM residual、typed EndTurnはsource／focused実装済みですが、production backfillと上記配備gateを未完了のままにします。

- ProfilePromotionのsource／focused実装は、COREがactiveな`confirmed | pinned | candidate`のbounded projectionを読み、
  LLMには必要な意味判断だけを渡し、前後でCOREがvalidation、正規化、exact／stable-key dedupe、scopeを検証します。
  installed binary、production config／DB migration、authenticated live routeは別の配備gateです。
- targetのProfileExtractorはL1 Raw evidenceを必須とし、allowed type／enum、候補数上限、statement／key／value長、
  confidence範囲、evidence binding、sensitive／default scopeを検証します。LLM出力が不正ならpersistせず、
  `failed`または有限retry receiptにします。candidateを自動で`confirmed`／`pinned`へ昇格させません。
- ProfilePromotion、operator propose、external importを含む新規作成APIは`candidate`だけを受け付けます。generic
  storage createへcaller選択の`confirmed`／`pinned`を渡さず、確定と固定は認証済みexact-IDの`confirm`／`pin`
  state transitionと同一transactionのaudit receiptだけで行います。
- ThreadSummarizerは正規RenCrow_LLM routeのWorker -> Wild -> Chatを空き順に各target最大1回・短いattempt上限で試し、全滅時はdeterministic fallbackへ確定的に縮退する（2026-08-19 利用者指示）。生成はresponse全体が64KiB以下のexact JSON
  `{"summary":"...","keywords":["...","...","..."]}`だけを出力します。未知key、重複key、前後文字、
  markdown、複数JSON valueを許しません。summaryはUnicode空白を一つへ正規化した1〜1024 runeでCR／LF／NULを
  含めず、keywordsは同じ正規化後1〜64 runeを3〜5個、case-fold keyで一意とします。LLMはprovider、mode、
  attribution、evidence、scope、stateを決めません。
- COREは保存前にthread／session ID、source turn count、順序index、speaker、本文をversioned canonical encodingへ
  束縛したSHA-256 evidenceを決定的に計算し、threadからrolesを導出します。summaryと同じSQLite transactionで
  `schema_version`、`generation_mode=llm | deterministic_fallback`、provider、固定failure code、evidence SHA-256、
  source turn count、roles、生成時刻をreceiptへ保存します。provider error／invalid outputは本文やraw errorを保存せず、
  bounded deterministic fallbackを作ってmodeと固定理由を明示します。receiptのない既存rowはread時に
  `legacy_unverified`とし、LLM成功へ推定しません。
- EndTurnはconversation responseの成功とmemory persistenceを分離した`ConversationTurnResult`を返します。
  canonical Agentはroot `job_id`を`turn_id`／root `trace_id`として再利用し、retry時に作り直しません。User／Agentの
  `message_id`は同じturn identityから別々の`msg_` UUIDとして一度だけ決定し、`turn_index`、時刻、process-local
  sequenceをidentityに使いません。同じturn ID＋同じcanonical payloadはstored resultを再生し、異なるpayloadは
  `conflict`として一件も追加しません。
- COREはL1 SQLiteの一transactionでdurable active-thread state、User／Agentのちょうど2件のRaw message、対応する
  event log、User発話のProfilePromotion job、実際にpromptへ使ったRecallPackのtrace start／items／injection／finish、
  turn receipt、必要なfollower outboxをcommitします。いずれかが失敗した場合は全てrollbackし、UserまたはAgentの
  片方、traceだけ、jobだけを残しません。receipt／outboxは本文を複製せず、ID、payload SHA-256、count、固定status／
  error code、必要targetだけを保持します。
- Redis active-thread projectionと、thread境界時のThreadSummarizer→archive SQLite→VectorDB→Redis cleanupはSQLite
  outboxのidempotent followerです。COREはcommit直後とstartupで`turn_id + target`をclaimして再生し、同じhashは
  no-op／収束、異なるhashは`conflict`、stale `running`は有限lease後に再取得します。archive／vector完了前にL1 Rawを
  削除しません。`completed`はSQLite正本と全required follower完了、`partial`は正本commit済みでfollowerが
  pending／failed、`failed`は正本transaction未成立です。legacy `EndTurn` wrapperもStore／flush errorをlogだけにして
  nilへ変換せず、canonical Agent経路はtyped request/resultを使います。
- UserMemoryのAgent readはtrusted `ToolExecutionScope`のauthenticated userと`DataScopeUser`を両方検証し、
  `confirmed | pinned`、active、non-sensitiveをstore projection前後で強制します。Recall sourceのread／embedding／
  index失敗を空の成功へ変換せず、採用・除外・source failureをRecall traceへ理由付きで残します。
- lifecycle／decayはCORE owner CLI／APIがplan／dry-runを既定にし、decay auditへ実計算scoreを残します。
  Parquet owner exportはsource DBを変更しない明示的なartifact生成commandです。configured absolute
  `storage.memory.cold_export_dir`内のrun temp、5つのdeterministic relative Parquet file、件数／bytes／SHA-256 manifest、atomic
  finalize、failure cleanup／quarantine、`request_id`によるexact target verifyを必須とし、呼出元任意pathやprivate本文のstdout出力を許可しません。

#### ChatGPT import command／APIのtarget契約

上記ChatGPT commandは、既存memory commandと同じ標準global optionの配置（`--url`、`--token-file`、
`--json`等）に従います。`memory import chatgpt`の`--manifest`と`--artifact`は利用者が選んだprivate
regular fileを指すdistinct pathで、CMDの事前検査はflagの有無、型、pathがopen可能なprivate regular fileであること、
multipartを組み立てられることだけです。CMDはhash、schema、batch、checkpoint、request ID、receipt、state、policy、
DBを解釈または保持しません。

CORE owner APIは旧 `/viewer/memory/import/chatgpt*` を置換します。旧Viewer routeはproduction登録から削除し、
ChatGPT import／status／progress／retry／finalizeのruntime入口は次の認証済みowner routeだけとします。

```text
POST /v1/memory/import/chatgpt
GET  /v1/memory/import/chatgpt/{percent-escaped-export-id}
GET  /v1/memory/import/chatgpt/{percent-escaped-export-id}/progress
POST /v1/memory/import/chatgpt/retry
POST /v1/memory/import/chatgpt/finalize
```

uploadはloopbackからの認証済みrequest一回だけで、interaction profileは`cmd-control`、multipart partの順序と
型は次に固定します。

```text
1. apply    text/plain      `true` または `false`（CLIの`--apply`省略時はCMDが`false`を送る）
2. manifest application/json  manifest JSON file
3. artifact application/x-tar artifact TAR file
```

unknown、duplicate、missing part、part name／media type不一致、part後のtrailing bytes／multipart EOF不備はCOREが拒否します。
callerはuser、scope、export／request／idempotency ID、DB／path、batch size／index、checkpoint、owner、policyを送らず、
request IDとidempotency identityはCOREが生成します。retryはJSON object`{"export_id":<id>}`、finalizeは
`{"export_id":<id>,"apply":<bool>}`だけを受けます。status／progressは`cmd-diagnostics`、retry／finalizeは`cmd-control`です。
CMDは再試行やclient-side batchを行わず、import中のcheckpointとresumeはCOREが所有します。旧
`POST /v1/memory/import/chatgpt/confirm`はbulk candidate confirmとしては廃止し、production経路で候補を変更しません。

COREは認証・scope検証後だけconfigured `storage.memory.raw_source_dir`配下のprivate stagingへ保存します。manifestは64 MiB以下、
artifact TARは64 GiB以下で、strict media／EOF／trailing part、full manifest／TAR／records／source-files／objects／reconstruction
をfirst Raw/domain commit前に検証します。staging／tempはprivate 0700 directory／0600 file、同一filesystemのatomic finalize、
quarantine／cleanupを使い、通常Recallへ出しません。crash／orphan stagingはactiveとは扱わず、安全なreconcile／removeで閉じ、再開は
一つのupload requestの再送で行います。

staging namespaceは`raw_source_dir/.chatgpt-import-staging/<CORE-generated-stage-id>/`に固定し、stage IDは
ASCII alphanumericとhyphenだけのpathless値とします。各request directoryは`manifest.json`と`artifact.tar`以外を
受け付けず、symlink／hardlink／device／別filesystemへの逃道を禁止します。成功、入力拒否、またはterminal
`blocked`応答後のstage copyはrequest終了時に安全に削除します。process中断で残ったstageだけを次回HTTP
route開始前に安全性とcontainmentを検証して削除し、symlinkやunknown entryは自動削除せずstartup errorにします。
staging copyはresume正本やbackup正本にせず、追跡に必要なstateはappend-only import ledgerだけに残します。startupは
staging reconcileを完了してからCommon Raw object reconcile、active importの`blocked/process_interrupted`終端化の順に
実行し、それらが完了するまでHTTP routeを提供しません。

COREはsource record最大100件かつdecoded Common Raw payload合計64 MiB以下のstable internal batchを決めます。全元fileをchunk-backed
synthetic Raw source recordとして取り込み、messageはcanonical Raw payloadを保持します。projection receiptはRawのimmutable `pending`
projectionを先にcommitし、L3／job／completed receiptを一つのtransactionで確定します。failed／blocked receiptは追記し、repeatは
同じartifact bindingへ収束します。assetsはchunk ingestとsource reconstructionが成功するまでmigratedと数えません。

status／import receiptはRaw本文、path、statementを返さず、export／binding hashとversion、source／message／file／chunk／object counts、
batch／Raw／projection／job aggregate、terminal `import_state`（`completed | rejected | blocked`）、warnings、audit reference、replay状態だけを返します。
active request中だけ`validating | committing`を観測でき、owner-reply-wait statusは作りません。partial commitで失敗したrequestは`blocked`で閉じ、
exact reuploadが再開・収束します。HTTPは400（invalid/schema/count）、401（auth）、403（profile/scope）、404（unknown export status）、
409（source changed／binding conflict）、413（bounds）、422（artifact semantic／reconstruction）、503（storage/root unavailable）、
500（storage failure）です。

confirmはauthenticated ownerのcandidate operationだけを対象にします。dry-runはread-only、applyはprojection completedかつfailedがなく、
owner scopeの一致を確認した後だけcandidate stateとaudit receiptをatomicに更新します。hardcoded `user:ren`をowner判定に使わず、別ownerの
status／candidateを返しません。legacy Tools `import/confirm`とCORE direct-L3 `/viewer/...`はproduction経路から削除済みで、
target APIの拡張やfallbackに戻しません。

Parquet owner export／verifyは、`rencrowctl memory export parquet`が
`POST /viewer/memory/export/parquet`を1回、`rencrowctl memory export verify --request-id <request-id>`が
escaped targetを1つ持つ`GET /viewer/memory/export/{request-id}`を1回呼ぶ契約です。COREがauthenticated owner／actorと
current request IDを生成し、`storage.memory.cold_export_dir`配下のconfigured absolute rootだけを使います。
callerはpath、user、current request ID、DB情報を送らず、CMDはreceipt／hashを計算せず、COREのtyped relative metadataだけを表示します。

archive SQLiteの一つのread snapshotから、5つのdeterministic relative Parquet fileとrows／bytes／SHA-256 manifestを作り、
private staging、atomic finalization、receipt、failure cleanup／quarantineを行います。source DBは変更せず、verifyはexact targetの
manifest／file hash／countを再検証します。同一export requestの再送はartifactを再検証してreplayを返します。旧24時間／env fallbackの
automatic Parquet jobは現行runtimeで起動・定義しません。

#### Recall／Trace owner APIの第一target（実装済み・配備／E2E未確認）

`memory recall`と`memory trace`はlegacy Viewer read routeの別名ではなく、認証済みowner専用のCORE APIとして実装します。
CMDは次のGETを一回だけ発行し、callerの`user_id`、session ID、request ID、DB情報を送信しません。

```text
GET /v1/memory/user/recall?query=<1..512 rune>&limit=<1..50,default12>
GET /v1/memory/user/traces?limit=<1..100,default20>
GET /v1/memory/user/traces/{escaped-trace-id}
```

COREはconfigured authenticated userと`ToolExecutionScope`／`DataScopeUser`からownerを決定します。Recallはsemantic stateを
変更しませんが、traceを永続化します。`query`は空でない1〜512 rune、`limit`は指定範囲だけを受け、未知または重複query、
空query、範囲外limitは400で拒否します。trace list／showはowner_id一致だけを返し、owner不明のlegacy rowと別ownerのexact IDは
同じ404として非公開にします。

RecallのrankingはCOREの決定論処理で、最大100件をscanします。採用対象はactive、非superseded、非decayed、
`confirmed | pinned`、normal sensitivity、authenticated scopeに適合するUserMemoryだけです。candidate、sensitive、inactive、
superseded、decayed、budget dropは空結果へ捨てず、trace itemへstatus／reasonを残します。LLMはこのoperationを呼びません。

Recall responseは`items`（既存`UserMemoryOwnerView`のbounded fieldsに`score`を加えたもの）、`trace`（`id`、`status`、
`query_text_redacted`、`total_candidates`、`selected_count`、`created_at`）、共通receiptを返します。receiptのoperationは`recall`、
`audit_reference`はtrace IDです。Trace list itemは`id`、`status`、`route`、`persona`、`total_candidates`、`injected_count`、
`total_injected_tokens`、`created_at`とし、receipt operationは`trace_list`です。Trace showはsummary fieldsに加えて
`query_text_redacted`とbounded items（`item_id`、`memory_id`、`kind`、`source_id`／`source_type`、optional `summary`、`score`、
`status`、`reason`、`prompt_section`、`token_count`、`memory_state`、`sensitivity`）を返します。sensitive、conversation short context、
full transcriptはsummaryを空にし、その他のsummaryも240 rune以内にします。receipt operationは`trace_show`です。

Trace tableには`owner_id`とowner indexを持たせ、新しいAgent／owner traceでは必須とします。`owner_id=''`のlegacy rowはowner APIへ
公開しません。BeginTurnのtraceもowner_id、選択されたUserMemory、除外されたUserMemoryを保持します。Startは`started`で記録し、
items／injectionが成功した後だけ`completed`または`partial`へFinishします。途中のstore、source read、index failureをcompletedへ
丸めず、source failure itemまたはtyped blocked／partial outcomeとして返します。

CMDの対応は`memory recall --query ... [--limit]`、`memory trace list [--limit]`、`memory trace show --id ...`です。profileは
`cmd-diagnostics`、Bearer tokenを付けたGET一回だけとし、CMDはranking、scope、state、receipt、traceを決定しません。

CLIは任意`user_id`、request／idempotency ID、DB path、table／column、SQL、物理output pathを受けず、authenticated
user、actor、scope、request ID、idempotency keyはCOREの認証済みserver contextとAPI contractから決定します。
CMDが行える事前検査はflagの有無、型、空文字、HTTP requestを組み立てられる範囲だけです。memory type、state遷移、
reasonの妥当性、bulk mutation／import／lifecycleのdry-run／apply可否と意味はCOREが再検証して決定します。
`--apply`は利用者の明示intentをAPIへ運ぶflagであり、CMD自身が変更を適用する権限や処理ではありません。Parquet exportは
COREがsource DBを変更せずconfigured `storage.memory.cold_export_dir`へ生成します。全effectful operationはCOREが生成またはAPI契約に従って
検証した`request_id`を持ち、memory stateを変えるoperationはCOREが`reason`を必須検証します。COREだけが
idempotencyを評価してtyped receiptを返します。
人の返答待ちstatus、許可待ちqueue、grantは作らず、各requestを`completed`、`rejected`、`blocked`の
いずれかで閉じます。

`memory propose`はcaller指定のsynthetic evidence IDを受けません。COREは認証済みoperatorのstatementをL1 evidence
eventとして保存し、そのeventとcandidateを同じtransactionへ束縛します。lifecycle `run`は直前のplan receipt／hashを
`--plan-request-id`で再検証し、入力cohortが変化していればapplyせず`rejected`で閉じます。

#### Receiptと受入境界

memory APIの共通response／receiptは少なくともCOREが確定した`request_id`、`operation`、`status`、`owner_route`、
`policy_revision`、`idempotency_key`、`idempotent_replay`、input／output count、`completed_at`、warnings、`audit_reference`
を持ちます。readは認証済みownerが明示要求したbounded UserMemory projectionとstateだけを返し、Raw payload、
全会話transcript、sensitive valueをstdoutへ出さず、通常logにはUserMemory statementも残しません。既存の
`memory status`／`memory retry-failed` responseは互換維持します。

ChatGPT adapterのtargetはToolsのlocal native Go `inspect | convert | verify`と、COREのauthenticated upload／
artifact verification／import／projectionです。manifest／artifact hash、schema／converter versionはCOREがrequest／
receiptへ束縛し、typed status／count／hashを検証してからcheckpointを進めます。HTTP 2xxやuntyped JSONだけで成功にせず、
Python predecessorへfallbackしません。Toolsの旧`import/confirm`とCORE direct-L3 `/viewer/...`はproduction経路から削除済みで、
新APIへのnetwork import／fallbackを持たせません。COREはCommon Rawのmanifest／record／state／projection receiptを先にcommitしてから
L3／UserMemoryをprojectionし、migrationは既存event、重複排除、confirmed、forget、supersede、Recallを不変のまま保持します。

次は全targetの最終受入条件であり、第一段階UserMemory owner APIの配備gateとは分けます。

1. CORE 02、04、06、08、CMD、Toolsの責務を`terminal -> CMD -> CORE -> owner store／outbox -> receipt`の一方向で追跡できる。
2. current／target／未実装／配備済みを分離し、既存2 commandのsource test成功を導入済みCLIの証拠にしない。
3. ProfileExtractorとThreadSummarizerのLLM出力がcandidate／summary residualに限定され、COREのschema、evidence、scope、dedupe検証を通らない保存がない。
4. normal ChatがL1 Raw evidenceを経由し、synthetic evidence、assistant-only evidence、candidateのprompt注入がない。
5. EndTurn、trace、memory state、archive、lifecycle、Parquetの部分失敗がtyped outcomeとreceiptに残る。
6. plan／dry-run、request_id、reason、idempotency、hash／count manifest、atomic finalize／cleanup、verifyを実際のowner routeで確認する。
7. same revisionのversion／commit、`rencrowctl memory --help`、target command dry-run、CORE capability／route handshake、typed receipt、authenticated owner-scope E2Eが揃う。未確認は未配備とする。

### Chatにおけるエピソード想起

Chatの記憶想起はKVキャッシュ制御ではなく、現在の話題に関連する過去のエピソードをCOREが検索し、Agentの非表示コンテキストとして渡す機能とする。Agentはそのエピソードを回答の参考にとどめてもよく、話題に合う場合は「そういえば以前……」などの自然な発言として会話へ出してもよい。

- 想起しただけのエピソードは会話履歴へ保存しない。
- COREは、想起結果をAgentの発言に見せかけた偽の会話messageとして履歴へ直接挿入しない。
- Agentが実際に口に出した内容は、通常のassistant発言として共通Chat履歴へ保存し、以後の会話コンテキストに自然に含める。
- 会話履歴とrolling summaryは現在の会話文脈、エピソード想起は過去の出来事の連想、Knowledge検索は仕様や事実の参照として区別する。
- 会話履歴、過去のエピソード、確定済みのユーザー記憶は、同じ認証済み利用者と許可scopeの中では全Agentの共通記憶とし、Agentのroleによってアクセスを制限しない。別利用者のprivate memoryや`family:shared`へ昇格していない情報は共有しない。Knowledge、外部検索結果、運用情報は共通記憶と混同せず、能力と安全policyに応じた個別の注入制限を維持する。

### X Bookmark収集・Knowledge取込

この節を、X Bookmarkを個人用Knowledge候補として収集する際のデータ意味、スレッド境界、
信頼度、取込状態の正本とします。収集runtimeとbrowser固有処理はRenCrow_Toolsのoptional
CLI `rencrow-x-bookmarks`が所有し、COREは出力recordの意味、staging、review、promotion、
Recallを所有します。X APIを標準runtimeの依存にせず、利用者がログインを許可した専用browser
profileから`https://x.com/i/bookmarks`の可視DOMをread-onlyで取得し、そこに明示された外部URLは
cookieを共有しない一時browser contextでリンク先本文まで取得します。

収集はBookmark追加、解除、投稿、返信、Like、DM送信を行いません。Bookmark一覧をscrollし、
数値status IDで重複排除します。既知IDのいずれかへ到達、新規IDのない既定回数への到達、
または明示したscroll上限への到達を停止条件とします。正常にartifactをatomic出力した後だけ、
今回観測した全status IDをrepository外の既知ID stateへmergeします。

同一ユーザーの連続返信は、次の規則で1recordへまとめます。

1. 各Bookmarkのstatus詳細を可視DOMで開き、Bookmark対象の投稿を特定する。
2. 対象投稿を含み、正規化した`author.username`が前後へ連続する最大範囲を1スレッドとする。
3. 別username、author不明、または取得できたDOMの境界へ達した時点で範囲を切る。別usernameを
   挟んだ後に同じusernameが再登場しても同じスレッドへ含めない。
4. 複数のBookmarkから得たスレッド候補は、投稿ID集合が1件以上重なる場合だけ1recordへ
   coalesceする。usernameが同じという理由だけでは統合しない。
5. status詳細の取得に失敗した場合は元のBookmarkをsingletonとして残し、
   `meta.thread.lookup_status=failed`を記録する。失敗を空の成功や欠落へ変換しない。

長文Noteは、可視DOMに`tweet-text-show-more-link`がある投稿または引用投稿について、同じ画面内の
展開buttonをread-onlyで操作してから本文を取得します。展開操作によってBookmark追加、投稿、Like
その他のX上の状態変更は行いません。Bookmark一覧とstatus詳細の展開成功回数を
`note_expand_click_count`へ記録し、DOM再描画等でclickできなかった回数は
`note_expand_failed_count`として欠落を隠しません。Community Noteは`community_notes`として表示本文、表示中の
link、`capture_status=visible_text`を投稿単位で保持し、統合スレッド上位にも重複排除して統合します。

投稿、引用投稿、外部preview、X Article coverに表示された画像と動画は、別のKnowledge cardへ
分割せず同じrecordの`media`へ保持します。画像は`type=image`、取得元URL、Xの可視DOMに設定された
Altを持ち、動画は`type=video`、URL、取得できる場合はAltとposterを持ちます。画像binaryはJSONLへ
複製せず、URL-backed mediaとして保持します。`raw_text`にも`[画像 n]`、画像の説明（Alt）、画像URLを
文章として続け、Altが未設定の場合は推測せず`Alt未設定`と明記します。動画も同じ規則で文章化します。

引用／リンク先は別のKnowledge cardへ分割せず、元のBookmarkまたは統合スレッドと同じrecordへ
保持します。可視DOMに引用投稿がある場合は`kind=x_post`としてstatus ID、URL、関係種別、本文、
author、時刻、link、mediaを取得します。本文中のX status URLだけを取得できた場合も
`capture_status=url_only`で残します。外部URLは`kind=external_url`としてURL、表示文字列、
X上に表示されたpreview textとmediaを保持したうえで、そのURLへ遷移して最終URL、content type、
page title、description、本文、取得時刻、切詰め有無を取得します。本文取得成功は
`capture_status=content_fetched`、取得失敗は`fetch_failed`、localhost、loopback、private、
link-localその他の非public宛てを遮断した場合は`blocked_private_network`、1回の取得上限を超えた
場合は`fetch_skipped_limit`として理由を構造化して残します。外部ページから発見したURLをさらに
辿る再帰crawlは行いません。redirect先とsubresourceも同じnetwork境界で検査し、Xの認証Cookieを
外部siteへ共有しません。既定は1 URL 30秒、本文100000文字、1 run 1000 unique URLを上限とします。

参照はX投稿ならstatus ID、外部URLならfragmentを除いた取得元URLで重複排除します。スレッドでは各投稿の
`references`へ対応関係を残し、record上位にも全投稿の参照を統合します。引用または外部本文の
取得に失敗しても元投稿、URL、取得済みpreviewを失わず、失敗状態を付けて同じcardに残します。

収集artifactのschema versionは`1.4`です。`raw_capture.jsonl`は可視DOMと外部本文の取得結果、
`rencrow_core.jsonl`はCORE import用record、`report.json`は実行結果です。1つのsingletonまたは
統合スレッドを`rencrow_core.jsonl`の1行とし、次の意味を固定します。

| field | 契約 |
| --- | --- |
| `domain` | 通常Recallの既定domainである`general` |
| `id` | スレッド先頭投稿の数値IDを使う`x:<root_tweet_id>` |
| `source_id` | `x:bookmarks_browser` |
| `source_url` | スレッド先頭投稿のcanonical status URL |
| `raw_text` | singletonは展開後の長文Noteを含む本文またはstatus URL。スレッドは投稿順の`[i/N] 本文`。各投稿のCommunity Note、画像／動画のAltとURL、引用X投稿、外部ページのtitle、description、取得本文、URLをラベル付きで同じ本文へ続ける。取得失敗時は取得済みpreviewとURLを残す |
| `title` / `summary` / `keywords` | 原文から作る検索用projection。原文の代替正本にしない |
| `license_note` | `private user bookmark; user-reviewed migration/collection` |
| `meta.collection` / `meta.platform` | `x_bookmark` / `x` |
| `meta.source_confidence` | `low`。Bookmarkであることを事実確認済みの意味にしない |
| `meta.review_status` | `user_bookmarked`。Knowledgeへの採用状態として扱わない |
| `meta.provenance.capture_method` | `visible_dom` |
| `meta.provenance.external_content_method` | 外部URLを処理した場合は`isolated_playwright_navigation`、外部取得対象がないか無効化した場合は`not_attempted` |
| `meta.media` | 投稿と統合スレッドの画像／動画。`type`、URL、可視DOMのAlt、動画posterを保持 |
| `meta.community_notes` | 投稿と統合スレッドのCommunity Note本文、link、取得状態を保持 |
| `meta.references` | record内の引用／リンク先。`x_post`または`external_url`、参照内のmedia／Community Note、取得状態、外部ページの`resolved_url`、`content_type`、`page_title`、`page_description`、`body_text`、`body_char_count`、`body_truncated`、`fetched_at`、`fetch_error`を保持 |

`meta`にはprovenance、author、投稿時刻、link、media、references、repost等の
`social_context`を保持します。`meta.thread`には少なくとも
`lookup_status`、`grouped`、`root_tweet_id`、`bookmarked_tweet_ids`、`tweet_ids`、
`status_urls`、`post_count`を保持し、取得できた場合は投稿順の`posts`を保持します。
既知ID stateにはrootだけでなく、`bookmarked_tweet_ids`と`tweet_ids`の全IDを保存します。

`report.json`は`bookmark_card_count`、統合後の`collected_count`、
`thread_lookup_count`、`thread_lookup_failed`、`threaded_record_count`、
`thread_post_count`、`reference_count`、`x_post_reference_count`、
`external_reference_count`、`media_count`、`image_count`、`media_alt_count`、
`community_note_count`、`note_expand_click_count`、`note_expand_failed_count`、外部本文の試行／成功／失敗／遮断／上限skip件数と取得文字数、停止理由、
既知ID件数、artifact名を含めます。Cookie、token、CDP URL、
browser profile pathはartifact、標準出力、logへ含めません。

`rencrow_core.jsonl`は`rencrow knowledge import-core-jsonl <path>`を通してCOREのpending
stagingへ取り込みます。Toolからproduction DBへ直接書きません。Bookmark登録と収集は、内容の
真偽確認、採用、Knowledgeへのpromotionを意味しません。外部SNS投稿はlow-confidenceの参照候補
として保持し、確定Knowledgeへのpromotionには利用者または許可されたreview workflowによる
明示確認を必須とします。

`import-core-jsonl`は既定で全recordをpending stagingへ保存し、`domain`省略時は`general`を使います。
同期的な明示reviewでは`--reviewed`を指定するとvalidationまで行い、`--reviewed --promote`を
同時指定した場合だけvalidation通過recordをJSONLのdomainへKnowledge promotionします。
`--promote`単独はstaging書込み前に拒否します。JSON reportはrecordごとの`event_id`、`staging_id`、
domain、状態、validation issueを返しますが、拒否した`raw_text`を含めません。同じidentityと本文の
再実行は同じstaging IDとKnowledgeを更新し、重複recordを作りません。

#### Heartbeatによる定期収集

CORE Heartbeatは、明示的に`heartbeat.x_bookmarks.enabled=true`とした場合だけ、
RenCrow_Toolsの`rencrow-x-bookmarks --headless`を定期実行します。既定はCORE起動直後に
1回実行し、以後6時間ごとです。この機能はoptional browser sidecarであり、無効時は
Go標準runtimeにNode.js、Playwright、browser profileを要求しません。

1つの収集runが実行中なら次の定期tickは重複起動せずskipします。収集は他のHeartbeat処理を
塞がない独立goroutineで実行し、既定90分の時間制限とCORE停止時のcancelに従います。
自動retry loopは行わず、失敗後は次の通常intervalまで待ちます。これによりログイン切れや
X側の制限時に高頻度の再試行を起こしません。

各runはrepository外の専用output root配下へ一意なdirectoryを作り、CLIがatomic出力した
`raw_capture.jsonl`、`rencrow_core.jsonl`、`report.json`を監査証跡として残します。CLI成功後に
COREが同じprocess内のKnowledge import境界から`rencrow_core.jsonl`をpending stagingへ取り込み、
ToolsがDBを直接開く構成にしません。0件の正常収集は成功として記録します。CLI失敗、
timeout、artifact不備、import失敗は取得済みcard、既存staging、review、promotionを変更せず、
`heartbeat.x_bookmarks.started | completed | error | skipped_running`の観測eventと秘密を含まないlogに残します。

受け入れ条件は、起動直後と設定intervalで収集されること、実行中の重複runがないこと、
HeartbeatのIdleChat、Workstream、Backlogが収集中も停止しないこと、取得結果がpendingのまま
Viewerから読めること、CORE停止時にbrowser収集がcancelされること、失敗時に既存データと
Xのログインprofileを破壊しないこととします。

### X Bookmarkの利用・評価

X Bookmarkは「保存した投稿の倉庫」で完結させず、画像promptの再利用、株式情報の
裏取り、RenCrow改善候補の評価、LLM候補の資源適合性評価に使います。収集recordは
immutableな原資料として残し、分類、検証、評価、提案、KnowledgeはCORE所有の派生データとして
分離します。派生データは収集済みの本文、Alt、画像、外部本文、URLを上書きしません。

#### 自動分類とuse case Tag

COREは1recordに1件以上の`use_case_tags`を付与します。Tagは将来の再分類とViewer絞り込みに使う
固定IDの`major`／`minor`ペアであり、1recordへ根拠の強い順で最大5件付与できます。`use_cases`は
`use_case_tags[].minor`を重複排除した互換projectionとします。

| `major` | 大分類 | 許可する`minor` |
| --- | --- | --- |
| `ai` | AI・モデル | `ai_tip`、`llm_catalog`、`agent_automation` |
| `creative` | 画像・映像・音声・デザイン | `image_prompt`、`creative_reference`、`video_audio_recipe` |
| `engineering` | 開発・Tool・運用 | `code_recipe`、`tool_catalog`、`workflow_runbook`、`security_advisory` |
| `finance` | 株式・金融調査 | `equity_research` |
| `research` | 調査・時系列情報 | `research_digest`、`news_watch` |
| `business` | 事業・収益化 | `business_idea` |
| `learning` | 教育・説明資料 | `education_reference` |
| `general` | その他の参照資料 | `general_reference` |

各`use_case_tags`は`major`、`minor`、`confidence`、`method=rules | llm`、短い`evidence`を
保持します。record上位の`classification`は`schema_version`、`classifier_revision`、
`classified_at`、`needs_review`、使用した論理`execution_alias`を保持します。物理Backend URL、
物理model path、credentialは保存しません。LLM分類は正規の
`CORE -> RenCrow LLM Gateway -> RenCrow LLM Runtime -> Backend -> Model`経路だけを使います。
既存検索との互換projectionとして、元の`keywords`を残したまま`category:<major>`と
`use-case:<minor>`を追加します。

CLI規則で十分な根拠が得られるTagはCLIだけで付与します。旧Vaultで人手整理済みのカテゴリkeywordは
元keywordを残したままCLI evidenceとして利用できます。未分類、低confidence、複数分類の競合、
`equity_research`または`security_advisory`の低confidence候補だけをLLM補完対象にできます。
分類不能時もrecordを欠落させず、`general/general_reference`と`needs_review=true`を付与します。
分類結果は別artifactへ書き、収集済みの本文、Alt、画像、外部本文、URL、元の収集artifactを
上書きしません。同一classifier revisionでの再実行はTag順序と内容について冪等にします。

分類は事実確認、信頼性確認、採用、Knowledge promotionを意味しません。`equity_research`、
`security_advisory`、時点依存情報は分類後も未検証候補です。分類済みartifactをCOREへ再取込する
場合も既存recordのidentityとpending状態を維持し、自動promotionしません。

受け入れ条件は、全recordが1件以上の許可済み`major`／`minor`ペアを持つこと、
`use_cases`と`use_case_tags[].minor`が一致すること、入力artifactのhashが変化しないこと、
LLM失敗時もCLI分類またはreview待ちへ安全に縮退すること、LLM接続なしでもCLIだけで完走できること、
Tag件数、method別件数、review待ち件数、失敗件数をreportで検証できることです。

用途別の評価結果は`source_record_id`、workflow種別とrevision、実行時刻、判定、根拠、
参照URL、失敗工程を保持します。Viewerで原文を閲覧しただけで外部取得、LLM評価、
Knowledge promotionを開始しません。評価にLLMを使う場合は正規の
`CORE -> RenCrow LLM Gateway -> RenCrow LLM Runtime -> Backend -> Model`経路を使い、
物理backendへ直結しません。

#### 画像prompt Viewer

`image_prompt`は、参考画像とその画像を生成・編集するためのpromptを1つの表示単位で
扱います。画像とpromptを別cardへ分割しません。Viewerは画像を主要要素とし、対応する
prompt原文、promptの取得先（投稿、同一スレッド、長文Note、引用投稿、外部本文）、
投稿者、日時、元URLを同じcardで確認できるようにします。promptのCopyは出典ラベルや
Altを混ぜず、保存したprompt原文だけをコピーします。

Altは画像の補足説明としてpromptと分けて表示し、promptの代用にしません。複数画像と
複数promptの対応関係が原資料から確定できない場合は`association=unknown`とし、推測で
結び付けません。画像URLが失効した場合も原URLと取得状態をcardに残します。このViewerは
参照と再利用のための機能であり、表示やCopyだけで画像生成を開始しません。

受け入れ条件は、1card内で画像、prompt原文、Alt、出典を判別できること、Copy結果が
prompt原文と一致すること、画像がないまたは関係不明でもrecord全体が欠落しないことです。

画像promptの利用処理は、利用者が明示的に開始した1record単位の
`image_prompt_draw` workflowとします。候補Tagだけを生成可否の根拠にせず、論理`worker` aliasが
原資料からprompt原文、negative prompt、取得箇所、画像との対応関係を再抽出します。判定は
`ready | not_applicable | needs_review`とし、`ready`だけを
`CORE -> RenCrow_Image -> configured backend`の正規経路へ渡します。画像生成結果は元Bookmarkと
同じ派生結果に紐付け、再実行時は同じworkflow revisionとsource recordの完了結果を再利用します。
候補一覧の表示、検索、page送りだけではLLM評価も描画も開始しません。RenCrow_Imageが無効または
unavailableの場合はprompt抽出結果を保持して`image_generation`工程をblockedとし、別経路へ
fallbackしません。

受け入れ条件は、誤分類候補が描画されないこと、1回の明示操作が最大1recordを処理すること、
prompt抽出成功後の画像生成失敗でpromptを失わないこと、完了済みrecordをresumeして重複描画しない
こと、生成画像から元Bookmark、prompt原文、取得箇所へ戻れることです。

#### 株式情報の裏取りとKnowledge化

`equity_research`のX投稿は調査の端緒であり、確認済み事実ではありません。投稿内の
主張を会社、銘柄、対象期間、数値、事象の単位に分解し、企業IR、取引所の適時開示、法定開示、
規制当局資料、企業の公式決算資料などの一次資料で検証します。報道、まとめ、他のSNSは
調査補助に使えますが、それだけをKnowledge promotionの根拠にしません。

主張ごとの検証状態は`unreviewed | verified | partially_verified | contradicted | unresolved | stale`
とします。結果にはX上の主張、事実、意見、推測の区別、一次資料URL、資料公開日、
確認日、対象時点、反証または不足資料を保持します。時間で変化する情報は対象時点と再確認条件を
必須とし、期限後は`stale`として再検証するまで現在事実としてRecallしません。

`verified`の主張だけをKnowledge候補にできます。`partially_verified`、`contradicted`、
`unresolved`、`stale`は調査記録として残し、確定事実としてpromotionしません。Knowledgeには
X投稿ではなく一次資料を事実根拠として紐付け、利用者または許可されたreview workflowの
明示確認後にpromotionします。このworkflowは投資助言、売買推奨、注文、自動取引を行いません。

#### AI TipsのRenCrow適合性評価

`ai_tip`は、現行のCORE正本、実装、production wiring、設定と照合してRenCrow改善への
価値を評価します。評価軸は、根拠の信頼性、アーキテクチャ適合性、期待効果、影響module、
実装・運用cost、新規依存、securityとprivacy、Windows・Linux・macOS影響、既存機能との重複、
陳腐化、回帰riskです。

判定は`valuable | conditional | not_applicable | obsolete | insufficient_evidence`とします。
`valuable`または`conditional`の場合だけ、利用者へ改善提案を出します。提案には原Tipの要旨、
裏付け資料、何が改善するか、影響moduleと正本、前提条件、cost、risk、検証計画を含めます。
その他の判定も評価記録として検索可能に残しますが、改善提案として通知しません。評価と提案は
コード、設定、dependency、runtimeを変更しません。Codexによる実装は、評価workflowとは分離した
ユーザーの明示的な実装指示を起点にします。RenCrow内に人待ちstatusを作りません。

明示的な`ai_tip_rencrow_evaluation` workflowは1recordずつ論理`worker` aliasで評価し、
`valuable | conditional`だけを同じsource recordから決まる安定IDで実装リストへ追加します。
追加時の状態は現行互換の`proposal_review`としますが、これはAgentによる再検証対象を表し、人の返答待ちを
意味しません。HeartbeatのBacklog intakeやCoder実行対象にはせず、Agentが根拠、前提、代替案を再考して
新revisionを作ります。Codexによる実装は別のユーザー指示を起点にします。
`not_applicable | obsolete | insufficient_evidence`は評価結果だけを残し、実装リストへ追加しません。
同じworkflow revisionの再実行は評価結果と実装候補を重複作成せず、LLM失敗、保存失敗、timeoutは
元Bookmarkと以前の評価結果を変更しません。

#### LLMカタログと現有資源評価

`llm_catalog`は、model family、parameter size、用途、license、release、公式model cardと一次情報を
整理します。利用可能性は一般論で判定せず、評価時点の実測または正規moduleが報告した
host、OS、CPU、GPU・VRAM、RAM、空きstorage、既存Runtime・Backend・driverのinventoryに対して
評価します。inventoryの取得時刻と取得元を残し、credential、token、秘密を収集しません。

評価には、必要quantization、予測memory、context条件、Backend・driver対応、想定速度、消費電力と
運用負荷、license条件、想定Execution Role、三OSでの配置条件を含めます。ベンダー値、第三者値、
RenCrowでの実測値を混同せず、実測でない速度を実績として報告しません。

結果は`usable_now | usable_with_conditions | runnable_but_impractical | unavailable_with_current_resources | insufficient_information`
のいずれかとし、必要条件、想定role、根拠、評価時点を利用者へ報告します。資源、Runtime、
Backend、driverが変更された場合は旧判定を現在事実として再利用せず、再評価します。評価workflowは
modelのdownload、install、起動、現行bindingを変更しません。Codexまたはhost operatorによる変更は、
評価workflowとは分離したユーザーの明示的な実行指示を起点にします。

#### 検索・Recall・Viewer表示

Viewerは原資料、`use_cases`、評価状態、検証状態、promotion状態で検索・絞り込みでき、
各評価から元Bookmark、外部本文、検証根拠へ戻れるようにします。初期表示は次に利用できる
内容と未確認事項を要約し、生JSON、全ログ、全証拠は詳細表示に分離します。デスクトップと
`390x844`の狭幅表示で、カードの本文、画像、状態、主操作が判別できることを受け入れ条件とします。

promotion済みKnowledgeだけを確定事実のRecall対象とし、pending、未検証、反証済みの内容を
確定事実としてAgent promptへ注入しません。調査候補として表示する場合は低信頼と状態を明示し、
出典と検証時点を隠しません。

### Windows Vault由来X Bookmarkの移行

旧Windows VaultのX Bookmarkは、収集済みの旧形式資料をUbuntu上の現行RenCrow形式へ変換する
一回性の移行workflowで扱います。移行元Vaultはread-onlyとし、削除、リネーム、上書き、属性変更を
行いません。機器固有pathはsource codeへ埋め込まず、実行時に明示された移行元と、repository外の
制限されたUbuntu inboxを使います。

移行は次の順で行います。

1. 移行元のファイル数、相対path、size、SHA-256、文字encodingをmanifestに記録する。
2. Ubuntu inboxへ複製し、複製後の件数とSHA-256がmanifestに一致することを確認する。
3. 旧Markdown、JSON、JSONL、CSVを元ファイル単位でparseし、schema `1.4`とCORE import契約に合わせた
   recordへ変換する。存在しないtweet ID、投稿者、日時、Alt、本文を推測で補わない。
4. X status ID、canonical status URL、最後に原ファイルhashの順で重複判定し、Ubuntuで直接収集済みの
   recordと照合する。新しいrecordで豊富な収集結果を古いVaultデータで上書きせず、旧source pathと
   hashを追加provenanceとして統合する。
5. `dry-run`で入力数、変換数、重複数、skip数、失敗数、理由、出力hashを報告し、apply時は
   `rencrow knowledge import-core-jsonl`を通してpending stagingだけへ取り込む。

変換recordは原ファイルの相対path、SHA-256、旧形式、移行run ID、変換時刻をprovenanceに
保持します。workflowはcheckpoint付きで冪等とし、同じmanifestを再実行しても重複recordや
重複Knowledgeを作りません。parse失敗、hash不一致、対応外形式、CORE import失敗は成功へ丸めず、
対象を残して工程別に報告します。変換ツールはRenCrow_Tools、recordの意味、staging、review、
promotion、RecallはRenCrow_COREが所有します。

## 継続作業と自動実行

Backlog、Scheduler、Heartbeat、Workstream が長時間作業を管理します。外部公開、送信、請求、契約、価格決定などのhigh-impact actionもowner-reply待機を挟みません。Workerが実行時にcapability、scope、allowlist、sandbox、credential、対象、risk policyを同期評価し、許可なら実行、条件不足または禁止なら理由付きで`blocked`にします。`draft`は成果物の作業状態であり、実行判断の待機状態ではありません。

### 長時間Agent Runの再起動Resume

COREが所有する長時間Agent Runは、LLMのprocess memoryや会話再送をresume正本にしません。`run_id`、
`workstream_id`、元のgoal、最後にcommit済みのcheckpoint revision、次action、queue identity、lease、
attemptをSuperAgent owner storeへ永続化します。LLM request途中のtoken位置は再開せず、最後にdurable commitされた
step境界から同じ`run_id`と`job_id`で再実行します。

queue claimは期限付きleaseです。稼働中runnerはheartbeatでleaseを更新し、CORE停止でheartbeatを失った
`claimed` itemだけをlease expiry後に再取得します。未失効leaseを別runnerが取得してはなりません。resume要求は
同じ`run_id + checkpoint_revision`から決定的なqueue identityを作り、同じ要求を再送してもqueueを増やしません。

checkpointは完了済みstep、次action、成果物／外部effectのreceiptまたはidempotency identityを指せる状態だけを
`resumable`とします。自然言語summary、会話履歴、`running`表示だけから完了位置を推測しません。checkpointを持たない
run、または未receiptの非冪等effectを含むrunは自動resumeせず`blocked`とします。会話履歴のRecall成功と実行Resume成功は
別の受入条件です。

## LINE通知

COREのLINE channelは、受信Webhook、replyTokenを使う同期返信、任意時刻のpush通知を同じadapterで提供します。任意通知とHeartbeatは`channels.Registry`から既存LINE adapterの`Send`を呼び、LINE Messaging APIのpush endpointを使います。replyTokenは任意通知へ転用せず、別のLINE senderを追加しません。

LINE Webhookは`POST /webhook/line`で受け付け、生のrequest bodyとChannel Secretで署名を検証してからeventを処理します。GET、署名なしPOST、署名不一致POSTを正常なWebhook受信として扱いません。

通知先は`heartbeat.channel`と`heartbeat.chat_id`を第一候補とします。LINEの`chat_id`はprefixから個人`U`、group`C`、room`R`を判定し、不正なIDや未展開の環境変数を送信しません。LINE通知先が未設定の場合だけ、署名検証とchannel policyを通過した最初の個人DMの`source.userId`を`workspace_dir/state/line_notification_target`へ`0600`で登録できます。登録用の本文`通知先登録`は通常CHATへ渡さず、reply messageも送らないため、後続のpush testを含む外向き送信を1通に保てます。このfallbackは既存targetを自動上書きせず、group／roomを自動登録しません。

管理者が明示的に任意通知を送る入口は`rencrow channels send --message TEXT`です。`--dry-run`はchannel初期化、送信先解決、target種別、秘匿表示までを確認し、Messaging APIを呼びません。実送信時も完全なLINE ID、Channel Secret、Access Tokenを標準出力やlogへ出しません。この入口はCOREの運用通知用であり、生活Routine、端末別配信、acknowledgement、snoozeの所有権をRenCrow_ASSISTANTから移しません。

ASSISTANT所有のLINE生活通知はlocalhost限定の
`POST /internal/assistant/notifications/line`から同じLINE adapterへ渡します。requestの
`trace_id`と`delivery_id`は必須で、タイトルは20文字以下、本文は100文字以下です。COREは
`delivery_id`ごとのtransport receiptを`workspace_dir/state/assistant_line_push_receipts.jsonl`
へ`0600`で保存し、同じIDの送信済みpushを再送しません。送信結果が不明な場合は
`uncertain`として同じIDの自動再送を拒否します。このreceiptは低レベル送信証跡であり、
利用者別Delivery状態の正本はASSISTANTです。完全なLINE ID、credential、通知本文をreceiptへ
保存しません。

## RenCrow_ASSISTANTとの境界

目覚まし、個人・家族予定、天気、交通、利用者別ニュース選定などの決定論的な生活RoutineとPUSHはRenCrow_ASSISTANTが所有します。COREはニュースの事実情報を共有`DailyNewsBrief`として収集・整形し、ASSISTANTから移譲されたAgent対話、調査、生成、継続作業、policy判定を伴うside effectを実行し、相関IDと利用者scopeを維持して結果を返します。

ASSISTANTが端末向けの短文化、発話、振動、acknowledgement、snooze、retryを所有し、COREは端末ごとの配信状態を正本として持ちません。ASSISTANT経由でも利用者scopeを越えず、Agent切替によって権限を広げません。

## ニュースの用途とデータ境界

ニュースは、目的の異なる次の3つのデータ商品に分けます。収集元が同じでも、生成物、鮮度、根拠、利用者向けの扱いを混同しません。

| データ商品 | 内部名 | 目的 | 主な利用者 |
| --- | --- | --- | --- |
| IdleChatのお題素材 | `IdleChatTopicSeed` | 会話のお題候補を作る。幅広さを優先し、SNS投稿を確認済み事実へ昇格しない | IdleChat |
| 朝刊ニュース | `DailyNewsBrief` | 04:00 JSTに準備した事実ベースの「今朝のニュース」を利用者へ説明する | Chat、Mio、ASSISTANT |
| 即時検索 | `LiveNewsSearch` | 「最新」「速報」「今起きていること」など、準備済みデータより新しい情報を取得する | Chat、Mio |

`DailyNewsBrief`は、04:00 JSTのニュース収集、特定URL本文の取得、翻訳、用語補足、サマリ、事実と分離したShiroの見解を含む読み取り専用の準備済みデータです。これは共通のニュースDBや利用者別配信履歴ではありません。利用者ごとの選定、既読、配信時刻、件数、PUSH、deliveryはASSISTANTが所有します。

共通ニュースDBはCOREのL1 SQLiteに置き、既定14 RSS／AtomをSource Registryへ定義・登録します。Sportsは既定disabledで収集対象外、他13 sourceはenabledとして定期取得し、validationを通過した項目だけを`l1_news_item`へ昇格します。これは`DailyNewsBrief`そのものではなく、
provenance、重複排除、時系列検索と朝刊cache欠損時の読み取りfallbackです。source bootstrapは既存URL、
既存ID、利用者の無効化を上書きしません。

L1 fallbackから組み立てたbriefは`Source=persistent_news_db`とし、04:00処理済みcacheの
`Source=scheduled_daily_cache`、前景検索の`Source=live_news_search`と観測上も区別します。

`IdleChatTopicSeed`は日次収集の共通入力からタイトル、カテゴリ、source typeなどのお題素材を選んだものです。`DailyNewsBrief`のニュース項目を再利用する場合もありますが、Wikipedia Randomなど朝刊対象外の外部刺激を含められます。IdleChatに入力枠を設けてニュースを選択させたり、IdleChatの画面をユーザー向けニュース閲覧画面として扱ったりしません。

「今朝のニュースを教えて」「朝のニュースは？」はIntent `daily_news_brief`として通常の汎用検索より前に検出し、当日04:00 JSTの`DailyNewsBrief`を最初に読みます。回答はMioを第一応答者とし、キャッシュが`ready`または`partial`なら外部検索を先に実行しません。キャッシュが空、未準備、または対象日より古い場合だけ`LiveNewsSearch`へフォールバックし、ニュースCollector／WorkerがToolを実行して構造化結果を作ります。Mioの会話処理からニュース収集Toolを直接呼び出しません。Mioが利用できない場合に限りShiroが同じ準備済みデータを要約します。

朝刊キャッシュがない前景要求では、待ち時間を隠すためにMioからShiroへ「朝刊データが届いていないため収集Workerで確認する」旨を、ShiroからMioへ検索源・本文取得・重複確認などの作業手順と完了状態を、`agent.progress`イベントとして表示します。これは演出用の会話イベントであり、ニュース本文・検索結果・帰属情報を含めません。収集結果は別の構造化`LiveNewsSearch`コンテキストとしてMioへ渡し、最終的な説明とTTSだけをMioが担当します。

「最新のニュース」「速報」「今のニュース」は`LiveNewsSearch`として扱います。`DailyNewsBrief`の取得時刻と`LiveNewsSearch`の検索時刻を回答へ付け、両者を「リアルタイム」として混同しません。04:00前の「今朝」は当日分が未生成であることを明示し、前日の朝刊を使う場合は対象日を表示します。

Chatの利用者はIdleChatを選択しません。最初の回答では`DailyNewsBrief`から主要項目を番号付きリストで返し、「2番を詳しく」のような追加入力は同じbriefのitem IDを参照します。Viewerの`/viewer/idlechat/collection`は内部観測用snapshotのままとし、ユーザー向けニュース取得の経路にはしません。

### ニュース収集と考察の二段階契約

ニュースworkflowは、外部情報を固定する`collect`と、固定済み情報を解釈する`analyze`へ分離します。両phaseを暗黙に連続実行する`run-all`は設けません。収集だけ、または同じ収集結果に対する考察の再実行を、それぞれ独立して行えることを必須とします。

| phase | 入力 | 出力 | 禁止事項 |
| --- | --- | --- | --- |
| 収集 `collect` | CORE所有のsource policyと、明示された件数・期間条件 | immutableな`NewsCollectionArtifact` | LLM、翻訳、用語判定、要約、見解生成を実行しない |
| 考察 `analyze` | 1つの`NewsCollectionArtifact` | 元artifactを変更しない`NewsAnalysisArtifact` | 元ニュースを再取得しない、物理Model／Backendへ直接接続しない |

`NewsCollectionArtifact`は`schema_version=rencrow.news.collection.v1`、`collection_id`、開始・完了時刻、`ready | partial | failed`のstatus、error一覧と、各項目の`item_id`、title、category、source、`source_type`、元URL、最終URL、取得時刻、本文取得状態、content type、取得本文、本文SHA-256を持ちます。credential、翻訳、要約、見解、用語の既知／未知判定を含めません。完成fileはatomicに確定し、後工程はそのbyte列のSHA-256を入力系譜として記録します。

`NewsAnalysisArtifact`は`schema_version=rencrow.news.analysis.v1`、`analysis_id`、`collection_id`、入力artifactのSHA-256、開始・完了時刻、`ready | partial | failed`のstatus、error一覧と、各`item_id`に対応する原文の日本語訳、事実サマリ、事実から分離したShiroの見解、用語補足を持ちます。用語補足はterm、explanation、`contextual | confirmed | unresolved | unavailable`のstatus、`article_context | searched_source`の確認方法、確認元URLを保持します。入力にない`item_id`、重複`item_id`、`collection_id`またはSHA-256の不一致を受理しません。

不明語は最初に収集済み本文の文脈で説明します。本文だけで説明できない場合に限り、考察phase内の限定的な根拠収集として`web_search`で確認先URLを発見し、そのURL本文を直接取得します。この取得は用語確認のevidenceであり、元ニュース本文の再収集や`NewsCollectionArtifact`の変更ではありません。検索結果の見出し・抜粋を根拠にはせず、確認先本文を取得できない用語は`unresolved`にします。

Shiroの見解を名乗れるのは、COREが認証した実在Agent Shiroへ割り当てた考察結果だけです。RenCrow_ToolsのCLI、任意のLLM、test doubleはShiroの人格や見解を自称しません。考察requestは`CORE -> RenCrow_LLM Gateway -> RenCrow_LLM Runtime -> Backend -> Model`の正規経路を使い、Toolsは物理Model、provider、Backend URLを選択しません。

CLIの実装所有先は`RenCrow_Tools/tools/news/news_brief/cmd/rencrow-news`です。CLI名は`rencrow-news`、subcommandは`collect`と`analyze`だけを正規入口とします。`RenCrow_CMD`へ`rencrowctl news`を追加せず、CMDをニュース収集runtimeや独立product forkにしません。schema、意味、source policy、Agent帰属、検証、import、公開状態はCOREが所有し、Toolsはnative Go executable、HTTP／RSS取得、artifact serialization、tool固有validationを所有します。

## Economic Objective

Opportunity、EconomicTask、RevenueEvent、EconomicReflection を管理します。Heartbeat の discovery は候補の draft 作成までに制限し、外部実行を自動化しません。

Economic chainの`trace_id`は必須です。新しいOpportunityの作成時に未指定ならCOREが`trc_` prefix付きUUIDを生成し、EconomicTask、Workstream Goal、Artifact、Policy Decision、Delivery、RevenueEvent、Reflectionへ同じ値を引き継ぎます。各entity固有IDを`trace_id`の代用にせず、同じ商機から派生した成果物・判断・実行結果を横断して検索できるようにします。

OpportunityをWorkstreamへ接続するproduction use caseは、draft Goal、`economic_opportunity_brief` Artifact、そのArtifactを対象とする`economic_opportunity_execution`のPolicy Decisionを一度に生成します。3 entityは同じ`trace_id`を持ちます。この接続API自体は外部side effectを実行せず、後続の実行requestごとに同期policy判定を行います。

Deliveryは外部送信成功だけを表すrecordではありません。`external_send`、`publish`、`billing`、`contract`、`handoff`、`other`を扱う汎用entityとし、`draft`、`pending`、`blocked`、`failed`、`completed`、`cancelled`の状態を持ちます。外部side effectを伴うDeliveryは、許可されたPolicy Decisionと実行後evidenceなしに`completed`へ進めません。判断参照には`policy_decision_id`だけを使います。`ExternalSendApplyRecord`は外部送信adapter適用の監査recordとして残し、同じ`trace_id`を持つDeliveryへ対応付けます。

## PORTAL、Debug Viewerと観測性

Debug Viewerは会話、agent、job、log、workstream、policy decision、memory、advisor、economic stateをREST/SSEで表示します。RenCrow_PORTALは外部利用者向けViewerを`Chat`、`IdleChat`、`Games`の3系統で提供します。`Chat`はallowlist内の会話操作、`IdleChat`はAI VTuber部屋の読み取り、`Games`はゲーム選択、Agent選択、Agent-owned sessionの起動、観戦、Retry／Start overを扱います。raw traceは要約と詳細を分け、`unavailable`、`pending`、`degraded`、`error`を区別します。

Debug ViewerのMemoryナビは左端列の折り畳み内にDB別の入口を持ち、同じDBの内容を別DBの画面へ混在させません。`Conversation L1 Database`は設定済み`conversation_l1` DBのL0／L1／L3とL1由来の項目、`Conversation Archive`は`memory_archive.db`、`Knowledge Memory`は`knowledge_memory.db`、`Glossary`、映画・人物、`Tool Registry`はそれぞれの正本DBだけを読み取ります。`DB Catalog`はDB rowを読む画面ではなく、起動時にAgentへ供給した同一Data Capability Catalogから、全20 storeの所有者、data category、`available | unavailable | restricted | blocked`、安全なoperation、対応Tool、制限理由を表示するmetadata画面です。狭幅画面でも同じMemory optgroupを使います。

PORTALの`Chat`と`IdleChat`は同時に動作させません。可視状態の`Chat`画面が1つでもある間はIdleChatを停止し、停止が確認できるまでChatの入力をreadyにしません。可視状態の`Chat`がなく、可視状態の`IdleChat`画面が1つ以上ある場合はIdleChatを開始します。両方が存在する場合は`Chat`を優先します。最後の`IdleChat`画面が非表示または終了した後に、PORTALを理由としてIdleChatを動作させ続けません。画面の再読込、複数tab、browserの異常終了でも孤立した実行を残さないため、COREが期限付きの画面在席を集約して有効状態を決定します。

`Chat`画面は通常会話の`message.received`、利用者向け`agent.response`、既存契約で公開対象の`agent.progress`／`agent.acknowledge`を会話欄へ表示し、`idlechat.message`、IdleChat用TTS、SSE再接続で届いた過去のIdleChat eventを表示・再生しません。`IdleChat`画面は`idlechat.message`だけを会話欄へ表示し、Chatの送信欄と会話eventを表示しません。画面在席の通知はsurface lifecycleのための狭い例外であり、`IdleChat`画面から任意のwrite操作や手動開始・停止を許可するものではありません。

`IdleChat`画面はキャラクター切替操作を持たず、画面表示直後からMioとShiroを描画します。この描画はIdleChat開始確認の完了を待ちません。横画面と縦画面のどちらも各キャラクターを同じ向きの`Chat`画面と同じサイズにし、画面幅を縦に4等分した左1/4（`x=25%`）をMioの中心、右1/4（`x=75%`）をShiroの中心とします。KuroとMidoriは`IdleChat`画面へ表示しません。

PORTAL Chatのキーボード操作はOSによらず、修飾キーを伴わない`Enter`を送信、`Shift+Enter`を改行とします。IME／FEPの変換確定中は送信しません。会話本文、入力欄、トピック、主要状態表示の文字サイズは小／中／大の3段階を提供し、選択はclient localな表示設定として保持します。この表示設定はCOREの会話状態、message、recipient、権限を変更しません。

Debug Viewerの`Games`タブは、Game Bridgeの要約に加えてAgent-owned Launch Deskを表示します。利用者は`game_id`、Mio／Shiro／Kuro／Midoriの参加者、任意の`reason`、`turns`、`mode`を指定し、`POST /viewer/games/launch`から起動できます。成功時は`session_id`と対応するObserverリンク、失敗時はupstreamのerrorを同じ画面へ表示します。タイトル固有の参加人数制約はViewerへ複製せず、RenCrow_GAMES Observerの応答を正とします。

PORTALの`Games`はDebug Viewerの複製ではなく、利用者向けの最小surfaceです。`GET /viewer/games/status`の`supported_games`だけをAgent E2E対応タイトルとして選択可能にし、実行sessionは`/viewer/games/observer-api/games/sessions`から取得します。ゲーム画面はGAMES ObserverをPORTALと同一originのiframeへ表示します。移動、攻撃など各turnの操作はCORE上の対象Agentが判断し、利用者がAgentの代わりにActionIntentを入力するUIは設けません。PORTALのRetry／Start overはsession lifecycle操作であり、Agent判断の代替ではありません。

Games画面のPuruPuruはPORTAL documentがiframe外のoverlayとして所有し、GAMESの盤面描画を複製しません。Agentの発話として表示できるのは、ObserverFrameで`bridge.decision_mode=agent`、`decision.agent_id`が空でなく`frame.persona`と一致し、かつ`result.speech`に公開発話がある場合だけです。`decision.reason`、`RuleBasedBrain`、`DummyBrain`、local simulationの出力をAgent発話へ変換しません。音声化はPORTALからTTS実体を直接呼ばず、COREのTTS契約を使用します。

Debug Viewerは左端のMemoryリストに「映画リスト」「人物リスト」を独立して表示し、選択した一覧だけを映画catalog画面へ表示します。主画面は作品名または人物名と「みた」「すき」を横1段にした行の連続だけで構成し、summary、D0/D1カード、検索・絞り込みtoolbar、件数header、pager、詳細paneを混在させません。初回50件を索引順で読み、一覧末尾へのscroll時に次の50件を追加して全件へ到達可能にします。各行には独立した「みた」「すき」の2 checkboxだけを表示します。映画の「みた」は`familiarity=seen`、人物の「みた」はstorage互換の`familiarity=known`、「すき」は共通で`sentiment=like`として保存します。checkboxを外すと該当dimensionだけを空値へ戻し、他方を維持します。人物一覧は出演者roleへ固定せずcatalog内の全人物を対象にし、変更は映画catalog SQLiteへ自動保存して再読込後も維持します。backend APIは既存互換の`unseen | unknown | dislike`も受理しますが、通常の一覧入力にはnegative checkboxを表示しません。既存の鑑賞履歴と人物の好みsignalは明示評価がない場合の初期表示にだけ使い、Viewerで保存した明示評価を優先します。

#### 映画・人物のD0/D1カード投影

映画・人物のD0/D1は、映画catalog内の関係treeにおける派生カードの深度です。会話Memory、UserMemory、Memory L1の階層やKnowledge Relationのhopとは別の概念であり、D0/D1カードをMemory L1へ保存・昇格しません。通常の映画／人物リストには混在させず、cards API等の明示的な派生projectionで現在の映画catalogから決定論的に再計算します。

D0のrootは次のいずれかです。

- 映画は明示評価の`seen`（見た）または`like`（好き）。
- 人物は明示評価の`known`（知ってる）または`like`（好き）。
- 利用者が映画名、人物名、または正規化された映画.com URLを明示して取得し、取得・artifact検証・local catalog importまで成功した対象。
- 明示assessmentが存在しない場合に限り、既存の映画鑑賞履歴を映画の`seen`、人物の正のfavorite signalを人物の`like`としてfallbackする。

`unseen`、`unknown`、`dislike`だけの明示評価はD0 rootにしません。明示assessmentの行が存在する場合は、値が空でもwatch／favorite fallbackへ戻しません。複数のrootから同じカードへ到達した場合、カードの`depth`は最小値を使います。`depth`、rootからの経路、D1カードは派生状態であり、catalogへ重複保存しません。

D1はD0から検証済みの直接関係で到達するカードです。D0のroot対象は現段階では映画と人物に限定し、D1には次のカード種別を含めます。

- `PersonCard`：出演、監督、脚本、音楽担当、原作者など、映画.comが作品との直接関係を明示した人物。
- `MovieCard`：D0の人物から直接関係で得られる映画。
- `MusicCard`：映画.comが作品名を明示した音楽作品、主題歌、劇伴、サウンドトラックなど。
- `SourceWorkCard`：映画.comが作品名を明示した小説、漫画、舞台、ゲームなどの原作・参照作品。

`MusicCard`と`SourceWorkCard`の汎用work card正本は`hobby_graph`に置き、`movie_catalog`は映画側のcredit／直接関係とprovenanceを所有します。映画側に文字列しかなく、`hobby_graph`のvalidated itemへ確定できない場合でも、明示されたlabelとprovenanceを持つ`partial`または`unresolved` cardとして返せます。ID、作品種別、関係先を推測で補完せず、validated direct relationだけを採用します。D1カードからさらに別の人物・映画・workを自動展開せず、D2以降は表示・取得対象にしません。validated cardは`kind`と`target_id`で重複排除し、`target_id`のないpartial／unresolved cardは正規化label、relation、provenanceで重複排除します。root、depth、relation role、source、validation stateを表示できるようにします。

名前queryが複数のlocal候補に一致した場合は候補を返し、COREは勝手に1件を確定しません。利用者が候補またはURLを明示選択して成功した対象だけをD0にします。映画.comの`/search` queryを取得経路として使用せず、robots.txt、rate limit、その他のアクセス制約を迂回しません。外部取得はRenCrow_Toolsのoptional Go sidecar、COREは検証済みimmutable JSONLのtransactional importを担当します。

映画catalogの個人評価、watch／favorite fallback、明示取得rootはViewerのD0/D1投影にだけ使います。owner scopeのない個人情報を通常会話のCategoryRecallへ注入せず、CategoryRecallは従来どおり公開catalog projectionだけを返します。

#### 評価済み人物からの日本語関連作品収集

人物一覧で`known`または`like`を明示した人物に加え、`seen`または`like`の映画から`movie_people`の直接edgeで到達する人物を、利用者scope内の関連作品収集対象にできます。収集対象は
`映画 | ドラマ | 受賞歴 | 音楽 | アニメ | 小説 | 漫画`です。checkbox保存そのものは外部収集を同期実行せず、
対象選定と収集runを別状態にします。収集Workerは人物一人・一カテゴリずつ有界に進め、永続cursorとreceiptで再起動と重複を制御します。この収集結果から別の人物や作品を再帰的に収集対象へ追加せず、D1の直接関係境界を保ちます。未評価映画にだけ関係する人物、空値へ戻したroot、同一人物と確定できない外部候補を自動収集または確定しません。

人物identityは映画.com人物IDを起点に、氏名だけでなく既存作品、生年月日、所属、各sourceの外部IDを
照合します。同姓同名または証拠不足では`ambiguous | unresolved`を返し、検索結果の先頭を採用しません。
確定したidentityから、既存の映画.com artifact、Wikidataの公開CC0構造化データ、ジャパンサーチの
利活用条件を確認できるrecord、NDL Searchが申請不要と明示するCC BY／CC0／PDM書誌record、
文化庁事業のメディア芸術データベース、
認証不要のMusicBrainz非商用read-only GET、賞主催者等の公開公式ページだけを用途別sourceとして使えます。
利用契約、利用申請、API key、access token、課金契約を新たに必要とするsource、非公式の第三者APIは採用しません。
各adapterはsourceごとのrate limit、User-Agent、license、provenanceを守り、利用不能なカテゴリを契約必要sourceや
別sourceへ暗黙fallbackしません。

取得計画は、情報量と到達可能性が高い経路を先に試す決定的な契約です。利用者が人物とカテゴリを要求した各runは、
次の順序を変えずに評価します。

1. **対象判定と既存結果確認**：人物が`known | like`の明示評価を持つか、カテゴリが要求範囲内かを確認し、人物reference、
   category、sourceごとのpositive／negative receiptと有効期限を索引から読む。十分に新しい`ready`結果または
   `negative` receiptがあればそのsourceへのHTTPを発行せず、次のapplicable sourceを評価する。
   run全体を終了できるのはfreshなvalidated resultが十分な場合か、全applicable sourceがterminalな場合だけである。
2. **identityの一回解決**：映画.com人物ID、既存作品、生年月日、所属、保存済み外部IDを一度だけ照合する。
   `confirmed`になった外部IDは同一runの全カテゴリで再利用し、名前だけの一致をconfirmed identityにしない。
   `ambiguous | unresolved`ならカテゴリ別の外部取得へ進まず、その状態を返す。
3. **人物・カテゴリ計画の作成**：同一人物について要求されたカテゴリを一つのplanへまとめ、sourceごとのprovider batchを
   作る。planのpriorityは固定tier、カテゴリ、source名の順で決定し、同じproviderが複数カテゴリを一つの要求へまとめられる
   場合は一回のbounded query／paginationへ統合する。
4. **Tier 0（ローカル）**：既存`movie_catalog`、`hobby_graph`のnamed indexとcollection receiptを最初に使う。
   映画は既存映画artifact／catalog、その他カテゴリは既存のvalidated relationを優先し、全件scanや名前の部分一致は行わない。
5. **外部source照会**：現行revisionはカテゴリごとに実装・検証した一つの固定sourceだけを発行する。未実装sourceを
   fallback候補としてplanへ載せず、semantic negativeまたはrights rejectionはTTL receiptにしてterminalとする。

| category | 専門sourceの固定順序 | 最終確認の扱い |
| --- | --- | --- |
| `映画` | 既存`movie_catalog`／映画.com artifact | 映画catalogのvalidated relation |
| `ドラマ` | `jpsearch` | JPS-RDFの人物URIと直接relationを検証 |
| `受賞歴` | `japan_academy_prize` | 利用条件確認済みの場合だけ賞公式を最終authorityとする。現行productionは`rights_unverified`で拒否 |
| `音楽` | `musicbrainz` | 完全一致で一意なMBIDとrelease-group relationを検証 |
| `アニメ` | `mediaarts_db` | 映画.com作品証拠とMADB creditを照合 |
| `小説` | `ndl_bibliography` | 正式な著者IDと申請不要条件の両方を満たす場合だけ採用。現行productionは`rights_unverified`で拒否 |
| `漫画` | `mediaarts_db` | 映画.com作品証拠とMADB creditを照合 |

freshな`ready`またはnegative receiptがあれば同じsourceを再発行しません。現行revisionはカテゴリごとに一つの
実装済みsourceだけを持つため、そのreceiptでterminalになります。各queryは固定`LIMIT`とpagination上限を持ち、hostごとの
rate limit、`Retry-After`、指数backoffを守ります。複数sourceを追加する将来revisionでは、各adapterとlive E2Eが揃ったsourceだけを
明示的に順序へ追加します。

planは`plan_revision`とともに保存し、少なくとも次のmachine-readable情報を持ちます。

```json
{
  "plan_revision": "person-related-plan.v1/1",
  "person_ref_id": "person:7",
  "categories": ["ドラマ", "音楽"],
  "provider_batches": [{"source": "jpsearch", "categories": ["ドラマ"]}],
  "attempts": [{
    "source": "wikidata", "priority": 10, "reason": "tier1_cross_category",
    "status": "ready", "started_at": "RFC3339", "completed_at": "RFC3339",
    "item_count": 2, "error_code": ""
  }],
  "stop_reason": "enough_validated_results | all_sources_terminal | identity_ambiguous | unavailable",
  "next_source": "jpsearch"
}
```

`attempts`には発行したsourceだけを順序どおり記録し、未実行sourceを成功扱いにしません。各item／relationにはsource hit、
source record ID、canonical／evidence URL、取得時刻、authority、rights、`name_state`を残します。日本語名はsourceが提示した
場合だけ採用し、提示されなければ原名を保持します。categoryの結果は`complete | partial | unavailable | ambiguous | rejected`
のいずれかで終了し、`stop_reason`と`next_source`から未取得理由を再現できるようにします。

#### 作品サマリ（WorkSummary）の取得・保存・公開

人物との関係が検証済みの各作品には、作品そのものの説明を表す公開意味契約
`WorkSummary`を任意付与します。関係が確認できたこととサマリが取得できたことは別状態です。サマリがない作品も
有効な作品／人物関係として保存し、category結果の`summary_coverage`へ`ready`、`unavailable`、`total`の件数を返します。

artifact／DBのfieldは次の意味で固定します。

| 公開意味field | 永続field | 契約 |
| --- | --- | --- |
| `summary_original` | `description_original` | sourceが返した説明原文を改変せず保存する。空欄は概要未提供であり、タイトルの代用にしない |
| `summary_language` | `description_language` | 原文の言語。sourceの申告または検証済みlanguage tagを保存する |
| `summary_ja` | `description_ja` | sourceが提供した日本語説明、または原文説明だけを忠実に翻訳した日本語説明。作品名等の固有名詞は確定済みdisplay nameを使う |
| `summary_translation_state` | `description_translation_state` | `not_required | ready | failed | not_attempted`。原文は翻訳失敗でも保持する |

公開応答には`summary_ja`と`summary_state`を含め、`summary_state`は
`source_summary | translated_summary | unavailable`のいずれかとします。`source_summary`はsourceの日本語説明をそのまま採用した状態、
`translated_summary`は原文説明から忠実に翻訳した状態、`unavailable`は説明を取得できなかった状態です。通常の日本語UIへ外国語の
`summary_original`をサマリとして露出せず、原文・翻訳失敗の詳細は認証済みdebug／内部照会だけで確認できます。

サマリはsourceの説明事実だけを保持します。タイトル、出演者・スタッフ、受賞、レビュー、周辺本文、別作品、LLMの知識から
要約文を構成・補完・創作してはいけません。作品名、人物名、団体名、賞名などの固有名詞は、既にidentity検証済みの
`display_name` tokenを使い、サマリ翻訳の工程で新しい邦題を作りません。sourceに日本語作品名がない場合は原名を維持します。

保存・更新契約は次の順序で適用します。

1. 最初の人物／カテゴリ専門sourceの応答に説明fieldが含まれていれば、同じresponseから関係とサマリを同時に検証する。
2. 説明が欠けた作品へ後段summaryを追加するときは、保存済みの正確な`source_record_id`、canonical URI、ISBN、MBID、MADB ID、
   ジャパンサーチID、NDL IDで対象を指定する。名前だけ、部分一致、曖昧一致では更新しない。
3. COREの更新APIは1 requestあたり最大20作品、1作品あたり最大2つのsummary sourceに制限する。現行production providerは
   relation取得時の説明だけを取り込み、欠落作品を外部へ再照会するsummary enrichment workerは未実装である。
4. 後段sourceがサマリだけを補充する場合、identity、作品名、人物関係を上書きせず、独自のsource record・evidence・権利検証を満たした
   サマリfieldだけを追加する。

現行source優先順は、映画=`movie_catalog`、ドラマ=`jpsearch`、アニメ／漫画=`mediaarts_db`、小説=`ndl_bibliography`、
音楽=`musicbrainz`、受賞歴=`japan_academy_prize`です。MusicBrainzのrelation／release metadataだけでは作品サマリとみなさず、
説明がなければ`unavailable`です。受賞recordも受賞対象作品のサマリを代用しません。

各サマリには`source`、`source_record_id`、canonical／evidence URL、`retrieved_at`、content hash、language、rightsを記録します。
source・categoryのrefresh TTLを適用し、同一sourceの概要なしはnegative summary receiptとして保存して再取得を抑止しますが、
次の適用可能なsourceによる補充は許可します。既存関係の`relation_status`とサマリの`summary_state`は独立して公開します。
受入条件は、原文の非破壊保存、翻訳失敗時の原文保持、未提供時の明示的`unavailable`、名前／関係の非上書き、
`summary_coverage`の件数整合、同一artifact再importの冪等性です。

receiptはsource・人物・カテゴリ単位で永続化します。positive結果はsource／categoryのrefresh期限に従って再取得し、
結果がない、権利条件を満たさない、またはidentityが解決できない場合は短い再試行ではないnegative receiptをTTL付きで保存します。
429／5xx／一時的ネットワーク障害だけを有限回再試行し、`Retry-After`があれば優先します。意味的なempty、identityのambiguity、
rights rejection、schema不正は再試行せず、別sourceへ進めるかterminal状態にします。

source順序の自動昇格は、人物の印象や単発の成功を根拠にしません。source・category単位の直近90日のterminal attemptが
30件以上ある場合だけ、`validated hit率 × 平均完全性 ÷ (1 + p95 latency秒)`で同一authority内のpriorityを次回planへ反映できます。authorityの低いsourceを
identityまたは受賞歴の最終確認へ昇格させず、同率時は固定source名順でtie-breakします。採用した統計snapshotとplan revisionを
receiptへ記録し、計画変更を追跡可能にします。

利用者向けの説明、役割、関係、カテゴリ、取得状態は日本語で保存・表示します。ただし作品名、人物名、
団体名、賞名等の固有名詞は翻訳しません。取得元が日本語名とその根拠URLを提供した場合だけ日本語名を採用し、
日本語名がない場合は取得元の原名を`display_name`としてそのまま使います。LLM、機械翻訳、読み仮名、類似作品、
別sourceの曖昧一致から邦題・和名を生成または補完してはいけません。説明文を日本語化する場合も、文中の
固有名詞tokenは確定済み`display_name`へ固定します。

関連作品はカテゴリ別DBへ分散させず、映画と映画creditは`movie_catalog`、ドラマ、受賞、音楽、アニメ、
小説、漫画の汎用item・直接relation・provenanceは`hobby_graph`を正本とします。人物の全プロフィールを
複製せず、`hobby_graph`には`movie_catalog`人物IDと確定済み外部IDを結ぶidentity referenceだけを置きます。
公開sourceから取得したvalidated関連itemはCategoryRecallの`hobby_graph`読取sourceに接続し、ドラマ、受賞、音楽、アニメ、小説、漫画の明示的な話題または登録済み作品名に一致する場合だけRecallPack候補にします。`hobby_person_relations.validation_state=validated`の直接relationを必須とし、summaryがあれば日本語summaryを優先します。個人評価、収集運用状態、未検証relation、歌詞本文は自動注入しません。
通常参照は人物reference、category、relationを指定した索引queryに限定し、全件scan、任意SQL、全文payload
decode、名前の部分一致fallbackを行いません。

受入条件は、各カテゴリについて取得元、外部ID、原名、採用した日本語名と根拠、直接relation、取得時刻、
validation stateを追跡できること、同一artifactの再importが冪等であること、1カテゴリ失敗時も他カテゴリの
成功を破棄しないこと、日本語名のない作品が原名のまま表示されること、生成邦題が一件も保存されないことです。

## IdleChatのお題とストック

IdleChatは利用者が会話へ介入するChatではなく、MioとShiroの会話を字幕と音声で読む／聴くための読み取り専用surfaceです。再生中にお題や各発話を生成せず、通常カテゴリもForecastも、会話台本全体を事前に完成させた`IdleChatEpisodeArtifact`を再生します。1ワードと2ワードはお題を事前生成した独立Stockを持ち、episodeごとに選択したcategoryに対応するStockから1件を消費します。その他の通常カテゴリはepisode準備時に候補を生成してJudgeで1件を採用します。Forecastは、AI技術、その他技術、医療、社会保障、政治、経済の6ドメインごとに最大2件、全体で最大12件の有効なお題を保持し、episode準備時にそのストックを入力として使います。

Forecastが展望する未来範囲はドメインごとに固定します。

| Forecastドメイン | 未来範囲 |
| --- | --- |
| AI技術 | 1〜2年後 |
| その他技術 | 2〜3年後 |
| 医療 | 3〜5年後 |
| 社会保障 | 3〜5年後 |
| 政治 | 3〜5年後 |
| 経済 | 3〜5年後 |

この範囲はお題候補、Judge、完成お題、Forecast対話、turn validatorの共通契約です。期間を明示しない抽象的な出力も許可しますが、論点や根拠が対象範囲を越える案は`topic_violation`または`factual_violation`として採用しません。

1ワードと2ワードの「ワード数」は完成topicの文字数ではなく、お題生成へ入力するseed語数です。安定した内部category値は`single`と`double`のままとし、Viewerと利用者向け表示は「1ワード」「2ワード」に統一します。旧表記の1ジャンルと2ジャンルはそれぞれ同じcategoryを指す互換表記です。

1ワードと2ワードの入力語彙は、固定コア48語と日次最新語最大32語を合わせた最大80語に制限します。固定コアは現代生活、科学技術、仕事、社会、自然を中心とし、古典・伝統語は4語までにします。日次最新語は04:00 JSTの共通収集を別途増やさず、当日`NewsAnalysisArtifact`から`DailySeedCache`へ反映された`term_notes`のうち`contextual`または`confirmed`だけから作ります。収集artifactだけでは最新語を作りません。Wikipedia Randomは最新語へ使いません。RSS／Atomを優先し、Reddit／X由来は合計8語までとします。日次最新語は過去分へ追記せず、当日分で全置換します。収集・分析が未完了または失敗した場合は固定コアだけで継続します。

1ワードは日次最新語を70%、固定コアを30%の確率で選びます。2ワードは日次最新語と固定コアを1語ずつ組み合わせ、最新語がない場合だけ固定コア2語へフォールバックします。2ワードの2語は異なる語とし、語順だけを入れ替えた組を別seedとして扱いません。同じ語は直近20回の選択対象から外し、古典・伝統語を使った次のsessionでは古典・伝統語を選びません。候補Judgeは既存の適合性、具体性、好奇心、会話発展性、カテゴリ軸、新規性、安全性に加えて`present_day_relevance`を0〜5で評価し、1ワードと2ワードでは4未満の候補を採用しません。文章上の重複だけでなく、入力語彙と時代感の連続を抑止します。

1ワード／2ワードStockの候補生成、Judge、お題確定、Forecast Stockのキーワード抽出、候補生成、Judge、お題確定と、これらのepisode台本の会話生成はCodexExeを使います。CodexExe requestは構造化JSON eventを読みながらcancel可能にし、途中のお題候補や発話を有効ストックまたは完成台本として公開しません。ユーザー入力によるInterruptは正規cancel経路へ伝播させ、前景のChatWorkerを優先します。この優先制御では入力、会話context、CTX上限を短縮しません。

1ワード、2ワード、Forecast、StoryのバックグラウンドStock生成は、会話開始時に実行中のCodexExeをcancelして前景会話へ実行資源を譲ります。生成前提、候補生成完了、Judge完了、Forecast検索keyword／seed確定、Story本文生成完了、意味検査完了をセッション保存先のcheckpointへ原子的に保存し、次のIdle／Heartbeat補充で最後に完了したphaseから再開します。完成Stockへ登録した後だけcheckpointを削除し、同じ`generation_id`が既にStockへ存在する場合は再登録せずcheckpointだけを完了扱いにします。IdleChat再生を停止していてもStock補充は継続し、会話中、Worker実行中、外部LLM busy中は開始しません。

### IdleChatエピソードの事前制作と朗読時TTS先読み

`IdleChatEpisodeArtifact`は、`episode_id`、revision、`episode_kind=dialogue|story_reading`、カテゴリ、採用済みお題、入力seedとsource参照、`content_mode`、判定理由、生成日時、有効期限、台本状態、品質判定、全発話を持つCORE所有の永続artifactです。`story_reading`は元話名`source.title`と、完成作品名`story_title`を分離します。各発話は`message_id`、`turn_index`、`speaker=mio|shiro`、相手Agent、`utterance_role=dialogue|narration|interjection`、表示本文、TTS本文、本文hash、検証状態を保持します。speakerは構造化fieldにだけ持たせ、表示本文やTTS本文へ`Mio:`、`Shiro:`、相手の台詞、台本用の話者labelを混ぜません。

Debug ViewerのIdleChatは、お題在庫を`Topic Stock`、episode化した物語在庫を`Story Stock`として分離します。
`Story Stock`には物語専用の読み取り専用リストを設け、`ready`、`needs_repair`、`failed`を含む
保存中の全episodeを選択して全文を読めるようにします。一覧は制作状態、revision、元話、読み手、
聞き手、発話数、最初のNG turnを示します。選択したepisodeでは全発話、表示本文とTTS本文、物語契約、
検証error、物語台帳を表示し、直接NGと判定されたturnと、`first_invalid_turn`以降のsuffix再生成対象を
異なる表示で区別します。NG表示はcode、turn、field、evidenceを本文と対応付けます。Viewerの表示と
再読込はepisodeの生成、修復、状態遷移、再生、TTS合成を開始しません。

episode準備phaseは「お題選定 → CORE正本のMio／Shiroキャラクター定義、採用topic、source context、直近topic、カテゴリ別禁止事項、出力schemaをCodexExeへ入力 → `episode_kind`に応じた対話全体または物語朗読全体を一括生成 → turn単位検証 → 全体品質確認 → artifactのatomic公開」の順で行います。CodexExeは台本を生成する実行機構であり、ActorやAgent identityではありません。出力発話は構造化された`speaker`によりMioまたはShiroへ帰属させますが、CodexExe自身、Model名、provider名、Kuro、test doubleを発話者として公開しません。キャラクター定義をRenCrow_ToolsやCodexExe側の独立正本へ複製せず、COREが実行ごとに正本から組み立てます。

`story_reading`では、物語本文と読み手／聞き手の演出をCodexExeで同じ完成台本へ事前生成します。episodeごとに`reader=mio|shiro`を1人選び、もう一方を`listener`とし、読み手をepisode途中で交代しません。読み手は`narration`、聞き手は直前の朗読箇所を指す`reacts_to`を持つ短い`interjection`だけを担当します。合いの手は段落境界に置き、全発話のおおむね10〜20%、3〜6朗読段落に1回、原則30文字以内とします。連続した合いの手、先の展開の漏洩、あらすじの言い直し、返答を必要とする長い質問、同じ口癖の反復を禁止します。読み手は通常、合いの手へ応答せず朗読を続けます。読み手の選択は直近episode履歴を使ってMio／Shiroの偏りを避けます。

`story_title`は完成した本文、genre、`interest_direction`、結末の余韻を確認した上でCodexExeに決めさせます。全作品を同じ構文へ当てはめず、`funny`はキャッチーさや人物の論理が見える題、`moving`は静かな余韻、`thrilling`／`scary`は不穏さや危機、`thought_provoking`は価値の対立や問いを感じる題など、作品ごとに方向を変えます。元話名の丸写し、「新・元話名」「元話名 SF版」のような機械的改題、本文にない固有名詞、結末を説明し切る題を禁止します。空欄、2文字未満または40文字超、破損文字、元話名と同一の題、意味検査で本文や雰囲気に合わない題は`title_violation`としてreadyにしません。

旧revisionのready episodeに`story_title`がない場合、COREは本文、turn順、speaker、message ID、story contract、物語台帳、検証結果を変更せず、作品タイトルだけをCodexExeで補完して新revisionとして追記できます。補完失敗時は旧ready作品を削除・再生成・再生不可にせず、`title_generation`を観測可能にして次回Idleへ延期します。

#### Story Stock ViewerのHTML・タイトル・表示仕様

Debug ViewerのIdleChatは、生成前のお題在庫`Topic Stock`と、完成台本artifactの在庫`Story Stock`を
別tabとして表示します。`Story Stock`は物語専用の読み取り面であり、ニュース一覧、通常IdleChat履歴、
お題一覧と同じlistへ混在させません。次のIDと`data-idle-view`はViewer内の安定したDOM契約です。

```html
<button data-idle-view="stock" aria-controls="idleViewStock">Topic Stock</button>
<button data-idle-view="episodes" aria-controls="idleViewEpisodes">Story Stock</button>
<div id="idleViewEpisodes" role="tabpanel">
  <div id="idleEpisodeOverview" aria-live="polite"></div>
  <label for="idleEpisodeSelect">物語を選択</label>
  <select id="idleEpisodeSelect"></select>
  <button id="idleEpisodeRefresh" type="button">再読込</button>
  <div id="idleEpisodeNotice" role="status" aria-live="polite"></div>
  <section aria-labelledby="idleEpisodeListTitle">
    <h4 id="idleEpisodeListTitle">物語専用リスト</h4>
    <div id="idleEpisodeList" aria-label="物語ストック一覧"></div>
  </section>
  <article id="idleEpisodeDetail" aria-live="polite"></article>
</div>
```

CSS class名は描画実装の内部詳細ですが、上記ID、tabとtabpanelの対応、labelとcontrolの関連、
`aria-live`による状態通知は維持します。物語本文、タイトル、元話名、検証根拠、台帳JSONなどartifact由来の
文字列をHTMLとして解釈せず、escapeしたtextとして描画します。story本文に含まれるtag、script、event
handler文字列をDOMへ展開しません。

一覧と選択欄は、現在storeに残る`ready`、`needs_repair`、`failed`を含む全episodeを表示します。
状態filterによる暗黙除外を行わず、既定順は`failed`、`needs_repair`、修復・検証・生成中、ready、expiredを
優先し、同状態内は更新時刻の新しい順とします。各行は次を表示します。

| 項目 | 表示契約 |
| --- | --- |
| 作品名 | `story_title`を優先する。旧artifactで空の場合だけ`source.title`へ表示上fallbackする |
| 制作状態 | 完成、要修復、失敗等を色だけでなくtextでも示す |
| revision | 現在参照している最新revision |
| 演者 | `reader → listener` |
| 発話数 | `utterance_count` |
| NG起点 | `validation.first_invalid_turn`がある場合だけ表示 |

Overviewは全件、完成、要修復、失敗、`untitled_ready`に対応する「タイトル待ち」、準備中を別々に表示します。
選択はlistと`idleEpisodeSelect`のどちらからでも可能で、両者は同じ`episode_id`へ同期します。選択中IDは
browser local stateへ保持できますが、episode正本、再生状態、検証状態には使いません。保存IDが一覧に
なければ状態優先順の先頭を選びます。

詳細は選択した1件についてだけ取得し、次の順で表示します。

1. `story_title`、制作状態、revision、reader、listener
2. 元話名`source.title`と元あらすじ`source.synopsis`
3. `transformation_axis`、genre、`interest_direction`、`content_mode`、`interest_contract`、generation ID
4. 検証結果と全errorのcode、turn、field、evidence
5. 全turnのspeaker、`utterance_role`、`display_text`
6. 折りたたみ可能な各turnの`speech_text`
7. 折りたたみ可能な`story_ledger`

検証errorが直接指す`turn_index`は赤系の「NG箇所」とし、同じerror根拠を当該turn内にも表示します。
`first_invalid_turn`以降で直接errorを持たないturnは黄系の「再生成対象」とし、直接NGと区別します。
turnを持たない`story_title`、contract、ledger、全体品質のerrorは詳細上部から除外しません。色だけに依存せず、
「NG箇所」「再生成対象」、code、field、evidenceをtextで読めるようにします。

`story_title`は本文を置き換える要約ではなく、完成作品を識別するCORE metadataです。タイトルがなくても
元話名だけで本文品質を合格にしてはならず、逆にタイトルだけを読まなければ元話や改変を理解できない本文も
品質合格にしません。方向別の題名設計は次を基本とします。

| `interest_direction` | タイトルの方向 |
| --- | --- |
| `funny` | 人物の妙な論理、道具、状況、オチを入口にしたキャッチーな題。無関係な駄洒落は禁止 |
| `moving` | 関係、喪失、選択を説明し切らず、静かな像や余韻を残す題 |
| `thrilling` / `scary` | 危機、不穏な規則、欠落、違和感を示し、結末を明かさない題 |
| `surprising` | 伏線の意味が変わる入口を示すが、反転内容をそのまま書かない題 |
| `rousing` | 覚悟、代償、突破を感じさせる動きのある題 |
| `comforting` | 小さな傷、居場所、回復を感じさせる穏やかな題 |
| `thought_provoking` | 対立する価値、未決着の選択、問いの余韻を持つ題。標語や説教は禁止 |

タイトル生成は全turnと結末を完成させた後の内容を入力に含めます。2〜40文字とし、元話名の丸写し、
「新・元話名」「元話名 SF版」のような機械的改題、全作品共通template、本文にない固有名詞、genre名だけの
説明、結末の完全なネタバレを禁止します。決定的検査と独立した意味検査のどちらかがNGなら
`title_violation`です。タイトルだけがNGの場合はturn、message ID、contract、ledgerを変更せず、タイトルだけを
再生成してrevisionを増やします。turn errorと併存する場合は、既存の最初のNG turn以降のsuffix修復契約を守り、
修復後の完成本文に対してタイトルも再評価します。

`story_title`はViewer、再生中topic、SessionSummaryの`title`／`story_title`に使い、`source_title`は元話名を
保持します。タイトルを新しい台詞やnarration turnとして暗黙挿入せず、TTSへ自動送信しません。将来タイトルを
読み上げる場合は、speaker、message ID、turn順、字幕、TTS ACKを持つ明示的な発話契約を別途定義します。

Story Stockを開く、選択する、再読込する、定期更新する操作はGETだけを使い、生成、タイトル補完、検証、
suffix修復、再生、MarkPlayed、TTS合成を開始しません。一覧取得失敗時は取得工程とHTTP状態を
`idleEpisodeNotice`へ表示し、既に表示中のsnapshotを消しません。詳細は、選択変更、明示的な再読込、または
保持中詳細のrevisionが一覧より古い場合に取得します。同revisionのままの定期一覧更新だけでは詳細を
繰り返し取得しません。高速な選択変更で古いresponseが返っても、現在選択中でないepisodeへ詳細を
巻き戻しません。

Desktopでは専用listと詳細を横に並べ、狭い画面では縦に積みます。390×844を最小受け入れviewportとし、
document全体の横overflowを出さず、選択欄、list、詳細本文を到達可能にします。固定入力barが最終turnや台帳を
覆わないscroll余白を確保します。

受け入れ条件は次の通りです。

1. Topic StockとStory Stockが別tabであり、物語専用listが存在する。
2. ready、needs_repair、failedを含むstore内全episodeがlistと選択欄へ出る。
3. 作品名は`story_title`、元話名は`source.title`として同時に確認できる。
4. 完成作品は2〜40文字の非templateタイトルを持ち、本文と雰囲気に一致する。
5. funny、moving、thrilling／scary、thought_provoking等でタイトルの方向が単調に固定されない。
6. タイトル欠落、元話丸写し、本文との不一致は`title_violation`となりreadyへ昇格しない。
7. legacy readyの補完はrevisionだけを進め、turn、message ID、contract、ledger、validationを変更しない。
8. タイトル補完失敗でも旧ready作品を削除、再生成、再生不可にしない。
9. 直接NG turnとsuffix再生成対象が色とtextの両方で区別される。
10. 全turn、TTS本文、error evidence、story ledgerを選択した1件について読める。
11. ViewerのGET操作が生成、補完、修復、再生、TTSを開始しない。
12. Desktopと390×844で選択・読了でき、横overflow、console error、page error、HTTP失敗がない。

物語の生成条件は混同せず、`transformation_axis`（元話の何を変えるか）、`genre`（どの世界観・物語論理で描くか）、`interest_direction`（聞き手に何を感じさせるか）へ分離します。`interest_direction`には、作品ごとの成立条件である`interest_contract`を必須とします。SFはgenreであり、笑える／泣ける等の感情方向の代替にはしません。主な方向と成立条件は次の通りです。

| `interest_direction` | `interest_contract`の必須観点 |
| --- | --- |
| `funny` | 前振り、段階的な誇張、人物の論理から生じる勘違い、オチ |
| `moving` | 人物への愛着、避けられない選択、喪失または別れ、説明しすぎない余韻 |
| `scary` | 違和感、予兆、情報制限、意味の反転 |
| `surprising` | 伏線、予想外の展開、振り返ると納得できる因果 |
| `rousing` | 困難、覚悟、代償、突破または決断 |
| `comforting` | 小さな傷、相互理解、回復、穏やかな着地 |
| `thought_provoking` | 対立する価値観、簡単には決着しない選択、問いの余韻 |

合いの手も`interest_direction`と`content_mode`へ従います。`funny`ではツッコミを許可し、`moving`では回数を減らして静かな反応にし、`scary`では緊張を補強し、`thought_provoking`では結論を説明せず短い疑問または異論を残します。戦争、武力衝突、災害、人命被害を扱う`serious`では、genreや感情方向にかかわらず茶化す合いの手を禁止します。

CodexExeへは本文の前提となる物語台帳も同時に出力させます。台帳は安定したentity ID、意味上の役割、作品内の主呼称、許可済み別称、各呼称の読みと適用条件、任意の固有名、人物関係、時系列上の状態、場所、重要な所有物、世界規則、登録済み造語と意味を持ちます。SF等の意図した造語は`coined_terms`へ表記、読み、意味を登録して許可し、未登録で文脈に成立しない語を語彙破綻として扱います。表示用`display_text`とTTS用`speech_text`を分け、人物呼称、地名、造語の読みを台帳と各turnで一致させます。

#### 物語人物の呼称と同一性

固定するのは「同一人物として追跡できること」であり、全作品で共通の人名や役割名ではありません。`entity.id`と`semantic_role`はepisode内の参照、関係、時系列、所有物を結ぶ安定keyとし、`primary_label`、`proper_name`、`aliases`は本文で使う表面呼称として分離します。entity IDを表面呼称から作らず、呼称を変えても人物関係や過去turnの参照を切断しません。

CodexExeは人物ごとに、その作品で姓名、名、姓、通称、役職、役割名、機体番号等のどれが最も理解しやすいかを選びます。主人公、感情移入の中心、複数の同役割を識別する人物は自然な固有名を持てますが、短く登場する人物、役割だけが重要な人物、名前を知らない視点では役割名を優先できます。姓名を全員へ機械的に補完したり、フルネームを本文で毎回呼んだりしません。`proper_name`は不要なら空で構いません。

表面呼称は固定poolの順回りで決めず、source、時代、地域、genre、世界規則、語り手の視点、当事者間の距離、`interest_direction`と温度からepisodeごとに作ります。同じ`semantic_role`でも、例えば「入口を管理する人」は、時代劇の「関守」、現代劇の「受付係」、SFの「入域審査官」、子供視点の「怖い制服の人」のように変えられます。直近の完成episodeで使った主呼称、姓名構文、役割名の傾向を`recent_naming_context`として生成入力へ渡し、合理的な理由のない連続再利用を避けます。ただし、明瞭さを犠牲にして奇抜な言い換えを強制しません。

episode内では、人物ごとに1つの`primary_label`と、必要な場合だけ少数の`aliases`を許可します。aliasは表記と読みに加え、`valid_from_turn`、任意の`valid_to_turn`、`perspective_entity_id`、変更理由を持ちます。名前を知る前の「検問官」から判明後の名前へ、または距離のある「駅長」から親しくなった後の「駅長さん」への変化のように、物語上の知識や関係の変化を表現する時だけ使います。同一場面に紛らわしい人物がいる間は識別力の低いaliasを使わず、台帳未登録の呼称へ突然切り替えません。

呼称の品質は、別人物と誤認する曖昧さ、台帳未登録alias、適用turn外のalias、視点人物が知らない名前の先行使用、同一人物を別のentityとして登録する二重化を`entity_reference_violation`として検証します。不要な姓名の強制、世界観に合わない呼称、直近作品との機械的な呼称pattern反復、関係変化のない無制限な言い換えを`entity_naming_violation`として検証します。読みと`speech_text`の不一致は`reading_violation`です。turn kで呼称破綻が発生した場合、台帳に後付けaliasを追加してready扱いせず、既存の修復契約に従ってturn k以降を作り直します。

呼称契約の受け入れ条件は次の通りです。

1. 姓名と役割名のどちらも一律に強制せず、作品上の識別と表現に適した方を選ぶ。
2. 同じ意味上の役割でも、時代、genre、視点、人物関係が異なるepisodeではそれに合う呼称を生成できる。
3. 呼称が変化してもentity ID、関係、所有物、時系列の参照が同一人物へ解決される。
4. aliasは台帳に登録した適用turn、視点、変更理由の範囲でだけ使い、同一場面で人物を誤認させない。
5. 主人公と感情的に重要な人物は必要に応じて固有名を持て、一時的な登場人物は役割名だけで成立できる。
6. `display_text`と`speech_text`が各呼称の登録済み表記と読みに一致する。
7. 無関係な連続作品で同じ姓名templateや役割名セットを機械的に再利用しない。
8. 未登録呼称や曖昧な指示の破綻は該当turnからのsuffix再生成とし、台帳の後付けだけで合格へ変えない。

COREは台本生成前にtopicとsource contextを判定し、episodeの`content_mode`を次の優先順で1つに固定します。この判定はキャラクターの語彙、語尾、関係性、感情表現を変更するものではなく、会話内容の向き合い方だけを指定します。

| `content_mode` | 対象 | 会話内容の契約 |
| --- | --- | --- |
| `serious` | 戦争、武力衝突、災害、および人命・被害・喪失を直接扱うセンシティブな話題 | Mio／Shiro本来の口調を維持したまま、茶化し、軽口、娯楽化、被害の矮小化、扇情的な断定を避け、確認できた事実と不明点を分けて真面目に話す |
| `assertive` | `serious`に該当しない政治、政策、制度、思想の話題 | 強い意見、率直な批判、異論、Agent間の対立を許可する。事実・推測・意見を区別し、批判対象は政策、制度、主張、思想とする。個人属性への侮辱、差別・人格否定、暴力の扇動、根拠のない事実断定は許可しない |
| `free` | 上記以外 | そのepisodeにおけるMio／Shiroの気分に委ね、軽快、真面目、懐疑的、遊び心のある進行を選べる。Persona、事実性、反復、カテゴリ別禁止事項は常に守る |

複数条件が重なる場合は`serious > assertive > free`を適用します。したがって政治的背景を持つ戦争や災害も`serious`です。`assertive`でも両者を人工的に同意させる必要はなく、MioとShiroが異なる見解を保ったまま会話を終えて構いません。分類結果と判定理由をCodexExeの入力へ含め、CodexExeの気分や生成結果から分類を後付けしません。

CodexExeの完成出力schemaは次の論理形とします。`turn_index`は1始まりで連続し、`speaker`は
`mio | shiro`だけを受理します。`text`は発話本文だけを持ち、話者label、説明、評価、内部推論を
含めません。turn数とspeaker順はCOREがrequestした`expected_turn_count`とspeaker sequenceへ
一致させます。`generation_id`はCodexExe呼び出し単位、`character_revision`はCOREが入力した
キャラクター正本revision、`input_hash`はtopic、source context、禁止事項、固定prefixを含む入力の
SHA-256です。

```json
{
  "schema_version": "rencrow.idlechat.script.v1",
  "generation_id": "...",
  "character_revision": "...",
  "input_hash": "...",
  "expected_turn_count": 12,
  "turns": [
    {"turn_index": 1, "speaker": "mio", "text": "..."},
    {"turn_index": 2, "speaker": "shiro", "text": "..."}
  ]
}
```

CodexExeによるIdleChat台本生成は、Kuro／Heavyの`danger-full-access`実行やCOREの汎用`codex.run` Toolとは別の、side effectを許可しない低優先度生成profileです。`read-only`かつ`ephemeral`で実行し、ファイル変更、command実行、外部送信、追加Tool実行を許可しません。お題素材とcharacter contextはrequest本文で渡し、CodexExeのthreadやworking directoryをPersona、Memory、episode正本として扱いません。

turn validatorは既存IdleChatガードをCodexExe出力にも適用します。話題については直近topicとの完全一致・高類似、1／2ワードの直近20語、カテゴリに合わないお題、source／prompt／provider等のmeta漏れを拒否します。発話については、同文反復、直前文の言い換え、同じ書き出し・語句、交互反復、template反復、高類似反復、「もし〜なら」の連発、汎用相槌だけの発話を拒否します。話者については`speaker`以外のAgentの台詞、相手発話の自己帰属、話者labelの本文混入、Persona逸脱を拒否します。外部刺激の取得元露出、架空映画の実在扱い、ニュースseedにない事実の断定、Forecastの未来断定、storyの改変軸消失もカテゴリ別違反として拒否します。さらに、`serious`で被害を茶化す発話、`assertive`で意見を不当に弱める一律中立化、または政治・思想への強い意見を理由なく禁止する処理、`free`を理由にPersonaや既存禁止事項を外す処理を`content_mode_violation`として拒否します。NG理由は少なくとも`schema_violation | speaker_confusion | repetition | topic_violation | persona_violation | factual_violation | meta_leak | quality_violation | content_mode_violation`へ分類します。

`story_reading`には物語整合性validatorも適用します。登録外で文脈に成立しない語や壊れた固有名詞を`lexical_corruption`、台帳と異なる親子・兄弟・敵味方等を`entity_relation_violation`、未登録alias、呼称の適用turn外使用、別人物と誤認する曖昧さを`entity_reference_violation`、不要な姓名強制、世界観との不一致、直近作品との機械的な呼称pattern反復を`entity_naming_violation`、生死・時刻・場所・所有物・人物の知識状態の矛盾を`continuity_violation`、採用した世界規則との矛盾を`world_rule_violation`、表記またはTTS読みの不一致を`reading_violation`、指定した面白さの成立条件の欠落を`interest_contract_violation`、作品タイトルの欠落、元話丸写し、本文・雰囲気との不一致を`title_violation`として拒否します。読み手の途中交代、聞き手による長い本文朗読、頻度超過、連続、先の展開の漏洩、不適切な温度の合いの手は`story_performance_violation`です。決定的な台帳照合とCodexExeによる意味検査を分け、意味検査が不確実なepisodeも合格扱いにしません。

turn検証で最初のNGを`turn k`に検出した場合、episodeを`needs_repair`へ遷移させ、`turn 1..k-1`を確定prefixとして保持します。修復jobは`turn k`以降の本文、message identity、検証結果、派生TTS cacheを破棄し、CodexExeへ確定prefix、元の採用topic、両キャラクター定義、NG理由、必要な残りturn数を渡して、`turn k`から最終turnまでのsuffix全体を再生成させます。複数NGがある場合は最小の`turn_index`を修復起点とし、再生成後の検証で`turn j`がNGなら同じ規則を`turn j`から繰り返します。保持prefixの`message_id`は変えず、再生成suffixには新しい`message_id`を発行します。有限回のsuffix再生成で合格しないepisodeは`failed`とし、全episodeを先頭から暗黙に作り直しません。補充生成はこの修復jobと独立して、最初のNG判定時点で開始できます。

途中まで生成した台本、NG suffixを残した台本、品質確認に失敗した台本、発話帰属が不明な台本は再生対象へ公開しません。全turn合格後にだけ`ready`へatomic公開します。NGまたは不確実と判定したepisodeは自動削除せず、検出code、該当箇所、根拠、修復起点を保持して`needs_repair`へ遷移させます。ready在庫には数えず、同episodeの修復や破棄判断を待たずに、別の`episode_id`と`generation_id`で不足数を追加生成します。追加生成は元のNG本文を上書きせず、同一失敗の無限loopを避けるため1回の補充cycleを有限件で終了し、失敗phaseと試行数を観測可能にします。`needs_repair`の修復は補充jobとは別に実行でき、合格後だけreadyへ遷移します。修復完了時に一時的にready数がtargetを超えても既存episodeを自動削除しません。

公開後の台本本文はimmutableとし、問題が見つかった場合は旧revisionを変更せず、新revisionで合格済みprefixを引き継いで最初のNG turn以降を再生成します。台本生成と品質確認は低優先度background処理とし、ユーザーChat、明示Worker、Coderまたは他の前景処理が始まった場合はcancelして、完了済みの安全なprefixから次回Idle時に再開します。

episodeの制作状態は`draft | generating | validating | needs_repair | repairing | ready | expired | failed`、再生状態は`buffering | playing | completed | interrupted | failed`として分離します。再生可能なのは制作状態が`ready`で、有効期限内のepisodeだけです。ニュースとForecastは入力sourceの日付と鮮度を保持し、古い情報を現在の話題として再生しません。再生可能episodeが0件の場合、PORTAL表示中に同期LLM生成へfallbackせず、`preparing`を表示してbackground準備を待ちます。

TTS音声はepisode全体を事前保存せず、台本が確定していることを利用して朗読時に先読み生成します。再生開始前に最初の1〜2発話を合成し、再生中は常に2〜3発話先、かつ15〜30秒の再生時間を目安に音声bufferを維持します。bufferは発話数だけでなく残り再生秒数で管理し、下限を下回る前に次の発話を`CORE -> RenCrow_TTS Gateway`の正規経路へ送ります。音声cacheは`episode_id`、`message_id`、本文hash、voice revisionで識別し、episode再生中の再利用に限定します。PORTALやCOREからIrodoriその他の物理TTS backendへ直結しません。

PORTALは受信した音声chunkを`turn_index`順の再生queueへ積み、現在発話の再生中に後続音声を受け取ります。`idlechat.message`の字幕と発話者表示は対応する音声の再生順と一致させます。再生完了ACKは再生結果、cache解放、観測のために使い、次のTTS合成開始を止めるgateにはしません。ACKが欠落しても既に確定した後続台本のTTS先読みを60秒単位で直列停止させず、surface leaseと再生状態を別に監視します。buffer不足時は`buffering`を明示して順序を保ったまま再開し、未生成の台本をその場で作るfallbackや、字幕だけを先に進めるfallbackを行いません。

可視Chatが現れた場合は、既存のChat／IdleChat排他契約に従いepisode再生を即時中断し、backgroundの台本生成とTTS先読みもcancelします。中断した再生は`interrupted`として再生位置を記録できますが、自動再開は有効なIdleChat surface leaseとepisode鮮度を再確認してから行います。Debug ViewerとCLIでは、ready episode件数、制作phase、失敗phase、episode鮮度、現在の再生位置、buffer秒数、TTS先読み件数、ACK遅延を別々に確認できるようにします。

受け入れ条件は次の通りです。

1. `ready` episodeの再生開始から終了まで、お題生成または発話生成のLLM requestを発行しない。
2. CodexExeへCORE正本のMio／Shiroキャラクター定義を入力し、全発話の`speaker`がMioまたはShiroへ一意に帰属することを検証する。欠落、重複、順序逆転、話者勘違いを含む台本を`ready`へしない。
3. 最初の音声が利用可能になるまで再生を開始せず、再生開始後は通常時に15秒以上のbufferを維持する。
4. 現在発話の再生ACKより前に後続発話のTTS合成を開始でき、ACK欠落だけで先読みを停止しない。
5. TTS合成が音声消費より遅い場合は`buffering`を明示し、字幕と音声の`message_id`、`turn_index`をずらさない。
6. 前景Chat開始時にepisode生成、TTS先読み、音声再生を停止し、IdleChat eventをChat surfaceへ流さない。
7. LLM、TTS、音声取得、browser再生、ACKの各失敗phaseを別々に記録し、別工程の成功へ丸めない。
8. 最初のNGが`turn k`なら`turn 1..k-1`の本文と`message_id`を保持し、`turn k`以降だけを新しいidentityで再生成する。
9. 戦争・武力衝突・災害などは`serious`、それ以外の政治・思想は`assertive`、その他は`free`とし、全modeでMio／Shiroの口調を維持する。mode不一致の最初の発話をNG turnとしてsuffix修復する。
10. `story_reading`はepisode中の読み手を固定し、もう一方のAgentだけが短い合いの手を担当する。合いの手が朗読を乗っ取らず、`interest_direction`と`content_mode`へ一致する。
11. storyのentity関係、呼称とaliasの参照解決、作品間の呼称多様性、連続性、世界規則、造語、読み、`interest_contract`を検証し、破綻または不確実な作品をreadyへしない。
12. NG作品を自動削除せず`needs_repair`へ保持し、その修復や破棄判断を待たず、ready不足分を別episodeとして追加生成する。

IdleChatの通常カテゴリで使う`IdleChatTopicSeed`は、JSTの毎日04:00に強制更新します。CORE起動時にも当日cacheがなければ初期収集し、04:00の更新は起動時収集済みでも省略しません。既定の報道RSSに加え、AI企業の公式RSS、研究機関の公式RSS、arXiv Atom、Redditと、明示設定されたX（旧Twitter）Recent Searchを取得できます。この日次収集は`IdleChatTopicSeed`と`DailyNewsBrief`の共通入力を作りますが、出力データと利用目的は分離します。収集先、カテゴリ、上限、利用toolの正本は`docs/05_設定リファレンス.md`の「日次ニュース収集とIdleChatTopicSeed」とします。

Redditは複数communityの公開Atom feedを1回の取得へまとめ、Xは公式APIと環境変数のBearer Tokenを使います。各シードは`source_type`、取得元名、元URLと、RSS／Atomに含まれるdescription／summaryを保持します。`reddit`または`x`のシードは世間の反応や話題候補であり、報道記事や確認済み事実として扱いません。お題生成時にもSNS投稿であること、主張を事実確定せず裏取り済みと仮定しないことを内部指示へ含めます。

Debug Viewerの`News Pack`はRSS／Atomのタイトルと本文情報を分離して表示します。CORE起動時と5分間隔で、enabledな全RSS／Atom sourceをdue時刻にかかわらず巡回します。収集時は各項目のリンク先を安全なHTTP取得境界で1件ずつ取得し、抽出できた元記事全文を`RawText`へ保存します。正規化URLを主キーとする永続取得台帳でHTTP取得をclaimし、`ready`の本文は別sourceで同じURLを受け取っても再取得せず再利用します。取得失敗だけを5分後以降の再試行対象とし、同一巡回内の二重試行は禁止します。本文抽出は記事本文領域だけを採用し、広告、関連記事、ナビゲーション、地域一覧などを混入させません。NHK News Webでは公開認証セッション後の本文マーカーを正本とし、同一本文クラスの先頭段落も含めます。末尾が省略記号の応答は全文取得成功にせず、マーカーから取得した完結短報は200文字未満でも全文として扱います。一般記事は200文字未満の抽出結果を全文取得成功にしません。成功時は一覧にも元記事本文を優先して表示し、詳細では省略されていない本文を確認できます。feedのdescription／summaryは`SummaryDraft`へ残し、元記事取得に失敗した場合も項目を削除せず、feedが提供したdescription／contentを本文fallbackとして保持します。再取得ではSource URLに対応する既存event／staging identityを再利用します。取得状態は`article_fetch_status=not_attempted | ready | unavailable`として記録し、過去に保存した`SummaryDraft=タイトル`形式でも`RawText`に残る本文情報を表示します。News Pack一覧は`COALESCE(published_at, fetched_at)`を基準とする直近24時間のローリングウィンドウで取得し、件数上限およびsource別件数上限を設けません。Sports categoryは収集対象と一覧から除外します。同一URLが複数行に存在する場合は一覧上で最新の1件へ束ねます。24時間を超えた行と既存Sports行は一覧から外しますが、L1 DBから物理削除せず、取得済み本文と台帳を保持します。

04:00 JSTのworkflowも、先に収集phaseを完了して`NewsCollectionArtifact`を固定し、その後にSkill `core.build-daily-source-brief`を専用の`Worker`で実行して`NewsAnalysisArtifact`を作ります。`ChatWorker`はチャット画面専用で、日次情報収集や考察には使用しません。考察は記事を1件ずつ完了させます。ユーザー会話または明示Worker実行が始まった場合、実行中の日次LLM requestをcancelして前景処理を優先し、前景処理の終了後に同じ収集artifact・同じ入力・context条件で再試行します。この中断を記事失敗として数えず、完了済み記事も破棄しません。原文を省略や事実の追加なく日本語へ忠実に翻訳し、本文から重要用語を抽出し、本文の文脈だけでは意味を説明できない用語に限って確認先URLを調査します。用語確認後に本文サマリと、事実から分離したShiroの見解を作ります。利用者向け本文はすべて日本語です。Wikipedia Randomは`DailyNewsBrief`へ入れず、`IdleChatTopicSeed`の外部刺激としてのみ扱います。前景の`LiveNewsSearch`も同じ二段階artifact境界を使いますが、収集結果は`Source=live_news_search`として朝刊cacheと分離します。

元記事本文を取得できない項目は、見出しやフィードsummaryから推測せず「本文を取得できませんでした」と明記します。不明語の検索または確認先本文の取得に失敗した場合は「意味を確認できませんでした」として`unresolved`を保持します。LLM失敗時も項目と完了済みの前工程を失わず、失敗した工程を日本語で明示します。SNS投稿は世間の反応として扱い、投稿内の主張を確認済み事実へ昇格しません。

項目別状態は、原文取得だけを表す`source_read_status`と、取得後の処理結果を表す`processing_status`へ分離します。`source_read_status`は`unprocessed | ready | unavailable`、`processing_status`は`pending | ready | source_unavailable | translation_failed | term_extraction_failed | brief_failed`です。`unprocessed`と`pending`は未着手であり、失敗ではありません。未着手項目へ「完了できませんでした」などの失敗文言を設定してはいけません。原文取得後に翻訳が失敗した場合は`source_read_status=ready`と`processing_status=translation_failed`を保持し、原文取得失敗へ丸めません。同様に用語抽出またはサマリ・見解生成の失敗時も、それ以前に完成した翻訳や用語補足を保持します。`processing_error`にはViewerへ表示可能な工程別の日本語理由だけを格納し、providerやbackendの生errorは含めません。

Debug Viewerの`情報収集`タブは、IdleChatの日次収集cacheを読み取り専用で表示します。最終取得時刻、処理状態と完了時刻、次回04:00 JST、使用Skill、ニュース件数、Wikipedia件数、カテゴリ別件数、設定済み取得先、利用toolを確認できます。収集phaseで見出しとURLを取得できた項目は、原文取得、翻訳、用語抽出、サマリ・見解の未着手または失敗にかかわらず全件台帳へ残し、検索やカテゴリ絞り込みによって台帳から除外しません。台帳の各行は「収集済み」、原文取得状態、後続処理状態、安全な工程別理由を表示します。詳細カードには原文取得状態と後続処理状態を別々のbadgeで表示し、本文は必ず「原文翻訳 → サマリ → Shiroの見解 → 用語補足」の順で表示します。表示は`GET /viewer/idlechat/collection`のsnapshotを使い、タブ表示や再読込によって収集、再収集、cache消費、Memory昇格を開始しません。XのBearer Tokenなどcredentialはsnapshotへ含めません。

#### 1ワード／2ワード Topic Stock

1ワードと2ワードは、それぞれ独立した永続Topic Stockを持ちます。各Stockは有効な完成お題を最大12件保持し、`single`の1件はseedを1語、`double`の1件は異なるseedを2語保持します。各recordはcategory、完成topic、seed語、固定／最新のkind、取得済みcontext、Judge結果、`content_mode`、生成時刻、generation IDを持ちます。ワードプール、選択履歴、Topic Stock、`idlechat_topics.jsonl`の履歴と重複排除は別の責務であり、履歴fileを有効在庫の正本にしません。

seed語の選択、ワードプールの日次更新、選択履歴、取得済みcontextの接続、在庫の永続化、重複排除、消費、補充はCOREが担います。お題候補生成とJudgeはShiro帰属のside-effectなしCodexExe requestで実行します。CodexExeはActorまたはAgent identityではなく、生成主体と監査上の帰属はShiroのままです。Worker LLM、ChatWorker、Coder系provider、別Model、固定文をこのStock生成の暗黙fallbackにしません。

1件の論理生成flowは「COREによるseed選択 → CodexExeによる最大3候補生成 → CodexExeによるJudge → COREの契約検証 → atomic保存」とします。CodexExeへはcategory、seed語とkind、取得済みcontext、直近お題、現在の全Topic Stockの既出topic、禁止事項、構造化出力schemaを渡します。`single`は1語を主題の中心にした具体的な論点、`double`は2語を並べるだけでなく、両者の距離、共通構造、緊張、相互作用のいずれかが具体的に話せる論点とします。

COREは候補とJudgeを再検証し、必要seedの欠落、2ワードの同一語重複、語順だけの入れ替え、`present_day_relevance < 4`、安全性違反、空topic、構造破損を有効在庫へ入れません。完成topicは1ワードStock、2ワードStock、Forecast Stock、直近topic履歴の間で正規化後の完全一致と高類似を検査し、重複候補を`topic_duplicate`として拒否します。重複候補の拒否は既存の有効在庫を削除または置換する理由にしません。

1ワード／2ワード Stockの生成契約は次の通りです。

1. 起動時に両Stockを読み込み、空topic、seed欠落、category不一致、重複topic、解析不能なrecordを有効在庫として数えない。
2. 各Stockの読み込み後有効在庫が0件の場合に限り、起動時bootstrapでそのStockを1件まで初期生成する。両Stockを同時に生成せず、1ワード、2ワードの順に有限に実行する。
3. あるStockに有効在庫が1件以上ある通常再起動では、そのStockの起動時bootstrapを行わない。不足分はIdle時またはHeartbeat時に補充する。
4. Idle時およびHeartbeat時に、COREの優先処理、ユーザー会話、Chat、Worker、Coder、既存IdleChatが生成資源を使用していないことを確認し、不足しているStockを各12件まで段階的に補充する。
5. 1回の補充契機で1件だけを生成し、両Stockを通じて同時生成を禁止する。生成資源がbusyなら失敗扱いにせず、既存在庫を変更せず次回のIdle／Heartbeatへ延期する。
6. episode準備でお題を1件消費したら不足状態として記録し、会話開始を補充処理で待たせず、次回のIdle／Heartbeatで補充する。
7. 要求されたcategoryのStockが空の場合は同じCodexExe契約でインライン生成できる。生成失敗、seed不足、空topic、重複を別category、Worker LLM、固定文の成功へ丸めない。
8. 生成、消費、補充のたびに永続在庫をatomic更新し、再起動で有効在庫を再利用する。CodexExe内部thread、working directory、Model contextをStock正本にしない。
9. Debug Viewerの`Topic Stock`は1ワード、2ワード、Forecastを別sectionで表示し、各Stockの件数、不足数、生成中状態、最終契機、最終エラー、topic、seed、生成時刻を読み取り専用snapshotとして表示する。Viewer表示、section切替、再読込は生成、消費、修復の契機にしない。

1ワード／2ワード対話は、episode準備phaseでCORE正本のMioとShiroのキャラクターSystemPrompt、採用topic、seed context、`content_mode`をCodexExeへ入力して会話全体を生成します。COREは1turnごとに話者帰属、Persona、直前発話との文脈、反復、seedとtopicの整合、事実性、meta漏れ、`content_mode`を判定します。最初のNGが`turn k`なら`turn 1..k-1`の本文、Agent identity、`message_id`を固定し、NG理由と確定prefixをCodexExeへ渡して`turn k`以降のsuffix全体だけを再生成します。有限回の再判定で全turnが合格するまで`ready`へ公開しません。

戦争、武力衝突、災害、人命被害、避難、喪失を直接扱う1ワード／2ワードtopicは`serious`、それ以外の政治、政策、制度、思想は`assertive`、その他は`free`とし、`serious > assertive > free`を適用します。Mio／ShiroのPersonaと口調は保ちますが、`serious`では茶化し、軽口、娯楽化、被害の矮小化、扇情的な断定を拒否し、確認できた事実、不明点、予測、Agentの意見を分けます。`assertive`は人工的な中立化を強制しませんが、個人属性への侮辱、差別・人格否定、暴力扇動、根拠のない事実断定を禁止します。Forecastのドメイン別未来範囲は1ワード／2ワードへは適用しません。

最低限の契約testは、各Stockの未作成、全件無効、片方だけ空、部分在庫、満杯、消費後、生成資源busy、同時Heartbeat、CodexExe失敗、重複topic、保存後再起動を対象とします。さらに、Stock生成がWorker LLMとChatWorkerを呼ばないこと、2ワードの同一語・逆順組を合格させないこと、カテゴリ横断の重複がないこと、Mio／Shiroの正本SystemPromptとrevisionが台本入力へ反映されること、最初のNG turn以降だけが新しい`message_id`で修復されること、`serious`違反を合格させないこと、CodexExe失敗を別provider成功へ丸めず既存在庫を維持することを確認します。

#### Forecast Topic Stock

Forecastストックのキーワード抽出とお題生成はShiroが担当しますが、実行機構はWorker LLMルートからCodexExeへ切り替えます。CodexExeはActorまたはAgent identityではなく、生成主体と監査上の帰属はShiroのままです。Coder系Forecast provider、Worker LLM、別Model、固定文への暗黙fallbackは設けません。Judge応答の途中終了と無制限な再生成を避けるため、1試行の候補は最大3件にします。

ニュース、RSS、トレンドの取得、source provenance、ランク付け、永続化、重複排除、消費と補充はCOREの責務に残します。CodexExeへは対象ドメイン、その未来範囲、選定済みseed、既出テーマ、禁止事項、構造化出力schemaを渡します。「キーワード抽出 → COREによる関連ニュース拡張 → 最大3候補生成 → Judge → COREの契約検証 → atomic保存」を1件の論理生成flowとし、CodexExe内部thread、working directory、Model contextをストック正本にしません。

Forecastストックの生成契約は次の通りです。

1. 起動時に永続ストックを読み込み、空topic、重複topic、解析不能なrecordを有効在庫として数えない。
2. 読み込み後の有効在庫が全体で0件の場合に限り、起動時bootstrap生成を行う。ストックファイル未作成、空ファイル、全件無効、全件消費済みを同じ0件条件として扱い、6ドメインを順番に各1件まで初期生成する。
3. 有効在庫が1件以上ある通常再起動では、起動時bootstrap生成を行わない。ドメインごとの不足はIdle時またはHeartbeat時に補充する。
4. Idle時およびHeartbeat時に、COREの優先処理、ユーザー会話、Chat、Worker、Coder、既存IdleChatが生成資源を使用していないことを確認し、不足しているドメインを上限2件まで段階的に補充する。
5. 1回の補充契機で生成を無制限に連鎖させない。同一ドメインの同時生成を禁止し、生成資源がbusyなら失敗扱いにせず次回のIdle／Heartbeatへ延期する。
6. お題を1件消費したら不足状態として記録し、会話開始を補充処理で待たせず、次回のIdle／Heartbeatで補充する。
7. ストックが空のまま利用要求を受けた場合はインライン生成を許可する。ただし、生成失敗、空topic、重複、seed不足を別のお題や別カテゴリの成功へ丸めない。
8. 生成・消費・破棄・補充のたびに永続ストックを更新し、再起動で有効在庫を再利用する。保存済み在庫がある限り、再起動だけを理由に同じ補充を繰り返さない。
9. CORE Debug Viewerは読み取り専用snapshotとして、合計件数、生成中状態、最終補充契機、最終エラー、各ドメインの件数、お題本文、生成日時、シードを表示する。Viewer表示や再読込を在庫生成・消費の契機にしない。

Forecast対話は、episode準備phaseでCORE正本のMioとShiroのキャラクターSystemPromptをCodexExeへ入力して生成します。各turnの生成と検証には、対応する構造化`speaker`のSystemPrompt、確定済みprefix、Forecastドメインと未来範囲、source context、`content_mode`を使います。CodexExe側にSystemPromptを複製せず、COREが実行ごとに正本から組み立てます。

対話の正当性は`story_reading`と同じturn単位契約で確定します。1turnごとに話者帰属、Persona、文脈、反復、事実と予測の分離、未来範囲、meta漏れ、`content_mode`を判定し、最初のNGが`turn k`なら`turn 1..k-1`とその`message_id`を固定します。NG理由と確定prefixをCodexExeへ渡して`turn k`以降のsuffix全体を再生成し、有限回の再判定で全turnが合格するまで`ready`へ公開しません。

戦争、武力衝突、災害、人命被害、避難、喪失を直接扱うForecastは`serious`とし、政治的背景があっても`assertive`より優先します。Mio／Shiroの語彙、語尾、関係性は保ったまま、茶化し、軽口、娯楽化、被害の矮小化、扇情的な断定を`content_mode_violation`として拒否します。確認できた事実、不明点、予測、Agentの意見を分けます。それ以外の政治、政策、制度、思想は`assertive`とし、人工的な中立化を強制せず、個人属性への侮辱、差別・人格否定、暴力扇動、根拠のない事実断定を禁止します。優先順位は`serious > assertive > free`です。

起動時bootstrapには、初回導入、ストック消失・破損、全件消費後でも最初のForecastを在庫なしで待たせない役割があります。Idle／Heartbeat補充には、通常稼働中の負荷を平準化しながら各ドメインの在庫を最大2件へ戻す役割があります。この二つを代替関係として扱わず、どちらか一方を削除してはいけません。

最低限の契約testは、ストック未作成、全件無効、部分在庫、満杯、消費後、生成資源busy、同時Heartbeat、生成失敗、保存後再起動を対象とします。部分在庫では起動時生成を行わずHeartbeatで補充されること、保存後再起動では不要な再生成が起きないことを確認します。さらに、Forecastストック生成がWorker LLMを呼ばないこと、6ドメインの未来範囲が候補・Judge・検証で一致すること、Mio／Shiroの正本SystemPromptとrevisionがForecast台本入力へ反映されること、最初のNG turn以降だけが新しい`message_id`で修復されること、`serious`違反が合格しないこと、CodexExe失敗を別provider成功へ丸めず既存在庫を維持することを確認します。

## 音声と外部 runtime

CORE は STT/TTS の接続、request、Viewer 操作、状態を持ちます。STTは
`Viewer -> CORE /stt -> RenCrow_STT -> external STT target`、TTSは
`CORE -> RenCrow_TTS -> synthesis target`を正規経路とします。表示文生成、音声認識、音声合成、音声取得、
通常CHATでは、Viewerが選んだMio・Shiro・Midori・KuroのAgent IDをTTSのcharacter_idとvoice_idへ引き継ぎます。明示commandなどの非CHAT routeは既存のroute ownerを優先します。
ブラウザ再生は別々の成功条件です。LLM も inference endpoint と management endpoint を分け、ready 確認後に選択を確定します。

## 画像・動画認識

画像・動画認識の正規経路は
`CORE -> RenCrow_Vision -> Wild backend -> RenCrow_Vision -> CORE`です。
COREはViewer、PORTAL、CMD、channelから受け取った画像・動画を保存し、種類を判定した後、
raw mediaと利用者promptをRenCrow_Visionへ送ります。

RenCrow_VisionはMIME、size、durationを検証し、動画では必要なframe samplingを行います。
認識backendとの通信と結果の解釈はRenCrow_Visionが所有し、COREはその内部設定を持ちません。
RenCrow_Visionは解析結果を`summary`、`text`、`segments`、`metadata`へ正規化してCOREへ返します。

COREはVision結果を利用者応答へ使うか、選択済みAgentへtext contextとして渡すかを
決定します。この後段判断はRenCrow_Visionが行いません。後段Agentへ渡す場合もraw mediaを
再送せず、Visionが返した解析textと必要最小限のmetadataだけを渡します。
Visionのunavailable、timeout、unsupported media、decode失敗、空結果は同じ`trace_id`で
利用者向けerrorと運用logへ残します。

## News Packの限定Article Reader fallback

通常HTTP取得が`blocked_by_policy`の場合に限り、`web_gather.article_reader.enabled=true`かつ元URLのhostが明示allowlistにあるときは第三者Readerをoptional fallbackとして使えます。Reader応答の元URLが要求URLと一致し、完全性検査を通過した本文だけを採用します。元URL、Reader取得URL、取得時刻、SHA-256、providerをmetadataと永続取得台帳に保存します。Reader失敗時はRSS description／contentと既存項目を削除しません。

## Atlas / Backlog / Implementation Lifecycle

Atlasは、Radar、Candidate、採用済みBacklog、Implementation Unit、Evidence、現在機能地図を
COREで一元管理するDebug／開発管理機能です。外部情報は命令ではなくRadar sourceとして保存し、
認証済みSystem Owner requestによってのみ採用を同期確定します。人の返答待ちstatusやdecision-wait
queueは作りません。

Concept StateとDelivery Stateを分離し、採用済みImplementation Unitのglobal WIPを1に制限します。
状態遷移はCOREの決定的state machineが検証し、LLMやlegacy `check_ok`入力から直接完了状態を
代入しません。`LIVE_VERIFIED`は仕様、TDD、E2E、build、deploy、restart、readiness、production
smokeのrequired Evidenceを各owner routeで検証できた場合だけ成立します。その後、Current／Workstream更新、
closure receipt、Lease解放を同じlifecycle runで冪等に完了して`DONE`とし、次Unitを開始可能にします。
失敗終端`BLOCKED`ではLeaseを解放してもdurable Queue Freezeを保持し、再起動やLease不在だけで後続へ進みません。
詳細状態、Evidence、Viewer、完了条件は
[Atlas / Backlog / Implementation Lifecycle仕様](RenCrow_Atlas_Backlog_Implementation_Lifecycle_仕様.md)を
正本とします。

初期Backfillはdataset ID `rencrow-atlas-initial-backfill`、revision 1、canonical SHA-256
`7fd72429f88ff6eeb4be9e08619087a6c7c7b3038ed1b81a7e0e519dab2fb4af`の復旧packageをCOREへ
埋め込み、起動時に既存Backlog JSONLへ冪等reconcileします。114 Design CardのPurpose、Problem、Idea、
Background、Expected Effect、Relations、Source Strength、SpecificationRefsを保持します。packageが申告する
Delivery Stateは`declared_delivery_state`へ保存し、Evidenceのないruntime `delivery_state`は`NONE`から開始します。
local Specification 8件はcontent hash検証済み本文、external 3件はEcoSystem正本へのmetadata参照として扱います。
fixture、JSONL representation、seed、staging directoryはproduction import sourceまたはruntime正本にしません。

`owner_module`は機能codeの配置先ではなく、Atlas Item、Implementation Unit、global WIP、
Evidence Gate、`LIVE_VERIFIED`判定を管理するLifecycle ownerであり、`RenCrow_CORE`に固定します。
ShiroとCoder AgentはCORE管理下の実装Actorです。codeの配置先repositoryは`target_modules`、完成機能の
利用先は`consumer_modules`、test・build・互換確認の影響範囲は`affected_modules`として分離します。
根拠のないtargetやconsumerをBackfill時に推測補完しません。

runtime合格にせず、claimsとCORE-owned verified resultを別投影します。固定sourceはembedded Specification、
stage marker付きExecutionReport、固定deployment receipt、clean executable revisionを束縛したloopback
`/ready`／Atlas item smokeです。stage receipt、durable Queue Freeze、atomic replacement、LIVE→DONE closure、
recovery、JSONLのfail-closed規則、legacy migrationの詳細は
