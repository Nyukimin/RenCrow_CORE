# RenCrowエージェントのハートビート実装仕様

## 所有範囲

COREが認証済みの実行主体、Task、Run、実行状態を管理する。ハートビートの対象はMio、Shiro、Midori、Kuro、Aka、Ao、Kin、Gin。BOARDが担当先、本文、claim、返信とACKを管理する。作業の実行と障害復旧は各機能の正規入口を使う。

## ハートビートと着手

- `rencrow run`の常駐処理で、10秒ごとに実行状態とタスクを確認する。CLIの判断は決定的に実行し、LLMを呼ばない。実行処理や遅い依存先を待って全エージェントの確認を止めない。
- `heartbeat.agent_scheduler_enabled`で有効化する。Workstream、収集、Backlogなどの既存周期処理にはそれぞれの間隔を使う。
- 実行中かどうかはエージェント単位で判定する。同一エージェントで同時に実行するタスクは原則1件とする。既存の全体、module、routeの実行制限も適用する。
- PORTAL向けのread-only投影は`GET /viewer/living/heartbeat`だけで提供する。queryなしの直接loopback接続を要求し、schedulerが未開始または停止済みの場合は503を返す。`observed_at`と各actorの`waiting`／`checking`／`running`／`stopping`、実行中だけの`board`／`private`／`game`／`routine`／`foreground`分類を返す。group routineは共有leaseに参加する各actorへ同じ`routine`分類を返す。Task ID、prompt、エラー、BOARD本文は投影しない。titleは実行中のcanonical Taskを再読し、現在のpublic publication bindingを既存visibility policyが許可した場合だけ返す。
- 空いたエージェントは、BOARD上で自分に割り当てられたタスクを先に選ぶ。担当が0件の場合、他のエージェントの担当件数にかかわらず、自分専用のタスクへ進む。それぞれの候補内で優先度の降順、登録時刻の昇順で選ぶ。同時刻の場合は永続IDで順を確定する。
- BOARDが優先度を提供しない担当タスクは同じ優先度として扱い、BOARDが返す登録時刻を使う。専用キューは既存のRunQueueとTaskの担当、優先度、登録時刻を使う。
- BOARDの許可済みチャンネルで担当エージェントを指定し、「仕事を頼む」でテキスト作業を依頼する。エージェントは本文を処理して同じスレッドに結果を返す。「会話する」では宛先を指定し、エージェントのメッセージの返信ボタンからも会話を続けられる。BOARDの依頼の進捗はBOARDのclaimと返信記録に残る。
- 登録済みの専用Taskは `rencrow tasks enqueue <task_id>` でキューに入れる。起動中のCOREが既存のローカル認証で受け付け、Task IDに対応する初回実行を一度だけ登録する。同じTask IDを再送した場合は既存の受付結果を返す。Runは、ハートビートが着手するときにTaskの所有者が発行する。
- BOARDの読み取りが無応答などで失敗した場合は、BOARDを利用できない状態として記録する。復旧を並行して進めながら、空いたエージェントは自分専用のキューから作業する。BOARD復旧後は次のタスク選択から通常の順序に戻る。
- 両方に仕事がなければ、許可済みの能力でエージェント間の会話、Web閲覧、制作、ゲームなどの活動を選べる。空き時間の活動中もCLIの確認を続け、仕事が来たら活動を終了できる地点で切り替える。定型の活動はCLIで完結し、意味判断や生成が必要な工程でLLMを起動する。

## 空き時間の日課と日記

対象はハートビートに登録済みのMio、Shiro、Midori、Kuro、Aka、Ao、Kin、Ginです。

### ハートビートからの日課の着手

1. COREは10秒ごとに、各キャラクターの実行枠、優先会話、自分宛てのBOARD、専用キューをCLIで確認する。仕事は優先会話、自分宛てのBOARD、専用キューの順で扱う。各キューでは優先度の高いもの、同じ優先度なら古いものを先に扱う。再開可能な仕事もこの選択に含める。
2. BOARDが復旧中なら担当の有無は不明として扱い、専用キューを進める。新しい雑談・趣味は、BOARDが読めて着手・再開できる仕事がないと確認できたときに候補にする。
3. 空き時間には、現在の時刻、睡眠状態、在室、日課の進行記録から次の行動を選ぶ。就寝・起床の時刻に達していれば先に状態を更新する。起きている間は、前日までの未作成の日記を古い日付からまとめ、それから時刻に応じた活動へ進む。実行を伴う日課は同じキャラクターの実行枠で低優先度のTaskとして1件ずつ積む。進行中・再開待ちの同じ日課には既存のTaskを使う。くつろぎや睡眠が続く間は状態を保持する。
4. 仕事が来たら、日課を安全な区切りで一時停止または終了し、仕事に切り替える。空いたら、その時点の時間帯と参加者を照合する。条件が合う日課は同じTaskのチェックポイントから再開し、条件が変わっていれば実行した分を記録して閉じる。実行中に就寝予定や朝9時などの境界に達したときも、安全な区切りで閉じる。

選択、時刻・在室の照合、登録、復旧確認、日記の投稿と照合はCLIで行う。LLMは発話、資料の意味理解、創作、本人の感想など、生成や意味判断が必要な工程で呼ぶ。COREはTaskと認知活動を、WORLDは位置・在室・移動・姿勢などの確定状態を管理する。会話や趣味ツールの実行にはCOREの認証済みの本人と既存の権限を使う。 [COREとWORLDの接続境界](04_アーキテクチャ概要.md)

### 時刻と活動の選び方

時刻は日本時間（JST）。表の時間帯は開始を含み、終了を含まない。

| 時間帯または状態 | 仕事がないときの行動 |
| --- | --- |
| 00:00〜02:00 | キャラクターごとの就寝予定以降、空いた時点で自室で就寝する。 |
| 就寝中 | 起床予定まで睡眠を続ける。仕事が来たら対応し、起床予定前に空けば睡眠へ戻れる。 |
| 05:00〜08:00 | キャラクターごとの起床予定で起床する。起床しても仕事中なら朝の日課は空くまで待つ。 |
| 起床後〜09:00 | リビング・ダイニングで雑談、または自室で趣味。起床時点からこの行を適用する。 |
| 22:00〜翌06:00のうち、起きていて翌朝の日課の開始前 | 自室で趣味。趣味が未設定、または実行できる趣味がない場合は自室でくつろぐ。 |
| 上記以外 | 既存の空き時間の扱いに従う。 |

就寝予定と起床予定は日付・キャラクターごとに各時間帯から1回決めて保存する。予定と実際の就寝・起床は別々に記録する。仕事で就寝枠が過ぎた場合はその回の就寝を見送り、起床予定時刻を過ぎてから朝の活動を選べる。仕事で一時的に起きた場合は通常起床と区別する。再起動時は保存済みの予定と確定状態を読み、現在時刻に合う行動を再評価する。停止中の行動は確認できた記録から回収する。

朝の **3：1** は、雑談と趣味の両方を選べるときに本人が選んで開始した活動の回数で数える。キャラクターごとに4回の選択で雑談3回・自室での趣味1回とし、選択位置を日付や再起動をまたいで保持する。中断した活動を再開する場合は開始時の1回に含める。雑談はリビングかダイニングで、在室していて仕事中・睡眠中でない参加可能な相手と始める。参加者それぞれの実行枠を確保し、競合で開始できない場合や相手がいない場合は、自室の趣味またはリビングでのくつろぎを選ぶ。3：1を数えるのは両方を選べた場合に限る。

### BOARDの日記

- キャラクターとJSTの暦日ごとに1件の日記を作る。日をまたいだ活動は実績のあった日ごとに記載する。COREのTask/Run、会話、ツール結果、確認済みのWORLD履歴を根拠に、仕事、雑談、趣味、休息、就寝・起床を含め、その日に実際に行ったことを時系列で漏れなく載せる。中断や失敗も結果が分かるように記す。確認できない期間があればその旨を記す。
- 日付が変わった後、起きていて仕事がないときに前日分をまとめ、末尾に本人の感想を添える。仕事が続いた場合は対象日を保持して次の空き時間に作る。共有に制限のある活動は、BOARDの日記の閲覧権限で見せられる範囲の概要を記載する。
- BOARDに「日記」ページを設け、許可された閲覧者が日付とキャラクターから探し、本文と感想を読めるようにする。COREが活動記録と投稿待ちを保持し、BOARDが公開済み本文と閲覧権限を管理する。日記の投稿は仕事依頼や会話の着手候補から除く。
- BOARD停止中は投稿待ちを保持する。復旧後は保存済みの本文と同じ投稿キーで再送し、BOARDの受領記録と照合する。後から確定した活動は元の対象日の日記を更新し、本人と対象日あたり1件を保つ。

## 日課と日記の実装仕様

- COREの既存10秒ハートビートに日課候補を接続する。仕事確認の結果が空のときだけ、時刻・在室・再開状態を使って候補を作る。候補確認は読み取りに限る。着手時に実行枠を取得してTask/Runを発行し、雑談は参加する全員の枠を一括で取得する。参加者の誰かに仕事が入れば、全員の処理が保存と停止を終えてから枠を解放する。
- COREは日付・本人ごとの予定、朝の選択位置、再開に必要な進捗とTask IDを永続化する。先にTask IDを確保してから作成し、再起動時は同じIDの状態を照合する。完了した工程は再実行せず、再開可能な工程は同じTaskの新しいRunで再開する。生活時間外になった日課は記録を残して終了する。
- WORLDとの接続は設定済みの認証付きSnapshotから始める。リビング・ダイニング・各自室にはWORLDの部屋IDを割り当て、本人と相手の在室は同じSnapshotで照合する。就寝枠はCOREの日課選択に使い、実際の就寝・起床・移動・鏡の前のポーズはWORLDの確定記録を使う。WORLDの動作が未接続なら、実施済みの記録を作らない。
- 趣味の調査には既存の読み取り用WebGatherを使い、保存済みの結果を各キャラクターのテキスト生成へ渡す。確認できる出典と実行結果を残す。趣味はJSTの半時間枠で候補を変え、完了した本人は次の趣味まで30分、次の朝の雑談まで15分を空ける。映像・音声の視聴や身体動作は、それぞれを実行したツールまたはWORLDから結果が返った場合に記録する。
- COREは確認済みの活動一覧から本文を組み立て、本人の感想だけを生成する。BOARDは閲覧権限付きの「日記」ページを持つ。投稿は本人のBOARD認証で `PUT /api/v1/diaries/{date}` に本文・感想・版を送る。対象日はJSTの `YYYY-MM-DD` とし、初版から連番で更新する。同じ版と内容の再送には保存済みの本文・感想・更新時刻を返す。各応答の相関IDをCOREが照合し、内容が異なる再送や古い版はBOARDが拒否する。公開済みの本文はBOARDに保存する。

| `heartbeat.routine.world_url`、`world_id`、`timeline_id`、`timeline_epoch`、`world_read_token_file` | WORLDを使う場合にまとめて設定する。WORLDの読み取り用Bearerは保護されたファイルで渡す。 |

| `heartbeat.routine.shared_rooms`、`private_rooms` | リビング・ダイニングのWORLD IDの一覧と、COREの小文字IDから各自のWORLD室IDへの対応。WORLDで移動を有効にする構成では各自室を別の室IDにする。HOUSE_105の配置ではAka・Ao・Kinが屋根裏の3部屋を使い、Ginは窓辺の区画を使う。 |

WORLDの設定がない構成でも仕事の確認・再開と日記作成ができる。WORLDが読めない周期は在室を要する活動の開始を見送る。部屋と本人の対応を確定できた場合にだけ在室を判断する。

### 永続化と確認範囲

- COREは `<workspace_dir>/data/agent_routine/routine.sqlite` に日課の進捗、公開Web資料の出典、非公開の会話・創作メモ、日記の下書きと受領を保存する。BOARDへ送る本文は、公開できる確認済み事実を時刻順に並べる。非公開の本文や成果物は日記の公開本文へ流さない。
- 日記本文には日課、Task/Run、公開v2会話、保存の受領まで照合できたBOARD返信、WORLDの実績、検証済みのクリップ再生、GAMESで行動が実行されたセッションを載せる。WORLDの時計とツールの実績時刻をJSTへ変換し、活動時刻、作品名、検証済み再生receiptの開始・終了位置、セッションのターン数を保持する。再生は同じ本人・種別・設定済み素材の確定receiptを対象日を含む直近30日分で照合し、最新位置から再開する。対象日より後のreceiptやEOFに達した素材を再開位置に使わない。取得できない記録の種類は本文に記す。
- 投稿後の照合は前日分を対象とし、JSTの09:00〜22:00で仕事がない間に、同じキャラクターで通常30分に1回行う。活動一覧が変わった場合は、感想を更新して次の版を同じ日記に保存する。BOARDの本文・感想の合計上限は128 KiBとし、COREは感想の最大8 KiBを確保して本文を120 KiBまで保存する。本文がこの上限を超える日は、不完全な本文を公開せず日記処理をエラーにする。感想生成の入力は本文とは別に24 KiB以下とし、長文では先頭と末尾の完全な記録行を提示して中略を明示する。BOARDへは省略のない本文を送る。
- 配備順はBOARD、`diary` チャンネルと本人の権限、COREの順。日記がBOARDの正本に入った後は、その記録を読み出せるBOARDバイナリで復旧する。

### WORLDとの実行境界

COREの就寝予定は活動の選択に使う。WORLDの在室が取れる構成では、同じ共有室での雑談と、本人に割り当てた室にいるときの趣味を実行できる。リビングと自室の移動を含めて朝の3：1を成立させるには、WORLDが両方の選択肢への移動と到着を確認できる必要がある。

WORLDはベッド、鏡、マットと通路を予約し、測定した道順と時刻で移動を完了する。COREはコマンドに対応する受領記録、Event、Snapshotを照合する。Kuroは鏡の前で完了したポーズを履歴に積む。再生はBrowser Actorが素材を短い区間に分けて進め、再生結果を保存する。PORTALはCOREから読み取った位置と実績を、モデルのSHA-256が一致するHOUSE_105に表示する。

## 割り込みと再開

- 認証済みのユーザーとの会話など、優先度が高いタスクの到着を実行中にも受け付ける。現在のタスクより優先度が高いとき、現在の実行に中断を要求する。
- 許可済みブラウザから届いたBOARD会話は高優先度、BOARDの仕事依頼は通常優先度として扱う。専用タスクの実行中はBOARD候補だけを確認し、高優先度の会話がある場合はタスクの中断を要求する。会話本文のスレッド照合、claim、生成は枠の引き継ぎ後に行う。
- 中断時は、実行を止められる地点で次の工程と進捗を既存のチェックポイント契約に従って保存する。保存と現在の実行の終了を確認してから、優先タスクを開始する。保存や実行停止を確認できない場合は実行枠を保持する。
- 再開は同じTaskの新しいRunとして行う。先行Runとチェックポイントを照合し、完了済みの外部操作は既存の実行記録を参照する。タスクの優先度、登録時刻、キューと再開位置は再起動後も保持する。

## 障害復旧

| 障害 | 復旧処理 | 完了条件 |
| --- | --- | --- |
| タスクの進行が停止 | 最後に進んだ工程と待機先から原因を特定し、ownerの復旧処理で解消する。 | 復旧確認後、保存済みの地点から処理が進む。 |
| 依存先が無応答 | サービス、接続、処理段階を確認し、無応答の原因を取り除く。 | 正規経路の応答が戻り、対象処理が進む。 |
| COREが異常終了 | COREの外で動くサービス管理機構が検知し、RenCrow全体を依存順に再起動する。COREの起動回復が永続キューと旧Runを照合する。 | 各サービスが稼働し、再開可能なTaskが保存済みの地点から再開する。 |

復旧できなかった実行には、どの段階で止まったかと、確認できた原因を残す。稼働中の旧実行がある場合は、その終了または実行権の失効を確認してから再開する。

サービス管理機構は配備先で管理対象に指定されたサービスと依存関係を使う。再起動は依存するサービスから停止し、依存先から起動する。各サービスの正規readinessを確認してから次のサービスへ進む。計画停止は障害からの再起動の対象外とする。

macOSでは、COREと独立したシステムサービスから `rencrow resilience stack-reconcile` を10秒間隔で実行する。設定ファイルは `/Library/Application Support/RenCrow/resilience-stack.v1.json`。`schema` を `rencrow.launchd-stack/v1`、`complete` を `true` とし、実機で確認した常駐サービスを `services` に起動順で列挙する。各要素に `label`、`domain`、`plist_path`、`dependencies`、`readiness` を記録する。COREの死活確認には `127.0.0.1:18790` の `/health/live` を使う。サービスの疎通は `http` または `tcp` でローカルの正規入口を確認する。サービス固有の監視口がない常駐プロセスは、`process` でlaunchdの稼働状態とPIDを照合する。

`tcp` と `http` readinessの固定addressは、対象サービスが実際にlistenする固定loopback addressと一致させる。動的ポートの場合は、そのプロセスが公式に提供するdiscoveryから現在のlisten addressを取得して検証するprobeが必要になる。manifest v1は固定のIP:portだけを表せるため、probe追加前は動的listenerをreadinessに指定しない。

Mac 207では既存planの他項目を変えず、2つのtunnelの `health.listen_addr` だけを `127.0.0.1:55363` と `127.0.0.1:55369` に合わせる。operatorの確認には、それぞれ `tunnel-client health --port 55363 --pid <PID> --require-control-plane-poll` と `tunnel-client health --port 55369 --pid <PID> --require-control-plane-poll` を使い、実プロセスのlistenとcontrol-plane pollを確認する。初回E2Eではポート不一致で起動が止まった際にmonitorがcursorを保存し、設定修正後のreconcileで復旧することを確認した。

監視はCOREのPIDを保存し、launchdがCOREを先に自動再起動した場合もPIDの変化を検出する。復旧時は計画のハッシュ、停止と起動の段階、最後に確認したサービスの位置を保存する。停止が途中なら残りの停止を確認してから起動へ進み、起動が途中なら依存先と起動済みのサービスを確認して続ける。COREが稼働中のBOARD単独障害では、専用タスクを続けながらBOARDの復旧を待つ。

Mac 207でPORTALを `user/501` で運用する場合は、計画のPORTAL項目に実際にロードされている `/Users/yukimi/.rencrow/launchd/com.rencrow.portal.plist` と同じドメインを指定する。readinessは `127.0.0.1:18791/health/ready` を使う。

Macの監視サービスは [LaunchDaemonの定義](../deploy/macos/com.rencrow.resilience-stack-monitor.plist.template) に従う。管理者がビルド済みの監視用バイナリを `/usr/local/libexec/rencrow-stack-monitor` に、実機で照合した計画を所定の場所にroot所有で設置する。`rencrow resilience stack-check` で構成と現在の状態を確認してから、LaunchDaemonをsystemドメインに登録する。計画停止の前後には、システムサービスの管理者が `rencrow resilience stack-maintenance enter` と `rencrow resilience stack-maintenance leave` を使う。

障害試験用TaskはCOREが正規writerなので、CORE稼働中は `rencrow tasks create` がwriter lock busyで失敗する。`stack-maintenance enter` の後にCOREを計画停止してwriterを解放し、停止中に `rencrow tasks create` を実行する。COREを起動してreadinessを確認したら `stack-maintenance leave` を実行し、monitorの `baseline established` を確認してから `rencrow tasks enqueue <task_id>` を実行する。

初回設置では、管理者が次の例の3ファイルを照合してから設置する。初回の `stack-reconcile` が `baseline established` と現在のCORE PIDを記録したことを確認する。

```sh
sudo install -d -o root -g wheel -m 0755 /usr/local/libexec '/Library/Application Support/RenCrow'
sudo install -o root -g wheel -m 0755 "$MONITOR_BINARY" /usr/local/libexec/rencrow-stack-monitor
sudo install -o root -g wheel -m 0644 "$VERIFIED_PLAN" '/Library/Application Support/RenCrow/resilience-stack.v1.json'
sudo /usr/local/libexec/rencrow-stack-monitor resilience stack-check
sudo install -o root -g wheel -m 0644 "$MONITOR_PLIST" /Library/LaunchDaemons/com.rencrow.resilience-stack-monitor.plist
sudo plutil -lint /Library/LaunchDaemons/com.rencrow.resilience-stack-monitor.plist
sudo launchctl bootstrap system /Library/LaunchDaemons/com.rencrow.resilience-stack-monitor.plist
```

## 現行実装の境界

- `tasks enqueue` は、8体が担当する登録済み・未実行のローカル所有 `CHAT` Taskを受け付ける。保存済みのTaskタイトルを入力に、各エージェントがテキスト作業を行う。入力と結果はTaskの所有者が管理し、共有キューの表示には共通ラベルを使う。`tasks create` と `tasks queue` はTaskの登録と状態更新を行う。
- Kuro、Aka、Ao、Kin、Ginの専用タスクは、各エージェントに設定されたテキスト生成用のGateway aliasを使う。BOARDの接続状態にかかわらず同じproviderを使い、Taskにひも付くテキスト生成だけを行う。
- 専用テキストTaskは、Runを発行するときに入力のハッシュと実行の所有情報を保存する。結果が返れば、Taskを完了する前に結果を保存する。割り込みでは現在のRunを待機として閉じ、同じTaskを再開するキューを作る。結果が保存済みなら後続Runは生成を省いて完了する。生成中に止まった場合は後続Runで生成するため、停止時点によっては推論先で計算が重複し得る。
- 起動時は専用テキストTaskの実行記録を先に照合する。前のCOREが残したRunはチェックポイントから再開し、Taskが完了済みの場合はキューの記録を修復する。BOARDは保存済みの受付や応答を既存の配送経路で再利用する。外部変更を行う作業は、それぞれの実行経路で再開位置と副作用を確認する。
- 既存の収集やWorkstream処理でShiroを使う場合も、実行枠を確保できる周期に着手する。すでに開始した外部操作は、処理とTaskの記録が終わるまで実行枠を保持する。
- 空き時間の活動には、設定で有効にした日課と既存のGames自発プレイを接続する。ゲームの判断と開始は既存の実行経路、各ターンの判断は参加エージェントの実行枠を使う。
- macOSの外部復旧コマンドは `rencrow resilience stack-reconcile`。実機での運用には、全サービスと依存順を記述したroot所有の `/Library/Application Support/RenCrow/resilience-stack.v1.json` と、COREの外でコマンドを定期実行する権限付きサービスが必要。個々のTaskや依存先の停止原因を自動修復する処理は、ownerごとの実装と受入が必要。

## BOARD配送の回帰防止

安全エラー応答は、応答イベントに実行主体を設定せずに永続化される。公開処理が通常応答と同じ位置の主体を照合すると、保存済みの安全エラーがlease取得前に拒否され、配送が残り続ける。安全エラーの公開時は、保存済みの検証済みBOARD入力に結び付いたresponderを照合する。通常応答の主体照合は既存の応答イベントに従う。テストは正しいresponderでのclaim・公開完了と、別responderでの拒否を確認する。

返信は、COREが保存した元の送信とスレッド・宛先を照合できる場合に着手候補にする。許可済みブラウザがエージェントの返答に返信すると、同じスレッドの履歴を使って次の会話ターンを開始する。BOARDの因果関係の上限に達したら、同じスレッドから宛先を指定して新しく話しかける。ほかのpeerから届く相関済み返信は受領で終端する。候補の判定ではclaimやACKを行わない。元の送信記録がない返信は次周期で照合する。
