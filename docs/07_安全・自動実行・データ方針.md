# 安全・自動実行・データ方針

## Workspace agent controlの優先境界

`workspace_dir/control/`はcharacterのcapability、route owner、handoff形式、Tool選択姿勢を宣言しますが、権限を付与しません。COREは読込時にproduction wiringとの整合を検証し、ToolRunner metadata、実行policy、sandbox、allowlist、runtime availabilityを常に優先します。

- characterは担当外で移譲先を独断選択せず、理由、必要能力、context、制約、期待出力、evidenceをOrchestratorへ返す。
- Tool providerの代替候補は自動fallbackしない。provider変更で外部送信、再現性、artifact保存先、画風が変わる場合は明示する。
- Workspace controlにendpoint、secret、任意model path、permission bypassを置かない。

## Global Policy Bundleとmodule policy

> 状態: schema v1、起動時read-only loader、hash／path／strict field検証、
> `/viewer/policy/status`を実装済みです。promotion、atomic reload、module側検査、監査、
> side effect enforcementは未実装です。policy fileを配置しただけで既存権限や挙動が
> 広がることはありません。

### ルールの分類と正本

| 種類 | 正本 | 実行時の役割 |
| --- | --- | --- |
| 利用者の意思、製品意味、module責務 | CORE現行正本 | 全policyが従う上位contract |
| 開発者／AI作業制約 | 各repositoryの最小`AGENTS.md`と関連rule／skill | 開発手順。runtime権限を付与しない |
| module横断の変更可能な運用方針 | `~/.rencrow/workspace/policies/` | active Global Policy Bundle |
| module固有のdomain rule | 各moduleの仕様、module policy、domain code | module内で検証・強制 |
| 絶対に越えられない上限 | 各moduleのbinary enforcement | runtime設定から緩和不能 |
| 判断と実行の証拠 | Policy Decision、audit、status、test | revisionと結果の追跡 |

全体ルールをWorkspaceへ集約する場合も、CORE製品仕様、各moduleのdomain仕様、binary hard limitを
Workspaceへ移動しません。Global Policy Bundleはそれらの範囲内で運用を狭める宣言です。

### Runtime directory contract

target layoutを次とします。

```text
~/.rencrow/workspace/policies/
├── manifest.yaml
├── global.yaml
├── capabilities.yaml
├── authorizations.yaml
├── data-handling.yaml
├── external-actions.yaml
└── deployment/
    ├── production.yaml
    └── development.yaml
```

- `manifest.yaml`は`schema_version`、`bundle_id`、`revision`、`created_at`、
  `minimum_core_contract`、各fileの相対pathとSHA-256、bundle全体のcontent hashを持ちます。
- pathはpolicy rootからの相対pathに限定し、`..`、symlink、hard link、絶対pathを拒否します。
- policy fileにsecret、credential、endpoint実値、個人情報、runtime DB、session、logを置きません。
- `deployment/*`はglobal上限を狭める差分だけを持ち、productionで許可されないcapabilityを
  development profileからproductionへ昇格させません。
- 未知field、未知schema version、hash不一致、重複policy ID、循環参照、上限拡大を拒否します。
- 読込順による暗黙上書きを許さず、各fieldの所有fileとmerge規則をschemaで一意にします。

schema v1の所有fieldは次のとおりです。

| file | field |
| --- | --- |
| `global.yaml` | `schema_version`, `policy_id`, `default_side_effect` |
| `capabilities.yaml` | `schema_version`, `policy_id`, `capabilities` |
| `authorizations.yaml` | `schema_version`, `policy_id`, `authorizations` |
| `data-handling.yaml` | `schema_version`, `policy_id`, `rules` |
| `external-actions.yaml` | `schema_version`, `policy_id`, `actions` |
| `deployment/*.yaml` | `schema_version`, `policy_id`, `profile`, `disabled_capabilities` |

v1は`default_side_effect: blocked`だけを受理します。`external-actions.yaml`のdecisionは
`blocked | explicit_authorization`に限定します。loaderは7 policy fileがmanifestに過不足なく
含まれること、各file hash、pathとhashをpath順に連結したbundle content hash、RFC3339時刻、
重複`policy_id`、未知field、symlink／検出可能なhard linkを検査します。

起動時statusは`active | missing | invalid`です。`missing`または`invalid`でも既存binary hard limitを
弱めず、invalidな内容を部分適用しません。現在はread-only status sliceであり、
`active`もside effect許可を意味しません。schema v1のstatusは安全側の`production` profileを
projectionし、profile切替とenforcement wiringは後続実装とします。

RenCrow_Workspace repositoryへ保存する場合は、このdirectoryのportable・non-secret fileだけを
明示allowlistへ追加します。runtimeからrepositoryへのsnapshotと、review済みrepository artifactを
runtimeへ反映するpromotionは別操作とし、backup処理からruntimeへ書き戻しません。

### 実効capabilityと優先順位

実効capabilityは次で決定します。

```text
effective_capability
  = binary_hard_limit
  ∩ global_workspace_policy
  ∩ module_policy
  ∩ deployment_config
  ∩ authenticated_request_scope
```

- Workspace、prompt、Agent、requestはbinary hard limitを解除できません。
- module policyとdeployment configはglobal policyを狭められますが、広げられません。
- capabilityを宣言しても、production wiring、Tool metadata、credential、runtime availabilityが
  不成立なら実行できません。
- 未分類のside effectは`blocked`です。少なくとも書込み、削除、外部送信、公開、課金、契約、
  Git remote操作、credential／network boundary変更、金融注文をside effectとして分類します。
- 複数のpolicyが一致した場合は最も制限の強い判断を採用し、denyをallowで上書きしません。
- Policy Bundleが未配置でも既存binary hard limitを弱めません。Policy Bundleを必須とする
  production capabilityは`disabled`または`unavailable`とし、暗黙の既定許可へfallbackしません。

### Module policyとbuild contract

各moduleは自分のdomain ruleを所有します。COREは共通envelope、global上限、module間contractを
所有しますが、TRADEの注文検査、LLMのruntime解決、Visionのmedia検証などを汎用Policy Engineへ
移しません。

module repositoryは必要に応じて次を持ちます。

- 現行仕様と実装仕様
- machine-readable module policyと安定したpolicy ID
- 純粋判定を行うdomain policy
- 外部I/O直前のenforcement gate
- allow／deny、境界値、unknown、dependency failureを含むcontract test
- buildへ埋め込むpolicy contract revisionまたはmanifest hash

Buildは`~/.rencrow/workspace`を入力にしません。repository内のschema、source、module policy、testだけで
再現可能にし、CIでCORE contract version、policy ID、上限非拡大、enforcement gate、拒否testを
検査します。文書やYAMLを`go:embed`等で同梱しただけでは実装済みとしません。

実行時はbinaryが持つcontract revision、module policy revision、active Global Policy Bundle revisionの
互換性を起動時に検証します。不一致時は対象side effect capabilityだけを安全側へ停止し、
通常Chatや安全なread-only機能まで偽の成功へ変換しません。状態はhealth／statusへ投影します。

### 変更、承認、promotion

Global Policy Bundleを通常のAgent、Coder、Workerがactive directoryへ直接上書きしません。
変更は次のlifecycleを通します。

```text
DRAFT
  -> STAGED
  -> VALIDATED
  -> PROMOTED
  -> ACTIVE
  -> SUPERSEDED

DRAFT | STAGED | VALIDATED
  -> REJECTED
```

1. 変更案をactive directory外へstagingする。
2. schema、hash、path、互換性、権限差分、必要testを検証する。
3. 現行revisionとの差分を`expansion | restriction | no_effect`へ分類する。
4. `expansion`は認証済み本人の明示許可をpromotion requestに含める。許可対象をbundle hashへ
   固定し、内容変更時は失効させる。許可がないrequestは待機状態を作らず同期的に`blocked`とする。
5. `restriction`の自動適用可否は専用capabilityで制御する。Kill Switch等の緊急停止は
   権限付与と分離し、即時かつ冪等に実行可能とする。
6. 検証済みbundleをatomicにpromotionし、同一request内でactive revisionを一つに固定する。
7. 読込後の互換性とstatus projectionを確認し、失敗時は直前のlast-known-good revisionを維持する。

validation失敗、許可不足、promotion失敗を成功扱いしません。部分適用、直接編集、mtimeだけによる
採用、Agent自身による権限拡大、許可後のpayload変更を禁止します。

### Policy Decisionと監査

Global、module、binaryの判定形式が異なっても、監査用envelopeは少なくとも次を持ちます。

- `decision_id`、`trace_id`、`request_id`
- requester、authenticated scope、対象module、action、artifactまたはresource
- binary contract revision、global bundle revision、module policy revision、deployment revision
- matched policy ID、`allowed | blocked | unavailable | degraded`
- 理由、入力snapshot hash、authorization ID、実行結果、時刻

secret、credential、個人情報、注文認証情報をPolicy Decisionへ保存しません。同じ処理のdomain固有
decisionを共通envelopeへ無理に統合せず、相関IDとrevisionで追跡可能にします。

### 受け入れ条件

- Policy Bundleなし、破損、未知version、hash不一致でside effectが既定許可されない。
- global、module、deployment、requestのどの層からもbinary上限を拡大できない。
- module buildがhome directoryやruntime Workspaceなしで再現できる。
- 権限拡大は同一bundle hashへの本人の明示許可なしにpromotionできない。
- reload中のrequestは単一revisionだけを参照し、部分適用されない。
- invalidなreload後も直前のactive revisionを維持し、失敗をstatusとauditへ残す。
- module固有の最終副作用地点に拒否testがあり、文書だけの禁止に依存しない。
- health／statusからbinary、global、moduleのrevisionと互換性、停止中capabilityを確認できる。
- RenCrow_Workspace snapshotへsecret、runtime state、DB、logを取り込まない。

## 同期実行policy

RenCrow_CORE は実行前の人間待機や判断queueを持ちません。各requestを受けた時点で、capability、利用者scope、allowlist、sandbox、credential、対象、risk policyを同期評価し、許可できる操作は直ちに実行し、許可できない操作は理由付きで`blocked`にします。

- 外部公開・投稿・送信は、設定済みadapter、許可scope、送信先、冪等性条件を満たす場合だけ実行する。
- 請求、支払、契約、価格決定は、専用capability、上限、対象、監査条件が明示されていない限り`blocked`にする。
- production dataや重要ファイルの破壊的変更は、対象path、sandbox、rollback evidence、事後検証を満たさない限り`blocked`にする。
- credential、権限、network boundaryの変更は、明示policyに存在しない限り`blocked`にする。
- 高リスクTool/Browser actionは、allowlist、timeout、scope、事後検証を満たさない限り`blocked`にする。

判断記録はPolicy Decisionとしてscope、requester、対象artifact、policy、判断、理由、実行結果、`trace_id`を保持します。過去の待機型field、endpoint、DB columnは現行契約へ引き継ぎません。

## Agent と Tool の境界

Advisor と Coder は提案者であり、実行責任者ではありません。Tool は人格や判断主体ではなく、allowlist、sandbox、timeout、監査 policy の下で呼び出される capability です。Shiro/Worker が side effect と実行policy境界の責任を持ちます。

ローカルModel、外部LLM API、Codex等のAgent RuntimeはAgentの推論実体であり、
通常応答に使用しただけではCORE Toolの実行権限を得ません。Kuro／Heavyは利用者決定による
明示的な例外で、CORE workspaceをworking directoryにしたCodex Agent Runtimeを
`danger-full-access`で実行します。この経路はGatewayでKuro／Heavy binding、target、
sandboxを固定し、request IDと実行結果を監査します。その他のAgent Runtimeのside effectは
COREのTool policyを通る別requestにします。

ローカルtargetから外部providerへの切替は単なる可用性fallbackではありません。
入力の外部送信、課金、保持policy、再現性が変わるため、COREが許可していない
providerへRenCrow_LLM、CMD、PORTALが無言fallbackしてはなりません。

## Knowledge と Memory

- external search は発見であり、確定 Knowledge の証拠ではない。
- source、取得時刻、要約、採用理由を provenance として保持する。
- Advisor 出力、候補資料、Revenue draft を自動 promotion しない。
- role visibility と context budget を適用し、不要な個人情報を Recall しない。
- 誤りを訂正できるよう、原資料と派生要約を区別する。
- L1 Raw会話からProfileExtractorが作るUserMemoryは、根拠event ID付きの`candidate`に限定する。自動処理だけで`confirmed`または`pinned`へ昇格せず、候補状態の情報をAgent promptへ注入しない。
- sensitiveと判定した候補、利用者scopeを確定できない候補、根拠Rawを参照できない候補は自動昇格せず、隔離または`failed`として観測可能にする。
- ProfileExtractor待ちを理由に利用者応答を遅延させない。未処理Rawを保持したまま、全LLMがIdleの期間へ延期する。
- X Bookmarkと外部SNS投稿は`source_confidence=low`の候補です。利用者がBookmarkした事実は内容の真偽確認ではなく、収集完了をreview済みKnowledgeやpromotion済みKnowledgeとして扱いません。

## Secret と個人データ

- secret を source、docs、log、trace、artifact に保存しない。
- runtime DBの物理pathは`storage.databases`へ明示し、backup運用時は全DBを`backup.core_source`配下へ置く。
- session、運用記憶、cold exportの物理pathは`storage.memory`へ明示し、backup運用時は全て`backup.core_source`配下へ置く。
- backup保存先、世代数、Redis/Qdrant export契約は`backup`を正本とし、runner内へ環境固有値をハードコードしない。
- Redis/Qdrantのlive volumeを直接archiveせず、backendの整合性あるsnapshot機能を使う。必須exportが欠けた実行を成功扱いしない。
- backupの圧縮は可逆形式だけを許可する。圧縮は暗号化ではないため、個人記憶を別host、removable media、cloudへ複製する前に暗号化し、復号鍵はbackup媒体と分離する。
- 世代数だけで保護済みと判断せず、checksum、展開、SQLite整合性、外部記憶exportを検証できた世代だけを復旧候補にする。
- local config、DB、session、音声、画像、browser profile は repository の外で管理する。
- log には必要最小限の識別情報だけを残し、公開前に redaction する。
- archive branch が公開であることを前提に、secret や私的 runtime data は archive にも置かない。

### Browser sessionの一回限り移植

画面のないhostへXのログイン状態を移す場合は、利用者の明示操作でX用Cookieだけを暗号化して
移植します。普段使用中の個人browser profile全体を複製せず、移植先ではrepository外の専用
persistent profileへ保存します。移植元browserのCookie、profile、ログイン状態を変更しません。

転送bundleはrandomな共通鍵によるAES-256-GCMで暗号化し、その鍵を移植先で生成した
RSA-OAEP公開鍵で包みます。秘密鍵は移植先だけに`0600`で保存し、平文Cookie、`auth_token`、
`ct0`、復号鍵を画面、clipboard、stdout、log、report、Gitへ出しません。import時は暗号形式、
X domain、必須Cookie、Bookmark URLへの到達を検証します。確認後は転送bundle、秘密鍵、
一時拡張を削除します。

認証切れや検証失敗は明示的なerrorとし、X API、別credential、個人profileの直接利用へ
暗黙fallbackしません。再認証または再移植は利用者の明示操作を必要とします。

## 失敗と degraded state

provider、LLM、STT、TTS、browser、storage の失敗を空の成功へ変換しません。`unavailable`、`pending`、`degraded`、`error` を区別し、再試行、fallback、利用者への表示を契約として扱います。
