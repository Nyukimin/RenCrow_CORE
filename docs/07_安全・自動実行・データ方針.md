# 安全・自動実行・データ方針

## Workspace agent controlの優先境界

`workspace_dir/control/`はcharacterのcapability、route owner、handoff形式、Tool選択姿勢を宣言しますが、権限を付与しません。COREは読込時にproduction wiringとの整合を検証し、ToolRunner metadata、実行policy、sandbox、allowlist、runtime availabilityを常に優先します。

- characterは担当外で移譲先を独断選択せず、理由、必要能力、context、制約、期待出力、evidenceをOrchestratorへ返す。
- Tool providerの代替候補は自動fallbackしない。provider変更で外部送信、再現性、artifact保存先、画風が変わる場合は明示する。
- Workspace controlにendpoint、secret、任意model path、permission bypassを置かない。

### Tool、Skill、MCPの共有選択原則

`workspace/control/tools.yaml`の`selection_principles`は、全Agentが作業方法を選ぶための共有ガイダンスです。これはruntimeのpermission、handoff／routeのdestination selection、deployment availabilityを付与・選択するものではなく、automatic fallbackも有効にしません。利用可能性と権限の正本はCORE metadataとruntime policyです。

- 作業開始時にCORE metadataと注入済み能力一覧から利用可能なTool、Skill、MCPを把握する。
- 目的、必要な証拠、副作用、再現性に合う最小の組合せを選び、単一手段への思い込みを避ける。
- 読み取りや検証に適切な能力がある場合は推測だけで済ませず、その能力で事実を確認する。
- 未提供・利用不能な能力を使ったふりをせず、必要能力と根拠をOrchestratorへ返す。

COREはproduction Worker Runner、起動時に検証済みのSkill catalog、接続済みMCPの観測結果から
`Runtime Capability Snapshot`を生成し、全AgentのStable RuntimeContextへ注入します。Snapshotは
認識と選択のためのprojectionであり、Agentの権限やroute ownerを変更しません。Skill本文の取得と
MCP呼出しはWorker Runnerのquery Toolとしてpolicy境界内で行い、任意path、未観測Tool、無効な
providerを暗黙に使用しません。

### Capability追加時の安全チェック

新しいTool、Skill、MCPは、既存のruntime source/listからWorker metadataまたはcatalogを作り、
同じ観測結果を`Runtime Capability Snapshot`へ投影し、Stable RuntimeContextへ注入する経路に
必ず参加させます。次のいずれかが欠ける変更は完了扱いにしません。

- Tool: Runner登録、Worker `ListTools`、Snapshot変換、policy付き実行の契約テスト
- Skill: 設定済み`SKILL.md`のstartup検証、`skill.read` catalog、Snapshot、無効化時の拒否テスト
- MCP: 起動／`tools/list`観測、namespaced Worker adapter、同一client停止、Snapshotの一致テスト

静的な重複一覧やdirectory scanによる実行登録を追加せず、認識と認可を混同しません。未接続・
未観測・一覧失敗は利用不可として理由を示し、別経路へfallbackしません。

### DB data capability境界

- Agentへ物理DB、任意SQL、table／column／path選択を渡さない。
- `data_capability.describe`はmetadataだけを返し、secret、絶対path、row内容を返さない。
- semantic lookupは固定されたread-only DBと名前付きindexを使い、必須keyと上限を検証する。
- Conversation／Persona／audit／governance／workflow等はraw参照を禁止し、認証済みowner serviceを使う。
- DB未配置、index不足、scope不明、Agent照会時のentity解決がcatalog-wide scanになる場合は
  `unavailable`または`blocked`とし、`%LIKE%`、別DB、Web検索へfallbackしない。起動時の明示的な
  schema migration／lookup key backfillは照会処理と分離し、完了後の名前付きindexを検証する。

### Catalog固有名詞の日本語表示と非翻訳

- 作品名、人物名、団体名、賞名等は事実identityであり、翻訳または創作の対象にしない。
- 取得元または公式根拠URLに日本語名が明示される場合だけ、その表記を`official_ja | source_ja`として採用する。
- 日本語名がない場合は原名をそのまま表示し、LLM、機械翻訳、読み仮名、類似作品、検索順位から邦題・和名を作らない。
- 日本語説明の生成は許可できますが、固有名詞を確定済み表示名へ固定し、説明翻訳の成功を名称検証の証拠にしない。
- 原名、原語、source record ID、canonical URL、日本語名の根拠URL、取得時刻を保持し、根拠のない日本語名はimport時に拒否する。
- source間で名称が競合する場合は優先順位だけで上書きせず、identityとprovenanceを再検証して`ambiguous | unresolved`を返す。
- 人物関連catalogは、新たな利用契約、利用申請、API key、access token、課金を必要とするsourceを使わない。provider未配置や公開source不足は`unavailable`とし、契約必要sourceへfallbackしない。

### 人物関連catalogの効率的な取得とreceipt

外部情報の取得は、requestごとにCOREが作る`person-related-plan.v1`の決定的な順序で行います。最初に対象人物の
明示評価、要求カテゴリ、既存indexed result、source・人物・カテゴリ単位のreceiptを確認し、freshなpositive resultまたは
TTL内のnegative receiptがある場合はそのsourceへのHTTPだけを発行せず、次のapplicable sourceを評価します。
名前だけでidentityを確定せず、identity解決は一run一回だけ行い、
確認済み外部IDを全カテゴリへ再利用します。

収集はTier 0の`movie_catalog`／`hobby_graph`、Tier 1のconfirmed external IDを持つカテゴリ専門source、
必要なIDがない場合だけ行うWikidata候補発見、Tier 2の次点sourceの順です。
Tier 2はドラマ=`jpsearch -> official_public／映画.com`、受賞歴=`mediaarts_db（収録範囲内） -> 賞公式／japan_academy_prize`、
音楽=`musicbrainz（確認済みMBID） -> jpsearch`、アニメ=`mediaarts_db -> jpsearch`、
小説=`ndl_bibliography -> jpsearch`、漫画=`mediaarts_db -> ndl_bibliography -> jpsearch`を既定とします。
前sourceが十分なvalidated resultを返したら停止し、`unavailable`、`ambiguous`、stale、明示coverage gapの場合だけ次sourceへ進みます。
同一providerへ複数カテゴリを要求できる場合は一つのbounded queryへ統合し、全件fan-out、無制限pagination、host rate limitの迂回を禁止します。

各runのreceiptは、少なくとも`plan_revision`、`attempts[{source, priority, reason, status, started_at, completed_at, item_count, error_code}]`、
`stop_reason`、`next_source`を持ちます。item／relationにはsource hit、source record ID、provenance URL、取得時刻、authority、
rights、`name_state`を保持し、未実行sourceを成功扱いにしません。categoryの終端状態は
`complete | partial | unavailable | ambiguous | rejected`を使い分け、取得不能と権利拒否、同定不能を一つの失敗へ丸めません。

positive receiptはsource・categoryごとのrefresh期限を持ち、結果なし、権利条件不適合、identity未解決はnegative receiptとしてTTLを
持たせます。再試行は429／5xx／一時的network errorだけに限定し、有限回、`Retry-After`、指数backoffを使います。semantic empty、
ambiguity、rights rejection、schema errorは再試行せず、次sourceへの計画判断またはterminal状態へ確定します。

source順序の昇格は、source・category単位の直近90日のterminal attemptが30件以上ある場合だけ許可し、
`validated hit率 × 平均完全性 ÷ (1 + p95 latency秒)`で同じauthority内だけを並べ替えます。
個人評価、単発の成功、LLMの判断でpriorityを変えず、identityまたは受賞歴のauthorityを下げるsourceを最終確認へ昇格しません。
同率時は固定source名順でtie-breakし、採用した統計snapshotとplan revisionをreceiptへ記録します。

### 作品サマリの事実性・公開境界

人物関連catalogの作品サマリは`WorkSummary`という意味契約で管理します。保存fieldは
`description_original`（source説明原文）、`description_language`（原文言語）、`description_ja`（source日本語説明または
原文説明だけの忠実な翻訳）、`description_translation_state`（`not_required | ready | failed | not_attempted`）です。
原文はsource factとして非破壊保存し、翻訳失敗時も捨てません。公開`summary_state`は`source_summary | translated_summary | unavailable`
だけを許可し、通常の日本語UIへ外国語原文をサマリとして表示しません。`source_status=ready | unavailable`と
`translation_status=not_required | ready | failed | not_attempted`は別々に監査します。

説明は初回の専門source responseに含まれるものを最優先で採用します。欠落した作品だけを正確なsource record ID、canonical URI、
ISBN、MBID、MADB／ジャパンサーチ／NDL IDでenrichmentし、名前だけの照会、fuzzy match、全件fan-outを禁止します。provider単位でbatch化し、
最大20作品／request、最大2つのsummary enrichment source／作品、固定pagination、response byte上限、timeout、host rate limitを
適用します。後段sourceはsummary fieldだけを補充でき、identity、名称、relationを上書きできません。

タイトル、credit、review、周辺本文、別作品、LLM知識からサマリを構成・補完・創作しません。作品名等の固有名詞は既存の
検証済み`display_name` tokenを使い、翻訳で新しい邦題を作りません。sourceに説明がない場合は`unavailable`とし、関係の有効性を
取り消しません。category resultには関係状態と独立した`summary_coverage={ready,unavailable,total}`を記録します。

各summary receiptはsource、source record ID、canonical／evidence URL、取得時刻、content hash、language、rightsを持ちます。
source／category TTLとnegative summary receiptで同一sourceの空結果を再取得しない一方、次のapplicable sourceは評価できます。映画の
既存概要、ドラマのジャパンサーチ／公式、アニメ・漫画のメディア芸術DB／ジャパンサーチ／NDL、小説のNDL／ジャパンサーチ、音楽の
MusicBrainz／ジャパンサーチを優先し、MusicBrainz relation metadataや受賞recordを作品サマリとして扱いません。

## Global Policy Bundleとmodule policy

> 状態: schema v1、起動時loader、hash／path／strict field検証、atomic in-memory reload、
> last-known-good保持、`/viewer/policy/status`を実装済みです。promotion、module側検査、監査、
> side effect enforcementは未実装です。policy fileを配置しただけで既存権限や挙動が
> 広がることはありません。

### ルールの分類と正本

| 種類 | 正本 | 実行時の役割 |
| --- | --- | --- |
| 利用者の意思、製品意味、module責務 | CORE現行正本 | 全policyが従う上位contract |
| 開発者／AI作業制約 | 各repositoryの最小`AGENTS.md`と関連rule／skill | 開発手順。runtime権限を付与しない |
| module横断の変更可能な運用方針 | `~/.rencrow/workspace/policies/` | active Global Policy Bundle |
| module固有のdomain rule | 各moduleの仕様、module policy、domain code | module内で検証・強制 |
| 絶対に越えられない上限 | 各moduleのbinary enforcement | runtime設定から緩和不能 |
| 判断と実行の証拠 | Policy Decision、audit、status、test | revisionと結果の追跡 |

全体ルールをWorkspaceへ集約する場合も、CORE製品仕様、各moduleのdomain仕様、binary hard limitを
Workspaceへ移動しません。Global Policy Bundleはそれらの範囲内で運用を狭める宣言です。

### Runtime directory contract

target layoutを次とします。

```text
~/.rencrow/workspace/policies/
├── manifest.yaml
├── global.yaml
├── capabilities.yaml
├── authorizations.yaml
├── data-handling.yaml
├── external-actions.yaml
└── deployment/
    ├── production.yaml
    └── development.yaml
```

- `manifest.yaml`は`schema_version`、`bundle_id`、`revision`、`created_at`、
  `minimum_core_contract`、各fileの相対pathとSHA-256、bundle全体のcontent hashを持ちます。
- pathはpolicy rootからの相対pathに限定し、`..`、symlink、hard link、絶対pathを拒否します。
- policy fileにsecret、credential、endpoint実値、個人情報、runtime DB、session、logを置きません。
- `deployment/*`はglobal上限を狭める差分だけを持ち、productionで許可されないcapabilityを
  development profileからproductionへ昇格させません。
- 未知field、未知schema version、hash不一致、重複policy ID、循環参照、上限拡大を拒否します。
- 読込順による暗黙上書きを許さず、各fieldの所有fileとmerge規則をschemaで一意にします。

schema v1の所有fieldは次のとおりです。

| file | field |
| --- | --- |
| `global.yaml` | `schema_version`, `policy_id`, `default_side_effect` |
| `capabilities.yaml` | `schema_version`, `policy_id`, `capabilities` |
| `authorizations.yaml` | `schema_version`, `policy_id`, `authorizations` |
| `data-handling.yaml` | `schema_version`, `policy_id`, `rules` |
| `external-actions.yaml` | `schema_version`, `policy_id`, `actions` |
| `deployment/*.yaml` | `schema_version`, `policy_id`, `profile`, `disabled_capabilities` |

v1は`default_side_effect: blocked`だけを受理します。`external-actions.yaml`のdecisionは
`blocked | explicit_authorization`に限定します。loaderは7 policy fileがmanifestに過不足なく
含まれること、各file hash、pathとhashをpath順に連結したbundle content hash、RFC3339時刻、
重複`policy_id`、未知field、symlink／検出可能なhard linkを検査します。

起動時statusは`active | missing | invalid`です。`missing`または`invalid`でも既存binary hard limitを
弱めず、invalidな内容を部分適用しません。現在はread-only status sliceであり、
`active`もside effect許可を意味しません。schema v1のstatusは安全側の`production` profileを
projectionし、profile切替とenforcement wiringは後続実装とします。

COREはactive bundleをimmutable snapshotとして保持します。reloadは全fileの検証完了後だけ
mutexで単一snapshotを交換し、同一requestが二つのrevisionを参照しない境界を提供します。
reload失敗時はactive snapshotを変更せず、`state=active`と`last_reload_state=missing|invalid`、
`active_revision_preserved=true`を同時にstatusへ出します。初回loadに失敗してactive snapshotが
ない場合だけ`state=missing|invalid`です。認証済みpromotionが未実装のため、HTTPからreloadを
開始するrouteは公開しません。

RenCrow_Workspace repositoryへ保存する場合は、このdirectoryのportable・non-secret fileだけを
明示allowlistへ追加します。runtimeからrepositoryへのsnapshotと、review済みrepository artifactを
runtimeへ反映するpromotionは別操作とし、backup処理からruntimeへ書き戻しません。

### 実効capabilityと優先順位

実効capabilityは次で決定します。

```text
effective_capability
  = binary_hard_limit
  ∩ global_workspace_policy
  ∩ module_policy
  ∩ deployment_config
  ∩ authenticated_request_scope
```

- Workspace、prompt、Agent、requestはbinary hard limitを解除できません。
- module policyとdeployment configはglobal policyを狭められますが、広げられません。
- capabilityを宣言しても、production wiring、Tool metadata、credential、runtime availabilityが
  不成立なら実行できません。
- 未分類のside effectは`blocked`です。少なくとも書込み、削除、外部送信、公開、課金、契約、
  Git remote操作、credential／network boundary変更、金融注文をside effectとして分類します。
- 複数のpolicyが一致した場合は最も制限の強い判断を採用し、denyをallowで上書きしません。
- Policy Bundleが未配置でも既存binary hard limitを弱めません。Policy Bundleを必須とする
  production capabilityは`disabled`または`unavailable`とし、暗黙の既定許可へfallbackしません。

### Module policyとbuild contract

各moduleは自分のdomain ruleを所有します。COREは共通envelope、global上限、module間contractを
所有しますが、TRADEの注文検査、LLMのruntime解決、Visionのmedia検証などを汎用Policy Engineへ
移しません。

module repositoryは必要に応じて次を持ちます。

- 現行仕様と実装仕様
- machine-readable module policyと安定したpolicy ID
- 純粋判定を行うdomain policy
- 外部I/O直前のenforcement gate
- allow／deny、境界値、unknown、dependency failureを含むcontract test
- buildへ埋め込むpolicy contract revisionまたはmanifest hash

Buildは`~/.rencrow/workspace`を入力にしません。repository内のschema、source、module policy、testだけで
再現可能にし、CIでCORE contract version、policy ID、上限非拡大、enforcement gate、拒否testを
検査します。文書やYAMLを`go:embed`等で同梱しただけでは実装済みとしません。

実行時はbinaryが持つcontract revision、module policy revision、active Global Policy Bundle revisionの
互換性を起動時に検証します。不一致時は対象side effect capabilityだけを安全側へ停止し、
通常Chatや安全なread-only機能まで偽の成功へ変換しません。状態はhealth／statusへ投影します。

### 変更、検証、promotion

Global Policy Bundleを通常のAgent、Coder、Workerがactive directoryへ直接上書きしません。
変更は次のlifecycleを通します。

```text
DRAFT
  -> STAGED
  -> VALIDATED
  -> PROMOTED
  -> ACTIVE
  -> SUPERSEDED

DRAFT | STAGED | VALIDATED
  -> REJECTED
```

1. 変更案をactive directory外へstagingする。
2. schema、hash、path、互換性、権限差分、必要testを検証する。
3. 現行revisionとの差分を`expansion | restriction | no_effect`へ分類する。
4. `expansion`はbinary hard limit、CORE正本、module policy schema、deployment capabilityの全条件を
   機械検証する。範囲内なら継続し、範囲外なら理由付きで`rejected`または`blocked`とする。
5. `restriction`の自動適用可否は専用capabilityで制御する。Kill Switch等の緊急停止は
   権限付与と分離し、即時かつ冪等に実行可能とする。
6. 検証済みbundleをatomicにpromotionし、同一request内でactive revisionを一つに固定する。
7. 読込後の互換性とstatus projectionを確認し、失敗時は直前のlast-known-good revisionを維持する。

validation失敗、policy範囲外、promotion失敗を成功扱いしません。部分適用、直接編集、mtimeだけによる
採用、Agent自身による権限拡大、検証後のpayload変更を禁止します。人の返答待ちへ遷移しません。

### Policy Decisionと監査

Global、module、binaryの判定形式が異なっても、監査用envelopeは少なくとも次を持ちます。

- `decision_id`、`trace_id`、`request_id`
- requester、authenticated scope、対象module、action、artifactまたはresource
- binary contract revision、global bundle revision、module policy revision、deployment revision
- matched policy ID、`allowed | blocked | unavailable | degraded`
- 理由、入力snapshot hash、authorization ID、実行結果、時刻

secret、credential、個人情報、注文認証情報をPolicy Decisionへ保存しません。同じ処理のdomain固有
decisionを共通envelopeへ無理に統合せず、相関IDとrevisionで追跡可能にします。

共通envelope v1は`internal/domain/policydecision`、append-only JSONL evidence storeは
`workspace/logs/policy_decisions.jsonl`を所有します。domain固有decisionの内容を置換せず、
そのID、相関ID、revision、最終outcomeだけを共通記録へ投影します。破損JSONLを読み飛ばして
正常に見せず、read APIは明示errorにします。

### 受け入れ条件

- Policy Bundleなし、破損、未知version、hash不一致でside effectが既定許可されない。
- global、module、deployment、requestのどの層からもbinary上限を拡大できない。
- module buildがhome directoryやruntime Workspaceなしで再現できる。
- 権限拡大はbinary hard limit、CORE正本、module policy、deployment capabilityの積集合を越えてpromotionできない。
- reload中のrequestは単一revisionだけを参照し、部分適用されない。
- invalidなreload後も直前のactive revisionを維持し、失敗をstatusとauditへ残す。
- module固有の最終副作用地点に拒否testがあり、文書だけの禁止に依存しない。
- health／statusからbinary、global、moduleのrevisionと互換性、停止中capabilityを確認できる。
- RenCrow_Workspace snapshotへsecret、runtime state、DB、logを取り込まない。

## 同期実行policy

RenCrow_CORE は実行前の人間待機や判断queueを持ちません。各requestを受けた時点で、capability、利用者scope、allowlist、sandbox、credential、対象、risk policyを同期評価し、許可できる操作は直ちに実行し、許可できない操作は理由付きで`blocked`にします。

- 外部公開・投稿・送信は、設定済みadapter、許可scope、送信先、冪等性条件を満たす場合だけ実行する。
- 請求、支払、契約、価格決定は、専用capability、上限、対象、監査条件が明示されていない限り`blocked`にする。
- production dataや重要ファイルの破壊的変更は、対象path、sandbox、rollback evidence、事後検証を満たさない限り`blocked`にする。
- credential、権限、network boundaryの変更は、明示policyに存在しない限り`blocked`にする。
- 高リスクTool/Browser actionは、allowlist、timeout、scope、事後検証を満たさない限り`blocked`にする。

判断記録はPolicy Decisionとしてscope、requester、対象artifact、policy、判断、理由、実行結果、`trace_id`を保持します。過去の待機型field、endpoint、DB columnは現行契約へ引き継ぎません。

### Capability applyの同期policy

Tool、Skill、MCPの追加・変更を反映する`capability apply`は、Agentが作成したcapabilityでも
同じpolicy積集合を通ります。COREはrequest bodyから認証主体やscopeの自己申告を受け取らず、
認証済みHTTP／Agent execution contextから確定します。そのscopeと`request_id`、idempotency key、
期待するkind／canonical name／source revision／source hash、current Snapshot revision／hashを使い、
source/list、production wiring、Worker policy、deployment availability、固定targetを一度の
同期判定で検証します。Agentの発話、Skill本文、MCPの自己申告、Workspaceの静的一覧はpermission、
認証、source観測の代用になりません。

判定は`execute | rejected | blocked`のいずれかで、その後の再起動処理に人の承認、grant、待機queue、
定期pollを挿入しません。

- `execute`は、期待するsourceとpolicyが成立したrequestだけに付与します。現行Stable Snapshotへ
  全期待capabilityがkind／canonical name／source revision／source hash一致で存在する場合は、
  receiptを`completed`へatomicに確定し、restartを行いません。
- `rejected`はrequest不正、stale Snapshot、idempotency payload conflict、policy拒否です。
  `CAPABILITY_INVALID_REQUEST`、`CAPABILITY_SNAPSHOT_MISMATCH`、`CAPABILITY_IDEMPOTENCY_CONFLICT`、
  `CAPABILITY_POLICY_REJECTED`を理由として返し、同じpayloadの無条件再送をしません。
- `blocked`はsource未配置、MCP接続／`tools/list`失敗、Skill catalog未検証、依存未ready、応答後
  supervisorへの引継ぎ不能などです。`CAPABILITY_SOURCE_MISSING`、`CAPABILITY_DEPENDENCY_BLOCKED`、
  `CAPABILITY_SCHEDULE_FAILED`を返し、別provider、別Tool、別PORTへfallbackしません。

accepted requestは`validated`から`restart_scheduled`、`stopping`、`starting`、`verifying`を経て
`completed`または`failed`になります。`restart_scheduled`へ遷移する前にCORE-owned Durable Storeの
receiptをatomicに保存し、監査eventをappend-onlyで記録します。supervisorは固定された
`task_id=rencrow-core`だけを扱い、任意unit、path、command、PORT、providerをrequestから受け取りません。
所有不明processを停止せず、ReservedPortの別Task競合は`PORT_OWNERSHIP_CONFLICT`、同一Taskの解放
期限超過は`PORT_RELEASE_TIMEOUT`、起動失敗は`TASK_START_FAILED`、readiness期限超過は
`CAPABILITY_READINESS_TIMEOUT`、期待Snapshot membership／hash不一致は
`CAPABILITY_SNAPSHOT_MISMATCH`として`failed`を確定します。

再起動後の検証は、停止したCORE process自身ではなく、CORE distributionのnative Go supervisorと
新instanceの観測で行います。新instance identity、同一ReservedPort listener、`/health/live`、
`/health/ready`、期待capability、receiptへ固定した最終Snapshot revision／hashの全てを確認できた
場合だけ`completed`です。詳細なAPI、CLI、HTTP mappingは[Public API仕様のCapability Applyとstatus](06_Public_API仕様.md#capability-applyとstatus)、
receiptの物理pathとManifestは[設定リファレンス](05_設定リファレンス.md#capability-applyとreceipt)、
event名と相関fieldは[ログ仕様](10_ログ仕様.md#capability-applyの観測)に従います。

## No-Human-Gate

RenCrowは人の判断待ちを作らない。人の返答で解除するstatus、grant、reference、queue、定期pollを
Agent、workflow、API、DBへ持ちません。利用者の発話は新しいrequest、目的、制約、事実として処理し、
過去artifactを解錠する判子として扱いません。

各requestは同一処理内で、確定済みCORE正本、binary hard limit、global／module policy、deployment
config、認証済みrequest scopeを評価し、`execute | rejected | blocked`を確定します。実行可能な操作は
直ちに実行し、policy不適合の案は`rejected`、越えられない安全境界または利用不能dependencyは
`blocked`とします。Codexのユーザー権限境界をRenCrow runtimeへ移植しません。

## Reject-Driven Revision

`rejected`は終了状態や人への差し戻しqueueではなく、再考を開始する機械的feedbackです。

1. rejectされたartifactを適用せず、`rejection_reason`、reason code、違反constraint、evidenceを固定する。
2. 失敗した前提と観測を特定し、目的を維持できる別の解き方を考察する。
3. 入力、証拠、分解、route、Tool、algorithm、data model、architecture、必要なら当初の思想のうち、
   少なくとも一つを実質的に変更する。
4. `parent_attempt_id`、新しい`revision_id`、`changed_dimensions`、変更理由を持つ新artifactを作る。
5. 新artifactを最初のvalidatorから再検証し、旧artifactのpass結果を流用しない。

同じ案の言い換え、同じpayloadの無条件再送、安全制約・test・validatorの弱体化、別名fieldによる
人待ちgateの再導入を禁止します。同じreasonで繰り返しrejectされた場合は、domain policyの有限attempt
上限内で戦略または思想を変更します。適合案が存在しない、または越えられない境界に達した場合は、
根拠と試したrevisionを残して`blocked`を確定し、無限再試行しません。

## Durable Store変更の機械gate

Durable Storeの`S1`／`S2`も人の判断待ちを持ちません。impact classごとのschema、path、privacy、
retention、capacity、migration、backup、restore、三OS、dependency failure条件を機械検証し、
`validated`または理由付き`rejected`を確定します。一度activeになったstoreの通常read／writeも、
確定済みConfig、schema、module policy、利用者scopeにより同期評価します。

Chatからの「保存できるようにして」「DBを構築して」という認証済みrequestは、変更目的とscopeの入力に
できますが、Storage Proposal、Manifest、validator evidenceの代用にはなりません。設計・比較だけの発話を
production変更の権限として扱わず、`requested_outcome=implement`が確定したrequestだけが、validated後の
実装・provisioningへ進めます。追加質問を待つ状態は作らず、必須事実を決定できないrequestは不足fieldを
reason codeへ含めて`blocked`で閉じます。

- runtime request、Agent、LLM、Toolが未登録のDB file、table、external databaseを自動作成してはならない。
- Executorは`validated`になったStorage ProposalとManifestの範囲だけを実装し、`S0`を装って新しい物理storeやdata classを追加してはならない。
- 一般CODE routeのplan、patch、commandだけでDurable Store validatorを迂回してはならない。
- 同一requirementの再送またはresume時は、既存proposal、migration、store、backupを照合してからside effectを行い、名前を変えた重複storeを作成してはならない。
- `S1`／`S2`は必須validator evidenceがなければ`validated`へ遷移できない。
- schema migrationはowner moduleのversioned migrationだけを使い、startup時の暗黙破壊、未知versionの読飛ばし、失敗後の空DB再作成を禁止する。
- migration前に対象、revision、backup／rollback条件、空き容量を検査し、失敗時は旧storeを保持して`unavailable`または起動失敗にする。
- configured durable rootが未mount、read-only、容量不足、permission不正、またはbackup rootと同一媒体の場合、repository、runtime home、system tempへfallbackしない。
- sensitivity、privacy、retention、削除条件を変更する場合、同じDB file内の変更でも`S1`として再審査する。
- DBやartifactの削除、schema downgrade、store統合は追加時のdecisionを流用せず、参照消滅、archive、restore、rollback期限を別途検証する。
- Manifest、runtime Config、実path、backup対象、health projectionの不一致をdegradedな成功として隠さず、deployment preflightを失敗させる。

AIはStorage Proposalのdata意味や代替案整理、reject後の再考を補助できますが、impact classの
引下げ、migration実行、production credential取得、store provisioningを行いません。決定規則と
Manifest検証は通常コードで実装します。

## Agent と Tool の境界

Advisor と Coder は提案者であり、実行責任者ではありません。Tool は人格や判断主体ではなく、allowlist、sandbox、timeout、監査 policy の下で呼び出される capability です。Shiro/Worker が side effect と実行policy境界の責任を持ちます。

ローカルModel、外部LLM API、Codex等のAgent RuntimeはAgentの推論実体であり、
通常応答に使用しただけではCORE Toolの実行権限を得ません。Kuro／Heavyは利用者決定による
明示的な例外で、CORE workspaceをworking directoryにしたCodex Agent Runtimeを
`danger-full-access`で実行します。この経路はGatewayでKuro／Heavy binding、target、
sandboxを固定し、request IDと実行結果を監査します。その他のAgent Runtimeのside effectは
COREのTool policyを通る別requestにします。

ローカルtargetから外部providerへの切替は単なる可用性fallbackではありません。
入力の外部送信、課金、保持policy、再現性が変わるため、COREが許可していない
providerへRenCrow_LLM、CMD、PORTALが無言fallbackしてはなりません。

## Knowledge と Memory

- external search は発見であり、確定 Knowledge の証拠ではない。
- source、取得時刻、要約、採用理由を provenance として保持する。
- Advisor 出力、候補資料、Revenue draft を自動 promotion しない。
- role visibility と context budget を適用し、不要な個人情報を Recall しない。
- 誤りを訂正できるよう、原資料と派生要約を区別する。
- L1 Raw会話からProfileExtractorが作るUserMemoryは、根拠event ID付きの`candidate`に限定する。自動処理だけで`confirmed`または`pinned`へ昇格せず、候補状態の情報をAgent promptへ注入しない。
- sensitiveと判定した候補、利用者scopeを確定できない候補、根拠Rawを参照できない候補は自動昇格せず、隔離または`failed`として観測可能にする。
- ProfileExtractor待ちを理由に利用者応答を遅延させない。未処理Rawを保持したまま、全LLMがIdleの期間へ延期する。
- X Bookmarkと外部SNS投稿は`source_confidence=low`の候補です。利用者がBookmarkした事実は内容の真偽確認ではなく、収集完了をreview済みKnowledgeやpromotion済みKnowledgeとして扱いません。

## Secret と個人データ

- secret を source、docs、log、trace、artifact に保存しない。
- Ubuntuのproduction基準ではlive dataを`/srv/rencrow/db`、別媒体のbackupを`/srv/rencrow/backup`へ分離する。Windows／macOSは設定済み絶対pathで同じ論理分離を維持する。
- live storeとbackup storeを同一filesystem、同一mount、同一障害領域に置かない。backup storeをlive write先や暗黙fallback先にしない。
- productionの必須mountがない場合、repository、`~/.rencrow`、OS一時directoryへ保存先を切り替えず、起動失敗または`unavailable`として観測可能にする。
- runtime DBの物理pathは`storage.databases`へ明示し、backup運用時は全DBを`backup.core_source`配下へ置く。
- session、運用記憶、cold exportの物理pathは`storage.memory`へ明示し、backup運用時は全て`backup.core_source`配下へ置く。
- backup保存先、世代数、Redis/Qdrant export契約は`backup`を正本とし、runner内へ環境固有値をハードコードしない。
- Redis/Qdrantのlive volumeを直接archiveせず、backendの整合性あるsnapshot機能を使う。必須exportが欠けた実行を成功扱いしない。
- backupの圧縮は可逆形式だけを許可する。圧縮は暗号化ではないため、個人記憶を別host、removable media、cloudへ複製する前に暗号化し、復号鍵はbackup媒体と分離する。
- backup媒体はbackup windowだけmountし、完了後にunmountする。媒体不在、mount失敗、容量不足、検証失敗を成功扱いしない。
- 世代数だけで保護済みと判断せず、checksum、展開、SQLite整合性、外部記憶exportを検証できた世代だけを復旧候補にする。
- local config、DB、session、音声、画像、browser profile は repository の外で管理する。
- log には必要最小限の識別情報だけを残し、公開前に redaction する。
- archive branch が公開であることを前提に、secret や私的 runtime data は archive にも置かない。

### Browser sessionの一回限り移植

画面のないhostへXのログイン状態を移す場合は、利用者の明示操作でX用Cookieだけを暗号化して
移植します。普段使用中の個人browser profile全体を複製せず、移植先ではrepository外の専用
persistent profileへ保存します。移植元browserのCookie、profile、ログイン状態を変更しません。

転送bundleはrandomな共通鍵によるAES-256-GCMで暗号化し、その鍵を移植先で生成した
RSA-OAEP公開鍵で包みます。秘密鍵は移植先だけに`0600`で保存し、平文Cookie、`auth_token`、
`ct0`、復号鍵を画面、clipboard、stdout、log、report、Gitへ出しません。import時は暗号形式、
X domain、必須Cookie、Bookmark URLへの到達を検証します。確認後は転送bundle、秘密鍵、
一時拡張を削除します。

認証切れや検証失敗は明示的なerrorとし、X API、別credential、個人profileの直接利用へ
暗黙fallbackしません。再認証または再移植は利用者の明示操作を必要とします。

## 失敗と degraded state

provider、LLM、STT、TTS、browser、storage の失敗を空の成功へ変換しません。`unavailable`、`pending`、`degraded`、`error` を区別し、再試行、fallback、利用者への表示を契約として扱います。
