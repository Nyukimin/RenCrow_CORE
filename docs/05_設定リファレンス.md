# 設定リファレンス

## 読込方法

`rencrow` は `RENCROW_CONFIG` が設定されていればそのパスを、なければ作業ディレクトリの `./config.yaml` を読み込みます。公開テンプレートは `config/config.yaml.example` です。

```bash
cp config/config.yaml.example config.yaml
RENCROW_CONFIG=./config.yaml ./build/rencrow
```

YAML 内の `${NAME}` は同名の環境変数で展開されます。secret は YAML に直書きせず、環境変数を使用してください。

`workspace_dir/control/`を使用する場合、`agents.yaml`、`routing.yaml`、
`handoff.yaml`、`tools.yaml`の4ファイルを一括で読み込みます。directoryが存在する場合は4ファイル全てが必要です。schema version、CORE route owner、handoff owner、Tool metadata source、自動fallback禁止を検証し、不整合時は起動しません。

このcontrol setはportableな宣言であり、endpoint、secret、Toolのenabled状態、引数schema、permissionを設定しません。それらはこのConfigとCORE runtime metadataを正本とします。

外部向け`Chat`／`IdleChat`画面は独立した`RenCrow_PORTAL`が提供します。COREはPORTAL URLのredirect設定を持たず、`/viewer`ではDebug Viewerだけを提供します。

## 主要セクション

| section | 用途 |
| --- | --- |
| `server` | bind host、port、TLS |
| `storage`, `backup` | DB物理配置の正本、backup保存先と世代数 |
| `llm_gateway` | production inferenceのRenCrow_LLM Gateway接続。物理LLM情報は置かない |
| `mio` | Mio の会話生成 sampling と input_audio prompt |
| `runtime_topology` | module と role の配置・参照 |
| `session`, `conversation` | session、Recall、永続化接続 |
| `worker`, `coder1`-`coder4` | 実行 policy と Coder slot |
| `line`, `telegram`, `discord`, `slack` | channel adapter |
| `tts`, `stt`, `audio_router`, `vtuber` | 音声と表示連携。STT/TTSは各Gatewayの接続だけを置く |
| `vision` | RenCrow_Vision接続、timeout、CORE受付上限。Wildや物理modelの設定は置かない |
| `image` | RenCrow_Image接続とtimeout。ForgeNeo、model、生成parameterは置かない |
| `advisor`, `knowledge_relation` | Advisor 記録と Knowledge Relation |
| `heartbeat`, `workstream`, `revenue`, `economic_objective` | 継続作業と Economic workflow |
| `security`, `sandbox`, `tool_harness` | 実行制限、監査、promotion gate |
| `web_gather`, `webwright_fetch`, `browser_actor` | 外部情報取得と browser sidecar |
| `codex` | Codex CLI Tool／Advisor。Kuroの通常LLMとは独立 |
| `idle_chat.news_sources` | `IdleChatTopicSeed`と`DailyNewsBrief`の共通ニュース収集元（互換性のため設定名は維持） |
| `viewer_log`, `log` | Viewer operation log と process log |
| `games` | RenCrow_GAMES 連携。`games.auto_play` でペルソナの自発プレイ（enabled / personas / max_sessions_per_day。ペースは LLM が next_check_minutes で自己決定） |

標準Go配布では、CORE Configは各Go Gatewayのbase URLとCORE側timeout／受付制限だけを
持ちます。Python／Node.js runtimeを自動導入する設定は持ちません。Browser Actor、Webwright、
`rencrow-data`はoptionalであり、明示的に有効化したhostだけが必要なruntimeを用意します。
映画カタログCrawlerは`RENCROW_MOVIE_CATALOG_CRAWLER_URL`でoptional Go sidecarへ接続し、
未設定時はbackfillをskipし、手動fetchには`MOVIE_CATALOG_CRAWLER_UNAVAILABLE`を返します。

`games.auto_play.personas`を省略または空にした場合の既定ロースターは
`mio`、`shiro`、`kuro`、`midori`の4人です。明示した場合は、その一覧だけを
自発プレイ候補として使います。`enabled`の既定値は`false`、
`max_sessions_per_day`が0以下の場合の既定値は8です。

Coderは4体セットで、identityは`coder1.name=aka`、`coder2.name=ao`、
`coder3.name=kin`、`coder4.name=gin`に固定します。欠落時はこの値を補完し、
異なる明示値はslotとidentityの不整合として起動時に検出します。COREには各slotの
有効状態、persona、tone、LightMemoryだけを置き、実行targetはRenCrow_LLMで管理します。

## 最小の考え方

`server.port` は 1-65535、`session.storage_dir` は必須です。LLMは`llm_gateway`へRenCrow_LLMの接続先とtimeoutを設定します。任意機能は `enabled: true` にしたときだけ、その機能固有の path や endpoint が必須になります。

endpoint は `http://<host>:<port>` のように環境ごとに指定してください。repository 内の例や test にある host、port、path を production 値としてそのまま利用しないでください。

`llm_gateway`にはRenCrow LLM Gatewayの接続情報だけを置きます。AgentからExecution Roleへの
割当はCOREのroute contract、Role profile revisionとRoleからRuntimeへの割当、
RuntimeからBackend／Modelへの割当はRenCrow_LLMのdeployment設定です。CORE Configや
client Configへ物理Model、provider、Backend URL、Runtime、port、execution aliasの
選択設定を複製しません。

CORE Configの`image`はRenCrow_Image Gatewayの接続情報だけを持ちます。
workflow、model、LoRA、生成parameterはRenCrow_Imageが所有します。
通常の画像生成経路は`CORE -> RenCrow_Image -> ForgeNeo / Z-Image`です。
Mio、Shiro、Midori、Kuroが文章生成工程の一部として利用するCodexExe経由の
ImageGenも、COREの画像生成設定とは分離します。

```yaml
image:
  enabled: true
  base_url: "http://127.0.0.1:8780"
  timeout_ms: 600000
```

`image.enabled=true`では`base_url`と正の`timeout_ms`を必須とします。
COREは`POST /v1/images/generations`と`GET /v1/images/{image_id}.png`を使い、
RenCrow_Imageの結果をViewerへ中継します。

音声認識では、CORE ConfigにRenCrow_STT Gatewayのbase URLとCORE側の制御だけを置きます。
認識engine、model、language、外部target URL、WebSocket stream URLはRenCrow_STT側が
所有します。ViewerはCORE同一originの`/stt`を使うため、外部stream URLを設定しません。

```yaml
stt:
  enabled: true
  gateway_base_url: "http://127.0.0.1:8766"
  timeout_ms: 120000
  busy_policy: "queue_latest"
  endpoint_path: "/stt"
  debug:
    save_audio: false
    save_transcript: true
```

`stt.enabled=true`では`gateway_base_url`を絶対HTTP URL、`timeout_ms`を正数にします。
COREはRenCrow_STTの`POST /v1/audio/transcriptions`だけを呼びます。

画像・動画認識では、CORE ConfigにRenCrow_Visionの公開endpointとCORE側の受付上限だけを
置きます。Wildのendpoint、model、provider、frame sampling方式はRenCrow_Visionが所有し、
CORE Configへ複製しません。

```yaml
vision:
  enabled: true
  base_url: "http://127.0.0.1:8770"
  timeout_ms: 120000
  max_image_bytes: 20971520
  max_video_bytes: 104857600
  max_video_duration_ms: 60000
  max_frames: 8
```

`vision.enabled=true`では`base_url`と正の`timeout_ms`を必須とします。COREは起動時または
status更新時に`GET /health`を確認し、`ok=true`、`status=ready`、
`ready.model_loaded=true`を満たす場合だけreadyと判定します。HTTP 200だけでreadyにしません。
認識backend、model、media前処理の設定はRenCrow_Visionが所有します。

## LINE Webhookと通知先

LINEのcredentialはYAMLへ直書きせず、環境変数参照にします。現行fieldは`line.channel_secret`と`line.access_token`です。Access Tokenの環境変数名はdeploymentが選べますが、Configに記載した参照名とEnvironmentFileのkeyを一致させます。

```yaml
line:
  channel_secret: "${LINE_CHANNEL_SECRET}"
  access_token: "${LINE_CHANNEL_TOKEN}"

heartbeat:
  enabled: true
  interval: 30
  channel: "line"
  chat_id: "${RENCROW_HEARTBEAT_CHAT_ID}"
  x_bookmarks:
    enabled: false
    interval_minutes: 360
    timeout_minutes: 90
    run_on_start: true
    command: "rencrow-x-bookmarks"
    output_root: "/home/<user>/.local/share/rencrow/x_bookmarks/heartbeat_exports"
    max_scrolls: 100
```

`heartbeat.chat_id`が具体値なら通知とHeartbeatはその値を使用します。LINEでは33文字の`U...`を個人、`C...`をgroup、`R...`をroomとして検証します。空値または未展開の`${...}`をMessaging APIへ送ってはいけません。

LINEの通知先が空または未展開で、`heartbeat.channel`が空または`line`の場合、COREは`workspace_dir/state/line_notification_target`をfallbackとして読みます。このfileは署名検証とchannel policyを通過した最初の個人DMから作成し、modeは`0600`です。本文が`通知先登録`のDMは登録専用として通常CHATとLINE replyを開始しません。後続DM、group、roomでは自動上書きしません。明示的な`heartbeat.chat_id`は常にこのfallbackより優先します。

設定確認と送信前確認には次を使います。出力されるtargetは先頭4文字と末尾4文字以外をmaskします。

```bash
rencrow channels list --json
rencrow channels probe --json
rencrow channels send --message '【RenCrow】通知確認' --dry-run --json
```

`channels probe`と`--dry-run`は実送信しません。実送信は`--dry-run`を外した1回のcommandだけで行い、自動retryしません。

`heartbeat.x_bookmarks`はX Bookmarkのoptional browser収集です。`enabled=true`にする場合は
Heartbeat本体も有効にし、`command`が専用ログインprofileを読める
`rencrow-x-bookmarks`を指すこと、`output_root`がrepository外の絶対pathであることを必須とします。
`interval_minutes`は60〜10080分、`timeout_minutes`は1〜180分、`max_scrolls`は0〜1000です。
`run_on_start`は未指定ならtrueで、falseでは最初の収集をinterval経過後まで延期します。
profile、Cookie、token、CDP URLはCOREの設定やlogへ記録しません。

## DB物理配置とbackup

DBファイルの物理保存先は`storage.databases`を正本とします。ConversationのL1とarchiveも
`conversation_l1`、`conversation_archive`だけで指定します。

```yaml
storage:
  memory:
    session_dir: "/home/<user>/.rencrow/sessions"
    operation_memory_dir: "/home/<user>/.rencrow/memory"
    cold_export_dir: "/home/<user>/.rencrow/exports/parquet"
  databases:
    conversation_l1: "/home/<user>/.rencrow/l1_memory.db"
    conversation_archive: "/home/<user>/.rencrow/memory_archive.db"
    tool_registry: "" # SQLite ToolRegistryを使う場合だけ設定
    glossary: "/home/<user>/.rencrow/glossary.db"
    movie_catalog: "/home/<user>/.rencrow/data/movie_catalog/eiga_catalog.sqlite"
    hobby_graph: "/home/<user>/.rencrow/data/hobby_graph/hobby_graph.sqlite"
    investment: "/home/<user>/.rencrow/data/investment/rencrow.db"
    advisor: "/home/<user>/.rencrow/workspace/logs/advisor.db"
    sandbox: "/home/<user>/.rencrow/workspace/logs/sandbox.db"
    dci: "/home/<user>/.rencrow/workspace/dci.db"
    skill_governance: "/home/<user>/.rencrow/workspace/logs/skill_governance.db"
    workstream: "/home/<user>/.rencrow/workspace/logs/workstream.db"
    revenue: "/home/<user>/.rencrow/workspace/logs/revenue.db"
    persona_architecture: "/home/<user>/.rencrow/workspace/logs/persona.db"
    browser_trace_to_api: "/home/<user>/.rencrow/workspace/browser_trace_to_api.db"
    complexity_hotspot: "/home/<user>/.rencrow/workspace/logs/complexity_hotspot.db"
    super_agent_harness: "/home/<user>/.rencrow/workspace/logs/superagent_harness.db"
    ai_workflow: "/home/<user>/.rencrow/workspace/logs/ai_workflow.db"
    knowledge_memory: "/home/<user>/.rencrow/workspace/logs/knowledge_memory.db"
```

映画、趣味、投資Viewerと映画catalog backfillはこの設定を直接使用し、表示先と書込先を同じDBへ揃えます。


`storage.memory`はsession JSON、運用記憶、Parquet cold exportの物理保存先です。Parquet jobも`storage.memory.cold_export_dir`を使用します。

backup保存先、世代数、外部記憶export契約は`backup`へ記載し、`scripts/rencrow-storage-backup`が`rencrow config backup-values`経由で読み込みます。backupを設定する場合は全pathを絶対pathで記載し、`storage.databases`、`storage.memory`を`backup.core_source`配下に置きます。Config上の永続情報が対象外にある場合はvalidation errorになります。

```yaml
backup:
  core_source: "/home/<user>/.rencrow"
  core_snapshot_root: "/srv/rencrow/backup-local/RenCrow/core-snapshots"
  knowledge_source: "/srv/rencrow/knowledge/RenCrowKnowledge"
  knowledge_mirror: "/srv/rencrow/backup-moca/RenCrow/knowledge"
  knowledge_versions: "/srv/rencrow/backup-moca/RenCrow/knowledge-versions"
  recent_keep: 28
  daily_keep: 14
  weekly_keep: 8
  monthly_keep: 12
  memory:
    require_exports: true
    redis:
      enabled: true
      container: "rencrow-redis"
    qdrant:
      enabled: true
      base_url: "http://127.0.0.1:6333"
```

`redis.container`はRedisのDocker container名、`qdrant.base_url`はREST snapshot APIです。Docker volumeのhost pathは設定しません。`require_exports: true`では両backendが利用できない限りbackupを完了させません。

snapshotはCORE停止中に次の順で作成します。

1. Redisへ`SAVE`を実行し、container内の`redis-check-rdb`に通ったRDBを取得する。
2. Qdrant full snapshot APIでsnapshotを作成して取得する。
3. `core_source`と両exportを`tar.gz`へ可逆圧縮する。
4. COREを再開する。
5. `rencrow-storage-restore-check`でSHA-256、gzip、危険なarchive path、L1/L2 SQLite、Redis、Qdrantを検査する。
6. 検査済みsnapshotだけを`recent`へ確定し、03時台の実行を日次・週次・月次へ昇格する。
7. Knowledgeをmirrorし、上書き前の差分を`knowledge_versions`へ保存する。

`.env`、秘密鍵、binary、log、lock、`tmp`はCORE snapshotから除外します。映画等の永続DBは`tmp`ではなく`core_source/data`配下へ置いてください。圧縮archive自体は秘密情報を暗号化しないため、snapshot rootは専用mountと所有者限定permissionで保護します。

```bash
make test-storage-backup
make install-storage-backup
make storage-backup-check
make enable-storage-backup
make storage-backup-run-once

# 任意の保存済み世代をlive領域へ書き戻さず検査する
make storage-restore-check SNAPSHOT_DIR=/path/to/core-snapshots/recent/YYYYMMDD-HHMMSS
```

timerはJST 03:30、09:30、15:30、21:30相当の1日4回です。`RandomizedDelaySec=15m`により各開始時刻は最大15分遅延します。手動復旧では、まず上記checkerを通し、別directoryへ展開して内容を確認してからCORE停止中に書き戻します。checker自身はlive dataを書き換えません。Redis RDBとQdrant snapshotのbackend投入は、交換先を用意してから各backendの公式restore手順で行います。

`mio.generation` は Mio の通常会話と input_audio直結経路で共有する生成設定です。`stream`、`max_tokens`、`temperature`、`top_p`、`top_k`、`min_p`、`seed` を指定できます。`Chat`契約では`think=false`と`chat_template_kwargs.enable_thinking=false`を送信し、`true`は設定validation errorになります。`ChatWorker`はreasoning effortを`low`へ固定し、`Worker`はRenCrow_LLM側の設定を使います。`stream: true`ではGatewayのstreaming responseを使います。WAVは`input_audio` partとして送り、`mio.input_audio.prompt`をtext partとして同じuser messageに付与します。

`Wild`のNoThinkとstreamingは個別のlive config値ではなく、COREのrole policyとWild Agentで固定します。Gatewayへは`think=false`と`chat_template_kwargs.enable_thinking=false`を送り、Wild Agentがtoken callbackを必ず設定してstreaming requestを行います。WILD routeでは受信tokenを逐次eventへ転送します。productionのMidori AgentはRenCrow_LLM GatewayのWild roleへ割り当て、描画・文章作成などの創作依頼にroleのcontext budgetを使用します。

### RenCrow_LLM Gateway

productionでは`llm_gateway.enabled: true`にし、COREからRenCrow_LLMの単一URLへ接続します。
COREはAgentとExecution Roleを決め、Gatewayへ論理execution aliasを送ります。論理aliasは
`mio`がMio／Chat、`shiro`がShiro／ChatWorker、`worker`がShiro／Worker、
`midori`がMidori／Wild、`kuro`がKuro／Heavyを表します。alias名がAgent名と同じでも、
Agentからtargetへ直結する意味ではありません。物理Model名、Backend URL、起動port、
Codex command、RenCrow LLM RuntimeはRenCrow_LLM側で管理します。Gateway障害時にCOREから
物理targetへfallbackしません。

Kuroの通常会話はCOREでHeavy Roleへ割り当てます。Heavyのcurrent targetを
Codex subscription runtimeへ接続する設定はRenCrow_LLMの`execution_aliases.kuro`、
`roles`、`bindings` schemaで行います。KuroのPersona、Memory、会話SessionはCOREが所有し、
Codex側threadを正本にしません。通常`Kuro -> Heavy`経路は`danger-full-access`を正式契約とし、
CORE workspaceをworking directoryにしたCodex Execを使います。RenCrow_LLMはKuro／Heavyの
Role profileとtarget sandboxの両方へ`danger-full-access`を要求します。これは
COREの`codex.enabled`による限定的な`codex.run` Tool／Advisorとは独立した経路です。

外部LLM APIへの入力送信は、接続credentialや物理endpointをRenCrow_LLMが所有していても、
COREの利用者scope、privacy、実行policyを越えて許可しません。現在のGateway契約に
明示的な外部送信許可がない経路では、ローカルtargetから外部APIへ自動fallbackしません。

```yaml
llm_gateway:
  enabled: true
  base_url: "http://127.0.0.1:8090"
  api_key_env: ""
  timeout_sec: 600
```

### IdleChat episode準備とTTS先読み

IdleChatは完成済み台本を再生し、朗読時だけTTSを先読みします。採用するConfig契約は次です。
現在の実装状況は`docs/08_実装状況・ロードマップ.md`を正とします。

```yaml
idle_chat:
  episode_preparation:
    enabled: true
    generator: "codex_exe"
    ready_target: 3
    no_ready_behavior: "preparing"
    max_suffix_regenerations: 3
    codex_exe:
      sandbox: "read-only"
      ephemeral: true
  tts_prefetch:
    initial_utterances: 2
    lookahead_utterances: 3
    low_watermark_seconds: 15
    target_buffer_seconds: 30
```

`generator`は`codex_exe`だけを受理します。episode producerはCORE正本のMio／Shiro character
context、採用topic、source context、直近topic、禁止事項、構造化出力schemaを同じCodexExe
requestへ渡します。CodexExe側のprompt file、thread、workspaceをキャラクター正本にしません。
`sandbox`は`read-only`、`ephemeral`は`true`を必須とし、IdleChat台本生成からfile write、command、
外部送信、追加Toolを許可する設定は受理しません。Kuro／Heavy用`danger-full-access` profileや
汎用`codex.run`設定を流用しません。

`ready_target`は有効期限内の完成台本をbackgroundで何件まで維持するかを表し、既定値は3です。
0にはできません。`no_ready_behavior`は`preparing`だけを受理し、episode在庫がないときに
PORTALの再生request内でLLM会話生成へfallbackする設定は設けません。

`ready_target`の集計対象は制作状態が`ready`のepisodeだけです。検証NGまたは意味検査が不確実な
episodeは削除せず`needs_repair`へ保持しますが、在庫数には含めません。COREは同episodeの修復や
破棄判断を待たず、不足数を別`episode_id`としてbackgroundで追加生成します。追加生成cycleは
有限件で終了し、連続失敗時は失敗phaseと試行数を公開して次のIdle機会へ持ち越します。

`max_suffix_regenerations`は最初のNG turn以降をCodexExeで作り直す最大回数で、既定値は3です。
1以上を必須とし、上限へ達したepisodeは`failed`にします。再試行のたびに最初のNGより前の
合格済みprefixと`message_id`を保持し、NG turn以降だけを新しい`message_id`で再生成します。

`initial_utterances`は再生開始前に音声化する発話数、`lookahead_utterances`は再生中に先読みする
最大発話数です。既定値はそれぞれ2、3です。残り音声が`low_watermark_seconds`未満になる前に
先読みを開始し、`target_buffer_seconds`まで補充します。既定値は15秒、30秒で、
`target_buffer_seconds >= low_watermark_seconds > 0`を必須にします。発話数と再生秒数の両方を
満たせない短文／長文では再生秒数を優先します。これらはCORE側のqueue制御であり、物理TTSの
model、reference音声、推論parameter、GPU設定を追加しません。

episode操作CLIは`RenCrow_Tools`のnative Go command `rencrow-idlechat`へ置きます。

```text
rencrow-idlechat prepare  --core-url <url> [--count <n>]
rencrow-idlechat status   --core-url <url>
rencrow-idlechat validate --core-url <url> --episode-id <id>
rencrow-idlechat expire   --core-url <url> --episode-id <id>
```

CLIはCOREのepisode operationを呼び、stdoutへmachine-readableな結果、stderrへ運用logを出します。
COREのproduction DBやsession保存先を直接開くoption、LLM／TTS Gatewayや物理backendを指定する
optionは設けません。`status`と`validate`は最初のNG turn、NG理由、suffix再生成回数、固定prefix長、
`needs_repair`件数、補充生成状態を返します。storyではreader、listener、改変軸、genre、面白さの
方向、物語整合性errorも返します。PORTALのIdleChatは読み取り専用を維持し、これらの制作・破棄操作を
中継しません。

### 日次ニュース収集とIdleChatTopicSeed

COREはニュースの共通入力をJSTの毎日04:00に強制更新します。CORE起動時は当日cacheがなければ初期収集し、同日cacheがあれば再利用します。04:00の定期更新は同日cacheの有無にかかわらず実行します。この入力から`IdleChatTopicSeed`とユーザー向け`DailyNewsBrief`を別々に作ります。設定キーは互換性のため`idle_chat.news_sources`を維持しますが、ユーザー向けニュースをIdleChat画面の所有物にはしません。どちらも一般ニュースDBや利用者別PUSHの正本ではありません。

1ジャンル／2ジャンル用のword poolは設定で無制限に増やさず、固定コア48語と当日最新語最大32語の合計80語を上限とします。当日最新語は当日`NewsAnalysisArtifact`から反映された`source_read_status=ready`の記事にある`term_notes`から、statusが`contextual`または`confirmed`の用語だけを正規化・重複排除して作ります。`NewsCollectionArtifact`だけでは最新語を作りません。固定コアと重複する語、空語、URL、24文字を超える語は除外します。RSS／Atom由来を先に採用し、`source_type=reddit|x`は合計8語までです。cacheの日付が当日でない場合は最新語を使いません。最新語抽出のための追加HTTP取得や追加LLM requestは行いません。

利用toolと処理境界は次の通りです。

| tool／方式 | 用途 |
| --- | --- |
| Go `time.Timer` | JST 04:00の次回実行時刻を計算し、CORE停止contextで終了する |
| Go `net/http` | 10秒timeoutとRenCrow User-AgentでHTTP取得する |
| Go `encoding/xml` | RSS 2.0とAtomのtitle、link、description／summaryを解析する |
| Go `encoding/json` | Wikipedia MediaWiki Random APIとX APIの応答を解析する |
| Wikipedia Random API | Newsとは別の外部刺激シードを最大10件取得する |
| Reddit public Atom | communityの話題候補を取得する |
| X Recent Search API | 明示的に有効化した場合だけSNS話題候補を取得する |
| `rencrow-news collect` | feedと特定URLの元記事本文を取得し、immutableな`NewsCollectionArtifact`を出力する。LLMを呼ばない |
| `web_gather.fetch` | 考察phaseで、不明語検索により選んだ確認先URLの本文を直接取得・抽出する。元記事は再取得しない |
| `web_search` | 元記事本文だけでは意味を説明できない用語の確認先URL発見に限って使う。記事内容の代替取得には使わない |
| Worker LLM | 取得済み原文の日本語訳を作り、用語補足を確定した後にサマリとShiroの見解を日本語で作成する。HTTP取得や検索自体には使用しない。ChatWorkerはチャット画面専用 |

`idle_chat.news_sources.reddit`は既定で有効で、`communities`を1つの公開Atom feedへまとめてhot投稿を取得します。`x`は既定で無効です。有効化する場合は`bearer_token_env`でtokenを保持する環境変数名を指定し、`queries`へ公式Recent Searchのquery、category、10から100件のlimitを設定します。token本体をYAMLへ保存しません。個別sourceの失敗、429、認証エラーは当該sourceだけをdegradedとして記録し、他のRSS／Atom、Wikipedia、SNS sourceの成功結果を破棄しません。

毎日04:00 JSTのworkflowは「feed／特定URL本文の取得 → `NewsCollectionArtifact`確定」で収集phaseを終了し、そのartifactを入力としてSkill `core.build-daily-source-brief`を`Worker`で1件ずつ実行します。考察phaseは「原文翻訳 → 用語抽出 → 本文で説明できない用語だけ検索 → 検索先URL本文の直接取得 → 用語補足確定 → サマリ → Shiroの見解」を`NewsAnalysisArtifact`へ記録し、ニュース記事だけを`DailyNewsBrief`へ反映します。Wikipedia Randomは`DailyNewsBrief`へ含めず、`IdleChatTopicSeed`の外部刺激として扱います。ユーザー会話または明示Worker実行が始まった場合は日次LLM requestをcancelし、前景処理終了後に同じ収集artifact、同じ記事、短縮していない入力・contextで再試行します。この中断は失敗回数へ含めず、完了済み記事を保持します。利用者への出力順は「原文翻訳 → サマリ → Shiroの見解 → 用語補足」で、本文はすべて日本語とします。原文入力は最大12000文字、翻訳出力は最大16384 token、記事単位timeoutは10分です。元記事本文を取得できない場合は見出しやfeed summaryで補完しません。LLM未設定、timeout、形式不正、一部記事失敗ではanalysis statusを`failed`または`partial`にし、推測せず確認不能を明示します。収集失敗を考察失敗へ、考察失敗を収集失敗へ丸めません。

### ニュースworkflow CLI

採用するTools側の実行pathとcommandは次です。現在の実装状況は`docs/08_実装状況・ロードマップ.md`を正とします。

```text
RenCrow_Tools/tools/news/news_brief/cmd/rencrow-news

rencrow-news collect --output <collection.json> [--max-items <n>]
rencrow-news analyze --input <collection.json> --output <analysis.json> [--core-url <url>]
```

両subcommandはstdoutへmachine-readableな完了要約、stderrへlogを出し、artifactは指定pathへatomicに書き込みます。終了codeは`0=ready`、`2=引数またはschema不正`、`3=partial`、`4=収集失敗`、`5=考察失敗またはCORE考察port unavailable`とします。credentialや記事本文をlogへ出しません。`--core-url`はCOREの論理入口だけを指定でき、RenCrow_LLM Gateway、Runtime、物理Backend、Modelを指定するoptionは設けません。source一覧、件数上限、timeoutの既定値をToolsへ複製せず、CORE所有のpolicy／contractから受け取ります。

現在のプロセス内cacheと解決済み取得先はDebug Viewerの`情報収集`タブ、または`GET /viewer/idlechat/collection`で確認できます。応答には使用Skill、取得項目のtitle、category、source、source type、元URL、原文取得だけを表す`source_read_status`、後続工程を表す`processing_status`、表示可能な工程別理由`processing_error`、両状態の件数集計、原文翻訳、サマリ、見解、用語補足と、credentialを除いたsource設定、利用toolを含みます。収集phaseで取得できた項目は後続処理の状態にかかわらず`items`へ全件残し、`total`は常に`items`の件数と一致させます。`source_read_status=unprocessed`と`processing_status=pending`は未着手であり失敗ではありません。原文取得後の翻訳失敗は`source_read_status=ready`、`processing_status=translation_failed`として区別します。このGETは観測専用であり、収集jobを起動しません。ユーザー向けChatはこのViewer endpointを呼ばず、CORE内部の`DailyNewsBriefReader`から`DailyNewsBrief`を読み取ります。`DailyNewsBrief`が未準備、空、対象日より古い場合だけ`LiveNewsSearch`へフォールバックし、検索時刻を回答へ付けます。

`conversation`の永続化設定は次を使用します。SQLiteの物理pathは`storage.databases`へ記載します。

| key | 用途 |
| --- | --- |
| `redis_url` | active threadを保持するRedis接続先 |
| `vectordb_url` | 意味検索を行うQdrant接続先 |

会話要約と非同期ProfileExtractorはRenCrow_LLM GatewayのWorker経路を使用します。`conversation.embed_model`にはRenCrow_LLMの論理embedding aliasを指定します。空の場合はvector embeddingと意味検索だけを無効化し、Redisのactive thread、L1 SQLiteのraw message、L2 SQLite archiveは維持します。

active threadが12メッセージへ到達した場合、次のactive thread作成と最新メッセージ保存を同期完了してから、旧threadのLLM要約を45秒上限のbackground処理でL2へarchiveします。応答完了はWorker要約を待ちません。Workerが時間内に応答しない場合は、期限切れcontextを保存処理へ再利用せず、新しい5秒contextで決定論的な簡易要約をL2へ保存します。

### Profile昇格設定

次のキーは非同期UserMemory昇格の現行Config schemaです。

| key | 契約 |
| --- | --- |
| `profile_promotion_enabled` | L1 Rawからの非同期UserMemory候補抽出。既定値`true` |
| `profile_promotion_idle_grace_seconds` | 全LLM利用数が0になってから処理開始までの継続Idle時間。既定値`10` |
| `profile_promotion_timeout_seconds` | ProfileExtractor 1回の上限時間。既定値`45` |
| `profile_promotion_batch_messages` | 1回に読む未処理ユーザー発話数。既定値`24`。超過分を破棄せず次回batchへ送る |
| `profile_promotion_max_attempts` | LLM、parse、L1保存失敗の最大試行回数。既定値`5`。busy/cancelは数えない |

非同期ProfileExtractorは`llm_busy`の`active_count=0`が
`profile_promotion_idle_grace_seconds`継続した場合だけ低優先度で開始します。この判定には
IdleChatを含む全provider sourceを含めます。処理開始後に通常LLM要求が来た場合はcancelし、
busy/cancelを抽出失敗として数えず次回Idleへ延期します。`profile_promotion_batch_messages`は
1回の処理量だけを制限し、入力Rawの削除や要約による代替を許可しません。job状態と失敗理由は
`GET /viewer/memory/profile-promotions`で確認できます。

### RenCrow_TTS Gateway

production TTSは`tts.gateway_base_url`で指定したRenCrow_TTS Gatewayだけを使います。

```yaml
tts:
  enabled: true
  gateway_base_url: "http://127.0.0.1:7870"
  timeout_ms: 120000
  voice_id: "mio"
  speed: 1.2
  tls_skip_verify: false
  output_dir: "./workspace/tts"
  playback_commands: []
```

`gateway_base_url`にRenCrow_TTS Gatewayを設定します。target、model、reference音声、
seed、推論parameter、target credentialはRenCrow_TTS側で管理します。

### TTS発音日次チェック

`tts.pronunciation_check`はCORE Schedulerが所有する運用タスクです。`schedule`はUTCの5フィールドcronで、`cron 30 19 * * *`はJST 4:30です。実行前に`gpu_match`で選んだGPUを`idle_samples`回確認し、空きVRAMが`min_free_mb`以上、利用率が`max_utilization_percent`以下のときだけRenCrow_TTSのTool APIを呼びます。条件を満たさない場合は失敗にせず、`retry_interval_seconds`後へ延期します。

### News Pack Article Reader

News Packの元記事は通常HTTP取得を常に第一経路とします。Cloudflare等のbot challengeを`blocked_by_policy`と判定した場合だけ、明示有効化したJina AI Readerを限定fallbackとして使えます。既定はdisabledで、現行hostはOpenAI公式記事だけを許可します。

```yaml
web_gather:
  article_reader:
    enabled: true
    endpoint_prefix: "https://r.jina.ai/http://"
    allowed_source_hosts:
      - "openai.com"
    timeout_ms: 30000
```

`endpoint_prefix`は承認済みのJina Reader HTTPS prefix、`allowed_source_hosts`はwildcardやURLではなく完全一致の公開host名だけを受け付けます。Readerの未設定、timeout、元URL不一致、本文不完全は`unavailable`とし、RSS description／contentと既存項目を削除しません。

## Secret とローカルデータ

- API key、token、private key は環境変数または外部 secret store に置く。
- `config.yaml`、runtime DB、log、cache、generated artifact は commit しない。
- 外部 bind を行う場合は TLS、認証、network allowlist を別途設定する。
