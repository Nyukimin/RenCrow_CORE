# ログ仕様

## 目的

ログは RenCrow の不具合調査における第一の証拠です。この文書は、ログが備えるべき三つの資質を契約として定めます。

- **イベントを落とさない**: 記録すると決めたイベントは、負荷や輻輳を理由に欠落させない
- **肥大化しない**: すべての出力先に上限か保持期間を持たせ、無制限に増やさない
- **観測しやすい**: 一つのユーザー操作を CMD／PORTAL／ASSISTANT から CORE まで一つの相関IDで追える

`docs/09_運用ログ・panic保存仕様.md` は journal 集約、日別アーカイブ、事故台帳、自己修復といった**運用面**を規定します。本書はアプリケーションが**何をどの形式で出力するか**を規定します。両者が衝突した場合、出力形式は本書、運用手順は `09` を正本とします。

横断ルールは `rules/common/rules_logging.md` を継承します。本書はその §9「プロジェクト固有ルール」に相当し、RenCrow における具体化です。

## 適用範囲

RenCrow_CORE、RenCrow_CMD、RenCrow_PORTAL、RenCrow_ASSISTANT、RenCrow_Vision に適用します。CORE が相関IDの発行者であり、他モジュールは受け取った相関IDを保持して出力します。

## クロスプラットフォーム前提

RenCrow は Windows / Linux / macOS で共通に動作します。ログ実装を特定OSに依存させません。

- アプリケーションは **stdout／stderr へ出力**し、収集はプラットフォーム側の仕組みに委ねます。
- Linux の systemd 環境では journal が収集します（`09` の規定）。Windows と macOS では収集手段が異なるため、`09` の journal 手順をアプリ側の前提にしません。
- ファイルへ直接出力する場合、パスは `filepath.Join` で組み立て、区切り文字を文字列連結しません。
- ログ本文へパスを埋め込む場合、JSON エンコーダに委ね、手動で文字列連結しません。Windows path の `\` が不正なエスケープになります。
- 改行コードに依存した解析を行いません。
- ファイル権限に依存した機密保護を前提にしません。Windows は POSIX パーミッションを持ちません。機密は**出力しないこと**で守ります。

## ログの形式

### 構造化ログ

アプリケーションログは **JSON 1行**で出力します。人間可読なテキストログは、CLI がユーザーへ表示する出力とは別物として扱い、混在させません。

```json
{"schema_version":1,"ts":"2026-07-27T12:00:00.000Z","level":"info","event":"viewer.send.accepted","module":"RenCrow_CORE","tags":["audit"],"trace_id":"job-...","job_id":"job-...","session_id":"...","viewer_client_id":"portal-...","operation_source":"RenCrow_PORTAL","interaction_profile":"portal-chat"}
```

### 必須フィールド

| フィールド | 内容 |
| --- | --- |
| `schema_version` | ログ形式のバージョン。破壊的変更時に増やす |
| `ts` | UTC、RFC3339、ミリ秒精度 |
| `level` | `debug` / `info` / `warn` / `error` / `critical` |
| `event` | ドット区切りの識別子。自由文ではなく列挙可能な値にする |
| `module` | `RenCrow_CORE` / `RenCrow_CMD` / `RenCrow_PORTAL` / `RenCrow_ASSISTANT` / `RenCrow_Vision` |

### 相関フィールド

該当する値がある場合は必ず含めます。値が無いことと空文字を区別できるよう、無い場合はフィールドごと省略します。

| フィールド | 内容 |
| --- | --- |
| `trace_id` | 一つのユーザー操作を端から端まで貫く識別子 |
| `job_id` | CORE が受け付けた処理単位 |
| `session_id` | 会話セッション |
| `viewer_client_id` | client 単位の相関 |
| `operation_source` | `X-RenCrow-Client` で申告された client 種別 |
| `interaction_profile` | 適用された profile |

`trace_id` は経路の途中で欠落させません。CORE が発行し、応答へ含め、client はそれを自身のログへ記録します。

### イベント名

`event` は `<領域>.<対象>.<結果>` の形式にします。grep と集計の対象になるため、可変値を名前へ埋め込みません。

```text
viewer.send.accepted
viewer.send.rejected
proxy.request.forwarded
proxy.request.denied
llm.request.failed
vision.request.started
vision.request.completed
vision.request.failed
```

## 記録と配信の分離

イベントの用途を二つに分け、**同じ経路で扱いません**。

| 種別 | 目的 | 欠落 |
| --- | --- | --- |
| **記録** | 事後の調査・監査の証拠 | **禁止**。捨てるくらいなら遅延させる |
| **配信** | SSE などのリアルタイム通知 | 許容する。ただし欠落を観測可能にする |

- 記録パスは、バッファ満杯を理由にイベントを破棄しません。書き込み失敗は無言で握りつぶさず、`error` として出力します。
- 配信パスは低遅延を優先し、遅い購読者への配信を落とすことを許容します。落とした場合は件数を計測し、`event.delivery.dropped` として記録パスへ出力します。
- 一つのキューが記録と配信を兼ねる構成は、記録の欠落を招くため禁止します。

`rules/common/rules_logging.md` §5 が定める8タグ（`audit` / `state_change` / `external` / `business_logic` / `error` / `exception` / `startup` / `config`）を持つログは、記録パスに属し、サンプリングの対象外です。

## 保持と上限

すべての出力先は、上限か保持期間のいずれかを持ちます。無制限に増える出力先を作りません。

| 出力先 | 方針 |
| --- | --- |
| 標準出力・標準エラー | 収集側（journal 等）の保持に従う。`09` の7日アーカイブが該当 |
| 会話セッションログ | 保持期間を設定する。既定は有限とする |
| LLM 生応答ログ（rawlog） | **既定で無効**。有効時はサイズローテーションと保持期間を必須とする |
| 監査・実行記録の JSONL | ローテーションまたは保持期間を設定する |
| イベントログのテーブル | 保持期間を設定し、GC を実装する |
| メモリ上のリングバッファ | 件数上限に加え、キー単位の TTL 退避を実装する |

GC 自身が出力するレポートも出力先の一つです。GC 対象から除外しません。

## 機密の扱い

`docs/07_安全・自動実行・データ方針.md` の「secret を log へ保存しない」を、ログ側で機械的に担保します。

- マスキングは**書き出し層で適用**します。呼び出し側の注意に依存しません。
- キー名ベースの再帰マスクとします。対象は `password` / `token` / `api_key` / `secret` / `authorization` / `credential` と、個人識別子です。
- 会話本文、LLM の生応答、ツール引数は、機密が混入し得る領域として扱います。これらを出力する機能は既定で無効にするか、マスクを通します。
- 接続元IPは生値を出力せず、マスク値と相関hashを出力します（`09` の規定）。
- ファイル権限による保護を前提にしません。Windows では成立しません。

## モジュール別の責務

### RenCrow_CORE

- `trace_id` の発行者です。受け付けた操作に対して発行し、応答へ含めます。
- すべての処理段階（受付、非同期開始、完了、エラー）で同じ `trace_id` と `job_id` を出力します。
- 相関フィールドを欠いたまま処理を進めません。
- Vision呼び出しでは`vision.request.started`、`vision.request.completed`、
  `vision.request.failed`を同じ`trace_id`、`job_id`、`session_id`で記録します。
  filename、MIME、size、kindは記録できますが、raw mediaとdata URLは記録しません。

### RenCrow_Vision

- COREから受け取った`request_id`を`trace_id`として保持し、Wild requestとresponseまで
  同じ値で追跡します。
- `vision.provider.request.started`、`vision.provider.request.completed`、
  `vision.provider.request.failed`にprovider、model、kind、latency、error codeを記録します。
- prompt、Wildの生response、raw media、base64 data URL、local temp pathは既定で記録しません。

### RenCrow_CMD

- CORE から受け取った `job_id` と `trace_id` を、ユーザーが参照できる形で出力します。ターミナル出力から CORE のログを引けることを要件とします。
- 未知のイベント種別を黙って破棄しません。未知として記録します。
- CLI の表示出力（stdout）と、調査用のログ（stderr）を分離します。

### RenCrow_PORTAL

- proxy したリクエストを記録します。method、path、status、所要時間を含めます。
- **自身が拒否したリクエストも記録します**。mode 不許可、endpoint 非許可、cross-origin 拒否、CORE 到達不能は、CORE に到達しないため PORTAL が唯一の証拠元です。
- `viewer_client_id` と、CORE から受け取った `job_id` を記録します。

### RenCrow_ASSISTANT

- 未実装です。実装時は本書の契約に従います。

## ログレベル

`rules/common/rules_logging.md` §8 に従います。RenCrow では次を追加します。

- レベルは設定から制御できるようにし、設定値を実際のロガーへ配線します。定義だけ存在して未配線の状態を残しません。
- 起動時に、適用されたレベルと設定の要約を `startup` タグで1回出力します。

## 障害調査の起点

一つの操作を追う手順を、次の順で成立させます。

1. ユーザーの手元（CMD のターミナル出力、PORTAL の画面）から `job_id` または `trace_id` を得る
2. その値で CORE のログを引く
3. CORE に該当が無い場合、client 側（PORTAL の proxy ログ、CMD のログ）で拒否・到達失敗を確認する

3 が成立するために、client 側の記録が必要です。CORE のログだけで完結させません。
