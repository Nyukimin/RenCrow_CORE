# ログ仕様

## 目的

ログは RenCrow の不具合調査における第一の証拠です。この文書は、ログが備えるべき三つの資質を契約として定めます。

- **イベントを落とさない**: 記録すると決めたイベントは、負荷や輻輳を理由に欠落させない
- **肥大化しない**: すべての出力先に上限か保持期間を持たせ、無制限に増やさない
- **観測しやすい**: 一つのユーザー操作を CMD／PORTAL／ASSISTANT から CORE まで一つの相関IDで追える

`docs/09_運用ログ・panic保存仕様.md` は journal 集約、日別アーカイブ、事故台帳、自己修復といった**運用面**を規定します。本書はアプリケーションが**何をどの形式で出力するか**を規定します。両者が衝突した場合、出力形式は本書、運用手順は `09` を正本とします。

横断ルールは `rules/common/rules_logging.md` を継承します。本書はその §9「プロジェクト固有ルール」に相当し、RenCrow における具体化です。

## 適用範囲

RenCrow_CORE、RenCrow_CMD、RenCrow_PORTAL、RenCrow_ASSISTANT、RenCrow_Vision に適用します。CORE が相関IDの発行者であり、他モジュールは受け取った相関IDを保持して出力します。

## クロスプラットフォーム前提

RenCrow は Windows / Linux / macOS で共通に動作します。ログ実装を特定OSに依存させません。

- アプリケーションは **stdout／stderr へ出力**し、収集はプラットフォーム側の仕組みに委ねます。
- Linux の systemd 環境では journal が収集します（`09` の規定）。Windows と macOS では収集手段が異なるため、`09` の journal 手順をアプリ側の前提にしません。
- ファイルへ直接出力する場合、パスは `filepath.Join` で組み立て、区切り文字を文字列連結しません。
- ログ本文へパスを埋め込む場合、JSON エンコーダに委ね、手動で文字列連結しません。Windows path の `\` が不正なエスケープになります。
- 改行コードに依存した解析を行いません。
- ファイル権限に依存した機密保護を前提にしません。Windows は POSIX パーミッションを持ちません。機密は**出力しないこと**で守ります。

## ログの形式

### 構造化ログ

アプリケーションログは **JSON 1行**で出力します。人間可読なテキストログは、CLI がユーザーへ表示する出力とは別物として扱い、混在させません。

```json
{"schema_version":1,"ts":"2026-09-05T12:00:00.000Z","level":"info","event":"viewer.send.accepted","module":"RenCrow_CORE","tags":["audit"],"trace_id":"trc_01a05220-f2ee-7bdf-9df9-e5106c0e2fa9","task_id":"tsk_01a07000-0000-7000-8000-000000000001","session_id":"ses_01a07000-0000-7000-8000-000000000002","viewer_client_id":"portal-...","operation_source":"RenCrow_PORTAL","interaction_profile":"portal-chat"}
```

### 必須フィールド

| フィールド | 内容 |
| --- | --- |
| `schema_version` | ログ形式のバージョン。破壊的変更時に増やす |
| `ts` | UTC、RFC3339、ミリ秒精度 |
| `level` | `debug` / `info` / `warn` / `error` / `critical` |
| `event` | ドット区切りの識別子。自由文ではなく列挙可能な値にする |
| `module` | `RenCrow_CORE` / `RenCrow_CMD` / `RenCrow_PORTAL` / `RenCrow_ASSISTANT` / `RenCrow_Vision` |

### 相関フィールド

該当する値がある場合は必ず含めます。値が無いことと空文字を区別できるよう、無い場合はフィールドごと省略します。

| フィールド | 内容 |
| --- | --- |
| `trace_id` | 一つのユーザー操作を端から端まで貫く識別子 |
| `task_id` | COREが受け付けた実行可能なTask。rootとchildは別IDを持つ |
| `session_id` | 会話セッション |
| `viewer_client_id` | client 単位の相関 |
| `operation_source` | `X-RenCrow-Client` で申告された client 種別 |
| `interaction_profile` | 適用された profile |

`trace_id` は経路の途中で欠落させません。CORE が発行し、応答へ含め、client はそれを自身のログへ記録します。
`trace_id`と`task_id`は別の識別子であり、同じ値にしません。Root／Child Task、routing、assignment、
execution、completionは同じCanonical Task契約を使い、旧`job_id`や`/viewer/jobs`互換aliasを残しません。

### LLM利用の観測metadata

COREからRenCrow LLM Gatewayへ送る各LLM requestは、prompt本文と分離した
`rencrow` metadataに次を含めます。

| フィールド | 内容 |
| --- | --- |
| `request_id` | 1回のLLM requestの相関ID。上流に無い場合はCOREが独立発行し、TraceID、TaskID、SessionIDから派生させない |
| `trace_id` | 元操作を貫く既存ID。無い場合は省略する |
| `task_id` | COREが受け付けたCanonical TaskID。Taskに属さないrequestでは省略する |
| `session_id` | 既存の会話またはworkflow session。無い場合は省略する |
| `initiator` | LLM利用を開始した既存Agent IDまたは認証済みuser ID。Model、provider、controllerをactorとして記録しない |
| `caller` | `idlechat.daily_source_brief`等の列挙可能で安定した呼び出しcomponent ID |
| `purpose` | `translate_article`、`image_prompt_evaluation`等の列挙可能で機密を含まない利用理由 |

Gatewayが解決する`agent_id`、`execution_role`、`execution_alias`、
`role_profile_revision`、`target_id`、`provider`、`model`と上記metadataを組み合わせ、
現在状態APIと`llm.request.started` / `llm.request.completed` / `llm.request.failed`の
開始・終了logで同じrequestを追跡できることを受入条件とします。
prompt本文、会話本文、LLM生応答、Persona、private Memory、内部reasoningは
このmetadataまたは観測logへ記録しません。

呼び出し側が個別の観測metadataを付与していない場合も空文字のまま送信しません。
GatewayProviderは確定済みの`agent_id`を`initiator`に再利用し、`caller=core.unattributed`、
`purpose=unattributed`として明示的に未帰属状態を記録します。このfallbackは上流が付与した
具体的な`initiator`、`caller`、`purpose`を上書きせず、未知のcallerやpurposeを推測しません。

### イベント名

`event` は `<領域>.<対象>.<結果>` の形式にします。grep と集計の対象になるため、可変値を名前へ埋め込みません。

```text
viewer.send.accepted
viewer.send.rejected
proxy.request.forwarded
proxy.request.denied
llm.request.failed
vision.request.started
vision.request.completed
vision.request.failed
agent.delegate
agent.acknowledge
agent.report
capability.apply.requested
capability.apply.validated
capability.apply.rejected
capability.apply.blocked
capability.apply.restart_scheduled
capability.apply.stopping
capability.apply.starting
capability.apply.verifying
capability.apply.completed
capability.apply.failed
news.brief.requested
news.brief.cache_hit
news.brief.cache_miss
news.brief.fallback_started
news.brief.responded
news.brief.failed
```

### Agent間協調の観測

Agent間の作業要求と返却は、既存の`agent.delegate`、`agent.acknowledge`、`agent.report`で開始、受領、終了を観測する。各eventは同じ`request_id`、`trace_id`、`task_id`、`session_id`を引き継ぎ、該当する場合は`from_agent_id`、`to_agent_id`、`from_contract_revision`、`to_contract_revision`、`work_type`、`expected_deliverable_type`、`actual_deliverable_type`、`status`、`error_code`を含める。

`agent.report`は`completed`、`partial`、`failed`、`rejected`、`timed_out`、`cancelled`のいずれかで作業を閉じる。移譲先が報告できない場合はCOREが`actor=orchestrator`のsystem failureとして記録し、Agent発言を捏造しない。Routerは候補Agent、選択Agent、選択理由を列挙可能なfieldで記録し、自由文だけを根拠にしない。Agent名、contract revision、期待成果物、実際の成果物の不一致を観測可能にする。

ログには成果物本体、大量のartifact、raw prompt、Persona本文、private Memory、credential、内部reasoningを複製しない。許可された要約、artifact reference、hash、件数、error codeを記録し、詳細は元の保存領域とprovenanceを参照する。Agent間の通信記録だけを根拠にUserMemoryまたは確定Knowledgeへ自動昇格しない。

### RenCrow_Harness委譲の相関

Status: 採用済み設計・未実装（RenCrow_Harness設計v0.2.2、2026-10-07）。`RenCrow_Harness` repositoryと
COREの委譲clientは未作成で、本節は実装が満たす観測契約を定めます。境界は
[アーキテクチャ概要](04_アーキテクチャ概要.md#rencrow_harness委譲境界)、IDの発行者は
[Identity正本](architecture/identity/IDENTITY_CANONICAL.md#51-rencrow_harnessのissuer境界)を正本とします。

HarnessはEventを自身のstoreへappend-onlyで保存し、EventIDも自分で発行します。COREはHarnessのEventをCOREの
Canonical Event Storeへ写してCOREの事実にしません。Harnessが発行するIDはCOREの相関ID発行の例外ではなく、別ownerのIDです。

- COREのlogは、自分の`trace_id`、`task_id`と、該当するRun、Action、AttemptのIDを出力します。これに加え、Harnessの
  `task_id`、`run_id`、`receipt_id`を、`{owner:"RenCrow_Harness", id}`の外部参照として記録します。同じ値が別ownerのIDと
  衝突しても区別できるよう、`id`だけを単独で記録しません。ログ上のfield名とevent名は、実装時（
  [ロードマップ](08_実装状況・ロードマップ.md#rencrow_harnessロードマップ)のWP08）に確定して本節とイベント名の一覧へ追記します。
- 逆方向の相関は、Harnessが`upstream`にCOREの`trace_id`、`task_id`、`action_id`、`attempt_id`等を参照として保持することで
  成立します。参照は権限を与えません。
- Harnessの`event_id`を引用する場合は`{owner, event_id}`とします。COREが記録する「委譲が完了した」という別の事実には、COREが
  新しいEventIDを付けます。HarnessのEventIDを流用しません。
- 再開は同じHarnessの`task_id`に新しい`run_id`を付けます。COREは旧`run_id`の記録を書き換えず、新しい`run_id`を追加して
  相関します。再送や取消の結果確認は`receipt_id`で行います。
- Harnessの公開Event payloadとstderrに、本文、鍵、credentialを入れません。COREのlogにも、Harnessのprompt、Model入出力、Tool結果の
  本文、鍵、`OriginProof`のMACを複製せず、許可された要約、reference、hash、件数、error codeだけを記録します。

COREのlogからHarness側を追う手順は、`trace_id`から委譲Action／Attemptを特定し、記録した外部参照のHarness `task_id`、
`run_id`でHarnessのEvent storeを引く順です。Harness側の詳細はHarness repositoryの内部契約に従い、COREのlogだけで完結させません。

WP08で確定したevent名とfield名は次です。形式は[構造化ログ](#構造化ログ)（1行JSON、`module`は`RenCrow_CORE`、`tags`は`native_harness`）に従います。

| event | 意味 |
| --- | --- |
| `native_harness.client.started` | Harnessを起動し、protocol versionとbuild_revisionの照合に通った。`protocol_version`、`build_revision` |
| `native_harness.client.start_failed` | 起動または照合に失敗した。`code`は`harness_start_failed`、`harness_incompatible`、`harness_build_revision_mismatch`。pathとHarnessのmessageは含めない |
| `native_harness.client.ended` / `.stopped` | 接続が終わった／CORE終了時に停止した（`orderly`） |
| `native_harness.client.stderr` | 子processのstderrの1行（警告、512 byteまで） |
| `native_harness.admission.refused` | admissionが`rejected`または`blocked`にした。`reason`と、該当するturnの`trace_id`、`task_id`、`turn_id` |
| `native_harness.delegate.started` | 委譲を開始した（Action／Attempt作成後） |
| `native_harness.delegate.accepted` | `turn/start`の受付を確認した。Harnessの`harness_thread`、`harness_task`、`harness_run`、`harness_receipt` |
| `native_harness.delegate.finished` | Harnessが決めたRunの終端を記録した。`status`、`code`、`verification`、`resumable`、`accepted`と`harness_*` |
| `native_harness.delegate.outcome_unknown` | 受付後に終端を読めなかった（`phase`が`start`または`await`） |
| `native_harness.delegate.record_failed` | 委譲Attemptの終端をCOREが記録できなかった |
| `native_harness.event` | Harnessの確定Eventのうち、`task.created`、`run.started`、`control.cancel_requested`、`checkpoint.committed`、`run.terminal`と、`code`を持つEventの参照。`harness_event`（`{owner, event_id}`）、`event_type`、`event_seq`、`harness_thread`、`harness_task`、`harness_run`、`harness_receipt`、`code`。payloadは出さない |

委譲に関するeventは、COREの`trace_id`、`task_id`（親Task）、`turn_id`、`run_id`（親Run）、`action_id`、`attempt_id`を出します。
Harnessが発行したIDは`harness_task`、`harness_run`、`harness_receipt`、`harness_thread`として`{"owner":"RenCrow_Harness","id":...}`の形
でだけ出し、`id`を単独で出しません。委譲Actionと同Attemptのsummaryにも同じ参照を`RenCrow_Harness/<id>`の形で残します。

### Capability applyの観測

`capability.apply.*`はTool、Skill、MCPのsource観測、Snapshot projection、policy判定、応答後の
CORE replacement、再起動後検証を一つのrequestとして追跡するeventです。全eventは同じ
`request_id`、`trace_id`、必要な場合は`task_id`を持ち、receiptの`decision`／`phase`、
`snapshot_revision`／`snapshot_hash`、期待capabilityのkind／canonical name／source revision／
source hash、`task_id`、instance identity、error codeを要約fieldとして記録します。

- `requested`はrequestの受付とrequester／authenticated scopeの要約を記録します。
- `validated`はsource/list、Worker policy、current Snapshot、期待する最終Snapshotの固定結果を記録します。
- `rejected`／`blocked`は確定したdecision、安定error code、理由、fallbackを行わなかったことを記録します。
- `restart_scheduled`、`stopping`、`starting`、`verifying`はCORE応答後のsupervisorと新旧instanceを
  相関します。終了したCORE processは再起動後のcompleted eventを発行しません。
- `completed`は再起動不要または新instanceのlistener、`/health/live`、`/health/ready`、期待Snapshot
  membership／hashを全て確認した場合だけ発行します。
- `failed`は`PORT_OWNERSHIP_CONFLICT`、`PORT_RELEASE_TIMEOUT`、`TASK_START_FAILED`、
  `CAPABILITY_READINESS_TIMEOUT`、`CAPABILITY_SNAPSHOT_MISMATCH`等を必須で持ちます。

receipt本体はCORE-owned Durable Storeへatomicに保存し、eventはappend-only監査へ記録します。
ログへsecret、credential、Skill本文、MCP payload、raw tool引数、user本文、任意shell commandを
出しません。CLIはstdoutのmachine-readable receipt／statusとstderrの運用logを分離し、利用者は
`request_id`からCORE log、receipt、再起動後instanceの観測を再現できます。物理receipt pathとretentionは
[設定リファレンス](05_設定リファレンス.md#capability-applyとreceipt)、APIとCLIのfield／statusは
[Public API仕様](06_Public_API仕様.md#capability-applyとstatus)を正本とします。

`rencrow health`、`rencrow health --json`、`rencrow status --deep --json`が出力する
health checkの`duration_ms`は整数ミリ秒です。Go内部の`time.Duration`が持つナノ秒値を
wire値として直列化しません。HTTP `/health`とCLI JSONは同じ単位で観測できるものとします。

通常運用のCOREでは、全文Promptの代わりにPrompt receiptをJSONLへ記録する。receiptは`trace_id`、Prompt全体とSystemPromptのSHA-256、section別件数、文字数、相関情報、SystemPrompt末尾の最新1文（最大240文字、機密値をマスク）だけを持ち、Prompt本文、ユーザー本文、添付データ、provider optionは保存しない。出力先は`RENCROW_PROMPT_RECEIPT_LOG`で変更でき、未設定時は`~/.rencrow/logs/prompt_receipt.jsonl`へサイズローテーション付きで保存する。receipt書き込み失敗はLLMリクエストを中断せず、`error`として記録する。

SystemPromptの到達性をデバッグする明示的な診断時は、RenCrow_LLM Gatewayの`RENCROW_LLM_PROMPT_DEBUG_LOG`を設定する。同一`request_id`／`trace_id`で、Gatewayが受信した`gateway_received`のHTTP body全文と、変換後にLLM実体へ送った`target_sent`のpayload全文を照合する。両方ともSystemPrompt、user／assistant／tool message、attachment、provider optionを省略せず、可読な`payload_text`とwire bytes完全再現用の`payload_base64`を持つ。これは通常ログと分離した0600の診断ログであり、Gitへ保存しない。

Step 09のTask identity切替では、旧session log、Prompt receipt、Gateway prompt-debug logを
`job_id`だけ機械置換しません。旧rowの多くは`trace_id == job_id`であり、一方だけの置換は
壊れたIdentityを現役logへ残すためです。COREとGatewayの全writerを停止し、各active artifactを
同一filesystem上のowner-only legacy archiveへ原子的にrenameし、path、size、mode、SHA-256を
cutover receiptへ記録してから、`task_id`を出力するfresh active artifactを開始します。
legacy archiveはbytesを変更せず保持し、active pathやcompatibility readerから公開しません。

### DailyNewsBriefの観測

`daily_news_brief` Intentを処理する場合、COREは同じ`trace_id`、`task_id`、`session_id`で次のイベントを記録します。`news.brief.requested`には`intent`と利用者の要求種別、cache選択後の`news.brief.cache_hit`または`news.brief.cache_miss`には`brief_date`、`fetched_at`、`enrichment_status`、`item_count`を含めます。外部検索へ切り替えた場合は`news.brief.fallback_started`に`source=live_news_search`と理由を記録し、最終結果は`news.brief.responded`または`news.brief.failed`で閉じます。

イベント本文へニュース記事の全文、LLM生応答、検索toolのcredential、未加工のtool引数を記録しません。調査に必要なsource名、URL、取得時刻、状態、item IDだけを許可された要約フィールドとして残します。`DailyNewsBrief`を使った応答で外部検索が発生していないことも、`news.brief.cache_hit`から確認できなければなりません。

### TaskStore transaction所要の診断行

Task store（`internal/infrastructure/persistence/task`）は、writerとして開いたstoreの全transactionの所要時間を観測し、
診断行を標準エラー（Go `log`の既定出力。収集は上記のとおりプラットフォーム側）へ出します。読取専用handle（`rencrow tasks`などのCLI）は観測しません。
形式は`[Heartbeat] worker finalization slow`と同じ`[<領域>] <語> key=value ...`の1行で、上記のJSON 1行の構造化ログ
（`event`を持つもの）ではありません。構造化ログへの移行はlogger配線を統一する別変更で扱います。目的は、Task store保持期限
（設計案`docs/調査/20261010_084428_TaskStore保持期限_設計案.md`の実装単位IU-1）の前後比較に使うbaselineの採取です。
healthの`degraded`判定には使いません。

計測するのは1 transactionの4区間です。`jsonlbatch.Store`の`Read` / `Write`が測り、flock解放後に通知します。

| 区間 | 内容 |
| --- | --- |
| `lock_wait` | 呼出しからflock取得まで（取れずにcontext終了した場合はそこまで） |
| `settle` | lock取得後・callback前。Writeは前回のWAL回復とcheckpoint、Readはjournalのcommit済み確認 |
| `exec` | callback。Task storeでは全件decodeを含む |
| `commit` | Writeのみ。callback後の検証、追記前後のSHA-256、追記、fsync、commit record |

`kind`は`read` / `write`、`op`はstoreの入口名（`Transaction` / `TaskTransaction` / `ReadTransaction` /
`ExecuteIdempotentTaskOperation` / `ExecuteIdempotentGlobalTaskOperation` / `LookupTaskOperation` /
`GetTaskExecutionFence` / `AcquireTaskExecutionFence` / `ReleaseTaskExecutionFence`。ラベルが無ければ`unlabeled`）です。
Manager層の操作名（Create / Start / Succeedなど）はstoreに渡らないため出ません。構成の比較には`files`を使います。

**遅いtransaction**は、`exec + commit > 5秒`または`lock_wait > 10秒`のとき（`settle`は判定に含めない）、1件につき1行出します。

```text
[TaskStore] tx slow kind=write op=TaskTransaction task_id=<task_id> result=ok lock_wait=1.234s settle=3ms exec=5.6s commit=1.2s files=task_run.jsonl+task_state.jsonl hot_bytes=95200000
```

- `task_id`はTaskに限定したtransactionだけに付き、無い場合は省略します。`result`は`ok` / `error`（lockを取った後の失敗）/
  `lock_failed`（lockを取れずに終了）で、エラー文言は出しません。`files`は追記したfile名で、無ければ省略します。
- `hot_bytes`は`task_state.jsonl`と`task_run.jsonl`のbyte数の和（`stat`、decodeしない）。取得に失敗した場合は`unknown`です。
- record本文、secret、LLM応答は出しません。

**要約**は、直近512 transactionについて、read / write別に件数とp50 / p95を1行で出します。transactionが完了した時に
「前回の要約から10分以上たっている」場合だけ出します（最初の要約はstoreを開いてから10分後以降）。timerもgoroutineも
使わないため、transactionが無い間は出ません。

```text
[TaskStore] tx summary window=9m58s write_n=312 write_lock_wait_p50=0s write_lock_wait_p95=8.1s write_settle_p50=1ms write_settle_p95=3ms write_exec_p50=2.4s write_exec_p95=3.1s write_commit_p50=0.5s write_commit_p95=0.9s read_n=40 read_lock_wait_p50=0s read_lock_wait_p95=0.2s read_settle_p50=1ms read_settle_p95=2ms read_exec_p50=1.9s read_exec_p95=2.2s hot_bytes=95200000 task_state_bytes=66200000 task_run_bytes=29000000
```

- `window`は要約対象のうち最も古いtransactionの経過時間です。percentileは昇順に並べたnearest-rank（順位`ceil(p/100 × n)`）です。
- 母数は区間ごとに異なります。`lock_wait`は全transaction、`settle`と`exec`はlockを取れたもの、`write_commit`は
  1件以上追記したWriteだけです。母数が0の値は`-`と出します。Readに`commit`はありません。
- 閾値（5秒・10秒）、間隔（10分）、件数（512）はコードの定数で、Configにはありません。

## 記録と配信の分離

イベントの用途を二つに分け、**同じ経路で扱いません**。

| 種別 | 目的 | 欠落 |
| --- | --- | --- |
| **記録** | 事後の調査・監査の証拠 | **禁止**。捨てるくらいなら遅延させる |
| **配信** | SSE などのリアルタイム通知 | 許容する。ただし欠落を観測可能にする |

- Canonical Eventの記録パスはowner requestと同期し、Event Store append成功後にだけ配信パスへ渡します。正本記録を非同期bufferへ委ねません。
- Canonical Event Storeの書き込み失敗は呼出元へ返し、requestをcancelして成功応答を禁止します。同期callerを持たないbackground producerはowner jobをfailedにするか、少なくともerrorを明示して成功通知を発行しません。
- 配信パスは低遅延を優先し、遅い購読者への配信を落とすことを許容します。落とした場合は件数を計測し、`event.delivery.dropped` として記録パスへ出力します。
- 一つのキューが記録と配信を兼ねる構成は、記録の欠落を招くため禁止します。

`rules/common/rules_logging.md` §5 が定める8タグ（`audit` / `state_change` / `external` / `business_logic` / `error` / `exception` / `startup` / `config`）を持つログは、記録パスに属し、サンプリングの対象外です。

## 保持と上限

すべての出力先は、上限か保持期間のいずれかを持ちます。無制限に増える出力先を作りません。

| 出力先 | 方針 |
| --- | --- |
| 標準出力・標準エラー | 収集側（journal 等）の保持に従う。`09` の7日アーカイブが該当 |
| 会話セッションログ | 保持期間を設定する。既定は有限とする |
| LLM 生応答ログ（rawlog） | **既定で無効**。有効時はサイズローテーションと保持期間を必須とする |
| 監査・実行記録の JSONL | ローテーションまたは保持期間を設定する |
| イベントログのテーブル | 保持期間を設定し、GC を実装する |
| メモリ上のリングバッファ | 件数上限に加え、キー単位の TTL 退避を実装する |

GC 自身が出力するレポートも出力先の一つです。GC 対象から除外しません。

## 機密の扱い

`docs/07_安全・自動実行・データ方針.md` の「secret を log へ保存しない」を、ログ側で機械的に担保します。

- マスキングは**書き出し層で適用**します。呼び出し側の注意に依存しません。
- キー名ベースの再帰マスクとします。対象は `password` / `token` / `api_key` / `secret` / `authorization` / `credential` と、個人識別子です。
- 会話本文、LLM の生応答、ツール引数は、機密が混入し得る領域として扱います。これらを出力する機能は既定で無効にするか、マスクを通します。
- 接続元IPは生値を出力せず、マスク値と相関hashを出力します（`09` の規定）。
- ファイル権限による保護を前提にしません。Windows では成立しません。

## モジュール別の責務

### RenCrow_CORE

- `trace_id` の発行者です。受け付けた操作に対して発行し、応答へ含めます。
- すべての処理段階（受付、非同期開始、完了、エラー）で同じ`trace_id`と該当Taskの`task_id`を出力します。
- 相関フィールドを欠いたまま処理を進めません。
- Vision呼び出しでは`vision.request.started`、`vision.request.completed`、
  `vision.request.failed`を同じ`trace_id`、`task_id`、`session_id`で記録します。
  filename、MIME、size、kindは記録できますが、raw mediaとdata URLは記録しません。

### RenCrow_Vision

- COREから受け取った`request_id`を`trace_id`として保持し、Wild requestとresponseまで
  同じ値で追跡します。
- `vision.provider.request.started`、`vision.provider.request.completed`、
  `vision.provider.request.failed`にprovider、model、kind、latency、error codeを記録します。
- prompt、Wildの生response、raw media、base64 data URL、local temp pathは既定で記録しません。

### RenCrow_CMD

- COREから受け取った`task_id`と`trace_id`を、ユーザーが参照できる形で出力します。ターミナル出力からCOREのログを引けることを要件とします。
- 未知のイベント種別を黙って破棄しません。未知として記録します。
- CLI の表示出力（stdout）と、調査用のログ（stderr）を分離します。

### RenCrow_PORTAL

- proxy したリクエストを記録します。method、path、status、所要時間を含めます。
- **自身が拒否したリクエストも記録します**。mode 不許可、endpoint 非許可、cross-origin 拒否、CORE 到達不能は、CORE に到達しないため PORTAL が唯一の証拠元です。
- `viewer_client_id`と、COREから受け取った`task_id`を記録します。

### RenCrow_ASSISTANT

- 未実装です。実装時は本書の契約に従います。

### RenCrow_Harness

- Status: 採用済み設計・未実装（RenCrow_Harness設計v0.2.2、2026-10-07）。
- 自分のlogとEvent storeを所有し、そのschemaはRenCrow_Harness repositoryの内部契約が所有します。COREは、`upstream`に
  相関IDを渡し、返却された外部参照を自分のlogへ記録するだけで、HarnessのEvent storeへ書き込まず、Harnessの内部log形式を
  正本にしません。相関の契約は[RenCrow_Harness委譲の相関](#rencrow_harness委譲の相関)に従います。
- stdoutはprotocol専用で、logを混在させません。stderrは機密を含まない診断だけを出力します。COREが子processのstderrを
  記録する場合も、機密を含まない診断として扱います。保存先は実装時（WP08）に確定します。

## ログレベル

`rules/common/rules_logging.md` §8 に従います。RenCrow では次を追加します。

- レベルは設定から制御できるようにし、設定値を実際のロガーへ配線します。定義だけ存在して未配線の状態を残しません。
- 起動時に、適用されたレベルと設定の要約を `startup` タグで1回出力します。

## 障害調査の起点

一つの操作を追う手順を、次の順で成立させます。

1. ユーザーの手元（CMDのターミナル出力、PORTALの画面）から`task_id`または`trace_id`を得る
2. その値で CORE のログを引く
3. CORE に該当が無い場合、client 側（PORTAL の proxy ログ、CMD のログ）で拒否・到達失敗を確認する

3 が成立するために、client 側の記録が必要です。CORE のログだけで完結させません。
