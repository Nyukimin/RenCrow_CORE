# システム概要

RenCrow_CORE は、会話型インターフェースと作業実行を、安全な複数エージェント構成で統合する orchestration runtime です。

## 目的

- 人格を保った自然な対話と、明示的な作業依頼を同じ入口で扱う。
- 会話、判断、提案、実行、policy判定の責任者を分離する。
- Agentが互いの公開契約を理解し、受信Agentが必要とする成果物として仕事を依頼・返却できる協調基盤を持つ。
- 会話履歴と Knowledge を provenance 付きで Recall する。
- 長時間の作業を Workstream、Scheduler、Heartbeat で継続する。
- 実行状態、失敗、degraded状態をDebug Viewerから観測し、外部利用者にはRenCrow_PORTALで許可した状態だけを公開する。
- 標準runtimeを可能な限りGoで構成し、Ubuntu、Windows、macOSで同じmodule contractと失敗時挙動を提供する。

## No-Human-GateとReject再考

RenCrow runtimeは人の判断待ちを作らない。Agent、workflow、API、DBのどの層にも、人の返答で解除する
待機status、grant、reference、queueを置かない。CORE正本、machine-readable policy、認証済みrequest
scopeをそのrequest内で同期評価し、条件を満たす処理は直ちに実行し、案が不適合なら`rejected`、
実行不能または越えられない境界なら理由付きで`blocked`にする。この原則を`No-Human-Gate`と呼ぶ。

`rejected`は作業終了を意味しない。Agentはreject理由と証拠を読み、失敗した前提を特定し、入力、証拠、
分解、route、Tool、設計、必要なら当初の思想まで再考して新revisionを作り、同じ検証を最初から通す。
利用者から新しい発話を受けた場合も、それを待機中artifactへの判子ではなく、新しい目的、制約、事実として扱う。

Codexがrepository、runtime、host、外部systemを変更する権限境界はRenCrow製品契約とは別である。
Codexはユーザーの明示指示を必要とするが、その規則をRenCrow runtimeの人待ちworkflowへ変換しない。

## 世界の主体

RenCrowの世界で行為の主体になるのは、認証されたユーザーとCOREが管理するAgentです。
Mio、Shiro、Kuro、MidoriはAgent identityです。LLM、Model、provider、Agent Runtime、
Execution Role、Controller、Brain adapterはAgentが判断・実行するための機構であり、
それ自体を人格や主体として扱いません。

本番の会話、作業、ゲームプレイはユーザーまたは実Agentへ帰属させます。
`RuleBasedBrain`と`DummyBrain`はunit／integration test、決定論simulation、
local observer確認には使用できますが、Agent identity、Persona、Memory、経験を名乗らず、
Agent E2Eの代替にはしません。

## CORE が所有する範囲

- RenCrow_ASSISTANT、RenCrow_PORTAL、Debug Viewer、LINE、Slack、Discord、Telegramなどの入力契約
- Mio による通常メッセージの route decision と明示 command の優先
- Agent、Agent Registry、Advisor、Tool の契約と責務境界
- Persona、会話履歴、RecallPack、Knowledge Relation、trace
- side effect 前の同期policy判定と監査記録
- Workstream、Backlog、Scheduler、Heartbeat、Economic Objective
- Viewer REST/SSE と外部 module の状態 projection

## 標準配布

標準installerが導入するruntimeはGo binary、設定、必要なbrowser assetです。利用者hostへ
Python／Node.js／WSLを必須導入しません。LLM／STT／TTS／Vision／Imageの演算backend、Model、
weights、GPU runtimeは外部computeとして別に用意します。Browser Actor、Webwright、
`rencrow-data`、映画カタログCrawlerはoptional capabilityであり、未配置時は
`disabled`または`unavailable`として扱います。詳細と対象artifactは
`04_アーキテクチャ概要.md`の「標準Go配布境界」を正本とします。

## Snapshot repository

RenCrow_Workspaceは外部runtime moduleやserviceではありません。
稼働中RenCrowを別machineへ再構成するMigration Snapshot契約と、実行時の正本である
`~/.rencrow/workspace`等から取得したportable non-secret Git snapshotを所有します。COREは実行時に
RenCrow_Workspaceのcheckoutへ接続しません。Config、durable State、secret実値を移行する場合、
Stateは所有moduleの整合性あるexport、secretはsource host上で暗号化したMigration Artifactとして
扱い、平文secret、稼働中DBの単純copy、通常log、cacheをGitへ保存しません。詳細は
[RenCrow Migration Snapshot仕様](https://github.com/Nyukimin/RenCrow_Workspace/blob/main/docs/01_RenCrow_Migration_Snapshot仕様.md)
を正本とします。

CORE は意味route、Agent、AgentからExecution Roleへの割当、Persona、Memory、Recall、
Tool policy、外部providerへ入力を送信してよいかの判断を所有します。LLM実行時は
RenCrow LLM Gatewayの単一URLと論理execution aliasだけを使い、RenCrow LLM Runtime、
物理Model、Backend URL、port、commandを選択しません。外部 module が未起動でも
CORE の実装欠落とは
限らず、利用時には明示的な unavailable/degraded として扱います。

COREはModel、provider、Backend、decoder、chat template、token、stop条件、生成時の
装飾形式を知りません。COREからRenCrow_LLMへ渡す要求はユーザーのChat入力と同等の
論理messageであり、RenCrow_LLMはユーザーがChatで受け取るのと同等のモデル非依存な
assistant出力をCOREへ返します。モデル固有形式の吸収と応答正規化はRenCrow_LLMが所有し、
COREはAgent／Game等のdomain contractだけを検証します。詳細は
`04_アーキテクチャ概要.md`の「CORE / RenCrow_LLM Chat境界」を正本とします。

Mio、Shiro、Midori、Kuroは同じAgent管理単位である。利用する推論実体がローカルModel、
外部API、Codex等のAgent Runtimeのいずれであっても、Agentの人格、会話、Memory、
実行policy境界はCOREに残る。Agentと推論targetの間にはChat、ChatWorker、Worker、Wild、
HeavyのExecution Roleを置く。特にKuroはCodexそのものではなく、Heavy Roleの現在の
targetとしてCodex subscription runtimeを利用するAgentである。

ASSISTANTの生活Routine schedulerとCOREのWorkstream、Scheduler、Heartbeatは別責務です。目覚まし、予定、天気、交通、ニュースの利用者別選定・定型配信・既読・deliveryはASSISTANTが所有し、複数工程、生成、継続監視、policy判定を伴うside effectはCORE Taskへ移譲します。ニュースの事実情報を収集・整形した共有`DailyNewsBrief`はCOREのNewsBrief境界で提供し、ASSISTANTとChatが同じ準備済みデータを読み取ります。各moduleが同じニュースを恒久的に重複取得しません。

PORTAL、CMD、ASSISTANTはCOREの周囲に置く兄弟moduleです。Chat、IdleChat、Games、
recipient、event、session、audio、Task、errorの意味はCORE Public APIを基準に揃えますが、
PORTALはWeb、CMDはterminal、ASSISTANTはproactive triggerとDevice deliveryを固有差と
します。ASSISTANTだけはpersonal／family／Routine／delivery状態を所有する常駐serviceで、
COREはASSISTANTを必須依存にしません。
